## 一、加时（Overtime）

### 1.1 触发 —— 原版代码只有一个判定点

`BattleManager.<NextTurn>d__395.MoveNext`
（`d:/2/Warpforge_tools/data/decomp_il2cpp_0827/decomp_out2/BattleManager._NextTurn_d__395__MoveNext.c`）：

```
:164-181  turnCounter 自增（判定用的是自增后的值）
:191-193  matchData.GameplayData.overtimeTurn 取出（Nullable<int>，两处空引用检查）
:194      if (!IsOvertime)
:205      if (turnCounter >= overtimeTurn)
:206          IsOvertime = true;                       // 字段偏移 +0x258（= +600）
:209          BattleHud.Instance.DisplayOvertime();
```

- `IsOvertime` 是 `BattleManager` 的 **private set** 属性（`BattleManager.cs:4719`）
  ⇒ **全盘唯一写入点就是这里**（`decomp_out` 1800 + `decomp_out2` 224 个方法体都搜过）。
- **每回合开始判一次；置 true 之后不再判**（`:194` 那道闸）。
- 🔴 **与回合时钟没有任何关系。** 这一段里**一个 `ClockManager` 调用都没有**；
  `ClockManager.StartTimer` 在 `_NextTurn:430` 的 `if (yourTurn)` **常规回合起钟**分支里，
  与 `IsOvertime` 无数据依赖。
  ⚠️ `资料/战斗规格/战斗重建_0827/子代理读报_csharp行为_0827.md:208` 那句
  「超时后再超 → `BattleHud.DisplayOvertime()`」**是错的** ——
  `DisplayOvertime` 全盘只有 `_NextTurn:209` 一个调用点（`BattleHud__DisplayOvertime.c` 只转发给 `OvertimeUi`）。

### 1.2 效果 —— 原版代码只做「多抽一张」

`decomp_out2/BattleManager__TurnStartCardDraw.c:35-65`：

```c
/* 常规：抽 GameplayData.drawCardsPerTurn 次 */
for (i = 0; i < *(int *)(gameplayData + 0x3c); i++) AddDrawCard(...);
/* 加时：再多抽 1 张 */
if (*(char *)(battleManager + 600) == '\0') return;   /* if (!IsOvertime) return; */
AddDrawCard(...);
```

⇒ **经典模式：加时 = 每回合起手多抽 1 张**（常规 1 + 加时 1 = 抽 2 张）。

🔴 **加时不动能量。** `GameplayVariablesData` 里**根本没有** `overtimeMana` / `overtimeDraw` 这类字段 ——
它那一族只有 `drawCardsPerTurn(0x3c)` · `manaAccumulation(0x40)` · `startingMana(0x2c)` ·
`manaPerTurn(0x38)` · `addedManaSecond(0x34)` · `handLimit(0x44)`。

### 1.3 两个模式口径不同（**用户 2026-09-16 指出**）

| 模式 | 加时效果 | 出处 |

`:137` 的「每回合 +2 能量直至游戏结束」落在**遭遇模式**。

### 2.7c 🆕 2026-09-26：**防御卡到底怎么来的**（用户点名要查；两路子代理并行查全量反编译，结论互相印证）

> **问题**：遭遇模式（Skirmish）**有没有防御卡？如果有，是不是玩家自己挑的？**
> 官方文案 `Random Defence card` 看上去像「系统随机给」，而粉丝规则书说卡组里就是「1 督军 + 1 防御卡 + N 张」。
>
> **判决**：**两边都对，因为它们是两件事** ——
> **①「卡组里那一格」只能由玩家在编辑器里点选**（全量反编译里**没有任何**随机/自动往里写的代码）；
> **②「开局发给后手的那张」是随机的**，而且**卡组里挑了就优先用你挑的那张**。

**① 卡组防御位 `CardDeck.defensiveCard`（+0x48）的全部写点**（逐个读过函数体，不是按文件名）：

| 写点 | 写的是什么 | 出处 |
|---|---|---|
| `DeckBasicSetup`（唯一的多字段构造点） | 由调用方给：`.ctor` 给 **null** · `GetEmptyDeck` 给 **null** · **`DeserializeDeckString` 给卡组串里那张** · `CopyDeck` 给源卡组的 | `CardDeck__DeckBasicSetup.c:42`；四个调用者见 `CardDeck__.ctor.c:23` · `GetEmptyDeck.c:27,30` · `DeserializeDeckString.c:129` · `CopyDeck.c:15-17` |
| 🔴 **`TryAddCard`（内联写）** | **卡是 `Tactic + DefensiveCard` 且 `CanAddDefensive()` 通过 ⇒ 写进去** —— 这是**玩家挑卡的唯一入口** | `CardDeck__TryAddCard.c:16-23`，调用者 `DeckEditingPanel__AddCard.c:45-56` |
| 清空 | `RemoveCard` / `RemoveCardFromDeck` / `GetEmptyDeck` 置 0 | `CardDeck__RemoveCard.c:23-24` · `DeckUtility__RemoveCardFromDeck.c:36-37` |

- ⛔ **`AddDefensiveCard` / `TryAddDefensive` 是死代码**（全库唯一的 "call" 命中是 ICF 折叠出来的 `InventoryManager.SetRawInventory` 假阳性）；`DeckUtility.HasDefensiveCards` 也**没有调用者**。
- ⛔ **`FixSkirmishDeck` / `ProcessSkirmishDecksToUpload` 只【读】+0x48 再上传**（组 `AzureDeckInfo` 时读 `defensiveCard.uniqueId`，**没有就填空**）—— 它们**不写**，更不随机。
  ⇒ 「名字像」差点骗过去：那个方法名是「修冲突卡组」，实际修的是**上传列表**，不是卡组内容。

**② 那句 `Random Defence card` 说的是【战前发放】，不是【组卡】**：

- `BattleManager.AddGoesSecondCardToDeck.c:145-184`：`GetEnvEffectCards`（**防御卡池**）→ `MatchData.GetRandomInt` **随机抽一张** → `AddNewCardToHand` ⇒ **发给「后手那一方」的，进的是手牌**。
- 🔴 **`:154-166`：如果玩家自己的 `DeckAndWarlordData.defensiveCard(+0x20)` 非空，随机那张会被【卡组那张】覆盖** ⇒ 随机只在「卡组没挑防御卡」时生效。
- 这与**规则书** `:105-121` 完全对得上：防御卡 = **后手（防守方）**可打出的战术；战前准备第 6 步「先手取得进攻卡（Offense）；**后手取得防御卡（抽牌后置入起手牌）**」。
  ⇒ 官方文案那句与它并列的 `No Offence card` 也是**发放规则**（原版先手不发进攻卡）—— **两者同族，都不在讲组卡**。
- ⚠️ **一条没查透**：那个随机分支的门槛写着 `matchType ∈ {50,80,110,120}`（PracticeOffline / EventAI / ClosedDeck / ClosedDeckBot），
  **FastMode(200/210/211) 不在内**（`[推测]`，receiver 是经 `PlayerDataManager+0x20 = matchData` 推出来的）⇒
  **遭遇模式那条路是不是同一个函数发的防御卡，没坐实**（要么另有一条，要么 FastMode 走 bot 退路时 matchType 变了）。

**③ 顺带查实：原版【完全不校验】防御卡。**

- `DeckUtility.ValidateDeck(deck, out err, bool validateOwnership)` 的第三参**只控制一条分支**（库存归属，`:16-17` → 不通过则 `err=1 CardsNotOwned`）；
  主干校验 = 督军 / 督军阵营 / 禁卡 / 逐卡（阵营 · `cardType∈{Minion,Tactic}` · `inventoryOptions==0` · 禁卡 · 同名上限） / **张数**。
- 🔴 **`ValidateDeck` / `ValidateDeckCards` / `ValidateDeckOwnership` / `ValidateDeckWarlord` 四个方法体里都不出现 `0x48`**
  ⇒ **「恰好 1 张防御卡」不是原版的要求，0 张合法**。`SkirmishEventWindow` 那道闸门（`HasValidDeckWithValidationMessage`）
  也只是 `ValidateDeck(...,true)` + `DeckError` 那 6 个取值 —— **没有「缺防御卡」这一项，不会拦人**。
- 12 个调用点**全部传 `true`**，没有传 false 的。

**✅ 对我们的影响（结论）· ✅ 2026-09-26 已落地**：

1. **编辑器卡池必须能列出防御卡**（否则玩家**永远**挑不到、卡组那一格永远是空）—— 判据是**代码路径**：

   `DeckRules.Validate` 原来要求**恰好 1 张**（比原版严），现在**只在「带了一张但不是防御卡」时报错**，

### 2.7b 🔴 同日订正：`assignDefensiveCardsInEditMode` 的**判据方向原来记反了**
