## ⑤ 顺手发现（**只报，没改**）

1. 🔴🔴 **原版那个 `ScrollRect` 是「摆设」**（判据见 §①-1 与 §③）：
   内容矩形高 300 < 视口高 521.5 ⇒ UGUI 判「不可滚」（`AdjustBounds` 的注释原文：
   *Scrolling is only possible when content is larger than view*）。
   ⇒ **A168 与本简报的「67.34 滚动范围」在原版并不存在**；`GfxScrollRange` 是我们**为了能用**补的。
2. 🔴 **原版行是紧凑排，我们摆的是带空格位的格位号**（`Vsync 5 / FPS 6`，应为 `4 / 5`，
   若 `Hi FPS` 也被关则是 `3 / 4`）。差 **80.64 px/行**。判据 = 序列化行位 + `rectChildren` 不收 inactive。
   ⚠️ **第 0 行（Small Screen UI）不受影响**（它在哪个模型里都是第一格）⇒ **A165 那节断言不用动**。
3. ✅ **A168 报告 §没查清 ① 有答案了**：`GraphicsTab__OnSetup` 结尾那个 vtable 调用**就是
   `Slider.SetValueWithoutNotify`** —— 反编译里那一句是
   `(**(code **)(*plVar6 + 0x438))(plVar6, GameStaticData_inst, *(+0x440))`，`plVar6` = `fpsLimit`(+0x70)、
   槽位 `0x438` = `Slider.SetValueWithoutNotify(float)`；第二个实参反编译器写成了**类实例指针**（该是它的
   `+0x128` 那个 `int` 字段）⇒ 值与 A168 的推断一致（开窗只摆值、不写帧率）。
   （顺带坐实：那段链式 `SetActive` 里 `fpsLimit.transform.parent` = `FPS Limit` 那一行，
   `title/gameObject` 与 `FPS Slider` 的父节点是同一个 ⇒ 原版确实是「整行一起开关」。）
4. ⚠️ **「拖滑块」与「滚列」在原版是有分工的，我们这套没有**：原版 `Slider` 自己吃 `IDragHandler`，
   事件不会冒泡到 `ScrollRect`；我们这里由 `PointerLayer` 按 10px 阈值判（它不认识滑块）⇒ **拖滑块会顺手滚列**。
   本件在白名单内兜了一层（`_fpsDragging` 期间 `MenuScroll.Stop()`），**正解在共用件**
   （`PointerLayer` 支持「按钮吃掉拖拽」，或给 `MenuScroll` 一个 `NoDrag` 开关）—— **两件都不在本件白名单**。
5. ⚠️ **`MenuScroll` 没有逐处的滚轮敏感度**（全壳一个 `NotchK = 0.4`，原版这一处是 `m_ScrollSensitivity 1`、
   别处 10/50/100）⇒ 要照原版得给 `MenuScroll` 加形参（共用件，白名单外）。
6. ℹ️ **`ChkRowStep = 80.6` 是近似值**（原版行高 75.641 + spacing 5 = **80.641**）：本件沿用（没动这个常量），
   代价 = 第 6 行比原版**高 0.24 px**（916.10 vs 916.34）。要精确就一起把 `ChkRowH` 改成 75.641
   （那会动 A165 那条已绿的断言）⇒ 建议**并进 §① 那条后续件**里一次做完。
7. ℹ️ **`Scroll View` 的 `m_Horizontal = 1`**（原版横轴也开着）：我们只做纵向（`MenuScroll.Vertical`）。
   横向本来也没得滚（内容宽 455 < 视口宽 963），**零可见差**，但结构上少一档。

## ③ 行位回正（判据 + 新期望值）

判据 = 审查 §③（VA 反汇编 + `QualityDefinition.allowSuperSampling` 五档表）：

| 画质 | 运行时可见行（0 起） | Vsync | FPS Limit | 内容高（设计 px） |
|---|---|---|---|---|

我们照 **VeryLow–High** 落（依据：`GameStaticData__.cctor` 写 `+0x120 = 3` = **High** ⇒ 出货默认档就是 4 行那一档）。
行顶（设计 px）：`432.50 / 513.141 / 593.782 / 674.423`；画布 px 里 FPS 行轨道 = `[842.57,736.76]–[1284.63,748.46]`、手柄底沿 `758.54`。

## ④ `Use super sampling` 为什么**不建**（停在方案，等口径）

1. **没有能力**：我们没有任何超采样开关（URP `m_MSAA 1` / `m_RenderScale` 谁都不受设置控制）⇒ 建了就是**假开关**；
2. **没有「哪档允许」那张表**：原版是 `QualityDefinition.allowSuperSampling`（五档 0/0/0/0/1），我们的 `Mobile/PC` 与原版 `VeryLow…Ultra` **没有对应关系** ⇒ 把 `PC` 当 `Ultra` 就是「自己发明一套画质系统」。
**方案（将来做时照这个落）**：① 先有一个真的超采样开关（最省事 = 把 `URP Asset.m_MSAA` 或 `renderScale` 接到设置项上）；② 再定「我们哪一档算 Ultra」；③ 那一行插在 **index 2**，`VsyncRow/FpsRow` 整体 +1（3/4），`GfxContentH` 换 **508.205**（代码注释里已写死这三步）。

## ⑤ `Auto Zoom` 建成什么样（**诚实申报**）

- 形状照原版：`GraphicsTab__AutoZoomClick` **同时**写 `autoZoom`(+0x125) 与 `autoZoomChosenManually`(+0x12f) —— 我们落成 `AutoZoom` 静态类（`Enabled` / `ChosenManually`）；标签照原版 TMP 原文 `'Auto zoom'`。
- 🔴 **我们还没有那个消费者**：原版这一格喂的是**战斗相机的自动缩放**（`BattleSettingsWindow__OnAutoZoomChanged` → `CombatAutoZoom.ResetCameraZoomUIAction`），我们**没做 `CombatAutoZoom`**（全仓 grep 零命中）⇒ 点它**只记值、不产生效果**，所以点击处理里加了 `Debug.LogWarning` 明说这一点（红线：不许让玩家以为它有作用）。
- **口径请裁**：这一格现在等于「一个没有消费者的真开关」。要么后续把 `CombatAutoZoom` 做出来（真复刻），要么按「不做假开关」把它撤掉 —— **两条路我都没走，按简报建了**。
