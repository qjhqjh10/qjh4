## 一 · 逐条细节

### 1 · 触发层 `PerCount` 增量型

**问题**：`EffectResolver.cs:6476-6498` 在触发路对 `PerCount > 0 ∧ verb ∉ {deal,heal}` 打一条 `trigger-repeat-percount` 提示、`opRepeats` 保持 1。
**现况（亲读）**：`PerCount` 只有 `EffectText.cs:4487`（追加型 `…, and an additional N for each X`）会置；
出牌路 `EffectResolver.cs:496-533` 做 `eff = Amount + n * PerCount`、`ScalePayload(...)`、递副本；
`ResolveOne/ResolveOneCore` **完全不读 `PerCount`** ⇒ 触发路递下去的是**原样的 op**（`Amount` = 基础值）。
⇒ **触发路不是「不重复」，而是「增量被整条丢掉」**（`give/gain/lose` 只剩基础值）。

**原版口径（增量，三层证据）**

1. `AbilityLogic.multiplier`（`AbilityLogic.cs:20-21`，Tooltip 原文 *"If different than 'Any', multiply by number of targets meeting criteria"*）
   → `PlayAbility.c:181-236` 算 `local_178`（`GetTargets(...).Count`；`ta∈{210,220}` 改成 traits 累加；最后 `if (0 < furtherMultiplier) local_178 *= furtherMultiplier`）。
2. 伤害族：`case 10/13`（`:1461-1508`）= **一个** `DamageInfo` → `DealMultiDamage(manager, dmgInfo, targets, …)` **一次**；
   倍率经 `GetValueFromCriteria(..., multiplierFactor)` 进**数值**。对比 `case 12 doDamageMultiRandom`（`:1511-1530`）
   = `if (0 < local_178) do { GetTargets…; GetValueFromCriteria…; DealMultiDamage… } while` —— **这才是「跑 N 遍」**。
3. 增益族：`AdjustCardEffect`（`AbilityLogic__AdjustCardEffect.c:14-50`）只对 buff 五格调 `NewBuffStat`；
   `NewBuffStat.c:61-67` `Normal` ⇒ `change × multiplier`；`:207-232` `200/201/202/203`
   ⇒ `计数 × (change × multiplier)`。数据实证 `BL43`：**两条 logic**，第二条 `meleeAttackValueOptions = 201`
   ⇒ 基础 +2（第一条）＋ `Dark Pact 数 × 2`（第二条）。
   伤害/治疗的计数型 `valueOptions` 走 `GetValueFromCriteria.c:116`（`80` = `min + max×multiplier`）、
   `:278-330`（`200/201/202/203/210`）。

**今天可达性（实测）**：加法型（`an additional/plus … for each`）全池 **4 张**：
`BL43` / `BL47` / `GOF74` / `8f2da55… Alpha Warrior`，`abilityTriggers` **全是 `[0]`**（出牌路）⇒ 触发路**0 张可达**。

**建议**：把 `:496-533` 抽成 `TryFoldPerCount(ctx, owner, source, by, op, chosen, sourceCard, out EffectOp effOp)`
（含 `TryStructuredMultiplier` 的数据优先闸），出牌路与触发路都调它；触发路删掉 `percount` 那条 skip。
⚠️ `died` 那一档（`CountScope=="died"`）**保持现状**（触发本身就是那次死亡，再乘就是平方；`AM34`/`TL46` 的
`multiCountCriteria.ta=0` 也证不重复）。

### 2 · `ta=200/201` 的手牌战术卡载体

**原版读侧**（`AbilityLogic__GetTargets.c`）

| ta | 值 | 行为 | 行 |
|---|---|---|---|
| 200 | `referencedCardInThisCard` | `AddRange(thisCard.referencedCards)`，然后 `goto LAB_180818466→474→485` = **直接 return** | `:770-781` |
| 201 | `referencedInPlayCardInThisCard` | 遍历同一张表，只加 `CardScript.IsInPlay(card)` 的；同样**直接 return** | `:784-806` |

⇒ **`targetCriteria` 的其它字段（friendly/enemy/include*/rarity/conditions）与 `maxTargets` 对 200/201 一律不生效**
（过滤循环在 `:1085-1130`，`maxTargets` 的 `Take` 在 `:1364`，两条都在这两次 `return` 之后）。
**`FilterMethods.CheckIfMeetsCriteria` 那半 ⇒ 不用接**（它虽然也认 `ta=200/201`，见 `:80-117`，但 200/201 根本走不到过滤循环）。

**写侧**：唯一写手 = `AbilityEffect.setReferenceCard = 380`（`AbilityEffect.cs:67`），
`PlayAbility.c:2128-2160`：`lVar11 = *(longlong*)(param_3 + 0x10)` = `abilityData.thisCard`
（字段序判据 = `AbilityData__SetNewData.c`：`+0x10 thisCard` / `+0x18 actingCard` / `+0x20 targetCard` / `+0x28 baseEnchantmentCard` / `+0x30 isPlayerTurn` / `+0x38 damageInfo` / `+0x40,0x41 whileInPlay(,Variable)` / `+0x44 priority` / `+0x48 blockPlayerActions`）⇒
`thisCard.referencedCards = new List(); AddRange(本条 logic 的 targets)`，
**然后该条 logic 自己的效果（buff/summon/damage）照常结算**（同一条 entry，不是单独的「只写表」动作）。

**现池谁用**：`ta∈{200,201}` 的只有 2 张（程序化扫 `cards_engine.json` 的 `abilityTargets`/`activeAbilityLogic`）：

| 卡 | 行 | 说明 | 载体要求 |
|---|---|---|---|
| `AM54 At All Costs` | 出牌块 entry2 = 380（`ta=150 previousAbilityTargets` + `buff{costChange:-3}`）· 触发 410（`abilityContext=50 InPlayOrCemetery`）entry = `ta=200` + `buff{costChange:-4}` | 「抽 3 张；若督军 ≤10 血，**给这 3 张降 4 费**」⇒ 引用表装的是**手里那 3 张牌** | **跨区域**（手牌） |
| `GOF93 Hunta Rig` | 出牌块 entry2 = 380（`ta=150` + `summon{isForEnemy:1}`）· 触发 410 entry = `ca=235` + `ta=201` + `maxTargets:1` | 「把敌方手里一个部队部署出来，本部队攻击它」⇒ 引用表装的是**刚部署到场的那个单位** | 场上（现有模型够） |

⇒ **载体结论：`CardScript.referencedCards` 是「运行时卡对象」列表，可跨区域**。
我们 `Core/UnitState.cs:674` 的 `readonly List<UnitState> ReferencedCards`
（`RuleCore.SetReferenceCards` 写、`ResolveTargets` 读）**只能表达 201 的那一半**；
`AM54` 那种「引用手牌」今天结构上装不下 —— `ResolveTargets` 里已经如实出声（`EffectResolver.cs:1330-1340`）。

**顺手发现（要改的地方，本代理不改）**：
`RuleCore.SetReferenceCards` 的 doc 与运行时日志写着
「原版 `PlayAbility.c:2139` 写的是 `actingCard + 0x278`」（`EffectResolver.cs:1268-1270`）——
**写错了**：`:2139` 用的是 `abilityData+0x10`，那个字段是 **`thisCard`（能力所属的那张牌）**，不是 `actingCard(+0x18)`。

### 3 · `AM22` 的 `chooseone` 分支

**原版没有 `chooseone` 这个 op**：`AbilityEffect.cs`（全文 130+ 项）grep `choose` **零命中**；
`CardAbility.randomAbilityChoice`（`CardAbility.cs:24-25`，*"If true, only one ability triggered, chosen randomly"*）
才是「随机抽一条」。`AM22` 用的**不是**它 —— 它 `randomAbilityChoice` 缺省（=false）。

**真形状**（`cards_truth.json` `AM22.activeAbility`，亲读）：

```jsonc
targeted: 1,
targetCriteria: { targetsAffected: 10, friendlyUnits: 1, enemyUnits: 1, includeHero: 1, includeMinions: 1 },  // 玩家可选任一方单位
logic: [
  { chosenAbility: 10 /*doDamage*/, targetCriteria: { targetsAffected: 90, enemyUnits: 1, … },
    damage: { minDamage: 2, maxDamage: 3, damageType: 5, valueOptions: 90 /*RandomizedOnResolution*/ } },
  { chosenAbility: 30 /*buffOthers*/, targetCriteria: { targetsAffected: 90, friendlyUnits: 1, … },
    damage: { …同上（该条不读，见下）… }, buff: { buffType: 3, trait: 80 /*shield*/ } }
]
```

- `ta=90 targetIfMeetsCriteria`：候选**恒为 `targetCard` 那一个**（`GetTargets.c:747-757`），
  再由 `FilterMethods.CheckIfMeetsCriteria` 用该条自己的 criteria 过筛 ⇒ 点敌人 ⇒ 第①条有目标、第②条空；
  点友军 ⇒ 反过来。**这就是「二选一」的全部机制**，没有额外的选择状态。
- 入口：`RawCardScript__ResolveActiveAbility.c:19-31` 选能力对象 → `:56-67` `SetNewData(thisCard, actingCard, targetCard=玩家选的那张, …)`
  → 逐行 `PlayAbility(…, 400 /*ThisUnitAbilityUsed*/)`。⇒ 玩家目标 = `targetCard`，一行都不少跑。
- 第②条的 `damage` 块**不参与**：`buffOthers` 只走 `AdjustCardEffect`→`NewBuffStat`，只读 `CardEffect` 五格
  （`AbilityLogic__AdjustCardEffect.c:14-50`，buffType 白名单 `1,2,3,10,70,85,90,95` 含 `3`）。
  这是 SO 序列化的残留值，⛔ 别拿它当「还要造成 2-3 伤害」。

**我们今天的形状**：`cards_engine.json` 的 `AM22.activeAbilityLogic` =
`{"ta":[90,90],"fm":[0,0],"ca":[10,30],"pa":[0,0],"dmg":[…, …]}` —— 数据侧**完整**，缺的是消费侧
（E1 的 `AttachByAbilityKind` 因为「一条 op 盖两分支」落 `gap:kind-no-op`）。
另：`activeAbility.targetCriteria`（对象级、玩家可选面）**我们没有这一列**。

### 4 · `SOR13` 的「op Target ↔ ta」二级匹配

`cards_truth.json` `SOR13.activeAbility.logic`（亲读）：

| 行 | chosenAbility | targetCriteria | 关键附加 | 对应卡面 |
|---|---|---|---|---|
| 0 | 30 buffOthers | `ta=10` + `friendlyUnits` + `includeMinions` + `includeSelf` | `furtherMultiplier=1`、**无** `untilEndOfTurn` | `to your troops`（永久） |
| 1 | 30 buffOthers | `ta=120` + `friendlyUnits` + `includeHero` | `furtherMultiplier=1`、`buff.untilEndOfTurn=1` | `to your Warlord **this turn**` |
| 2 | 462 `triggerPray` | `ta=20` self + enemy… | —— | `Duty:` 关键词本身（不参与配 op） |

**为什么判据成立（不靠猜）**：
- `ta=10 allFiltered` 与 `ta=120 friendlyHero` 是**两个不同集合**，反编译各有独立分支
  （`GetTargets.c:721-737` 的 120 = `BattleManager.GetHero(manager, thisCard.owner)`，即**施放方督军**；10 = 己方全体+includeSelf 过滤）。
- 我们的 op 已经带目标短语的分类：`EffectTargetSpec{Raw, Side, Kind, Count, …}`，`Kind` 明写含
  `warlord` / `troop`（`EffectText.cs:850-862`）⇒ `Kind=warlord → 120`，`Kind∈{troop,unit} → 10`。
- 更强的第二判别：`buff.untilEndOfTurn`（行 1 = 1、行 0 = 0）↔ 卡面 `this turn` 只出现在后半句。

**建议**：`CardDef.AttachByAbilityKind` 在「族内所有行 (ta,fm) 相同」这道闸失败时，加一道
**`(taFromTargetKind, untilEndOfTurn)` 唯一命中**的二级匹配；命中数 ≠ 1 ⇒ 仍留 `-1` + `gap:kind-ambiguous`。
⛔ 不要退化成「按第 j 行配第 j 条 op」（`AM23` 1 op / 2 行已证伪，见 `EffectText.cs:2260-2275` 的 doc）。

## 二 · 顺手发现（只报不改）

1. 🔴 **`SetReferenceCards` 的判据文案写错字段**（见 §一·2 末）：日志/注释说「写的是 `actingCard + 0x278`」，
   原版 `PlayAbility.c:2139` 是 `abilityData.thisCard`（`+0x10`）。→ 按铁律 5 应就地订正；
   同时确认我们的 `acting` 形参在触发路上确实传的是「能力所属那张牌」。
2. 🟡 **卡表缺 `abilityContext` 列**（E1 的 v24 表没有）。全池 **17 条 Hand 上下文**（清单见 §一·5）
   今天与 Play 上下文**不可区分**。其中 4 条是降费（已被别的路覆盖），另 13 条里至少
   `Jammed Communications`（10 OtherCardPlayed，对己方督军 1 伤）· `Poisoned Supplies`（40 TurnEnd，己方部队 1 伤）·
   `Abaddon's Chosen`（30 TurnStart，召唤 `BL37`）· `Cult Propaganda`（40 TurnEnd，给敌方造牌）
   是**手牌里的真行为**，我们是否漏触发**没逐个验**（只验了 4 条降费）⇒ 建议另立账。
3. 🟡 **`unitConditions` 里 `role` 有两种拼法**：`"multi"`（`AM18`，带 `multiSet`）vs `"mult"`
   （`AM44`/`BL40`/`GOF74`，带 `multiplierSet`）—— 它们对应原版**两个不同字段**
   （`CardAbility.multiCountCriteria` = 整条 ability 触发 N 遍；`AbilityLogic.multiplier` = 本条 logic 的数值倍率）。
   形状不同是**对的**，但只差一个字母，⛔ 消费端别把两者混用。
4. 🟢 `AM22` 第②条 logic 的 `damage` 块是**死值**（`buffOthers` 不读）—— 将来做数据校验时别把它当第二个效果。
5. 🟢 `ta=200/201` **不吃 `maxTargets`**（`GOF93` 那条写着 `maxTargets:1`，实际整表返回）；
   同理不吃 friendly/enemy/include* 过滤。我们现在的实现（`EffectResolver.cs:1324-1357`）也对，
