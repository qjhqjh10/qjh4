## 口径（出处 `资料/规则书/Warpforge_Offline_Rulebook_1_5-3_中文翻译.md`）
- 规模：经典模式 = 1 督军 + 1 防御卡 + **30** 张阵营卡（:43）；遭遇 Skirmish = 1 督军 + 1 防御卡 + **12** 张（:55）。
  `decklists.json` 里 `gameMode==13` 的 106 副就是遭遇模式 —— **「30 张够不够」要分模式判**，别一律按 30。
- 同名上限：经典 普通/稀有/史诗 ≤2、**传说 ≤1**；遭遇另加 **传说 ≤4**（:49/:60）。
- 卡组里那一张防御卡**不在 `cardIds` 里**（210/236 副的 cardIds 一张防御卡都没有），规则书 :43 的 32 张 = 督军 + 防御 + 30。

## 🆕 为什么「拼不齐」—— 根因是 **id 对照表的口径**，不是卡池缺卡（2026-09-24 查）

**一句话**：卡一张不少（**1126 = PnP 1126，双射零剩余**），拼不齐是因为**预组牌用原版 id 写的**
（`UM15` / `GOF65`），而「**原版 id → 卡名**」这张表本身有洞。

**链条**：

1. 卡池的 `id` 有**两套**（都是 `工具/gen_cards_engine.py` 给的）：数字式 `UM83`（查 `数据/游戏数据/card_ids.json` 得来）·
   名字式 `UM_Lieutenant_Titus`（**我们自造的 slug，共 153 张**，`gen_cards_engine.py:506-508`）
   —— **后者正是「查不到号」的产物**（`:511-532 pick_id`：挑不出唯一号就**不猜**）。
2. `card_ids.json` 是 **2026-08-17 自建**的，口径写在自己的 `note` 里：「**PnP 卡表编号 = 游戏卡 ID，偏移 0**」。
3. 🔴 **这条假设有一半是错的**：实测 **UM / TAU 第二批 = PnP 文件号 +64** · **GOF / DA 第二批 = +74**
   （Core 批才是偏移 0），用已知组反验证约 170 组、100% 命中。
   ⇒ 按「偏移 0」建表 ⇒ **一批卡被记到了别的号上，另一批号就空着**。
   实据：`Ultramarines/3部队/Warpforge_19_1st-Company-Terminator.png` 被记成 `UM83`（=19+64），`UM19` 就空着；
   UM 的 PnP 编号只到 67，而池内编号到 101。
