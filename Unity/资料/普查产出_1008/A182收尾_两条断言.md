### 1·2 改后长什么样

`:3745-3805` 那一段整体重写（注释 + 断言）。量的东西换成 **`BG` 的渲染左沿**，期望值写**原版常量算出来的表达式**：

```csharp
if (ds.entries.Count > DailyData.StreakCollected + 1)
{
    float bx1, by1, bx2, by2, nx1, ny1, nx2, ny2;
    bool okB = RectOfUnion(FindChild(ds.entries[DailyData.StreakCollected], "BG"),     out bx1, out by1, out bx2, out by2);
    bool okN = RectOfUnion(FindChild(ds.entries[DailyData.StreakCollected + 1], "BG"), out nx1, out ny1, out nx2, out ny2);
    CheckTrue(okB && okN, "两格的 `BG` 都量得到渲染矩形（…压在视口右沿 ⇒ 量到的是被裁过的那一块）");
    if (okB) CheckNear(bx1, 1770.988f - (1770.988f - 1595.64f) * 1.2f, 0.5f, "…左沿 = 1560.57 …");
    if (okN) CheckNear(nx1, 2f + 6f * 315.816f + 14.56f,                    0.5f, "…邻格 1911.46，**没有被放大** …");
}
```

- **为什么左沿是干净的量**：`BG` 那条路 `keepAspect = false` ⇒ quad 矩形**逐字段等于原版 `E_Bg`**；
  左沿在视口内（> 0），右沿被 1920 裁、顶沿被 159.33 裁，**只有左沿两边都没被碰**。
  软边那条带（`1831..1920`）对第 7 格是**只改四角 alpha、不改几何**（第 6 格的左沿在带外）。
- **期望值表达式逐项**：`pad.L 2` + `5 × 步长 315.816` + `E_Bg.x1 14.56` = 未缩放左沿 **1595.64**；
  格心 `2 + 5×315.816 + 379.816/2` = **1770.988**；绕格心 ×1.2 ⇒ **1560.57**。
  邻格 = `2 + 6×315.816 + 14.56` = **1911.46**。⛔ 全部写**字面量**（不调 `DailyStreakPopup.*`、不读被测实参）。
- **为什么留两条**：只比第 6 格的话，「**所有格子一起放大**」这种实现会**假绿**；第 7 格那条钉的就是
  「1.2 只作用在那一格」（原版语义 = 第一次循环、`i == collectedRewards`）。
- ⚠️ 两条都**依赖开机偏移 = 0**（原版 `FocusOnItem` 在本机数据下不触发；A182 那一段另有断言钉着 `Offset = 0`）。

## 四、顺手发现的（**都没动手改**）

1. **`MenuDraw.Node` 不给节点设尺寸**（`Shell/MenuDraw.cs:59-65`：只 `new GameObject(name, typeof(RectTransform))`
   + 父级 + `localPosition`）⇒ **奖格节点自己没有 rect**（`sizeDelta` 是 0）。
   ⇒ 「量节点矩形」这条退路**不成立**（这是我放弃「设计空间量宽」那条建议改法的原因之一）——
   凡是要量「这一格的几何」，只能量它**子件渲出来的矩形**。
2. **`Label.WorldH` 是 TMP 网格高（随文字内容变）**，不是我们传进去的框高
   （`Battle/Label.cs:42-43`：`_tmp != null ? _tmpH : _texH/PixelsPerUnit`）
   ⇒ **别拿两段不同文字的「渲出来的高」比倍数**（第 6 格与第 7 格的奖励名不同）。
   记一笔：这也顺带说明「用 `Reward Name` 的高去比 1.2」那种写法不可靠。
3. **`(89,0)` 这类软边**在别的窗也可能被误读成「那个方向不裁」——`m_Softness` 的两个分量**只管渐隐带**，
