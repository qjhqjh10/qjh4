## 一、A173 · `repack_tree()` 多 CAB 包静默取错对象

### 1.1 结论

**已修，并且「口径」先定死了才动手**（这是 `§A173` 点名的前置条件：⛔ 不是把 `sf.objects` 换成
「在所有 CAB 里按 pid 找」就完事 —— 那样必错，因为两份 CAB 的 pid 会撞号）。三条口径：

| # | 口径 | 判据（**代码级**，不是猜） |
|---|---|---|
| 1 | **写哪一份 CAB = 装着 `AssetBundle` 对象的那一份**（不是「第一份」） | `_write_bundle:427-434` 把容器/预加载写成 `PPtr(m_FileID=0, PathID)`；`m_FileID == 0` 在 Unity 语义里 = **引用方自己所在的那一份**（UnityPy `PPtr.deref` 同规则）⇒ 容器**只指得进** AB 对象那一份。另：`_write_bundle` 的裁剪循环只在**写的那一份**里找 AB 对象，找不到就中止 |
| 2 | **另一份怎么留 = 依赖树引用到的其它 CAB 整组保留 + 整组改名**。整组 = 那个 CAB 连同它的 `.resS`/`.resource`；改名 + 改 `externals[].path` + 改那些 CAB 里对象的 `m_StreamData.path`。**整份不裁剪** | ① 少留一条流 = 那个 CAB 里的贴图/网格「有对象没数据」；② **不改名 ⇒ 与源包内层名撞名 ⇒ Unity 判「同一个包」整包拒收**（`extract_missing_shaders.py:961-979` 那段实测原文：`another AssetBundle with the same files is already loaded`）；③ 改名而不改 `externals` ⇒ 跨 CAB 引用**断在运行时**（`PPtr.deref` 就是按那个名字找的） |
| 3 | **根不在那一份里 ⇒ 中止并点名**（⛔ 不许退而求其次） | 根落在别份时它的 pid 属于**另一套命名空间**（实测碰撞见下表）⇒ 容器项会指到**同 pid 的另一个对象**上，且一个字都不报 —— 这正是 A173 本来的缺陷 |

**全库普查（本件实跑，84 个包全扫，只读）** —— 这组数字是上面三条口径的事实底座：

| 量 | 实测 |
|---|---|

| AB 对象在哪一份 | 15 个**全在「第一份」= `.sharedAssets`** ⇒ 旧写法「取第一份」选**文件**碰巧没选错、**pid 命名空间**选错了 |
| 两份 CAB 的规模（arena1） | 写的那份 63 个对象 / 另一份 **5304** 个 |
| **pid 撞号**（arena1） | **63 个 pid 两边都有**（pid 1 = `PreloadData` vs `GameObject`；pid 2 = `AssetBundle` vs `GameObject`；pid 3-10 全是 `Material` vs `GameObject`） |
| 跨 CAB 引用（arena1） | 主 CAB → `.sharedAssets` **97 条**；`.sharedAssets` → 主 CAB **0 条**（15 个场景包全 0） |
| 非写那份里的「走流对象」 | **0 个**（15 个包都没有 Texture2D/Mesh 走流）⇒ 我为了验「整组不瘦身」那一支**造了合成包**（见 1.4·d） |
