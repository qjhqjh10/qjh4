## §二 证据

### 2·1 `InstanceId` —— 判据是原版**实体访问链**，不是「座位 + 格号」

**原版那一格**
- `CardScript__SetInBattleId.c:8`：`*(undefined4 *)(param_1 + 0x22c) = param_2;` —— **本局唯一号的唯一写点**；
- 发号方：`BattleCardManager__RegisterCardInPlay.c:58` 与 `BattleCardManager__CreateCard.c:152`，
  号源 = `BattleCardManager + 0x28..0x38` 那枚 `ObscuredInt`（`op_Increment`，单调递增）；
- 反查口：`BattleCardManager__GetCardFromUniqueId.c:33`
  —— `if (*(int *)(lVar2 + 0x22c) == param_2)`；
- **跨对象引用全用它**：`PlayerAction` 的 `act` / `tget`（`dump.cs:119892-11993`，偏移 `0x14` / `0x18`），
  `BattleManager__ParseEnemyAction.c:64,69` 两处都是 `GetCardFromUniqueId(...)`；
- `dump.cs:21973`：`public bool isPlayer; // 0x40`（另一条判据里用到）。

**结论**：原版的动作/事件**按实体唯一号**指人，格位只是「这一刻在哪」——
我们的 `BoardSlots` 是同一套「插入推人 / 外侧补位」模型（`CLAUDE.md` §三），
**先死后补位**时同一个格号会换人 ⇒ 用「座位 + 格号」对账就是同名单位血账错挂的根因。
⇒ 加 `BattleEvent.InstanceId` / `TargetInstanceId`（`0` = 哨兵；正数 = 真对局；负数 = `CardInstance.Detached`）。

**落点（全仓）**
- `Core/UnitState.cs:48`：`InstanceId` **只转发** `Instance.Id`（不另存一份）；
- `Core/RuleCore.cs:6660`：`EmitUnit` **唯一默认口**（`Hit` / `Death` / `Trigger` / `AmbushExit` / 治疗那一族都走它）；
- 直接 `ctx.Emit` 的落点各自显式传：`RuleCore.cs:2578/3257`（Deploy）· `:4578`（Attack，含 `TargetInstanceId`）·
  `:4722`（attacked 触发）· `:6992/7008/7114`（Death）· `:7933/8089/8331`（Ability）· `:8403`（Return）·
  `:8587`（BloodThirst）· `:8676/8777`（Trigger）· `:8542`（CollectWaystone）· `:5808`（SecretOrder）·
  `EffectResolver.cs:5106`（Return）· `:8972`（Reanimate Deploy）· `TutorialScript.cs:1295`（教程起始单位）。
- `BattleContext.cs:1472`：`Emit(...)` 末尾加可选 `instanceId` / `targetInstanceId`（既有调用点零影响）。
- **回放**：`ReplayStore` 只存 `actions`（`MsgAction`），`BattleEvent` 不进 `.json` ⇒ **不加版本号、旧录像照读**。

### 2·2 多候选「时间错开」—— 原版的 `t` 是**串行累计时长**，不是 `timeAtStartPos`

**原版数据结构**
- `CardAnim` = ScriptableObject，只有一格 `animInfo`（`dump.cs:20376-20384`）；
- `AnimInfo`（`dump.cs:20403-20434`）：`vfxDelayTime // 0x24` · `startDelay // 0x28` ·
  `timeAtStartPos // 0x2C` · `timeMoving // 0x30` · `timeAtEndPos // 0x34`；
- **时长 = `AnimInfo.GetAnimDuration()`**（`AnimInfo__GetAnimDuration.c:3-6`）=
  `timeMoving + timeAtStartPos + timeAtEndPos + vfxDelayTime`（⚠️ **`startDelay` 不在内**）。

**原版执行链（候选之间是串行）**
1. `AbilityLogic.PlayAnim` 对 `cardAnimations[]` 的**每一条**压一条 `BattleActionType.playAnim(=11)`
   （`AbilityLogic__PlayAnim.c:232/273` → `BattleManager__AddCardAnim.c`）；
2. 队列**一次只弹一条**（`BattleManager__ResolveActionFromQueue.c:44-76`：`get_Item(0)` + `RemoveAt(0)` →
   `ResolveAction`）；
3. 每条 `playAnim` 的协程**等完 `GetAnimDuration` 才结束**
   （`BattleManager._ResolveAnim_d__466__MoveNext.c:200-210`：`WaitForSeconds(GetAnimDuration)`）。
⇒ **第 n 条的起点 = 前 n-1 条的时长之和**。这不是「拍一个固定间隔」——每条的时长都从它自己的 SO 读。

**数据是怎么解出来的（可复现）**
- `cardAbilities[].abilityLogic[].cardAnimations[]` 的每一项 = `m_AssetGUID`（`cards_raw.json`）；
- GUID → `CardAnim` 资产 = `资料/普查产出_1018/cardanim_guid_map/guid_map_bundles.tsv`
  （`className == CardAnim`；本轮 **580/580** 都能解）；`CardAnim.animInfo.animAdressable` GUID →
  prefab 名（`type == GameObject`；**576/580** 有，4 条是**纯计时占位**，原版合法）；
- `animInfo` 本体从 `d:/2/新解包资源/assets_full/bundle_<bundle>/MonoBehaviour/<name>.json` 读（**580/580 全在**）。

**落值（`cards_engine.json` v12 · 每卡 `animTimes`）**
| 字段 | 含义 | 判据 |
|---|---|---|
| `a` | `CardAnim` 资产名 | = 运行时 `card_vfx_by_card.json` 的 `es[].a`（**精确 join 键**） |
| `n` | prefab 名 | = `es[].n`（`a` 为空的那几条靠它 join） |
| `tg` / `tn` | 原版 `CardAbility.trigger` 数值 / 枚举名 | `AbilityTrigger.cs`；`activeAbility` 一路 = `-1` / `""` |
| `rc` | `randomAbilityChoice` | `CardAbility.cs:27-29` |
| `o` | 原版路径索引三元组 `i.j.k`（`-.j.k` = activeAbility） | 审计 / 同名重复（59 行）的逐条对账 |
| `d` / `sd` / `s` / `m` / `e` | 五个原始时间字段 | `AnimInfo` 五个偏移（见上） |
| `u` | `Duration` | `GetAnimDuration` 逐字 |
| `t` | **组内起点偏移** | 同 `(卡, tg)` 组内前面各候选的 `u` 之和 |

**现读**：`animTimes` 落值 **873/1127** 张 · **1466** 条候选；
其余 **254 张在真值快照里没有任何 `cardAnimations` GUID**（逐张核过：不是解错）。
GUID 解不出 **0** · 资产文件缺 **0** · 不是 CardAnim **0** · 纯计时占位 **4**。

⚠️ **战斗线 B4 §一·5 把 `t` 说成 `timeAtStartPos`，那是错的**：`timeAtStartPos` 是
「VFX 在起点**停留**多久」，不是候选之间的间隔（实测 `timeAtStartPos` 众数 = `0.0`，475/580）。
数据侧两样都给（`s` 与 `t`），**消费端用 `t`**。

### 2·3 `A2143` —— 原版没有「敌方手牌」来源档，判据是 `card.isPlayer`

- `BattleManager._ResolveCardAutoSummoned_d__511__MoveNext.c`（= 我们 `DeployFree(fromHand:true)` 那一路）：
  - `:74/92/101` 三处都读 **`*(char*)(card + 0x40)`**（`EntityScript.isPlayer`，`dump.cs:21973`）；
  - `isPlayer == 0` ⇒ `+0xe8`（**`enemyMinionManager`**）；非 0 ⇒ `+0xe0`（`playerMinionManager`）——
    字段名见 `dump.cs:30742-30743`；
  - 演出两支：`:110` `PlayEnemyCard`（`DisplayEnemyCardInCenter` + `TurnCardAround`）/ `:128` `PlayPlayerCard`。
  - 闸：`:89` `CardScript__IsInHand(...)`（`AddAutoPlayFromHand.c` 里还有
    `cardState == 0x10` 那一条退路）。
⇒ **牌从谁的手里拿出来，就落在谁的棋盘上**；「谁的牌」= 事件里的 `Player`。
表现层要挑 `PlayEnemyCard` / `PlayPlayerCard`，判别式 = **`e.Player == 本机座位`** ——
**再加一个 `DeploySource` 枚举值就是同一条规则的第二个表示**（本笔不加，判据写进
`DeploySource.AutoPlayFromHand` 的 doc）。

**我们这边的真缺陷（已修）**：`EffectResolver.DoChooseCard` 的 `case "deploy"`
（`EffectResolver.cs:3505` 一带）改前对**所有** `ChooseSrc` 都用 `owner`（施放者）部署、且**没传 `fromHand`**。
`GOF93 Hunta Rig` 的 SO 是 `chosenAbility 250 (autoPlayFromHand)` +
`targetCriteria{targetsAffected:50, enemyUnits, includeMinions, selectFromChooseResolution:1}` ⇒
选中的敌方手牌部队原版落在**敌方**棋盘（下一句 `This troop attacks it` = Hunta Rig 打它）。
改后：
- `deployOwner = (ChooseSrc == "enemyhand") ? 1 - owner : owner`；
- `fromHand = (ChooseSrc == "enemyhand" || ChooseSrc == "hand")` ⇒ `DeploySource = AutoPlayFromHand`
  （触发 Rally、兑现手牌加成）；
- 日志点名「部署到 `<那一方>` 的槽 N」。
`AM58 Siege Warfare`（`Draw two Vehicles from your deck and deploy them`）是**另一条**：
它是「代词部署」而不是 choose，见 2·5。

### 2·4 `A2142` —— 天赋名 → id 表

- 真值来源：`cardAbilities[trigger == 46 /*Talent*/].abilityLogic[0]
  .summonCriteria.unitsToSummon[*]`（PPtr → `path_id` → `uniqueId`，判据 = `CardScript__GetTalentCard.c`
  与 `AbilityLogic__GetCardToSummon.c`）；
- 键的三种写法都归一（`CreatePool.Norm`：小写、只留 a-z0-9）：我们池里的 `name` / `nameZh` ·
  真值 SO 的 `cardName` · `m_Name` 尾段；
- 只收**落在我们卡池里**的 id；**一个名字指向多张卡 ⇒ 整条丢掉**（现读 2 条：
  `pathofthewarrior`、`waaagh`），跑完摘要逐条打出来；
- 现读 **186 键**，写进 `cards_engine.json` 顶层 `talentNameIds`（数组 `[{n, id}]`，
  因为 `JsonUtility` **不支持字典**）；
- 读取口：`Data/CardDatabase.Parse` → `TalentCardData.SetNameMap`
  （`CardDatabase.cs:288` / `TalentCardData.cs:127`）；`SpawnTalents` 先
  `TalentCardData.ResolveByTalentName`（`RuleCore.cs:9102`），查不到才退回
  `CreatePool.FindByName` 老路。
- ⚠️ **现读覆盖率**：池里带 `Talent` 的 **96 张全部**在 `talent_cards.json` 那张按卡 id 的表中
  ⇒ 今天这条新表**没有可观测差异**（产品路径一次都不走它）。它买的是**未来的新卡**
  （真值快照里没有的那批）——把最后一条兜底从「按显示名」换成「按 id」。

### 2·5 顺手做：`AM58` 的 `deploy them`

- 解析（`ruleprobe seg`）：`drawtype(2, vehicles)` + `deploy(payload="them", deployFrom=<空>)`；
- 改前 `DoDeployOnce` 把 `them` 当卡名去 `CreatePool` 查 ⇒ **一张都不部署**
  （探针实测：抽了 2 张、棋盘不动、也没有「部署不了」的日志）；
- 代词槽本来就有：`BattleContext.LastHandTargets` / `LastHandTarget`
  （`DoDraw` / `DoDrawType` 末尾按**实例**填）；`HandReferents` 的兜底 = `DrawnThisResolve`；
- 改法（`EffectResolver.cs:2466`）：`deploy them/it` 且 `DeployFrom` 为空 ⇒
  逐份 `ps.Hand.Remove` → `DeployFree(..., fromHand: true)`；失败**留回手里**并 `unresolved` 出声。
  `it` 只认单数槽（一堆里挑一个 = 猜，红线）。
- **探针实测**：`play AM58` ⇒ 「抽了 2 张」→「免费部署 … 到槽 2 / 7」→
  「把上一条效果留下的 2/2 张直接部署」✓。

## §三 没查清 / 不猜

1. **`randomAbilityChoice = true` 的「按组随机抽一组」** —— V2 报告 §3·3 要的 `g`（组号）**没有单独落**，
   但**可以从 `o` 的中间那一段推出来**：`o = i.j.k`，`j` = 该 `CardAbility` 内 `abilityLogic` 的索引；
   `rc = 1` 时调用方应「**按 `(i, j)` 分组、用种子随机抽一组、再播该组的全部候选**」。
   今日唯一为真的是 `GOF12 Spanner`（5 条 logic 的 prefab 全是 `Buff_Ork_Mek`）⇒ **无可观测差异**。
2. **`timeAtStartPos` 的语义**在上面的证据链里是「VFX 在起点停留时长」；但**单看 `AnimInfo` 字段名**
   也能读成「到起点那一刻的时间」。两者的差别只在「候选之间」这一维 —— 我们按**串行时长**给出 `t`，
   把 `s` 原样也给出，**消费端按 `t` 播、别按 `s` 播**。如果将来真机对比发现「候选应当同时开始」，
   判据要回到 `BattleManager.ResolveActionFromQueue` 的**调用时机**（本笔只读到「一次弹一条」，
   没有读到「动作之间是否有并行窗口」）。
3. **4 条纯计时 `CardAnim`**（无 prefab）：它们进不了 `card_vfx_by_card.json` 的 `es[]`
   （那一层要 prefab 名）⇒ `animTimes` 里有、运行时**没有可播的东西**。这是原版合法状态，
   ⛔ 不要当「缺数据」去补 prefab。
4. **`t` 的分组是 `(卡, tg)`**，而 `VfxMap` 的事件键更粗（`TRIGGER_EVENT` 把
   `Strike` / `Slay` → `trigger`、多处 trigger → 同一事件）。当同一事件合并了多个 trigger 时，
   `t` 会在 trigger 边界**重新从 0 开始**。**消费端要按 `tg` 分组用 `t`**（见 §五 接口需求）；
   若它宁愿只看「顺序 + `u`」自己算累计，`u` 也在数据里。
5. **`animTimes` 覆盖 873/1127**：其余 254 张**真值里就没有 `cardAnimations` GUID**（逐张验过）。
   这不是「没解出来」；`--check` 与跑完摘要都能复现这个数。
6. **`cards_engine.json` 从 842,451 B 涨到 1,102,287 B（+30.8%）**：新增的 `animTimes` 约 245 KB。
   `CardDatabase.Parse` 的实测耗时（原注释：1127 张 ≈2.4 s）**本批没跑 Unity、没重量** ——
   下次真机/自检跑起来时留意启动时间；若明显变慢，优先砍 `tn`（可由 `tg` 查表得到）。
7. **`talentNameIds` 今天不可达**（§2·4）：96/96 张带天赋的卡都在按 id 的那张表里。
   新表只在「未来新卡 / 真值快照外」时生效 —— **没有实测样本**，不要在报告里当成已验过。
8. **`AM58` 的探针夹具里抽到的是 `filler25/21`（不是 Vehicle）** —— 夹具牌库没有载具，
   `DoDrawType` 的 `MatchesKind` 在夹具上判成了「可抽」。部署链路本身已验证；
   **真实牌库里抽的是不是载具，本批没验**（需要预置一副有载具的夹具，见 §五）。
9. **`JsonUtility` 对新形状的实际解析没跑**（铁律 12：本批不起 Unity）。`AnimTimeDto[]` /
   `TalentNameIdDto[]` 都是标准「公共字段 + `[Serializable]` 数组」，`typecheck` 只保证编译过；
   **下次跑 `RuleEngineTest.Run` / 进游戏时，第一件事确认 `CardDatabase.Parse` 没抛**
   （失败会留一条 `Debug.LogError` 或空池 —— 空池就是硬信号）。

## §五 接口需求（给主对话 → 战斗线 / 自检线）＋ 顺手发现

### 5·1 【战斗线】`Core/VfxMap.cs` 怎么消费 `t`（本批不能改它）

`CardDef.AnimTimes` 已经能从卡池拿到（`CardDatabase` 解析 → `CardDef`）。建议形状：

1. `VfxMap.ResolveAll(evt, faction, card)` 拿到 `es[]` 之后，**逐条**在
   `card.AnimTimes` 里找匹配：
   - 首选 `at.Anim == es[j].a`；
   - `es[j].a` 为空 / 空串 ⇒ 用 `at.Prefab == es[j].n`；
   - **同一个 `a` 在一张卡里出现多次**（现读 59 行）⇒ 按 `o` 的顺序**逐次消费**，⛔ 别去重。
2. 播放延迟 = **`at.Offset`（`t`）**，⛔ **不是** `at.TimeAtStartPos`（理由见 §2·2 末段）。
   `at.Duration` 可拿来算整组的总时长（收尾/清理）。
3. **随机组**：`at.RandomChoice == 1` ⇒ 按 `o` 的中间段（`j`）**分组**，用一局的种子随机抽**一组**，
   再播该组全部；今日只有 `GOF12` 一条，且 5 组的 prefab 相同 ⇒ 行为不变。
4. `BattleDriver.AdvanceTimeline` 那条泵已经在（B4 报告 §五·1）——把这批「延迟」挂上去即可。
5. ⚠️ `t` 的分组键是 `(卡, at.Trigger)`；**`VfxMap` 自己的事件键更粗**（`Strike`/`Slay` 合并成
   `trigger`）。如果一次 `ResolveAll` 里混进了多个 `Trigger` 值的候选，
   要么按 `Trigger` 分组分别计时，要么只用「顺序 + `Duration`」自己累计 —— **两种都在数据里，⛔ 别拍一个固定间隔**。

### 5·2 【战斗线】`InstanceId` 的下游

- 「同名单位血账」（受击/阵亡/治疗/增益）的键**从 `(Player, Slot)` 换成 `InstanceId`**；
  格位只用于「这一刻播在哪」。
- `Attack` 的目标用 `TargetInstanceId`；其余事件只有主语（`InstanceId`）。
- 自检判别式：
  1. 打出一张单位卡 ⇒ `Deploy.InstanceId != 0`，且 = 该单位后续 `Hit` / `Death` 的 `InstanceId`；
  2. 同一张卡的两份（两张同名）⇒ **两个不同的非 0 id**；
  3. 同格补位（A 死、B 进同一格）⇒ 两条 `Death` / `Deploy` 的 id **不同**（灭自证：
     改回 `(Player,Slot)` 时这条仍然是两条不同事件，但**分不出是同一个人**——所以第 3 条要断言
     「A 的 Death 与 B 的 Deploy 的 id 不相等 **且** 都非 0」）；
  4. 手工 `new BattleEvent{Kind=Deploy}`（不填）⇒ `InstanceId == 0`（哨兵不变）。
