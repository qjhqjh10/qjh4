## 一、原版语义判据

### 1.1 同一张卡两条 `trigger = 605` 的能力 —— **各自判定、各演一次**

| 环节 | 判据（全量反编译 `d:/2/tools/decomp_full/`） | 读出来的语义 |
|---|---|---|
| **派发** | `RawCardScript__TriggerAbilities.c:59-88,207-265` | 它**逐条**遍历这张卡的 `cardAbilities`，对每一条调 `CardAbility__CanTriggerAbility`；通过就 `RawCardScript__TriggerAbility`（= `PlayAbility`）**那一条**。⇒ 两条 605 能力 = 两次独立演出。 |
| **605 的门槛** | `CardAbility__CanTriggerAbility.c:114-126` | `trigger == 0x25d(605)` ⇒ 取 `PlayerManager.GetCurrentFaith`（`:122`），再落到共用闸 `LAB_180922dd1`：`if (faith < *(int*)(ability + 0x20)) return 0;` —— **`0x20` = `CardAbility.triggerValue`**。 |
| **发起源（战术卡）** | `RawCardScript__OnCardPlayedWithTarget.c:66` → `:73` | 600 在前、605 在后；605 只在 `cardType == 0x14(Tactic) / 0x28(Whispers)`（`:68-78`）发。整段在 `param_3 == param_4`（打出的就是收回调那张）里。 |
| **「门槛」的真身** | `cards_raw.json` 的 `cardAbilities[].triggerValue`（当前 build 1,351 张） | 605 能力的 `triggerValue` **就是信仰门槛**：SOR56 = 4 / 7（能力 1 / 2）· SOR23 = 2 / 4（能力 0 / 1）· SOR67 = 2 / 4（能力 1 / 2）。 |

⇒ **原版**：SOR56 在 Faith≥7 时两条 605 各演一次；4≤Faith<7 时**只有 4☀ 那条**的动画（7☀ 那条不激活，也不该播）。
**我们改前**：只发 1 条 `EvtKind.Trigger`，`VfxMap.TryResolveTriggerPicks` 只按 trigger 名筛 ⇒ 把这张卡**全部**
`UseFaith` 行一起播（Faith 4~6 时也把 7☀ 的动画播了）。

### 1.2 触发时怎么区分是哪一条 ability —— **`cardAbilities[i]` 下标**

- 原版靠 `CardAbility` 对象本身（`TriggerAbilities` 里的循环变量），效果与动画都在那一条里
  （`abilityLogic[j].cardAnimations[k]`）。
- 我们的运行时数据已经有这个下标：`CardDef.CardAnimTime.Order` = 原版字段路径 `i.j.k`
  （`cards_engine.json` 的 `animTimes[].o`，`CardDataBase.MapAnimTimes` 逐字搬运）。
- 「信仰门槛 → 能力下标」的配对：`FaithOps` 的**付费组首**（`Cost > 0 && !CostShared`）就是正文里的
  `N ☀:`；3 张卡现读「门槛升序 = 能力下标升序」，且**条数相等**（见 §三）。

## 四、没查清 / 已知近似 / 建议记账

   （`PlaySignals` 的 `EventTiming.DelayBetween(prev, Trigger) = TriggerHold 0.3` + `DurationOf(Trigger) = TriggerLen 0.2`）。

   原版单事件整批是 2/3 s。**这是本设计的已知近似**（数据 `t` 是「整张卡全部候选串行」的累计，而事件又各占一拍）。
   ⛔ 没有改 `EventTiming`（战斗线）；若将来要精确对齐，需要在表现层按「同卡多事件」扣掉那段间隔 —— 判据要另查。

   `EvtKind.Trigger` 日志分支直接印 `e.Keyword`）、`PulseBadgeByKeyword` 的「没有徽标位」提示会各多一条。
   **只影响这 3 张卡**；改日志属 `BattleDriver`（T09-WIRE 持有）⇒ 未动，留作记账。
3. **配对是「门槛升序 ↔ 能力下标升序」的推断**。口径收窄（2026-10-20 复核后）：
   **本笔 3 张逐张核过**（`cards_raw.json` 的 `triggerValue` 与 `cards_engine.json` 的 `Desc` 门槛、
