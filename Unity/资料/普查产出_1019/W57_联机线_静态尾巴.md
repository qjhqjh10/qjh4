### 下一次真连「一眼判」配方（按顺序 grep）

```
【接收方】
  1) grep "收到 `bye`"                      → 到了应用层 ⇒ 这条 bye 没丢（问题在别处）
  2) grep "拒收了新进来的那条连接"           → 这条连接被本机丢了 ⇒ 若 bye 在它上面 = S6
  3) grep "传输层掉线：原因 ="               → 看原因：
       对面关掉了连接                        → 收到 FIN 但没读到整帧 ⇒ 去发送侧 / S6
       读取中断：…reset…                     → abortive（RST）⇒ 接收缓冲可能被丢；查发送侧 S5
       收到的帧解不出信封 / 帧长度不合理      → 截断/坏帧（R1）
【发送方】
  4) grep "已给对面捎一句 `bye`"             → 已交给传输层（与接收方 1 对账）
  5) grep "本来要给对面捎一句" / "没发出去"   → S1/S2/S3
  6) grep "在传输层报失败了"                  → S4
  7) grep "优雅关闭："                        → S5（Shutdown/排空/超时）
【两侧都没有上面任何一条】                    → 本端没 Pump（R5）或会话被 Reset 换掉（R7）
```

### 对历史 X2 证据的静态结论

F5 的三个硬事实（客机确实 `Close(true)`、确实写进传输层且零告警、主机从未处理任何 `Bye` 帧，
主机侧原因是「对面关掉了连接」）在**静态上**只剩两条候选：

1. **S6（最可疑）**：客机在**重连分支**里刚建起来的新连接，被主机 `AcceptLoop` 以「已有活对家」**拒收**
   —— 客机的 `bye` 写在这条被立即关闭的连接上；主机那头看到的是**旧连接的 FIN**（=「对面关掉了连接」）。
   旧代码这一支**完全静默**，所以当时查不出来；本轮已补日志，下一次真连**一行就能判**。
2. **S5 的残余窗口**：`CloseGracefully` 只等「对端关」，**不等我方接收缓冲排空**；200ms 超时后硬关，
   Windows 对「接收缓冲还有未读数据」的 socket 会走 abortive（RST），对端可能连带丢弃已收到的 `bye`。
   静态判不了概率（读线程一直在抽，窗口极小）⇒ 下次看发送侧有没有 `排空**超时**`、接收侧原因是不是 `读取中断`。

> ⛔ 本轮**没有**跑 `NetBattleTest` / `NetSelfTest` / 真连，所以以上是**静态候选**，不是定因。

## 五、顺手发现（**只报不改**）

1. 🔴 **我方 `Close` 之后，队列里的旧 `bye` 仍会被处理**：`NetSession.Pump` 在
   `State == Closed/Off` 的早退（`NetSession.cs:226`）**之前**就 `_t.Pump` + `Handle` 完了；
   而 `NetSession.Close` / `TcpTransport.ClosePeer` 都**不清 `_inbox`** ⇒ 先 `Off`、下一帧又
   `收到 bye` + `SetState(Closed)` + `OnClosed`（`NetBattle.HandlePeerClosed` 会再说一遍「联机对局结束」+ 弹窗）。
   建议：`Close` 里丢弃 pending inbound（要先给 `INetTransport` 加口或按类型分派）；
   ⚠️ 改它会动「Close 后仍处理最后一帧」的既有语义 ⇒ 本轮没敢动。
2. ⚠️ **`NetMatchmaking.PumpLobby` 会 `s.Inbox.Clear()`**（`NetMatchmaking.cs:733`）。若 `LobbyHandled`
   在对局中意外还是 true（`AttachForTest` / 手工改标志的夹具），**对局类消息会被大厅层清掉**（不是 `bye`，
   `bye` 在 `NetSession.Handle` 就消化了）。生产侧 `NetBattle.Attach` 会置 false，暂不现形。
3. ⚠️ **`TcpTransport.Send` 的失败是靠「`_lastError` 前后变了才算」**（粘性字段）。同一条连接上
   **第二次失败且原因字符串一模一样**时，`NetSession.Send` 会误判成功（返回 true）。概率低、且第一次已出声。
4. ⚠️ **`ReadFull` 部分读**：body 读到 `got>0` 但 `< len` 时（对端半帧后关连接），`ReadLoop` 仍会
   `Parse` 那半截缓冲（后面全是 0）—— 多半 `BadEnvelope` 出声，但**理论上**存在「半帧被当成整帧」的形状。
   建议将来把 `n != len` 单独判成「截断帧」并出声。
5. 📌 **`NetBattle.ReconnectCountdownExpired` 主机支 `_s.Close(true, Wire/RoomGone)`**（`NetBattle.cs:926`）
   在「对面已经没了」时必然触发 `本来要给对面捎一句 bye…没有活的连接` 的告警 —— 这是**预期噪声**，
   不是缺陷；下一次真连别把它当成 `bye` 丢失。
6. 📌 **`NetSelfTest` 的 `R㉝` 是源码结构断言**（读 `.cs` 文本）。本轮 `Close` 重构后必须跟着改，
   已改成两条（`R㉝` + `R㉝-b`），见 §二；将来再动 `Close` 的结构要一起看这两条。
