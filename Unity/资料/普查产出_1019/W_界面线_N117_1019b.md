## 一、结论

### 1.1 根因（现读确认）

`Shell/MainMenuRuntime.cs` 里导航命中区 `QNavHit = 3156` 高于详情窗压暗层命中区 `CardDetailPopup.QShade = 3105`。
`PointerLayer.HitButton` 按「渲染队列大的先」挑赢家 ⇒ 详情窗开着时，点**看起来已被压暗**的左栏会走导航，
而不是像原版那样落到弹窗的 `Menu Dark Background`（= 点暗处关窗）。

2026-10-18 抬到 3156 是为了修「商店开着点不动左栏」（那次是对的，本次不回退）。

### 1.3 落地方式

- **模态窗成为顶窗**：五颗导航 `Hit` quad 的渲染队列整体降到 `QNavHitBlocked = 3001`
  （严格低于全工程最低的窗压暗层 = `DailyRewardPopup.QShade` / `DailyStreakPopup.QShade` / `InboxWindow.QShade` 的 **3002**）。
  ⇒ 左栏不可点；那一下落到模态窗的压暗层命中区（= 原版「点暗处关窗」）。
- **非模态窗 / 无窗**：恢复 `QNavHit = 3156` ⇒ 2026-10-18「商店开着也能点左栏」的修复不回退。
- **刷新点**：`WindowsManager.OpenWindow` 末尾 · `NotifyClosed` 末尾 · `CloseAllWindows` 末尾 · `SetBaseMenu` 末尾；
  另外 `MainMenuRuntime.BuildNavigationPanel` 末尾补一次（重建左栏后旧 quad 已销毁）。
- 画面逐像素不变：只动**透明命中区**的档，可见图标/文字/高亮一个字节没碰。

### 1.4 COLLECTION 重开保留当前页

**做了**，判据如下（原版反编译）：

- `GameWindowWithTabs__Open.c:9-21`：先读**当前页签**（字段 `0x12`）；**非空就不调 `GetStartingTab()`**、
  只对该页调 `OnOpen`；只有它为空（= 新建实例）才走 `GetStartingTab()`（虚表 `0x218`，回落 = `tabs` 的
  `FirstOrDefault` = 第一页）。
- `WindowTabBase__CloseTab.c` 只 `SetActive(false)`；`GameWindowWithTabs__Close` 也不写 `0x12`
  ⇒ **隐藏 → 被 `ShowPreviousWindow` 带回来**这一路，原版**保留当前页**。
- 我们的实现：`CollectionWindow.Open()` 原来恒 `tabButtons.Click(0)` ⇒ 每次 `Open()`（含 Closed 支重建）都回第 0 页。
  现在改为 `StartVisualIndex()`：`CurrentTab != None` 就点回同一页签，新实例才落第 0 页。
  用 `Click(visualIndex)` 而不是 `ChangeTab`：左栏高亮读的是 `TabButtons.CurrentVisualIndex`。

**一条如实记（见「没查清」§3.1）**：`COLLECTION` 导航钮原版 `closeOtherMenus=1`（MB_2494 实读），
`OpenWindowCO` 会先 `CloseAllWindows()`；而原版 `CloseWindowCO` 对缓存里的窗是
`Hide → Remove → Destroy`。这一支**理论上会销毁正在打开的那一扇**（Unity 的 Destroy 延迟到帧末）。
本次没有把这条链跑实况，所以「原版这一支到底表现成『回第 0 页』还是『窗消失』」标注为没查清。
但无论哪种，`CurrentTab` 的保留语义（上面的 `GameWindowWithTabs__Open` 判据）是确定的，
且用户 2026-10-19 明确要求「重开收藏窗保留当前页」⇒ 按用户口径 + 隐藏/带回这一路照原版落地。

## 三、没查清

1. **原版 `OpenWindow` 的「查缓存」与 `CloseAllWindows` 的先后顺序**（`N117` 的 COLLECTION 支线）：
   - 本次用 `工具/disasm_va.py` 读了 `WindowsManager.OpenWindow`（VA `0x180875990`）：
     cache `TryGetValue` 在 `0x180875A74`，命中后 `0x180875C1C` 调 `0x180875650` → `0x180875380`
     （= `OpenWindowCO`，其 `closeAll` 支在 `0x1808753F5-0x1808753FA` 调 `0x180874740 = CloseAllWindows`）。
   - ⇒ **查缓存确实在 `CloseAllWindows` 之前**。若被开的那一扇此刻正开着且在缓存里，
     它会在同一次调用里被 `CloseWindowCO` **销毁**，而随后 `OpenWindowCO` 仍拿着同一个（已被 Destroy 的）
     引用继续 `set_CurrentWindow` / `openWindows.Add` / `Open()`。Unity 的 `Destroy` 延迟到帧末。
   - **没查清的部分**：这一支在真机上最终**用户看到什么**（是「回第 0 页」还是「窗消失/回主菜单」）。
     本次没跑实况（原版已关服、无卡组数据，且派单禁止跑 player）。
   - 本轮的处理：按 `GameWindowWithTabs__Open` 的确定语义（当前页签非空就保留）+ 用户 2026-10-19 的明确要求
     落地保留当前页。**这一条不冒充「原版该支已核」。**
2. **原版导航钮的 `allowClickWhenAlreadySelected = 0` 是否真把「COLLECTION 已选中时再点」挡掉**：
   - 我们的实现已照原版置 `false`（`Shell/MainMenuRuntime.cs:1107`，`wb.allowClickWhenAlreadySelected = false`）。
   - 若原版确实挡掉，则「收藏窗开着时再点 COLLECTION」这一支**根本不可达**，`CloseAllWindows` 那条链不会被玩家触发。
     本次没有跑实况确认（同上）。
3. **`QNavHitBlocked = 3001` 与 `Deck/DeckRuntime.cs` 的 `QDoneHl` / `QCurveBg`（也是 3001）同号**：
   两者不会同屏（卡组编辑是独立场景，且开窗时左栏已 `Toggle` 收起）⇒ 本批按「无害」保留；
   若将来卡组编辑改成主菜单内的窗，需要重新取号。

## 五、附：为什么不用「几何覆盖判定」

曾考虑在运行时扫描「顶窗是否有覆盖左栏 rect 的整屏 quad」来判模态。放弃理由：
- 需要每帧/每开窗遍历整棵窗子树并反推设计矩形（`MenuDraw.QuadRectPx`），批处理与运行期都多一条开销；
- 我们已经有了**更硬的原版字段判据**（`windowsPlacement` / `type`），且 `BlocksLeftNav` 可逐窗覆写
  （已经用它处理了 `SearchingOpponentWindow` 这个字段判不出来的例外）；
- 几何判定的两个已知反例（`BoosterPackOpenWindow` / 活动三页）本来就被它们自己更高的压暗层档覆盖，
  不依赖这条规则。
