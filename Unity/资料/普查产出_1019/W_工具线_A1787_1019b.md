### 二·四 编码约定（实测；每条都有独立证据）

1. **普通字符串** = `[u32 byteLen][UTF-8 bytes]`，**id 指向 bytes**（长度在 `id-4`）。
   证据：`idOffset=0x171D0` → 30 字节 `AddressablesMainContentCatalog`，`0x1E` 在 `0x171CC`；
   `buildResultHash=0x1751D` → 32 字节 hash，`0x20` 在 `0x17519`。
2. **动态字符串** = id 带 `0x40000000`；指向 `{u32 stringId; u32 nextId}` 链；
   **各段按链的逆序拼接**，段间插**调用点给的** `sep`（文件里不存 sep）。
   证据：allcards 键由 `"allcards"`（0x13E940）+ `"assets_all"`（0x0E8259）+ `"ea8bca4f….bundle"`（0x13E911）
   三段逆序拼成，remap 的 sep = `'_'`（0x5F）⇒ `allcards_assets_all_ea8bca4f….bundle`。
3. **数组** = `[u32 byteSize][elements]`，**id 指向元素区**（长度在 `id-4`）。
   证据：KeyData 数组（上条）；locationSet `0x13E974` 的 len 在 `0x13E970` = 4 → 1 个元素 `122737`。
4. **key 对象** = `ObjectTypeData{typeId, objectId}`；`typeId` → `TypeSerializer.Data{assemblyId, classId}`
   （两者都是字符串 id）；`System.String` 的 `objectId` → `ObjectToStringRemap{stringId, separator}`
   （separator 是 char，存低 16 位，高 16 位为 0）。
5. **ResourceLocation.Data**（28 B，7×u32）：
   `primaryKeyOffset, internalIdOffset, providerOffset, dependencySetOffset, dependencyHashValue(int), extraDataOffset, typeId`。
   - `dependencySetOffset` → `uint[]`，元素是**别的 location id**；`0xFFFFFFFF` = 无。
   - `extraDataOffset` → `ObjectTypeData`，本 catalog 87/87 都是 `AssetBundleRequestOptions`。
6. **AssetBundleRequestOptions.SerializedData**（20 B，5×u32）：
   `hashId, bundleNameId, crc, bundleSize, commonId`。
   🔴 **`hashId` 不是字符串 id，是 16 字节 `Hash128` 原始值所在的偏移**（`ea8bca4f…` 直接是 16 字节）；
   `bundleNameId` 才是字符串（32 hex）。这条最容易踩错。
7. **Common**（8 B）：`short timeout; byte redirectLimit; byte retryCount; int flags`。本 catalog 全部
   `timeout=0, redirectLimit=32, retryCount=0`，flags ∈ {20:53, 16:15, 17:10, 21:9}（十进制；位含义未解，见 §三·4）。
8. **`0xFFFFFFFF` = null**（数组/字符串/extraData/typeId 通用）。

## 三、没查清 / 解不出的（附"为什么"）

1. **动态字符串的 `sep` 不在文件里。** `Reader.ReadString(id, out size, char sep)` 的 `sep` 是**调用点实参**
   （签名见 `BinaryStorageBuffer.cs:216`），文件只存分段。
   本脚本按实测反推：`internalId/primaryKey` 用 `/`（URL/路径能完整拼回）、provider 与类型名用 `.`、
   key 名用 `ObjectToStringRemap.separator`（实测 `_`）。**若未来某份 catalog 的调用点换了 sep，可能拼错**——
   认不出时会输出 `None`，不会静默编一个。
2. **Unicode 字符串（`0x80000000`）**：实现已写（UTF-16LE），但三份 catalog 里**未观察到**
   （判据：所有实际 string id 的最高位都是 0）。**未验证**。
3. **`dependencyHashValue`**：按 int 读出（本 catalog 全是 0）；它是否真是"依赖集 Hash128 的低 32 位"未验证。
4. **`Common.flags` 的位定义**：原始值分布 {20:53, 16:15, 17:10, 21:9}（十进制）；`dump.cs` 只给字段布局，
   getter 体读不到 ⇒ 没有把 bit 映射到 `chunkedTransfer / useCrcForCachedBundle / …`。
5. **`redirectLimit=32`** 是照 `Common` 布局读出的原始值；未做运行时对照（UnityWebRequest 默认值也是 32，
   但"默认值"不能当证据）。
6. **`ObjectInitializationData` 的内部 payload** 只解到 provider 名（4 项）；其 `data` 字段未解（与 bundle 表无关）。
7. **334 个 asset location 的短 internalId**（`"0"`、`"d"`、`"db9"`…）：这是 bundle 内部容器键；
   "短键 → 资材"的映射要读 bundle 的 `AssetBundle` 对象，不在 catalog 里（已有 `_guid_resolve_probe.py` 那条链）。
8. **远端 CCD 的 `{CcdManager.*}` 运行时替换值**：来自 settings/远端，不在 catalog 里，未解。
9. **`catalog_main.json` 不能当校验源**：A 目录里那份 JSON 的 `m_BuildResultHash = a011a011…`、
   10,490 个 InternalIds，**既不是 A 也不是 B 的 build**（B 目录里的 JSON 与它字节相同，sha `567f96ae…`）。
10. **`catalog.hash`（32 hex）不是 bin 的 md5/sha256**（实测 md5 `bf24cf02…` / sha `34d91332…` 都对不上）；
    Addressables 自己的 catalog hash 算法未查。
11. **A1787 报告里的"1,304,923 B"**：只在 `d:/4/_tmp_view/...` 找到这一份（见 §四·1）；
    `d:/2` 下没有这个尺寸的 catalog。

## 四、顺手发现

1. 🔴 **A1787 原文那份 `catalog_main.bin`（1,304,923 B）不在 `d:/2`，在 `d:/4`**：
   `d:/4/_tmp_view/localboot_1002/前/com.unity.addressables/catalog_main.bin`（sha `bb176f45…`，
   2026-10-02 00:07）。`d:/2` 下 5 份 `.bin`（关服前存档 / unity_run_ref / 10.13游戏 / Warhammer 40k /
   assetripper_out）**全部是 A**（1,305,148 B / `34d91332…`）。
2. 🔴 **B（1,304,923）与磁盘上的本地包不是同一 build**：87 个 bundle 里 **40 个 hash128 不同、38 个 size 不同**；
   B 的 84 个本地 bundle 只有 **47 个 size 对得上**，而 3 个远端包 **3/3** 与缓存完全对上
   （localization `10,764,942` = 缓存 `__data` 一分不差）。反过来 A（1,305,148）是 **84/84 本地对上**，
   localization 与缓存是**另一 build**（`4fc53ae5…` 10,764,894 vs 缓存 `dca1724a…` 10,764,942，差 48 B）。
   ⇒ 引用"当前 build"时必须先说是**哪一份** catalog；A ≠ B。
3. **归档里"Android catalog 134 条 bundle 名"不是条目数**：三份 catalog 的 `KeyData` 实测都是
   **87 条 `.bundle` 键**。134 / 141 / 157 这类数字是"在文件里朴素扫连续 `*.bundle` 串"的口径
   （含 base 名、片段、被动态串拆开的部分）。判据 = `catalog_keys.tsv` 的 `.bundle` 行数。
4. **`decomp_full` 里没有 Addressables 的方法体**：25,096 个 `.c` 只覆盖 Assembly-CSharp + firstpass；
   `ls | grep -i ContentCatalogData|BinaryStorageBuffer|AssetBundleRequestOptions` = **0**，
   `grep -rl ContentCatalogData` = **0**。Addressables 的字段布局只能从
   `d:/2/Warpforge_code/Scripts/Unity.Addressables|Unity.ResourceManager`（签名桩）和
   `d:/2/tools/il2cpp_out/dump.cs` 拿；**Reader 的 sep 实参在 Ghidra 全量里没有**（§三·1 的根因）。
5. **同一个 bundleName 在旧 profile 缓存里还有更老的一份**：
   `d:/2/远端缓存_旧profile_1013/Unity缓存_按哈希/54bdb7b1…/dca75913…/__data` = 467,359 B，
   与新缓存 `ea8bca4f…` 的 531,962 B 不是同一份。⇒ **认版本要看 `<bundleName>/<contentHash>` 两级**，
   不能只看第一级目录名。
6. **`bundleNameId` / `hashId` 与 CCD 缓存布局一一对应**：第一级目录 = `bundleNameId`（如 `54bdb7b1…`），
   第二级目录/文件名 = `hashId`（如 `ea8bca4f…`）。这条可直接用来定位任何一只远端包；
   在 catalog 里远端包的 `internalId` 是 URL 模板（`remote-ccd`），其余 84 只是 `{...RuntimePath}\StandaloneWindows64\...`（`local-runtimepath`）。
7. **allcards 是卡 SO 总包**：5,701 个 asset location 依赖它，含全部 1,351 个 `RawCardScript`；
   `addressableVersion` 这条 key 指向的 `AddressablesBuildNumber` 同时依赖 `[122737, 120840]`
   （allcards + `Waprforge_monoscripts.bundle`）。
8. **`Waprforge_monoscripts.bundle` 是依赖数第一的包**（8,516 个 asset location 依赖它），
   多数资产同时依赖它和各自的内容包（这解释了依赖集大小 32/34 那种条目）。
