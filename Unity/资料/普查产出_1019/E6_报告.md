## 五、顺手发现（⛔ 都没顺手改白名单外的东西）

1. **接口需求（给 E3 / Core 的）**：`ValueOfEnchantments` 要完全对齐原版，需要引擎侧能枚举
   「场上单位身上的 activeEffects」并区分 `buffType`（至少 `addStats` / `enchantment` / `singleUse` /
   `choice` / `SecretOrder`）。现在 `UnitState` 只有折平的 `Attack/RangedAttack/MaxHealth` + 关键词
   ⇒ enchantment `+1` 与 `SecretOrder −2` 两档**永远补不上**。建议在 `UnitState` 加一个只增不减的
   「附魔记录」表（`buffType` + 数值 + 来源卡 id），由 `EffectResolver` 的加/减效果各写一次。
2. **`RuleEngineTest.cs:23470` 会红（预期）**：那条断言写死「带盾出口 = `dmg/3+1` = 3」，
   而原版是 **`目标的当前近战攻击/3+1`**；该夹具的盾单位攻击 0 ⇒ 新值 **1**。
   本批不改 `Editor/`（不在白名单），**请自检断言线在收口时把这条改到原版口径**（并保留「盾用掉后 = 9」那半）。
3. **`A2144` 第 3 条写错了原版**（详见 §一·1.2）：`ScoreDraw` 空牌库是 `−2 − 疲劳`，不是 `−2 − 手牌张数`。
   账上的「我们 vs 原版」两列都要改。
4. **`DropPod` 关键词在我们的解析表里是空支**：`KeywordTable.DropPod = "droppod"` 存在，
   但 `KeywordTable.Prefixes` **没有登记 `drop pod` / `droppod`** ⇒ 卡数据里写了会被 `Parse` 静默丢掉。
   池内 **0 张**卡带它（今天无行为影响），所以新加的 `dropPod → 0.5` 分支实际是「等数据/等登记」；
   要它活起来需要在 `Core/CardDef.cs` 的 `Prefixes` 补一行（**Core 归 E3**）。
5. **`59` 张卡的 `cardTargetScoringCriteria` 是死列**（`targeted=0`），其中 **12 张没有任何其他评分**
   ⇒ 原版 AI 出牌分 = 0。列表见 `资料/普查产出_1018/AUD_T06…` 之外的本轮统计（可按 id 重跑
   `gen_ai_scoring.py` 后过滤 `targeted==0 && cardTargetScoringCriteria`）。这不是数据 bug，
   但会反复被问「为什么 AI 不打这张」—— 建议写进卡牌线/引擎线的「已知的坑」。
6. **`ta=0 (any)` + 筛选字段**（如 `DA50 Sacred Standard`）在原版 `GetTargets` 里得到的是
   **空表**（`any` 不是「全部」，它落到函数尾部、候选表在 case 链之前是空的）。我们照做 ⇒ 该卡评分 0。
   数据作者显然想写的是「数友方 hero+minion」，但原版的 `targetsAffected` 忘了填 —— 属**原版数据缺陷**，
   ⛔ 不要为了「让它能打」自己补一个 `any = 全部`。
7. **87 张池内卡 `hasActiveAbility=1` 但 `desc` 里没有 `Ability:` 文本**（多为 `Duty:` / `Rally:` 形态）。
   我们的 `CardDef.Ability` 只从 `Ability:` 文本解析 ⇒ 这 87 张走其它入口（`Duty` 走替代行动），
   是否与原版动作表等价**没核**。**反向 0 张**（有 `Ability:` 文本且 flag=0）⇒ `AUD_T06` §4.4
   说的「今天行为恰好一致」这一半成立。
8. **`gen_ai_scoring.py` 的 bool 规范化**（§二末）是**必须保留**的一步：`cards_truth.json` 的 1/0
   数字在 Unity `JsonUtility` 下**不会**变 bool。同族的未来消费者（若直接读 truth）也会踩。

  `buffType(+0x38) ∈ {12,15,16}` ⇒ **+1**，若 `enchantment.spellType(+0x90) == 0x3C(60)` ⇒ **−2**；

  其余类型（含 3 addTrait / 4 removeTrait）**不加**。
- 落点 = `Data/AiScoring.cs` 的 `ValueOfEnchantments(UnitState)`：
  - **12/15/16** 读 `u.Instance.ActiveEffects`（E3 的层），用
    `Enchantments.IsEnchantmentBuffType` + `Enchantments.SpellTypeSecretOrder` 判；
    **花掉的附魔照样算**（原版不读 `usedEnchantment`）；
  - **addStats** 仍按「运行时属性 − 卡面属性」之和 ×0.5 —— 因为 E3 的 `ActiveCardEffect`
    **只承载附魔那一族**（`Attach` 明确拒绝非 12/15/16），addStats 效果没有对象可枚举。
    🔴 **接口需求（给 Core/E3，不改）**：若要把 addStats 也做成对象表，需要
    `CardInstance` 再收 `buffType == 1` 的 `ActiveCardEffect`（目前 `Attach` 会拒绝）——
    本批**没有**为了它去改 E3 的白名单文件。
- ✅ **验证（临时 harness，见六·末）**：`Attach(12)` ⇒ +1 · `Attach(15, spellType 60)` ⇒ −2 ·
  `Attach(buffType 1)` 被拒（不进附魔层）—— 三条全过。

### 六·② option 5 / option 12（原「只加 base」的两类）

**option 5 `ValueOfBuffingAttack`（8 条）** = 原版 `ScoreFromBestAttack`（**RVA 0x939A00**；
⚠️ `AUD_T06` 写的 0x939B00 是 `ScoreFromBuff`，差 0x100）：
- 语义（反汇编 + `AI__ScoreFromBestAttack.c` + `AI__ScoreFromBuffedAttack.c`）：
  `base + (对该目标「带 buff 的最佳攻击分」−「不带 buff 的最佳攻击分」) × sideMul × multiplierCount`；
- `GetPotentialBuffedAttackActions` **只枚举近战 action**（`actionType=1`），所以只算近战；
- 攻击力 = `CurrentMeleeAttack + buff.meleeAttackChange`（⛔ 不是 `FieldAttack`）；
- 目标分 = `ScoreDamaging(target, atk, ignoreDroppod: true)`；会被反击 ⇒ 扣
  `ScoreDamaging(attacker, target.Attack)`，反击后还活着 `+0.1`。
- 落点 = `AiScoring.BestAttackScore`；⚠️ **未做**：`extraScoreFromAttacking / …TargetingOnAttack`
  （真值 0 张非零）、poisonous 的追加分（需要原版 `EnemyReturnsAttack`/bastion 组合，未逐条核）。

**option 12 `ValueOfBuffingCost`（2 条）** = 原版 `ScoreFromHandBuff`（RVA 0x93B7A0）：
- **`handEffect == null` ⇒ 0**（第一句 early return）。⚠️ `cards_truth.json` 会把全默认的
  `handEffect` **整个省略**（`compact_hand_buff`）；生成器现在**从 `cards_raw.json`（`full_raw`）补回「存在性」**
  —— 池内那 2 条（`GSC54 Rampant Infestation` / `Greatest Deeds`）在 SO 里都是**非 null 的默认对象**。
- 算法：`manaLeft = 当前能量`、`change = handEffect.cardEffect.costChange`；
  - 每个手牌候选：`CurrentCost ≤ manaLeft` ⇒ `playable++`；
    `manaLeft < CurrentCost ≤ manaLeft − change` ⇒ 取它 `ScoreFromPlayingCard` 的最大值；
  - `score = best − 3 × playable`（常数 3.0 @ `0x1834B2E8C`）；
  - `cardEffect.untilEndOfTurn` 为假 ⇒ 再加
    `(−change) × 2 × (multiplyByFriend × (友方候选数−1) + multiplyByEnemy × 敌方候选数)`
    （`limitedUses` 时两个计数夹到 `numberOfUses`）。
- 落点 = `AiScoring.HandBuffValue`。⚠️ **我们数据里两条的 `cardEffect` 全默认（`costChange=0`）**
  ⇒ 结果 = **`−3 × 已经打得起的手牌数`** —— 这是原版算式的结果，不是我们造的；
  `ScoreFromPlayingCard` 递推不带目标（原版会把动作目标传进去；池内 2 条都无目标）。

### 六·③ `conditionsFilter = 221 diedThisTurn`（1 条）

- 判据 = `FilterMethods__MeetsConditionCriteria.c:258` → `CardScript__HasDiedThisTurn.c`：
  **`card.turnDied(+0x250) == battleManager.turnCounter(+0x3F8)`**。
- 落点 = `AiTargets.MeetsCondition` case 221：扫 `ctx.DeadUnits`（`{Card, Owner, DeathTurn}`，
  `BattleContext.cs:85-101`），`Owner == 候选侧 && Card == 候选卡 && DeathTurn == ctx.Turn`。
- ⚠️ **边界**：`DeadUnit` 按**卡模板**存（那条注释自己写着「要精确到某一次的死亡得再动那张表」）
  ⇒ 同名牌两张死在不同回合时，这条会同时认定两张都「本回合死过」。
