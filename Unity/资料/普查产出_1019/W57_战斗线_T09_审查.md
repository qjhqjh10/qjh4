## 二、问题清单（按严重度）

### P0-1（本批引入，A3-e3）技能面板的全屏捕获区吃掉「点目标」⇒ 目标型主动技能在真机上按不出来

- **错在哪**：`SkillPanel` 新建成原版那块**远大于屏幕**的透明捕获区 `HideAbilityButton`（`SkillPanel.cs:205-206` 的 3707.83×1985.32；`:662-676` 建件并把 `raycastTarget` 置 true；`:815-823` 显示时 `SetActive(true)`），它的 `PointerDown` 是 `Hide()` + `CloseRequested`（`:783-789`）。而**棋盘单位仍是 3D 网格**、不是 uGUI 件 ⇒ `EventSystem` 的射线在整屏上**唯一能命中的就是这块捕获区**。
- **后果**：玩家进入「选目标」时（`BattleDriver.cs:10218` 弹面板 → `SetInputEnabled(true)`），**每一次点合法目标**都先触发捕获区 ⇒ 面板 `Hide()` + 驱动 `ClearSelection()`（`BattleDriver.cs:10278-10282`）⇒ 松手那一帧 `_selectedSlot == -1`，`BattleDriver.cs:9890-9904` 的 ④ 分支再也走不到 ⇒ **技能无法释放**（并且每次点击都只是把面板关掉）。原版不会这样，因为原版的棋盘卡自带 `UI Collider`（uGUI 靶）会先吃掉点击 —— 我们的卡还是 3D。
- **应该是什么**：在卡格迁 uGUI 之前，`HideAbilityButton` 的 `PointerDown` 必须先判「指针下是不是合法目标」（`LegalTargetCode(WorldPointer()) >= 0` ⇒ 不关、把这一下留给驱动），或者只把捕获区限制在面板之外的**非棋盘**区域，或者把 `Hide()` 延后到「确认没有目标」再执行。
- **判据**：`SkillPanel.cs` 文件头自述「远大于屏幕的捕获区」（`:105-115`）；`WIRE:238-244` **已经如实记了这条**，但把它写成「第一次真 Play 必须先验」——按静态读它不是「可能」，是**必然**（射线路径上没有任何东西能挡在它前面）。
- **备注**：这不是「未实测所以不确定」，是结构性的。**真 Play 之前必须先修或先加闸**，否则技能这一整块不可用。

### P0-2（本批之外 · 既有，A462 2026-10-13 引入）`HandleReplayBar` 先吃掉松手沿 ⇒ 所有排它后面的 release 分支在真机上可能收不到

- **错在哪**：`Update` 的调用顺序是 `TickMultiCards → TickCardWinPointerExit → TickCardDisplayClick → **HandleReplayBar** → TickMulligan → HandleMulligan → HandleChoose → … → HandleSettings → HandleChatPopup → … → DrivePlayerTurn`（`BattleDriver.cs:9538-9649`）。`HandleReplayBar` 第一句是 `if (_replayBar == null || !ReleasedThisFrame()) return false;`（`:4910-4914`），而 `ReleasedThisFrame()` 是**破坏性**的（`_upEdge = false`，`:21891-21897`）。`_replayBar` 在 `BuildHudExtras` 里**必建**（`:18989-18990`），普通对局只是 `Setup(false)` 把 holder 关掉，**不是 null**。
- **后果（静态推演）**：普通对局里每一次松手，**先被 `HandleReplayBar` 消费掉**（`ReplayClickAt` 因 `HolderVisible=false` 返回 false，但沿已经没了）⇒ 之后的 `HandleMulligan`(`:5144`)、`HandleChoose`(`:6633`)、`HandleChatPopup`(`:4524`)、`DrivePlayerTurn` 的 `ReleasedThisFrame()` 分支（`:9876` 牌堆 / `:9890-9904` 选目标）**在真机上都收不到**。自检全部直调 `Tick*ForTest` / `DrivePlayerTurnForTest`，绕过了 `Update`，所以全绿。
- **这一条对本批的意义**：本批把 Chat/Log/选牌/换牌/技能的 uGUI 层做出来了，但**动作仍留在手搓路**（Chat 选台词、BattleLog 行、选牌面板、换牌面板）；如果这条成立，那些面板在真机上本来就不工作 —— **本批的「手搓路仍可用」前提不成立**。另外它**暂时掩盖了 P1-1**（见下）。
- **应该是什么**：`HandleReplayBar` 在 `!_replayBar.HolderVisible` 时**不许消费沿**（把 `HolderVisible` 判到 `ReleasedThisFrame()` 之前），或把回放条挪到所有 release 消费者之后。改之前先用真机 5 分钟验一次「换牌 Done / 选牌 Done / 点牌堆 / 点目标」是否真的不响应。
- **判据**：上面行号逐条现读；A462 提交 `29d73be0`（2026-10-13）把这里从 `ClickedThisFrame()` 改成 `ReleasedThisFrame()`，同为破坏性、同位次。**不是本批引入**，但**会否决本批的验收前提**。

### P1-1（本批引入，A3-e2 / A3-e4）多卡窗 / 展示窗的 uGUI 关闭「当场 Hide」，与另三扇的 `LateUpdate` 延迟不同 ⇒ 修好 P0-2 后会立刻暴露「点继续反而重开牌库」

- **错在哪**：`MultiCardDisplay` 的 `_bar` / `_bgClose` 直接 `BattleHudButton.Attach(..., Hide)`（`MultiCardDisplay.cs:492 / 526`），`Hide()` 立刻把 `Visible=false`（`:697-706`）；`CardDisplayWindow._backdrop` 同样直接 `Attach(..., Hide)`（`CardDisplayWindow.cs:581`，`Hide()` 立刻 `Visible=false`，`:1249-1267`）。
- **为什么另三扇没问题**：`ChatPopupPanel` / `BattleLogPanel` / `AlliancePanelWindow` 都是「uGUI 只记 `_closePending`，`LateUpdate` 再落账」（`ChatPopupPanel.cs:659-693`、`BattleLogPanel.cs:650-672`、`AlliancePanelWindow.cs:895-917`），注释里写明的理由正是「`EventSystem.Update` 与 `BattleDriver.Update` 都是默认执行顺序」。
- **后果**：若 `EventSystem.Update` 先跑，uGUI 在松手那一帧已经把窗关掉 ⇒ `TickMultiCards` 的 `if (!Visible) return false`（`:9664-9666`）直接放行 ⇒ 同一松手落到 `DrivePlayerTurn` 的 `HitMyDeckPile`（`:9876-9879`）⇒ `ShowMyDeck(true)` **把牌库窗又打开**。几何上这不是小概率：Continue 条 x[1322.7,1900.2] y[937.3,1016.9]（`BarCx/BarCy/BarW/BarH`，`MultiCardDisplay.cs:148`）与牌堆命中区 x[1615,1845] y[850,1080]（`MyDeckX01=0.90104 / MyDeckY01=0.10648`，`BattleDriver.cs:1456 / 8883`）**大面积重叠**。展示窗的整屏 backdrop 同理。
- **现状**：这条**目前被 P0-2 掩盖**（松手沿先被 `HandleReplayBar` 吃掉，落不到 `DrivePlayerTurn`）。⇒ **修 P0-2 时必须同批给这两扇补延迟关闭**，否则修好一个立刻炸另一个。
- **应该是什么**：照 Chat/Log/联盟的配方：uGUI 回调只置 `_closePending`，`LateUpdate` 落 `Hide()`；或者驱动在 uGUI 关闭的那一帧置 `_swallowNextRelease`。

### P1-2（已知，本批确认）展示窗的全屏 backdrop 会压住仍是 3D 的卡格 ⇒ 点相关卡 = 关窗

- **错在哪**：`CardDisplayWindow._backdrop` 是整屏透明 uGUI 靶（`CardDisplayWindow.cs:571-584`），而展示窗里那几张卡是**世界空间 `CardView`**（`_cardsShell`，`:598-610`）。驱动的 `HitSlot → SwapToFront` 仍是手搓路（`BattleDriver.cs:8851-8858`），但 uGUI 的射线在整屏上只会命中 backdrop。
- **后果**：点相关卡这一下**一定会先关窗**；`SwapToFront` 是否同时发生取决于 `EventSystem.Update` 与 `BattleDriver.Update` 的先后（先驱动 ⇒ 换位+关窗；先 EventSystem ⇒ 只有关窗）。两种都不是原版（原版卡自己的 `UI Collider` 先吃掉点击、只换位）。
- **应该是什么**：`T09` 第 5/6 步把卡格迁 uGUI，或在 backdrop 上按 `HitSlot` 放行（与 P0-1 同一类修法）。
- **判据**：`A3-e4` 报告 §三·4 与 `WIRE:245-247` 已如实记；本条只是**确认它是结构性的**。
