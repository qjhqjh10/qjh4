## §二 判据与实现（逐项）

### 2·1 多候选「时间错开」—— 数据在哪、怎么钉、为什么不是固定间隔

**判据（第一权威，E12 已逐行读过并落成数据）**
- 原版 `AbilityLogic.PlayAnim` 把 `cardAnimations[]` 的**每一条**压成一条 `playAnim` 动作；
  `BattleManager__ResolveActionFromQueue.c:44-76` 队列**一次只弹一条**；
  `BattleManager._ResolveAnim_d__466__MoveNext.c:200-210` 每条 `WaitForSeconds(GetAnimDuration)` 才结束
  ⇒ **第 n 条的起点 = 前面各条时长之和**。
- 数据侧（E12）：`cards_engine.json` **v12** 每卡 `animTimes[]`，字段 `a`（CardAnim 名）/ `n`（prefab 名）/
  `tg`（原版 trigger）/ `o`（路径索引）/ `d sd s m e`（五个原始时间）/ `u`（= `GetAnimDuration`）/ **`t`（组内累计起点）**。
  `CardDef.AnimTimes` / `CardAnimTime`（`RuleEngine/Core/CardDef.cs:258-296`）；运行时表
  `Resources/card_vfx_by_card.json` 的 `es[].a` 是**精确 join 键**（E12 报告 §5·1）。

**怎么钉（`Core/VfxMap.cs`）**
1. `ByCard` 的值从 `List<string>` 改成 `List<CardPick>`（`N` = prefab 名，播放用；`A` = `es[].a`，join 用）。
   对外 API 一个字没变（`Resolve` / `ResolveAll` / `AllNames` 仍给字符串，`AllNames` 取 `N`）。
2. 新增 `ResolveAllTimed(evt, faction, cardIdOrName, times)`：
   - 逐条在 `times` 里找**它自己那条** `AnimInfo`：首选 `Anim == A`；`A` 为空 ⇒ `Prefab == N`；
     游标**只前进**（同名 `CardAnim` 在一张卡里可重复，现读 59 行 ⇒ 按数组顺序逐次消费，不去重）；
   - **钉不上 ⇒ `T = 0`**（= 改前的行为）；⛔ 不拿别的候选的时长凑一个；
   - **单候选 ⇒ `T` 恒 0**（回归口径；理由见 §三·2）；
   - `Duration` = 该条 `CardAnimTime.Duration`（给演出闸/队尾用，见 2·1·b）。
3. 现读分组：`t` 的组键是 `(卡, 原版 trigger)`；本表的事件键更粗（`Strike`/`Slay`→`trigger`，
   多条 trigger→`ability`）。现读 **23 行**多候选混着不同 trigger 组 ⇒ 那些候选的 `t` **各自从 0 起**
   （数据本来如此），**如实保留**（⛔ 不把后一组累加到前一组上 = 不编间隔）。

**a) 测算（可复现，本轮 Python 现读）**
- 逐卡逐事件复刻「折叠最优档 → 贪心按 `a`/`n` 匹配」：**2,517** 条候选里 **1,514** 条钉上、**608** 条钉不上；
  另有 **395** 条所在卡**整张没有 `animTimes`**（三数相加 = 2,517）。钉不上的那 608 条**全部**是
  「`a`/`n` 根本不在该卡的 `animTimes` 里」的来源（卡 SO 顶层字段 `customRangedAttackParticles` 等 /
  我们的 `inferred-*` 推断档）⇒ **本来就没有逐候选时间**（不是匹配算法漏了：按相反顺序再查一次
  「该选的那条在游标前面」= **0 条**）。
- 多候选行 **382** 条，其中 **381** 条**每一件**都钉得上；同一行里出现「后一件 `t` 比前一件小」的有 **11 条**
  （就是上面那 23 条跨 trigger 组的子集）⇒ 那些候选可能同时播（如实记，见 §三·4）。
- 首候选 `t`：有 `animTimes` 且有命中的 1,008 行里 **993 行 = 0**；15 行 > 0，原因都是
  「它前面还有一条被本表过滤掉的纯计时拍 / 别的触发拍」（例：`Bomb Squig` 的 `death` 前面有 `Wait_1s`
  ⇒ 爆炸原本就在 1.0 s 后；`Dimensional Breach` 的 `deploy` 前面有 3.0 s 的战场特效）。
- 最小非零 `t` = **0.1 s**（466 个非零值），它支持 `VfxTimeEpsilon = 1e-3` 不会吞真实错开。

**b) 排进现有时间线泵（`Battle/BattleDriver.cs`）**
- `FireEventAll` 两个重载：`T <= 1e-3` 的候选**当场** `CardEffects.Fire`（首候选 = 行为不变）；
  `T > 1e-3` 的走 `ScheduleVfxCue(name, pos, points, parent, T, Duration)`。
- `ScheduleVfxCue`：`at = _clock + T`，往 `_timeline` 里加一条 **cue**（`PendingSignal.cueVfx`），
  并把 `_timelineTailAt` / `_blockingQuietAt` 推到 **`at + Duration`**（原版队列要等这一拍演完才放行下一条动作；
  只推起点会让下一批事件压在它身上开场）。
- `AdvanceTimeline` 弹到 cue **只做一件事**：`CardEffects.Fire` —— ⛔ **不重演事件级副作用**
  （语音 / 战斗音效 / 手感补间 / 血账 / 视图同步那些在事件那一拍已经跑过）。
- 补卡池查询：`AnimTimesOf(cardId, faction)` = `CardDatabase.Find(_pool, …).AnimTimes`（null ⇒ 全 `T=0`）。

### 2·3 `_pendingDeploy` 身份守卫（名字 → 卡实例 id）

**改法（`Battle/BattleDriver.cs`）**
- 账型：`Dictionary<int,int> _pendingDeploy`（键 `HpKey(座位,格号)`，值 = **`CardInstance.Id`**）；
  第二本 `Dictionary<int,string> _pendingDeployByName` = **`InstanceId == 0` 的退路**（与 B5 的
  `_pendingHp` / `_pendingHpBySlot` 同一形状）。
- `NotePendingDeploy`：`e.InstanceId != 0` ⇒ 先验**那一格站着的是不是这一份**（`u.InstanceId != e.InstanceId`
  ⇒ 不记 —— 同名的另一份不算「这一格已经换人了」）；`0` ⇒ 退回名字口径。
- `CompletePendingDeploy`：按实例 id 销账；**账上那一笔不是这条事件的人**（同一批里这一格又换过手）⇒
  **不销、也不放视图**（那一笔由它自己那条 `Deploy` 销）。
- `IsPendingDeploy(owner, slot, u)`：先查 id 表（`u.InstanceId != 期望` ⇒ 当场作废），`InstanceId == 0` 那档查名字表。
- 清账点成对清：跨局（`:3330`）· `DropSignals`（`:13675`）· `SyncBoard` 空格（`:15465`）。
- 自检口：`DeployPendingForTest` 兼容两本账；新增 `DeployPendingInstanceForTest`（读账上的 id）。

**判别式（自检断言 `:24950` 那条）**：两个**同名、不同实例**的单位 A/B；事件说的是 A（`InstanceId = idA`），
而那一格现在站着**同名的 B**（且 B 没有视图）——
- 新口径：`u.InstanceId(idB) != e.InstanceId(idA)` ⇒ **不记账** ⇒ B 的视图**照建**；
- 旧口径（按名字）：名字相同 ⇒ 被当成「还没演到」⇒ 这一帧**没有视图** ⇒ 断言红。
反方向（正例）：事件说的就是那一格的人 ⇒ 账上记的必须是 **实例 id**（名字口径记不出这个数）。

## §三 没查清 / 不猜

1. **跨 trigger 组的 11 行**：`t` 的组键是 `(卡, trigger)`，而本表事件键更粗 ⇒ 不同组的候选各自从 0 起、
   可能**同时播**。这是 B3 的「事件归口」近似（`gen_card_vfx_by_card.py` 的 `TRIGGER_EVENT`），
   本批**只做时间、不动归口**。⛔ 不把后一组的 `t` 累加到前一组上（那是编一个间隔）。
2. **单候选为什么 `T` 恒 0**：15/1,008 行的首候选 `t > 0`（前面有一条被本表过滤掉的纯计时拍）。
   若单候选也按绝对 `t` 延迟，会凭空多出一段「这一拍什么也没发生」的等待；而本件的目标是
   「**同组多候选**错开」。⇒ 单候选保持 `T=0`（回归口径，任务明确要求「单候选取值不变」）。
   ⚠️ **这是本批唯一一处「不用绝对 `t`」的地方**，判据与代价写在这里；若将来要改成绝对口径，
   只需删掉 `ResolveAllTimed` 里那句 `picks.Count <= 1` 的提前返回 —— **但它会让那 15 行多出 0.2~3.0 s 空等**。
3. **`randomAbilityChoice = true` 的「按组随机抽一组」**：仍是 B3 记的账（数据侧有 `rc`，VfxMap 没消费）。
   现读唯一为真的是 `GOF12 Spanner`，5 条 logic 的 prefab 全相同 ⇒ 今天无可观测差异。**本批没动**。
4. **同名 `CardAnim` 的 59 行**：贪心游标（只前进）是 E12 §5·1 指定的做法；本轮量到 **173** 条候选的 `a`
   在一张卡里出现多次，其中 **81** 条贪心选了「后面的那次」（前面那次已被前一件消费）——
   本轮**没有发现** `before-cursor` 型失败（即「该选的那次在游标前面」= 0 条）。
   断言夹具额外要求「`Anim`/`Prefab` 在整张卡里都唯一」⇒ 自检**不依赖**这个贪心在歧义样例上的选择。
5. **`Duration` 的边界**：只用于「演出闸 / 队尾」的收尾时刻，没有参与播放时刻（`T`）。
   数据里 `t + u` 最大 **7.0 s**，`StepThrough` 的上限 9 s 够用（同族先例：`A1816` 把它从 6 抬到 9）。
6. **没有跑真机**：`t` 的观感（多候选是不是「一段接一段」）只能真 Play 看 ⇒ 见 §五·2。
