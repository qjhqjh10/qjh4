## 一、结论

### 1.1 `buffEffect` 的收益方 = **`CardScript.AddEffect` 被调用的那张卡**（不是「施放者」也不是「同族」）

`AbilityLogic.buffEffect` 在 `AbilityLogic.PlayAbility`（VA `0x18081C000` / RVA `0x81C000`）里共 **4 个「取实例」点**（`GetNewInstanceOfThisEffect`：`:837 / :917 / :1187 / :1337`）+ **1 个只传引用**（showCardsWindow）—— **收益方在调用点就定死了**：

| `chosenAbility` | 消费点（`AbilityLogic__PlayAbility.c`） | 收益方 |
|---|---|---|
| `buffOthers` 30 / `buffOthersNotResetPool` 31 | `:1186-1187` 取实例 → `:1218` `BattleManager__AddEffect(manager, target, effect, …)`，逐个目标一份实例 | `AbilityLogic.GetTargets(targetCriteria)` 选出的**每个目标**（`possibleTargets`，`AbilityLogic+0x78`） |
| `buffSelf` 40 | `:1336-1337` 取实例 → `:1369` `AddEffect(manager, AbilityData+0x10 …)` | `AbilityData.thisCard`（`AbilityData+0x10`）= **能力所属的那张卡**（不是 `actingCard`，`actingCard` 在 `+0x18`） |
| `summonUnit*` 70/71/72/75 | `:829-838`（读 `buffEffect.enchantment` / 取实例） | **新召唤出来的那张卡** |
| `transformSelf(WithBuff)` 80/85 | `:916-917`、`:2852-2853`（`AddTransformCardWithBuff`） | **变形后的那张卡** |
| `showCardsWindow` 470 | `:1926-1931`（只把 `buffEffect` 传给 `AddShowCardsWindowAction`） | **只用于展示**，不落效果 |
| **`doDamage` 10 / `doDamageFast` 13** | `:1461-1508` —— 只建 `DamageInfo` + `DealMultiDamage`，**整个 case 不读 `param_1+0x50`** | **没有人**（字段被忽略） |

落地链（任何一支都一样）：
`BattleManager.AddEffect`（排队）→ `ResolveAction` 的 addEffect 分支 `:1360 CardScript__AddEffect(目标, effect, -1)` → `CardScript.AddEffect` 里按 `effect.buffType` 分派。
`addTrait(3)` 的分支在 `CardScript__AddEffect.c:460-499`，最后一行 `:499 CardScript__AddTraitSilently(param_1, effect.trait(+0x3c), …)` —— **`param_1` 就是 `AddEffect` 的 `this`（收件卡）**。

`extrinsic`（`CardEffect+0x30`）= 效果**生命周期**绑到「施放来源」而不是目标（`PlayAbility:1195-1196` 用 `AbilityData.whileInPlay/whileInPlayVariable` 覆写；`enchantingCard = AbilityData.thisCard` 在 `:1209`），**不改变收益方**。

### 1.2 `addTrait fast`：`fast` 是 **trait/关键词**，不是 `side` 参数、不是种族

- 值：`BuffType.addTrait = 3`（`BuffType.cs:6`）· `DefinedTrait.fast = 40`（`DefinedTrait.cs:7`）。
- 字段：`CardEffect.buffType`（`CardEffect.cs:38` / dump.cs `0x38`）· `CardEffect.trait`（`CardEffect.cs:40` / `0x3C`）。
- 施加：`AddEffect` case 3 → `CardScript.AddTraitSilently(card, 40, hide, value)`：
  - 先按 `card+0x128`（`CurrentTraits`）去重（`Enumerable.Any(x => x._trait(+0x18) == 要加的 trait)`，命中就 return；同型 lambda 见 `CardScript.__c__DisplayClass490_0___AddTraitSilently_b__0.c`——⚠️ 该文件**文件名与内容不符**，里面装的是 `EntityScript.<>c__DisplayClass228_0.<IsShowingTrait>b__0`，但函数体正是 `param_2+0x18 == param_1+0x10` 这一个比较），再 `CardTrait__GetNewTrait` 写进 `card+0x128` 与 `card+0x130`（`CardScript__AddTraitSilently.c:26-60`）。
  - `EntityScript.HasCurrentTrait(fast)` 的判定 = **在 `+0x128` 的 trait 列表里** 或 **在 `+0x108` 的 activeEffects 里有一条 `buffType==3 && trait==40`**（`EntityScript__HasCurrentTrait.c:18-31` + `:34-47`；`+0x128` = `CurrentTraits`、`+0x130` = `CurrentShowingTraits`，见 dump.cs `EntityScript` `:22030-22031`）。
- **何时生效：立刻。** `CardScript__AddEffect.c:570-572`：trait 是 `fast(0x28)` / `flank(0x1cc)` 时**当场**调 `CardScript__UpdateSummonSicknessAnims(card)` → 重算 `displaySummonSickness`（现在为 false）→ `CardScript__ActivateMinion` 把 `canAct(+0x230)` 与 `canAttack(+0x23C)` 一起写成 `!displaySummonSickness`（`CardScript__ActivateMinion.c:25-26,39-42`）⇒ **当回合就能动/能攻击**。
- `fast` 的消费点（**读 `HasCurrentTrait(…, 0x28)` 的只有两处**；另有「按 trait id 判断」的两处，见下）：
  1. `EntityScript__get_displaySummonSickness.c:7-10` —— `+0x58(summonSickness) && !fast && !flank` ⇒ 免召唤病（含 UI 动画与 `ActivateMinion`）；
  2. `BattleManager__IsValidAttackTarget.c:201` —— 刚下场的单位**不带 fast/flank 就不能打敌方部队**；
  3. 部署那一刻 `CardScript__ActivateTraitsOnSummonOrEnchantment.c:76-85`（按 **trait id** 判）= `fast/flank` ⇒ `canAct = true`（`card+0x230`）；
  4. `CardScript__AddEffect.c:570` （按 **effect.trait** 判）= 刚挂上 `fast/flank` 时**立刻**重算召唤病。
  （`ferocity/oath` 只抬 `canAct`、`canAttack=false`，**不属于** fast 那一档，别混。）
- 卡面语义一致：官方本地化 `CardTraitDescription/fast` = "This unit can attack the same turn it goes into play"／「此单位可以在进入战场的同一回合攻击」；规则书（旁证）`:185` 同义。

### 1.3 关键判定：**GOF92 等 18 张 Unstable 单位的 `addTrait fast` 在原版里是死字段（no-op）**

`GOF92` ability 0（`cards_raw.json`）：
`trigger=81(Unstable)` · `chosenAbility=10(doDamage)` · `damageCriteria{valueOptions=90(RandomizedOnResolution), 1-3, damageType=5(Random)}` · `buffEffect{buffType=3, trait=40(fast)}` · `targetCriteria{targetsAffected=10, friendly+enemy, hero+minion+remnant, maxTargets=1, conditionsFilter=220, excludeCondition=1}`。

**判据四条，互相独立：**
1. **代码**：`PlayAbility` 的 `case 10/0xD`（`:1461-1508`）**不访问 `AbilityLogic+0x50`**；全文件里 `GetNewInstanceOfThisEffect(buffEffect)` 只出现在 `:837 / :917 / :1187 / :1337`（summon / transform / buffOthers / buffSelf）。⇒ 原版跑 GOF92 这条 Unstable 时，`buffEffect` 一次都不会被实例化。
2. **数据形状**：当前 build 全池 **18 张** `trigger=81` 的 Unstable 能力在 `chosenAbility / buffEffect / damage / maxTargets / targetCriteria` 这几格上**完全相同**（`10 / bt3 / trait40 / 1-3 / maxTargets1`），全部是兽人 Unstable 单位 —— 这是一份**共享模板**；它们的卡面/官方描述**没有一张提到 Fast**。
3. **官方文案**：`CardTraitDescription/unstable` = "When this unit dies, it deals 1-3 damage to a random unit"／「当此单位死亡时，对一个随机单位造成 1-3 点伤害」；`Card_Description/GOF92` = `[[unstable]]. [[shield]]. [[talent]]: $$e3d67d…$$`；成品卡图 `d:/2/Warpforge部队卡片/Orks/3部队/Warpforge_17_Weirdboy.png` 印的是 **Unstable. Shield. Talent: Waaagh! Energy** —— 没有 Fast。
4. **对照**：`fast` 真正被消费的卡，数据形态都是 `buffSelf(40)` / `buffOthers(30)`：`GOF7 Warbiker`（trigger 0 / chosenAbility 40 / fast，卡面「Rally: … gain Fast」）、`SAU3 Flayed One`（570 Reanimated / 40 / fast，「When Reanimated, gain Fast」）、`ASH67 Hornet`（600 / 40 / fast）——**它们的卡面逐字写着 Fast**，而 GOF92 这一族一个字都没有。同一套代码/数据里两种形态泾渭分明。

⇒ **`A1916` 的正确落法不是「补实现」，而是「按原版 no-op 关账」**（铁律 11 例外①：原版本身没有这个行为）。我们的 `RuleCore.UnstableBlast`（关键词通用实现）已经与「代码真正会跑的那部分」一致，**不需要为 GOF92 加任何 Fast 授予**。

> 顺带：`AI` 侧不读 `AbilityLogic.buffEffect`；`ScoringCriteria.buffEffect`（`ScoringCriteria.cs:50`）是**另一个类**、只给 AI 打分，且 18 张 Unstable 的 `attackScoringCriteria` 里也没有 trait 授予。别把两个 `buffEffect` 混为一谈。

## 三、最小实现方案（若判据够）

### 3.1 对 GOF92 / A1916：**不改引擎代码**

- **原版语义 = 无效果**（`doDamage` 分支不消费 `buffEffect`）。我们的 `UnstableBlast` 已经覆盖「1-3 随机、排除已注定死亡的、含双方/督军/残骸、maxTargets=1」这套真实行为。
- 关账动作（给调度台，**本代理未做**）：
  1. `A1916` / `A1994(a)` / `A1914` 一并按「**原版 no-op（死字段）**」关账，判据写本报告 §1.3 四条 + `AbilityLogic__PlayAbility.c:1461-1508`；
  2. `_a1759_reconcile.py:1010-1018` 那条 `③·a` **保持现状即可**（结论不变，注释可加一句「`addTrait fast` 在原版不被消费，属序列化残留」）；
  3. `W5_对账_1019.tsv:1377` 那一行的说明已经写成「别层承载·关键词」，无需改判定，只需在人工台账里注明「红格已定案 = 原版不生效」。

### 3.2 若将来真要「让我们的引擎消费 raw `buffEffect:addTrait`」（现在不需要）

- **只在 `chosenAbility ∈ {30,31,40,70,71,72,75,80,85}` 时**才该施加；`10/13` 一律忽略。
- 收益方照 §1.1 的表选卡；施加 = `UnitState.AddKeyword("fast", 1)` **+ 立刻重算一次部署态**：`RuleCore.ApplyDeployTurnState(u, keepStatus: true)`（`RuleCore.cs:2522-2564`，它算的就是 `SummonSickness && !fast && !flank → Exhausted/CannotAttackThisTurn`，与原版 `AddEffect.c:570-572 → UpdateSummonSicknessAnims → ActivateMinion` 一一对应）。⚠️ 只 `AddKeyword` 不清位的话会「有关键词却动不了」（`EffectResolver.cs:5909` 的坑，`UnitState.AddKeyword` 不会重算 `Exhausted`）。
- 但注意：我们引擎是**文本驱动**的，`fast` 的真卡（Warbiker / Flayed One / Hornet）已经从 `desc` 的 `gain Fast` / `give it fast` 走 `give/gain` 通道落地（`EffectResolver.DoGive` → `AddKeyword`），**不需要另开一条 raw buffEffect 通道**。

## 四、仍缺什么

- **没有阻塞项。** `AbilityLogic__PlayAbility` / `CardScript__AddEffect` 方法体都在（全量反编译 99.97%，7 个失败方法不涉及这两处），不是「代码被剥」。
- **唯一的残余风险（低）**：本结论是「反编译代码 + 同一 build 的卡数据」的静态结论，没有跑实况（本代理只读，且按铁律 12 不做事后验收）。若要 100% 封口，可在以后真机轮次里做一次 **Unstable 单位死亡**的实拍：看被打中的单位身上**是否出现 fast 图标**（预期：没有）。这不影响现在按「no-op」结账。
- 若日后有人把 `buffEffect` 误接到 `doDamage` 上，反例就是本报告 §1.3 第 1 条（代码根本不读 `+0x50`）——别拿「数据里有」当「原版会做」。
