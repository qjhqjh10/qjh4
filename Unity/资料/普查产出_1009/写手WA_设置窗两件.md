## 件 1 —— A202①：`UpdateFpsDrag` 的手算几何 → `WfSlider.HitBand`

### 判据
- `Battle/WfSlider.cs` 的 `HitBand(trackL, trackR, halfTrackH, handleCx, halfHandle, hasHandle, …)` 是**唯一一份**命中几何
  （`Contains` 走它；`UpdateFpsHit` / `FpsHitRectPx` 也走它）⇒ 设置窗那条路不许再留第二份。
- 手感/原版：`Background`（轨道）与 `Handle`（手柄）两颗 Image 的 `m_RaycastTarget` 都是 **1** ⇒ 命中 = **轨道 ∪ 手柄**。

### 改了什么（`Shell/SettingsWindow.cs`）
1. **新增 `FpsHitBandCanvasPx(int idx)`**（约 `:858-865`）：`FpsHitRectPx(idx)`（原版设计 px）→ `Screen()`（画布 px）。
   `UpdateFpsHit` 原来那两行（`FpsHitRectPx` + `Screen`）**改成调它** ⇒ 命中区 quad 与命中带**同一次调用**。
2. **新增 `FpsPressAtCanvas(float px, float py)`**（约 `:1027-1070`，`public`）：= `UpdateFpsDrag` 按下分支**本身**那段代码
   （行没建出来 / 落在命中带外 / 被视口裁掉 ⇒ 三种都返回 false 并把 `_fpsDragging` 清掉；否则 `_fpsDragging = true` + 记抓手偏移 + 取值）。
   `UpdateFpsDrag` 的按下分支现在只有一句 `FpsPressAtCanvas(LayoutSpace.PxX(wp.x), LayoutSpace.PxY(wp.y));`。
   ⛔ 删掉了 `px < s.x1-24 || px > s.x2+24 || py < s.y1-16 || py > s.y2+16` 那一整段（连同不再需要的 `var s = Screen(_fpsL…);`）。
3. **新增只读口 `public bool FpsDragging`**（约 `:1116`，与 `FpsIndex` 并排）—— 自检读的是**状态**。
4. 注释里写明两套值的**逐维对照**（旧带 vs `HitBand`），见 `FpsPressAtCanvas` 的 `<list>`。

### 两套值**并不等价**，但方向是「旧 ⊋ 新」（🔴 与简报的预期不同，如实记）
| 维度 | 旧（`±(24,16)`，从轨道矩形量起） | 新（`HitBand` = 轨道 ∪ 手柄） |
|---|---|---|
| 横向左端（0 档） | 842.57 − 24 = **818.57** | 853.37 − 15.93 = **837.44** |
| 横向右端（2 档） | 1284.63 + 24 = **1308.63** | 1286.43 + 15.93 = **1302.36** |
| 纵向半高 | 5.85 + 16 = **21.85** | `max(6.5, 17.703) × 0.9` = **15.93** |

⇒ **旧带在四个方向上都更宽**（新带 ⊂ 旧带）⇒ 任何「新带内」的点**旧带也认** ⇒
**简报设想的「正例那条红」不成立**。按简报的兜底要求，另加了一条**专门分辨两态**的探针（下面 ③）。

### 断言在哪（`Editor/SettingsScene.cs`，A168 那一节里、A193 之后，约 `:932-989`）
批处理里 `Mouse.current` 是 null、`Update` 也不跑 ⇒ 自检直调 `win.FpsPressAtCanvas(画布 px, 画布 px)`，断 `win.FpsDragging`。
期望值全是**原版字面量**手算（⛔ 不引 `SettingsWindow.FpsSliderW…`）：轨道画布 px `[842.57,736.76]–[1284.63,748.46]`
（与同节 ① 那条**已有**断言同源）、手柄实画 35.406 设计 px ⇒ **31.87 画布 px（半 15.93）**、`m_AnchoredPosition.x = 12`、滑区让位 10。

| # | 探针（画布 px） | 期望 | 🔴 改坏法（⇒ 红） |
|---|---|---|---|
| ① 正例 | 2 档 `(1290.63, 742.61)` = 轨道右端**之外 6px**、手柄之内（手柄右缘 1302.36） | `FpsDragging == true` | 命中带退回「只有轨道」那一块 |
| ② 正例（纵向） | 1 档 `(1069.90, 752.61)` = 中心线**上 10px**（轨道半高只 5.85、手柄半高 15.93） | `true` | 纵向半高只取轨道那一档（漏掉 `HitBand` 的 `max(…, 手柄半高)`） |
| ③ 🔴 **负例（分辨新旧）** | 0 档 `(828.0, 742.61)` —— 轨道与手柄**都不在那儿**（0 档手柄左缘 837.44），但**落在旧带里**（818.57） | `false` | **换回硬编码 `±(24,16)` ⇒ 旧带会认下它 ⇒ 红**（两边各留 9.4px 余量，不是浮点边界） |
| ④ 负例（真在外面） | 2 档 `(1324.63, 742.61)` = 轨道右端之外 40px（新带 1302.36 / 旧带 1308.63 都在外） | `false` | 带铺成一大块（例如 `±(60,40)`）⇒ 红 |

- ③ 之前 ② 刚把 `FpsDragging` 置成真 ⇒ ③ 不是「一直为假」；② 与 ③ 互为对照、① 与 ④ 互为对照 ⇒ **四类改坏法各有一条会红**。
- 探针**都不改档位**（算过 `SetFpsFromCanvasX` 的取整结果仍是当前档）⇒ 结尾一条 `Check(Application.targetFrameRate, f0c, …)` 钉住「进程帧率一个字节没动」。

### ⚠️ 有意的**行为变化**（记录在案）
收口后判据**变紧**：原来「落在旧带里、但既不在轨道也不在手柄上」的那一圈（例如中心线上下 16~21.8px 处）**会开始拖**，
现在**不开始拖**。这是**有意的** —— 原版那条射线的目标是「轨道图 + 手柄图 + **三个刻度 TMP**」，我们照旧只收
**轨道 ∪ 手柄** 这一份（刻度那段差额仍记在报告 §没查清 里，⛔ 不是在这里再补一份余量）。若认为刻度那一段也该认，
**那是另一条账**（要改的是 `FpsHitRectPx` / 命中区，不是把余量写回 `UpdateFpsDrag`）。

## 件 2 —— A208：联机页两个输入框的矩形没过 `Screen()`

### 判据
- **不是原版判据**：联机页是**我们自己的设计**（原版设置窗里没有这一页，见 `SettingsWindow.cs` 文件头 ①）——
  代码注释里逐句标了「这一页没有原版对应物」。
- 本窗的**自洽要求**：同页那几个包装函数 `Node` / `Rect` / `Text` / `Hit` / `NineOut` **每一个**第一行都过
  `SettingsWindow.Screen()`（根那层 `m_LocalScale = 0.9` 烘进矩形）；字号 A171 起也已缩（`InputFontPx = 40 × 0.9 = 36`）
  ⇒ **只有这两个输入框的矩形**跳出那条换算 ⇒ 框比字大 11%、与同列标签错位。

### 改了什么（`Shell/SettingsWindow.cs`）
- `MenuInputField.Create` **进门第一行**：`r = SettingsWindow.Screen(r.x1, r.y1, r.x2, r.y2);`（**唯一**那一处换算）。
  节点矩形 / 底板 / 文字框 / 命中区**四个量**都用缩过的 `r`。
- 文字在框内的内缩 16 从「裸 16」改成 `16f * SettingsWindow.RootScale`（**同一个漏斗内的连带项**：矩形缩了、内缩不缩就变成
  16 画布 px = 17.8 设计 px）。视觉差 1.6 画布 px；若审查认为该原样保留裸 16，改这一行即可。
- **调用点（`BuildRoleBlock`）不写 `Screen()`** —— 只加了一条注释说明「这里给的是设计 px、换算在 `Create` 里」：
  同页其余件也是这个分工（调用点给设计值、包装函数过漏斗）⇒ 换算只留一处。

### 断言在哪（`Editor/SettingsScene.cs`，联机页那节，约 `:1460-1505` + 客机块抽查 `:1581`）
量的是**渲出来的矩形**（`RectOf`：quad 的 `WorldW/H` + 世界位置 ⇒ 画布 px），期望值是**设计值 × 0.9 手算的字面量**：

| # | 对象 | 期望（字面量） | 算式 |
|---|---|---|---|
| ① | `Host Block / IP Field` | `[632.868, 414]–[1082.868, 468]` | 设计 `[596.52,400]–[1096.52,460]`（= `TitleL`/`OnFieldT`/`+OnFieldW`/`+OnFieldH`）⇒ `960+(x−960)×0.9`、`540+(y−540)×0.9` |
| ② | `Host Block / Password Field` | `[632.868, 513]–[1082.868, 567]` | 设计 y `510→570` ⇒ `513 / 567` |
| ③ | 对照：框左沿 = 同列标签左沿 | `\|框左 − 标签左\| ≤ 2px`（两者都应是 **632.868**） | 两条**不同**的建树路径（`MenuInputField.Create` ↔ `Text`+`AlignLeft`）必须落在同一个 x 上（量 `Label.WorldW` + 节点位置，同 `CheckLeftS` 那份算法） |
| ④ | 客机块 `/ IP Field`（抽查） | 同 ① | 同一条 `Create` 路径 |

- 🔴 **改坏法**：把 `MenuInputField.Create` 里那句 `SettingsWindow.Screen(...)` 去掉（= A208 之前的样子）⇒
  渲染矩形回到 `[596.52,400]–[1096.52,460]` ⇒ ①②④ 各差 11%、③ 差 **36.3px** ⇒ 全红。
- ③ 的独立价值：①②④ 都是「过没过 `Screen()`」，③ 抓的是**半缩半不缩**（只把框缩了、标签没缩，或反过来）——
  只留①②④ 时那种改法**抓不住**。
- ⛔ 期望值**不过 `Screen()`**（这条抓的正是「矩形没缩」，期望值再过一遍那条换算就分辨不出来）、
  ⛔ 不引 `OnFieldT / OnFieldW / OnFieldH` 那几个**实参**。`Screen()` 本身另有锚断言（本文件 §② 那节 `CheckRectPx`）钉着。

## 顺手发现（只报不改，越界的都在别的文件）

1. **旧那行注释的数字是没有出处的**：`±(24,16)` 旁边写「横向 24、纵向 16 画布 px = 手柄半高 15.9」——
   横向 24 既不是手柄半宽（15.93）也不是端帽（82.8），是**手调出来的**余量。已随收口删除（这是本件要治的那类「看着有依据」）。
2. `MenuInputField` **没有公开的节点/quad 访问口**（`_root` / `_bg` 都是私有）⇒ 自检只能**按名字**取节点
   （`FindChild(block, "IP Field")`）。本件够用；若将来要断「输入框的命中区」，得加只读属性（本件**没加**）。
3. `UpdateFpsDrag` 那句「正解在共用件：让按钮吃掉拖拽 / 给 `MenuScroll` 一个 `NoDrag`」**仍未做**（`MenuScroll.cs` 不在本件白名单）——
   拖这根滑块时每帧 `_gfxScroll.Stop()` 的兜底照旧，建议继续挂在「共用件欠账」上。
4. `MenuInputField.Create` 的矩形过 `Screen()` 之后，**联机页**还有一个件是「自己算的画布 px」：`RoleButton` / `ActionButtonAt`
   都走包装函数（已过漏斗）⇒ **这一页现在只有输入框这一处是新的；扫了一遍没发现别的裸矩形**。
