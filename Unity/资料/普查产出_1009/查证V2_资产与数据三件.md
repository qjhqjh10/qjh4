## 一、A235 —— 6 组同名 Texture2D + 同名 Sprite，哪一份是该用的

### 结论

1. **"同名"其实是"两条独立的 Addressables 记录"** —— 不是「一个资产被导出两次」：
   `m_Container` 里两个 **不同 guid**，各自 `preloadSize = 2`（= 1 个 Texture2D + 1 个同名 Sprite）。
   ⇒ 原版里这个问题**本来就有答案**（数据侧指其中一条 guid），只是答案不在本地。
2. **avatar 2 组：查清了，而且我们盘上那份就是该用的那份。**
   消费方 = cosmetic SO 的 `imageReference.m_AssetGUID`。
3. **necron 4 组：本地无判据。** 但其中 2 组两条**逐像素完全相同**（= 不需要判）；
   只有 `Ramatekh The Cruel` / `Immortals Phalanx` 真有差异，而这两组的消费方在**远端包**里。

### 证据

**necron 组**（`assets_full/bundle_necronssautekhcardassets_assets_all/AssetBundle/AssetBundle_1.json`）
—— 347 条 container / **242 个唯一 key**（= 同名 guid 各占两条），`m_ExplicitDataLayout = 1`：

| guid（= 地址） | 挂的对象 |
|---|---|
| `ab3f30fbaf9de534289c302846573785` | Texture2D pid `-8614432028123467792` + Sprite pid `-528821648699887632` |
| `d8db62b4f259945aca71a63417ee43ac` | Texture2D pid `924291845888298716` + Sprite pid `3676678240580161244` |

**avatar 组**（`bundle_cosmeticsso_assets_all/MonoBehaviour/Avatar_UM_Chaplain Cassius.json`）：

- SO 的 `imageReference.m_AssetGUID = 98ab2063725b84e1cacb8121eb4682fe`
  → Texture2D pid `1098785227856623382`（像素 md5 **`e8ba0abf961a`**）+ Sprite pid `-2089582408629733610`
- 盘上导出那份 `…/Texture2D/Avatar_UM_Chaplain Cassius.png` 的 md5 = **`e8ba0abf961a`** ⇒ **同一份** ✅
- 另一份（没人用）：guid `bbbace6792184db48bb5be1ccd0dc05f` → pid `-2931647423715446835`（md5 `8a593928c2df`）
- `Avatar_UM_Eliminator`：SO → `217017774fca44c34997bf88090b9b97`（pid `9117861109080715423`）；
  另一份 `d357bdb09c21b47f4b40443f5ee468c1`（pid `7539841541184024491`）——
  **两条内容 md5 都是 `88684248a66e`** ⇒ 判不判都一样（无损失）
- 两个 md5 与 `资料/普查产出_1008/波B3_解包缺口与工具缺口.md:68-72` 的表**逐位吻合**

**"本地没有消费方"这句的判据（搜过什么）**：

- 全 `assets_full` 的 `*.json`（24.7 万文件）搜 4 个 sprite pid + 2 个 texture pid + 4 个 guid
  → **只命中各自 bundle 的 `AssetBundle_1.json`**（`grep -rl --include='*.json'`，全树 16~18 秒）
- 全树搜 sprite 名 `Necron_Sautekh_warlord_Ramatekh The Cruel` → 只命中它自己那两份 `Sprite/*.json`
- 地址表 `%LocalLow%\Everguild\Warpforge\com.unity.addressables\catalog_main.json`：
  **两条 guid 都在**（各 1 次）；`m_KeyDataString` 解 base64 后搜 `Necron_` / `Avatar_UM_` / `.png` / `Assets/`
  **全 0 命中**，只有 `.bundle` 85 处 ⇒ **Addressables 只有 guid 地址、没有名字地址**（不可能按名字取）
- 卡→画的映射 SO 在 **`allcards_assets_all.bundle`**：`m_InternalIds` 里它是 **CCD URL**；
  本地 84 包目录与 `assets_full` **都没有这个包** ⇒ 消费方不在本地

**两份内容差多少**（用 UnityPy 从真包读回两条，逐像素比）：

| 名字 | 差异像素 | 占 1024² |
|---|---|---|
| `Necron_Sautekh_warlord_Ramatekh The Cruel` | 26,485（bbox 173,104–844,609） | 2.53% |
| `Necron_Sautekh_inf_Immortals Phalanx` | 24,529（bbox 426,89–669,280） | 2.34% |
| `Necron_Sautekh_strat_Awakened Dynasty` | **0** | 逐像素相同 |
| `Necron_Sautekh_strat_Inescapable Retribution` | **0** | 逐像素相同 |

8 件元数据全同（1024² · RGBA32 · 1 MB）；两条 `m_RD.textureRect` 也全同（x 176.5 / w 670.5 / h 1024）。
差异区在角色内部（`Ramatekh` 那份是枪尾那块有无），**不是**「一张对一张错」那种差别。

### ⇒ 该怎么做

- **avatar 2 组：不用做**（已是对的）。建议把这一条判据写进 `工具/import_original_art.py` 注释：
  「导出树里那份 = **后写**那份 = 恰好就是 SO 指的那份；**那不是判据、是巧合** —— 判据只能是
  `cosmetic SO.imageReference.m_AssetGUID → m_Container[guid] → 对象 pid`」。
- **necron 组：现在不欠任何"改造"，欠的是判据来源。** 具体：
  - `Awakened Dynasty` / `Inescapable Retribution`：**两条逐像素相同 ⇒ 关闭，不需要判**
  - `Ramatekh The Cruel` / `Immortals Phalanx`：**没查清**。缺 `allcards_assets_all.bundle`（远端 CCD）
    或一次能跑到实况的原版客户端；拿到任一个，按同一字段形态（`m_AssetGUID`）一查即定
- ⛔ **别按「哪张像素多/更完整」挑** —— 两份都是原版资源，没有判据支持这种挑法

## 二、A242 —— 368 张没受"确定性 guid"保护的图，有没有被场景按 guid 引用过

### 结论

1. **有。117 / 451 被引用**（26%）；其中 **未受保护的那 368 里被引用 70 张（19%）**，
   受保护的 83 里被引用 47 张（57%）。
2. **但风险比设想的低得多**：`import_original_art.py` 走 `shutil.copyfile(src, dst)`，
   **从不写、也不删 `.meta`**（全文 `guid` 出现 **0** 次）⇒ **常规重跑不会换 guid**。
   真会断的只有一条路：**`.meta` 被删掉**（现有工具里**一处都没有**指向 Art 树的删除）。
3. 报告点名的三个场景**都在**：`MyGame/Assets/CardPresentation/Scenes/{CardBase,CollectionCheck,DeckEditor}.unity`；
   **另多一个 `MainMenu.unity`** 也引用这批图（合计 4 份 `.unity`，**没有别的资产类型**）。

### 证据

- 451 张 PNG（`ui/` 93 · `ui_deck/` 93 · `ui_menu/` 265）**全部有 `.meta`**；
  受保护 83 = `sync_battle_ui_art.py` 的 `NAMES`(41) + `NAMES_DECK`(40) + `NAMES_MENU`(2)，**逐条都在盘上**。
- 引用分布（**受保护 / 未受保护 / 合计**）：
  `CollectionCheck.unity` 35 / 48 / 83 · `DeckEditor.unity` 39 / 21 / 60 ·
  `MainMenu.unity` 4 / 17 / 21 · `CardBase.unity` 2 / 1 / 3（列和 167 > 117 ⇒ 同一张被多场景引用）。
- 扫描面：`Assets/**` 下 2214 个 `.unity`/`.prefab`/`.asset`/`.mat`/`.controller`/`.anim`，
  **命中的只有上面那 4 份 `.unity`**（= 没有 prefab / mat / controller 引用它们）。
- 未受保护而被引用的 70 张：`ui/` **2** · `ui_deck/` **28** · `ui_menu/` **40**。
- `MyGame/.gitignore:91`（`Resources/Art/`）+ `:131`（`CardPresentation/Scenes/`）**整目录不进仓库**
  （`git ls-files` 在这两处都是 **0 个文件**）⇒ 场景本身是**构建产物**
  （`Editor/{CardBaseDemo,CollectionScene,DeckScene,MainMenuScene,ShellScene}.cs` 各自 `BuildAndSaveScene`/`Run`）。
- 工具里的删除代码只有 3 处，**都不指向 Art 树**：`collect_unmatched_art.py:193/196`（只删它自己的
  `README.md`/`原版卡面/`/`候选插图/`，见其 `clean_own_output` docstring）·
  `install_dotween.py:81/87`（DOTween 插件目录）· `rebuild_overtime_start_ogg.py:44`（一个 ogg）。

### ⇒ 该怎么做

- **不给那 368 张补"确定性 guid"**。正解仍是「**重建次序：先图 → 后场景**」——
  本次实测把这条规矩覆盖的引用数从「83」**订正为 117**（场景按**当时盘上**的 guid 落引用，
  图先到位、guid 先定，就永不悬空）。
- 唯一值得加的护栏是**别删 `.meta`**。可选加固（交调度台定）：`import_original_art.py` 加一条
  **只读体检** —— 「有 PNG、没 `.meta`」或「`.meta` 在但 PNG 不在」就点名；
  照 `sync_battle_ui_art.py` 的先例：**只报不修、不进退出码**。
- 未受保护那 70 张的清单见 §五·4（要"补保护"时它才是清单）。

## 三、A275 —— `CrateCounter` 的 `MenuDraw.AlignLeft` vs 原版 Center

### 结论

1. **原版确实是 Center** —— 我们的注释没写错，**实现 `AlignLeft` 是真偏离**。
2. **同一文件里还有第二处同性质**：保底进度条上的 `counter`（`100/200`）原版也是 **Center**，
   我们同样走了 `AlignLeft`。

### 证据

- 节点 `CrateCounter` → `assets_full/bundle_menus_assets_all/MonoBehaviour/MonoBehaviour_7693323916674998959.json`：
  `m_HorizontalAlignment = 2`（TMP `Center`）· `m_VerticalAlignment = 4096`（`Midline`）·
  `m_fontSize = 35.0` · `m_characterSpacing = -2.0` · `m_fontSizeMin/Max = 3.0/35.0` · `m_margin` 全 0 ·
  `m_text = "Boosters opened since last Legendary "`
- **同窗三个兄弟全是 Left（对照）**：`Title` `H=1` · `Category` `H=1` · `Descripton` `H=1`
- 保底条 `counter`（`100/200`，字号 26.35）→ `MonoBehaviour_8510044244370989743.json`：**`H = 2`**
- RT：`RectTransform/RectTransform_1062604289391534767.json` → `m_AnchorMin = m_AnchorMax = (0,1)` ·
  `m_Pivot = (0, 0.5)` · `m_SizeDelta = (485.284, 45)` —— **框是左锚的，Center 说的是「框内居中」**（别混）
- 复现命令：`python d:/4/Unity/工具/menu_dump.py bundle_menus_assets_all "Booster Info Popup" --depth 7`
  → `CrateCounter … 对齐=Center/Midline 字距=-2` · `counter … 对齐=Center/Middle`
- 我们：`Shell/BoosterInfoPopup.cs:348-353`（`MenuDraw.AlignLeft(cc, CrateCounterR)`）·
  `:380-384`（`MenuDraw.AlignLeft(cnt, SliderCounterR)`）
- `Shell/MenuDraw.cs:1304/:1310` —— `MenuDraw` **只有 `AlignLeft`/`AlignRight`，没有 Center 助手**；
  而 `MenuDraw.Text` 建的 Label pivot 是 `(0.5,0.5)`（`Shell/MenuDraw.cs:1272`）
  ⇒ **不调 `AlignLeft` 就是居中**，正好等于原版的 Center

### ⇒ 该怎么做

- 两处 `MenuDraw.AlignLeft(...)` 去掉即可（默认居中 = 原版 Center）。
- ⚠️ **是否肉眼可见没验**：`AlignLeftOn` 把**渲染块**（TMP `textBounds`，`WorldW`）左缘挪到框左缘，
  块宽 = 框宽时两法等价、块宽 < 框宽才看得出差 `(485.284 − WorldW) / 2`。
  要坐实可见性得渲一张比 —— 本次红线禁跑 Unity ⇒ 这一格**没验**（差一次渲染）。
- 建议另开一条**同族普查**：`MenuDraw.AlignLeft` 的全工程调用点里，有多少落在「原版 `H=2`」的节点上
  （本件只核了这一扇窗）。
