## 〇 结论（一句话）

**「快」不是时长错、也不是调度加速 —— 真正的原因是原版在近战位移的【每一帧】都在按「卡在战场里的深度」重算 `localScale`，我们一次都没算**：
原版卡从自己那行飞到目标旁边时**局部缩放 0.36 → 0.63（≈1.74×）**，就是为了抵消透视、让屏幕上看起来大小不变；
我们恒 0.36 ⇒ 卡在 0.1 s 内**视觉缩小到约 55%**、再用 0.2 s 涨回来 —— 读起来就是「一顿快缩快涨」，而原版几乎没有这个变化。

判据（第一权威）：`d:/2/tools/decomp_full/CardScript.__c__DisplayClass357_0___AttackMeleeAnim_b__0.c`（**近战序列的 `OnUpdate` 回调**）
→ `MinionScaleByPositionSO__GetScale` → 曲线真件 `d:/2/解包整理/08_预制体特效/战斗预制体/MonoBehaviour/MinionScaleByPosition.json`。

四条直接回答（详见下文）：
1. **走哪条路**：卡体位移**不走** `Card3DAnimationController` —— 走 `CardFeel.MeleeAttack` 的纯 DOTween 序列。`Card3DAnimationController` 只吃**技能动画那一拍**（`UnitAttack`/`UnitDamaged`），且本局（SaimHann）**一条都没有**。
2. **是不是空壳 clip**：**不是**。`Clip` 那一路**根本没人喂** —— `CardAnimClips.BodyClipOf()` 恒回 `null`（判据见 `CardAnimClips.cs:210-236`）。生产走 `Prefab` + `Duration` 那一路。
3. **调度有没有加速**：**没有**。全仓无 `Time.timeScale` / `DOTween.timeScale` 赋值；`AdvanceTimeline(Time.deltaTime)`；`CardTween.Mode = Normal`；近战序列 **0.4 s / 命中 0.1 s**，与反编译**逐字相同**。
4. **「细节不对」还有第二条**：`attackSequenceTimeScale`（卡预制体字段，原版 `sequence.timeScale = …`）我们没接（本 prefab = 1.0 ⇒ 今天无可见差）；以及 `-wfdrive` 每 1 s 无脑 `SimulateAiTurn → RefreshAll → SyncBoard → SetPose(0)` 会把正在冲的卡**一帧拉回格位**（次要，见 §五·6）。

## 四 🔴 根因：原版每帧按「战场深度」重算 `localScale`，我们一次都没有

### 4·1 原版怎么做（逐句）

`CardScript.__c__DisplayClass357_0___AttackMeleeAnim_b__0.c`（= 近战 **Sequence 的 `OnUpdate`**，在 `_AttackMeleeAnim.c:126-129` 挂上）：

```
localPosition = transform.localPosition
so           = card.CardUI[+0x290].minionScaleByPositionSO[+0x1C0]
scale        = so.GetScale(isPlayer, localPosition, card.defaultScale[+0x324])
transform.localScale = scale
```

`MinionScaleByPositionSO__GetScale.c`：
```
x = isPlayer ? localPosition.z : (curve.lastKey.time + localPosition.z)   // 敌方那侧整体平移 7.7
v = curve.Evaluate(x)                                                     // 两端 Clamp
scale = 基准向量 × v × (defaultScale.x ÷ curve.keys[0].value)
```

曲线真件（`d:/2/解包整理/08_预制体特效/战斗预制体/MonoBehaviour/MinionScaleByPosition.json`，
同内容第二份 `MinionScaleByPosition_-2123600674758724809.json`）：

| 关键帧 | time | value |
|---|---|---|
| 0 | **0.002811431884765625** | **0.36000001430511475** |
| 1 | **7.699999809265137** | **0.699999988079071** |

🔑 **交叉验证**：两行 `MinionArea` 的 z = **−6.655**（我）/ **+1.043**（敌）⇒ 差 **7.698** ≈ 曲线的横轴 7.700。
第一关键帧 0.36 = `ArenaSlots.PlayerCardScale`、第二 0.70 ≈ `EnemyCardScale 0.69`（`Board/ArenaSlots.cs:59,69`）。
⇒ **这条曲线就是「从自己这行到对面那行」的深度→缩放表**，目的 = 抵消透视、让卡在屏幕上**看起来大小不变**。

### 4·2 算一遍（我方近战，本局就是这一档）

卡根挂在自己的 `MinionManager` 下（原版 `PlayerManager__SetupFullHero.c:26-46` 把它 `set_parentInternal` 到 MinionManager），所以**主位 `localPosition.z ≈ 0`** ⇒ `x≈0` ⇒ 曲线给 **0.36**（= 平时的大小，自洽）。

近战段1 把卡搬到 `endPos = 目标位 − dir×1.7`。以我方槽 3 → 敌方槽 3 为例（`ArenaSlots.Position`）：
起点 `(-0.91, 0, -6.655)` → 终点 `≈(1.66−…, 0, -0.57)` ⇒ **Δz ≈ 6.08** ⇒ `x = 6.08` ⇒
`scale = 0.36 + (0.70−0.36) × (6.08−0.0028)/(7.700−0.0028) ≈ **0.628**`（≈ **1.74×**）。

**原版**：0.36 → 0.628（0.1 s）→ 0.36（0.2 s）。透视 + 局部放大的乘积 ⇒ 屏幕上大小**基本不变**。
**我们**：恒 0.36。而透视那一侧是 `资料/3DBody_原版场上卡体规格.md` 量的 **182.14 px/单位（我方行）vs 86.2 px/单位（敌方行）** ⇒ 同一 `localScale` 下，卡飞到目标旁边**视觉只剩约 47%~55%**，0.1 s 缩下去、0.2 s 涨回来。

⇒ 观感 = **一次极快的「缩小→回弹」脉冲**，正是用户说的「很奇怪 / 速度很快 / 不是原版的样子」；而「细节上有点问题」= 尺寸与朝向都跟原版不一样。

> 敌方进攻是**反方向**同理：敌方 `x = 7.7 + localZ`，从敌方主位（`x≈7.7` ⇒ 0.70）飞到我方那行（`localZ≈−8.6` ⇒ `x<0` ⇒ Clamp 到 **0.36**）⇒ 原版敌方那一击是**缩小**到 0.51×；我们同样不动。

### 4·3 这不是「近战专用」

同一套回调还挂在 **`_AfterAttack` 的序列**上（`CardScript___AfterAttack_b__370_0.c:22,29` 逐字同形）。
⇒ 原版**任何**棋盘位移（攻击、收招、让位 `Reassemble`、登场飞行）都会按深度改缩放；我们**全部没有**。
`WFModuleTransformModifier.cs:74-75,420-421` 把这条记成「那份 SO 没有导出来」——**那句已过期**：件就在本地（见 4·1 的路径），建议就地订正（铁律 5）。

## 五 其余细节差异（按影响排）

1. 🔴 **§四的逐帧缩放**（本件主因）。
2. 🟠 **单候选拍的 `Duration` 被压成 0** ⇒ 技能动画那一层 0.05 s、时间线不等（§2·2）。11 张卡会看到「技能动画一闪 + 下一件事立刻压上来」。
3. ⚠️ **近战段2 的旋转基可能不对（未核实，如实标）**：我们 = `homeRot × Euler(0,90°,0) × Euler(0,0,25°)`（`CardFeel.cs:900-902`）；原版是
   `Quaternion.AngleAxis(90f, <归一化向量>) …`（`:186-190`），那个 `<归一化向量>` 存在 display class `lVar5+0x18` 里、由 `:186-190` 之前的 `Vector3` 归一化得到（**不是** `Vector3.up` 这个静态量 —— 对比 `CardScript__TurnCardAround.c:29-32` 那里用的是 `new Vector3(0,0,90)`）。
   若它是**指向目标的方向**，那原版那 90° 是绕「视线轴」**在屏幕平面内翻滚**（卡一直看得见），而我们绕世界 up **偏航**（卡在 0.1 s 内转成**侧面一条线**）。
   ⚠️ **反编译把 12/16 字节结构读串了，我无法从 `.c` 断定**；判别方法见 §七。
4. ✅ **命中帧手感齐**：`PlayHitFrameFeel` 在 `Attack+0.1` 做 ①`AttackHitSmall`（= 原版 `attackHitSmallParticles`，卡 prefab 里 small/big **同一个 pathID 4239831775333917772**，我们只播一件是对的）②`meleeAttackHitSmall` ③震屏 ④受击后坐（`BattleDriver.cs:17764-17790`）。原版 `CardScript__ResolveAttackAnimationEffects.c` 同四件。

## 六 最小修法（给主对话派活用）

### 6·1 主因（必做，改动面小）

在 `CardPresentation/Core/CardFeel.cs` 的 `MeleeAttack` 里给序列挂一个 `OnUpdate`，按「本行 → 对面行」的深度重算缩放；判据数据**已经在本机**，直接落成两个常数 + 线性插值即可（曲线两键、`inSlope==outSlope==0.04417` ⇒ 就是直线，无需 `AnimationCurve` 资产）：

```
// 判据：MinionScaleByPosition.scaleCurve = [(0.00281143, 0.36), (7.6999998, 0.70)]
static float ScaleByDepth(float zFromOwnRow) => Mathf.Lerp(0.36f, 0.70f, Mathf.Clamp01((zFromOwnRow - 0.00281143f) / (7.6999998f - 0.00281143f)));
// 我方（isPlayer）: x = localZ ; 敌方: x = 7.7 + localZ   —— 原版 GetScale 逐字
```
⚠️ 我们的卡父节点是 `Battle` 而不是 `MinionManager`（真机 dump：`父=Battle`），所以「相对自己那行的 z」要用 `worldZ − ArenaSlots.PlayerZ`（我方）/ `worldZ − ArenaSlots.EnemyZ`（敌方）现算（`ArenaSlots.cs:58,68`），⛔ 别用 `localPosition.z`（那恒等于世界 z）。
⚠️ 缩放**要经 `CardView` 的口**（`_baseScale`/`ApplyScale`），别直接写 `transform.localScale` —— 否则下一次 `SetPose` 会弹回旧值（同类坑见 `CardView.TweenPose` 的 doc；`CardView.cs:7790-7801`）。最省事：给 `CardView` 加一个 `SetDepthScale(float)` 只改 `_baseScale` 并 `ApplyScale()`。
⛔ 判据只此一处：把这条曲线收进一个共用口（建议 `ArenaSlots` 或 `CardFeel` 的单个静态方法），**`MeleeAttack` / `Reassemble` / 登场飞行三处共用**（原版是三处都吃同一个 SO，见 §4·3）。
