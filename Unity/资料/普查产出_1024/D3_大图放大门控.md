（「战术/防御卡的大图档我们多乘了 1.27」）。
**结论**：已按卡类型门控落地 + 4 条断言（含灭自证）。**并且把 `A7` 只引一处时的漏洞补全了** ——
`ChangeState` 那条路**不判卡类型**，门控真正成立靠的是 `useOverDraw`（见 §一·3）。

### 1·1 门控那一处（`A7` 引的）

- `0x1834b2bb8` 用 `工具/read_literal.py` 从 `D:/2/unity_run_ref/GameAssembly.dll` **现读**
  = **4 字节 float `1`**（8 字节读是 `2`；上下文是 float ⇒ 取 1）。
- `param_1 + 0x20` = 序列化字段 `bigSizeMultiplier`；`CardImage.json`
  （`bundle_battleprefabs_vfxandmisc_assets_all/MonoBehaviour/MonoBehaviour_5393623139443973056.json`）
  **现读 1.2699999809**（同文件 `tacticsOffsetPosition = (0, 0.5, 0)`，与 `A7` §五·3 一致）。
- **字段偏移的独立校验**（不是猜）：`param_1+0x28` 当 `Image` 用、`+0x30` 当 `SoftMaskScript` 用、
  `+0x38` 当 `CardImageScalebyCardTypeSO` 用、`+0x40/44/48` 当 `tacticsOffsetPosition` 用
  （`SetImage.c:126-128` 的 `param_3 == 0x14` 分支恰好吃这三个）、`+0x64` 当 `currentState` 用
  （`SetImage.c:110` / `ChangeState.c:30`）—— 与 `CardImageController.cs` 桩的字段顺序一一对上。
- `param_3` 的类型 = **`CardTypeOptions`**（桩：`SetImage(Sprite, CardTypeOptions)`；
  `CardTypeOptions.cs` = `Minion 0 / Hero 10 / Tactic 20 / Whispers 40`）。
- 传进来的值确实是**卡的 `cardType`**：`BasicCardUI__SetCardImage.c:20-22` 传
  `*(undefined4 *)(rawCard + 0x94)`，而 `+0x94` = `RawCardScript.cardType`
  （`RuleEngine/Core/CardDef.cs:299` 的注释已记过这条读数）。

⇒ **状态 1（Big）∧ 卡类型 ∈ {0 Minion, 10 Hero}** 才乘；Tactic(20) / 防御 / 其余 ×1.0。

### 1·2 「防御卡的 cardType 是几」不影响结论

- 我们卡池 39 张 `type="defence"`（33 张在 `cards_truth.json` 里按唯一名对上）读到的原始
  `cardType` = **20（Tactic）**；`CardScalesByCardType.json` 里另有一条 `cardTypeOptions: 5 → 0.60`
  —— 但**全表没有任何一张卡读得到 5**。
- 20 和 5 **都不是 0/10** ⇒ 两条路都挡掉防御卡，**结论不受这个分叉影响**。

### 1·3 🔴 **补全：`ChangeState` 那条路不判卡类型 —— 门控靠 `useOverDraw` 兜住**

`CardImageController__ChangeState.c:90-95`（Small→Big 的正常路径）**不看 cardType**：

```c
:90    uVar13 = DAT_1834b2bb8;                    // maskStrength = 1.0
:91    local_58 = *(undefined8 *)(param_1 + 0x58); // originalImageScale（SetImage 存的是**未乘**值）
:92    fVar8 = *(float *)(param_1 + 0x20);         // = bigSizeMultiplier，**无条件**
:93    fVar7  = *(float *)(param_1 + 0x60) * fVar8;
:94-95 fVar14/fVar8 = originalImageScale.xy * fVar8;
```

—— 所以「×1.27 只给 Minion/Hero」在原版里**不是一条断言，而是两条事实合起来的结果**：

1. 只有 `useOverDraw == 1` 的卡才会被送进状态 1（`CardDisplayWindow__ShowCard.c:62-84`
   → `BasicCardUI.SetImageOverDraw` → `ChangeSize` → `ChangeState`）；
2. 卡池里 **`useOverDraw == 1` 的正好只有 unit 585/586 + hero 56/56，tactic 446 + defence 39 全是 0**
   （`cards_engine.json` 现读）。

⇒ 能进 Big 的卡**本来就全是 0/10**，`SetImage` 那道 `if` 只是把「已经处于 Big 时再换图」
（复用槽位）这条路的倍率也钉住；两条路对 0/10 给出同一个值（1.27），对 20/5 那条路**根本走不到**。

**我们这一侧少了一步**：`_artFront` 是**照建**的（`bigFront` 只看「大图档 + 有真立绘」，
**不看 `useOverDraw`**），`useOverDraw=0` 只是把它**藏起来**（`ArtFrontVisible`）。
⇒ 战术/防御卡会烘出一块**按 1.27 算的网格**（今天看不见，`useOverDraw` 数据一变就现形）。
这就是本笔要在**倍率**上补门的原因（不是「原版另一条路也门控了」——它没门控，是走不到）。

## 六、顺手发现（⚠️ 未改，只记账）

1. 🔴 **`SetImage` 里 Tactic(20) 那一支根本不设 sprite**：`SetImage.c:126-144` 是
   `if (param_3 == 0x14) { …frameMask 关掉 + textBackground.material = null… } else { texture = sprite.texture }`
   ⇒ **战术卡的 `CardImage` 贴图不在 `SetImage` 里赋值**（原版大概另有赋值点）。我们没这条分叉。
   **与本笔无关**（`A7` 的 `_Clamp_Range` 仍对该层生效），但值得哪天单独查「战术卡 CardImage 从哪拿图」。

   我们**没有**「`useOverDraw=0` ⇒ 不建前景层」这一步（只藏）⇒ 网格照算。若哪天为省开销改成「不建」，
   断言 ②③ 会因 `_artFront == null` 变成**前提红**（那时要改断言，别当成回归）。

   `A7` 的 `ChangeState.c:99-105` 对得上（现读 `:100-105`），但它**只描述了 clamp**，
