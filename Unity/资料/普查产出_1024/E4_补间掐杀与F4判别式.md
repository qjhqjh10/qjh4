## 一、红 #1 · `③1 掐完之后补间真的死了（实测 True）`

### 1·1 成因（读到什么）

**先把「代码写法」那一半证否**（现读 `Core/CardView.cs:7930-7970`）：

```csharp
var tw   = DG.Tweening.DOTween.To(() => t, x => { t = x; SetPose(...); }, 1f, duration);
var used = CardTween.Use(tw, ease, this);   // `Core/CardTween.cs:55-60`：SetEase→SetUpdate→SetLink，**全部 return this**
used.SetTarget(transform);                  // `SetTarget<T>(this T,…)` 也 return this
_poseTween = used;                          // ⇒ _poseTween **就是** tw
return used;
```
⇒ `_poseTween` **确实被赋值**、且 **`== tw`**；也没有第二个 `_poseTween` 字段（全仓 `grep -rn "_poseTween"` 只有
`CardView.cs` 那 5 行）。⇒ **DG3 猜的「`_poseTween` 是空 / 是别人」不成立。**

**真正的成因：两条 pass 走的是两条不同的「杀」路径，其中一条在编辑器批处理里是死的。**

现读日志（`20261024_sync2/CardBaseDemo.log`）给了**同批对照**，这是决定性证据：

| 行 | pass | 用的口 | `tw.IsActive()` | 位姿 |
|---|---|---|---|---|
| `:96332` | ③1 | **`CardView.KillPoseTween()`** | **True**（红） | `1.616,-1.759 → 3.500,-2.200`（被推完） |
| `:96384` | ③2 | **`transform.DOKill()`** | **False**（绿） | 停在 `1.616,-1.759` |

同一条补间、同一割点，**换一个口就活了** ⇒ 问题在 `Kill` 的**实现路径**，不在补间本身。

**IL 级判据**（把 `Assets/Plugins/Demigiant/DOTween/DOTween.dll` 用 Unity 自带的
`Data/MonoBleedingEdge/lib/mono/4.5/ikdasm.exe` 反汇编看过；临时 IL 在 `/tmp/dotween.il`）：

1. `TweenExtensions::Kill(Tween t, bool complete)` 的**头三条指令**就是：
   ```il
   IL_0000: ldsfld  bool DG.Tweening.DOTween::initialized
   IL_0005: brtrue.s IL_0008
   IL_0007: ret                  ← initialized == false ⇒ **直接 return，什么都不做**
   ```
   ⇒ **未初始化时 `tw.Kill()` 是 no-op**（且不报错 = 静默）。
2. 而 **编辑器批处理里 `initialized` 永远是 `false`**：
   - `DOTween.Init()` 自己就挡着：`IL_000d: get_isPlaying; IL_0012: brfalse.s IL_001b; … IL_001b: ldnull; ret`
     —— `!Application.isPlaying` ⇒ **返回 null、不初始化**；
   - `DOTween.InitCheck()`（`DOTween.To` 每次建补间都会调）在 `!isPlaying` 时同样**不调 `AutoInit()`**；
   - 全仓 **没有任何 `DOTween.Init(` 调用**（`grep -rn "DOTween.Init" --include=*.cs` 零命中）。
   ⇒ `-batchmode -executeMethod`（不进 play）里，`initialized` 从进程生到进程灭都是 `false`。
3. **对照组为什么活着**：`transform.DOKill()` → `DOTween.Kill(object targetOrId)` → `TweenManager.FilteredOperation`，
   这条链**不读 `initialized`**（IL 里 `initialized` 全库只被读 3 处：`Init` / `InitCheck` / `TweenExtensions.Kill`）。
   ⇒ 同一批里 ③2 绿、③1 红，**完全自洽**。

**为什么上一轮（E3）改完还是红**：E3 只去掉了 `IsActive()` 闸 —— 闸确实该去掉，但**闸后面的 `Kill()` 本身在批处理里是死的**，
所以「无条件 Kill」和「带闸 Kill」在批处理里**表现一样**（都空转）。这也解释了为什么 DG3 的 3 行探针
（`null / active / same`）即使加上也只会打出 `null=False active=True same=True` —— 三个值都正常，
**问题不在状态、在实现**。⇒ 探针**不再需要**（本来也是会污染日志的可选项）。

### 1·2 修法（`Core/CardView.cs`）

1. `TweenPose` 建完补间后**多挂一个本卡唯一的 id**（`:7967`）：
   ```csharp
   used.SetTarget(transform);
   used.SetId(_poseTweenId);      // 新增；`readonly object _poseTweenId = new object();`（:7978）
   _poseTween = used;
   ```
2. `KillPoseTween()`（`:7983-8010`）改成「**正常路径 + 非 play 兜底**」：
   ```csharp
   Tween tw = _poseTween;
   _poseTween = null;
   if (tw == null) return;
   tw.Kill();                                        // play 模式的正常路径（批处理里被 DOTween 空转）
   if (tw.IsActive()) DOTween.Kill(_poseTweenId);    // 非 play 兜底（按 id 杀）
   ```
   **兜底为什么一定能杀**（IL 判据）：
   - `DOTween.Kill(object)` 不读 `initialized`；
   - 它把 `OperationType.Despawn(=1)`、`FilterType.TargetOrId(=1)` 交给 `TweenManager.FilteredOperation`
     （两个枚举值都在 IL 里核过：`OperationType.Despawn = 1`、`FilterType.TargetOrId = 1`）；
   - `TargetOrId` 分支比 `tween.stringId` / `tween.intId` / **`tween.id`** / `tween.target`
     ⇒ `SetId(object)` 写的就是 `Tween.id` ⇒ **只命中本卡这一条**；
   - 同一条 `FilteredOperation` 链**就是 ③2 那条绿的路径**（`transform.DOKill()` 也走它）⇒ 行为有实测背书。
3. ⛔ **为什么兜底不用 `transform.DOKill()`**：那会连本卡 Transform 上 `DOMove/DOScale` 那一族
   （自带 `target = transform`）一起收掉，违背本函数「只掐位姿补间」的约定。
   ⛔ **为什么 id 不用 `transform` / `this`**：`DOTween.Kill(x)` 是「target **或** id 命中」，
   拿 `transform` 当 id 等价于上面那条误杀。用**每卡一个独立 `new object()`** 才精确。

**断言没动内容、只更新了「怎么改坏它」的文案**（`Editor/CardBaseDemo.cs:3480-3481`、`:3491-3492`）：
`!tw.IsActive()` 与「位姿不再被推走」两条**原样保留**；🧨 从原来的「把 `Kill()` 放回 `IsActive()` 闸后面」
改成「**删掉兜底那句 `DOTween.Kill(_poseTweenId)`**（或 `TweenPose` 里不 `SetId`）」——
因为有了兜底之后，旧的改坏法已经**不再会红**（闸挡住 `Kill()` 也还有兜底），旧文案属于过期判据。

## 二、红 #2 · `F4 小图档的 v 窗口是 (0,1] ⇒ 纵向没被收窄`

### 2·1 读到什么（E3 的判别式为什么恒红）

新日志 `:95460`：
```
小图档 y [-0.2487, 1.2135]   vs   BIG 档 [-0.2487, 1.0708]   （不夹那块 [-0.5946, 1.2135]）
```
**两档下沿完全相同（−0.2487）** ⇒ E3 的 `onY0 > bigY0 + 0.1` **结构性不可能成立**。
机理解释（写进代码注释了）：BIG 的 v 下沿 = `yB0 + 0.10·h = −1.4732 + 0.28583 = −1.1873`，
**比卡框开口还低** ⇒ 下沿先被**卡框开口**截住（两档都停在 −0.2487），轮不到 v 窗口去夹。
所以「下沿」这个维度对这张样本框**没有判别力**，不是缺陷、更不是误用 BIG。

### 2·2 新判别式（`Editor/CardFaceProbe.cs:1186-1201`）

```csharp
Check(onY1 > bigY1 + 0.05f        // ① 主判据：上沿不许被压（有牙）
   && onY0 <= bigY0 + 1e-3f,      // ② 方向闸：下沿不许被【抬】(弱，见下)
      …同上三组读数…);
```

- **①是牙在哪**：BIG 的 v 上沿 = `yB0 + 0.89·h = 1.0707` 会把上沿压下去。
  「误用 BIG 档」时 `mOn` 与 `mBig` 是**同一份网格** ⇒ 两上沿**相等** ⇒ `onY1 > bigY1 + 0.05` 假 ⇒ **红**。
- **②是方向闸、且**⛔ **不是主判据**：本例 `onY0 == bigY0` ⇒ 它恒真。
  它只挡反方向（「SMALL 比 BIG 收得还狠」⇒ 下沿被抬到 BIG 之上）。文案里已明写「下沿对这张框没有判别力」，
  免得下一个人把它当主判据。
- 🧨 文案改成**实际机制**：「误用 BIG 档 ⇒ **上沿被压到 ≈1.0707**（本例 1.2135→1.0708，差 0.143）⇒ 红」。

**读数预期**（同一份日志的样本，跑绿时应打）：
`小图档 y [-0.2487,1.2135] vs BIG 档 [-0.2487,1.0708]` ⇒ `1.2135 > 1.1208` ✓、`−0.2487 <= −0.2477` ✓ ⇒ **绿**。
若哪天真的误用 BIG ⇒ 两组读数**完全相同** ⇒ 红（判别力保住）。

## 五、顺手发现（只报不改）

1. 🔴 **这条是通用的：编辑器批处理里 `TweenExtensions.Kill / Complete / Play / Pause …` 全是静默 no-op**
   （同一道 `DOTween.initialized` 闸，IL 见一·1）。批处理自检里**所有**「掐掉 / 完成补间后断状态」的断言都可能**空验**。
   现读命中的调用点：`Editor/CollectionScene.cs:8643`（`fxBtn.Kill(); fxCard.Kill();`）、
   `:8781`、`:8842`（`fp.Kill()` / `kill3` 那一组）、`Editor/VfxPicker.cs:116`（`fx.Kill()`）。
   建议后续统一成「`Kill()` + 按 id / target 的 `DOTween.Kill(...)` 兜底」，或在这些宿主开头**显式**记住
   `DOTween.initialized == false` 这件事，别把「杀没杀」当断言。**本轮没动**（不在白名单，且都不是红）。
2. **`Core/CardFeel.cs:1584` 的 `if (s != null && s.IsActive()) s.Complete();`** 走的是生产 play 路径 ⇒ **不受影响**，
   但它的注释里「`Complete()` 会触发 `OnKill` ⇒ 复位」这句在批处理自检里**不成立** —— 谁在 Editor 里调它就要注意。
3. **`CardBaseDemo.cs:3476-3477` 那段注释**（「下次红时能一眼分清『闸门空转 / `transform.DOKill()` 杀不到』还是『`Kill()` 本身没牙』」）
   现在**少了第三种可能**：`Kill()` 有牙、但**在非 play 环境里被 DOTween 闸住**。我只改了 🧨 文案，**没改这段注释**（不在这次必须改的范围内）。
4. `DOTween` 的对象是**池化**的：`Despawn` 会 `t.active=false` + `Reset()` 后回池，下一次 `DOTween.To` **可能拿到同一个对象**。
   所以**别长期持有 `Tween` 句柄去判状态**（本轮的 `_poseTween` 只在「建 → 掐」之间用，安全）。
   本条也是「为什么不能靠 `tw == _poseTween` 判身份」的注脚（对象会被复用）。
