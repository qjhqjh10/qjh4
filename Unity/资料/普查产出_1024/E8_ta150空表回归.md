## 一 · 复核结论（E7「顺手发现 1」的推断 **成立**，另外多查出一处坑）

1. **现象复现**（改前，`bash 工具/ruleprobe.sh play BL51` 的引擎日志）：
   ```
   战术卡：「Draw 2 cards」抽了 2 张
   战术卡：「For each troop drawn, create a copy of Abaddon's Chosen in your hand」按 any 计 2 遍
   战术卡：「…」正文计数「any」= 2，而原版 `multiplier` 结构化数据 = **0** ⇒ 按数据 0 遍
   ```
   读数：手牌只多了 `filler27/28`（抽到的两张），**一张 `BL37` 都没造**。
2. **根因链（逐段现读，全部成立）**：
   - `G6` 让 `unitConditions` 里 `(ab=0, lg=1, role=mult, cond=0)` 这一行落下来了；
     `multiplierSet.targetsAffected = 150 (previousAbilityFiltered)`、`friendlyUnits 1`、`includeMinions 1`。
   - `EffectResolver.TryStructuredMultiplier`（`:11849-11889`）→ `CountMultiplierTargets`
     （`:11945-11953`，`filterSpecificCards` 为空 ⇒ 直接转 `CountEval.CountTargets`）
     → `CountEval.CountSet` 的 `ta == 150` 分支（改前 `:412-434`）**只数 `ctx.PreviousAbilityTargets`**。
   - 抽牌那一跳**不写** `PreviousAbilityTargets`（它的写点 `NotePreviousAbilityTargets` 取的是
     `ctx.LastTargets`，而 `DoDraw` 不写 `LastTargets`）⇒ 表空 ⇒ 循环一次不跑 ⇒ **返回 0 且不报 gap**
     （`gap` 只在候选「不在场上」时置）。
   - 于是「结构化乘数优先」按 0 覆盖了正文算对的 2（`TryComputeRepeats` `:11749-11768`）。
3. **原版判据（为什么不是 0、也不该判 `null`）** —— `d:/2/tools/decomp_full/` 逐句现读：
   - `AbilityLogic__AddDrawCard.c`：抽牌那一支把
     `BattleManager__GetNextCardsInDeck(...)` 的结果 **`AddRange` 进 `abilityTargetsToSave`
     （`param_1 + 0x80`）**（`System_Collections_Generic_List<object>__AddRange(lVar2, uVar3, …)`，
     `lVar2 = *param_7`，调用点传的正是 `param_1 + 0x80`，见 `AbilityLogic__PlayAbility.c:1442-1451`
     与 `:2399-2413`）；
   - 每个 effect 出口调 `AbilityLogic__SetPreviousAbilityTargets.c:19-28`（`Array.Clear` + `AddRange`，**整表覆盖**）；
   - `AbilityLogic__GetTargets.c` 的 `iVar6 == 0x96 (150)` 支把静态表 `AddRange` 成候选池。
   ⇒ **抽到的牌就是「上一跳的目标」**，候选数 = 抽到的部队数（夹具里 2 张 `filler27/28` 都是 `type == "unit"`
   —— `PlayProbe.cs:270-276`，`i % 5 != 4` ⇒ `Fix(...)` = unit）。
4. **另外查出一处坑（我第一版修法就撞上了）**：`CountSet` 的签名是 `out int count`，
   我一开始写 `return CountDrawnAsPreviousTargets(...)` —— 返回值非 `null`、**但 `out count` 还是入口赋的 0**
   ⇒ 调用方拿到 0 且**不报 gap**，与回归的形状一模一样（`play` 日志仍打「按数据 0 遍」）。
   现在改成先 `count = drawn.Value;` 再 `return count;`（`CountEval.cs:445-451`，并在代码里写了 ⚠️ 注）。

## 二 · 选了 **②**（把「本跳抽到的牌」建模成 `150` 的候选），不是 ①

**做法（`Core/CountEval.cs`）**：
- `CountSet` 的 `ta == 150` 分支（`:416-471`）：**先判「本跳抽过牌」**——
  `ctx.DrawnThisResolve.Count > 0` ⇒ 候选 = 抽到的牌（新helper `CountDrawnAsPreviousTargets` `:550-583`）；
  否则才走原来的 `ctx.PreviousAbilityTargets`（场上单位）那条老路。
- 新 helper 的筛：阵营（`SideOfCardInstance` `:585-595` —— 看这份牌在**谁的手牌**里，
  与 `SideOfUnit` 同构）＋ 卡种白名单（`DrawnKindPasses` `:605-616`：`hero`/`unit`/`tactic` 分别读
  `includeHero`/`includeMinions`/`includeSpells`；`includeWhispers`/`includeWeapons`/`includeHeroParts`
  非 0 或卡种不在三档里（`defence` 等）⇒ `null` + `gap`，⛔ 不静默当「都算」）＋ 条件行
  （`ConditionEval.MeetsCard`，主语是一张不在场上的卡 —— 与墓地那一支同口径）。

**为什么是 ② 而不是 ①**：
- **① 的代价**：`null` 会让「结构化乘数优先」整条退回正文（`try… else if (smGap != null)` 打一条
  `mult-gap` 通知）。对**这 5 张**结果数一样（3 个正交的正文/结构化都指向同一个数），但**每次都降级**、
  而且把「抽到的牌 = 上一跳的目标」这条**已经查清**的判据丢掉，往后任何「抽到的牌还要再筛一次」的
  卡（如按兵种 / 按阵营）都判不了。
- **② 能不能做干净**：能。原版证据是**抽牌那一跳自己把牌塞进 `abilityTargetsToSave`**，
  所以「候选 = 抽到的牌」不是猜的；而 `ctx.DrawnThisResolve` 本来就是这条窗口的现成载体
  （「一张卡一次结算」，`ResolveOps` 入口 `Clear`、`DoDraw`/`DoDrawChoose`/`DoDrawRef` 写），
  不需要动 `BattleContext`（也不在白名单里）。
- **为什么不往 `PreviousAbilityTargets` 里塞**：它是 `List<UnitState>`（只装场上单位），
  抽到的牌是 `CardInstance` ⇒ 结构上装不下；新开一个 `List<CardInstance>` 字段要改
  `BattleContext.cs`（⛔ 白名单外）。
- 🔴 **为什么「先判抽牌、再判场上表」**（这是我做的一个语义选择，写进代码注释了）：
  `PreviousAbilityTargets` **只在 `ResolveOps` 出口同步**（`EffectResolver.cs:592`、`:6513`），
  **结算过程中读到的还是上一张卡残值**。若先看它，实战里「先打一张指定目标的卡、
  再打 `Draw N cards. For each troop drawn …`」会把上一张卡的目标当成候选（静默多数）。
  今天池内 `ta = 150` 的消费行**只有这 5 张**「先抽后数」的战术卡 ⇒ 抽牌优先对它们**逐张精确**。
- ⚠️ **仍是近似（已标在代码里）**：`DrawnThisResolve` 的窗口是「**一张卡**」而不是「一跳」——
  若同一张卡里抽牌之后又打了别的目标再用 `150`，原版取的是**最后那一跳**（整表覆盖），
  这里会取抽到的牌。池内**0 张**这种卡。

## 六 · 顺手发现（⛔ 只报不改）

### 1 🔴 `CountSet` 的 `out int count` 是个**静默 0** 的坑（我第一版就撞上了）
`return <某个 int? 表达式>` 时若没先写 `out count`，返回值**非 null** ⇒ 调用方既不报 gap、还拿 0。
形状与本次回归**一模一样**（「看起来判了，其实读到 0」）。
建议：以后往 `CountSet` 加分支，**一律先 `count = …; return count;`**；
或把 `CountSet` 的签名改成只返回 `int?`（那是一次全文件重构，不在本件）。

### 2 🔴 `PreviousAbilityTargets` **在结算过程中是上一张卡的残值**（结构性近似，未改）
写点只在 `ResolveOps` **出口**（`EffectResolver.cs:592` / `:6513`），入口**不清**。
而原版是**每个 effect 出口**就整表覆盖（`PlayAbility.c` 各 case 末尾那串
`AbilityLogic__SetPreviousAbilityTargets` 调用点，共 27 处 `param_1 + 0x80` 引用）。
⇒ 任何在**同一次 ResolveOps 内**消费 `ta = 150` 的卡，读到的都可能是上一张卡的目标。
本件用「抽牌优先」让这 5 张免疫了，但**结构上仍开着**；`AiTargets` 那一侧同样会读到残值。
要根治得在 `ResolveOps` 主循环里**逐 op 同步**（或把槽做成随结算帧的局部表）—— 会改 AI 行为，
需要单独一件 + 重钉基线。⏭ 建议进账。

### 3 ℹ️ 造牌日志的玩家名是 1-based
`DoCreate` 的日志 `造了 1 张给 {ctx.Players[who].Name}`（`EffectResolver.cs:3576`）对 P0 打的是
「给 P1」——`PlayerState.Name` 是 1-based 显示名，不是索引，**不是错**（本件一开还以为造给了对手）。

### 4 ℹ️ `play check` 的基线里仍有 6 张历史差异
`ASH46 / GOF31 / GOF4 / GSC75 / TL68 / UM77`（+ 事件电池一长串）—— 与 E7 报的一致，属**别批**改动，
等主对话统一重钉基线。
