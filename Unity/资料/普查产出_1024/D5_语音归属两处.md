## 一、件 1 · `_vs_` 台词的主人认错

### 1·1 根因（与 D4 §六·1 一致，本轮补齐判据）

`match_owner` 以前拿**整条 header**（`" - "` 分隔符之前那一段）去比卡名。`<主人>_vs_<对手>` 这种文件**两头都是卡名**：

```
VO_BlackLegion_Hexscorn_vs_Varro
  主人 side = "vo blacklegion hexscorn"   ← 卡表里叫 `Sylar Hexscorn`（全名、首段 `sylar` 都不在 header 里）⇒ 认不出
  对手 side = "varro"                    ← `Varro Tigurius` 的短名，**池里唯一** ⇒ 唯一命中
```

⇒ 这条**黑军团**台词被记到 **`UM48` Varro Tigurius** 名下（`deploy` / `src=orphan`），
而 `UM48` 的卡 SO `summonAudio` **是空的** ⇒ 原版 Varro 登场**没有语音**，我们却会播一条黑军团台词。

### 1·2 改法（`match_owner`，判据写在函数 docstring）

```python
header_raw = stem.split(" - ", 1)[0]
header_raw = re.split(r"_vs_", header_raw, maxsplit=1, flags=re.I)[0]   # ← 只留主人侧
header = " " + _norm(header_raw) + " "
```

⛔ **不许「两边都试」** —— 那正是这次错配的来源。认不出就落进「仍未并上的孤儿」，**不猜**。
（`orphan_is_dead` 里那条 `if "_vs_" in base.lower(): return None`（`_vs_` 一律保留、不当死行）**原样未动**。）

## 二、件 2 · `card_index.json` 与卡表口径不一致 ⇒ ② 级 join 不上

### 2·1 现读形状（先读再动手）

`数据/索引/card_index.json` 的 `cards[]` 键 = `name / faction / factionId / type / art / sprite / altArts / voice`
—— **没有 `uniqueId`**（1,193 行，键组合只有这一种）。所以按任务口径走第二条：**用 `cards_raw.json` 的原版 SO 身份去对**。

### 2·2 两条身份级 join（`load_index_identity_join`）

| 路 | 键 | 落到 | 为什么不是启发式 |
|---|---|---|---|
| **A（uniqueId）** | `card_index.name` + `factionId` | `cards_raw.json` 的 `cardName` + `cardArmy`（**归一化后逐字相等**）→ `uniqueId` → 我们卡 id（`_assetRefs[].origCardId`，1,127 对 / 缺 0） | 两边本来就是**同一套本地化键**；`factionId` 与 `cardArmy` 是**同一套编号**（13 个阵营各 1 个值） |
| **B（立绘）** | `card_index.art` 的**文件名 stem** | 卡 SO 的 `cardImageReference` 解出的**资产名**（`_assetRefs` 里 `assetKind=="art"`，1,127/1,127 张）→ 我们卡 id | **同一张卡的立绘资产名是唯一身份**，与卡叫什么无关 |

⛔ **没有做**：词序重排、编辑距离、模糊匹配之类的启发式（任务明令不许 —— 这一族本来就有真重名）。

**护栏（宁可认不出，不可认错）**

- 路 A：同一 `(factionId, 归一化卡名)` 对到**多个 uniqueId** ⇒ **整键不收**（实测 **105** 个键，多为同名变体/异画）；
  uniqueId 不在 `uid2our` ⇒ 不收。
- 路 B：同一立绘资产名对到**多张卡** ⇒ 整键不收（实测 **1** 个：`SM_UM_strat_Righteous Fury`）；
  **解出的卡阵营必须与 index 那行相同**（实测 38/38 一致）。
- 路 B **只在名字与路 A 都失败时**才用 —— 交叉校验：名字已 join 成功的 **564 张**里，立绘只有 **1 张不一致**
  （`EmperorsChildren / Lord Exultant`：名字指 `EC13`，立绘指 `EC56 Lord Kaphrael` 的 warlord 图）
  ⇒ 这就是「B 不能抢在名字前面」的实证。

## 四、顺手发现（只报不改，除注明外）

1. 🔴 **`AM17 "Commissar"` 名下有 10 条本来属于 `AM3 Commissar Denkler` 的语音**（本轮已由件 2 顺带纠正）。
   - 根因：`match_owner` 的 `tables` 顺序是 **full → short**，而 `"commissar"` 在 **full 表里就是 `AM17 "Commissar"` 的整名**
     ⇒ `VO_AM_Commissar Elan_*` 的 header 里含 `commissar`，**在 full 那一层就命中并直接返回**，
     根本没机会用 `short["commissar"] → AM3`。这与文件头「先全名、后首段短名」的**本意相反**
     （全名短得更离谱时反而优先）。
   - 同一批文件里 **14 条是 `AM3` 的卡 SO 直指**（`introChatSound` 等）⇒ 归属毫无疑问。
   - ⚠️ 剩下的「full 表先命中」错配风险**还在**（本轮只是把这一批从 ③ 挪到 ②，绕开了它）。
     建议另立账：`match_owner` 是否该先试**更长的全名**、或 full/short 命中冲突时**不认**。
     ✅ **2026-10-24 已由 `F5` 修掉**（`资料/普查产出_1024/F5_语音主人匹配优先级.md`）：full/short 两表
     改为**统一比较、词数多者优先**，同词数不同卡 ⇒ 多义 ⇒ 不认。SO 真值核过：**18/18 有 SO 引用的
     `Commissar Elan` clip 全部指 `AM3`，`AM17` 一条都没有**；另 5 条（`gen4..gen7` · `vsMinka`）SO 零引用。
