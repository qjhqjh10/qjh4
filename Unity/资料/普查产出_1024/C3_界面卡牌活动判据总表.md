### 一·二 🔴 未解开的冲突（这正是探针要回答的）

**若真按 112.5 画**：卡高 374.77、在 384 格里居中 ⇒ 卡底距格底 → 4.6 px；而 `Counter` 的 y 锚点是 **0.002 … 0.099667**（= 距格底 0.77 … 38.27 px）⇒ 卡会盖住张数条 33.7/37.5 px、`x2` 只剩底部 ~4 px ≈ **看不见**。
**但**用户实拍里 `x2` 清清楚楚画在卡**下沿之外的 63 px 空档里** —— 所以「有效渲染高度」一定小于 374.77。

**实拍为什么不能拿来定数**：`收藏—张牌的界面参考图（打开过滤器按钮后）.png` 里左栏右缘/卡区左缘在 **x≈330–335 image px**，而我们的 `CardsViewport.x1 = 330.2` 设计 px（`CollectionWindow.cs:191`）⇒ 这张图的「设计 px ↔ image px」≈ **1.0**，**不是** 1920/1578 = 1.2168。也就是说这张实拍的 UI 设计帧与我们的 1920×1080 假设对不上（可能是移动端 build / 录像裁切），**因此它的 83.5% 只能当「画面上卡明显小于格」的定性证据，不能当设计 px 尺子**（铁律 3：截图不定参数）。

⇒ **结论**：静态第一权威 = **格 262.5×384、零间距、`localScale = 112.5`（比例式 97.6%）**；但「张数条会被盖住」这一条与实拍矛盾，且「盖不盖住」是**能不能看见字**的硬指标。**在实况探针读到那 5 个数之前不要改 `CollectionWindow.cs:1421`**；探针一旦证实 `CardUI.localScale ≈ 112.5` 而 `x2` 仍可见，就说明还有一层我们没读到的缩放（例如 `CardUI` 内部 `2DCard` 的实际矩形 / 另一处 `localScale` 写入），那时再照实况改，⛔ 不要照 83.5% 反推。

        float bottomMargin = cardH > 0f ? (cell.H - cardH) * 0.5f : -1f;                      // 居中假设下卡底距格底

                  $"张数条y=({bar.y1:F1}..{bar.y2:F1}) 卡scale={(card != null ? card.localScale.y : -1f):F4} " +
                  $"卡高={cardH:F2} 卡/格={(cardH > 0f ? cardH / cell.H : -1f):F4} 卡底距格底={bottomMargin:F2} " +
                  $"卡底是否压住张数条={(bottomMargin >= 0f && bottomMargin < bar.y2 - vis.y1 ? \"是\" : \"否\")}");

### 5·3 静态查出的「壳卡死」唯一可疑机制（给主对话照着点）

## 顺手发现（只报不改）

1. 🔴 **事件钮图标的颜色与五颗不同**：`Event Navigation Button/Image` 的 `m_Color = (0.73585,0.73585,0.73585,1)`（73.6% 灰），而通用 `Main Menu Navigation Button/Image` = **(1,1,1,1) 白**；`OpenEventButton.SetButtonInfo` **只设 sprite、不设 color**（`OpenEventButton__SetButtonInfo.c:28-39`）⇒ 原版事件图标**天生比五颗暗 26%**。我们导入后若按白色画，会比原版亮 —— 建议照 0.7358 乘上去（或至少在注释里写死「原版这颗是灰的」）。
   - 出处：`bundle_menus_assets_all/MonoBehaviour/MonoBehaviour_-1269977380222428235.json` vs `MonoBehaviour_9040980472260485328.json`。
2. **`Menu Dark Background` 不是 1920×1080**：它的 rect 是 **4574.6 × 2572.36**（≈2.38× 宽、2.38× 高），且 `raycastTarget=1`、挂 `BackgroundCloseButton`、Image 黑 a=0.4667 —— 这是一块**远超屏幕、盖住超宽/超高的「防穿透暗底」**，`BackgroundOverDrawController` 只负责「同时只让最后一颗 `enabled`」。若哪天真要画它，⛔ 别按 1920×1080 建。
3. **`RecyclableScrollRect._mobileSizeScale`**：Cards = **1.5**、Decks = **1.25**、另一族 = 1.2 —— 这是**移动端专用**的格缩放字段（PC 上不生效，我们也没有等价物）。记下来：将来若做移动端分档，别用 `_cellWidth/_cellHeight` 直接乘，要先查这个字段在 `Initialize` 里怎么用（本轮未查它的使用点）。
4. **实拍不能当设计 px 尺子**（第 1 条已展开）：`收藏—张牌…png` 的「左栏右缘 ≈330–335 image px」对上我们的 `CardsViewport.x1 = 330.2` 设计 px ⇒ 该录像的设计帧≈1578×888，**不是** 1920×1080 下采样；凡从这张图直接量设计 px 的结论都要重算。A3 报告 §5.2 的 384/322/83.5% 是**在 image 空间里量的比值**（比值本身有效），但**换算成设计 px 的那一步不成立**。
5. **`IconSizeProbe.cs` 只有日志、没有任何 `Check`**，而它 `:61/:72/:74` 把 `1.65` 写成「标定目标」—— CalibScale 落 1.0 之后这三行注释会误导下一个人。它同时是唯一能复量 ⑨ 的探针。
6. **`MenuWindowBase.cs` 名不副实**：整份是 `WindowHeader`（窗头构建器），**没有** `MenuWindowBase` 类、也不是任何窗的基类。本任务书里「`Shell/WindowsManager.cs` 与 `MenuWindowBase` 关窗路径差异」这个前提不成立 —— 关窗只有一条路（`GameWindow` + `WindowsManager`）。
7. **原版 `CloseAllWindows` 是在 `ToArray()` 副本上倒序关、然后无条件 `Clear`**；我们是在活表上倒序关、再过滤 `Closed`。今天等价（`baseMenu` 支不会把它 Re-Add），但**形状不同** —— 将来若加新的「关窗时会重开某扇」的支，这个「等价」就会破。
8. **安卓战斗教程 SO 与菜单 FTUE SO 极易混淆**：`bundle_tutorialso_assets_all` 里的 `Warpforge_TutorialStage1..6` 是**战斗内**教程（`bg/playerDeck/turnScriptedData`），PC 和安卓都有；菜单 FTUE 的 5 份（`1_/2_/3_/4_/7_TutorialStage*`）只在 `sharedassets0.assets` 的一颗小 pid 上。报「引导缺两份」时别把前者当后者。
9. **`Event Navigation Button` 的 `Image` 出厂 sprite 是 `0_GeneralUI Atlas` 的占位**（`PPtr(3, -7836703677562955936)`），不是空引用 —— 所以「`m_Sprite` 空」这个说法（我们 `MainMenuScene.cs:819` 的注释）**要更正为「占位图」**；这也解释了为什么只看 prefab 会以为这颗钮本来有图。
