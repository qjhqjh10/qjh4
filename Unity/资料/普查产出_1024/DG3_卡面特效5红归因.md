## 二、逐条证据与修法

### #1 / #3 `A7 ④a`（δ）—— 断言量的不是「这张卡」

**被证否的那一半（可以从代码确定，不用跑）**：生产小卡档**根本不受硬矩形影响**，两种开关下**网格逐位相同**：

- `CardView.cs:3649-3650` 底层 `_art` 的调用**不带 `clampKind`**（默认 0）；
- `CardView.cs:3739` 前景层只有 `bigFront || (!board && cut && UseFrontLayer)` 才建，生产档 `UseFrontLayer=false`、`_bigImage=false`
  （`RenderCardPixels` 用的是 `CardView.Create(root.transform, data, "chk_a7_…")`，`IsBigCardView` 在 `:1704-1711` 对它回 false）⇒ **`_artFront` 不建**；
- `CardView.cs:9174` `clampKind = DebugDisableArtClamp ? 0 : clampKind;` —— 唯一读这个开关的地方，而生产档进去就是 0；
  key 也带 clampKind，两次是**同一个 key ⇒ 同一份缓存网格**。

⇒ **被测卡自己一个像素都不该变**。而日志说变了 35249 / 29008 点、最大通道差 255（= 有一块东西整块不同）。

**剩下那一半（结论）**：`RenderPixels()`（`CardFaceProbe.cs:1709-1735`）**新建一台相机渲整个场景**，没有 cullingMask、没有隔离，
而 `CheckLayers()` 是从 **`CardBaseDemo.Run` 的中途**（`CardBaseDemo.cs:322`，日志栈逐字可证）调起的 ——
那时现场里有**7 张手牌 + 1 张场上卡 + 背景 + 板位标记 + 粒子**。⇒ 「两次渲染只差被测卡的硬矩形开关」这个**夹具前提不成立**。

**修法（必做，二选一）**：
1. `RenderCardPixels` 建卡时把整棵树放到一个专用 layer（如 `LayerMask.NameToLayer("WfProbe")`），`RenderPixels` 设 `cam.cullingMask = 1 << that`；
   相机背景色仍深底 ⇒ 其它对象一个都进不来。
2. 或者 `CheckLayers()` 在空场景里跑（`EditorSceneManager.NewPreviewScene` / 临时禁用现场根节点），跑完还原。

⚠️ 这两条改完**必须复跑** `CardBaseDemo.Run` 把 ④a/④b 的读数重取一次（现在这两个数不可信）。

### #2 `A7 ④b` 矩形内 4630 点（α）—— 容差符号反了

`CardFaceProbe.cs:1254-1277`：
```csharp
float tol = 3f / ppu;                    // 3 px 容差（抗锯齿边）
wx0 -= tol; wx1 += tol; wy0 -= tol; wy1 += tol;      // ← 1261：向外扩
...
if (x > wx0 && x < wx1 && y > wy0 && y < wy1) inside++;
Check(inside == 0, …)
```

断开档（`clampKind=0`）→ 开档（`clampKind=1`）**只少画两条竖条**：从立绘板边 **x=±0.9363** 到夹边 **x=±0.9148**
（单位卡 UM78 = 671×1024：`w = 1.80059×1.04 = 1.8726`，`u0 = 0.0117` ⇒ 夹后 **±0.9148**；`ppu ≈ 300.5` ⇒ 条宽 ≈ **6.5 px**）。
**被夹掉的那条正是「从 ±0.9148 往外」开始**，而 `tol` 又把边界**往外**推了 3 px ⇒ 这条 6.5 px 里约 **3 px 落进「矩形内」**，
所以 `inside` 不可能为 0。实测 4630/7607 = **61%**（我按 3px/6.5px 算出 ~47%，加上抗锯齿正向，量级吻合）。

**这同时说明断言的原意（「夹只发生在矩形外」）是对的，只是判据写反了**：
「矩形内不许变」应该用**内缩**的矩形（把边界那圈抗锯齿排除掉）。

**修法（一行）**：
```csharp
wx0 += tol; wx1 -= tol; wy0 += tol; wy1 -= tol;   // 内缩：只断「严格在矩形里面」的像素
```
（若想更贴题，可再加一条「变化像素全落在 `|x| ∈ [0.9148−tol, 0.9363+tol]` 这两条竖带内」的正向闸。）

⚠️ 修之前先修 #1：现在这条 ④b 的差集里混着**不属于这张卡**的像素（见 #1），`inside` 那个数同样不干净。

### #4 `F4 小图档只夹 x、不动 y`（α）—— bbox 不是 v 窗口

**先确认代码是对的**：小图档 `clampUv.z = Clamp01((c.w − vMin)/spanV)`，`c.w = 0`、`spanV = 1`（1024²）
⇒ **v 窗口恒为 (0,1]**，`clampCard.z = yB0`、`.w = yT0` ⇒ 交集对 y **一格都不收**。A7 ② 的读数也印证：
`战术卡·小图档窗口 … (0.1800,0.8200)×(0.0000,1.0000)` ✓。

**y 为什么会动**：条带 mesh 是**逐行组**造的（`CardView.cs:9096-9121`）：
```csharp
float yB = Mathf.Max(FramePxYEdge(...rows.Y0 + j0), byB);
float yT = Mathf.Min(FramePxYEdge(...rows.Y0 + j1 + 1), byT);
if (yT > yB) for (…每一段…) { xL = Max(edge, bxL); xR = Min(edge, bxR); if (xR <= xL) continue; … }
```
x 一夹（`bxL/bxR = ±0.914668`），**底部那些「整段都在 ±0.9147 之外」的窄行组被整组丢掉**
（它们正是这一族卡框开口最宽的那一截：不夹时 x 能到 **−1.0403**）⇒ 保留下来的最低行组从 **−0.2487** 起 ⇒ bbox 的 y 下沿上移。

**离线复现（我按 `FrameMaskData`/`BuildFrameRows`/`ArtWindowMesh` 逐句复刻，输入 `frame_astramilitarum_strat_tier2.png`）**：

| | 预测 | 日志实测 |
|---|---|---|
| 不夹 | x[−1.0403, 0.9843] y[**−0.5848**, 1.2135] | x[−1.0403, 0.9942] y[**−0.5946**, 1.2135] |
| 夹 ±0.914668 | x[−0.8395, 0.7736] y[**−0.2487**, 1.2135] | x[−0.8395, 0.8395] y[**−0.2487**, 1.2135] |

⇒ **y 的 −0.2487 被精确复现**（差 1 px 的两处是像素边界/`ring` 复刻的细差）。结论：这不是实现缺陷、也不是误用 BIG 档，
是**断言的量具选错了**（拿 bbox 当 v 窗口）。

**修法**（`CardFaceProbe.cs:1165-1168`）：另建一块 `mBig = CardView.ArtMeshForTest(art, 1f, fr, true, 2)`，改成
```csharp
// 小图档 v=(0,1] ⇒ y 与「BIG 档夹出来的那块」必须不同（BIG 会把下沿夹到 yB0+0.10·h，上沿夹到 yB0+0.89·h）
Check(onY0 > bigY0 + 0.1f && onY1 > bigY1 + 0.05f, "…没拿 BIG 档的 v…");
```
（BIG 的预期读数：`yB0 = −1.4732`、`h = 2.8583` ⇒ 下沿 **−1.1873**、上沿 **1.0715**；离 ON 的 −0.2487 / 1.2135 都很远 ⇒ 有牙。）
另：`F4 ②`（x ⊆ ±0.9147）现在**过得太容易** —— ON 的 x 极值 0.8395 根本没碰到夹边（宽度变窄是「整行组被丢掉」造成的）。
真正有牙的是 `F4 ③`（宽 1.679 < 2.0345：不夹时两块会相等）。⛔ 别把 ② 当成「夹生效了」的唯一证据。

### #5 `CBD ★ ③1`（β）—— `KillPoseTween()` 没掐掉

**现象重算（关键，逐位对上了）**：`BaseScale 0.5508` **不是**「起点值」，而是**补间 64% 处的值**：

- 起点 `fromScale = wantBase = layout.cardScale × LayoutSpace.Scale`；
  `HandLayout.DefaultCardScale = 165 / (2.0927×108) = ` **0.73007**（`Hand/HandLayout.cs:87,96`），本自检 `LayoutSpace.Scale = 1`
  ⇒ `fromScale = 0.7301`（① 那条断言「`BaseScale` = wantBase」通过，即起点就是这个数）；
- 目标 `scale = 0.45`；割在 `Step(0.2×0.4 = 0.08 s)` = **40%**，`Ease.OutQuad` ⇒ eased `x = 1−(1−0.4)² = 0.64`；
- `0.7301 + 0.64 × (0.45 − 0.7301) = ` **0.5508** ← 与日志**逐位相同**。

⇒ **切点在 40% 进度上（补间确实在推进），`Step(0.4f)`（= 2× 时长）之后到了终点 (3.5,−2.2)/0.45** ⇒
补间**一路跑完了**，`Kill()` 没有生效（不是「本来就在终点」）。

**代码位置**：`Core/CardView.cs:7974-7978`
```csharp
public void KillPoseTween()
{
    if (_poseTween != null && _poseTween.IsActive()) _poseTween.Kill();
    _poseTween = null;      // ← 闸门不成立时，引用被丢掉、补间还活着（静默）
}
```
`TweenPose`（`:7930-7965`）建的补间：`DOTween.To(...)` → `CardTween.Use`（`SetEase/SetUpdate(Manual)/SetLink`）→
`used.SetTarget(transform)` → `_poseTween = used; return used;`。断言前置 `tw.IsActive()` **通过**（日志 `③1 前提 ✓`）。

**修法**：
```csharp
public void KillPoseTween()
{
    if (_poseTween != null) _poseTween.Kill();   // 不设闸：TweenExtensions.Kill 对已死/空补间本就是 no-op
    _poseTween = null;
}
```
并在断言里补一条自证：掐完立刻 `Check(!tw.IsActive(), "掐完补间真的死了")` —— 这样下次红的时候能一眼分清
「闸门空转」还是「`Kill()` 本身没牙」。

⚠️ **`③2`（`transform.DOKill()`）的绿是空验**：pass=1 开始时卡已经停在 `farLocal (3.5,−2.2)`（③1 把它跑完了），
切口读数「3.500,−2.200 → 3.500,−2.200」⇒ 掐不掐都绿，**它对 `SetTarget(transform)` 一点牙都没有**。
修法：两个 pass 各自从**不同的起点位姿**起（例如先 `SetPose` 到槽位再掐补间去另一个远处位姿）。
