## 零、先读这三条（会改变做事方式的结论）

### 🔴 ① 原版的规则实现**不在反编译代码里** —— 那是空壳

`d:/2/Warpforge_code/Scripts/Assembly-CSharp/`（1891 个 `.cs`）看起来像实现，**其实只有签名**：

> 全库 `if (` 出现 **0 次**，`foreach`/`for` **0 次**，**0 行方法体**。
> 每个方法都是 `return null;` / `return default;`。连 `BattleAction` 的构造函数都只赋 default。

这是 IL2CPP 的**元数据 dump**。**别再去里面找"某个机制怎么结算"** —— 找得到类型，找不到逻辑。

**它仍然有用**（类型骨架是真的）：见 §二。

### 🔴 ② 效果是**数据**，不是代码

`CardEffect.cs` 的字段（**真实保留**）：

```
string   effectName;
string   effectText;        // ← 只给 UI 显示用（CardEffectItem.cs 里它是 TextMeshProUGUI）
DefinedTrait trait;         // ← 关键词，枚举
int      traitValue;
int      meleeAttackChange;
int      healthChange;
string   buffType;
ChooseValueOptions ...;
bool     untilEndOfTurn;
```

⇒ 原版架构：**卡牌是数据，效果也是数据；"怎么结算"在引擎里、全卡池共用。**
**448 张战术卡不需要 448 段代码** —— 要写的是**动词**（约 15 个）和**触发时机**。

⇒ **例证**：「黑暗契约给予四个效果之一」**不是四段代码分支，是四张真卡**。
反编译库里搜 `pact` 零命中（`DefinedTrait` 枚举里都没有 `darkPact`），
但 `card_stats.json` 里那四张卡**确实存在**，效果文字与我们的实现**逐字一致**（见 §一）。

⇒ 对我们的意义：`EffectText.cs`（解析英文卡面）**结构上与原版同构**（数据驱动 + 引擎共用结算），
差别只在**数据来源** —— 原版拿的是结构化字段，我们拿不到（在远程包里），只能解析文本还原。
**这条路没错，继续走。**

### 🔴 ③ 回合模型：**一方整回合做完 → 换另一方**（不是双方并行）

`IPunTurnManagerCallbacks.OnPlayerFinished(...)` + `PunTurnManager.finishedPlayers` +
`IsCompletedByAll` 一度被读成"同回合双方各自行动"，**那是误读**：
`SendMove(move, finished)` 的 `finished=false` 表示**同一方在一个回合里还要继续提交动作**，
`finished=true` 才是这一方做完了。⇒ **和我们引擎现在的模型一致，不用改。**
（本条由用户 2026-09-12 当场纠正，记在这里免得下个会话又读岔。）

`EffectResolver` 按 **`EffectDispatch` 表**分派结算。**加新效果 / 关键词 / 阵营机制的三条路见 §四·六。**

### 一·二、`create` 造牌（第十四轮）

### 一·三、`deploy` 免费部署（第十五轮）

**做了什么**：`Deploy …` 这一族 **50 个分句 / 49 种写法**从「解析得出来、结算没分支」变成真能部署。

| 件 | 落点 |
|---|---|
| 解析五种写法（具名 / 阵营+兵种+费用 / 从牌库 / 从弃牌堆 / `and` 尾句） | `EffectText.TryDeploy`（`DeployFrom` / `CostMin` / `CostMax` / `UpTo` / `Tail`） |
| **免费下场** | `RuleCore.DeployFree`（逐条照抄原版 `rule_core.gd:3871 _deploy_unit`） |
| 结算 | `EffectResolver.DoDeploy`（和 `create` **共用** `CreatePool` 与 `PickN`） |

**⚠️ 三条语义上是**故意的**，不是漏的**：
1. **不触发 Rally** —— 规则书 `:200` 写的是「集结：**从手牌**部署后触发」，原版 `rule_core.gd:2314`
   也只在 `play_card` 那条路上触发。`RuleCore.PlayCard` 照旧触发，两条路不一样是对的。
2. **满场不硬塞** —— 原版 `_deploy_unit` 返回 false，我们照办并**在日志里说「没空格了」**。
3. **`2-cost` = 恰好 2 费**（不是「≤2」）—— 三条实证：GSC 恰好 2 费 = 5 张（对上附录 C 的 1d5 名单）、
   Sautekh = 6 张（对上附录 B「次元裂隙…**6 种**」）、Leviathan = 6 张（对附录 C 的 1d5 + 1）。
   `that cost N or less` / `that costs N or more` 才是显式区间，两种分开处理。

**⚠️ 弃牌堆那条是近似**：`Deploy up to 5 friendly Infantry troops that died this game` 拿
`Discard` 里 `type == "unit"` 的充数 —— 我们**没有「本局阵亡」的账**，手牌超上限打进弃牌堆的
单位卡也会被算进去。原版有完整的阵亡流水，我们没有。**如实标着，别当它是精确的。**

### 一·四、`give it/them X` 的指代（第十五轮，顺手修的，但影响面很大）

**问题**：`TryGive` 的第三种语序 `Give it Flank` / `give them Vanguard` 把**代词本身吃掉了**，
`op.Target` 成了 null → 结算层落到「**己方全体**」那个近似（原版 `rule_core.gd:3137` 自己标着「近似」）。
后果有两层：
- **打错人**：`Deploy 3 Grot and give **them** Vanguard` 给**全体**加，而不是给刚部署的 3 个；
- **判成半懂**：`Finish` 见「没目标」就判 `Partial`，于是**六个 `Deploy … and give it/them X` 的卡
  白白掉出「完全解析」** —— 做 deploy 时撞到的。

**修法**（两处，都在一处判据上）：
- `TryGive` 的代词**留着**当目标（`ParseTarget` → `Side = "prev"`）；**单复数分开**：
  `it` / `the target` = 1 个，`them` = 一批（`Count = 0`）。
- 新增 `BattleContext.LastTargets`（**上一条效果影响到的整批**）—— 只记单个 `LastTarget`
  表示不了 `them`。`ResolveTargets` 和 `DoDeploy` 都写它。
- `Finish` 里「没目标算半懂」收成一处 `NeedsTarget(op)` —— 原来写死 `op.Verb != "draw"`，
  `create`/`deploy` 这些**本来就不带目标**的动词一进来就被判半懂。

**效果**：半懂分句 **28 → 4**（`_tmp_view/tactic_unparsed.txt` 第 ② 栏几乎清空）。

### 一·五、第十六轮：四个动词补完 + 两个阵营的机制（用户指定）

**用户定的方向**：先做简单的 → 把**极限战士 + 兽人**做到能完整对战 → 然后检查对战顺不顺。

**做了四件**：

| 件 | 落点 | 关键点 |
|---|---|---|
| **`drawtype`** | `RuleCore.DoDrawType` + `CreatePool.MatchesKind` | 语义照**规则书 L461-466**：「从牌库顶往下翻，找到匹配的拿走，翻过去的**留在牌库**，然后**洗牌**」 |
| **`lowercost`** | `EffectOp` + `RuleCore.CostOf` + `ctx.CostMods` | ⚠️ 要给**卡实例**存费用覆盖，但 `CardDef` 是共享不可变对象 ⇒ 修正只能记在 **ctx** 上。**当时按卡名匹配（同名卡一起降价）；2026-09-13 改成按卡 id**（同名卡不再一起降）—— ⚠️ **卡实例身份仍未做**，见 `资料/阵营推进_清单与交接.md` 候选 0 |
| **`repeat`** | `EffectOp.RepeatOps` + `RuleCore.DoRepeat` | **这是 `EffectOp` 里第一种「op 之间的引用」**（此前只有 `instead` 靠一个下标硬撑）。由 `Parse` 在整条 desc 解析完后回填 |
| **`Oath N:` / `Codex:`** | **复用已有的付费层和条件层** | `Oath N:` = 付费激活（和 `12 [Energy]:` 同一条路）；`Codex:` = 条件 `energyzero`（规则书 :175「能量为 0 时触发」）。**没另开动词** |
| **`Stomp`（践踏）** | `RuleCore.DeclareAttack` | 规则书 :213「溢出伤害对目标相邻**随机**敌方单位造成」；照 `rule_core:4372` 的三个判据（目标死了 / `dealt > 打之前血量` / 相邻有单位） |

**顺手修掉的四个真问题**（都是做上面那些时撞出来的）：

1. **三个「清单」收成一处** —— `ResolveOne` 的 `switch` 和 `ImplementedEffectVerbs` 原来要**手工对齐**，
   忘一边就是「能打但不报」或「报了但能打」，两种都静默。现在是一张 `EffectDispatch` 表，清单**从它派生**。
2. **覆盖率里有两条过期的误报** —— 「付费激活没接结算」这条检查是**过期的**（结算层早就实现了付费分支），
   留着它把 `Oath N:` 一族**错报成没机制**（Ultramarines 7 条）。已删。
3. **`StarterDeck` 的 `unitsOnly` 开关从来没实现** —— 函数体里写着「已经是只收 unit 了」。
   后果：**自动凑出来的牌组一张战术卡都没有**，实战里永远看不到战术。
4. **`SimpleAI` 只出单位卡** —— 同上。`NextCardToPlay` 里写着 `if (!c.IsUnit) continue`。
   ⇒ 3+4 合起来：**引擎自检里战术卡用例全绿，真打起来却从来没碰过它们**。
   现在 `NextPlay` 单位/战术都考虑，落点**由引擎说了算**（挨个格位问 `CanPlayCard`）。

**⚠️ 我自己踩的一个坑（值得记）**：`lowercost` 的正则第一版把四条写法塞进一条大正则，
其中 `of?` 被当成「`of` 里的 f 可选」，于是 `Lower the cost of all Vehicles…` 的 payload
被切成了 `f all vehicles…` —— **而且照样算解析成功**。
是「切出来的 payload 长什么样」的断言抓不住「认不认识」这类检查漏掉的错。
教训写进了 `TestLowerCost` 的注释：**只断言「认不认识」抓不住静默的错解析。**

### 三种 `for each` 写法**语义不同**，别混（`EffectOp.CountRef` / `PerCount`）
| 写法 | 例 | 语义 |
|---|---|---|
| 前导 / 后置 | `Deal 1 damage to an enemy for each friendly unit` | **重复 N 遍**（N=0 就一次都不结算） |
| 追加 | `…, and an additional +2 X for each Dark Pact on it` | **基础 + N × 增量**（当重复算会 +2 变 +6） |

### 另外四个坑（都写进代码注释了）
1. **`give` 的数值不在 `op.Amount` 里，在载荷原文里** —— 只改 `Amount` 的话增量静默丢掉
2. **`EffectOp` 列表是解析产物、会被复用** —— 直接改 `Amount` 会让同一张卡第二次打出时翻倍
3. `instead` 的替换判断读到了**上一张卡**留下的 `ctx.LastTarget`
4. 计数写 0 时不能去改载荷（会把基础值抹掉）

### 一·六、第三十一轮（2026-09-13）：**单位卡 `desc` 的触发式效果接进引擎**

**修之前**：触发式正文**只**走 `EffectSpec` 那个**封闭文法**（只有 `Damage` / `Heal` / `Draw`），
而原版卡面写的是 `Rally: Stun an enemy` / `Strike: Return this troop to your hand` ——
**解析失败 ⇒ 卡面标 `*` ⇒ 打起来静默不动**。实测 **89 张卡**在 `keywords` 和 `desc`
**两处都登记了触发、正文却没人认**。

**修之后**：正文交给 `EffectText`（**战术卡用的同一个解析器**，卡面本来就是同一套语法）。

| 件 | 落点 |
|---|---|
| **触发关键词 → 正文 op**（两个来源都收：`Desc` 优先、`keywords` 兜底） | `CardDef.CollectTriggerOps` + `TriggerOps()` / `TriggerText()` |
| **只有本版有时机的触发才收**（`RoutableTriggers`） | `CardDef.RoutableTriggers` = Rally / Strike / Slay / Backlash / Penitence |
| 触发时优先走 op，没有才退回封闭文法 | `RuleCore.FireTriggerAt` |
| 把一串 op 结算掉（**新入口**，和 `ResolveEffect` 并存） | `RuleCore.ResolveOps`（定义在 `Core/EffectResolver.cs` 里） |
| 查证探针（只报数、不断言） | `RuleEngineTest.ReportUnitDescCoverage` → `_tmp_view/unit_desc_unparsed.txt` |

**数字**：以自检探针 `RuleEngineTest.ReportUnitDescCoverage` → `_tmp_view/unit_desc_unparsed.txt` 为准
（每次自检重写），**本文档不抄第二份**。

**收哪些触发点**（这是结构，不是数字）：`CardDef.RoutableTriggers` 只收**本版有时机的**那几个 ——
`Rally` / `Strike` / `Slay` / `Backlash` / `Penitence`；其余（`Talent` / `Pray` / `Duty` / `Agenda` /
`Mob` / `Regiment` / `Artifice` / `Codex` …）**缺的是触发时机、不是解析** ⇒ 收了也没人消费，**故意不收**；
`When <事件>, …` 要的是**事件层**。

**踩的坑（都值得记）**：

- 🔴 **代词 `this troop` 是静默错打**。`ParseTarget` 把 `it`/`this troop`/`this unit` 这一族
  **统一归到 `prev`**（那是给战术卡的 `Choose a troop … Draw it` 用的）。
  触发式正文里**没有「上一句」** ⇒ 不处理的话 `Return this troop to your hand` 会去回手
  **上一张被指过的牌**，而场上还看不出哪里不对。
  **修法**：`ResolveOps` 在开头把**触发者自己**种进 `LastTargets`/`LastTarget`
  （借的是同一套代词机制，不另开口子），**只种一次**（后面的 `and give it …` 要能接着用），**用完还原**。
- **不能只看 `Desc`**：有 **35 张卡只在 `keywords` 里写了正文**（`Desc` 里没有）—— `CardDef` 两个来源都收。
- **别用 `KeywordTable.Normalize` 判触发名** —— 它是**前缀匹配**，`Pray: …` 会被它当面。用整词比对。
- **断言要钉两层**：① 正文被解析出来了 ② **它真的改变了局面**。
  只钉① 会漏掉「解析出来了但结算层没分支」。**打断 `FireTriggerAt` 那条新路重跑验证过**：
  断言会红（`Check` 失败 + `ResolveEffect` 空引用，两条都亮）。

**还没做的（下一件）**：`When <事件>, …` 要**事件层**；其余触发时机类关键词要的是**新的触发时机**，
不是新的解析。**现状与剩余清单看 `资料/阵营推进_清单与交接.md` §五 + 候选 A**（本文档不抄数）。

### 🔴 最大的发现：**14 条里有 6 条只差正则宽度**

`EffectText.cs:2128` 的 `RePaid` 比 `rule_core.gd:1549` **窄两处** ——
**主对话已独立核过两边的正则原文**：

| | 写法 | 后果 |
|---|---|---|
| Unity | `\[\s*(energy\|faith\|…)\s*\]` —— **方括号必选** | 收不了 `4 Energy:`（无括号）→ **#8 / #23** |
| Unity | **没有 `\((\d+)\)` 分支** | 收不了 `(5) Reduce…` / `(1) Draw…` → **#31 / #33** |
| `rule_core` | `\[?[Ee]nergy\]?` —— 括号**可选**；另有 `\((\d+)\)` 分支 | 两边它都收 |

### `CardTrait` 的形状（每关键词一个 ScriptableObject）

```csharp
public class CardTrait : ScriptableObject {
    public enum TraitStackType { ... }
    public enum EffectTriggerType { ... }
    public List<TraitEffect> TraitEffects => null;   // ← 效果是**数据**
    public virtual bool IsActive(CardScript card) { ... }   // ← 唯一的虚方法
    public float AIScore => 0f;                      // ← AI 评分也是数据
}
public class CardTraitDuty : CardTrait { public override bool IsActive(CardScript card) { ... } }
```

## 四·五、**效果分类表**（2026-09-12 第十五轮新增，自动生成）

`_tmp_view/tactic_taxonomy.md` —— 由 `RuleEngineTest.DumpTaxonomy` 每次跑自检时重写。

**为什么要有它**：这套分类一直**只活在 `Dispatch` 的 handler 顺序里**，没有任何一处写下来。
于是「加新效果该放哪一格」只能靠读代码推。写成表之后，缺格/混格/哪格满了，一眼能看出来。

一张卡的效果 = **(动词, 载荷, 目标, 条件, 时机)** 的组合。表分三层：动词 → 载荷子类 → 目标/条件。

**实测的分布**（449 张战术卡 / 660 条分句）：

| 层 | 规模 | 说明 |
|---|---|---|
| **动词** | **18 个** | `give` 201 · `deal` 91 · `deploy` 35 · `gain` 27 · `draw` 25 · `create` 22 · `heal` 17 · `destroy` 16 · `drawtype` 14❌ · `repeat` 12❌ · `lowercost` 12❌ · `stun` 11 · `gainenergy` 9 · `chooseone` 6 · `refill` 6 · `reanimate` 3❌ · `blind` 3 · `lose` 1 |
| **载荷** | `give` 一族有 **14 种组合** | 关键词 / 属性增减益 / 属性+属性 / 属性+关键词 / 嵌入效果 … |
| **目标** | **34 类** | `own/troop(n1)` 68 · `own/unit(n1)` 62 · `enemy/any(n1)` 51 · `prev/prev` 32 … |
| **条件** | **13 类** | `targetdies` 16 · `istype` 9 · `controlcount` 8 … |

⚠️ 上面这组**分布数字与 ❌ 标记是 2026-09-12 的快照**（❌ = 当时没实现的动词）—— 那三个 ❌
后来都补完了（§一·五）。**最新分布看 `RuleEngineTest.DumpTaxonomy` 生成的 `_tmp_view/tactic_taxonomy.md`。**

⚠️ **这张表暴露了三处分类本身的问题**（不是实现 bug，是分层没分干净）：

1. **`stun` / `blind` 本来是「关键词」，被提升成了动词** —— 它们和 `give Stun to X` 是同一件事，
   而 `GivePayload.GiveKw` 里**也有 `stun`**。同一个效果有两条路 = 「两处写同一条规则」。
2. **`gainenergy` 是 `gain` 的特例** —— 解析器把裸数字的 `Gain 1` 改写成它，不值得占一个动词。
3. **`chooseone` / `repeat` 是控制流，不是效果** —— 和 `deal`/`heal` 并列在同一个 switch 里，语义层级不同。

⇒ **真正的分类重心在载荷层，不在动词层**：`give` 一家占了 30% 的 op，而它的分支全在载荷里。

## 四·六、加新东西怎么办（2026-09-12 第十五轮，回答「以后要加新效果/词条/阵营机制」）

三条扩展路径，各自的**摩擦点**（都是实测的代码事实，不是估计）：

### A. 加一个新**效果（动词）** —— 比如下一步的 `repeat`

| 要动哪 | 为什么 |
|---|---|
| `EffectText.TryXxx` | 解析（多半已经写好了，`repeat` / `lowercost` / `drawtype` / `reanimate` 都在这状态） |
| `RuleCore.ResolveOne` 的 `switch` | 结算分支 |
| `RuleCore.ImplementedEffectVerbs` | **覆盖率清单** —— 不加它，卡就「能打但不报缺机制」 |
| 自检 | 断言 |

⚠️ **摩擦点（2026-09-13 已消掉）**：`switch` 和 `ImplementedEffectVerbs` 这两张清单原来要**手工同步**，
忘一边就是「能打但不报」或者「报了但能打」。**现在收成一张 `EffectDispatch` 表、清单从它派生**
（§一·五）—— 加动词只改一行。

⚠️ **`repeat` 是唯一会顶到架构的一个**：它要「把**本句之前**的效果再来一遍」，
而 `ResolveOps` 是**顺序遍历 + 扁平 ops 列表**，op 之间没有引用关系
（`instead` 的配对靠 `insteadBase[i]` 这个**下标**硬撑）。**做它的时候顺手把「op 之间的引用」
正经设计了一遍**（`EffectOp.RepeatOps` + `Parse` 整条 desc 解析完后回填，§一·五）——
**再要跨 op 引用就沿用这套，别再堆第二种下标技巧。**

### B. 加一个新**关键词** —— 比如 `Ephemeral`（原版 `DefinedTrait.ephemeral = 5`）

| 要动哪 | 为什么 |
|---|---|
| `KeywordTable.Implemented` | 第三张清单 |
| `RuleCore` 的**机制代码** | ⚠️ **散在 3–5 个函数里**：`FieldAttack`（pack/blind）、`DeclareAttack`（sentry/sniper/blast/shuriken）、`ApplyDamage`（vulnerable/invulnerable）、`EndTurn`（regeneration/blind 到期）、`ResolveTargets`（stealth/camouflage 拦截） |
| `GivePayload.GiveKw` | 如果它能被 `give` 授予 |

⚠️ **摩擦点：没有一个「关键词对象」可以往里塞。** 加一个关键词 = 改 3–5 个函数，
而且改的地方取决于这个关键词属于哪类时机（攻击前 / 受伤时 / 回合结束 / 选目标时）。

**原版给的形状**（§二 早就查到了）：每个关键词一个 **ScriptableObject**
（`CardTrait.cs` + `CardTraitCollection` 的 `Dictionary<DefinedTrait, CardTrait>`），
替代行动族甚至是**独立子类**（`CardTraitDuty` / `CardTraitFerocity` / `CardTraitOath`）。
**原版没有这个摩擦点。**

### C. 加一个**阵营特色功能** —— 比如黑暗契约之后再来 Oath / Codex / Agenda

现状：黑暗契约散在**五处** —— `KeywordTable.DarkPact`（名字）、`GivePayload.ExtractVariant`（变体名）、
`EffectResolver.GrantDarkPact` + `DarkPactFx` 表（结算）、`_keywordsPact` 旁表（状态）、
`PactGrantedKeywords`（回收）。而且**硬编码在通用结算器 `EffectResolver.cs` 里**。

⚠️ **摩擦点：一个阵营的机制坐在通用结算文件里。** 加第二个会继续往里堆，加到第五个这个文件没法看。
原版是**独立子类**。

### 结论

- 加新东西**不会崩**，三条路现在都走得通、也都有先例（`create` / `deploy` 就是照这条路加的）。
- **「清单要手工同步」那条已经消掉一半**：**动词**那两张已合成 `EffectDispatch` 一张表（§一·五）；
  ⚠️ **关键词那张（`KeywordTable.Implemented`）还是手工的** —— 加关键词时别忘。
- **两处真正的架构摩擦**：① 关键词没有对象（散在函数里）② 阵营机制硬编码在通用结算器里。
  这两处**现在不用动**，但**每加一个都会更疼** —— 关键词批量补（还差 30 个）或第二个阵营机制要开工时，
  就该先花一轮把它们对象化。
