## 一、3 条 tier4 覆盖红 —— 是 H 的改动引入的（但不是渲染缺陷）

### 1·1 具体哪一行
- **H 的拆分**：`Core/CardView.cs:7344-7353` —— `Runs` 只收 `hole ∪ ring` 的**连通段**，
  同一行里被**实心金属隔开的两块开口**会分成两段，中间那段金属**不画**。
- **基线的口径**：`Core/CardView.cs:7355-7366` 存 `L/R` = 该行**开口像素的 min..max**；
  `FrameArtCoverage` 拿它当分母（`:7768-7783`），分子只认网格盖住的 x 区间（`:7793-7817`）
  ⇒ **金属那一段永远算"漏"**。
- 对照 **HEAD**（`git show HEAD:…/CardView.cs` `:7397-7430`）：当时 `ArtWindowMesh` 每行是
  **一条 `[L..R]` 的大 quad**，把金属那一段一起画了 ⇒ 基线 == 画法 ⇒ 覆盖率恒 100%。
  **H 一拆段，基线与画法就分叉了** —— 红就是这么来的。
- ⚠️ `FrameArtCoverage` 的 doc（`:7729-7731`）写着「逐行开口 = 该行 min..max（**条带方案要画的正是这一段**）」
  —— **这半句现在是假的**，H 之后条带只画连通段。

### 1·3 为什么 tier1 / tier3 没事
- `saimhann tier1`：单连通圆角窗，每行只有**一段** ⇒ 基线 = 段 ⇒ **0.000%**。
- `blacklegion tier3`：只有少数行有侧向小洞 ⇒ **0.16%**（< 0.5% 阈值）。
- 三张 tier4 在**主窗的同一行上有大侧洞**（106~157 px 宽）⇒ 5.10~7.37%。
- 附带一笔：gene 还有 **4.8% 的漏**来自**立绘板之上**的行（y≈1.398–1.408 > 板顶 1.385，行基线按
  min..max 把它算进去了；逐像素只占开口的 0.10%）。原版 `CardImage` 是 2.7484²、板顶更低，
  那几行**原版也没有图**。⇒ 基线必须**夹到立绘板**。

### 1·4 修复方向（二选一，**不要靠放宽阈值**）
- **方案 A（推荐 · 改断言口径 · 零渲染改动）**：把 `FrameArtCoverage` 的基线换成
  **逐像素 `hole`（+`ring`）∩ 立绘板 ∩ 卡体**，即照 `FrameArtBevelCoverage`（`:7876-7919`）那套写；
  改 `CardView.cs:7764-7818`。改后五张全是 **0.0000%**，红线当场归零，且**仍有牙齿**。
  - ⚠️ **连带要改**：`Editor/CardFaceProbe.cs:577-580` 的 `rectMiss > 1f`。逐像素口径下测得
    `ultramarines tier4 = 0.99%`（gene 6.88 / astra 5.95 / blacklegion3 6.56 / saimhann1 3.22）
    ⇒ 阈值改 **0.5**，或把 ultra 那张的牙齿换成 gene/astra（那两张矩形确实漏 5~7%）。
- **方案 B（改渲染 · 保持断言原样）**：`AddBevelRun`（`:7507-7519`）的跨段合并**允许跨越
  `alpha ≥ 248` 的实心金属**（⛔ 只许金属，不许 `outside`/透明 —— 那正是 `ultramarines` 底部
  16 行缺口的成因，跨过去 `spillPct` 会红）。补满 min..max 后视觉逐位不变，且**更像原版**
  （`FlipAlphaMask=1`：金属底下本来就有图）。⚠️ gene 仍余 **0.32%**（板外那几行）⇒ 基线还得夹板。

## 二、CBD ②（板心 = 卡名行心 − 0.3765）

### 2·1 是 L 的字体改动引入的吗 —— **是**（但它是"压垮"不是"造病"）
- 本会话前（`cardbase_textbg_1021.log` / `w61_cardbase.log` / `cardbase_run.log` / `rerun_…log` 四份一致）：
  **−0.2916**（差 0.3584，离 0.02 容差只剩 **0.0019**）。
- 本次：**−0.2936**（差 0.3564）⇒ 偏差 **0.0181 → 0.0201**，比值 **1.1105 ≈ 1/0.9 = 1.1111**。
- 战术那条同样下移（−0.4791 → −0.4805，偏差 0.0180 → 0.0194），只是**离阈值还剩 0.0006** 才侥幸绿。

### 2·2 链路（为什么 `m_Scale` 会动到卡名行心）
1. `CardView.cs:3326` 卡名 TMP 走 **`TmpFont.Face.LatinUi`（Asar，`m_Scale = 1`）**；
2. 字号 = **`NameFontSize`**（`:3672-3679`）→ **`TmpFont.FontSizeForGlyphHeight`**
   （`TmpFont.cs:358-360`）→ **`WorldGlyphPerFontSize`**（`:333-340`）→ `MeasureGlyph('国')`
   （`:590-625`）**量的是 CJK 那一份**；L 把它的 `m_Scale` 改成 0.9 ⇒ 读数 0.0948 → 0.0853
   ⇒ **fontSize × 1/0.9**；
3. **Asar 的 `m_Scale` 仍是 1** ⇒ 同一个 fontSize 下字形 **真的大了 11%**；
4. `Fill` 末句 `PlaceAt`（`:3702-3708`）按 `textBounds`（**行盒**）摆，随后
   `verticalAlignment = Geometry`（`:3345-3348`）才把整块字平移一个「行盒心 ↔ 墨心」的差
   ⇒ 实测行心 = 目标点 ± 那个差；**该差 ∝ 字号** ⇒ 0.0181 × 1.111 = 0.0201。
- 🔴 **L 的「渲染逐位不变」只对 CJK 渲染成立**（`fontScale = fontSize/pointSize × scale`：
  fontSize ↑ 与 scale ↓ 抵消）；**对 Asar / Pragati 面不成立**（scale 恒 1）。

### 2·3 由此暴露的真缺陷（β，比这条红更重要）
- `ArmyFontSize`（`:3504-3507`）· `RaceFontSize`（`:3509-3513`）· `KeywordFontSize`（`:3689-3692`）
  **同样吃 CJK 标定，却渲染 Pragati**（`:3377/:3406/:3414`）⇒ 本次一并**涨了 11%**（名/createdBy = Asar，
  desc/army/race = Pragati）。`FontSizeForEm`（按面）全仓只有 `Battle/Label.cs:1410` 一个消费者。
- 全仓**没有一条断言量卡面字号**（本次日志里 0 条「字号」）⇒ 只有 CBD ② 间接抓到。

### 2·4 修复方向
- **修实现（β）**：卡面这几档字号改成**按实际面**换：`TmpFont.FontSizeForEm(face, worldEm)`
  （原版 em 注释里都写着：name `0.19` / desc `0.2355` / army `0.15` / race `0.18`；
  即 `Height × 0.0570 / 0.0707 / …`）。这一步**同时**让字号与 CJK `m_Scale` 解耦，CBD 回到 **0.3584**。
  ⚠️ 副作用：比现在**小 11%**（回到 L 改之前），且比原版 em 目标**大 5.4%**（那是既有偏差，另开账）。
- **修断言（α）**：`TmpRowCenterY`（`CardBaseDemo.cs:1906-1914`）量的是 `textBounds.center` = **行盒**，
  而 `0.3765` 的期望来自 `NameTextUnit` 的**节点中心**（Midline 时 = 墨心）
  ⇒ 天然带一个**随字号缩放的系统偏差**，容差 0.02 又是「没跑过就定」的（`普查产出_第十七会话/J_断言_CardBaseDemo.md:76`）。
  改量**墨心**（`MeshFilter.sharedMesh.bounds.center` 或 `textInfo.meshInfo` 的 bounds），容差收到 **≤0.005**。
  改量墨心后 ①（绝对 −0.65）与 ②（相对 −0.3765）仍是两个独立来源，灭自证不受影响。

## 三、原版判据（回答「能不能算原版如此」）
- **插图画窗**：`bundle_staticgeneralassets_assets_all/MonoBehaviour/MonoBehaviour_5590396362908354958.json`
  —— `SoftMaskScript` · **`FlipAlphaMask = 1`** · `CutOff = 0` · `HardBlend = 0`，`MaskArea` = 2.7484²。
  ⇒ 立绘**铺开、由卡框 α 反相遮罩**：**透明处（开口）必须有图，半透明处按 1−α 透出**；
  **不透明金属底下有没有图看不出来** ⇒ **基线只该算 `hole` + `ring`，不该算 min..max 里的金属**
  （这就是判「改断言」而不是「改渲染」的原版依据）。
- **卡名位置**：`bundle_battleprefabs_vfxandmisc_assets_all/RectTransform/RectTransform_4173703600236829632.json`
  —— apos **y = 0.5009999871**、`m_LocalScale = 0.01`、pivot 0.5（父级 −0.7745 ⇒ 节点中心 **−0.2735**）；
  TMP 实例 `bundle_staticgeneralassets_assets_all/MonoBehaviour/MonoBehaviour_-1615900510080513528.json`
  —— `m_fontSize = 19` · **`m_VerticalAlignment = 4096`（Midline）** · `m_HorizontalAlignment = 2`。
  ⇒ 该落在 −0.2735 的是**墨心**（Midline 的定义），不是行盒心 —— 判据同上 §2·4。
