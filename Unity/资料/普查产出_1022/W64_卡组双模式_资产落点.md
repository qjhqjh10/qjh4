## 一、两张模式卡的大图 ★核心

### 1·1 结论

| 卡 | 原版真名 | bundle | 分辨率 | `ui_extract` | 我们 `Resources/Art` |

| **左（小冲突）** | `40k_main_GameMode_Skirmish` | `bundle_liveopsmenuimages_assets_all` | **1024×1024**（`m_TextureFormat`=28） | `d:/2/Warpforge_tools/data/ui_extract/liveopsmenuimages_assets_all/Sprite/40k_main_GameMode_Skirmish.png` ✅ | `Resources/Art/ui_menu/40k_main_GameMode_Skirmish.png` ✅ |

- 两张**与参考图逐像素对得上**：左卡 = 泰伦虫族扑向白甲（钛）战士 + 底部蓝色能量剑光；右卡 = 极限战士跃起劈向兽人。已把解包 PNG 与参考图并排核过。
- 我们本地两份与解包原件 **byte-identical**（PIL 逐像素 `maxdiff = 0`）。
- sprite 参数：`m_Rect = (0,0,1024,1024)`、`m_Border = 0`、`m_Pivot = (0.5,0.5)`、`m_PixelsToUnits = 100`、`uvTransform = (100, 512, 100, 512)` ⇒ **满幅、无九宫、无 tight 打包**。

### 1·2 ⚠️ 关键：prefab 里**没有**这两张图的 PPtr

`Game mode deck selector` 的 `Background Image`（RT `3173866314144024004`）与 `Foreground Image`（RT `6612486878597940676`）：

```
IMAGE sprite=file0/pid0   ← m_Sprite = null（= PPtr 0/0，没有任何 sprite 可反查）
Background Image: m_Material = Material 3583370424645672959（shader = `Shader Graphs/UI Container Main Menu`）
Foreground Image: m_Material = null
```

⇒ **不存在「按节点字段的 PPtr 反查 GUID」这条路** —— 这两张图是**运行时由 liveop 活动数据灌进来的**（`GameModeDeckSelector` 的 `backgroundImage` / `foregroundImage` 两个字段）。

我核过**同族一共 5 份**卡 prefab，`Background Image` / `Foreground Image` 的 `m_Sprite` **全部为 null**：
`Game mode deck selector` · `Base Game Mode Container 1x2`（RT `-5265826691577602442`）· `Base Game Mode Container 1x1` · `Ranked Game Mode Container 1x2`（RT `1753533556652153358`）· `Skirmish Ranked Game Mode Container 1x2`（RT `7201036260871538908`）。

**那「左=Skirmish / 右=Ranked」是怎么定下来的？（三条独立证据）**

1. **画面**（最强）：两张解包 PNG 与参考图的那两张卡**一模一样**，不是「像」—— 构图、色块、人物姿态逐个对得上（见 §1·1）。
2. **工程内已有同一条映射**：`Assets/CardPresentation/Shell/MainMenuRuntime.cs:2293-2294`（2026-10-13 那一轮，用用户 `主界面参考图.png` 逐列放大核过）已经写下「`40k_main_GameMode_Skirmish` = 小冲突 · `Container_Image_Ranked` = 排位/经典」，并注明「与我们的那张**一模一样**，已并排比过」。
3. **几何自洽**：卡面 505.93×802.67（竖），`Background Image` 挂 `AspectRatioFitter(m_AspectMode=2 HeightControlsWidth, ratio=1.0)` ⇒ 画成 **802.67×802.67 的正方形**，锚点 `(-0.294,0)-(1.294,1)` ⇒ 803.3 宽，再被根上的 **`RectMask2D`**（`m_Padding 0 / m_Softness 0`）裁回卡片 ⇒ **正好是「1024² 方图取中间竖条」**。这与「原图是 1024×1024 方图」完全吻合。

> ⛔ **不要**去找一个「保存着这两张图引用的 SO」—— 本地没有（见 §七·1 搜索证据）。

### 1·3 顺序

参考图里 **左 = 小冲突 · 右 = 经典**。原版这一页的卡片来自 liveop 活动列表（`SelectDecksTab.ChooseTabToOpen` 数 `IOwnDeckPlayEvent`），**顺序由服务端事件数据决定**，本地拿不到事件实例 ⇒ 这个左右次序**只能当「参考图口径」**，不是能从 prefab 推出来的常量。

### 7·3 `Border` 的加法材质

原版 `Border` 挂 `Everguild/UI/Additive`（blend One/One）。我们现有实现是**普通 alpha 混合**。在暗红底上两者视觉差很小（参考图核对过是「浅灰细线」），但**严格说这是一处已知偏离**；要不要做加法混合，由施工方按代价决定并记账。
