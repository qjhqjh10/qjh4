# C1 · 卡背「比例」裁定 —— 原版取的到底哪个矩形

> 只读查证代理 C1 · 2026-10-19 · **本件只出结论，没有改任何代码/资产**。
> 判据全部现读（原文出处见每条的 `文件:行号` / 资产路径）。**没读到的照写「没读到」。**

## 〇 一句话结论

**原版的规则是两段、不是「二选一」**：

1. **定框**：uGUI 只用 `activeSprite.rect`（= Sprite 的 **`m_Rect` = 707×1020 = 0.693137**）去内接进节点/框 ——
   *不是* `textureRect`（每张不同）。
2. **贴画**：把贴图贴到「框」里**按 `padding` 内缩后的那一块**上 —— 等价于
   **画出来的尺寸 = 框 × (`w_t`/707, `h_t`/1020)**，因框的比例 == `m_Rect` 的比例 ⇒ 两轴系数相等 ⇒ **等比**，
   **画出来的比例 = `textureRect` 的比例**。

⇒ 对我们那批**已按 `textureRect` 裁好**的 PNG：**比例（aspect）现在是对的、不用改；尺寸要大改**（见 §三）。
⇒ 卡面两说「取哪个矩形」的回答：**定框取 `m_Rect`，画心比例取 `textureRect` —— 两份都要**，
   单取任何一个都复刻不出原版。

## 二 `Orks Back.png` 的读数，与它能/不能证明什么

**读数**（`python -I` 读 PNG 头 + 逐像素 alpha）：
- 画布 **900×1200** ⇒ 比例 **0.750000**（= PnP 整卡比例）
- 画心（alpha>6）bbox = x84..800, y152..1127 = **717×976 ⇒ 比例 0.7346**（阈值 40 时 702×975 ⇒ 0.7200；边框是软边，阈值敏感）

**三档判定 → 落到「其它值」那一档**：既**不是** 0.6931（`m_Rect`），也**不是** 0.75（画布）。
⇒ **它证明不了 `m_Rect`**；但它也**不否定** —— 0.7346 正好落在数字卡背 `textureRect` 比例区间（**0.6186~0.7653**）之内，
与「打印的是可见画心」不矛盾。⚠️ **仅此而已，不足以定案。**

**另外 12 个阵营的 PnP 背**（同一个「卡背和部队卡PDF（用不着）」目录，13 份全量）：
画布各不同（662×879 / 667×888 / 636×880 / 647×902 / 666×943 / 657×938 / 586×896 / 633×905 / 623×870 / 586×878 / 661×956 / **1024×1024**），
画心比例 **0.6540 ~ 0.7608** —— **没有一张是 0.6931、也没有一张是 0.75**。
（对照：PnP **正面**卡也是 900×1200 画布，画心却 0.6220~0.7408 都有 ⇒ 这套打印件**内部就不自洽**。）

**「这张图对应哪张 sprite」→ 判不了**：我把 Orks Back 的画心与 233 张数字卡背逐张做归一化灰度相关（80×80），
最高只有 **0.32**（`Cardback_GOF_Red Gobbo`），且 0.32 远低于「同一张图」应有的 ~0.9 ⇒ **找不到对应关系**。
⇒ 结论：**这张 PnP 背接不上数字卡背**（另有一套画/另一套裁法），**不能当比例判据**。

## 四 裁定建议（取哪个矩形）

**规则（照原版，两段）**：
```
frame  = fit(m_Rect 707:1020, 节点框)        // 外壳 PA=1；战斗侧 PA=0 且节点本身已是 707:1020
drawnW = frame.w * (w_t / 707)
drawnH = frame.h * (h_t / 1020)              // 与上式恒等（因为 frame.w/707 == frame.h/1020）⇒ 等比
offset = ((padL-padR)/2, (padB-padT)/2) * (frame.w / 707)
```
对**已裁成 `textureRect` 的 PNG** 的可落地简化：
**保持现在用的比例不变（PNG 自己的比例就是画心比例 ✔），把画出来的尺寸整体乘 `w_t/707`，并按 `offset` 挪位。**

- 已经**不需要**再问「707×1020 还是 textureRect」——**定框用前者、画心比例用后者，两份都要**；
  但**只有 `m_Rect`（一个常数）不足以修**，也不是「改成 `m_Rect` 就对了」：
  单拿 0.6931 套到我们裁好的 PNG 上，`Shield of Humanity` 会变成 220×317.4（原版 220×305.3）⇒ **竖着多 4%**。
- **数据在哪（现成，不用重新解包）**：`m_Rect` 是常量、`textureRect` 每张一个数，都在
  `d:/2/新解包资源/assets_full/bundle_cosmeticscardbacksimages_assets_all/Sprite/<名>_Main.json`。
  本仓 `MyGame/Assets/CardPresentation/Resources/Cardbacks.json` **现在只有 `items`（name/so/armyId/army/rarity/uniqueId）与 `defaults`**
  ⇒ **没有** `texW/texH/padL/padB`。两条路：(甲) 给这张表加 4 列（生成器加 4 行读 `textureRect` 的代码）；
  (乙) 改导入器**别裁**、连 `m_Rect` 一起带进来（PNG 保留画布位置）。
- **改动面**（我没动，只列）：`DraggableController.cs:320`（共用件）/`MenuDraw.cs:1502`（共用件）/
  `DeckRuntime.cs:2126,2205,2387` / `CollectionWindow.cs:1170` / 战斗侧 `BattleDriver.cs:11174,11867,13026`；
  🔴 **自检腿**：`Editor/CollectionScene.cs:359 InsetFit` 是**手抄的同一套（贴图比例）口径**，
  它现在**在替一个偏离原版的口径作证**（改口径要连它一起改；这也正是铁律 13·5「审查盯原版判据、不盯我们自己的常量」那一类）。

**顺带一条要推翻的旧结论（有实据）**
`Battle/BattleDriver.cs:11859-11866` 的 A20 注释写：「原版那两个 rect 与两张贴图的宽高比都不一样
（`_Main` 707×996、`_SDF` 100×130.5）⇒ 按贴图比例画，两者的比值会跟着『这次用哪张卡背』浮动」。
—— **前提错了**：那两个 **节点 rect 的比例 == 两张 sprite 的 `m_Rect` 比例**（0.693120 vs 0.693137 · 0.766277 vs 0.766284）
⇒ **原版一处都没拉伸**，画心只是**按 padding 内缩**。所以牌堆现在的 `SetAspect(CardbackRectAspect)`（拿 PNG 铺满节点）
**是一次拉伸**（最坏 +16.1% 宽 / +10.0% 高）。
⚠️ 这与 `CLAUDE.md` 里「战斗侧是另一个模型」**不冲突** —— PA=0 仍是另一个模型，
只是「节点比例 == `m_Rect` 比例」这条事实把 A20 当年的困惑解释掉了。
