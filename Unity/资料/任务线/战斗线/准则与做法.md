## 三、干一件活的流程（**六步**）

```
① 读「本任务文件」→ 它里面有判据与出处
② 判据不够 ⇒ 先补判据（派只读子代理去勘），⛔ 别凭印象动手
③ 动手改（.cs）→ 立刻跑 `bash d:/4/Unity/工具/typecheck.sh`（**秒级，唯一挡「编不过」的**）
④ 落盘：把「查出的事实 / 坑 / 判据」写进该去的地方（见 §五）
⑤ 收工：按 `任务线/README.md` §五 那四步改总表
⑥ ⛔ 不跑自检、不起 player（见 §四）
```

**五条本线的硬规矩**：
1. 🔴 **判据只留一处**：同一条规则**不许写两遍**（本线的判据常常分散在 `BattleDriver` / `CardInteraction` / `BoardLayout` 三处——**先 `grep` 谁在用**再改）。
2. 🔴 **改完 `.cs` 必须跑类型检查**（它是「攒批不跑自检」这条规矩下**唯一不能省**的一步）。
3. 🔴 **一个值 ≠ 全部情况**（本线**连撞三次**：`NameTextUnit` 字号 16/19 · `_ShadowColor` 三个值 · 棋盘槽位序列化是死值）⇒ 读到「原版值」先问：**这是哪种情况下的值？一共几种？谁在运行时改它？**
4. 🔴 **父链 `m_LocalScale` 必须逐跳乘**（本线查出**两处漏乘**：多卡窗卡片漏 0.7 ⇒ 高 43%；`BattleDoors` 漏 1.06647 ⇒ 小 6.65%）。⚠️ **唯一的例外 = 根 Canvas 那一跳**（`BattleHud/Canvas` 的 RT 序列化是 `(0,0,0)`，**由 Canvas 接管，⛔ 不能乘**）。
5. 🔴 **回合计时 / 胜负门**：**胜负判定发生在「每条动作解析完」那一刻**，不是回合末；**骷髅分 = 敌方督军生命跨过 {20,10,0} 的档数**（`BattleScoreUiManager` 只画数、不算分）。

## 四、验收口径（**现行：只做不验**）

🔴 **用户 2026-10-15 第八次收口**：「**之后暂时别检查，先完全复刻，复刻好了再检查**」。
⛔ **不跑 `*.Run` 自检**（一条都不跑）· ⛔ **连「起 player 截图看界面」也停**。
✅ **只留两件**：**秒级类型检查**（几秒，不算检查）· **「原版 vs 我们」的缺口普查**（那是复刻的**输入**，不是验收）。
🔑 **判别句**：**这件事是在「找出还没复刻的」，还是在「验证我刚改的对不对」？** 前者做，后者停。
🕐 **什么时候才验**：**复刻完成之后**统一验收（进游戏 → 截图 → 点）。

## 五、形成文件说明（**任务文件怎么写**）

### 5·1 一件活一个文件，文件名 `T<两位序号>_<短名>.md`
**必须有的六节**（⛔ 别写成散文）：
```markdown
# T03 · <一句话说清这件活>
> 状态 / 起于哪一版 / 关联 A 编号

## 一、要做什么（**能一句话说清「做完之后画面/手感有什么不同」**）
## 二、判据（**逐条带出处**：资产路径 / `文件:行号` / 类名+方法名）
## 三、我们现状（现状**逐处**给 `文件:行号`）
## 四、怎么改（**改哪个文件、改什么**；分几步；先做哪步）
## 五、做完了怎么自检（**照当时的验收口径**：现在是「只跑类型检查」，将来是「进游戏点」）
## 六、还差什么 / 判不准的（⛔ **不许猜**，写「没查到 + 我搜过哪些词/哪些包」）
```

### 5·2 什么写进**任务文件**、什么**不**写
| 写进任务文件 | ⛔ 不写 |
|---|---|
| 判据（带出处） | `CLAUDE.md` 已有的铁律（**抄一遍就会过期**） |
| 我们现状 + 行号 | 别的任务已写过的东西（**给指针**） |
| 改动清单 | 大段反编译原文（**给 `文件:行号`**） |
| 「还差什么」 | 已经做完的过程叙述 |

### 5·3 详情**超过 ~150 行**就再拆
判据原文太长 ⇒ 搬进 `资料/待办判据_*.md`（**编号同一套**），任务文件只留「一句话 + 指针」。

### 5·4 收工后的归档
按 `任务线/README.md` §五。**已完成的详情文件搬进 `资料/历史/已收口_战斗线_<日期>.md`**（原文一字不改）。

## 六、本线已知的坑（**继续加，⛔ 别删**）

1. 🔴 **`2D层_battlearena1全树.md` 是截断版**（缺 373 个 GO、缺口正好在 HUD），而**标题写着「全树」** ⇒ 它已经**实际致错两次**（判「原版没有提示条」· 判「`Match Skulls` 丢行」）。
2. 🔴 **`BattleHud/Canvas` 的 RT 序列化 `m_LocalScale = (0,0,0)`** —— 逐跳乘到这一跳会把整棵 HUD 乘成 0 ⇒ **这一跳必须显式跳过**。
3. 🔴 **`BattleHud` 根（RT 1471）是 `Transform` 不是 `RectTransform`** —— 「给 BattleHud 设 rect」这类操作会踩空。
4. ⚠️ **旧文档引的 `BattleDriver.cs` 行号整体偏移**（15.5k 区偏 ~18 行、`Update` 那族偏 ~4 行）⇒ **引行号前一律现核**。
5. ⚠️ **`资料/说明书/01_战斗_对战/2D层_*全树.md` 这一族只能当分区骨架**：不收 `Canvas/Camera/粒子/Animator/材质`、**节点顺序 ≠ 绘制层级**、3D 节点**没有坐标**、只打印 `script` 计数**分不出类名**。
6. ⚠️ **批处理下没有帧循环** ⇒ 新加的任何「随时间推进」的东西（计时 / 补间 / 淡入淡出）**必须挂在 `BattleDriver.AdvanceTimeline` 上**，⛔ 别挂在 `Update` 里 —— 挂错 = **只在一种环境下活的实现**（自检永远推不动）。
7. ⚠️ **TMP 在对象没激活时量不出尺寸** ⇒ 任何「读回来比对」的断言，要么趁激活时读、要么缓存（先例：提示条的 `_tipW`）。
8. 🔴🆕 **量「战斗场景里某节点的矩形」别用 `menu_dump.py` / `menu_rect.py` 的常规模式**（2026-10-16 实测）——
   那两个工具**从根往下走**，而战斗场景的根 `BattleHud` 是**纯 `Transform`**（RT 1471）⇒ 它们会在那一级
   **断链**、整表退化成「整屏当父 + 缩放 1」（两个工具都会印那行警告，但**表照样打出来**，很容易照着用）。
   ✅ **本线专用口 = `工具/_probe_node_rect.py`**（2026-10-16 新写）：
   `python -I -X utf8 工具/_probe_node_rect.py bundle_scenes_scenes_battlearena2 <节点名> <祖先名>`
   —— 沿 `m_Father` **逐跳**算到指定祖先，输出「相对该祖先中心」的 px（y 向上，与本工程 `U(px)` 同口径）。
   ⚠️ 它给的是**祖先内坐标**，不是屏幕绝对坐标（这正是我们要的那种）。
9. 🔴🆕 **同一个 bundle 里，同 pid 可以是不同对象**（2026-10-16 实测）——
   `scenes_scenes_battlearena1.bundle` 里 **`pid 32` 既是 `AudioClip 'Warpforge Ultramarines Combat High'`、
   又是 `GameObject 'Cardback Shadow SDF'`**（bundle 里有多个 CAB）。
   ⇒ 用 UnityPy 解 PPtr 时**必须带上 `m_FileID`**（→ 该 SerializedFile 的 `externals` 里的 CAB 名），
   拿「pid 相同」当判据会**静默拿错**（`工具/import_battle_bgm.py` 的 `resolve_ptr` 就是按这条写的）。
10. 🔴🆕 **一条「否掉某个方案」的注释，如果把【否掉的理由】记错了，会把真缺陷挡住很久**（2026-10-16 实测）。
   **实例**：`BoardLayout.PlaceMarkers` 那条 2026-10-01 的注释写着「换 `DropTargetWorld` ⇒ 实测**偏左 600 px** ⇒ 不能用」，
   于是那半年的正确改法一直被否掉；**真根因是【层】** —— 同一次改动里底片被挂到了 `ArenaLayer`
   （于是由**透视**相机画），后来那一处修好了，**功记到了「换算」头上**（旁证 = `BoardLayout.cs:218-222` 自己那句
   「试过挂 `ArenaLayer` ⇒ 被战场相机投到左边 600 px 外」）。
   **做法**：写下「某方案被否」时必须**连实测条件一起写**（哪台相机 / 哪一层 / 什么分辨率 / 什么场景），
   并在**那个条件变了之后回头复核这一条**；只写结论的否决句，下一个人（包括你自己）会**照它躲开正解**。
11. 🔴🆕 **断言两边同源 = 同义反复**（2026-10-16 第 3 个实例）。
   **实例**：`Editor/BattleScene.cs` 那条「整条挂在单位身上」比的是 `sel.AnchorWorld` 与 `selUnit.transform.position`，
   而**实现喂的正是后者** ⇒ 差恒为 0，**一直是绿的、什么都没测**（`A304`/`A337` 那一族同型：**靶对齐到错的那一半**）。
   **做法**：写断言先问「**这两个操作数是从哪来的**」—— 一个来自实现、另一个也得来自实现 ⇒ **重写**：
   期望值取**判据侧**（原版值 / 另一个已独立验证的口），并配一条**灭自证**（证明两个候选值真的分得开）。
12. 🔴🆕 **Unity 的层【不继承】—— `Instantiate(prefab, parent)` 保的是 prefab 自己的层**（2026-10-16 踩）。
   **后果**：把特效挂到卡上以为「它会跟着卡进第 8 层、由透视相机画」，实际它还停在层 0
   ⇒ 被 HUD 正交相机画 ⇒ **位置与尺度的量纲全错**（而画面「有东西在动」，不容易当成 bug）。
   **做法**：挂到别人身上时**显式走一遍整棵子树设层**（本仓现成口 = `WarpforgeEffectHook.SetLayerRec`；
   `CardView.SetLayerRec` 是私有的）。⚠️ 判据 = 原版那批「挂在卡/棋盘上的特效」由**透视相机**画 ——
   见 `CardScript__LandOnGround.c:87-106`（挂 `MinionManager` + `localScale = one × desiredScale`）。
13. 🔴🆕 **两处记录互相打架、而且都「看着有依据」—— 先别照任何一处动手**（2026-10-16 `T03` 只读代理查出）。
   **实例**：`CardFan.cs:151` 写「角上那 31 px **与转角无关**」，而 `A2093` 的判据说可点区
   **挂在【内层 `2DCard`】、跟着倾摆转**（`2DCard/UI Collider` 的 `NonDrawingGraphic`）—— **两说不能同时成立**。
   **做法**：这类矛盾**先记在这里**（⛔ 别按任一处改），等一次**真机/放大窗实量**再裁；
   裁之前谁都不知道哪个是「当时对、现在错」的那一半。同族先例 → 坑 10（把「否掉一个方案的理由」记错）。
   ⚠️ 与铁律 5 的关系：铁律 5 管「查出**与事实不符**的就地改掉」；本条管「**两处都还站得住**、
   但**互斥**」的那种 —— 证据不足时**留问题**比**改错一处**好。
