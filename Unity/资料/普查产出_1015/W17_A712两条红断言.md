## 三、为什么新量法**对位移免疫**（逐条）+ 改坏法

### 3·1 免疫的机理（两条都同）

- **被测量 = 「字形盒中心 − **节点**世界 y」**（`TmpInkCenterPx` 取的是**两点之差**）。
  A712 的位移加在 **TMP 子节点**的 `localPosition.y` 上（`Battle/Label.cs:936-937` 逐字实读：
  它只写 `_tmp.rectTransform.localPosition`，**节点自己一点没动**）⇒ 节点挪到哪、父链怎么排，
  这一条**只跟「字墨相对节点摆在哪」有关**。
- **期望值 = 原版那一格**（`+5/95 × FontPxNow`），四个数全是**原版资产字段**，没有一个来自我们的实现。
  ⇒ 「我们改位移算式」与「这条断言」**不共用任何一个口**（⛔ 不是同式自证）。
- **旧量法为什么不行**：`py1/py2` / `nty1/nty2` 走 `textBounds`（= **行盒**），而行盒**跟着位移一起挪**
  ⇒ 那是「**我们的新摆位**」；要让它绿就得把期望值改成 `原值 − 0.1291 × fontPx`（= 自证）。

### 3·2 容差 1.5px 的来路（**逐字算过**，⛔ 不是拍的）

我们摆位用的代理是**大写墨盒**（原版那一档只看字体度量、与串里有没有下伸部无关 → `W11` §2·4），
而本条量的是**这一串真渲出来的字形盒** ⇒ 两者有差，差多少**逐串算得出来**：

| 串 | 字形盒中心相对行盒心 | 代理（大写盒）| 偏差 | 换算到生产档 | 没做位移那一态 | 与期望的距离 |
|---|---|---|---|---|---|---|
| `4500`（排行榜 `Points`，注入数据） | −0.06750 em | −0.07250 em | **+0.00500 em** | **+0.22px @F=43.2** | −0.0725×F + 0.22 ≈ **−2.9px** | **5.2px** > 1.5 ✅ |
| `Next Tier:`（奖杯窗） | −0.04700 em | −0.07250 em | **+0.02550 em** | **+0.89px @F=35** | −0.0725×F + 0.89 ≈ **−1.65px** | **3.5px** > 1.5 ✅ |

⚠️ **`Next Tier:` 那 0.89px 是 `i` 的点（+0.785 em）与 `t`（+0.665）比 cap（+0.729）高一点**造成的 ——
这正是 `W11` §2·4 说「别拿逐串字形盒当基准」的那个自由度；本笔**没有**把它算进期望值（那是我们字体的私货），
而是**把它算进容差**（容差是「量法分辨率」的一部分，可以公开写出来）。
⚠️ **容差的下界也守住了**：`Points` 那一格容差若 > 2.0px，就分辨不出「档位错成 `Capline`（0px 目标）」
（差 2.05px）；1.5px 还抓得住。

### 3·3 本条**分辨不出**什么（如实记）

- **`Next Tier` 分辨不出「档位记错」**：`Middle` 那一格只有 **1.84px**，而同串字形差 **0.89px** 同量级
  ⇒ 档位错成 0px 目标时只差 **0.95px < 1.5**（绿）。那一族由 `Editor/BattleScene.cs` §4.6d
  的专门探针（逐档目标 + 档序 + 幂等）覆盖，**本件不重复造**。
- **两串都分辨不出「位移只做了一半」**（差 ~0.9px 量级）—— 同上，判据不在这里。

## 四、那两个偏差数怎么复算（给审查用）

依赖（**一次性、装在临时目录，没动系统环境**）：
`python -m pip install --target <某临时目录> fonttools`（PyPI `fonttools` 4.66.1）。
脚本（跑一次 ≈ 10 秒）：

```python
import sys; sys.path.insert(0, r"<上面那个临时目录>")
from fontTools.ttLib import TTFont
from fontTools.pens.boundsPen import BoundsPen
f = TTFont(r"d:/4/Unity/MyGame/Assets/CardPresentation/Fonts/NotoSerifCJK-Regular.ttf", lazy=True)
upem, cmap, gs = f['head'].unitsPerEm, f.getBestCmap(), f.getGlyphSet()
ASC, DESC, CAP, PS = 57.55, -14.30, 36.0, 50.0          # 我们字体资产的 faceInfo（`Resources/Fonts/NotoSerifCJK-Regular SDF.asset`）
def ink(s):
    ys = []
    for ch in s:
        if ch == ' ': continue
        bp = BoundsPen(gs); gs[cmap[ord(ch)]].draw(bp)
        if bp.bounds: ys.append(bp.bounds)
    lo = min(b[1] for b in ys); hi = max(b[3] for b in ys)
    return (lo + hi) / 2.0 / upem                        # 字形盒中心相对**基线**（em）
for s in ("PLAY", "Counter", "Points", "4500", "Next Tier:"):
    rel = ink(s) - (ASC + DESC) / 2.0 / PS               # 相对**行盒心**（em）
    print(f"{s:12s} 字形盒心−行盒心 = {rel:+.5f} em   偏差(相对代理 −0.0725) = {rel + 0.0725:+.5f} em")
```

**校准**（这一步是本笔敢用这些数的理由）：`PLAY` → **−0.06450** · `Counter` → **−0.06750** ·
`Points` → **−0.04700** —— 与 `d:/4/_tmp_view/valign_probe.txt:11-50` 逐**位**吻合（探针打的是
`-0.6969·fs / -0.7290·fs / -0.5079·fs`，除 10.8 换成 em 后正是这三个数）⇒ 算法（= 字形盒中心，
SDF 留白上下对称不影响）**校准过**，不是估的。
⚠️ **一处口径订正（顺手发现①）**：`W11` §2·4 与 `BattleScene.cs:3195` 把 `Points` 的偏差记成 **0.95px** ——
那是**字面串 `Points`**（`Round1015Probe.cs:128` 的探针串）的数；**生产里那一格渲染的是 `Points` 字段
（注入数据 `"4500"`，数字）**，偏差只有 **+0.005 em = 0.22px @43.2**。两个串别混。
