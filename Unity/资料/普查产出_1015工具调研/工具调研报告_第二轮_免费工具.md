## 〇、一句话结论（给主对话转发用）

**用户那句「git 上面应该有大量可以使用的免费导出工具」是对的 —— 这一轮挖到了正主：
`FractalTools/Ruri.RipperHook`（AGPL-3.0 · 2026-10-03 仍在提交 · 33★）把 AssetRipper 免费版缺的那几件
（shader 反编译 · Prefab Outlining · Static Mesh Separation · IL2CPP 方法反编译）**用 AOP Hook 免费实现了**，
而且**有 headless CLI**（`--load <path> --export <dir>`），出口就是 Unity 工程（`.unity` / `.prefab` / `.mat` / `.shader`）。
上一轮那句「免费版 shader = 通用 Lambert 占位」**只对 AssetRipper 本体成立**，加上这个 Hook 层就不成立了。**
代价：要 **.NET 10 SDK**（本机现读只有 `8.0.425`）、AGPL-3.0、以及「能不能吃我们这 4.4 GB 解包树」**尚未实测**。

## 一、`MeikoMei16/AssetRipper-CLI` 专项

### 1. 它是什么 —— **不是 fork，是一个「用 vendor 方式内嵌了上游源码」的 CLI 包装**

- `fork = false` · `parent = None`（GitHub REST `repos/MeikoMei16/AssetRipper-CLI`）⇒ **不是 fork**。
- README 原文（`raw.githubusercontent.com/.../main/README.md`）：
  「从 Unity 游戏中提取素材的命令行工具 —— CG、音频、背景、立绘，一条命令搞定。」「基于 [AssetRipper](…) 构建，专注于 CLI 导出工作流。」
  仓库结构一节原文：`vendor/　上游 AssetRipper 库（vendor 方式引入）`。
- 实测树（`git/trees/main?recursive=1`，996 条）：`src/AssetRipper.Tools.ExportRunner`（23 个文件，这就是那个 CLI）＋
  `vendor/assetripper/Source/`（**834 个文件**，上游源码整棵抄进来）。
- 🔴 **内嵌的是哪个版本**：`vendor/assetripper/Source/Directory.Build.props` 的 `<VersionPrefix>1.3.13</VersionPrefix>`；
  上游 master 同一文件是 `2.0.0` ⇒ **它内嵌的是 1.3.13（≈2026-04-07），比上游 2.0.0（2026-08-24 发布）老**。
  1.3.13 夹在 release `1.3.12`（2026-03-19）与 `1.3.14`（2026-04-25）之间。

### 2. 比 GUI 多什么 —— **只多「能进流水线」，不多一个导出能力**

读了 `CliExportExecutor.cs`（489 行）· `ExportProfileResolver.cs` · `CliPrimaryExporterFactory.cs` · 三份 `docs/articles/*.md`：

| 它多出来的 | 实据 |
|---|---|
| **四个真 CLI 工作流** `inspect` / `analyze` / `export` / `report`，有退出码、无浏览器、无端口 | `CliImplementationStatus.md` §Current Workflow Model |
| **10 个 profile**（`cg` `audio` `characters` `backgrounds` `sprites` `ui` `player-art` `narrative` `full-raw` `full-project`）—— ⚠️ **全是「视觉小说素材分类」的启发式**，不是「Unity 工程重建」 | 同上 §Profiles + `ExportProfileResolver.cs`（原文 `profile matching is heuristic`） |
| **清单产物**：`export-plan.json` / `export-manifest.json` / `skipped-assets.json` / `failed-assets.json` / `summary.txt` | README §导出产物 |
| **环境变量控并发**（`ASSETRIPPER_LOAD_WORKERS` / `..._EXPORT_WORKERS` / `..._UNPACK_WORKERS`）· 分片 + `.done` 标记断点续跑 · 递归解包嵌套 bundle | `CliImplementationStatus.md` §Execution Model |
| **`--mode dump` = 真的出 Unity 工程**（⚠️ 这是唯一一条实质能力） | 见下 |

🔴 **`--mode dump` / `--profile full-project` 走的是 `handler.Export(gameData, outputPath, fileSystem)`**
（`CliExportExecutor.cs:166-167`）→ `vendor/.../ExportHandler.cs:95-101` 里是
`ProjectExporter projectExporter = new(Settings, …); … projectExporter.Export(gameData.GameBundle, …)`
⇒ **headless 直出 Unity 工程（`.unity`/`.prefab`/`.mat`/mesh）**，`full-raw`/`cg`/… 走的才是
`PrimaryContentExporter`（`CliExportExecutor.cs:152`，一资产一文件的原生格式）。

### 4. 能不能绕开我们那两条硬限制 —— **一条都绕不开**

| 我们的硬限制 | 它行不行 | 判据 |
|---|---|---|
| **bundle 里的 Shader 落不了工程资产**（`m_Script` = null） | ❌ | 内嵌副本的 `Shaders/` 目录 = `DummyShaderTextExporter.cs`·`SimpleShaderExporter.cs`·`ShaderExporterBase.cs`·`ShaderExportCollection.cs`·`TemplateShader.cs`·`Templates/{Default,SingleColor,SingleTexture,TransparentDiffuse}.txt`·`YamlShaderExporter.cs`·（多 4 个辅助档 `PropertyType/RequiredProperty/TemplateJson/TemplateList`）—— **与上游 2.0.0 的开源仓逐名相同、没有反编译器**。`ShaderExportMode.cs` 里有 `Decompile` 枚举项（注释 `Export as decompiled HLSL`），**但实现不在仓里**（与上一轮结论一致） |
| **MonoBehaviour 字段读不出来**（脚本不在 bundle 里） | ❌ | 这是原版构建方式决定的，与提取器无关（上一轮 §三.9，AssetRipper CommonIssues 原文） |
| 附：**Prefab Outlining / Static Mesh Separation** | ❌ | 上游 `ExportHandler.cs:118` 那句 `protected virtual void BeforeExport(ProjectExporter)` 注释原文 `// Needed for the premium edition` —— **免费路径这里什么都不做** |

### 5. 结论：**有条件有用，但不建议采用**（判据三条）

1. **能力上是 `Ruri.RipperHook.CLI` 的真子集**：同样是 headless + 同样出 Unity 工程，
   而 Ruri 那边**多出 shader 反编译 / Prefab Outlining / Static Mesh Separation**（见 §二），
   且 Ruri **以内嵌 submodule 的方式跟着上游走**（`.gitmodules` 指 `AssetRipper/AssetRipper`，pin 的 commit 未读），
   AssetRipper-CLI 则是把 1.3.13 **抄死在仓里**、半年不动。
2. **它的差异化卖点（10 个 profile）不是我们的用例**：目标写着 `CG、音频、背景、立绘`，
   `docs/articles/CliImplementationStatus.md` §Current Risks 自陈 `profile quality is still heuristic`；
   我们要的是场景/粒子/材质，一个都不在里面。
3. **它的目标框架要 .NET 10**：README 原文 `[.NET SDK 10]（版本 >= 10.0.200）`；
   **本机现读 `dotnet --list-sdks` = `8.0.425`** ⇒ 一样要先装 .NET 10，那就不如装给 Ruri 用。

> ⚠️ 与上一轮的关系：上一轮说「免费版不能反编译 shader」→ 对 **AssetRipper 本体**仍成立；
> 本轮的更正是「**有第三条路（Ruri Hook 层）**」，不是上一轮写错了。

## 三、逐类对照 —— 免费件里有没有比我们现在更好的

### 3.1 材质 / shader（**本轮唯一的实质突破**）

- **我们现在**：运行时从 bundle 取原件（`WarpforgeShaderLoader`），因为**免费 AssetRipper 只能给 Lambert 占位**。
- **新路（一）：Ruri 的 Hook 层**。读了源码，机制很硬：
  `AssetRipperHook/ShaderDecompiler/CommonHook/ProjectExporterHook.cs` 用 MonoMod **IL Hook 掉
  `ProjectExporter` 的构造函数**，判断式原文是「找到 `newobj DummyShaderTextExporter` 就把操作数换成
  `ShaderRuriDecompileExporter` 的 ctor」⇒ **它顶掉的正是上一轮认定的那条「免费版只剩占位」的路**。
  出口判定在 `Exporters/ShaderContentExtractor.cs:28-33`：`SimpleExporter.TryCreateCollection`（= `m_Script` 有源码）
  成功就走上游透传，**否则走 `ShaderRuriDecompileExporter`（从 `shader.CompressedBlob` 反编译）**。
  平台挑选 `PickBestPlatform` 顺序 = `D3D11 → Vulkan → …`，可用环境变量 `RURI_SHADER_PLATFORM` 钉死。
- **新路（二）：Ruri.ShaderDecompiler 独立 exe**。管线在 `Ruri.ShaderDecompiler.csproj` 的注释里写死：
  **DXBC/DXIL → SPIR-V（`AssetRipper.Bindings.DxilSpirV`，含 legacy SM5 译者）→ HLSL/GLSL（`Silk.NET.SPIRV.Cross`）**；
  符号名从**引擎侧 metadata** 注入（`Symbols/` + `Unity/UnityShaderMetadata.cs`），不靠猜。
- **新路（三）：HlslDecompiler**（MIT，**今天还在提交**）—— 只需一个 DXBC 文件就能出 HLSL，
  与我们已有的 `工具/dump_shader_blob.py` / `disasm_dxbc.py` **能直接接上**，零集成成本。
  ⚠️ 明确不支持 SM6/DXIL ⇒ **要先确认我们那 527 个 shader 的 blob 是 DXBC 还是 DXIL**（还没查，见 §六）。

### 3.2 场景

- **我们现在**：`gen_unity_arena_manifest.py` → `ArenaBuilder.cs` 逐场建场。
- **新路**：`Ruri.RipperHook.CLI --export-scene <map>` 的选项原文（`Cli/CliOptions.cs:177`）：
  `placements → best-LOD → CAB closure → Unity-project export, plus Assets/Scenes/<map>.unity placing every one of them
  (meshes referenced, prefabs instantiated) and a ruri_scene_placements.json manifest` —— **形态与我们的 arena manifest 同构**。
  ⛔ **但它自己写明 `Needs … a VFS-game --hook`**（VFS = 它那几个游戏的私有容器），Warpforge 不是 VFS 游戏
  ⇒ **这条对我们大概率不通**，只能当「别人怎么把 scene 变成 .unity」的参照实现。
- **通用的那条**：Ruri 的 `--hook PrefabOutlining` 叠加在普通 Unity 工程导出上，**能把平铺的内联 GameObject 还原成 prefab**
  （`AssetRipperHook/PrefabOutlining/Prefabs/PrefabProcessor.cs` 等 9 个文件）—— 这正是上一轮说「免费版没有」的那条。

### 3.3 粒子

- **没找到任何「专门为粒子做的 bundle→工程」工具**。本轮搜过的词见 §六。
- 好消息：`ParticleSystem` 是 Unity 原生类，**随 prefab 一起出去** —— 所以「PrefabOutlining 能不能把粒子的引用连同
  `SpriteRenderer`/`SpriteMask` 一起还原」比「有没有粒子工具」更关键（上一轮那条「78 个 prefab 被遮罩」的坑）。
- ⚠️ **这条是本报告最大的未知**：**没查到 Ruri 对 `ParticleSystem` 的还原度**，也没有实测。

### 3.4 光照

- **没找到**任何 Unity bundle 侧的光照/lightmap 专项目录或工具（搜 `unity lightmap extract` = **0 结果**）。
- 我们现在的做法（SceneJumpShot 探针读运行时 `RenderSettings` + `extraProbe`）**没有免费工具能替代**。

## 四、红队：看着有用、实际不行

1. **「`AssetRipper-CLI` 的 10 个 profile 能帮我们分类素材」** —— **不成立**。
   `ExportProfileResolver.cs` 原文 `applies coarse visual-art selection` / `coarse UI-oriented selection`，
   `CodeReviewFindings.md` 自陈 `cg` 会有误报、`audio` 会过宽；**且 10 个里没有「场景/粒子/材质」这一类**。
2. **「有 CLI = 能进流水线 = 能用」** —— **不成立**。它要 `.NET SDK 10 >= 10.0.200`（README 原文），本机只有 8.0.425；
   **"能不能装"是一件事，"装完能不能吃我们 4.4 GB / 24.7 万文件的树"是另一件，两件都没验**。
3. **「`USCSandbox` 能白救 shader」** —— **要打折**：README 全文 3 行，末行 `project is on hold for now`。
4. **「`dxbc_reader` 322★ 最多，所以最好」** —— ★ 高 ≠ 合适：它是 **Lua 脚本**（要 Lua 5.1+ 与 **LPeg**），
   且它的可读性来自**外部符号表**（例子里的 `CBUSE_UB_*` 名字不是从字节码推的）⇒ 对「没有符号表」的我们**不给名字**。
5. **「`DXBCSandbox` 直接吃 bundle，所以最省事」** —— **要打折**：4★、README 自陈
   `High-level shader and compute reconstruction is experimental`、`Targets supported Unity 2021.3 formats`
   （我们是 **6000.2.6f2**）、且 `VERIFICATION.md` 的编译验证**只在 macOS + 2021.3.35f1 上做过**。
6. **「Ruri 那套能不能直接用在我们身上」** —— **有一条明确的坎**：
   `Core/GameType.cs` 的枚举是**按游戏名**列的（`Arknights` `Endfield` `EXILIUM` `StarRail` `PunishingGrayRaven`
   `AzurPromilia` `ExAstris` `Koikatu` `KoikatsuSunshine` `HoneyCome` `SamabakeScramble` `UnrealEngine`），
   **没有 Warpforge，也没有通用 Unity 成员**；游戏专属解码器在**私有子模块** `Source/Ruri.GameHook`（**404 = 私有**）。
   ✅ 但 CLI 允许**直接点名 host 能力**（`--hook <id>`，`Program.cs` 原文 `or name one with --hook`），
   而 `ShaderDecompiler` / `PrefabOutlining` / `StaticMeshSeparation` 都是 `[RipperFeature(...)]`（**与游戏无关**）
   ⇒ **理论上可跑**，但 CLI 会打印 `Reading it without one yields a fraction of the assets.` —— **未实测**。
7. **「fork 里可能有更好的」** —— 本轮查了：AssetRipper 的 1002 个 fork 里**没有任何一个被搜索排序选出来**，
   唯一的「加功能 fork」是 `StArraySharp/AssetRipperPatcher`（6★，**README 取不到**）⇒ 不采信。
8. **「Preface 那条老路（UtinyRipper / AssetStudio）」** —— **过期**：`mafaca/UtinyRipper` 最后 push **2022-01-14**、
   `Perfare/AssetStudio` **archived / 2022-12-08**（本轮 atom 无输出，与上一轮一致）。

  是「DXBC → 可读 HLSL」里**最省事的一条**。判据 = 反出来的 HLSL 能不能编过 / 逐 pass 状态对不对得上。
- **B2**：`Ruri.RipperHook` 的 **PrefabOutlining + StaticMeshSeparation** 单独试 —— 这两件与 shader 无关，
  且我们 13 场里**只有 `battlearena2` 有静态合批**（上一轮结论，且我们已修）。
- **B3**：`DXBCSandbox`（C11，直接吃 bundle）—— ⚠️ 版本与验证范围都不对口，**排在最后**。

### C. 不建议
