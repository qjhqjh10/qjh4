## 一、用户三条主张的裁定

### ① 「每日骷髅头档位 = 3 / 10 / 25 / 50 / 100」 —— ✅ **对**（有实拍 + 反编译双判据）

- **实拍**（`奖励—布道所（每日任务）参考图.png` 左栏「每日骷髅头」卡）：`x0` 下面**五个方框逐格印着 `3` `10` `25` `50` `100`**。
- **反编译证「方框里的数 = 那条里程碑自己的 `targetValue`」**：
  · `MissionMilestoneStep__Setup(longlong* this, int value, int currentValue, …, byte collected, …)` 头两句 =
    `System_Int32__ToString(value)` → `TMP_Text.set_text`（vtable 槽 `0x558`）⇒ **方框文本 = 第 1 个 int 形参**。
  · 调用点 `MissionMilestonesDisplay__Setup.c` 传的是 `*(int *)(milestone + 0x14)`；
    `ChallengeMilestone` 的 `targetValue` 就在 **0x14**（`dump.cs:59736`）⇒ **方框 = 里程碑阈值**。
  （第 2 个 int 形参 `*(progress + 0x40)` 才是 `currentValue`，只用来算「亮没亮」。）
- 我们这边 **2026-10-11 已由 A370 改对**：`Shell/DailyData.cs:81` `_skullsSteps = { 3, 10, 25, 50, 100 }`（同一次改动删掉了旧的 `const int SkullsTarget = 200` + 五等分 `40/80/120/160/200`）。**本件不重复这活**。

### ② 「每个档位获得 200 活动点」 —— ⚠️ **半对：「200 活动点」对，「每档」证不出来**

- **「活动点」对** ✅：实拍那颗是**蓝色漩涡**，与同屏三条「每日布道所」任务（各 300）和顶栏 `300/2000` 是**同一种货币** = `CampaignPoints`（`CampaignPointDrawer : ItemDrawer<CampaignPoints>`，`dump.cs:92770`）。A370 已按 `40K_genearl_icon_Campaign_points_big` 改图。

- 🔴 **「每档」证不出来 —— 实拍上那格奖励是【当前里程碑】的，不是「每档」的**：
  `MissionRewardsDisplay__Setup.c` 取 `MissionChallengeProgress.CurrentMilestone()`，而
  `MissionChallengeProgress.<CurrentMilestone>b__15_0.c` 的谓词是 **`progress.currentValue < milestone.targetValue`**
  ⇒ **CurrentMilestone = 第一条「还没到的」里程碑**（全到齐才取最后一条）。
  实拍是 `x0` ⇒ 当前里程碑 = **第 1 档（3）** ⇒ **实拍只证明了「第 1 档 = 200 活动点」**，第 2~5 档各是多少**读不出来**。
- ⇒ **要证「每档都是 200」还差**：① 一张 `x≥25`（或 `x≥50`）的同卡实拍；② 或 PlayFab TitleData 的 `MissionsConfig`（§五）。

### ③ 「每日登录卡是每天服务器下发的任务」 —— ⚠️ **一半对**（详见 §四）

### 2·2 阈值本身：**硬编码在客户端、只有 3 档**

`MatchData__GetMilestones.c`：按 `matchData.playMode`（`MatchData @0x18`）分支 ——

- **构造 3 个 `HealthThresholdData`**（值 = **`0x14` = 20**、**`10`**、**`0`**）：`playMode ∈ {0 Classic, 3 Dungeon, 6 OfflinePractice, 7 ClosedDeck, 10 Replay, 11 RankedFriendly, 12 OwnDeckTraining, 13 Skirmish, 14 Battle4Warpforge}`
- **返回空数组**（= 这局没有骷髅里程碑）：`playMode ∈ {1 Duel, 2 PracticeLodge, 4 Tutorial, 5 CutScene, 8 Campaign, 9 TutorialReplay}`
- 别的值 ⇒ `throw NotImplementedException`

⇒ **一局产出 0~3 个骷髅**：把**敌方督军**生命削到 **≤20 / ≤10 / ≤0** 各得 1 个（首次即置位、不回退）。
**不是按场次、不是按胜负、不是按阵营、不是按击杀数。**

> ⚠️ **符号名存疑、但值可信**：Ghidra 把那个构造器标成 `<>f__AnonymousType7<Int32Enum>___ctor`（不是 `HealthThresholdData___ctor`）。
> 三条互证让「值 = 20/10/0 + 类型 = HealthThresholdData」站得住：
> ① `GetMilestones` 的返回类型是 **`HealthThresholdData[]`**（`dump.cs:78323`）；
> ② `BattleScoreIcon.Config(HealthThresholdData)` 把 `data + 0x10` 印到 `targetPointsText`（`BattleScoreIcon__Config.c`）——与构造器写入的字段同偏移；
> ③ 🔴 **本仓独立旁证**：`RuleEngine/Core/DeckRules.cs:89` 早就有 `SkullThresholds = { 20, 10, 0 }`，注释写明判据 =「规则书:36」+「运行时 dump 里 `skull1..3`」
> ⇒ **反编译 / 规则书 / 运行时 dump 三个独立来源同值**。

### 2·3 这个数怎么进「每日骷髅卡」

- `SkullsCount.OnBattleEnd(BattleEndSignal)` → `MissionChallenge.UpdateProgress(challenge, signal + 0x18 /* SkullsCount */, 0 /* shouldOverride */)`（`SkullsCount__OnBattleEnd.c`）。
  它前面那两段是**过滤**：`if (!anyGameMode) 检查 gameModes 里有没有本局 mode` · `if (!anyArmy) 检查 army == 0x68 字段`。
- `UpdateProgress(int value, bool shouldOverride)` 的实现在
  `MissionChallenge.__c__DisplayClass35_0___UpdateProgress_b__0.c`：
  `shouldOverride == false ⇒ currentValue = value + currentValue`（**累加**）；`true ⇒ currentValue = value`（覆盖）。
  ⇒ **每日骷髅卡是「这一天所有战斗的骷髅数之和」**，不是「最好那一局」。
- 重置：`SkullsCount.OnReset` 挂在 **`MissionResetSignal`**（`MissionResetSignal.missionId`，`dump.cs:60974`）上；`OnInitialize` 挂在 `BattleEndSignal` 上。
- 可行性算一眼：**每局最多 3 个** ⇒ 第 1 档（3）**一局就能到**；第 5 档（100）≥ 34 局。

## 八、顺手发现（⛔ 只报不改）

1. 🔴 **每周挑战：实拍是 6 格，我们建 4 格** —— 同一张实拍上「每周挑战」一行是 **6 个宝箱**、下面印 `5 10 15 20 25 30`、右上一个 `25/30` 计数；我们 `Shell/MissionsTab.cs:900` 是 `for (i < 4)`、`DailyData._weeklySteps` 只有 4 项、`WeeklyTarget = 15`。
   根因与骷髅卡同源：prefab「4 格」只是出厂占位，**格数由 `AvailableRewards()` 决定**。（A370 也报了这条，我独立复看实拍确认。）
2. ⚠️ **本次核出「格数是数据驱动」的第 3 处**：`MissionMilestonesDisplay__Setup.c` 逐条 `Instantiate` step 预制体（`Math.Min(i, stepPrefabs.Length - 1)` 取模板）⇒ **`steps` 容器里那 5 颗也是作者预览**，`资料/日常_原版规格.md:294` 那一行「steps（5 格）」应注明这一点（该文件 §3·3/§3·4 已有同类更正，此处是**里程碑格**那一侧、尚未加）。
3. 🔴 **`MissionDebugButtons` 是开发件、且会随 prefab 一起被销毁重建** —— prefab 上那排 `Reset / Re-Roll / +1 / +5 / Complete / 00:00` 不该出现在我们的复刻里（我们没建，✅ 对的）。但 `资料/日常_原版规格.md` §3·2 第 16 行把 `Mission Debug Buttons` 当正常子件列进表里，**容易被误读成要建**。
4. `BattleScoreUiManager.UpdateMilestonesCount` 的计数文案格式 = **`"x{0}"`，传的是 `index + 1`**，开局传 `0xffffffff` ⇒ `x0`（`BattleScoreUiManager__Initialize.c:13` + `…__UpdateMilestonesCount.c:13`）—— 与实拍骷髅卡的 `x0` 是**同一套写法**；「x0」不是「0 个」的巧合写法，是**设计好的 0 基/1 基差一**。
5. `Missions.__c__<InitializeHandler>b__8_1` 把某物的 key 与字符串 **`"Daily_Login_MainMenu"`** 比（字面量 `0x4262EA8`）—— 这看着像**每日登录那条事件的 eventId / handlerKey**。本件没查它指向谁（`LiveOpsHandler.HandlerKey`），**只报**。
6. 桌面上另外两张实拍（`奖励—活动的参考图.png` / `奖励—锻造厂的参考图.png`）**本件没读**，但按前两张的信息量，**值得单独派一件**逐张对账（铁律 7「拿不准就去看成品图」的同类）。
7. `资料/日常_原版规格.md:296` 记的 `count '200'` 在**独立 prefab** 上，而**页内实例**（`Missions Tab/…/Daily Skulls Mission Container`）那一格是 `count '1'` + `Icon Currency Drawer Variant`（**不是** Campaign Points variant）—— 两处**连奖励类型都不同**，再次说明它是作者预览。（规格里已按 §3·3 那条更正的精神处理，但**没有点出两处的 variant 名不同**。）
