## 二、逐条发现

### 🔴 R1 —— A310⑤ 的闪烁公式取错了三角函数：原版是 `Mathf.Cos`，不是 `Mathf.Sin`

**结论**：原版那一行是 `t = Clamp01(|cos(blinkSpeed × currentTime)|)`；我们实现成了 `sin`（`Shell/RewardWindow.cs:354`
`BlinkT { get { return Mathf.Clamp01(Mathf.Abs(Mathf.Sin(BlinkSpeed * _blinkT))); } }`）。
两者**同形、同幅、同周期**，但**相位差 90°** ⇒ 开窗第一刻原版 α = `Lerp(a, a×0.5, |cos 0| = 1)` = **0.5a**（最暗），
我们是 **1.0a**（最亮）；到 `t = π/2`（约 1.57s）反过来。`Tap To Continue` 上**没有别的组件写颜色**
（我查了同节点的 `EverguildTextController`：`EverguildTextController__Awake.c:29-41` 只写字号，不写 `m_Color`）⇒ 这 90° 看得见。

**证据（四条，逐条独立于报告的说法）**：

1. `d:/2/tools/decomp_full/BlinkGraphic__Update.c:17` 调用的就是 `FUN_180488130`（`uVar3 = FUN_180488130(blinkSpeed(0x28) × currentTime(0x30))`）。
2. **`FUN_180488130 = Mathf.Cos`，用它自己的同族 easing 定死**：
   `d:/2/tools/decomp_full/UnityEngine.UI.Extensions.EasingCore.Easing___Get_g__inOutSine_0_30.c:7-8`
   = `(DAT_1834b2bb8 − F130(t × DAT_1834b2e90)) × DAT_1834b2bb4`；
   三个字面量我用 `工具/read_literal.py` 复算：**`0x1834b2e90` = 3.14159（π）· `0x1834b2bb8` = 1 · `0x1834b2bb4` = 0.5**
   ⇒ 就是 `(1 − F130(πt))/2`。**任何 easing 库的 InOutSine 都必须 g(0)=0** ⇒ `F130(0)` 必须是 1 ⇒ **只能是 cos**
   （`sin(0)=0` 会得 0.5，那不是一条 easing 曲线）。它也是 R.Penner 的经典写法 `-(cos(πt)−1)/2`。
3. **同族三个兄弟互相印证**（都在 `decomp_full/`）：
   `…g__outSine_0_29.c` = `F6e0(t × 0x1834b2ec4)`（我复算 `0x1834b2ec4` = **1.5708 = π/2**）⇒ `F6e0 = Mathf.Sin`；
   `…g__inSine_0_28.c` = `F6e0((t−1) × π/2) + 1` ✓ 同一支；
   `…g__inBack_0_1.c` = `t³ − F6e0(t·π)·t` —— 这正是 **Siccity EasingCore** 的 `InBack(t) = t³ − t·sin(t·π)`
   （`outBack` = `1 − InBack(1−t)` ✓ 也对得上）⇒ **`F130 = cos`、`F6e0 = sin`**。
4. **一条不依赖任何库的纯几何复核**：`UIFlippableAndRotableUVs__RotatePointAroundPivotUVs.c:16-25`
   读 `fVar1 = F6e0(θ)`、`fVar2 = F130(θ)`，然后
   `x' = ox + (px−ox)·fVar2 − (py−oy)·fVar1`、`y' = oy + (py−oy)·fVar2 + (px−ox)·fVar1`
   —— 这是**标准逆时针二维旋转**（`fVar2 = cosθ`、`fVar1 = sinθ`）逐项对上 ⇒ 再次得 **`F130 = cos`**。

**报报告里那条「反证」是错的**：它写「同族 `UIGradientUtils__RotationDir.c` 用同一对助手返回 `(sin, cos)` 的方向向量，可反证」
（`Shell/RewardWindow.cs:288-289` 与报告 §二·④ 同一句）。实读 `decomp_full/UIGradientUtils__RotationDir.c:9-10`：
`uVar1 = F130(θ)`、`uVar2 = F6e0(θ)`，`return CONCAT44(uVar2, uVar1)` ⇒ Vector2 的 **x = uVar1 = cos、y = uVar2 = sin**
⇒ 返回的是 **`(cos θ, sin θ)`**，**恰恰是报告说它不是的那一种**。即使它真是 `(sin, cos)`，也证明不了哪一支是 sin。

**该照哪个判据**：`BlinkGraphic__Update.c` 逐句 + `FUN_180488130` 的身份（上面 4 条）。⛔ 不要拿 `UIGradientUtils.RotationDir` 的
返回序当判据（那句在 `资料/主菜单_原版规格.md:270-271` 与记忆 `warpforge-ui-preserve-aspect` §② 里也是这么写的 ——
**它把「有效渐变轴 = (sin θ, cos θ)」说成了「`RotationDir` 返回 (sin θ, cos θ)」**；那份文档的**实测表与 188° 的改法仍然成立**
（有效轴确实是 `(sinθ, cosθ)`，因为消费者用的是矩阵的**第二行**，见 `UIGradientUtils__LocalPositionMatrix.c`），**但它的解释错了**，
而这次 W1 正是踩在这句错解释上）。

**顺带**：这条错记录在两个地方还挂着（`资料/主菜单_原版规格.md:270-271`、记忆文件），修 blink 时**不要照抄那句**。

### 9③ 的错因（值得当通用教训记一笔）

它按**文件名**搜 `find … -name "*_<PathID>.json"`。这套导出树的命名规则是：
**名字唯一的对象只叫 `<名字>.json`（不带 PathID）**，重名的才叫 `<名字>_<PathID>.json`；
而 `ParticleSystem/` / `Transform/` / `MonoBehaviour/` 一律叫 `<类型>_<该组件的 PathID>.json`。
⇒ 「按 GameObject 的 PathID 找文件名」**永远找不到那条 GameObject**（它的 PathID 只出现在别的文件里当引用）。
正确做法：**拿这个 PathID 去 grep 文件内容**（`grep -rl <PathID>` 命中的就是引用它的那些组件），
再用组件反查 `m_GameObject` 的宿主 —— 我就是这么拿到 `RewardAppearParticle` 这个名字的。
