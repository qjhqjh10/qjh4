## 三、若是 (b)：错在哪一行

**(b) = 0 条**，`ApplyGroupNodes` / `ResolveGroupParent` / `FindBuilt` **无需改一行**。

但「喂进去的表」有一处**真错**，落在这里 —— **这就是 W11 那条判据自相矛盾的根因**：

```
d:/4/Unity/工具/gen_arena_groups.py:246-254
    def build(arena, want, anims, manifest):
        sc = Scene(arena)
        built = set()
        for e in (manifest.get('meshes') or []):
            if e.get('go'):
                built.add(norm(e['go']))
        for e in (manifest.get('particles') or []):
            if e.get('go'):
                built.add(norm(e['go']))
```

以及它下游那一行分类（`:314`）：

```
        if norm(leaf) in built and ps not in want:
            targets.append(...)          # ← 「已建 ⇒ 只改挂」
        else:
            nodes.append(...)            # ← 「没建 ⇒ 新建节点」
```

**为什么会漏**：`built` 取的是「**清单里存在这个名字**」，而 `ArenaBuilder.BuildContent` 真正建的时候还要过四道闸门（`:1997-2039`）。两个集合**在语义上不是一个东西**：

```
生成器的 built   ⊃   ArenaBuilder 真建出来的
   （多出来的那部分 = 被闸门挡掉的 = 这 58 条）
```

**最小改法**（一条判据，别写第二套口径）：把闸门**共用一份**。两条路选一：

- **(甲) 生成器里复刻闸门**（3 行）——在 `built.add(...)` 的那个循环里加判定：

  ```python
  # 与 ArenaBuilder.BuildContent:1997-2039 同口径（⛔ 别各写一份，见「两处写同一条规则 = 迟早不一致」）
  def _is_built(e, kind):
      if kind == 'particles':
          mesh_ok = (e.get('renderMode') == 4 and e.get('mesh'))
          if not e.get('texFile') and not mesh_ok: return False       # ①无贴图
          if not e.get('active'):                 return False       # ②!active
          if e.get('renderMode') == 5:            return False       # ④renderMode==5
      return True
  ```
  ⚠️ 闸门**有先后**：`①` 在最前，所以「既无贴图又关着」的（`Lance Fire (5)` / `Big Gun Effect`）记在①那一档 —— 这正是日志 `:4362` 那句「另跳过无贴图 2」的来源，顺序错了数就换了。

- **(乙) 反过来：把闸门结果**导出一张**旁挂**（`gen_arena_content_gates.py` → `<场>_gates.json`：每个 `go`+`pos` 是否建），生成器与建场**同读一张表**。这更符合本仓「旁挂 + `gen_arena_*.py`」那套，但多一个文件。

> 无论走哪条，**改完必须重跑 `gen_arena_groups.py` 再重跑 `ArenaBuilder.BuildArenaPrefabs`**（旁挂是前者的产物）。

## 六、顺手发现（⛔ 只报不改）

1. 🔴 **`A191` 那两条自检断言现在必红，且红的原因不是缺陷** —— `W11_子8b.md:213-214` 期望 `改挂 61/61` / `60/60`；实测 51 / 12。**主对话若正要跑 `BattleScene.Run`，别把这两条当新缺陷追。**
2. 🔴 **「没对上」这条日志的文案会误导人** —— `ArenaBuilder.cs:2587` 写的是「target `X`（旁挂 pos …）**在我们建出来的树里找不到**」。读起来像「查找逻辑可能有 bug」，实际三类原因（`!active` / 无贴图 / `renderMode==5`）**都在上游已经被单独出声过了**（`:4336` · `:7455` · `:4362` · `:7468`）。建议文案里带上「**很可能是上游闸门没建**（见同一场的『内容：…另跳过…』那行）」，省下一个会话的整轮诊断。
   同理 B 类文案（`:2643`）建议补一句「**父可能是被闸门挡掉的**」。
3. 🟡 **`FindBuilt` 会把「本表刚建的空节点」当候选** —— `root.GetComponentsInChildren<Transform>(true)`（`:2658`）**包含步骤①刚 `new GameObject` 出来的那些空节点**，而它们与真对象**可能同名**。本件**没触发**（实测：两场 `nodes[]` 的叶子名与 `targets[]` 的名字**零交集**），但下一个「宿主自己也是 target」的场会静默挂错。
4. 🟡 **tau 有 3 对「同名 + 同世界位置」的对象**（`Muzzle Glow 1 (5)` / `(6)` / `(7)`，各 2 条，位置逐位相同）—— `FindBuilt` 在它们之间只会挑到**先遍历到的那个**（`d < bd` 是严格小于 ⇒ 后到的等距候选不覆盖）。本件**没触发**（这 3 个名字**都不在 `targets[]` 里**），但这是「按名+最近位置匹配」这套口径的**固有盲区**，记一笔。
5. 🟡 **原版那 4 个炮口位的 `Muzzle Flash glow` 只有 `rMode=5` 这一种，而 `Railgun BIG (1)/Big Gun Effect` 下面那两个 `Muzzle Flash glow` 是 `rMode=0` 且**靠祖先 `Big Gun Effect` 关着** —— 同一个名字**两种成因**（铁律 5·c「一个值 ≠ 全部情况」）。清单**逐实例写对了**（6 条里 4 条 `rMode=5`、2 条 `rMode=0`，`active` 也逐条不同），这条**没问题**，只是提醒：**别把「`Muzzle Flash glow` 是 renderMode 5」当成一个可以硬编码的常量。**
6. 🟡 **我在 `d:/4/_tmp_view/d4_diag/` 下留了三个只读诊断脚本**（`sim.py` 复刻查找逻辑 · `detail.py` 抽清单明细 · `orig.py`/`orig3.py` 直读原版包核 `m_IsActive`/`m_RenderMode`）。派单说「只写报告」，这三个是**跑只读 python 的载体**，不是交付物 —— **要清就删整个 `d4_diag/` 目录**。命令见 §七。
