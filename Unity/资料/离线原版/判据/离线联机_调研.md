## 〇、一句话结论（先看这段）

1. **联机栈只有一个：Photon Realtime SDK 4.1.6.5（`Photon3Unity3D`）+ Photon Chat**，UDP 传输，
   AppID / ChatAppID 就写在本地 `resources.assets` 里，**读得到、运行时可改**。
   没有自研 socket / WebRTC / SignalR / 主机权威服务器。
2. **游戏层的联机代码是完整的、活的**：27 个 RPC、开局握手 5 条消息、逐动作锁步同步、actionCounter 补发、
   desync/投降/断线重连/重连回房——全部在这份 build 里。
   ⇒ **不需要重写 `BattleCommsManager`**（这一点与 `B151_原版离线版_可行性方案.md:449` 的假设相反）。
3. **唯一缺的是 Photon 服务端**。客户端侧最小改动 = **把连接目标改到自己的服务端**：
   要么 mod 里一个 prefix（改调 `PhotonNetwork.ConnectToMaster`），
   要么 **改 hosts + 自建服务器扮演 NameServer**（名字服务器会在 auth 响应里用参数 230 告诉客户端 master 地址，
   客户端随后自己连过去 —— 见 §6·2）。
4. **三个前置必须先解决**（否则两台机器一定连不上/连上也开不了局）：
   - 两台机器的 **PlayFabId 必须不同**（现在假服务端写死 `OFFLINE0000000001`）；
   - **好友/邀请链走 Photon Chat**（`ChallengeManager` 用私聊发邀请）—— Chat 是独立前端（`"chat"`），
     on-prem 是否附带 **没查清**，最坏情况这条链失效（两人对打可绕开，见 §6）；
   - **随机匹配（排位/活动房）用 `LobbyType.SqlLobby`**，SQL 大厅是否只有云端支持 **没查清**（§9）。
     两人对打可以绕开它：走「好友房 / `JoinOrCreateRoom`」这条（`DoJoinCasualGameRoom`）。

## 四、对局数据流：客户端权威（锁步），服务器只转发

### 4·1 权威模型

**不是主机权威，也不是服务器权威**：每个客户端**自己完整模拟**，**自己的动作自己做主**，然后广播给对手。

- 发出：`BattleManager.CommunicateBattleAction`（`BattleManager.cs:17811-17834`）
  ⇒ 本地先记账（`playerActionsLog`）⇒ `if (IsNetworkedGame()) commsManager.RemoteSendPlayerAction(playerAction);`
- 收到：`BattleCommsManager.PUNReceivePlayerAction(...)`（`:939`）⇒ `battleManager.ReceivePlayerAction(sentAction)`
  （`BattleManager.cs:17835-17865`）⇒ `CreateRemoteAction → AddAutoActionToQueue`（远程动作入队执行）。
- 服务器**只做广播**（`PhotonTargets.All`），**不做合法性校验**。

### 4·2 动作报文（7 个字段，全靠 RPC）

`BattleCommsManager.cs:341-539` → `photonView.RPC("PUNReceivePlayerAction", PhotonTargets.All, …)`：

```
(actionType, actingCardID, targetCardID, targeted, cardPlayedPos, actionCounter, attackTpye)
```

可靠性：`actionCounter` 连续递增；收到「超前」的动作 ⇒ `ResendLostActions()`（`BattleCommsManager.cs:541-593`、`:1212`）；
`SendDesync()`（`:601-605`）/ `PUNReceiveEnemyDesync`（`:1293`）⇒ 双方判 desync 并取消对局。
（`BattleManager.cs:17712-17717` 是发 desync 的那一段。）

### 4·3 随机数从哪来（**这是联机最关键的同步点**）

1. 每份 `MatchData` 开局**预烧 100 个整数**：`UnityEngine.Random.Range(0, 1000)`
   （构造里内联 `MatchData.cs:213-231`；同名私有方法 `:739-761`，两处逻辑相同）；
2. 结算路径 `GetRandomInt(min,max)` **按下标取**（`MatchData.cs:541-575`），**不再调用 RNG**；
3. 联机时 **先进房的人（firstPlayerInPvProom）把自己的 100 个整数广播**：
   `PUNReceiveAckStartGame` 里发 `PUNReceiveRandomNumbers(index, randomNumbers)`（`SearchOpponentManager.cs:1884-1906`）；
4. 收方 **直接用自己的数组被覆盖**：`matchData.randomNumbers = receivedRandomNumbers; randomNumbersIndex = index`
   （`SearchOpponentManager.cs:2032-2043`），再回 `PUNReceivedRandomNumbers`（`:2047-2094`）。

⇒ 两边拿到**同一份 100 个整数** ⇒ 之后所有 `GetRandomInt` 结果一致 ⇒ 同一局可复现。
⚠️ 注意这里**不是**「种子同步」：是**整段数组覆盖**。所以**两台机器上 `UnityEngine.Random` 的初始状态无所谓**，
但**必须让第 3 步真的发生**（否则各用各的数组，第一回合就分叉）。

## 六、自托管 Photon 可行性

### 6·1 客户端这边到底要改什么（先看清楚它怎么连）

```
MatchMakerManager.Initialize()            Everguild/MatchMakerManager.cs:238-249
  └ photonManager.StartConnection(playFabId, connectionSettings)     NetworkCustomManager.cs:249-315
      └ ConnectToPhoton()                                          NetworkCustomManager.cs:341-354
          └ PhotonNetwork.ConnectToRegion(serverVersion.photonServerRegion, appVersion)   PhotonNetwork.cs:1633
              └ NetworkingPeer.ConnectToRegionMaster(region)       NetworkingPeer.cs:1046
                  └ Connect("ns.exitgames.com:5058", "ns")         NetworkingPeer.cs:989-1130
                      └ [NameServer auth 响应] Address 参数(230) ⇒ 断开 NS，连 master
```

关键判据（Ghidra 补的，**这条把「hosts 重定向」方案坐实了**）：
`decomp_full/NetworkingPeer__OnOperationResponse.c:1044`（**Authenticate 分支**，`ServerConnection.NameServer == 2`）
读响应参数 **`0xe6`(=230 = Address)** → 写进 **`param_1[0x28]`**（偏移 **0x140 = `MasterServerAddress`**；
setter 证据 `NetworkingPeer__set_MasterServerAddress.c:5`）→ **`:1074` `NetworkingPeer__DisconnectToReconnect(0)`** 去连 master。
（顺带：`JoinRoom(226)`/`CreateRoom(227)` 的响应走同一机制，把 Address 写进 **0x148 = `GameServerAddress`**：
`NetworkingPeer__set_GameServerAddress.c:5`，`OnOperationResponse.c:739/806` → `LAB_1805baa84`。）

### 6·2 两条可行路线

#### 路线 A：**hosts 重定向 + 自己实现「NameServer + Master + Game」三角色**（客户端零 hook）

- 做法：`C:\Windows\System32\drivers\etc\hosts` 加 `127.0.0.1 ns.exitgames.com`；
  服务端在 **UDP 5058** 上扮演名字服务器：
  - 回 `InitResponse`（协议 1.8）；
  - 收 `Authenticate`(op 230) ⇒ 回 **`Address` 参数(230) = `127.0.0.1:5055`**；
  - 客户端自己断开、连到 5055 ⇒ 之后是 Master/Game 角色。
- 优点：**一个 mod hook 都不用写**（AppID/AppVersion 保持原值，服务端忽略即可）。
- 已确认：`Address`(230) **按字符串处理**（Authenticate 分支里紧接着对它做 `System_String__Replace`：
  `OnOperationResponse.c:1052-1063`），格式就是 `主机:端口`（和 `ServerSettings.ServerAddress + ":" + port` 同族，`PhotonNetwork.cs:1410-1425`）。
- 风险：hosts 是系统级改动（需管理员）；Photon **Chat 也连同一个主机**（`ns.exitgames.com:5058`），
  我们的 NS 要能区分 Chat 的 AppId，或者接受 Chat 连接失败。

#### 路线 B：**mod 里改连接点**（推荐，影响面最小、可控）

在 `NetworkCustomManager.ConnectToPhoton` 或 `PhotonNetwork.ConnectToRegion` 上打 prefix，
改调 **`PhotonNetwork.ConnectToMaster(ip, 5055, appId, appVersion)`**（`PhotonNetwork.cs:1446`，公开静态）。
这样**完全跳过名字服务器**，服务端只需实现 Master/Game 两个角色（少一组 NS 语义）。

推荐 **B**：① 不用改 hosts；② 不必实现「区域列表 / NS auth / Address 回跳」；③ 出错时好回退。

### 6·4 「现成的 Photon Server 能不能直接用」

- SDK 侧兼容性：客户端是 **Realtime 4.1.6.5**（协议 1.8）。官方 on-premises **Photon Server 4.x/5**
  面向 4.x 客户端，**理论上兼容**，但**本机没有任何 Photon Server 副本可验**（全盘搜过，见 §9），
  且 **Exit Games 已多年不更新 on-prem 产品线** ⇒ 拿授权/下载都可能有障碍。**必须实测，不能假设。**
- 就算拿到，仍有 **两个已知风险点**：
  1. **Chat**：客户端连的是另一个前端（`"chat"`），on-prem 是否提供 **没查清**（§9）；最坏情况 = 世界/联盟聊天与好友邀请链不可用；
  2. **SQL Lobby**：客户端随机匹配用 `LobbyType.SqlLobby` + `C1/C2/C3` 过滤（`NetworkCustomManager.cs:749-761`、`:877-950`），
     on-prem LoadBalancing 是否支持 SQL 大厅 **没查清**（§9）。
     绕法：**不走随机匹配**，直接用好友房（`JoinOrCreateRoom`，`LobbyType.Default`）。
- 认证：客户端设 `authType = CustomAuthenticationType.Custom` 且**不带 token**（`NetworkCustomManager.cs:308-312`）。
  on-prem 的 LoadBalancing 对自定义认证通常要插件；**最省事的做法是 mod 里把它改回 `None`**（§7 第 2 条）。

### 6·5 最小可行步骤（建议顺序）

1. **先把 PlayFabId 分开**：假服务端 `responses/fragments/playfab_profile.json:20` 现在写死
   `"PlayFabId": "OFFLINE0000000001"`。改成按 `config.json` / 环境变量 / 启动参数给不同 id（机器 A=`…0001`、B=`…0002`）。
2. **写服务端**（先用 Python 或 C# 都行），实现 §6·3 那张 op 表 + 房间/广播/属性；**先只做 2 人房**。
3. **mod 里加连接重定向**（§7 第 1 条）→ 目标 `127.0.0.1:5055`（跨机就填主机 IP）。
4. **mod 里关掉 Chat**（§7 第 4 条），避免它一直重连、刷日志。
5. **用固定房名直接开局**：绕过随机匹配与邀请链 —— 在 mod 里给一个「开发用入口」：
   两边都调 `MatchMakerManager.FindMatch(..., matchRoomName: "Practice_" + 对方id, playfabIdFirstPlayer: 我方id, ...)`
   或 `MatchMakerManager.StartMatch(PlayModes.Duel, …)` + 固定 `matchRoomNameDuel`。
   （`MatchMakerManager.cs:298-363` 的两个 `FindMatch` 都收 `matchRoomName` / `playfabIdFirstPlayer`。）
6. 跑通「进房 → 握手 5 条 → 双方卡组到齐 → 开局」后，再回头补随机匹配 / 重连 / Chat。

## 八、风险与备选

| 方案 | 成本 | 风险 | 需要什么 |
|---|---|---|---|
| **A. 真·自托管 Photon Server（on-prem）** | 低（若拿得到） | 🔴 on-prem 是否还可得/可授权 **未验**；Chat 是否随附未验；SQL Lobby 未知；自定义认证要插件 | 服务端二进制 + 授权；`PhotonServer.config` 里配 LoadBalancing 实例；客户端只改连接地址 |
| **B. 自己写协议兼容服务端（Python/C#）** | 中（op 表齐全、协议 1.8 有 `GpType` 表；**2 人房**只用到 6-8 个 op） | 🟡 1.8 的细节（压缩整数 / 字典编码 / 事件 200 的 RPC 载荷）必须逐字节对；建议先用客户端自己的 `Protocol18` 解析 | §6·3 的 op 实现 + 房间/广播 + 30s 空房；服务端只需 UDP 5055 |
| **C. mod 层拦截收发 + 自建中继**（不实现服务端协议，只在客户端之间转发） | 中高 | 🔴 仍需回答「客户端收到的必须是服务器事件」：要么自己造事件，要么真的解析 op —— 等于回到 B；且要替换 `IPhotonSocket`（**IL2CPP 下从 mod 继承游戏类型不可行**） | 只能在 `PeerBase`/`SocketUdp.Send`/`OnEvent` 这层做字节级注入，稳定性差 |
| **D. 只做 UI 不真连** | 极低 | 没有对局 | 无需网络 |
| **E. 复用 `d:/4` 的 P2P 联机**（B151 的旧建议） | 与本项目无关 | 那是「我们自己的复刻工程」，和原版客户端不是一套代码 | ❌ 不适用 |

**推荐**：**B + 客户端 #1/#2/#4 三个 hook**，先做 **2 人固定房**（跳过随机匹配 + 跳过 Chat + 跳过邀请 UI）。
**A 只在能拿到 on-prem 二进制时优先**（能省掉整个服务端工程量）。

**必须提前接受的三个「不完美」**（都属于「原版本身没给」或「远端已死」，不是我们偷懒）：
1. **好友邀请链要重接**：原版靠 Photon Chat 私聊发邀请（`ChallengeManager.cs:258-263`）。
   自托管后要么自己实现 Chat 服务，要么在 mod 里做一个「按 PlayFabId 直接进房」的测试入口。
2. **随机匹配（排位）大概率不可用**：SQL Lobby 依赖服务端能力（§9）。
3. **世界/联盟聊天可能不可用**：取决于 on-prem 是否提供 Chat 服务（没查清，见 §9）。

## 顺手发现（与本任务无关但重要）

- **`assets_full` 的解包缺口**：`02_解包资源/assets_full/resources/MonoBehaviour/` **是空目录**
  （`resources.assets` 里的 MonoBehaviour 一个都没导出）。本次要找的 `PhotonServerSettings` 就属于这一类。
  ⇒ 以后凡「`resources.assets` 里的资产」都不能靠 `assets_full` 判有无；要么读真包字节，要么看 `assetripper_out`。
- **真包里 `ServerSettings` 的 AppID 是等长的 GUID**（36 字符）。
  ⇒ 如果只想换 AppId（不引 mod），**理论上可以按等长字节原位改写 `resources.assets`**（不动长度、不破序列化）。
  ⚠️ 仅当「换 AppId 就够」时才有用；改 `ServerAddress` 不行（原值为空串，长度会变）。
- **`PhotonServerSettings.RpcList` 只有 27 条，但 `PhotonView` 的 view ID 是固定常量**
  （`BattleManager.photonView.viewID = 1`、`SearchOpponentManager.photonView.viewID = 5`）。
  ⇒ 两个客户端必须**加载同一个战场场景**，否则 view 路由会错（这也解释了 §3·5 为什么必须两边算出同一战场）。
- **`CustomDebug.Log` 默认级别是 `Error`**（`CustomDebug.cs:6-24`，`defaultLogLevel = LogLevel.Error` 在 `:14`）——
  这就是为什么 `Player.log` / `unity.log` 里看不到任何 Photon 的「Connecting to Photon using Region」这类关键行。
  调试联机时要么 hook `CustomDebug.Log` 旁边的判断，要么直接自己打日志。
- **好友挑战的房间名有两套写法**：`MatchMakerManager.StartMatch` 用 `"Practice" + playFabId`（无下划线），
  而 `BattleNetworkManager.GetPracticeRoomName` 用 `"Practice_" + id`（有下划线）。
  ⚠️ 做「两个人直连」时**别混用**，否则一个建房一个找房，永远碰不上。
- **`PlayModes.Duel` 与 `MatchType.Duel(150)` 走的是「固定房名 + JoinOrCreateRoom」**，
  是全套联机里**最不依赖服务端能力**的一条（不需要 SqlLobby、不需要随机匹配）。
  做最小可用联机，建议直接拿它当第一条通路。
