## 四、没查清的部分（如实留白，⛔ 没拿猜测顶替）

1. **A183 · 那颗 `m_AnchoredPosition (0, −0.02)` 在本窗折算成几 px（本条明确没做）**。
   原版那个 `−0.02` 是**卡单位**，折算成 px 要先定本窗卡的**运行期渲染尺度** —— 而它是
   `Card2DController.cardScales` / `bigSizeMultiplier` **运行期**喂的（prefab 里只有 `2.09×3.33` 的设计值）。
   **静态读不出**（同 `普查产出_1009/查证V1_原版prefab四件.md` §五·1）。
   ⇒ 我们**仍按卡心居中**，所以上面四条边是**关于卡心对称**的；战斗侧那 5px **没有照抄**（本窗卡体比战斗侧小得多）。
   ⚠️ 一个旁证（**不是判据**，只是量级参考）：若按本工程自己那个 `CardK = 132.3153` 折算，0.02 卡单位 = **2.646px**。
2. **A275 · `CrateCounter` 那一格的判别力弱（如实标）**：那句长文案被 `SetAutoFitBox(485.284, 45, 3, 35)`
   缩到**几乎正好填满**框 ⇒ 两种对齐的差 ≈ `(485.284 − 块宽)/2 ≈ 0` ⇒ 它那一格**只能断「块心 = 框心」**，
   **分不出两种状态**。真正分得出的是 `counter`（块 ~90px / 框 243.945px，差 ~76px）—— 已由第 3~5 条钉住。
   `CrateCounter` 块宽的具体值**本轮也没量到**（要跑 Unity 才读得到 `WorldW`）。
3. **A183 · 容差覆盖缺口（如实说）**：比率容差 0.0005、边容差 0.5px ⇒ **`0.86792` 误抄成 `0.8679`
   （差 0.0091px）罩不住**。与 A156 那条已记账的缺口同性质（`待办判据_1008.md` 的 A156 行）。
   x 那一路（本次真缺陷）差 **10.1px**，远超容差，抓得住。
4. **`CardInBoosterPack` 那 5 张卡在动画期间的命中区**：原版 `UI Collider` 是 `CardUI` 的**兄弟子树**、
   会被 `Booster Window Open` 那条 clip 的 `localScale`（157.58 → 151）**带着缩放**；我们只按**末帧 151** 摆。
   中间帧的命中区**没查**（本轮没做，属于另一件事）。
5. **同族普查没做**：V2 §三 建议的「`MenuDraw.AlignLeft` 全工程调用点里有多少落在原版 `H=2` 的节点上」**没查**。

## 五、顺手发现（⛔ 只报不改）

1. 🔴 **`ShopScene.cs` 里有一段别人正在改的代码**：`git diff` 的第一处 hunk（`:733-743`）是
   **2026-10-09（A221④）**「`MenuDraw.AbsorbTierWarns` 全局计数器 → `MenuDraw.AbsorbTierWarned` 按窗记账」——
   **不是我改的、我一个字节没碰**（本块动工前 `ShopScene.cs` 就已经是 `M`）。⚠️ 因为共用同一个文件，
   **这一处的账要记在它自己的写手名下**。
2. **同一扇窗里两种「对齐」机制并存**，抄判据时别混：`MenuDraw.AlignLeft/Right` 挪的是**整块**（等效 TMP 的
   `m_HorizontalAlignment`），而 `Label.SetAlignLeft()` 改的是 **TMP 每行的行内对齐**（多行才看得出）。
   本窗两处**都不需要**（原版 Center = 两者都居中）。出处 → `Battle/Label.cs:210-225` + `:608-627`。
3. `Assets/.../Editor/ShopScene.cs` 的 `RectOf()`（`:895-909`）**优先取 `Label`、其次 `ImageQuad`**，
   且用的是**组件自己的 `transform.position`**——`AlignLeft` 会把 Label 节点挪走，所以拿外层容器量会偏
   （注释里已记过「字飘走了而矩形断言全绿」）。本块两条 A275 断言正是靠这个特性才量得到「块左缘」。
4. `ShopScene.cs:1874-1878` 那句卡背矩形断言（`2.17×3.14 × CardK`）与 A183 用的是**同一个 `CardK`**
   （ShopScene 里的 `const float CardK = 151f × 0.876259982585907f`）——
   将来若有人改 `CardK`，两块会**一起**红（这是好事，不是耦合缺陷）。
5. 原版 `counter` 的 RT 锚是 `(0.2,0.2)-(0.8,0.7)`、`pivot (0,0.5)`、`sd (0,0)` —— 我们用的是一个
   **写死的绝对矩形** `SliderCounterR`（`1085.70 → 1329.66`）。两者**等价到 0.02px 以内**（本轮算过：
   原版 = `1085.729 → 1329.674`），所以不影响本块断言，但**「我们那份是抄来的字面量、不是按锚点算的」**这一点值得知道。
