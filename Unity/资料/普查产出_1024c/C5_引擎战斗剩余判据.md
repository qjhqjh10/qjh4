**结论**

1. 那个「本地没有」的枚举 **= `DefinedTrait`，不是 `TraitId`**（`TraitId` 这个名字全库不存在）。

### Q2 `EffectResolver.EmitCardTrigger` 的 `HasTriggerSource` 不查 ability presence

**结论**

原版**先看 ability，后看（且只看）动画有没有东西播** —— 顺序与我们**相反**：

- `RawCardScript.TriggerAbilities(trigger,…)` 是**唯一入口**，它遍历 `cardAbilities`（分支 A：`rawCard+0x290`）
  或 `CardScript.activeAbilities`（分支 B：`card+0x110`），**每一条都先过 `CardAbility.CanTriggerAbility`**
  （调用点 `RawCardScript__TriggerAbilities.c:108` / `:207`）。
- `CardAbility__CanTriggerAbility.c:46-48` 的**第一句**就是
  `if (*(int *)(ability + 0x10) != trigger) return 0;` —— 即 **ability 的 trigger 不相等 ⇒ 什么都不发生**
  （既不结算、也不发事件、也不播动画）。
- 动画在**里面**：`RawCardScript__TriggerAbility.c:60` → `PlayTriggerTraitAnim`，
  而 `TriggerAbility` **只**在 `CanTriggerAbility` 返回 true 之后才被调（同一个 for 循环体）。
  ⇒ **「有动画行、没有 ability」在原版是绝对静默的**（连 `EvtKind.Trigger` 这一层都没有）。
- 另外 `AbilityTrigger` 里有**两个**永远不走 `PlayTriggerTraitAnim` 的：
  `WhileInPlay(0x14=20)` / `WhileInPlayVariable(0xf0=240)`（`TriggerAbility.c:60` 那两条 `!=`）。

所以 `HasTriggerSource` 现在的 ① → ② → ③ 顺序**语义不对**，正确顺序是
`presence == 1` 优先 ⇒ `presence == 0` 直接不发 ⇒ `presence == -1` 才回退动画行（旧卡表兜底）。

**证据**

| 内容 | 出处 |

| trigger 相等是第一道闸 | `d:/2/tools/decomp_full/CardAbility__CanTriggerAbility.c:46-48` |

| `IsRightContext` 兜底 | 同上 `:126-129` |
| 逐 ability 判 | `RawCardScript__TriggerAbilities.c:108`（分支 A）· `:207`（分支 B） |
| 动画在 `TriggerAbility` 内、且 20/240 不播 | `RawCardScript__TriggerAbility.c:58-62` |
| 我们现在的闸 | `RuleEngine/Core/EffectResolver.cs:7073-7092`（`HasTriggerSource`）· `:7098`（`EmitCardTrigger`） |
| 我们这两个判据 | `RuleEngine/Core/CardDef.cs:564`（`HasAnimTrigger`）· `:1656`（`AbilityTriggerPresence`） |

**影响面（现读 · 41 个引擎真发包会用的 trigger 名，逐名算）**

- 「**有动画行、没有 ability**」= **0 张卡 / 0 个 (卡,trigger) 对**。
  ⇒ 今天这道闸的**顺序**虽然错，但**零可观测差异**（所以 E8 说「顺手发现」是对的，不紧急但要修）。

**建议落点**：`RuleEngine/Core/EffectResolver.cs:7073` `HasTriggerSource`，改成：

```csharp
// 判据：原版 CardAbility__CanTriggerAbility.c:46-48 —— ability 的 trigger 相等是第一道闸；
// 动画只在 TriggerAbility（RawCardScript__TriggerAbility.c:60）里头播 ⇒ 没有 ability 就什么都不发生。
int p = card.AbilityTriggerPresence(triggerName);
```

`WhileInPlay` 会从「1 张有动画行的卡」变成「13 张有 ability 的卡」都发事件（多 12 条空转日志）。
⇒ 建议**拆成两个方法**（`HasTriggerSource` = 语义闸 / `HasAnimRowOnly` = 表现闸），
`WhileInPlay` 那一路继续用后者；A/E/F 三族 + 600/605 用前者。理由写进 doc。

**还差什么**：「全池 0 张」这条不变式值得做成**断言**（数据变了会响）：
「凡 `animTimes[].tn = T` 的卡 ⇒ `AbilityTriggerPresence(T) == 1`」。
今天 1,127 张逐卡逐行都成立（上面那张 41 名总表 `aOnly` 列全 0）。

### Q3 `RequireActorInPlay` 的入队 vs 出队口径差

**结论**

这个差**已经被 W63 抹平了**（主闸搬回入队），现在剩下的**不是时序差，而是一个漏判条件**：

- 原版：`IsRightContext` 的**唯一调用者**是 `CardAbility.CanTriggerAbility`，而它由
  `RawCardScript.TriggerAbilities` 在**广播那一刻同步**调用（`:108` / `:207`）⇒ **入队前**判一次，判过就照跑。
  入队之后**死亡 / 回手 / 洗回牌库都不取消**（`BattleManager.CancelEffectsFromDisappearingUnit`
  的调用点只有 5 处，全是 jam / transform / removeEffect 族：
  `ResolveJamUnit.c:263` · `ResolveAction.c:2574` · `RemoveSelfBuffsFromQueues.c:5` ·
  `ResolveTransformUnit.c:654` · `CancelEffectsFromDisappearingUnitFromQueue`）。
- 我们：`ActionPump.EnqueueAbility`（`Core/ActionPump.cs:181`）已经做了同一件事（`:216-235`），
  出队只留 `CarrierReplacedByRemnant`（残骸 / transform）。
  ⇒ **时序口径现在与原版一致**。
- **仍开的口子**（`:216` 那个 `if`）：
  ```csharp
  if (abilityContext != Unknown && actor != null) {
  ```

### Q4 v25 `targetCriteria` 与 `unitConditions` 的合成顺序

**结论（三句）**

1. **原版只有一个对象**：`TargetCriteria` 38 个字段，`conditionsFilter`（`+0x38`）与
   `excludeCondition`（`+0x3c`）就是其中两个 ⇒ **不存在「两列谁先」**，
   v25 把它们拆两处是**我们的数据形状**，不是原版的两阶段。
2. **消费端按 `(ab, lg)` 把两处拼回一个对象**：
   `unitConditions[role == "target"]` 提供 `cond`/`ex`，`abilityTargetCriteria[(ab,lg)].criteria` 提供其余 36 格。
   - `lg >= 0` ⇒ **logic 级** `AbilityLogic.targetCriteria`（`AbilityLogic.cs:16-17`），
     在 `GetTargets` 里筛候选（`AbilityLogic__GetTargets.c:1095`）。
   - `lg == -1` ⇒ **ability 级** `CardAbility.targetCriteria`（`CardAbility.cs:17`，偏移 `+0x30`），
     在 `CanTriggerAbility` 里**触发前**判一次（`CardAbility__CanTriggerAbility.c:134`；同族另两条 `:131` / `:136`）。
     🔴 **这 27 行不是 v25 那些行的补充，而是另一条 criteria**（现读：162 条 role:target 行 / 130 张卡，
     其中 **27 条 `lg = -1`**；`(ab,lg)` 在同卡内**0 条重复**）。
3. **那一行不一定存在；缺行 = 无条件 = 放行**（这是对的）：
   `conditionsFilter == none(0)` ⇒ `MeetsConditionCriteria` 走默认支 ⇒ **返回 1**；
   生成器也只在 `cond != 0` 时才落 `role:"target"` 行
   （`工具/gen_cards_engine.py:2338-2341`；`CONDITION_ROLES_OPTIONAL_COND` 只含 `mult/multi/avail/choice`，
   **不含 `target`**）⇒ 缺行**必须**读成 `none`，⛔ 不能读成 `-1` 未知、更不能读成 `exclude`。

**谁过滤谁（文字流程图）**

## 顺手发现（只报不改）

1. 🔴 **R9 的 96/9 挂错了表**（详见 Q1「口径订正」）：这两个数来自 `card_vfx_by_card.json`
   （逐卡能力动画条目），不是 `trait_effect_bindings`（每个 trait 只有 1 行）。
   主对话回填时请把「96 行/96 卡」「9 行/9 卡」改挂到前者。
2. 🔴 **两个函数在本 build 是死代码**（全库 0 调用者）：
   - `CardScript.ActivateTraitAnim`（`CardScript__ActivateTraitAnim.c`，状态类 trait 动画的旧入口）
   - `BattleManager.ResolveAbilityIconAnim`（`BattleManager__ResolveAbilityIconAnim.c`）
   ⇒ 我们的 `TraitFrames` 直接照 `DisplayStatusAnim` / `DisplayTriggerAnim` 建模是**对的**，
   ⛔ 别再回头去实现 `ActivateTraitAnim` 那条链。
3. 🟡 **`Pray` 族 23 张卡有 655 ability、**一行动画都没有**（Q2 的表）⇒ 修 `HasTriggerSource` 时那条日志会每局刷；
   建议改成「每个 trigger 名一次」而不是每卡一次。
4. 🟡 **`u.Has("talent")` 不能用作天赋闸** —— `CardDef` 没有 `CardTraits` 列（`EffectResolver.cs:10982` 明写
   「`cardTraits` 是纯落值、不喂引擎」）。要判「这张卡有天赋」只能用 `TalentName` / `TalentCardData`
   （实测与 96 张 trait 卡逐张相等）。**这条**很容易被下一个代理踩。
5. 🟡 **`regeneration` 在池内 0 张卡身上**（只有 12 张卡的文案会**授予**它）⇒ 任何「regeneration 的
   表现缺口」都只可能出现在**施加那一刻**（`DisplayStatusAnim` 的 Start/OnPlay 两档），
   而它两档都没有 ⇒ 施加时也不该演框。⛔ 别按「9 张卡」去补 9 处动画。
6. 🟢 `PlayerDataManager.SaveMatchRecording` 的 matchType 位掩码已解码（见 Q5.3），
   可当「哪些模式出回放」的判据（**不含** 100 教程 / 130 战役 / 140/160 回放 / 190 场景 / 80 活动AI）。
7. 🟢 `gen_card_vfx_by_card.py` 把 `…TraitTrigger` 结尾的 CardAnim **按名字后缀**归进 `trigger` 桶
   （`:403-416`），而 `VfxMap.IsNonTriggerBeatTraitRow`（`:2575`）对 `TriggerType 3/6` **放行**
   ⇒ 这些行今天**在粗桶里是可播的**。所以 R9 说「永远播不出」对 `talent` **不完全准确**：
   准确说法是「**正确那一拍**（Talent 46）永远不响；它只可能在其他 trigger 的粗桶拍上**错拍**播」。
   给 `regeneration` 则是纯错拍 ⇒ 建议在粗桶侧把「无可达 trait 的 3/6 行」排除。
