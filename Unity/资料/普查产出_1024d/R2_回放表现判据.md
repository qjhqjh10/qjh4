## 1. 结论先行

### 1.1 部队卡牌消失 = **回放侧（表现层）**，不是录制缺动作、也不是引擎分叉

| 层 | 判定 | 证据 |
|---|---|---|
| **录制侧** | ✅ **没缺**。24 条动作里 **7 条 `kind:0`（PlayCard）= 单位的创建**，逐条见 §2 | 录像 JSON `actions[3,6,8,9,13,17,21]` |
| **引擎重演** | ✅ **逐条一致**。`trace`（每条动作后的 `DeepHash`）**24/24 全等**，摘要 `1187623750` = 录制时 ⇒ 第 0~23 条**每一条落地后的局面完全相同** | `BattleDriver.PlayReplay` 的 `replayTrace.Add(fin)` / `fin != rec.trace[i]` 比对；日志 `轨迹摘要 1187623750（录制时 1187623750）` |
| **表现层** | 🔴 **根因在这里**：`PlayReplay` 把 24 条动作**在同一个 `for` 循环里一口气灌完**，`ApplyLoggedAction` 每条末尾都调 `RefreshAll()` → `SyncBoard()`；等这一帧开始时，**引擎棋盘已经是终局**。整段回放期间 `SyncBoard` **读的都是终局棋盘** | `PlayReplay` 的 `for (int i = 0; i < rec.actions.Count; i++)`；`ApplyLoggedAction` 里 `RefreshAll(); UpdateHud();`（`:313` 起，`RefreshAll` 在 `:356`）；`RefreshAll`（`:16258`）→ `PlaySignals()` → `SyncBoard(...)`×2 |

**具体消失机制（两条叠加，都由「画面读终局」派生）：**

1. **阵亡单位从来没有视图。** 终局棋盘上**没有**它 ⇒ `SyncBoard` 遍历 `board[s]` 时 `u == null` ⇒ 走「这一格空了」那一支（`Kill(v)`），**永远不会为它建件**。所以整局里死掉的兵在回放中**一次都不出现**。
2. **活到终局的单位也只有「自己那条 `Deploy` cue 播到」那一刻才出现。**
   `SyncBoard` 开头有一道登场闸：`if (u != null && IsPendingDeploy(owner, s, u)) … continue;`
   （现读 `:22570`；`IsPendingDeploy` 在 `:17964`，账由 `NotePendingDeploy :17829` 记、`CompletePendingDeploy :17858` 销）。
   活局里这条闸**只压一格**（一次只有一张牌在路上）；回放里**整局所有 `Deploy` 全部同时处于 pending**
   ⇒ 终局盘面上的每一张兵**在它那条 cue 播到之前都被压着不建件**。
   而 `_syncAfterDeploy` 触发的补建（`AdvanceTimeline` 末尾 `if (_syncAfterDeploy)`，现读 `:17595`）**再读一次终局棋盘**
   ⇒ 建出来的视图是**终局的格号 + 终局的数值**，不是那一刻的样子。

⇒ 用户看到的「部队的卡牌都消失了」= **回放里盘面长期只有督军 + 个别刚播到登场 cue 的兵**，与「这一局实际有多少兵」无关。
实拍吻合：`62_replay_playing.png` 盘面只有 2 张（位置 = 双方督军格，HP 23 / 19，与 `46_endturn_ok.png` 里督军位置一致）；
`63_replay_esc.png` 多出 1 张敌方兵（5/1/3）与 1 张改成 21 HP 的兵 —— **正是「cue 播到一条、冒出一张」的节奏**。

**同一根因的第二个可见面（⛔ 别当另一条缺陷）**：手牌 / 牌库数 / 能量从一开始就显示**终局值**
（`62/63` 里我方手牌 **8 张**，而正常对局同一时点只有 5 张）—— `RefreshAll` 里 `SyncHand/SyncFoeHand` 同样读终局。
只有「血量」是**相对正确**的，因为 `_pendingHp` 那本账（`ToBoardCardData` 把「引擎已扣、还没演到」的差值加回去）
会按 cue 时刻显示旧血 —— 所以截图里能看见 23→21 / 19→7 在变。

### 1.2 一句话对照原版

原版回放**不是「先算完再演」**，而是**一条动作一条动作地推进**：
`BattleManager.ExecuteNextAction(log, ref index, isPlayer)` —— **唯一调用点**是 `<AddNextReplayAction>d__420` 协程，
一步一条，`<ReplayPlayAction>d__415` 在「队列空且不在结算」时才取下一手
（判据 → `资料/普查产出_0927/回放_入口与数据链.md` §B·2 / §C·④，原文 `DF/BattleManager__ExecuteNextAction.c:52-65`）。
⇒ **引擎状态与画面天然同步**，不存在「画面读终局」这一类问题。**我们缺的正是这一层。**

## 4. 20 s 安全阀的机理（为什么「排着 32 条、最后一条 35.90」）

**我们的闸**：`WaitingForBlockingAction => _blocking`（现读 `:17002`）。
- 开窗：`BeginBlockingWindow(quietAt)`（`:17529`）—— 每次 `PlaySignals` 排进一批 cue 就调一次，
  `_blockingQuietAt = max(旧, 这批最后一条 cue 的收尾时刻)`、`_blockingSince = _clock`、`_blocking = true`。
- 关窗（正常）：`TickBlockingWindow`（`:17541`）—— **队列空 且 `_clock >= _blockingQuietAt`** 才放行。
- 关窗（安全阀）：`_clock - _blockingSince > BlockingMaxSeconds(=20)` ⇒ `LogWarning` 并放行（行文与简报里那行一致）。

**为什么回放必然撞阀（这不是「卡住」，是闸的定义与回放的形状不匹配）：**
1. 活局里 cue 是**一手一手**排的（AI 出牌 / 玩家出牌各自一批）⇒ 队列最长也就 1~2 手，几百毫秒清空。
2. 回放里 **24 条动作在同一个 `for` 里全部落地** ⇒ 每条都会 `BeginBlockingWindow`，
   而每批的 `t = Mathf.Max(_clock, _timelineTailAt)`（排队尾，见 `PlaySignals` 那一段）⇒
   **整局 24 条动作的 cue 被串成一条长队**，队尾 = **35.90 s**。`_blocking` 从这一刻起**恒真**，
   而 `_blockingSince` 也停在「最后一批」那一刻 ⇒ **20 s 到点必然触发**，与「事件表有没有 bug」无关。
3. 所以那行日志的读法要改：**「排着 32 条」= 整局还没演完的 cue 的剩余数**，不是「堵住了 32 条」；
   「最后一条收尾 35.90」= **这一份回放总时长约 35.9 s**。⇒ **§1.1 的根因（一口灌完）才是它出现的原因**。

**🔴 原版这一处有明文短路，我们没照做：**
`BattleManager__WaitingForBlockingAction.c:26-30`：
`if (matchData.matchType == 0xa0 /*Replay*/) return 0;` —— **原版回放里这道闸恒返回「不阻塞」**。
⇒ 我们缺的不是「把 20 s 调大」，而是**回放局直接让它恒 false**。

**顺带（新发现的危险）**：`_blocking` 一旦被安全阀放行（`_blocking=false`），
`EndTurnClick` 那道 `if (fromUi && WaitingForBlockingAction) return;` 就**不再挡** ⇒
回放里点「结束回合」（截图里它是亮的）**会把一条 `EndTurn` 真落进引擎**，从此这一趟回放被污染。
原版因为 `WaitingForBlockingAction` 恒 0 **不靠这道闸**，它靠的是动作流游标（`ExecuteNextAction` 只由回放协程调）。

## 6. 终局指纹分叉：5 个候选（按可能性排序）

**已知约束（这条把范围压得很小）：**

`StateHash`（`Net/NetProtocol.cs:466` 起，`PlayerHash`）**多出**：`MaxEnergy` · `Faith` · `SpiritStones` · `QuestPoints` ·

## 7. 修法建议（每条带落点；⛔ 无「大概加个判断」）

> 顺序即依赖顺序。**1 与 2/3/4 都改 `BattleDriver.cs` ⇒ 必须串行**（铁律 13·3）。2~5 是 1 的子集，若只想先止血，可只做 2~5。

**① 【根因】回放改成「一条一条推」，而不是「一口气灌完」**（判据 = 原版 `ExecuteNextAction` + `<ReplayPlayAction>`）
- 落点 1：`PlayReplay`（`:803`）把 `for` 循环体抽成 `bool ApplyReplayActionAt(int i)`（内部：`RecKindForfeit` 支 / `ApplyTutorialRaw` / `ApplyLoggedAction` + 逐条 `DeepHash` 比对 + 两条开局次序断言，**原样搬**，⛔ 别改语义）。
- 落点 2：新增字段 `_replayRec` / `_replayCursor` / `_replayTrace` / `_replaySame`；进回放时置游标 0。
- 落点 3：`AdvanceTimeline`（`:17373`）末尾（`TickBlockingWindow()` 旁边）加 `TickReplayPump()`：
  `if (!_replaySession || _replayPaused || _replayCursor >= _replayRec.actions.Count) return;`
  `if (_timeline.Count != 0 || _clock < _blockingQuietAt) return;`  ← **「上一手演完才推下一手」**，与原版 `ActionsInQueue()` 空才取下一手同义
  `ApplyReplayActionAt(_replayCursor++)`。
- 落点 4：收尾（循环后的 `CompleteReplayBeginTurn()` + `StateHash` 比对 + 那句 `[Replay] 演完了`，`:1019-1029`）挪到「游标到底 **且** 时间线空」那一刻执行一次（加 `_replayFinished` 闩）。
- 附带收益：`_timeline` 不再堆 32 条 ⇒ §4 的 20 s 阀**从根上不会再撞**；`SyncBoard` 读到的就真的是「这一刻」的棋盘 ⇒ §1.1 两条消失机制同时消失（`IsPendingDeploy` 恢复成「只压一格」的原义）。

**② 回放局的 `WaitingForBlockingAction` 恒 false**（判据 `BattleManager__WaitingForBlockingAction.c:26-30`）
- 落点：`public bool WaitingForBlockingAction => _replaySession ? false : _blocking;`（`:17002`）。
- 附带修掉 §4 末段那个危险：回放里 `EndTurnClick` / `CommitCommand` 那道闸**永远挡着**（⛔ 但这会让「回放里结束回合」从「能点」变成「点了没反应」—— 应连同 ③ 的出口一起看）。

**③ 回放出口**（判据 `BattleManager__ClickExitBattle.c:43`：回放不判负、直接 `LeaveBattle`）

  ⇒ `Update` 的 `Ctx.IsOver` 分支（`:12324-12335`）里 `HandleEndBattleExit()`（`:12333`）自然生效，点/ESC 回主菜单。

**④ 把四颗回放钮显示出来 + 解掉冻结点**
- 落点 A：`BuildHud` 里 `_replayBar.Setup(false)`（`:25143`）**不要动**（那是「普通对局不显示」的判据），

  调 `_replayBar.Setup(false)` —— `_replayBar` 只建一次（`_hudBuilt` 闩），所以**必须每次 `Begin` 都复位**。
