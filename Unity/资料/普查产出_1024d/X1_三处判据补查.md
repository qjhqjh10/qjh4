## 一、`_Clamp_Range` 到底被什么门控 —— **没有任何门控；而且它根本不是「裁切」**

### 结论（一句话）
`_Clamp_Range` 属于 `Everguild/Card ImageUI`（材质 `Card Image Overflow`，**所有 `CardImage` 节点都用它**），
**四个 PS 变体里都无条件生效、没有任何关键字/材质态门控**；它的算式是
**`alpha = saturate(alpha + (矩形内 ? 1 : 0))` = 「矩形内把 alpha 顶到 1」**，
**矩形外完全不改成 0** ⇒ **它从来不会切掉任何插图**。所以「战术卡为什么不套硬矩形」这个问题**不成立** ——
原版对**所有卡型**都没有「削两侧 18%」这回事。`H1` 的整条推断（含 `CardView` 里那段 `α *= (…) ? 1 : 0` 的注释）**是错的，要改**。

### 证据

**① 属性默认值 / ② 是否有关键字门控**（`bundle_shaders_assets_all/Shader/Shader_-2318977921299023320.json`，`m_ParsedForm.m_Name = "Everguild/Card ImageUI"`）

| 项 | 值 |
|---|---|
| `m_PropInfo.m_Props[]` 里的 `_Clamp_Range` | `m_Type = 1`（Vector）、**`m_Attributes = []`（没有 Toggle）**、`m_DefValue = (0.81, 1.0, 0.18000001, 0.0)` |
| 唯一带 Toggle 的属性 | `_UseUIAlphaClip` → `Toggle(UNITY_UI_ALPHACLIP)`（**不是** `_Clamp_Range`） |
| `m_KeywordNames` | `STEREO_INSTANCING_ON / UNITY_SINGLE_PASS_STEREO / STEREO_MULTIVIEW_ON / STEREO_CUBEMAP_RENDER_ON / UNITY_UI_CLIP_RECT / UNITY_UI_ALPHACLIP`（`m_KeywordFlags = 0,0,0,0,1,1`）—— **6 个，全是 Unity UI 内置的，没有一个是 clamp** |
| SubShader 0 / Pass 0 | 1 个 pass；fragment 只有 **4 个变体**（无 / ALPHACLIP / CLIP_RECT / 两者），关键字表里**没有 clamp 相关项** |

**③ 常量缓冲绑定 = 铁证**（同文件 `m_SubShaders[0].m_Passes[0].progFragment.m_CommonParameters`）

```
m_ConstantBuffers[0]: $Globals, m_Size = 128 (= 8 行 × 16B ⇒ cb0[0..7]), m_IsPartialCB = true
   VectorParams: _TextureSampleAdd  @ byte 48  (= cb0[3])
                 _Clamp_Range      @ byte 112 (= cb0[7])   ← **cb0[7] 就是 _Clamp_Range**
m_ConstantBufferBindings: $Globals → cb0
```

**④ 四个 PS 变体逐字节相同的那段（唯一用到 `cb0[7]` 的地方）** —— 反汇编 `disasm_dxbc.py "Card ImageUI"`（600/668/768/844 B 四段）：

```
ge   r0.xyzw, cb0[7].xyzw, v2.xyxy      ; x=0.82>=u  y=1>=v  z=0.18>=u  w=0>=v
and  r0.xy,   r0.xyxx,    l(1,1,0,0)    ; 转成 1.0f / 0.0f
movc r0.xy,   r0.zwzz,    l(0,0,0,0), r0.xyxx
                                        ; ⇒ r0.x = (u>0.18 && u<=0.82) ? 1:0 ; r0.y = (v>0 && v<=1) ? 1:0
sample r1.xyzw, v2.xyxx, t0.xyzw, s0
mad_sat r1.w, r0.x, r0.y, r1.w          ; ★ alpha = saturate(矩形内 + 纹理alpha)  ← **加法，不是乘法、不是丢弃**
mad  o0.xyzw, v1.xyzw, r1.xyzw, cb0[3].xyzw
```

- `mad_sat dst,a,b,c` = `saturate(a*b + c)` ⇒ 矩形**内** α=1，矩形**外** α **原样保留**。
- **VS 的 `dcl_constantbuffer CB0[7]` 只到 cb0[6] 的语义范围、指令流里一次都没读 cb0[7]**（UV 只走 `cb0[5]` = `_MainTex_ST`）⇒ 只作用在片元的 alpha 上。
- 同一份 4 段在 `wf_shaders.bundle` 与 `shaders_assets_all.bundle` 里**逐字节相同**（两份都给 `Everguild/Card ImageUI`）。

**⑤ 材质序列化值（3 个带 `_Clamp_Range` 的材质，全库只有 3 个）**

| 材质 | 所在包 | shader | `_Clamp_Range` 序列化值 | 有没有用 |
|---|---|---|---|---|
| **`Card Image Overflow`** | `bundle_duplicateassetisolation_assets_all/Material/Material_-8301844802436097929.json` | `-2318977921299023320` = `Everguild/Card ImageUI` | **(0.82, 1, 0.18, 0)** | ✅ 真正生效 |
| `Card Image Simple` | `bundle_menus_assets_all/Material/Material_-7392060973429676950.json` | `-1015833530554052331` = `Everguild/UI/Card ImageUI Simple` | (0.81, 1, 0.18, 0) | ❌ **该 shader 的属性表里根本没有 `_Clamp_Range`**（9 个属性：`_MainTex/_Color/_Stencil*/_ColorMask/_UseUIAlphaClip`）⇒ **死值** |

**⑥ C# 侧（与之前结论一致，补上「谁写」）**

### 该怎么做
1. **`_art` 不套 = 对**（`ArtClampKindFor` 恒 0 保持）。但**理由要换**：不是「实况证伪了它生效」，而是**它本来就不裁**。
2. 🔴 **`CardView.cs:884-945` 那段注释必须按铁律 5 改**：`α *= (z<u≤x && w<v≤y) ? 1 : 0` / 「矩形外整块 α=0（不是按轮廓、也不是渐变）」**两句是错的**，正确写法 = `alpha = saturate(alpha + inside01)`（出处见上表 ④）。这段错误注释正是 `H1` 那一版「非单位卡也套 1/2」的判据来源。
3. ⚠️ **`_artFront` 现在把 `clampKind 1/2` 落成「缩网格 + 反算 UV」= 硬裁**（`CardView.ArtMeshInFrame` `:9683-9706`），**那不是原版的操作**。`_artFront` 是我们自己的 opt-in 层，硬裁可以留，但**不能再写成「原版那一层是 `_Clamp_Range` 的等价物」**（`ArtClampKindFor` 的 doc 末段、`CardView.cs:10654` 那句要改口径）。生产出厂 `UseFrontLayer = false` ⇒ 改口径即可，不改行为。
4. **我们的值**：`Card3D.shader` **完全没有 `_Clamp_Range`**（`grep -c Clamp = 0`，我们烘在网格里）；`CardView.ClampRangeSmall = (0.82,1,0.18,0)`、`ClampRangeBig = (0.75,0.89,0.25,0.1)` —— 数值本身抄对了，**语义抄错了**。
5. 副作用（可顺手核）：原版在矩形**外**用纹理 alpha，矩形**内**强制不透明。我们是「整幅插图不透明（`ArtOpaque`）」⇒ 对内接图的单位卡，**矩形外那圈**我们比原版更不透明。要看真机有没有可见差异，**不阻塞**。

### 还没查清的
- `DOColor` 那条 tween 支的**第 3 个实参是 `_Clamp_Range` 的 propertyID**（`+0x68`），但 DOTween 的 `DOColor(Material, Color, string, float)` 只吃属性名 —— 反编译把重载名贴错了。**大图档（状态 1）实际插值的是不是 `_Clamp_Range`** 没定；本 build 产品路径**走不到状态 1**（`ChangeState` 只在 `CardDisplayWindow.CardOverdrawHandle` 里被 `SetImageOverDraw` 触发），不影响结论。

## 二、战术卡立绘中心 y —— **0.456 是 `Front` 局部值；量到的 0.57 是含 `Front` 的 +0.08 的卡体空间；两棵树都真实存在，但差值不在这里**

### 结论（一句话）
`0.456 = (CardImage.apos.y −0.044) + tacticsOffset.y 0.5`，**作用空间 = `Front` 局部**；
把 `Front` 自己的 `apos.y = +0.08` 算进去才是**卡体（`2DCard`）空间 = 0.536**，
而原版大卡量到的 **0.57 ± 0.06 正好含 0.536**（差 0.034 < 0.06）⇒ **缺的就是那个 +0.08（= `M2` §八·1 同一条），不是「详情窗 prefab 不同」**。

## 三、回放会不会推进「日常骷髅 / 场次」—— **不会。闸在基类 `MissionChallenge.UpdateProgress` 里**

### 结论（一句话）
**回放（`matchType = 160/0xA0`）与教程回放（`140/0x8C`）在 `MissionChallenge.ValidateMatchConditions()` 里被直接判 false**，
而**所有** `UpdateProgress` 重载都先过这一关 ⇒ 骷髅 / 场次 / 一切 MissionChallenge 子类**都不推进**。
`R3` §七·1 的怀疑（「静态看会推」）**不成立**；`RE1 §G3` / `A381` 的旧结论 **是对的**，只是**闸的位置**记错了（不在 `SkullsCount` / `GamesPlayed` 里，在基类）。

### 证据（静态即可定，不需要运行时探针）

1. **信号确实在回放时也发**（`R3` 那半是对的）：`ChallengeLogMgr__LogMatchEnd.c` 全文**不含任何 matchType 判断**，无条件
   `BattleEndSignal(matchData, gameMode, BattleCardsScoreManager.GetSkullCount(), isWin)` → `Signal.Raise`；
   调用点 `BattleManager__ProcessMatchResult.c:152` 在 matchType 分叉**之前**。
2. **但两个订阅者最后都汇到基类**：
   `SkullsCount__OnBattleEnd.c` 末尾 `MissionChallenge__UpdateProgress(this, skullCount, 0, 0)`；
   `GamesPlayed__OnTrigger.c` 末尾 `MissionChallenge__UpdateProgress(this, 1, 0)`。
3. **基类的三个重载共用一个入口**（`all_methods.txt`：RVA 6946992 / 6947296 / 6947488）：
   - `0x1806a02a0`（`UpdateProgress(int, bool)`）= 装 `DisplayClass35_0` 后 `jmp 0x1806a00b0`
   - `0x1806a01e0`（`UpdateProgress(Action<…>)`）= 装 `DisplayClass34_0` 后 `jmp 0x1806a00b0`
   - **`0x1806a00b0`（主入口）第 4 条指令级判据**：
     ```
     1806A013B  xor  edx, edx
     1806A013D  mov  rcx, rbp
     1806A0140  call 0x1806a03f0     ; = MissionChallenge$$ValidateMatchConditions (RVA 6947824)
     1806A0145  test al, al
     1806A0147  je   0x1806a01bc     ; false ⇒ 直接返回，进度一点不写
     ```
4. **`ValidateMatchConditions` 的第一条实义判据就是回放闸**（`MissionChallenge__ValidateMatchConditions.c:65-68`）：
   ```
   cVar3 = BattleManager__IsReplayMatch(lVar5, 0);
   if (cVar3 != '\0') { return false; }
   ```
   其后才是 `PlayModes == 1 ⇒ allowOnDuels(+0x35)` / `IsTutorialMatch ⇒ allowOnTutorials(+0x34)` / allowlist(+0x40) / blocklist(+0x38)。
5. **`IsReplayMatch` 的真值**（`BattleManager__IsReplayMatch.c`）：读 `matchData + 0x1c`（= `get_matchType` 同一个字段）
   ⇒ **`== 0x8C || == 0xA0` 为真**。`MatchType.cs`：`Replay = 160 (0xA0)`、`TutorialReplay = 140 (0x8C)`。
