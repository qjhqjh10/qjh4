### S2 · 「加攻/加血时数值变红」

#### 2·4 我们这一层的真实链路（现读）

```
BattleDriver.SyncBoard → CardView.SetData(d)
  └ CaptureStatChanges(d)      // 必须在 Data = d 之前；逐格 newV > oldV ? 涨 : 落
      └ FlashStat(s, up)  → _statFlash[s] = up ? StatUpColor(0,1,0) : StatDownColor(0.9725,0.306,0.353)
  └ SyncStatLayers() / ApplyStatFlashes()
      └ mr.sharedMaterial.color = **(_tint * c)**        ← 🔴 问题就在这个 `_tint`
```

- **涨落色本身没错**：`CardView.CaptureStatChanges`（`newV > oldV`）+ `CardFeel.StatUpColor` 绿 / `StatDownColor` 红；
  `Editor/BattleScene.cs` 那条「掉血 ⇒ 落色 / 加攻 ⇒ 涨色 / 同值 ⇒ 回白」单测**现读仍在**、且都过。
  ⇒ **「升却变红」不可能是这条判据给的**（除非走的是另一条路，见 2·6）。
- **真凶 = `_tint` 乘法**：`CardView.SyncStatLayers` 与 `ApplyStatFlashes` 都是 `_tint * c`。
  `_tint` 来自 `SetHighlight → SetTint(CardHighlight.ColorOf(s))`，而：
  | 状态 | `ColorOf` | 白字 × 它 = |
  |---|---|---|
  | `SelectedTargetInBoard` | **(1.0, 0.5176, 0.0) = #FF8400 橙** | **(255,132,0) 橙红** ← 用户说的「红」 |
  | `ValidTarget` | (0, 1, 0.1294) 绿 | (0,255,33) 绿 |
  | `Selected` / `Playable` / `Normal` | 白 | 原色（此时升才是绿） |
  `CardHighlight.ColorOf` 那一行**自己写着**：「⚠️ 原版**只拿它点那圈状态环**（见 `FrameColorOf`），『整卡着色』这一路是**我们的表达方式**」。
- **触发场景**：任何**指向性**操作（打人 / 指向性战法 / 指向性增益）在**指针压着目标**那一刻给整卡上了 `SelectedTargetInBoard`；
  指向性增益的合法目标则是 `ValidTarget`（整卡绿）。两者都会把四个数值一起染掉 ⇒ 增益落地那一拍看到的数字不是白/绿，而是**橙/绿混色**。
- 另：`ValidTarget`/`SelectedTargetInBoard` 的**整卡绿/橙**也让「白→绿」这条预期失效（本来该只是环变色）。

#### 2·5 原版判据

- `CardTextCountersController` 的 `DoColorChange(old,new)`：**只改那一个 counter 自己的颜色**，没有「再乘一层高亮色」这一步（`CardView` 的注释也这么写，判据在 `CardFeel.StatUpColor` 那一段）。
- 高亮色在原版是 **`CardHighlight.FrameHighlight` / `FrameHighlightRemnant` 两个 SpriteRenderer** 的颜色（`CardHighlight.cs` 文件头：`ValidTargetColor/SelectedColor/PlayableColor/SelectedTargetColor/RegularColor` 五色全给那两层用）。
- ⇒ **数字的颜色不该被高亮色乘**。

#### 2·6 第二候选（没闭合，别当结论）

数值真的**下降**也能出红。`BattleDriver.ToBoardCardData` 会 `d.health += pend.amount`（`_pendingHp` 是「引擎已改、表现没演到」的欠条，`Heal` 记 **−实际量**）。
只要有一条刷新落在「账记了但事件还没轮到」之后、且符号/清账出错，显示值就会先掉。**今天没有证据**说它错（`NotePendingHp` / `CompletePendingHpBeat` 两侧符号成对）；
要证伪得靠探针：每次 `SetData` 打 `(cardId, old{melee,ranged,armor,health}, new{...}, flash{up/down})`，一局就能看出是**值掉了**还是**被染红**。

#### 2·7 修法落点 + 断言

- **落点**：`Core/CardHighlight.cs` 的 `ColorOf` —— 棋盘上的 `ValidTarget` / `SelectedTargetInBoard` **返回白**（整卡不着色），颜色只走 `FrameColorOf` → `_rim`（`CardView.SetHighlight` 里那一段）。`Selected` 现读已是白。
  ⚠️ **同时核手牌**：手牌 `ValidTarget` 现在也整卡染绿（同一行代码），改之前先确认手牌那档原版也不整卡着色。
- **次选（只治标，不建议单独上）**：`SyncStatLayers` / `ApplyStatFlashes` 不乘 `_tint`，只乘 alpha。⛔ 这会把「置灰 (Unplayable) 时数字不变灰」的现有行为一起改掉。
- **断言**：① 棋盘卡 `SetHighlight(SelectedTargetInBoard)` 之后，`_stats[s].sharedMaterial.color == 白`（或只等于 flash 色）；**改坏法**：把 `ColorOf` 改回 #FF8400 ⇒ 必红。
  ② 成对：`SetHighlight(Normal)` 后 `_rim` 不亮、整卡白。③ 增益端到端：`melee 3→4` 后立刻读材质色 **逐分量 == `StatUpColor`**（不是「偏绿」）。

### S3 · 「插图有白边、一直闪」（**证据已闭合**）

#### 2·8 机制（`文件:行号` 现读）

`Assets/CardPresentation/Shaders/Card3D.shader` 主 pass：

```hlsl
const float2 ArtUvMin = float2(0.1818, 0.0017);
const float2 ArtUvMax = float2(0.8203, 0.9978);
float2 artUv = (i.uv1 - ArtUvMin) / (ArtUvMax - ArtUvMin);   // ← 把 UV1 整块铺满【裁好的 PNG】
float4 art   = tex2D(_CardImage, artUv);
art.rgb *= tex2D(_BaseMap, i.uv1).a;
```

两条映射**不一样**：
- **原版**：`_CardImage` = `rawCard.cardSprite.texture` = **1024² 图集整图**，UV1 ∈ [0.1818,0.8203] ⇒ 采样范围 = 图集 **x 186.2 … 840.0**（宽 653.8 px）。
- **我们**：`_CardImage` = `Resources/Art/cards/art_*.png`，按 `Sprite/<名>.json` 的 `m_RD.textureRect` 裁过 = **x176.5, w670.5 ⇒ 671×1024**（`工具/import_original_art.py:28` 与 `:1022` 都写着这一组数）。UV1 重映射到 0..1 ⇒ 采样范围 = **整张 671 px**。
- 差 = **左多 ~9.7 px、右多 ~7.0 px**；而那正是立绘 PNG 的**纯白（255）卡框内沿**：实测 **左 5–6 px / 右 5–6 px**，`art_*.png` 里 **664/1168 张左+右都有**（左 662、右 663、上 151、下 7）。

#### 2·9 现场证据（今日真机截图）

`_tmp_view/shots/2026-10-24_第七十四会话/39_battle_now.png`：横穿中间那张兽人卡的扫描行（y=560），
`x=1204` 一整列亮度 **195–200**（RGB ≈ 205,199,198），左右邻列只有 **13–50** ⇒ **恰好 1 px 宽的纯白竖线**，
沿立绘窗高度**连续**存在；右缘 `x≈1300–1305` 也有 228–245 的亮带（框内沿）。
卡片在屏上约 150 px 宽 ⇒ 5–6 px 白边缩成 **~1 px** = 用户说的「一点点白边」。

#### 2·10 为什么「一直闪」

白带宽度 = **1 屏像素量级**（亚像素），而
- 场上卡每帧按**战场深度**重算 `localScale`（`CardFeel.HookDepthScale` → `MinionScaleByPosition` 曲线 `0.36→0.70`，冲出去/挨打时每帧变），
- 相机 `CombatAutoZoom` 会改 zoom（同帧改投影 ⇒ 采样点移动），
⇒ 那条 1 px 的边界**每帧落进不同的像素格**；再加上贴图 mip（`_CardImage` 与 `_BaseMap` 都有 mip）在不同 LOD 下把白边摊成不同宽度 ⇒ **闪烁/呼吸**。

#### 2·11 修法落点 + 断言

- **落点（一处）**：`Shaders/Card3D.shader` 的 `artUv` —— 把 UV1 再映射进 **crop 的内子矩形**（= 原版在 1024² 图集里的采样范围，换算到 671×1024 的 crop 坐标）：

  ```
  u ∈ [(0.1818×1024 − 176.5)/670.5 , (0.8203×1024 − 176.5)/670.5] = [0.01441, 0.98954]
  v ∈ [0.0017×1024/1024            , 0.9978×1024/1024            ] = [0.00170, 0.99780]
  artUv = lerp(float2(0.01441, 0.00170), float2(0.98954, 0.99780), t)
  ```
  （四个数在 shader 注释里带上 `textureRect` 与 UV1 角点的算式，别只写结果 —— 换卡框/换裁法时要能重算。）
  等价的另一条路：导入器裁立绘时**再内缩 1.2%**（`import_original_art.py`），但那样 2D 卡面（手牌/卡池/详情）会一起变 —— **2D 那边现在被卡框 alpha 盖着，改它属于无谓风险** ⇒ 建议只改 shader。
- **断言**：① 加一条**渲图级**断言（`CardFaceProbe` / `BattleScene` 的 board 档）：渲一张 `CardFace.Board` 的场卡（挑一张有白边的卡，如 `art_um11` 对应的卡），
  沿立绘左右边界外扫 3 px，**不得出现「整列亮度 > 180 且两侧邻列 < 80」的列**；**改坏法**：把 `artUv` 改回 `0..1` ⇒ 必红。
  ② 常量一致性（源码普查）：`ArtUvMin/Max` × 1024 与 `textureRect` 的四个数互相验算，误差 < 1 px。

### S4 · 「演出时间有点快」

#### 2·12 结论

1. **主因 = 命中那一拍短了 0.25 s**：我们 `EventTiming.DurationOf(EvtKind.Hit) = CardFeel.HitRotDuration(0.5) + ResetDuration(0.25) = 0.75`；
   原版 `CardScript._ReceiveDamage_d__381__MoveNext.c:342` 收尾是 `WaitForSeconds(DAT_1834b2bb8)`，该常量 **4 字节实读 = 1.0**
   （`资料/待办判据_战场与战斗视图.md:970` / `加时与冲突模式_原版规格.md:543` 都实读过同址 = 1.0f），调用点 `_ResolveAttack:993` 传 `ReceiveDamage(dmg,0,0)` = 双 false ⇒ 会走到那一句。
   ⇒ **每次命中整条事件流少排 0.25 s**（10 次命中/回合 ≈ 少 2.5 s）⇒ 观感「快」。
2. **台账「偏多 0.3 s」是方向写反了**（见 §四）。那句话来自旧口径「0.4 / 0.2 两种」的对比，与 `_ReceiveDamage` 的 1.0 无关。
3. **`DurationOf(Hit)` 那 0.75 的出处本身就是机制错位**：`HitRotDuration/ResetDuration` 取自 `Impact Light/Heavy Tween`，

## 五、顺手发现

1. **`CardHighlight.ColorOf` 的整卡着色是**整个战斗/菜单共用的**一条偏离**：`ValidTarget` 绿、`SelectedTargetInBoard` 橙都乘到**每一层**（含数值、卡框、立绘）。原版五色全给 `FrameHighlight`/`FrameHighlightRemnant` 两个 SpriteRenderer。改它同时影响**手牌可打出/合法目标**的观感 ⇒ 派活时把手牌那一档一起核（别只修棋盘）。
2. **立绘 PNG 的白边是导入器带进来的**：`工具/import_original_art.py` 按 `m_RD.textureRect` 裁（x176.5 w670.5），**没做内缩**。2D 卡面（手牌/卡池/详情/卡组格）用的是同一批 PNG，但它们**被卡框 alpha（`SoftMaskScript` 那一套）盖住**，所以看不出来；3D 卡体没有那层框可盖 ⇒ 只有场上露白。⇒ 「是不是需要宽一点点」的正解**不是把插图放大**，而是**把多采的那 ~1.2% 缩回去**。
3. **`Card3D.shader` 的 `m` 是硬二值**（`uv1.x > 0.18 && uv1.x <= 0.82 && uv1.y > 0`），2×2 像素的边界必然 aliasing；即使修好 2·11，卡在极小屏幕上仍可能有一条亚像素亮线。若将来并排比仍看得出，考虑 `lerp` 一像素宽的过渡（**但原版是硬 mask，改了就是偏离** ⇒ 先按原版修，别提前优化）。
4. **`BattleDriver` 已有 `_aiDeployHiddenRenderers`（飞行时关渲染器）**，只在 `RestoreAllBoardViewVisibility()` 还原（3 个调用点：`Begin` / `Begin` 另一处 / `DropSignals`）。若将来有人在这条路上漏还原，症状就是「卡牌消失」——**同族**，值得在 §2·3 的探针里一起打。
5. **`CardFeel` 的 `HitRotDuration / ResetDuration` 在改完 S4 之后就没有消费者了**（两行 doc 都写着「唯一消费者 = `DurationOf(Hit)`」）⇒ 改的时候把这两行的 doc 一起订正，否则又留一份过期口径。
