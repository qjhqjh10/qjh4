## 一、诊断结论（为什么差这么多）

**根因 = 两套帧混用：`PosInDesignSpace` 给的是「设计世界单位」，被直接当「设计 px」用了。**

`CheckV5`（修前 `:256-263`）这么写：

```csharp
var ctr = MenuDraw.PosInDesignSpace(cell);        // ← 世界单位（可见高恒 10 单位）
float nameY1 = ctr.y + CellHalf;                  // ← 90 也被当成 px 加上去
var clip = ViewportClip.Resolve(cell, null, …).RenderClip;   // ← 设计 px（1920×1080）
MenuDraw.Visible(new PxRect(ctr.x - 90, nameY1, ctr.x + 90, nameY2), clip);
```

- `MenuDraw.PosInDesignSpace(t)` 返回的是 **设计世界单位**：`LayoutSpace.DesignHeight = 10`（可见高）、
  `DesignPxH = 1080` ⇒ **1 px = 1/108 单位**（`Core/LayoutSpace.cs:205-211`）。它**不是** px。
- 要换成 px 必须再过一次 `MenuDraw.PixelOfDesign(...)`（= `LayoutSpace.ToDesignPixel`，
  x 走实测 `VisibleWidth`、y 走 `PxY` 翻向）。判据 = `Shell/ViewportClip.cs:302`
  （`ClipPx` 的「实时反推」那一支自己就是 `MenuDraw.PixelOfDesign(MenuDraw.PosInDesignSpace(transform))`）、
  `Shell/MenuDraw.cs:677`。
- 于是那条断言拿 **px 的视口框（x 654.16..1680.12 / y 210.69..855.46）** 去比
  **世界单位的矩形**（格子中心量级 x ≈ −1.9..6.5 单位、y ≈ −4.4..1.8 单位；
  加 90/41.31 之后 x ≈ −92..88、y ≈ 92..133）⇒ **x2 ≪ 视口 x1、y 也在视口上沿之外 ⇒ 15 格全部判「不在框内」**，
  所以前提条实得 **0**，主条实得「应建 0 / 实建 10」。

**为什么这不是 `ViewportClip.Resolve` 的问题**（派单 ③ 里问的那一层）：

- 该节点（`Avatar Tab/Item Display Panel/Scroll Rect`）的 `BaseRect` 是 `vc.CaptureNow()` 在
  `Node(...)` 之后立刻抓的，`ClipPx` 走「记过 `BaseRect`」那一支 ⇒ 框 = `654.16, 210.69 → 1680.12, 855.46`，
  与 `MenuScroll.Viewport`（`ProfilePage.NewScroll(vp, …)`）**逐位同值**。
- 交叉验证：同一宿主 `Editor/MainMenuScene.cs:6760` 的 `CheckAtWorld(scr2, 654.16f, 1680.12f, 210.69f, 855.46f, …)`
  一直绿 ⇒ 节点的实读矩形就是那四个数；而 V3 / V6 在同一趟里用 `QuadRectPx` 读出的绝对设计 px 也都对
  ⇒ **窗根在世界原点、`PosInDesignSpace` 的换算前提成立**，问题只在「少换一次」。
- **生产侧没有错**：`ProfilePage.Text` 的闸拿的是**字面设计 px 的 `r`**（`AvatarTab.BuildRows` 的
  `new PxRect(ox + CNmL, oy + CNmT, ox + CNmR, oy + CNmB)`）比同一个 px 框 ⇒ 建 10 格，
  与几何逐位吻合（第 3 行名字 `890.70..932.01` 在视口底 `855.46` 之外）。⛔ 没有改生产。

## 三、新口径一句话（为什么不是自证）

**期望值 = 原版字面视口矩形 ∩ 由「格子当下设计 px 中心」推出来的名字矩形**，两者都**不经过**被测的那道闸：
视口取 `Shell/AvatarTab.cs:151` 的四个常量（同一组数 `Editor/MainMenuScene.cs:6760` 已按实读矩形钉过），
求交在本文件里**手工写四比较**（先例 = `Editor/MainMenuScene.cs:18835-18865` 的 `RowsInViewport` /
`CellsInViewport`，`MenuDraw.Visible` 注释点名「那是自检的独立算一遍，别去收它」）。
⇒ 把 `ProfilePage.Text` 的闸改坏（`VisibleAbove` → `Visible` / 直接 `return` 不裁）或把视口挪走，
这条都会红；而**改坏闸的同时改坏 `MenuDraw.Visible` 不会一起变绿**。

`PixelOfDesign` 只当「世界单位 → 设计 px」的**换算器**（任何从节点读回来的矩形都必须过它），
它不是判据 —— 判据是上面那两组数字。

## 六、顺手发现（只报不改）

1. `Editor/MainMenuScene.cs:8288` 那一段调 `ProfileAssertU2b.Run()` 时，`PlayerProfileWindow.LastOpened`
   **可能是一个已经 `Close()` 掉的实例**（上面 `:8265` 关过一次、`:8270` 开回来、`:8271-8272` 的
   `CheckShadeClickRule` 又会把它关掉）。`U2b.Run()` 只在 `LastOpened == null` 时才重开
   ⇒ 今天是在**关着的窗**上断的（V3/V6 能绿说明节点的 transform 没被关窗影响）。
   **建议**：`U2b.Run()` 里加一句「`CurrentState != Open` ⇒ `TryOpen()`」，否则将来某次关窗若做了
   「挪走/缩放归零」的收尾动画，这一整组会集体假红。⚠️ 不在本批白名单（`ProfileAssertU2b.cs` 的
   `Run()` 在本批可改，但那是行为面的决定）⇒ 没动。
2. 上一版把「视口」写成 `ViewportClip.Resolve(...).RenderClip` 时，注释里写的是
   「它读的是视口节点自己的矩形 = 产品几何，不是本断言的被测值」——**这句话本身就是自证的入口**
   （那个 `RenderClip` 正是 `ProfilePage.Text` 首句用的同一份）。同族先例：`MenuDraw.Visible` 注释
   `:354-355` 明写「`RowsInViewport`/`CellsInViewport` 是自检的独立算一遍……别去收它」。建议以后
   所有「期望值」注释都补一句「⛔ 不读被测闸」。
3. `ProfilePage.Text` 的闸与 `AvatarTab.BuildRows` 的 `_scroll.Intersects(r)`（判**格子**矩形）用的是
   **两个不同的矩形**（格子 vs 格子下方的名字）⇒ 同一次重建里「建了格子但不建它的名字」是**正常**的
   那 5 格。以后写同族断言别把两者混成一个计数（本条已写进 V5 的消息里）。
