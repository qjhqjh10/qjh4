## 结论

**在「从卡组编辑回壳」那一跳补上了 `CollectionData` 那份进程级库缓存的作废口** ——
玩家在编辑窗存完回主菜单，落到的收藏窗卡组页**读的就是刚写进存档的那一版**；
改前它读的是**进程级缓存**（`static DeckLibrary _lib`），而编辑器写盘走的是**另一个 `DeckLibrary` 实例**
（`DeckLibrary.Load()` 每次 `new`），那份缓存**没有任何生产侧作废口** ⇒ 「落页对了、内容还是旧的」。

改动落在**三件**上；白名单第四件 `Deck/DeckRuntime.cs` **一个字没动**（落点表写着 `:726` / `:5941-5956` 不动）。

### 与落点表的一处**主动加宽**（请调度台裁）

落点表那一行写的是「由 `MainMenuRuntime:328` 消费到 **`Collection` 那条路**调一次」；
我写成了 **`ret.Source != None` 就作废**（= `Collection` 与 `LiveOpsEvent` **两条来路都作废**）。理由：

1. **两条来路都能改卡组、都写盘**（`DeckRuntime.CommitDeck` 与来路无关）；
2. 事件窗那条今天只是「**不开窗**」（判据不齐 —— `MainMenuRuntime` 那段三条理由），
   而 **`LiveOpsEventWindow` 读的就是同一份 `CollectionData`**（`:421` / `:497` / `:936` / `:1048` / `:1134-1153`）
   ⇒ 只作废 `Collection` 那支的话：**从事件窗编辑完、之后玩家手动进收藏页或再进事件窗，看到的仍是旧那一版**（静默）；
3. 它**仍然不是「无条件调」**（落点表禁止的是那个）：`Source == None` = 没有回程意图 = 正常进主菜单 ⇒ **一次盘都不读**。

⛔ **若裁定要严格照「只在 `Collection` 那支作废」**：把 `:339` 那一行挪进 `if (ret.Source == Collection)` 块内即可（一处一行）。

## 验收标准①的**代码级**证明链（⚠️ 不是跑出来的）

「从编辑回壳 → 落到收藏窗卡组页 → **列表显示的是刚存的内容**」：

1. 离场 `DeckRuntime.BackToMenu()`（`:3355`）→ 兜底/保留回程意图 → `LoadScene("MainMenu")`（`:3363`）；
2. 新场景起来 → `MainMenuRuntime.Start()`（`:48`）→ `Build()`（`:271`，"和自检同一条路"）；
3. `Build()` 尾段：`TakePendingReturn()`（`:328`）→ **本波新增的作废**（`:339`）→ `OpenCollection().ChangeTab(tab)`（`:341`+）；
4. `OpenCollection()` → `OpenByRef(…, closeAll: true)`（`:921`）→ `WindowsManager.OpenWindow` 里 **`CloseAllWindows()` 先跑**
   （`WindowsManager.cs:921`）⇒ 缓存里那扇 `CollectionWindow` 的 `CurrentState` 变 `Closed`；
5. 紧接着 `win.TryOpen(data)`（`:940`）→ `OpenByState()` 的 **`Closed` 支**（`WindowsManager.cs:513-521`）→ **调 `Open()`**；
6. `CollectionWindow.Open()`（`:2268`）→ `Build()` → … → `RebuildDeckCells` → `BuildDeckCell`（`:3029`）
   → `CollectionData.DeckAt(i)`（`:3032`）；
7. `DeckAt` → `Raw(i)` → `Lib.Decks[i]`；`Lib` 此刻 `_lib == null`（第 3 步作废过）⇒ **`DeckLibrary.Load()` 从盘重读**
   （`DeckLibrary.cs:117-119`，`DeckStore.LoadAll` 每次都读文件，**没有第二层缓存**）。

⇒ 第 7 步读到的就是编辑器 `CommitDeck()`（`DeckRuntime.cs:5954`）写进盘的那一版。

**这一步的反面（改前为什么看不到）**：第 3 步不存在 ⇒ `Lib` 命中**进程启动时/上次收藏窗打开时**那份拷贝，
而那份拷贝**永远不会被编辑器的写盘刷新**。

## 顺手发现的（⛔ **一个字都没改**）

1. **`CollectionData._lib` 是全仓【唯一】的进程级卡组缓存** —— 核过 `DeckLibrary.Load()` 的**全部**调用点：
   `BattleDriver.cs:2439` · `DeckRuntime.cs:661` · `DeckRuntime.cs:726` 三条**每次都是从盘新读**，
   `DeckStore` 也**没有**缓存层 ⇒ **作废一处就够**，不会出现「第二份陈旧拷贝」。
   （这条是「本次修复够不够」的**正向证据**，不是猜测。）
2. **`CollectionData.ResetForTest()`（`:379`）没清那三个 sticky 错误串** ——
   `LastSelectError`（`:132`）/ `LastDeleteError`（`:195`）/ `LastDuplicateError`（`:232`）它都不碰
   ⇒ **自检之间不隔离**：前一个夹具留下的失败文案会漏到后一个夹具（若那条断言读它、而自己**没先制造一次失败**）。
   建议（**下一波自检写手**，本波不改）：`ResetForTest` 里一并清掉，或补一条断言钉住。
3. **`DeckRuntime.BackToMenu` 的兜底意图（`DeckRuntime.cs:3359-3360`）也会走到我这一跳** ——
   「直接按 Play 打开 `DeckEditor.unity` 再离场」没有来路 ⇒ 兜底写 `Collection` ⇒ 回主菜单照样**作废 + 开收藏窗**。
   行为上无害（就是这条来路的「按来路回」），但它意味着**没有来路的来路也吃这一跳** ⇒ 如实记一笔。
4. **回程那条路不依赖 `ChangeTab`**：`CollectionWindow.Open()`（`:2270-2271`）先 `Build()`（按**新数据**画完卡组页）
   再 `tabButtons.Click(0)`；`MainMenuRuntime` 随后才 `ChangeTab(tab)`。⇒ 即使页签哪天落错，
   **「列表是新内容」这一条仍然成立**（两件事各自独立，⛔ 别把这条当成「页签的判据」）。
