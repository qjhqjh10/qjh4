## 三、疲劳那条链（2b 的触发）—— 我们的判据与已知偏差

我们引擎里疲劳**没有专用事件**：`RuleCore.cs:1230-1235` 是
`ps.Fatigue++` → `ps.Warlord.Health -= ps.Fatigue` → `ctx.Emit(EvtKind.Hit, p, BoardSpec.WarlordSlot, 名字, amount: ps.Fatigue)`，
而 `EvtKind.Hit` 的 doc 自己写着「**含护盾挡下（Amount = 0）和疲劳**」。
`RuleEngine/` **不在本件白名单** ⇒ 只能在表现层挑。落点 = `BattleDriver.NoteFatigueBanners`（`:12425`），七道闸：

① `Kind == Hit` ② `Slot == 4`(督军) ③ `Amount ≥ 1` ④ `Amount == Ctx.Players[方].Fatigue`
⑤ 那一方**牌库为空** ⑥ **同批里没有一条 `Attack` 打的就是这一方的督军** ⑦ 这个疲劳值**没弹过**

**已知偏差（如实标）**：④ 读的是**drain 那一刻的活值** ⇒ 一次抽多张而牌库空两次时，两条事件读到同一个值
⇒ **只会弹一条**（值是对的）；⑥ 挡不住「牌库刚好空的同一刻、一次伤害量正好等于疲劳值的攻击」。

**顺手查实的一条**（把查证报告里那一格钉死）：`BattleManager` 的字段表
（`dump.cs:30738-30741`）是 `+0xC0 playerManager` / `+0xC8 enemyManager` / `+0xD0 playerHand` / `+0xD8 enemyHand`，
而 `GetHero(bm, b)` 里 **`b == 0` 取 `+0xC8`(敌)、`b != 0` 取 `+0xC0`(我)**
⇒ 那个 flag **确实是 `isPlayer`** ⇒ `DamageFatigue` 归「我方牌库空」、`DamageFatigueEnemy` 归敌方
—— **我这边 `e.Player == _me` 的映射与它逐格一致**（不是猜的）。

## 四、🔴 两处「按实况/算法纠正查证报告」的地方（铁律 4 / 5）

### 1. 横幅的 y：报告写 **525.25**，真正生效的是 **510.23974609375**（差 15 px）
- **错因**：报告那张表的 `chain_rect` 是拿**场景里的序列化 `anchoredPosition`** 算的
  （`283.94973754882813 + 241.29000854492188 = 525.23974609375`）。
  而那颗 item 的 `ap` **是模板的存档值**：布局组只在「某一条亮起来」时才写它。
- **两条证据**：
  - **运行期 dump**（`runtime_ui_dump_Battle_Arena_1.tsv:1174/1177/1180/1183/1186/1189`）里**六个 item 全是同一组 `ap (960.3, −241.3)`**
    —— 正是「一条都没亮 ⇒ 布局没跑」那个状态（所以 dump 也不能直接当「亮起来时的位置」用）；
  - **uGUI 源码**（本工程 `Library/PackageCache/com.unity.ugui@…/Layout/LayoutGroup.cs`）：
    `:59` 只收 `activeInHierarchy` 的子件 · `:193-200` `GetStartOffset` · `:207-213` LowerCenter 竖轴 `=1.0` ·
    `:249-269` 竖轴那句是 **`ap.y = −pos − sizeDelta.y × (1 − pivot.y)`**（负号是坑）。
- **算出来**：单条亮着 ⇒ `pos = 266.2900085449219 − 80 = 186.2900085449219` ⇒ 中心 = `283.94973754882813 + 186.2900085449219 + 40`
  = **510.23974609375**（横轴 960.0 与存档值一致 —— 那份 `x` 差 0.35 也是同一个错因）。
  多条堆叠：**最后一条恒在 510.23974609375、前一条高 80 px**（`j` 是**子件序**里的名次）。
- ⇒ 本件取 **510.23974609375**。**报告 / `战斗界面JSON权威表_0827.md` §J 那一格建议按此订正**（本件不改 `资料/*.md`）。

### 2. 底条**不是固定 `870.98 × 60.85`**，是 **ContentSizeFitter 的 Hug**
- 判据：`MB_4344`（挂在 `Background` 上）= ContentSizeFitter **H=1/V=1 都是 PreferredSize**；
  `MB_4467` = HorizontalLayoutGroup padding L120/R120/T4/B0；TMP 那颗自己也带 ContentSizeFitter。
- ⇒ **底条 = 文字 (preferred) 尺寸 + padding**：`宽 = 文字宽 + 240`、`高 = 文字高 + 4`。
  `870.97998046875 × 60.849998474121094` 是**参考串 `ERROR MESSAGE CONTENT`** 量出来的那一组
  （交叉印证：`630.97998046875 + 240 = 870.97998046875` ✓、`56.849998474121094 + 4 = 60.849998474121094` ✓）。
- ⛔ 写死 `870.98` 的后果：中文/长文案**会溢出底条**。⇒ 本件照**规则**实现（量 `Label.WorldW/WorldH` 再重建九宫格）。
- 🔴 **高度那一格我们掺了原版一个常量**（如实标）：`高 = max(56.85, 我们量到的文字高) + 4`。
  理由：原版的「文字高」是**字体的行高**，那条字是 Pragati 族（0.9475 em）；我们这条是 **NotoSerifCJK（1.437 em）**
  ⇒ 直接拿我们的行高会**高 40%**。取「两者取大」⇒ 英文句子上与原版**逐位相同（60.85）**、中文不被切。
- ⇒ 断言建议：**别断 870.98×60.85**，改断**两条关系**（`底条宽 − 文字宽 == 240`、`底条高 ≥ 文字高` 且英文时 == 60.85）；
  另留了 `TemplateBarSizePx`（模板按参考串建的那一颗）可以量「我们 TMP 与原版度量的差」。

## 五、没查清 / 停手的部分（逐条写「卡在哪」）

1. **原版的 DOTween 缓动曲线**：那两条 tween **没有显式 `SetEase`** ⇒ 吃 `DOTween.defaultEaseType`。
   原版自己的 `DOTweenSettings` 资产**本地全盘按名找不到**（`assets_full` 0 命中）⇒ **「原版 = OutQuad」是推断**。
   我们按 `OutQuad` 写（`EaseOut`）；本仓 `Assets/Resources/DOTweenSettings.asset` 读出来也是 `defaultEaseType: 6` = `OutQuad`。
2. **那两枚黑边 quad 在原版到底可不可见**：它们是 Canvas 的头两颗子件、`m_IsActive` 13/13 都 true，
   而按 box 的 `CanvasScaler`（`m_UiScaleMode 1` + `m_MatchWidthOrHeight 0` = match-**width**）算，
   只有画布半高 > 720.09（即 `aspect < 1.33317`）才可能露出来；而那块画布又是
   **ScreenSpaceCamera**（`m_Camera = 1462`）——「画布尺寸跟不跟相机的 rect 缩」这一格**没查到实据**
   （两种模型下结论相反：跟缩 ⇒ 恒不可见；不跟缩 ⇒ 窄屏可见）。⇒ **本件按原值建、按我们的固定可见高摆**
   （我们这边恒在屏外，与原版 16:9 下的观感一致），**如实标成未查清**。
3. **原版疲劳的额外闸门**：`_ResolveDrawCard_d__432__MoveNext.c` 里那条 `ResolveFatigue` 之前还有
   `matchData != null && matchData+0xa8 != null && *(byte*)(matchData+0xa8 + 0x48) == 0` 一道条件
   —— `matchData+0xa8` 是什么、`+0x48` 那个字节是什么，**没追**（属引擎侧「什么时候才有疲劳」，
   与我们已实现的疲劳规则是另一笔账，不在本件白名单）。
4. **`GL.Clear` 那一路验不了**（批处理没有帧循环 ⇒ `beginCameraRendering` 不抬）—— 本件照原版接上，

5. **`_ResolveFatigue` 里 `DealMultiDamage` 的参数**（`DamageInfo` 的 5 个实参）没逐格解 —— 本件用不到
