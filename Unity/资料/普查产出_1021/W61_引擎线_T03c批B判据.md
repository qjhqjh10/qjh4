## 1. 一句话结论

**判据闭合。** 原版是 **四条独立 FIFO 队列 + 固定消费序 `Interrupt(2) → Instant(1) → DelayedInstant(3) → Player(0)`**；priority 来自 `CardAbility.priority`（**默认 1 = Instant**），经 `AbilityData.priority` 透传到 `BattleManager.AddAutoActionToQueue` 分道。**它不是按枚举数值排序**（3 反而最后）。`PlayOrder` 是**内层**：只决定「谁先入队」，同一条道内 FIFO 才看它；**跨道时 priority 压过 PlayOrder**。

未闭合 3 点（都不影响队列语义本身）：① `VarsGlobal` **资产**对五个 priority 字段的覆盖值（只核到 ctor 默认）；② `NextActionInQueue` 的调用点（反编译里找不到文本调用者，确认点只有 `Update`）；③ 我们引擎没有帧循环，「泵点等价物」是施工决策，不是原版语义。

### 2.1 枚举与字段

- 枚举：`ActionPriority { Player = 0, Instant = 1, Interrupt = 2, DelayedInstant = 3 }`（`ActionPriority.cs:1-7`）。
- 承载：`CardAbility.priority`（`CardAbility.cs:12`）。
- 默认：`CardAbility__.ctor.c:5` 写 `+0x18 = 1` ⇒ 不写就是 Instant。
- 透传：`RawCardScript__TriggerAbility.c:29-33` → `AbilityData+0x44`。
- 主动技能：`RawCardScript__ResolveActiveAbility.c:47-48` 硬编码 **1（Instant）**，没有 priority 字段。

### 2.2 四条队列的字段、偏移与分道

- 字段：`BattleManager.cs:4535/4537/4539/4541`（`actionQueue/instantQueue/delayedInstantQueue/interruptQueue`）。
- 偏移：`BattleManager__.ctor.c:97/101/105/109` 按同序初始化 `0x350/0x358/0x360/0x368`；由消费序反证 `0x368=Interrupt`、`0x360=DelayedInstant`。
- 分道表（`AddAutoActionToQueue.c`）：0→`0x350`、1→`0x358`、2→`0x368`、3→`0x360`；非法值 LogError 丢弃。
- ⚠️ **Player 道有额外副作用**：`ClockManager.LogPlayerAction`（`:146`）+ `thisTurnActionCounter(+0x3bc)` 自增（`:151-165`）。我方 `RuleCore.cs:6635` 已认 `0x3bc` 未接。
- ⚠️ `ActionScheduler.cs` 不是这套队列（它是 DateTime 定时调度器）。

### 2.3 入队 / 出队 / 打断

**入队**：按 priority 选道 → `List.Add` 追加到队尾（`AddAutoActionToQueue.c:98/281`）。全库无 `Insert(0, …)`。

**出队**（`Update.c:1271-1299`）：仅在 `duringBattleFlag(0x25c)` 或 `duringScriptedActionsFlag(0x268)` 为真、且 `resolvingActionFlag(0x280)` 为假时，按 `0x368 → 0x358 → 0x360 → 0x350` 找第一条非空队列 → `ResolveActionFromQueue`（置 flag、取队首、先 `RemoveAt(0)`、再结算）。**每帧最多一条**。

**打断**：Interrupt **不抢占当前动作**，只是下一个动作边界的最高道；同一 Interrupt 道 FIFO。`ActionsInQueue` 把「四道总数 > 0 或 resolving」都视为忙。

**队列卫生**：`ResolveAction.c:1728-1734` 对四道调 `CancelAnimFromUnitFromQueue` / `CancelEffectsFromDisappearingUnitFromQueue` ⇒ 出队时要重新校验单位是否还在场。

### 2.4 嵌套触发 / 死亡链

- 普通触发 = **入队**（`TriggerAbilities` → `TriggerAbility` → `AbilityLogic.PlayAbility` → `Add*Action` → `AddAutoActionToQueue`）。这闭合了 `W58_审查_引擎改动.md` §没查清②（同步还是入队 → **入队**）。
- 死亡链逐动作入队；`ResolveDeadCard`（死亡能力）在 `TriggerUnitDeathActions`（`minionDeath(4)`）之前；`minionDeath` 执行时才从 `MinionManager` 与 `allCardsInPlay(+0x470)` 移除。
- 嵌套死亡 → 追加到 **Instant 道尾**（`List.Add`），排在已排队的 Instant 动作之后。

### 2.6 与 PlayOrder 的关系

层次：① 监听者遍历序（`allCardsInPlay` 进场序）→ ② 卡内序 → ③ 入队（各 ability 的 priority 道尾）→ ④ 执行（固定道序，同道 FIFO）。
⇒ PlayOrder 只在同一条道内等价于执行序；跨道 priority 压过它。
**决定性例子**：`SAU13` / `SAU70` 的 Artifice `priority=3`，其余 17 条 Artifice 是 1；若 `SAU13` 先落场，正确执行序仍是 p1 的先响。

## 4. 施工建议

### 4.A 全队列（推荐）

**第 0 步：数据层**
1. `gen_cards_engine.py` 从 `cards_truth.json` 的 `abilities[].priority`（默认 1，只有 !=1 才落）写入 `cards_engine.json`。⚠️ **GOF97 陷阱**：两条 `trigger=0`，第 0 条 `priority=0` 且 logic 为空，第 1 条 `priority=1` 才是真效果 ⇒ 取「该 trigger 下有 logic 的那条」。
2. `CardDef` 加 `_triggerPriority` + `TriggerPriority(string)`（默认 1）。
3. `OffensiveCardData.priority` 要么消费、要么删。

**第 1 步：队列原语**
4. 新文件 `Core/ActionQueue.cs`：枚举 0/1/2/3 + 四道 FIFO + `Enqueue`（非法值 LogError 丢弃）+ `TryDequeue`（2→1→3→0）+ `Count` + `Resolving`。
5. 先写单测 T1/T2/T3/T4/T9。

**第 2 步：能力效果改成入队**
6-11. `FireBoardWhenListener:7138`、`FireTriggerAt:9957`、`ResolveAtTurn:6013`、`ResolveDeploy:6625`、`PlayedThirdCardInTurn:55` 等改成入队；一次 ability 结算 = 一条队列动作。

**第 3 步：玩家动作外壳**
12. `PlayCard` / `PlayTactic`：入口置 `Resolving=true`，内部触发入队；结束后泵队。若要网络/回放等价，再补 `thisTurnActionCounter` +1。

**第 4 步：死亡链**
13-14. 判死入 `backlash(13)`@Instant；按 `_ResolveBacklash` 顺序：死亡能力入队 → `minionDeath`@Instant → `AddReassembleMinionsOrder`@Instant → 观察者入队；`minionDeath` 执行时才移除。

**第 5 步：泵点**
15-16. `DrainActionQueues`：`Resolving` 为假时按 2→1→3→0 出一条、结算、循环到空；动作内部不递归泵队。泵点集合 = 施工决策。

**第 6 步：队列卫生**
17-18. 出队时校验单位在场；`MaxEffectChain=8` 不是队列容量。

### 4.B 降级方案（只做同广播内按道分组）

能覆盖多 Artifice p3 vs p1、同广播 Interrupt；**不能覆盖**跨动作的死亡先后、DelayedInstant vs 下一条 Player、Player 道计数。⛔ 不建议当成「已对齐」。
