### 3·1 三个数分别是「量什么」

| 路 | 算法 / 代码位置 | 读数 | 量的是什么 |
|---|---|---|---|

| **原版字段推出** | `CardBaseDemo.cs:1160-1166`：`1 − 0.647 × 0.830 = 0.463`（带 `±0.06` ⇒ `[0.403, 0.523]`） | **0.463** | `m_Color.a = 0.647`（原版 Image）× 贴图在 Sliced 映射下的平均 alpha `0.830` |

### 3·2 分歧在哪：**是估计量，不是画面**

本笔用跑出来的三张 PNG 自己复算（`_tmp_view/cardbase/cardbase_a1934_textbg_{on,off}.png`，1920×1080，`px` 矩形 `x864 y559 w192 h167`，与日志 `:4478` 的矩形逐字相同）：

| 估计量（同一帧、同一矩形、同一份 `Color32[]`） | 值 | 换算出的**平均 alpha**（`a = (1−T)/0.647`） |
|---|---|---|
| `ratio-of-means`（`Σon / Σoff`，**探针与 ④ 用的都是它**） | **0.3799** | 0.958 |
| **`mean-of-ratios`**（`mean(on_i / off_i)`，逐像素求透过率再平均） | **0.4609**（R 0.4608 / G 0.4610 / B 0.4606） | **0.833** |
| 原版字段期望 | **0.4630** | **0.830** |

**为什么两者差这么多**：这块底板是 **Sliced 九宫格**，**上缘 9px（含 7 行羽化带）落在 quad 高 39.5% 里**（`CardBaseDemo.cs:1057-1070` 的 ③·b 断言）。羽化带那几行 alpha 低（透过率高），可它们**正好压在更暗的背景上**（实测 off 帧线性亮度：顶部 0.026 / 羽化段 0.041 / 核心段 0.181）。`ratio-of-means` 是**亮度加权**的 ⇒ 羽化段被系统性压低权重 ⇒ 读数被核心段（alpha ≈ 0.996）拖到 0.38。逐像素求比值就没有这个偏。

**行剖面**（从 PNG 直接量，`a = (1−tr)/0.647`）：`row 0 → 0.014` · `row 24 → 0.406` · `row 48 → 0.959` · `row 56..160 → 0.99~1.00` —— 羽化带约 **48 行**（≈ `7/9 × 39.5% × 167 = 51` 行），**与 Sliced 映射逐格吻合**；左右方向均匀（0.35–0.38），也没有多余的内缩。

⇒ **底板本身画得对**：平均 alpha `0.833` vs 原版映射 `0.830`（**差 0.003**）；透过率 `0.461` vs 期望 `0.463`（**差 0.002**）。

### 3·3 路 B 的 `0.906 / 0.927` 是什么

`AssertTextBg` ④（`CardBaseDemo.cs:1171-1177`）跑在 `Run()` 的 **:309**，`ProbeTextBgDiff` 跑在 **:326**。两处的 `px` 矩形**逐字相同**（`:3256` 与 `:4478` 都是 `x864 y559 w192 h167`）⇒ **不是「矩形取错」**。

但两帧的**背景亮度差了 3 倍**：④ 的线性读数 `开 0.04035 / 关 0.04452`（日志 `:3269`，`关` = 该矩形内的场景背景 = **0.0445**）vs 新探针同一矩形 `关 = 0.1284`。也就是说 **这两次量的不是同一个渲染状态**，而且 ④ 那一帧里这一层**只压暗了 7–9%**（若真是 0.83 的 alpha，`关 0.0445` 应掉到 `≈0.0205`）。⇒ **④ 那一帧里这一层没有正常合成**（被盖 / 队列不对 / 未就绪），**不能拿它当「这一层的强度」**。

⚠️ **最后一环没钉死**（见 §五）：本笔禁令不跑 Unity，只能确定「不是矩形错、不是画面错」，不能确定 ④ 那一帧到底是什么盖住了它。

### 3·4 裁定与建议（**待用户拍板，本笔一个数都没改**）

1. 🔴 **不要动 `TextBgAlpha`（`CardView.cs:833` 的 `0.647`）** —— 它就是原版 Image 的 `m_Color.a = 0.64705884`；改它会让画面**真的**偏离原版。
2. 🔴 **不要动贴图 alpha** —— 贴图是原版资产 `Card_Text_smooth_background`；渲染出来的平均 alpha `0.833` 与按原版 Sliced 映射算出来的 `0.830` 只差 0.003。
3. ✅ **要改的是仪器（不是美术）**：
   - `ProbeTextBgDiff`（`CardBaseDemo.cs:1759-1773`）与 `AssertTextBg` ④（`:1171-1177`）的估计量都从 `Σon/Σoff` 换成 **`mean(on_i/off_i)`**（逐像素透过率再平均）—— 这样它直接就是「这块 quad 上的平均 alpha」，**背景不均匀也不再偏**。
   - 换完之后，④ 可以把量级那半**重新收回到原版带 `[0.403, 0.523]`**（中心 `0.463`；实测 `0.461` 在带内），不用再挂着「只断画了没有」。
   - 顺手把路 A 那个「sRGB 台阶比值」也换成「先各自线性化、再求比值」（现在那条把 sRGB 比值当线性用，约 0.43 里有这一层误差）。
4. ⚠️ 若还要保留 `AssertTextBg` ④ 在 :309 那一刻量，**先查它那一帧为什么只压暗 7–9%**（渲染队列 / 卡片实例状态），否则它测的永远是「另一个状态」。

## 六、顺手发现

1. **影子探针（把旧提交的 `RuleEngine/Core` 编进一份临时 `ruleprobe`）是重钉归因的通用工具** —— 它能把「基线过期」与「真回归」**逐卡**分开，代价约 3 分钟（拷源码 + `dotnet build` 两次）。本笔已把方法写进 `PlayProbe.cs` 常量上方的注释，下次重钉照做即可，⛔ 别再「红了就重钉」。
2. **`ratio-of-means` 这个坑不只 `A1934` 有**：任何「拿开/关两帧求透过率」的探针，只要**背景在被测矩形内不均匀**，都会被它带偏。`AssertRarityGem` / `AssertFaithCostIcon` 那几条渲图判据如果也是这个形状，值得顺手扫一遍（它们目前只断「亮不亮」，影响小）。
3. `_tmp_view/cardbase_textbg_1021.log` 的 `:3269`（④ 的 0.906）与 `:4478`（探针的 0.378）**在同一个 run 里**，两条都自报「线性透过率」，一个 0.91 一个 0.38 —— 光看日志会以为画面自相矛盾，实际是**估计量 + 帧状态**两件事叠在一起。建议以后日志里把估计量名字打出来（`ratio-of-means` / `mean-of-ratios`）。
