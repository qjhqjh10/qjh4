## 一、`A1262` · CJK 行盒残差（本件唯一真活）

### 1·1 结论

**原版用的是哪份字体资产、行盒是多少 —— 两条都查到了：**

| 项 | 原版（判据） | 我们（旧） | 新（应为） |
|---|---|---|---|
| 字体资产名 | `NotoSerifCJK-Regular SDF`（`bundle_fonts_assets_all`） | `Resources/Fonts/NotoSerifCJK-Regular SDF.asset` | 同名（不必改） |
| 家族名（TTF 面） | **Noto Serif CJK JP** | **Noto Serif CJK SC** | JP（见 §六·1） |
| `m_FaceInfo.m_PointSize` | 50 | 50 | 50 |
| **`m_FaceInfo.m_Scale`** | **0.9** | **1** | **0.9** |
| `m_FaceInfo.m_LineHeight` | 71.85 | 71.85 | 71.85 |
| `m_AscentLine` / `m_DescentLine` | 57.55 / −14.3 | 57.55 / −14.3 | 同 |
| **face 行盒**（`lineHeight ÷ pointSize`） | 71.85 ÷ 50 = **1.437 em** | 1.437 em | 1.437 em（不变） |
| **有效行盒**（face × `m_Scale`） | 1.437 × 0.9 = **1.2933 em** | 1.437 em | **1.2933 em** |
| 同一把原版框高下的收敛字号 | `Timer` **38**（= `m_fontSize` = max，不缩）· `Victories title` **53.5** | **36.851** / **48.111**（被竖界压） | 预期回到 **38 / 53.5** |

**为什么 `m_Scale` 是「有效行盒」的那一格**（判据 = 工程自带包源码，不是推断）：
`Library/PackageCache/com.unity.ugui@27635d171b1a/Runtime/TMP/TMP_Text.cs:4188/4190`

```
adjustedScale = m_currentFontSize * smallCapsMultiplier / fontFace.pointSize * fontFace.scale * orthographicMultiplier;
elementAscender  = elementAscentLine  * currentElementScale;   // TMP_Text.cs:4391
elementDescender = elementDescentLine * currentElementScale;   // TMP_Text.cs:4396
textHeight       = m_maxTextAscender - (m_maxLineDescender - m_lineOffset);   // TextMeshProUGUI.cs:3387
```
⇒ 一行字的行盒 = `(ascentLine − descentLine) / pointSize × faceInfo.scale` = **1.437 × 0.9**。
（`TextMeshPro.cs` 与 `TextMeshProUGUI.cs` 这一段逐字同构；我们用世界空间 `TextMeshPro`，只多一个 `isOrthographic` 常数，不影响**比值**。）

### 1·3 我们这一侧的口径（⛔ 别把两个数混着用）

- **由资产字段算**：face 行盒 = 71.85 ÷ 50 = **1.437 em**（`Resources/Fonts/NotoSerifCJK-Regular SDF.asset:129-150`，`m_Scale: 1` 在 `:134`）。
- **W58 那组读数**（`1.5170 / 1.5252 / 1.5470 / 1.5252`，判据 → `普查产出_第十一会话/D1_九条红诊断.md` §证据 A）
  量的是「**原版框高 ÷ 我们收敛后的字号**」= **渲出高**口径（含字形外扩），与 face 行盒**不同源**，
  ⛔ **不能拿 1.52 去减 1.437**（那 0.08 em 的差本件没查清，见 §七）。
- **外推**：同一管线里 `m_Scale` 是**纯乘子** ⇒ 改成 0.9 后这组读数会是 **1.517 × 0.9 = 1.365**，
  而原版那一侧的上界是 `55.905 ÷ 38 = 1.471`（`38` = 原版 `m_fontSize` = max）⇒ **装得下、不再被竖界压**
  ⇒ `Timer` / `Victories title` 会**重新收敛到原版上限 38 / 53.5**（现读实得 36.851 / 48.111，差 −3.0% / −10.1%）。

### 1·4 影响面（为什么必须单独一批，不能顺手改）

- **全部 CJK 站点**（`A1024③` 那一批 ≈510 站 + 默认面）的实渲字号会统一缩到原版那一档 ≈ **−10%**。
- 换算链是**实测**的、会自动跟：`TmpFont.WorldGlyphPerFontSize`（`Core/TmpFont.cs:306`，量 `'国'` 的 `textBounds`）、
  `Label.OneLineBoxWorld()`（`Battle/Label.cs:2015`）⇒ 版面/VAlign 的派生量不用改常量。
- **会跟着动的是「期望值是 CJK 像素字面量」的断言**：`FontSizeToPx*` 182 处 · `FontPxNow` 109 处 ·
  `RenderedPx` 87 处 · `WorldW/H` 644 处（全仓 `--include=*.cs` 计数，含非断言站）——
  **要逐个判「这条期望值是从原版来的（不动）还是从我们字体量出来的（跟着动）」**。
- ✅ **不失效的两处**：`A1178` 的下限 `原版框高 ÷ 1.55em`（改完 `1.365 < 1.55` 仍然过）；
  `Battle/Label.cs:2165` 的 VAlign 三比值走 `faceInfo` 的**比值**（`scale` 在分子分母里约掉）⇒ 不变。
