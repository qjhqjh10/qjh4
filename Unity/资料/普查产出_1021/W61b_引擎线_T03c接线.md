## 1. 结论（一句话）

**四道队列真正接进引擎了。** `ActionQueue` 从「有原语、零消费点」变成：
**所有 ability 层触发只入队**（`FireTriggerAt` / `FireBoardWhenListener` / 三个广播跳 /
回合起止三段 / 部署触发 / 灵魂石 / 信仰 / 第三张牌 / 「被这套打过的」/ 死亡结转 / 死亡链），
**顶层动作**（出牌 / 战术 / 攻击 / 回合起止 / 抽牌 / 伤害 / 免费部署 / 主动技能 / 替代行动 / 收集）挂 `ActionScope`，
退出时按 **Interrupt(2) → Instant(1) → DelayedInstant(3) → Player(0)** 取空队列、同 FIFO。
`ruleprobe` 侧 `TriggerPriority()` 也读到真值了（现读 4 张非默认卡）。

**行为变了（这是本批的目的，也是唯一一类变化）**：一次出牌/一次攻击里产生的触发，
**不再在中途同步递归结算**，而是排到这条动作**之后**按道序结算 —— 正是原版
`AddAutoActionToQueue` + `Update` 的形状（判据报告 §2.3 / §2.4）。

## 6. 🔴 泵点口径 / 与原版不同的选择（逐条列死）

### 6.1 泵点口径（= 本批的施工决策，判据报告 §6 第 3 条把它留给施工方）

原版：`Update` **每帧最多取一条**。我们没有帧循环（铁律：批处理下没有帧循环）。

**本批的映射**：**在「一条顶层动作结束」这个边界上把队列取空**（`ActionScope.Dispose` → `PumpActionQueues` → `while (!Resolving && TryDequeue)`）。

**理由（可核）**：
- 取出的**次序**与原版**逐字相同**（2→1→3→0 循环、同道 FIFO）。帧间隔只是「两条之间隔多久」，
  纯规则引擎里**不可观测** —— 表现层读的是 `ctx.Signals` 的**序列**，序列本身不变。
- 原版每帧都泵 ⇒ 玩家**点得动的时候队列必然是空的**（`ActionsInQueue` 为真时输入层不该放行）
  ⇒ 「先攒到边界再取空」与「每帧取一条」在**动作序列**上等价。
- 泵点集合 = **14 个 `BeginAction` 调用点**（**13 个入口名**，其中 `DeployFree` 两处）—— 🔴 **2026-10-21 就地订正（铁律 5 · 审查代理 R 现核）**：原文写「13 个顶层入口」而同一句清单列了 14 项，审查按代码数出 `RuleCore.cs:1418/1965/2526/3233/3959/4118/5263/7124/9266/9454/9559/9664/9924` + `EffectResolver.cs:1662` = **14** 处。漏一个泵点 = 静默丢动作，这个数不能写错（本轮已查出 `BattleScene.cs:32898/32905` 两条 `ResolveAtTurn` 调用点**没有泵点** ⇒ `Gun Drone` 2 伤不结算）。清单：`PlayCard` / `PlayTactic` / `BeginTurn` / `EndTurn` / `Draw` / `ApplyDamage` / `DeployFree`×2 / `DeclareAttack` / `UseAbility` / `UseOathAbility` / `UseFaithAbility` / `UseAlternative` / `CollectWaystone`。**嵌套调用一律不泵**（`Resolving` 闸）。
