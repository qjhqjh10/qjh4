## 一、商店左栏 VLG 与原版不符 —— 已修

### 1.1 结论

原版 `Shop Menu Variant/Tab Buttons` 的 `VerticalLayoutGroup` 是 **`pad = 0,0,20,0` · `spacing = −20`**，
不是基类缺省的 **`padTop = 120` · `spacing = 0`**：

| 项 | 原版（解包现读） | 改前（我们） | 改后（我们） |
|---|---|---|---|
| `m_Padding` | **0,0,20,0**（顶 20） | 0,0,120,0（吃基类缺省） | 覆写 `BarPadTop = 20` |
| `m_Spacing` | **−20** | 0（`TabBtnH * i` 写死） | 覆写 `BarSpacing = −20` |
| 首键顶边 | **90.94**（70.94 + 20） | 190.94 | **90.94** |
| 步长 | **160**（180 − 20，相邻两键**重叠 20 px**） | 180 | **160** |
| 键高 / 键宽 | 180 / 165 | 180 / 165 | 180 / 165（未动） |

### 1.4 新增的断言（`Editor/ShopScene.cs`，`Section("左栏 VLG：padTop / spacing …")`）

- 四颗键的**矩形**：`90.94..270.94` / `250.94..430.94` / `410.94..590.94` / `570.94..750.94`（x 一律 167.17..332.17）。

  必须是 `MainMenuSubmenuWindow`（= 两扇**不覆写** ⇒ 吃基类缺省），并钉死基类缺省 `120` / `0`。

    本宿主**不建那两扇窗**，所以这里拿不到它们的真实键矩形。
- 改坏法：删掉 `ShopWindow` 的两个覆写 ⇒ 首键红（差 100 px）、第 2 键起全红；把 20/−20 塞进基类缺省 ⇒ 反向断言红。

## 二、原版 UI 实际加载哪份 TTF —— 已有确凿判据（**回答 T07 的卡点**）

### 2.1 结论（一句话）

原版加载的是**随包发的那一份 4 面 TTC**（`NotoSerifCJK-Regular`，24,810,096 B，**md5 `776e130c2253fdbfc9e9dd827c71e8cc`**），
TMP 用的面 = **`m_FaceIndex = 0` = `Noto Serif CJK JP`**。

| `d:/4/Unity/MyGame/Assets/CardPresentation/Fonts/NotoSerifCJK-Regular.ttf`（工程在用的那份） | 23,613,200 · `0844582f…` | **单面 `Noto Serif CJK SC`**（name 表：`NotoSerifCJKsc-Regular` / `1.001;GOOG;…`） | ❌ **不是原版那一面**（SC） |
| `d:/4/_tmp_view/wfC/NotoSerifCJK-Regular-JP.ttf`（「抽出的 JP」） | 23,624,316 · `395466fc…` | 单面 `Noto Serif CJK JP` | ✅ **= 原版 TTC 的 face 0**（15 张表里 **14 张逐字节相同**；`head` 只差 `modified` / `checkSumAdjustment`，即单面化时重算的校验和） |

⚠️ 任务简报里把 `0844582f` 标成「游戏解包」、把 `395466fc` 标成「抽出的 JP」——**前者其实是【我们工程导入的 SC 面】**，
不是解包里那一份（解包里那份是 `776e130c`）。这一条建议订正到简报/台账里。

### 2.3 对我们工程的实际影响（给 T07 的判据结论）

- 我们工程现在那份 `Assets/CardPresentation/Fonts/NotoSerifCJK-Regular.ttf` 是 **SC 面**，
  `Resources/Fonts/NotoSerifCJK-Regular SDF.asset` 由它生成 ⇒ **汉字字形是简体（SC）变体，与原版（JP）不是同一套**。
- **度量不受影响**：两面（SC / JP）的 `head/hhea/OS2` 度量**逐值相同**（upem 1000 · hhea 1151/−286 · cap 729），
  ⇒ `Label.cs` / `DeckRuntime.cs` 里那套「行盒 1.437 em」的算式**不用改**；只有**字形轮廓**变。
- **字形差多少（实测抽样）**：抽 56 个常用汉字比轮廓 ⇒ **30 个不同**（`直骨化角火海道週類說説明値真…`）；
  对 CJK 统一表意区 20,971 个码位比映射 ⇒ **11,820 个映射到不同 glyph（56.4%）**。
  ⇒ 不是「理论差异」，是**过半汉字的字形会变**。
- **正确做法（等主对话拍板，本代理只查不改）**：把工程的源字体换成 **`395466fc`（JP，= 原版 face 0）**，
  重新生成 `NotoSerifCJK-Regular SDF`；⛔ 不要直接把 24.8 MB 的 TTC 塞进工程（Unity 的 TrueTypeFontImporter
  能否把 TTC 当 `m_FaceIndex=0` 导入未验，且体积 +1.2 MB）。

### 2.4 没查清的部分

- **`TMP Settings` 的字段是【AssetRipper 导出】读的，不是从 `resources.assets` 直接读出来的** ——
  那个文件（和 `sharedassets*`）**没有 type tree**（`read_typetree()` 616 个 MB 全失败），
  所以「`m_fallbackFontAssets` 列表 = [Roboto, Noto]」这一条**只能引导出工程**，没能用 UnityPy 逐字段复核。
- **运行时没读到「每个文本用的是哪份字体」**：`资料/原版参照图/Unity参照管线_0825/data/runtime_ui_dump_*.tsv`
  的列是 `path/name/activeSelf/activeInHierarchy/rect/pos/pivot/text/fontSize/color/image` —— **没有字体资产名这一列**。
- **Unity 对 TTC 的导入行为**（`m_FaceIndex` 在 player 里按第几面取）本机没跑过原版/没做导入实验 ⇒ 未验。
  但「原版包里就是 TTC + TMP 记着 `m_FaceIndex=0` + FaceInfo 名字是 JP」这三条是直读的。
