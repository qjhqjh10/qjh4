## 1. `★★ 交错：A 的 Slay 先落地`

### 分类：**β 实现缺陷**（不是断言错、也不是本批有意改动）

### 证据（逐跳）

1. **日志里的取消警告**（`ruleengine.log:118260`，就在那条红上面几十行）：
   ```
   [ActionQueue] **取消**一条待结算动作「W58ILBlaster·slay」…… 施放者「W58ILBlaster」已经离场
   （原版 `CardAbility.IsRightContext` 的 `Play(0)` 同样不结算；⚠️ 这一支是 `abilityContext=-1` 的**旧口径回退**…）
   ```
   —— 取消它的是 **`RequireActorInPlay` 那一支**（旧 `Play(0)` 口径），**不是** `A1` 新加的
   `RequireActorInPlayOrDying`（那一支的文案是「已不在棋盘上、也不处于「待死」」）。
2. **判点先后**：`Core/ActionPump.cs` 的出队复核段里，`else if (act.RequireActorInPlay && !UnitInPlay(...))`
   排在 `if (act.RequireActorInPlayOrDying && … !IsOnBoardOrDying(...))` **之前**，两者**同时为真**时
   前一支先 `continue` ⇒ 后一支永远轮不到。而 Slay 那一跳（`RuleCore.TryCreditKillCore`）
   **两闸都传了**（`FireTriggerAt` 的 `requireActorInPlay` ＋ `requireActorInPlayOrDying: true`）。
3. **原版判据（第一权威）**：`BattleManager__ResolveTriggerSlay.c:116-226` 在**出队时**判的是
   `CardScript__IsInPlayOrDying()`（`CardScript__IsInPlayOrDying.c:8-13`：`state ∈ {2,15,3,17,5}`）——
   **`waitingToDie(5)` 算在场**。`ActionQueue.cs` 自己的 doc 也写着「本条**不比** `RequireActorInPlay` 严」。
4. **离场时序**：凶手死于 `BACKLASH: Deal 4 damage to all enemies`（B 的反噬）。它死时
   `ctx.DyingThisAction.Add(u)`（`RuleCore.cs:8719`），而 `DyingThisAction` 的清理在
   **最外层 `ActionScope.Dispose`（泵完队之后）**（`Core/ActionPump.cs:124`）⇒ Slay 动作出队那一刻，
   它**应该**仍算「待死」。`IsOnBoardOrDying` 本来就把 `DyingThisAction` 算进去
   （`RuleCore.cs:9524`）—— 只是被旧口径那一支抢先拦掉了。

### 改动（`Core/ActionPump.cs`，出队复核段）

旧判回退支加一条前置：**传了 `RequireActorInPlayOrDying` 就不走它**，交给下面那道更宽、
且是原版明写的出队闸。

```csharp
else if (act != null && !act.RequireActorInPlayOrDying
         && act.RequireActorInPlay && !UnitInPlay(ctx, act.Actor))
```

同时把 `Core/ActionQueue.cs` 的 `RequireActorInPlayOrDying` doc 补上「两闸同时为真以本条为准」，
`ActionPump` 那段块注释补上同一条例外（铁律 5：文档=现状）。

## 5. 顺手发现（不算本批四条，如实记着）

1. **`RequireActorInPlay` 的语义错位（结构性，未改）**：它自称是 `Play(0)` 的近似，但原版的
   `Play(0)`（`CanTriggerAbility → IsRightContext`）是**入队前**的闸（`W63` 收口已搬进
   `EnqueueAbility`）；留在**出队**的这一支只对 `abilityContext == -1` 的载体生效
   （合成夹具卡 / 旧卡表 / 第二解析路）。真卡现在全带 v14 `abilityContext`（探针现读：157 卡 / 170 条），
   ⇒ 这一支实际只影响夹具与「数据缺列」的卡。**今天唯一被它误伤的家族是 Slay**（已修）；
   其余关键词若哪天在缺列卡上走到，仍会比原版**更严**。没有判据说它该在出队，建议后续统一收口
   （本笔记账，不改：超出 F1 白名单判据范围）。
2. **`DyingThisAction` 的生命期是「最外层动作」**，而 Slay 的出队闸依赖它 —— 这层等价关系
   （原版「`UnitDeath` 协程跑完之前」↔ 我们「一条顶层动作」）成立的前提是**同一次攻击/结算不跨顶层动作**；
   一旦哪天把某条触发挪出外层 `BeginAction`，Slay 会在「跨顶层动作」的格子上重新被取消。已在报告里钉着。
3. **`LogTail(ctx, n=6)` 只给最后 6 条**（`RuleEngineTest.cs:2021`）⇒ 从失败文案里反推队列次序会漏掉
   前面的条目（本次我一开始就被这 6 行误导过一次）。要查次序别只读 `⟪日志⟫`，配合 `[ActionQueue]` 警告一起看。
4. **同一课在 A1688 上又出现了一次**：改了实现（删同动词闸）却没回来改钉旧行为的断言 + 方法 doc；
   与 `CLAUDE.md` 铁律 5「发现记错了就地改掉」同族 —— 改判据时要 grep 断言里的旧措辞。
