## 五 · `AbilityContextOfAbilityV14`：改前 / 改后的**实际判定**

### 5·1 实测读数（离线探针，同一份 `Core/`，不跑 Unity）

做法：在 `%TEMP%` 下建了一个**仓库外**的临时 net8 工程，显式编译
`RuleEngine/Core/*.cs` + `Data/CardDatabase.cs` + `ruleprobe` 的 `Stub.cs`，直接调真 API。
**「改前」= 把那份副本里的两个 `case` 删掉再编一次**（仓库里的文件一个字节没动）。
「改前」这一列**不是推的**，是把 `tn` 传 `null`（= 改前 `TriggerNameOfWhenKind` 的返回值）真跑出来的。

| 卡 | `abilityContextsVersioned` | `AbilityTriggerPriority(null)` | `AbilityTriggerPriority(名字)` | `ctx` 改前（`tn = null`） | `ctx` 改后（`tn = 名字`） |
|---|---|---|---|---|---|
| `SW20` | `true`（池 v21） | 1 | **1** | **-1（未知）** | **0（`Play`）** |
| `SW35` | `true` | 1 | **1** | **-1** | **0** |
| `SOR38` | `true` | 1 | **1** | **-1** | **0** |

⇒ ① **车道（`ListenerLane`）零变化**：三张卡都**没有** `abilityTriggerPriority` 列，
`CardDef.AbilityTriggerPriority` 对查不到的名字回 `DefaultTriggerPriority = 1`（`CardDef.cs:1565-1570`）
—— 与 `triggerName == null` 时那条缺省**同一个值**。
⇒ ② **`abilityContext` 确实从 `-1` 变成了 `Play(0)`**（`RuleCore.AbilityContextOfAbilityV14` 的 ② 跳：
`v14+ 且认得出 trigger 名 ⇒ 缺行 = Play(0)`，`ActionPump.cs:339-350`）。

### 5·2 这个 `0` 会不会真的开始生效？——**不会（今天不可达）**

全仓 `AbilityContextOfAbilityV14(card, <来自 TriggerNameOfWhenKind 的名字>)` 的调用点**只有一处**：

```csharp
EffectResolver.PendingDeathAllowsListener  (:8150 → 改后现读 :8174)    ...
    if (!ctx.IsPendingDeath(u)) return true;
    if (!preCall || kind != WhenEventKind.Attack) return allowPendingDeath;   // ← 这两族在这里就返回了
    int actx = AbilityContextOfAbilityV14(u.Card, TriggerNameOfWhenKind(kind));
```

`GetsHuntMark` / `GainFaith` **永远不等于** `WhenEventKind.Attack` ⇒ 那行**读不到**。
另外三处也不受影响：

- `FireBoardWhenListener` / `BroadcastPersistentWhen` / `BroadcastHandTrapWhen` 的 `EnqueueAbility`
  **根本不传 `abilityContext`**（`abilityContext` 缺省 = 未知 ⇒ 泵点回退旧口径）；
- `FollowUpSchedulerOf(card) == TriggerNameOfWhenKind(kind)`（`:8199`）—— 调度表里只有
  `ThisCardPlayed` / `OtherCardSpiritStone` / `Regiment` / `Strike` / `Artifice` / `Mob` / `OtherCardPlayed`
  七个值，**没有**这两个名字（`EffectResolver.cs:6233-6254` 现读）；
- `RuleCore` 的 `_kwTriggerName = TriggerNameOfKeyword(keyword)` 走的是**关键词**那一套（21 条），
  `"gethuntmark"` / `"gainfaith"` 不在里面。

### 5·3 结论与风险

- **不需要加任何例外**（今天这两族的 context 一个字节都没被读）。
- **将来若把 `PendingDeathAllowsListener` 放开到所有 kind**（那是 `W63` 的范围，不在本批）：
  这三张卡会被判成 `Play(0)` = 「必须在场、且不是待死」。这**不是「比原版严」**——
  池是 v21，生成器 `ability_contexts_of()` **只落非 0 行**（`ActionPump.cs:311-333` 的判据），
  「没有这一列」在真值上就**等于** `Play(0)`；三张卡的 SO 里那条 ability 的 context 就是 0。
  ⇒ ⛔ 别在放开的那天为这三张卡补「例外值」；要改先证 `IsRightContext` 的建模对得上
  （`CardAbility__IsRightContext.c` 的 `Play(0)` = `IsInPlay && !EnoughPendingDamageToDie`）。
- **残留风险（如实记）**：我们没跑过「监听者被打成待死时，huntmark / faith 那一拍还响不响」的实机；
  今天的代码**一定响**（没有 context 闸）。原版按 `Play(0)` **不该响**。这是 `W63` 的欠账，
  **本批没改**、也不该在映射这一层偷偷补。
