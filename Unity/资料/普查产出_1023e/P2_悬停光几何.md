## 一、分类

**(α) 几何确实该是 4.4281，是「量法」算错了 —— 但错不在并层本身，而在那个自检属性用了一把
会被视口裁切污染的尺子。** 不是 (β)（不需要两套几何），更不是 (γ)（原版判据就是 4.4281）。

一句话：**并层之后 `OutlineQuadSize` 量的还是「渲染包围盒」，而收藏页的卡是带视口裁切的 ——
`CropLayer` 把软光/影那一层的 `sharedMesh` 换成「按视口裁过的副本」，`MeshRenderer.bounds`
量到的是「视口里还剩多少」，不是原版节点的 `m_SizeDelta`。**

### 为什么并层之前是绿的（这条很重要，别当成「并层弄坏了它」）

旧实现在 `_outlineLayer != null ? _outlineLayer : _shadowLayer` 里**优先量专用层**，而专用层是
**懒建**的（`EnsureOutlineLayer()`，第一次真的要亮描边时才建）—— 建它的时候 `ApplyClip` 早就跑完了
⇒ **那一层从没被裁过**，`bounds` 永远 = 4.4281²。

也就是说：那条老断言之所以绿，是靠**专用层缺了一个本该有的裁切**。
反过来看，那是 `outlineGlow` 层的一个真 bug：那圈 6² 的 SDF 光会**画到滚动视口外面**
（同一段自检 `CollectionScene.cs:5845-5875` 就是在测「影子的溢出必须被视口裁掉」）。
并层顺手把这个 bug 也消掉了。

### 数字对账（这一步把假设锁死）

- 卡单位 → 像素：`510.4 px ÷ 4.4281 = 115.27 px/卡单位`（`510.4` 出自上面那条已有断言）。
- **纵向**：上沿被裁 `155.9 − 94.2 = 61.7 px` = `61.7 ÷ 115.27 = 0.5354` 卡单位
  ⇒ 预测高 `4.4281 − 0.5354 = 3.8927`，**实测 `3.8923`**（差 0.0004 卡单位 = 0.05 px）。
- **横向**：实测宽 `3.5495` ⇒ 被裁 `0.8786` 卡单位 = `101.3 px`。
  按 5872 行那句「左沿 213.6 vs 视口左沿 330.2」应是 `116.6 px` ⇒ 预测 `3.4165`，与实测差 **15.3 px**。
  ⚠️ 这条**没对到毫厘**：那句数是在 A181 那一段「`SetOffset(0)` + 重新 `Shift`」的态下量的，
  而悬停那一段的滚动/裁切态不保证逐像素相同。**方向与量级一致、Y 轴逐位吻合**，足以坐实「是裁切」；
  但「横向到底为什么差 15px」**没查清**（要跑 Unity 打一行 `CropLayer` 的 `lx1/lx2` 才说得准）。

## 三、改动

### 1) `Core/CardView.cs` — `OutlineQuadSize` 改成量**设计网格**（`:2624` 起）

```csharp
var mf = mr.GetComponent<MeshFilter>();
var mesh = mf != null ? mf.sharedMesh : null;
for (int i = 0; i < _crops.Count; i++)
    if (_crops[i].mr == mr && _crops[i].original != null) { mesh = _crops[i].original; break; }
if (mesh == null) return Vector2.zero;
var bs = mesh.bounds.size;
var ls = mr.transform.lossyScale;                 // 层 → 世界
var rs = transform.lossyScale;                    // 卡根 → 世界
float kx = Mathf.Abs(rs.x) > 1e-6f ? Mathf.Abs(ls.x) / Mathf.Abs(rs.x) : Mathf.Abs(ls.x);
float ky = Mathf.Abs(rs.y) > 1e-6f ? Mathf.Abs(ls.y) / Mathf.Abs(rs.y) : Mathf.Abs(ls.y);
return new Vector2(bs.x * kx, bs.y * ky);
```

- **①** 被裁过的层回到 `_crops` 里那份**原件**（整层被裁到视口外那一档 `_crops` 只记 `mr`/`wasEnabled`、
  没有 `original` ⇒ `sharedMesh` 本来就是原件，照样对）。
- **②** 乘「层 → 卡根」的缩放（两边 `lossyScale` 之比），**不再过世界包围盒** ⇒ 卡转过 90° 也不会被外接盒撑大。
- **没删任何东西**：`OutlineMat` / `ClearOutline` / 并层那套（L1 的改动）原样保留；只换了这一个属性的量法。
- 语义变严了一点点（**唯一的语义变化**）：以前「转过 90° 的卡」会被 AABB 撑大，现在量的是设计尺寸 —— 那是修对，不是回退。

### 2) `Editor/CollectionScene.cs` — ③ 那一块加「灭自证」4 条（`:7889-7910`）

期望值**一个都没改**（仍是 4.4281 / 容差 0.02）。

## 四、断言（怎么才会红）

| # | 断什么 | 怎么才会红（逐条可执行） |
|---|---|---|
| ★③a | 悬停光 quad 宽 = 4.4281（原断言，未改） | 把 `OutlineQuadSize` 里的 `mesh` 取值删掉、写回 `mr.bounds` ⇒ 这张被裁的卡量成 3.5495 ⇒ **红** |
| ★③b | … 高 = 4.4281（原断言，未改） | 同上 ⇒ 3.8923 ⇒ **红** |
| **前提** | 那一刀真的落下去了（`view0.Clipped`） | `SetClip` 被删 / 被改成跟随节点解析以外的空实现 ⇒ **红**（并明示后面的绿是假绿） |
| **★裁后宽** | **故意裁成 40×40 px 之后**，宽仍是 **4.4281** | 量 `mr.bounds` ⇒ 40px ÷ 115.27 ≈ **0.35** ⇒ **红**（这一条与上面两条**不是同义反复**：它把「裁切真会改网格」这件事变成可执行前提） |
| **★裁后高** | 同上，高仍是 **4.4281** | 同上 ⇒ 红 |
| **还原** | `SetClipFromTree()` 之后卡仍是裁着的（回到视口节点那一档） | `SetClipFromTree` 被删/抛 ⇒ `_clip` 停在 40×40 ⇒ 后面的 ④⑤ 组会连带红 |

**灭自证逻辑**：这套断言的前提（「这张卡真的被视口裁过、裁切真的会换掉网格」）由我们**主动制造**
（40×40 px 那一刀），不依赖外部滚动状态 ⇒ 退回旧量法**一定**红，而不是「碰巧绿」。
⚠️ 那 40×40 的矩形用 `LayoutSpace.ToDesignPixel`（= `ApplyClip` 里 `FromPixel` 的**逆**）算卡心，
⛔ 不是 `ToPixel`（108 px/单位那一份，两者只在 16:9 重合，见 `Core/LayoutSpace.cs:287-298`）。

**它为什么以前能绿（别被误导）**：并层前量的是懒建的专用层，那层**从没被裁过** —— 见 §一末尾。
