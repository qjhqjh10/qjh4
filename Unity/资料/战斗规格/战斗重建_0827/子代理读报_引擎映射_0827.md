## 1. Canvas 体系:主 Canvas(SS Camera)+BackCanvas(Overlay)+FrontCanvas(SS Camera overrideSorting)→Godot CanvasLayer

### Unity 侧机制(本机证据)
battlearena1 三个 Canvas 组件(**原始 JSON 逐字段**,`解包整理/07_场景/battlearena1/Canvas/`):

| Canvas(PathID) | GO | m_RenderMode | m_Camera | 关键字段 |
|---|---|---|---|---|
| Canvas_2572[主] | Canvas(983) | **1=Screen Space Camera** | PathID 1462(UI Camera) | m_PlaneDistance=100, sortingOrder=0 |
| Canvas_2575[Back] | BackCanvas(1198) | **2=Screen Space Overlay** | 无 | sortingOrder=0 |
| Canvas_2569[Front] | FrontCanvas(606) | **1=SS Camera** | PathID 1462 | **m_OverrideSorting=True**, m_SortingLayerID=2007638115(自定义层), sortingOrder=0 |
| Canvas_2574[门] | BattleDoors→Canvas(1055) | 2=Overlay | 无 | (inactive, EndBattlePanel 层) |

- UI Camera(`Camera/Camera_1462.json`):clearFlags=4(Depth only)、**FOV=40(透视!非正交** — F册已更正"正交"旧说法")、near 0.3/far 300、cullingMask bits=**32**(bit5=UI 层)、depth=0。位置参见权威表 L 节与规格表六节:pos(−343,0,−18.52)。
- CanvasScaler(`MonoBehaviour_4731.json` 挂 Canvas GO 983):`m_UiScaleMode=1`(Scale With Screen Size)、`m_ReferenceResolution=(1920,1080)`、`m_ScreenMatchMode=1`、**`m_MatchWidthOrHeight=0.0`(匹配宽度)**、m_ReferencePixelsPerUnit=100。
- GraphicRaycaster(`MonoBehaviour_4843.json`):m_BlockingMask bits=32(只被 UI 层阻挡)、m_IgnoreReversedGraphics=1、priority=0。
- SafeArea(自定义组件,`MonoBehaviour_5170.json`):m_safeZones=[RT 3498(Safe area BackCanvas), RT 2862(Safe area FrontCanvas)],applyWidth=1 / applyHeight=0(只处理刘海横向避让)。
- 层级次序(Unity):主 Canvas 先渲染 → BackCanvas(Overlay 在 SS Camera 之上)→ FrontCanvas(OverrideSorting+自定义 SortingLayer=在 Back 之上)。**权威表坑14 已明确:复刻需"两层级"(Back=overlay、Front=相机空间层)。**

### Godot 对应物
- **Godot 没有"Screen Space Camera Canvas / Overlay Canvas"之分**——所有 Control UI 都画在某个 CanvasLayer 上,CanvasLayer 始终是屏幕空间(与视口正交)。等价映射 = **CanvasLayer 数字分层**:
  - `CanvasLayer(layer=1)` = 主 Canvas 层(背景 Aspect Filler 等)
  - `CanvasLayer(layer=2)` = BackCanvas 层(HUD 左/右区、Replay、WaitText)
  - `CanvasLayer(layer=3)` = FrontCanvas 层(攻击选择器/Mulligan/聊天/弹窗/教程)
  - 或按 Unity 的 Overlay 语义排序:`layer` 越大越靠上(CanvasLayer API 本机核实:layer/visible/offset/transform,`extension_api.json` CanvasLayer 9 属性)。
- **本项目现状:全项目 0 处 CanvasLayer**(`grep CanvasLayer scripts/ autoload/ scenes/*.tscn` 全空)——现役 UI 是"单 Control 树 + add_child 顺序 + z_index 局部排序"(`main_menu.gd` 弹窗 `panel.z_index=60`;SceneTransition 遮罩 `z_index=4095` = **Godot z_index 上限 4096,旧值 10000 超限=从不生效**,scene_transition.gd:77 注释)。**战斗重建建议按权威表坑14 用 CanvasLayer 分层**(规模 = 战斗 HUD 三层+3D 世界),层内再用 z_index;若沿用现役"单树+z_index"也可以,但 popup/z_index 叠层必须 ≤4096。
- **CanvasScaler matchWidth→Godot 等效**(项目已定):`project.godot` = viewport 1920×1080 + `window/stretch/mode="canvas_items"` + `window/stretch/aspect="expand"` + theme `res://theme.tres`。即 UI 坐标=设计像素 1:1,窗口尺寸变化时 canvas_items 缩放 + expand 加宽可视区(左右扩展,不裁切);**与 Unity matchWidth 语义上等价但不逐像素相同**(expand 会在宽窗口显示更多横向区域,右缘锚元素贴窗口右缘)。原版 CanvasScaler 还有 m_ReferencePixelsPerUnit=100(UI 图片 1px=1 单位)与 Godot TextureRect 尺寸直给一致,无额外换算。
- Safe area:Godot 无内置;本项目桌面 1920×1080 无刘海,可直接忽略(原版按 applyWidth 只避让横向;若日后移动端需 `DisplayServer.get_display_safe_area()` 重设根边距)。
- **原版第 5 层(UI layer)的"3D 粒子穿 UI"技巧**与 CanvasLayer 的关系见 §8。

### 实现要点/坑
1. CanvasLayer 的子节点坐标 = 视口像素坐标(层无缩放);Control 树内坐标继续用锚点绝对值(§2)。
2. 4096 上限虽在 z_index;CanvasLayer.layer 无上限但保持小数字便于排布。
3. **Overlay vs SS Camera 的另一个差异**:Unity SS Camera 的 UI 由透视相机在 planeDistance=100 处渲染(严格说带微小透视);Godot CanvasLayer 永远是正交屏幕空间 → 所见即所得,反而更接近 Overlay 语义。对"UI 相机上的 FOV40 透视畸变"无需复刻(原版 UI 无可见畸变)。
4. 权威表坑14 已给结论:**Back=overlay、Front=相机空间层 → Godot 两 CanvasLayer(建议三层含主 Canvas)**;BackCanvas 在 Overlay 时它不含 UI 相机剔除问题,但**所有 Canvas(renderMode=2)与 3D 粒子同层共存的次序**由 §8 方案处理。

## 2. RectTransform(anchor/pivot/anchoredPosition/sizeDelta)→Godot Control 锚点

### Unity 机制(本机证据,已在权威表中)
- 每元素原始值:RT JSON `m_AnchorMin/Max`(4 浮点)、`m_Pivot`、`m_AnchoredPosition`、`m_SizeDelta`(如 TurnBtn: anchor(0.5,0.5) pos(2.81,0.19) size(130.70,80.43));且**子元素坐标沿 m_Father 链式累加**。
- 坐标系:Unity **y 向上**、Godot y 向下 → 必须翻转;anchoredPosition 是 **pivot 点相对锚点(拉伸时=锚点矩形中心)的偏移**。
- 本场景 3 类根偏移:全屏零偏移容器(Canvas/BackCanvas/Safe area LeftArea/RightArea)、锚在边角的锚容器(Left Anchor anchor(0,0.5) pivot(0,0.5) 100×100)、拉伸域容器(Clock anchor 0.3898-0.9502 拉伸,sizeDelta=(0.27,−11.19) 式奇值)——**权威表已用 chain_rect 实算全部绝对坐标,重建直接取绝对,不必重推**。

### Godot 对应物(本机核实 = F1 权威公式)
`Control` 属性:anchor_left/top/right/bottom、offset_left/top/right/bottom、position、size、pivot_offset(`extension_api.json` Control 63 属性+`set_anchors_preset`/`set_offsets_preset`/`set_anchor_and_offset`/`get_global_rect` 等方法全确认)。**F1 公式(Unity→Godot,1:1)**:
- anchor_left=ax0 / anchor_right=ax1 / **anchor_top=1−ay1 / anchor_bottom=1−ay0**(锚点 y 翻转)
- offset_left = apx−pvx·sdx;offset_right = apx+(1−pvx)·sdx;**offset_top = −(apy+(1−pvy)·sdy);offset_bottom = −(apy−pvy·sdy)**
- **pivot_offset=(pvx·w,(1−pvy)·h)**(旧公式 bug=`pivot.y*size.y`,F册 F7-4 已发现,unity_params_to_godot.py:147;Godot 4.7 另有 `pivot_offset_ratio` 新 API[本机核实])

### 项目代码惯例(本机核实)
- 全屏容器:`set_anchors_preset(Control.PRESET_FULL_RECT)` + 直接 add_child(全项目 413 处)。
- 绝对定位:`set_anchors_preset(Control.PRESET_TOP_LEFT)` 后写 offset_left/top/right/bottom(122 处),或直接 `position`+`size`(deck_builder/main_menu/settings 内大量使用——**注意 `position`/`size` 等价 set_position/set_size 但会清 offsets,不改锚点时安全;改锚点后必须重设**)。
- 伸展锚点:offset 用负值(如 filter 图标 `offset_left=10` `offset_right=-10` 表示 10px 内边距,deck_builder.gd:173-177)——Godot 的 offset 语义=相对锚边距离,与 Unity sizeDelta 不同但直观等价。
- Settings 0.9 缩放先例(使用地图·批次4 知识):原版设置根 m_LocalScale=0.9 全树缩放 → Godot:full-rect Control + `pivot_offset=(960,540)`+`scale=(0.9,0.9)`,内部坐标零改动(验证 (328,123)→(391.2,164.7)=权威 (391.3,164.8))。**战斗若有全树缩放(如 2DCard 运行时放大)照此方案**。
- **卡单位换算先例**:`sd_card.gd` `_pos(x,y)=Vector2(x*_scale, -y*_scale)`,卡内子元素用"卡单位×scale"(池格 112.5=150×0.75;大卡 250;权威值 fs0.34→int(0.34*sc) 等)。战斗手牌/场卡 = 直接复用此坐标体(2DCard 权威表三节数值全在)。

### 坑
1. **chain_rect 是权威**;树文件/dump 的"[x,y w,h]"是 anchoredPosition+sizeDelta 的局部表达(全树 EnemyDeck [-318,880]=1602-1920/1080-200 局部写法)——**权威表坑1/四-1 已明确,重建只认 chain_rect 绝对列**。
2. 07_场景 chain_rect 曾因 world-space Canvas m_LocalScale=0.01 报 0×0(F册 F7-3);本批权威表已修通(坐标全部实算)。
3. `set_anchors_preset` 的 `keep_offsets` 默认 false 会重置 offsets——先 preset 后写 offset(项目惯例)。
4. pivot≠(0.5,0.5) 元素(PlayerDeck pivot(0.5,0)、OffensiveButton pivot(0,0)、Left Anchor pivot(0,0.5)):换算时必须代入公式,不能"只翻转 y"。

## 3. 9-slice(m_Border)→NinePatchRect(border 顺序坑)

### Unity 机制(本机证据)
- 官方字段顺序:**Sprite m_Border=(左,下,右,上)**(Vector4.x=left, .y=bottom, .z=right, .w=top);本场景 9-slice 实例(坑56 权威表):`40k_bt_underbutton` 485×83 **border(240,0,240,0)**(错误横幅底,权威表 J 节引用)、`40k_popup` 359×336 **border(169,160,169,160)**(弹窗底 BattleSettingsPanel)、`40K_button` 489×107 **border(234,46,234,46)**(Resign 绿钮)等。
- Unity 侧 `m_Type`:0=Simple / 1=Sliced / 2=Tiled / 3=Filled(Image 组件,MB 4543 = m_Type 0 Simple);
- Filled=m_FillMethod/FillAmount(回合时钟环形填充、设置滑块等 UGUI 填充机制;battle 里 ClockManager.SetFillPercentage 用 Image Filled 做倒计时环[反编译字段级证据 ClockManager.cs:175])。

### Godot 对应物(本机核实)
- `NinePatchRect`(官方文档本机页+API):texture / **patch_margin_left/top/right/bottom** / draw_center / region_rect(图集子区!)/ axis_stretch_horizontal|vertical(AXIS_STRETCH_MODE_STRETCH=0/TILE=1/TILE_FIT=2)。
- **顺序转换(权威,C_册:28 + 坑56.2)**:
  - `NinePatchRect.patch_margin = (border.x, border.w, border.z, border.y)` = (L, T, R, B)——**即 Unity (L,B,R,T) → Godot (L,T,R,B)**,`unity_params_to_godot.py --border l,b,r,t` 直出。
  - Button 版(带九宫格底图的按钮)= **StyleBoxTexture.texture_margin_left/top/right/bottom**(deck_builder._mulligan_btn 等:12/6/12/6 惯例);**flat=true 时 StyleBoxTexture override 不渲染**(deck_builder.gd:128 实测注释;坑32/59)。
- **没有比 NinePatchRect 更近的等价物**(TextureRect STRETCH_SCALE/COVERED 均不能保留角);原版 Slice 类 Image 一律 NinePatchRect,Sliced 的 tiling=mode TILE。

### 项目惯例
- `_sb_tex(path, ml, mr, mt, mb)`(settings.gd:575)= StyleBoxTexture 九宫格封装(参数顺序 **L,R,T,B**,与 Unity 顺序不同——**写代码时最容易错**)。
- 已落地 9-slice 点:deck_info_popup 5 处/deck_builder 3 块/mode_select 2 处(坑56.2)。

### 坑
1. **参数顺序三重坑**:Unity JSON 是(L,B,R,T);Godot patch_margin 是(L,T,R,B);项目 _sb_tex 参数是(L,R,T,B)——三处顺序各不相同,引用数值时先用 `unity_params_to_godot.py --border l,b,r,t` 核对。

3. 贴图顶带 1-2px alpha=0 是设计值勿修(坑56.4,40k_deck_cardlist_bg 等)。
4. NinePatchRect 在 atlas 贴图上的子区 = `region_rect`(坑:图集 m_Rect 不可信→RenderDataMap,C册专题)。

## 4. 文字:TMP(TextMeshProUGUI)→Label + 项目字体 + "0x03 上标字符"

### Unity 侧机制(本机证据,MB 3971 = TurnText 'END TURN' 全字段)
TMP 字段名=机制(与 Unity legacy Text 完全不同,注意**勿按 m_Color 取色**):
- `m_text`='END TURN';`m_fontAsset`=PathID −8244042478085975641;**`m_fontColor`(TMP 真色,非 m_Color!— F册 F2 审计盲区已指出)**=(1,1,1,1);m_fontColor32(same);m_enableVertexGradient=0;m_colorMode=3。

- 字体资源(本机):战斗全部文本组件 666 个带 m_fontAsset(TMP)vs 仅 6 个 legacy Text;fontAsset PathID −8244042478085975641 = **TMP FontAsset "Asar-Regular SDF"**(`解包整理/10_字体/字体资源/MonoBehaviour/Asar-Regular SDF.json`,source GUID 5e30571fc9ef0cd439d276cca07ce673,atlas="Asar-Regular SDF Atlas.png" 在 10_字体/字体资源/Texture2D/);同目录另有**"NotoSerifCJK-Regular SDF"**(原版就带 Noto CJK TMP!)、Pragati-Regular/RobotoCondensed。材质变体("Asar Regular Almost white.json"=m_fontColor 4293848814≈奶白)**= 同字体不同着色**,与 m_fontColor 字段互证。
- **原版字体文件**:10_字体/fonts/NotoSerifCJK-Regular.ttf 与 resources/{LiberationSans,NotoSerifCJK-Regular,PerfectDOSVGA437}.ttf(Asar 的 .ttf 未解出,只有 SDF atlas+glyph 表)。

### 项目字体(本机核实)
- **项目 UI 字体 = `res://assets/fonts/NotoSerifCJK-Regular.ttf`**(theme.tres `default_font`,default_font_size=16;**该 ttf 就是解包原版 10_字体/fonts/ 的原文件**——中英混排一体字体,项目选择=原版资源优先)。

- **关键差距**:原版英文 UI 正字是 **Asar-Regular**(SDF),项目现在用的是 Noto 衬线——战斗中"(原版)字形观感"会有差异。**Asar 只有 SDF atlas+`Asar-Regular SDF.json` glyph 表(无 .ttf)**;可行路线(待定):从 TMP FontAsset JSON 的 glyph 表(m_GlyphRect/m_XAdvance)+SDF Atlas PNG 生成 Godot FontFile 位图字体(`FontFile` 支持 bitmap glyphs,API 本机核实 has_char/fallbacks 等)——**列为战斗重建"字体保真"可选项,工作量中等**;否则维持 Noto(项目现规,零成本,字面宽度与 Asar 不同→部分文字宽度需微调)。
- 文字颜色:全部用 `add_theme_color_override("font_color", …)`(勿用 modulate 染色文字,那是整控件);原版 m_fontColor 直译(如 ERROR 横幅暗红 (0.8019,0,0,1),权威表 J 节)。

### "上标 0x03"字符('12\x03'/'0\x03'/'1\x03' 等)
- Unity 侧事实[本机核实]:FaithText/SpiritStoneText/CostText/Melee/Range 数值文本的 `m_text` 字面含 U+0003(ETX 控制字符),同时 `m_parseCtrlCharacters=1`;对应组件是 TMP —— **本地无 TMP 源码**(Unity.TextMeshPro.dll 仅 146KB 引用壳),0x03 在 TMP 内部的确切割语义**未能本机核实**[知识未核实:控制字符由 m_parseCtrlCharacters 处理,具体渲染表现(上标小图标/特殊字形)未见);权威表中其描述为"上标字符(0x03)"。
- Godot 出现方式:Label 直接渲染 0x03 = 不可见/空格;RichTextLabel 有 `[sup]` 标签无原生"0x03 语义"。
