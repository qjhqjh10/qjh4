# Warpforge 解包项目 — 行为准则

## 🔒 安全红线（必须遵守）

1. **`~/.claude.json` 和 `~/.cc-switch/` 绝不同步网盘、不上传、不提交 git**——里面包含 API key 等敏感配置。任何备份/迁移/分享操作都不得包含这两个位置的文件。
2. **API key（MINIMAX_API_KEY 等）不写入任何项目文件、代码、文档、日志**——只从环境变量读取；不打印 key 值；配置里只用 `${MINIMAX_API_KEY}` 占位。
3. 对话中出现的 key 属于敏感信息，不引用、不重复、不写入任何持久化内容。

## 🎨 开发准则（用户指定）

- **🔴 完全读取说明书准则（用户 2026-08-22 指定，最高优先）**：做某个地方/场景/界面的任务时，**必须先派多个子代理完整读取该部分的说明书（`解包整理/说明书/`）与原始 Unity JSON（说明文件）**——不允许漏掉一点、不允许嫌麻烦只读简介/摘要。**在子代理完整读取全部说明书并彻底理解相关设置之后，才允许开始任务**；不要直接修改、不要跳读。行动顺序：**① 完全读取+彻底理解说明书 → ② 按说明书的指导/设置完全复刻 → ③ 复刻完成后再做优化调整**——在此之前只做完全复刻，不允许自作主张的"优化"。实操：主代理只读索引/摘要定位，子代理（可多只并行，按组件类别分工：MonoBehaviour/Animation/SkinnedMeshRenderer/材质/粒子/Camera+Light+RenderSettings 等）全文深读+按需问答；**子代理报的数值必须用原始 JSON/权威工具复核**（实测子代理 diff 有 2 处误报：FirePit α 键位、CrosshairLine active 状态）
- **🔴 问题=找说明书指导，禁止无依据反复修改（用户 2026-08-22 指定，最高优先）**：遇到问题（渲染不对/效果缺失/画面奇怪）时，**第一步是回去读该部分的说明文件（原始 Unity JSON），找到说明书里"应该是什么"**，与代码逐项对比定位差异；**没有说明书指导就不要动手修改**（本会话教训：没先读全粒子/动画说明书就自行多次调参，反复试错=浪费时间且修错方向）。**对"看起来合理、符合逻辑"的地方也要保持怀疑**——说明书里常有意想不到的设置（黑军团 LUT 是 identity 无分级、环境光在 SH probe 不在 Trilight、Chain 动画是形态键不是骨骼、unity 光强直通 Godot 会过曝），以原始 JSON 数值为准，不凭直觉。
- **优先使用解包资源**：游戏开发（UI/美术/特效/音效）优先从解包资源取用（12 大类 44.9 万文件，大量原版美术资源），只有解包真没有的才用视频帧裁图/生成图替代
- 新发现的资源用途及时写入 `解包资源使用地图.md`
- **探索发现及时落档**：任务执行中探索得到的新资源用途、布局/坐标换算/踩坑等知识 → 写入 `解包资源使用地图.md`（含"使用中的坑"清单）；任务进展、**步骤顺序调整**、新发现待办 → 同步更新 `项目任务文件.md`（含末尾"给新会话的情况说明"），不滞留到会话结束
- **解包资源使用核查（每任务后必做）**：每次完成任务后，检查**是否使用了解包资源、用在什么地方** → 之后检查 `解包资源列表清单.md` 是否需要更新（使用状态/位置/备注）。**清单目标：全部解包资源用上 = 项目完成**
- **资源使用说明书优先**：解包文件本身（`03_界面UI` 场景 JSON、`09_游戏数据` 定义/配置、`07_场景`、`08_预制体特效` 等）就是"资源怎么使用、用在哪里"的说明书——做 UI/界面/大厅还原时先系统检查解包里的说明文件，再动手实现，不依赖用户口述或视频帧裁图
- **复刻一致性准则（用户指定 2026-08-18，最高优先）**：本项目是对原版 Warpforge 的**复刻**，成果与原版一致（允许极小差异），不是"看起来像"。**完成/修改/优化任何部分前的固定流程**：① **先查资源**——该功能对应的解包资源在哪（速查 `按阵营资源索引.md`/`解包资源使用地图.md`/`解包资源列表清单.md`）② **再查说明书**——场景 JSON（GameObject/RectTransform/MonoBehaviour 布局/坐标/纹理引用）、预制体（组件组装）、定义数据、MonoScript（查 Warpforge_code 实现）③ **按说明书复刻**——按说明文件的布局/坐标/纹理/文字使用资源 ④ **缺失才替代**——只有解包真没有的（查缺失清单确认）才用替代资源并标注：**优先用 imagegen skill 生成类似图标/按钮（美观协调），禁止用视频帧/截图裁剪覆盖（生硬不美观）** ⑤ **改动前自查三问**——素材名字/用途与原版元素匹配吗（不是同类近似）？位置/尺寸按说明书坐标吗（不是拍脑袋）？质感/纹路是原版贴图吗（不是纯色块/无底纹）？⑥ **验收对照**——改动后用 vision 与原版（说明书还原预期/原版截图/视频帧）对比评分，确认一致才交付。**反例（禁止）**：用近似素材/自绘色块/自排布局替代原版资源；不查说明书直接按自己想法实现；用截图裁剪做按钮/图标。
- **说明文件（说明书）准则（用户指定 2026-08-18）**：**说明文件就在解包资源里**——`D:\2\解包整理\` 中有大量 Unity 序列化 JSON 文件（Sprite / GameObject / RectTransform / MonoBehaviour / Texture2D / SpriteAtlas 等类型），例如 `解包整理\12_主程序资源\Sprite\40k_DeckSelection_icon_FactionAstraMilitarum.json`。**这些文件写着什么图标、按钮、文字、区域应该放在什么地方、多大尺寸、怎么使用对应解包资源**：Sprite JSON = 图片尺寸/锚点/图集归属（m_Rect/m_Pivot/m_AtlasTags）；RectTransform JSON = 元素位置/尺寸/父子层级（anchor/pos/size/pivot）；MonoBehaviour Image/Text JSON = 用哪张贴图（m_Sprite PathID）、显示什么文字（m_text）、颜色/透明度；GameObject JSON = 界面层级结构（谁包含谁、active 状态）。**做任何界面/图标/按钮/排版任务前，必须先找到对应说明文件**，按其坐标/尺寸/纹理使用解包资源，不按自己想法排布。说明书查找途径：① 已解析产物 `Warpforge_tools/data/ui_layout/`（`菜单全树.md`=308 个根界面全景、`主菜单全树.md`、`battlearena1全树.md`、`主菜单聊天面板.json`、`卡组界面说明书.md`）② 原始 JSON 在 `解包整理/03_界面UI/`（菜单界面）、`07_场景/`（对战/主菜单场景）、`12_主程序资源/` 等目录 ③ 需要新解析时用 `Warpforge_tools/scripts/dump_scene_tree.py`/`ui_layout_parser.py` 重跑。
- **说明文件=原始 Unity JSON（用户指定 2026-08-19，最高优先）**：**"说明文件"指 `解包整理/` 下的原始 Unity 序列化 JSON**（`03_界面UI/菜单/`、`07_场景/`、`12_主程序资源/` 等目录中的 GameObject/RectTransform/MonoBehaviour/Sprite/Texture2D 文件），**不是整理文档**（`菜单全树.md`/`卡组界面说明书.md`/`要点文档`等仅作定位索引，**不得作为坐标/尺寸/贴图/文字的最终依据**——以原始 JSON 数值为准）。① **代码编写/修改/审查一律直接检查原始 Unity JSON**：任何界面元素的坐标（m_AnchoredPosition）、尺寸（m_SizeDelta）、锚点（m_AnchorMin/Max）、pivot（m_Pivot）、贴图（m_Sprite PathID→Sprite JSON→m_Rect）、文字（m_text）、颜色（m_Color/m_fontColor）都直接从原始 JSON 读取，**禁止自设坐标、拍脑袋排布**；发现"看起来怪/不美观/残缺" = 未按原始 JSON 布置，立即代码审查逐项对照。② **分辨率依据（2026-08-19 查证；2026-08-20 修正"直接照抄"错误结论）**：原版 CanvasScaler 参考分辨率 1920×1080（匹配宽度），当前项目 viewport 同为 1920×1080 → **分辨率相同、数值可直接换算（≠直接照抄）**。**m_AnchoredPosition 不可直接照抄进 Godot offset**：① Unity y 向上、Godot y 向下 → 必须 y 翻转（godot_top = 1080 - unity_top - h）② anchoredPosition 是 **pivot 点**相对锚点（锚点拉伸时相对**锚点矩形中心**）的位置，pivot≠(0.5,0.5) 必须修正（如 PlayerDeck pivot(0.5,0)）③ 子元素坐标相对父，需**沿 m_Father 链式累加** ④ 根元素（m_Father=0，如 Gacha/Forge/Packs Tab）的 anchoredPosition/sizeDelta 仍相对全屏 Canvas 有效（x+163.8 之类偏移不可丢）。**权威换算工具：`Warpforge_tools/scripts/chain_rect.py`**（沿 m_Father 链式累加 → Godot 绝对屏幕坐标；同名 GO 多变体必须用 PathID）。子代理/整理文档给的坐标一律用 chain_rect 交叉验证后再用（实测子代理报告有 2 处坐标错误、整理文档沿袭错误如 social 积分面板）。③ 审查验收：界面是否合格 = 与原始 JSON 逐项对照（位置/尺寸/贴图/文字），**"基本达标/无明显错误"不构成完成**——坐标没按 JSON 就是不合格。④ 整理文档与原始 JSON 冲突时，**以原始 JSON 为准**，并更正整理文档。
- **整屏截图审查准则（用户指定 2026-08-18，最高优先）**：**截图分析必须截取整个游戏画面（1920x1080 全屏），绝不截取部分区域/局部裁图作为审查依据**——局部分析会漏掉全局布局问题（重叠、错位、黑区分布、比例失衡）。审查时对整屏进行深度分析：① 以**游戏制作人的审美标准**评价画面——布局平衡（是否有大块空区/黑区/死区）、层级秩序（重要元素是否突出）、视觉密度（内容是否过空或过挤）、纹理质感（是否有纯色块/无底纹区域）② **逐区扫描**——顶部栏/侧栏/中央区/底部栏全部区域都要检查，找出：黑色死区、无纹理区域、缺图标按钮、元素重叠/错位/裁切、文字溢出/乱码/双语混排问题 ③ 输出结构化审查报告（区域清单+问题位置+严重度+修复建议）→ 修复 → 重新整屏截图 → vision 复验，直到整屏评分达标。截图脚本用 `tools_dev/shot_*.gd`（`get_root().get_texture().get_image()` 全屏保存），禁止手动裁剪局部再让 vision 判断。
