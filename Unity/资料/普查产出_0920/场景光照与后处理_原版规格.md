## 一、光源（平行光）

**做法**：`ArenaBuilder.ApplyLightAndAmbient`（原来是 `BuildSceneTail` 里的私有段）。

🔴 **根因（原来为什么一盏都没有）**：灯与环境光原本只写在 **`BuildSceneTail`** 里，
而那个函数**只在建独立战场场景时跑**；战斗场景走的是 `BuildContent`
（`BattleScene.cs` 的 `BuildArena3D`）⇒ **灯根本没跟过来**。
`BattleScene.cs` 全篇没有 `AddComponent<Light>`、也没有 `RenderSettings`，是一处**静默缺失**。
修法 = 把这两段挪进 `BuildContent`（那里本来就被声明为「两处共用的**唯一判据**」）。

**原版 arena1 实读**（解包 JSON + 实况探针**逐位一致**）：

| `m_Type` | 1（Directional） | `Light/Light_1605.json` |
| `m_Color` | (1.0, 0.95686, 0.83922) | 同上 |
| `m_Intensity` | 1.0 | 同上 |
| `m_Shadows` | `type=2`(Soft) · `strength=1.0` · `bias=0.05` | 同上 |

⚠️ **原来只写死 `LightShadows.Soft`、阴影强度从没搬过** —— 而原版 13 场的 shadowStrength

## 二、环境光 —— 🔴 两处都是错的

### 2.1 模式：原版是 **Flat**，不是 Trilight

**13 场全部** `m_AmbientMode = 3`（`AmbientMode`：0=Skybox · 1=Trilight · **3=Flat** · 4=Custom）。
出处：`07_场景/battlearena*/RenderSettings/RenderSettings_1604.json`（逐场一份，13/13 都是 3）。
**实况复核**：原版跑起来读 `RenderSettings.ambientMode` = `Flat`（见 §三）。

⚠️ `资料/索引与盘点/解包资源使用地图.md:716` 写着「AmbientMode=3 Trilight」—— **那条是错的**，
按「发现记错就地改掉」已一并更正。

### 2.2 颜色：运行时用的**不是**场景里那个值

🔴 **这是本轮最重要的一条**。静态场景里的 `RenderSettings.m_AmbientSkyColor` **会被运行时覆盖**：

```
EnvironmentConditionsController (m_IsActive: true)
  └ ScenarioEnvironmentConditionsManager (m_Enabled: 1)
      Awake() → ApplyEnvironment(defaultEnvironment, instant: true)
                → EnableEnvironment(so, true)
                    → ApplyAmbientColor(so, true)
                        → Shader.SetGlobalFloat(ambientColorBlendPropertyId, so.ambientBlend)
                        → RenderSettings.ambientLight = so.ambientColor      ← 就是这一句
                    → ApplyFog(so, true)
```

**出处（全量反编译 `d:/2/tools/decomp_full/`）**：
`ScenarioEnvironmentConditionsManager__Awake.c` · `…__ApplyEnvironment.c`（:13 调 `EnableEnvironment`）·
`ScenarioEnvironmentConditionSO__EnableEnvironment.c`（:35 `ApplyAmbientColor` / :36 `ApplyFog`）·
`ScenarioEnvironmentConditionSO__ApplyAmbientColor.c`（instant 支：`RenderSettings.set_ambientLight`）。
管理器实例：`07_场景/battlearena1/MonoBehaviour/MonoBehaviour_4688.json`（`defaultEnvironment` 指向外部 SO）。

**🔴 实况双场交叉验证**（原版跑起来用 SceneJumpShot 探针读，见 §三）：

| 场景 | 场景里的 `m_AmbientSkyColor` | 默认环境 SO 的 `ambientColor` | **实况 `RenderSettings.ambientLight`** | 跟谁 |
|---|---|---|---|---|
| battlearena1 | (1, 1, 1, **α1**) | (1, 1, 1, **α0**) | **(1, 1, 1, α0)** | **SO**（连 α 都跟） |
| battlearena3 | (0.6840, 0.9229, 1.0) | (0.8066, 0.9522, 1.0) | **(0.80660, 0.95225, 1.0)** | **SO**（逐位吻合） |

⇒ **运行时权威 = `defaultEnvironment.ambientColor`**。arena1 两值恰好相同（所以只看它分不出），
**arena3 才把它分开** —— 这就是为什么要跑第二场。

**13 场共 6 个不同的默认环境 SO**（逐场值见 §五）：

| SO 名 | 哪些场景用 | `ambientColor` | `ambientBlend` | `fogDensity` |
|---|---|---|---|---|
| `Ultramarines Default Enviromental Condition` | arena1 · astramilitarum · darkangels · emperorschildren · genestealers · sororitas · spacewolves · tauviorla（**8 场**） | (1, 1, 1, 0) | 0.0 | 0.0 |
| `Orks Default Enviromental Condition` | battlearena2 | (1, 0.935, 0.8632, 0) | 0.0 | 0.0 |
| `Necrons Default Enviromental Condition` | battlearena3 | (0.8066, 0.9522, 1, 1) | 0.0 | 0.0 |
| `Saim Hann Default Enviromental Condition` | aeldari | (0.9811, 0.9083, 0.8377, 0) | 0.0 | 0.0 |
| `Black Legion Default Enviromental Condition` | blacklegion | (1, 0.8322, 0.8066, 1) | 0.0 | 0.0 |
| `Leviathan Default Enviromental Condition` | leviathan | (0.9811, 0.8942, 0.8099, 1) | 0.0 | 0.0 |

⚠️ **13 场的 SO 全是 `ambientBlend = 0` / `fogDensity = 0`**（SO 的构造函数里那两项默认是 1.0 / 0.05，
是**作者显式改成 0 的**）⇒ 那个 shader 全局量不参与、雾全关。
⚠️ `ambientBlend` 只喂 `Shader.SetGlobalFloat`，`RenderSettings.ambientLight` 是**无条件**赋值的 —— 两件事。

### 2.3 `ambientIntensity = 0.41` 在 Flat 下**不参与**

**实况实测**：arena1 `ambientLight=(1,1,1)` → `RenderSettings.ambientProbe` 的 DC = **(1,1,1)**；
arena3 `ambientLight=(0.8066,0.9522,1.0)` → probe DC = **(0.6150811, 0.8947905, 1)**。
若 0.41 参与，DC 应是 0.41×。**⇒ Flat 模式下 Intensity 不乘进去**（Lighting 窗口里 Source=Color 时
Intensity Multiplier 会置灰，与此自洽）。

**probe DC = sRGB→linear(ambientLight)**（我逐位验算过：0.8066 → 0.61505 vs 实测 0.61508；
0.95225 → 0.89481 vs 实测 0.89479）。我们工程 `m_ActiveColorSpace = 1`（Linear），与原版同色空间。

### 2.4 🚫 `m_AmbientProbe` 那 27 个 SH 系数**不能用**

序列化里的 `m_AmbientProbe`：**13 场逐位完全相同**（DC 全为 `0.28913, 0.1833, −0.08031`，
`m_UseRadianceAmbientProbe = false`）⇒ 那是**天空盒烘出来的**，与逐场环境光**无关**。

🔴 **实况反证**：arena1 序列化 probe DC 是 (0.289, 0.183, −0.080)，**运行时读到的是 (1,1,1)** ——
Unity 按 Flat + ambientLight **现算**了。

⚠️ 旧的 Godot 移植笔记（`资源使用地图` 坑 47）说「单色环境光用 SH DC 三项」、并据此给黑军团取了
`(0.289,0.183,−0.080)` —— **那条已作废**：照它做会让 **13 场环境光变成同一个值**，而且方向也错
（B 为负、还被 clamp）。**就地更正。**

## 四、后处理 —— 整块原来没接

原版战场的后处理 = **`BoardCamera` 这个 GameObject 上挂的一个全局 `Volume`**
（`07_场景/battlearena1/MonoBehaviour/MonoBehaviour_4375.json`：`m_IsGlobal:1` / priority 0 / weight 1），
profile 名 `<场景> PostProcessing`（同目录 `Battle Arena 1 PostProcessing_63.json`），里面 **3 个 override**：

| 组件 | 值 | 我们接了吗 |
|---|---|---|
| **Bloom** | `threshold 1.15` · `intensity 5.0` · `scatter 1.0` · `maxIterations 6` | ✅ |
| **Vignette** | `color` 黑 · `center (0.5,0.5)` · `intensity 0.297` · smoothness/rounded 未打勾 | ✅ |
| **ColorLookup** | LUT `LUT Normal`（256×16）· `contribution 1.0` | ❌ **故意不接**（见下） |

🔴 **`ColorLookup` 的 LUT 是严格 identity** —— 256×16 条带按 16³ 展开、V 轴翻转之后，
**4096 个采样点与恒等映射偏差 0/255**。⇒ **不产生任何分级效果**，不搬那个贴图。
（判据脚本见本文末；LUT 本体在 `battlesharedresources_assets_all.bundle`
PathID 382974660631151556，`m_Name = LUT Normal`。）

🔴 **`skipIterations` 是废弃死值，不能抄**：URP 的 bloom pass 读的是 **`maxIterations`**
（`Runtime/Passes/PostProcessPass.cs:1342` 的 `m_Bloom.maxIterations.value`），
而 `skipIterations` 在 `Runtime/Deprecated.cs:324` 是 `[Obsolete(..., true)]` —— **没人读它**。
原版 Bloom 里 `skipIterations` 打了勾=6、`maxIterations` 没打勾（字段值也是 6）⇒ **生效值 = 6**。
**抄错字段 = 白抄**（这一条正是「名字像的那个不是生效的那个」那一类）。

### 4.1 🔴 开关：`renderPostProcessing`

原版 `BoardCamera` 的 `UniversalAdditionalCameraData.m_RenderPostProcessing = **1**`（开着），
`UI Camera` 是 `m_CameraType = 1`（**Overlay**）+ `m_RenderPostProcessing = **0**`。
出处：`MonoBehaviour_4374.json`（GO 348 = BoardCamera）/ `MonoBehaviour_4453.json`（GO 350 = UI Camera）。

**不开这个开关，上面那些值一个都不会生效** —— 和 `lensShift` 没开物理相机**同一个形状**
（「值都抄对了、就是没生效」）。

### 4.2 ⚠️ 已知差异（**没接**）：相机栈

原版是 **base（BoardCamera）+ overlay（UI Camera）** 的相机栈 ⇒ 后处理作用在**合成后**的整帧，
**HUD 也会被 bloom/vignette 影响**。
我们是**两台各自独立的 base 相机**（BoardCamera 画 `ArenaLayer`、HUD 相机清深度叠上去）
⇒ 后处理只作用在 3D 那层，**HUD 不带 bloom/vignette**。
改成 overlay 会动到刚调稳的取景/相机结构，**本轮没动**，如实记在这里。

## 六、战斗用哪个战场 —— 机制查清了，**表不在本地**

- **唯一决定点**：`decomp_full/SearchOpponentManager__StartBattle.c:57`

### 10.3 🔴 沿途修掉的三个**静默** bug（每个都会让产物「看着建出来了、其实不对」）

1. **dump 的名字解析会抢占 pathID**（`unity_scene_to_godot.py` 的 `load_go_dir`）。

2. **磁盘文件名是消毒过的**（`win_safe`：`\/:*?"<>|` → `_`，因为 `:` 在 NTFS 上是 ADS 流），

   **arena2 缺 obj 从 34 条 → 1 条**（剩的那条是 `Cache Stealth`，本来就该跳过）。

## 十二、`CandleFlame_*` 三个网格查证（2026-09-20，用户追问）

**原来记的**：「`CandleFlame_big` 类网格 `m_IndexBuffer = None`（**数据损坏不可导出**）」
（`d:/2` 侧的旧笔记 + 我在 §十 照抄了一遍）。**用户追问「是不是真的损坏、会不会是导出造成的」⇒ 查实如下。**

### 12.1 结论：**不是导出造成的；是资产本身就只有裸位置**

**A/B 对照（最强证据）** —— **同一个共享包、同一段读取代码**，能导出的与导不出的并排：

| 网格 | 顶点 | `m_IndexBuffer` | 子网格 `indexCount` | 非零通道 |
|---|---|---|---|---|
| `Candles 112`（**能**导出） | 75 | **576 字节** | **288** | 位置 · 法线 · UV · UV2 |
| `Candles 102`（**能**导出） | 162 | **1212 字节** | **606** | 位置 · 法线 · UV · UV2 |
| `CandleFlame_big` | 10 | **0** | **0** | **只有位置** |
| `CandleFlame_mid` | 74 | **0** | **0** | **只有位置** |

⇒ **读法没问题**（同一个包里别的网格索引/法线/UV 齐全），**是这三个资产本身如此**。
另两条旁证：
- 顶点缓冲 `m_DataSize` = **888 字节 = 74 × 3 × 4**，**逐字节吻合**（`m_Channels` 里只有 channel 0
  的 `dimension = 3`，format 0 = float32）—— typetree 读歪不可能吻合得这么准。
- `Mesh.export()` 抛断言，原因同一个（没有索引就构不出面）。
- 三条路径**互相印证**：dump JSON / UnityPy 直读**原始 bundle** / `export()`。

**⇒ 不要把「导不出来」写成「数据损坏」** —— 更准确的说法是「**这个资产的形态就是不能画三角形**」。

### 12.2 影响：**没有**（两条证据）

1. 那几个对象上的 **`ParticleSystemRenderer` 是 `renderMode = 0`（Billboard）、`m_Mesh = 0`**
   —— **根本不引用网格**。蜡烛火苗是**粒子**画的，不是这个网格画的。
2. 挂着的 `MeshRenderer` 在原版也是开着的，**但一个 `indexCount = 0` 的网格在原版里同样什么都画不出来**
   ⇒ **我们不缺任何原版会显示的东西**。
3. 直观验证：**我们的圣女战场预览里，左下 / 右下两排蜡烛与火苗是渲出来了的**。

**⇒ 不补救**（位置数据解得出来，但没有索引就无从知道三角形怎么连；而它本来就不显示）。

**症状**：圣女战场的地板是一块均匀灰 **(106,101,96)**（原版同一位置是红毯 (84,15,2) / 大理石），
而**13 场里只有这一场有这个问题**（中央下部亮度标准差 8.2，其余 15~42）。

**根因是两层叠在一起：**

1. **我们只给第 0 个材质**。`Floor` 原版有 **2 个材质**（第 0 个**透明**、第 1 个**不透明**），
   而 `mr.sharedMaterial = …` **只作用于子网格 0**，其余子网格拿不到材质 ⇒ Unity 套默认灰材质。
2. 🔴 **Unity 的 OBJ 导入器根本不切子网格**（2026-09-20 实测**两轮**）：
   ① 原文件只有 `g` 组、没有 `usemtl` ⇒ 导入成 **1** 个子网格；
   ② **补上 `usemtl mat_<i>` 之后仍然是 1 个**（诊断行照旧报「网格 1 个子网格 / 材质 2 个」）。
   判据就是构建时那行诊断：`Floor：网格 1 个子网格 / 材质 2 个`。

**合起来的症状**：整块地板按「透明」渲染（第 0 个材质），而 `Sororitas Ground Atlas` 这张图集
**九成是 α=0**（整图平均 α=21/255）⇒ **地板整片透掉**，露出后面的东西 = 那块均匀灰。

**修法（最后落地的那一版）—— 按组把 OBJ 拆成多个文件**：
- 生成器 `split_obj_by_group()`：把 `g <名>_<i>` 每个组连**同一段顶点块**写成 `<名>__sub<i>.obj`
  （几何无损；实测 `Floor` 拆出来 `5385 + 1790 = 7175` = 原文件面数**逐条对上**），
  清单里落成 `MeshEntry.subFiles`（与 `subMats` 一一对应）。
- `ArenaBuilder`：`subFiles.Length > 1` 时**一个子网格建一个网格对象**（`mesh0`/`mesh1`…，
  同一个 Transform），各配各的材质；单文件的老路一字未改。
- 生成器同时给清单带上**每个子网格的材质**（`MeshEntry.subMats`，顺序 = 原版 `m_Materials` 顺序）。
- ⚠️ **只对「原版这个网格真有多个材质」的才拆** —— 别的网格一律原样拷贝。
  （`Combined Mesh (root_ scene).obj` 有 31 个 `g` 组但渲染器只有 1 个材质，那种本来就
  「一个材质画全部」，拆了反而会多出没有材质的对象。）

**守卫**：构建时诊断（`子网格数 ≠ 材质数` 就报红）· `BattleScene.Run` 断言
（任何子网格材质为 `null` 就红）。**改完实测：13 场诊断 0 条不匹配**。

**影响面（诊断实测，不是估的）**：13 场里**只有 2 场共 6 条**真的多材质 ——
sororitas 的 `Floor` · tauviorla 的 `Energy Bar`（5 个对象共用那个 OBJ。
⚠️ 注意：**同一份拆出来的 OBJ 被多个对象复用** —— 拆文件是按「源 OBJ 名」做的，
`Floor__sub0/sub1` 在多个对象之间共享，不会重复拆）。
> ⚠️ **中途一个错数要记下来免得再犯**：我先按 OBJ 的 **`g` 组数**点，得出「29 个网格受影响」——
> **是错的**。`g` 组数 ≠ 渲染器材质数：`Combined Mesh (root_ scene).obj` 有 **31 个 `g` 组、
> 但渲染器只有 1 个材质**。**按渲染器材质数点，才是 6 个。**

### 13.1 🔴 **但地板那片灰没修好，根因仍未坐实**（如实记，别当已解决）

**拆完子网格之后，圣女战场的画面一个像素都没变**（中央下部仍 (106,101,96)、标准差仍是 8.2）
⇒ **那片灰不是第二个子网格造成的**。继续量到的是：

| 量了什么 | 结果 |
|---|---|
| 从相机往灰区中心打射线（`Floor.obj` 的 AABB + 相机参数） | **最近命中就是 `Floor` 网格本身**（t≈9.1），下一个是 `Altar Stairs`（t≈38） |
| 画面左上角 | 我们 **(146,169,190) 浅蓝 = 天空**；原版同处 (33,29,18) 暗色室内几何 |
| 灰区像素 | (106,101,96)，几乎均匀，带一点竖向渐变 |
| `Sororitas Ground Atlas` 的 alpha | **只有 8.3% 像素不透明**（原版 bundle 里那张**逐项一致** ⇒ **我们的导出是忠实的**） |
| 地板 UV 落在图集内容上的比例 | **约 16%**（按 4749 个 `vt` 采样） |

**⇒ 现象是**：我们的圣女战场**有洞**，透出了 **Unity 默认天空盒的「地面」半（灰褐）** = 那片灰，
以及左上角的天空。（我们**从没设过 `RenderSettings.skybox`**，而原版 `RenderSettings.m_SkyboxMaterial`
指向一个外部资产 —— 但那只是「洞被填成什么」的问题，**主因是洞**。）

**⇒ 最像的根因（⚠️ 假设，未坐实）**：那块地板材质在我们清单里是
`transparent = True`（依据 `_SrcBlend=5 / _DstBlend=10`），而 **这两个属性是内置 Standard shader 的属性**
—— 很可能是**残留值**，原版的**自定义 shader 根本不看它们** ⇒ **原版那块地板是不透明的**。
这与 `CLAUDE.md` 第三节那条已知坑（「**原版材质上带着内置 Standard shader 的残留值**」，
以及 `_EmissionColor` 那次 13 个效果同时变暗）**是同一个形状**。
**没坐实的原因**：去读那个材质的**原始属性表**时，材质**不在场景包里**（在别的 serialized file / 外部包），
**没读到**；`mats_of()` 那条路给的是解析后的结果，看不到「shader 属性表里到底有没有 `_SrcBlend`」。
**下一步该做的**：拿那个材质的 `m_Shader` → 去 `bundle_shaders_assets_all` 读它的属性表，
**属性表里没有 `_SrcBlend/_DstBlend` 就一律按不透明**（与自建 shader 那条规矩同源）。

⚠️ **别把这条当成「arena 材质全都要改」**：arena1 的匹配是 0.0375、blacklegion 天空 0.025，
说明**多数材质这样判是对的**；目前**只有 sororitas 这一场**有肉眼可见的症状。
**在坐实之前不要一刀切改判据。**
