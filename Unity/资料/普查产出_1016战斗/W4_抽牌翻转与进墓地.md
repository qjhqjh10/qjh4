### A-2 判据缺口 / 我判不出来的

- 🔴 **任务书写「翻 180°」，常量实读是 90**。`0x1834b2e04` 用 `read_literal.py` 读 = **90.0f**（同址在本文件里已经是 `AttackTurnDeg` / `DeathShakeRandomness` 的出处，三处互证）；`0x1834b2e7c` = **0.25**。**180 = 两段 90 之和**（`TurnCardAround` 一段 + `FinishCardDrawRotation` 一段）。已按「两段 90」实现；把单段写成 180 会变成「一下转过去、回不来」。
- ⚠️ **「起手时卡是哪一面」没实据**：`RotateMode.Fast` 走最短路径，从 `(0,90,0)` 起转，只要起点是 180° 之外才叫「翻面」（否则是来回摆）。原版把卡的初始朝向定在哪一句**本件没追到**（`DrawCard` 里没有；推测在 `ResetToValuesInHand` / 手牌复位那条链）。⇒ 我们的实现按「90° 去、90° 回」落地，**视觉上等价**，但「起点那一面是背面」这一条**没有出处**。
- ⚠️ **`DORotate` 的 world/local 语义**：DOTween 的 `DORotate` 与 `DOLocalRotate` 是两条口，本机 DOTween 是 DLL（源码不在工程里）**没能静态证实**。既有代码一路用它，本件**沿原文形状**（不换口）；批处理里 `driver.transform` 是 `new GameObject("Battle")` ⇒ 恒等 ⇒ 两者等价，所以断言没被这一条影响。

### A-3 没做的 + 为什么

### B-2 判据缺口 / 我判不出来的

- 🔴 **「飞进墓地」不是补间，是瞬移**。原版 `GoToCemetery` 里那句是 `Transform.set_position(globalVars.cardInCemeteryPos)`（**一帧到位**），唯一的补间是 `DOScale(one × 0.65, growInCemeteryTime 0.3)` —— 而它**在下一行就被 `gameObject.SetActive(false)` 盖掉**（`CemeteryManager__AddCardToCemetery` 里 `SetAsCemetery` 与 `SetActive(false)` 紧挨着）⇒ **原版画面上根本看不见那 0.3 s**。**可见的只有「留一拍 + 到点收掉」**。⇒ 我们照判据落地（`DOScale` 照发、随后 `onDone` 收掉），⛔ **没有自己发明一条飞行动画**。任务书里「飞进墓地」这个措辞**判据不支持**，如实报。
- ⚠️ **那份「0.5 s」用的是督军的字段**：`:120` 读的是 `gVars + 0x34`（`deathTimeWarlordDuration`），而且**在 `if (cardType == 10)` 分支之外** ⇒ **不分档**（分档的只有「抖」，`:100-109`；`CardTypeOptions.Hero = 10` = 督军）。小兵抖 0.2 s 之后**还要多站 0.3 s** 才爆散 —— 这是原版自己的写法，不是我们的笔误，已在常量注释里标死「⛔ 别改成分档」。
