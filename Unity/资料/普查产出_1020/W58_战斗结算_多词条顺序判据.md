## 〇、结论（先给排序键）

**原版有【三层】排序键，任何「谁先谁后」都由这三层依次决定：**

| 层 | 排序键 | 判据 |
|---|---|---|
| **① 单位层** | **`BattleManager.allCardsInPlay`（`+0x470`）的列表序 = 卡片【进入战场】的先后**。⚠️ **不是棋盘位置、不是左→右、不是所属玩家、不是卡 id、不是卡名**。 | 见 §一·A1/A2 |
| **② 手牌层**（只在「场上那趟」跑完之后） | **当前回合方的手牌 → 另一方手牌**；每一边内部按**手牌自身顺序** | `Broadcast*` 全族同一形状（见 §二） |
| **③ 卡内层** | 同一张卡：`cardAbilities` **序列化列表序**（同触发器多条按列表序、**不去重**）；一条 ability 内：`abilityLogic` **列表序**（`randomAbilityChoice=true` 时只**随机取一条**，全池 1 例） | §一·A3 |
| **④ 动作层**（触发之后动作怎么排队） | `CardAbility.priority` → `AbilityData.priority` → **四条队列**，消费序 **`Interrupt(2)` → `Instant(1)` → `DelayedInstant(3)` → `Player(0)`**；同一队列 **FIFO** | §一·A4 |

**⇒ 用户点名的例子：场上多个【工匠 / Artifice】同时听「我方打出一张战术卡」——原版顺序 = 这几个单位【进入战场的先后】（先落场的先结算）。**
例外只有一种：**`priority=3 (DelayedInstant)` 的 Artifice 会排到 `Instant` 那一批【之后】**（全池 2 张，见 §一·A4·b）。

**玩家没有选择权。** 没有 APNAP 式「同时触发，由玩家决定顺序」；也没有「当前行动方先」这种规则。随机只出现在 `randomAbilityChoice`（全池 1 条 ability）与随机目标（`randomSelect`）上。

**我们的实现用的是另一个键 + 另一种调度：**
- 单位层 = **`ctx.Players[p].Board[s]`，`p` 升序、`s` 升序**（= 玩家 0 整排 → 玩家 1 整排 / 每排格号升序）——`EffectResolver.BroadcastWhen` 的棋盘快照；单方关键词用 `RuleCore.FireTriggerOnSide`（格号升序）。
- **没有任何动作队列 / 没有 `priority`**：触发即**同步递归结算**（`FireTriggerAt` / `FireWhen` → `ResolveOps` 当场跑完），靠 `BattleContext.MaxEffectChain = 8` 截断。
⇒ **多单位局面下，我们与原版的结算顺序会不同**（详见 §四）。

## 一、原版排序键证据

### A1 · `allCardsInPlay` 是「进场序」的**追加列表**

| 事件 | 证据 |
|---|---|
| 它是 `List<CardScript>`，`BattleManager.GetUnitsInPlayRef()` 直接返回 `manager + 0x470`（`BattleManager__GetUnitsInPlayRef.c:5`） | `BattleManager.cs:4643 private List<CardScript> allCardsInPlay` |
| 开场：先放**双方督军**（P0 → P1），再放**先手方起始部队**、再放**后手方起始部队** | `BattleManager__SetupBoardPhase.c:120 / :145 / :159-166`（`SetPlayerDataAndWarlord(…,0)` → `(…,1)` → `SetupPlayerDeckAndInitialTroops(先手)` → `(后手)`）；督军落列表在 `BattleManager__SetupFullHero.c:43-70`（`List.Add`/`AddWithResize`） |
| 起始部队：`List.Add` | `BattleManager__CreateStartingTroop.c:71-100` |
| 从手牌打出：`List.Add` | `BattleManager._ResolvePlayCardFromHand_d__447__MoveNext.c:709-711` |
| 召唤（效果召唤）：`List.Add` | `BattleManager._ResolveSummonUnit_d__510__MoveNext.c:179-183` |
| 自动召唤：`List.Add` | `BattleManager._ResolveCardAutoSummoned_d__511__MoveNext.c:284` |
| 小兵死亡：`List.Remove` | `BattleManager._ResolveMinionDeath_d__454__MoveNext.c:56-59` |
| 回手/回牌库/移出游戏：`List.Remove` | `_ResolveRecallToHand…:266-268` · `_ResolveRecallToDeck…:119-121` · `BroadcastRemoveFromGame.c:21` · `DestroyUnitSilent.c:22-24` |
| **全库没有任何一处对该列表按格位/方/卡 id 排序**（`grep "__Sort"` 在战斗相关文件里 0 命中） | —— |

⇒ 列表序 = 「谁先进场谁在前」；**死掉的人被 Remove，之后复活/再造会重新 Add 到表尾**（= 新的进场序）。
⇒ 开场时双方督军先占前两位（P0、P1），随后是**先手方的起始兵**、再是后手方的 —— 所以「玩家 0 先」在开场只是巧合，**不是规则**。

### A2 · 广播遍历的是【活列表】，不是快照

`BattleManagerSupport__BroadcastTurnStart.c:18-31` / `BroadcastTacticPlayed.c:15-33` / `BroadcastDeadUnit.c:82-150` 全族同一形状：

```
lVar = *(longlong *)(manager + 0x470);              // 缓存的【列表对象】
for (i = 0; i < *(int *)(lVar + 0x18); i++) {       // ⚠️ 每轮重读 count
    card = get_Item(lVar, i);
    if (!IsInPlay(card)) continue;                  // 只处理「在场」的
    ...CardScript__OnXxx(card)...
}
uVar2 = IsPlayerTurn(manager);
hand = GetCardsInHandRef(manager, uVar2);           // ① 当前回合方手牌
... foreach hand card ...
hand = GetCardsInHandRef(manager, !uVar2);          // ② 另一方手牌
... foreach hand card ...
```

🔴 **`count` 是每轮重读的 ⇒ 本趟广播期间被召唤/打出、`List.Add` 进表尾的卡，会被【同一趟】扫到并收到同一个事件。**（我们实现是「先快照」——这是差异 D10。）
⚠️ `GetCardsInHandRef` = `PlayerManager+0x50`（手牌本体，`BattleManager__GetCardsInHandRef.c:5-11`），不排序。

### A3 · 卡内顺序（`RawCardScript.TriggerAbilities`）

`RawCardScript__TriggerAbilities.c` 两个分支：

1. **自己的 `cardAbilities` 分支（else，`:199-266`）**：`for (i = 0; i < cardAbilities.Count; i++)` → 逐条 `CardAbility__CanTriggerAbility(...)` → 命中就 `RawCardScript__TriggerAbility(...)`。
   ⇒ **触发 id 相同**的 multiple 条目按**列表序全部触发、不去重**。
   ⚠️ 进入这个分支的闸（`:42-48`）：`thisCard` 存在时，**不带 trait `0x82`（= `DefinedTrait.jam = 130`）** ⇒ 强制走自己的列表；`resolveOnlyEnchantments != 0` 或自己列表为空 ⇒ 走附魔分支。
2. **附魔分支（`LAB_18094b822`，`:49-198`）**：遍历 `thisCard + 0x110`（`activeEnchantments`，`CardScript__AddEnchantment.c:44-75` 追加），每个附魔再遍历它自己的 `+0x290`（`cardAbilities`）**列表序**。
   ⇒ **附魔能力是「兜底分支」**：自己列表为空 / 卡被 jam / 显式 `TriggerEnchantment` / `OnTriggerAlt(resolveOnlyEnchantments=true)` 时才走。
   ⚠️ 这一条与我们 `A1567` 的注释（「载体自己的先跑、附魔随后」**无条件**）**不一致**，见 §四·D12 / §六·2。
3. **一条 ability 内的 `abilityLogic`**：`RawCardScript__TriggerAbility.c:79-112`：
   - `randomAbilityChoice`（`ability + 0x48`）为真且 `abilityLogic.Count > 1` ⇒ `GetRandomInt(0, count)` **只随机取一条**（`:82-105`）；
   - 否则 `for (j = 0; j < abilityLogic.Count; j++) AbilityLogic__PlayAbility(...)`（`:107-113`）。
   - 桩上的注释原文：`"[Header(\"If true, only one ability triggered, chosen randomly. Otherwise, all are triggered in order:\")] public bool randomAbilityChoice; public List<AbilityLogic> abilityLogic;"`（`CardAbility.cs:26-30`）。
   - ⚠️ 全池 `randomAbilityChoice=true` **只有 1 条**：`GOF12 Spanner`，`trigger=300(Mob)`，5 条 logic（5 种加成，原版随机 1 种）。

**同一张卡在【同一个时刻】碰到多个不同 trigger id 时**：按**代码里的调用顺序**，不是 ability 列表序（见 §三）。同一 trigger id 的多条：列表序。

### A4 · 动作层：`priority` 四条队列（这一层决定「谁先真正生效」）

| 环节 | 证据 |
|---|---|
| `CardAbility.priority` 是字段（`ActionPriority`） | `CardAbility.cs:12`；枚举 `ActionPriority { Player=0, Instant=1, Interrupt=2, DelayedInstant=3 }` |
| 触发时把它塞进 `AbilityData.priority` | `RawCardScript__TriggerAbility.c:29-37`（`uVar11 = *(uint *)(ability + 0x18)` → `AbilityData__SetNewData(..., priority, ...)`） |
| `AbilityLogic.PlayAbility` **几乎每个分支**都把 `AbilityData+0x44`（= priority）传给对应的 `Add*Action` | `AbilityLogic__PlayAbility.c:339/362/379/397/409/432/455/496/513/527/558/581/598/617/635/652/677/715/811/901/937/975/1022/1098/1140/1219/1296/1305/1333/1370/1413/1432/1505/1624/1672/1696/1715/1732/1755/1778` |
| 入队按 priority 分四条 | `BattleManager__AddAutoActionToQueue.c`：`p3==0 → +0x350`（`:48`）· `1 → +0x358`（`:284`）· `2 → +0x368`（`:175`）· `3 → +0x360`（`:231`） |
| 出队顺序 | `BattleManager__NextActionInQueue.c:11-25`：**先 `+0x368`(2) → 再 `+0x358`(1) → 再 `+0x360`(3) → 最后 `+0x350`(0)**；每个队列 FIFO 取 `index 0` |
| 每帧只取一条 | `BattleManager__Update.c:1287-1303`（同一套顺序） |

**a) ⇒ 有效次序 = `Interrupt` > `Instant` > `DelayedInstant` > `Player`。** 触发遍历顺序只在**同一队列内**决定先后（FIFO 就是触发顺序）。
**b) 全池 priority 分布**（1351 张，逐卡统计）：

| priority | 条数 | 非 Instant 的实例（全部列出） |
|---|---|---|
| 1 Instant | 1484 | —— |
| 2 Interrupt | 6 | `DA12 Company Veteran`(trig 695) · `BL72 Accursed Helbrute`(510) · `Z-BlackLegion-Spreading Corruption_enchantment`(80) · `Abaddons Chosen_startinghand`(30) · `Z-Sororitas-Raging Storm_enchantment1`(190 与 40，两条) |
| 3 DelayedInstant | 4 | **`SAU13 Canoptek Spyder`(560 Artifice)** · **`SAU70 Damaged Hexmark`(560 Artifice)** · `UM37 Death from Above`(145 idx1) · `ASH53 Reclaim the Stars`(600 idx1) |
| 0 Player | 2 | `GOF97 Gargantuan Squiggoth`(0，**无 logic**) · `DA14 Ravenwing Speeder`(410) |

🔴 **Artifice 专项**：17 条 Artifice ability 是 `priority=1`，**2 条是 `priority=3`**（`SAU13` / `SAU70`）。
⇒ 多个 Artifice 同时触发时：**先按进场序入 `Instant` 道**，那两张 `priority=3` 的进 `DelayedInstant` 道 ⇒ **它们的效果最后结算**（哪怕它们先落场）。

## 三、同一张卡「同一时刻」多个触发：代码调用序 > 列表序

`TriggerAbilities` 每次只处理**一个** trigger id；同一时刻的多个 id 由调用方**按固定顺序各调一次**。逐条：

| 场合 | 原版调用序（＝生效序） | 出处 |
|---|---|---|
| 回合开始 | `30 TurnStart` → `31 TurnStartPlayer` →（`:151` `230 Relentless`）→（`:166` `46 Talent`） | `CardScript__OnTurnStart.c:137/144/151/166` |
| 回合结束 | `43 Courtesy` → `40 TurnEnd` → `45 Resolution` | `CardScript__OnTurnEnd.c:64/72/80` |
| 死亡（自己） | `80 ThisUnitDeath` → `81 Unstable` → 按 deathType 二选一：`10 → 175` / `20 → 180` / `40 → 170` | `RawCardScript__OnMinionDeath.c:22/23/37` |
| 死亡（别人死在场上） | `90 OtherUnitDeath` → 同上的 deathType 那一支 | `RawCardScript__OnMinionDeath.c:19/37` |
| 召唤（自己） | `195 ThisUnitSummoned` → `605 UseFaith` | `CardScript__ResolveUnitSummoned.c:46/50` |
| 召唤（别人被召唤） | `190 OtherUnitSummoned` →（同方）`550 Support` →（同方、之后）`680 Uprising` | `…:31/65/97` |
| 攻击（攻击者自己） | `50 UnitAttack` → `580 Strike` → `300 Mob` 或 `301 Regiment` | `CardScript__ResolveUnitAttacked.c:28/99/133/155` |
| 受伤（观察者） | `130 Rage`（仅被打者）→ `720 Cruelty`→ `715 Ecstasy` → `60 UnitDamaged` → `185` 或 `187` | `CardScript__ResolveDamageDealt.c:98/104,120,150,160,195/203` |
| 常驻 | `20 WhileInPlay` → `240 WhileInPlayVariable` | `RawCardScript__UpdateWhileInPlay.c:19/25` |
| 附魔加入 | `0`（attach-time）→ `500 TriggerEnchantment`，各一次 | `RawCardScript__TriggerEnchantment.c:18-22` |

⚠️ **这一层与「ability 列表序」无关**：即使一张卡的 `cardAbilities` 写成 `[40, 45]`，同一回合末也是 40 先 45 后（代码写死）；只有**同一个 trigger id 的多条**才回落到列表序。

## 四、我们 vs 原版逐条

> 「可见」= 什么时候看得出来。**单单位局面大多看不出来；多单位 / 多触发 / 有连锁时才现形**。

## 六、落地建议（若主对话要改，给文件 + 符号）

**优先级按「能看见的差异」排，不是「值不值得做」（铁律 11：全部要做，只有先后）。**

1. **D5（Backlash vs Unstable 反了）—— 改动最小、判据最硬。**
   `RuleCore.CleanupDeaths`：把 `FireTriggerAt(ctx, u, KeywordTable.Backlash, p, slot)`（现 `:7478`）移到 `UnstableBlast`（现 `:7472`）**之前**。
   判据：`RawCardScript__OnMinionDeath.c:22-23`（80 → 81）+ 数据（`Goff-Bomb Squig` 的 `Backlash:` = trigger 80、Unstable = trigger 81）。
   断言建议：`Bomb Squig` 型夹具（Backlash 打全体 1-2 + Unstable 随机 1-3），用 `Signals` 下标断 `Trigger(backlash) < Trigger(unstable)`；**并把随机源固定**（`ctx.Rng`）避免抖动。
   ⚠️ 现有注释（`RuleCore.cs:7469`）自称顺序来自 `rule_core.gd`（旁证）——**按铁律 5 就地订正那条注释**。

2. **D4（死者自己 vs 观察者）** —— 把死者的 80/81 挪到观察者广播**之前**（或给 `BroadcastWhen(Die)` 加一个「先对死者自己跑一次」的口）。
   判据：`_ResolveBacklash…:88`（ResolveDeadCard(死者)）**在** `:144`（BroadcastDeadUnit）**之前**。
   ⚠️ 这一改会牵动 `FlushDeaths` 的「先反噬、后记账」结构（W58-INTERLEAVE），**必须与 Slay 顺序一起核**。

3. **D1/D3（顺序键 + priority）—— 结构性改动，建议先补「进场序号」再改扫描。**
   - `UnitState` 加 `PlayOrder`（int），在 `RuleCore.PlayCard` / `DeployFree` / `DoReanimate` / `DoSummon` 的**落场点**从 `BattleContext` 的单调计数器取号（不能复用 `InstanceId`：那是**建卡序**，不是**进场序**）。
   - `EffectResolver.BroadcastWhen` 的棋盘快照（`:6859-6874`）改成「收集后按 `PlayOrder` 升序」；`RuleCore.FireTriggerOnSide`（`:9331`）同改；`EffectResolver.ResolveAtTurn` 的 `unitJobs`（`:6041-6054`）同改。
   - ⚠️ **原版是「死掉 Remove、复活重新 Add 到表尾」** ⇒ `PlayOrder` 必须在**每次进场**时**重新取号**（不是首次生成时固定）。
   - `priority`：若要全量对齐，需要引入四条队列；**建议不要只加排序而保留同步递归** —— 那会得到一个「半队列」语义（更容易错）。要么照原版做队列（大改），要么先只改顺序键（D1），把 priority 记成已知差异。

4. **D9（攻击广播位置）**：把 `BroadcastWhen(WhenEventKind.Attack, …)`（`:4837`）移到哨戒/星镖之后、`ResolveUnitAttacked` 族之前（原版 `:988`）。⚠️ 与既有的「事件在伤害之前」注释（`:4826-4827`）冲突 —— 订正注释时说明「原版是在**哨戒/星镖之后、主伤害之前**」。

5. **D8（受伤广播的被击者预调）**：在 `BroadcastWhen(Damaged…)` 的调用点先对被打者跑一次，再广播；⚠️ 需先核「原版被打者是否在循环里被**跳过**」——本会话**没钉死**（见 §七·1），**别先改**。

6. **D11（回合开始形状）**：`ResolveAtTurn` 的「手牌 → 棋盘 → 常驻」顺序在**手牌陷阱**这一族上**没有原版判据**（代码注释已自认照 `rule_core.gd`）；但**棋盘 vs 手牌**的原版顺序是「棋盘在前」（`BroadcastTurnStart.c:20-51`）——与我们的 `ResolveAtTurn` 相反。⚠️ 手牌陷阱是我们自定的容器，**改动前先把「手牌陷阱在原版到底存不存在」这一格查清**（`资料/普查产出_1019` 的 `A2001` 余账）。

7. ~~**D12（附魔参与方式）**~~ **已核清并撤回**：我们现状正确（见 D12 行订正）。

## 七、没查清的部分（如实记，附「去哪拿」）

1. **受伤广播里「被打者是否会被扫两遍」**
   `BroadcastUnitDamaged.c:19` 先对被打者预调一次，随后 `:24-60` 的循环**没有看到自排除**（`IsInPlay` 为真就会再调一次）。按字面读 = 被打者的 `Rage(130)` / `UnitDamaged(60)` / `185|187` **会响两次**。
   但该循环的 `get_Item` 调用在反编译里**丢了索引寄存器**（Ghidra 常见坑），而且 `DamageInfo.damageAbsorbed(+0x24)` 以外的早退闸没找到写点 ⇒ **不能凭这份 `.c` 下结论**。
   **去哪拿**：对 `BroadcastUnitDamaged` 的 VA 做一次反汇编（找 `loop` 内是否 `op_Equality(item, param_2)` 自排除），或真机加探针（`d:/2/Warpforge_tools/scenejumpshot/SceneJumpShot.cs` 可改）。

2. **附魔能力到底何时参与（直接影响 D12 与「Slay 附魔能不能响」）**
   本会话读法：`TriggerAbilities` 在「非 jam 且自己 `cardAbilities` 非空」时**只跑自己的**，附魔只在兜底分支。**独立复核**：`GetAbilitiesForTrigger.c:26-30` 是同形判据。
   ⚠️ 但这与「Helspear / Ferocious Rage 给**督军**挂 `Slay:` 附魔」矛盾（督军自己有 ability）。可能原因：① 读法错（需要看机器码）；② 附魔加入时某种「换 raw card / 合并」我们没找到；③ 原版这条确有边界。
   **去哪拿**：反汇编 `RawCardScript__TriggerAbilities` 的 `0x18094b822` 分支入口（VA 从 `all_methods.txt` 取）；或实况给督军挂 Slay 附魔 + 看是否部署。
   ✅ **已核清（2026-10-20）：「无条件追加」是正确的**（反汇编共享尾块），⛔ **别改**；见 D12 行订正。

3. **`trait 0x82(=130, jam)` 在 `TriggerAbilities` 里的语义**
   现读：非 jam 卡强制走自己列表、jam 卡走附魔列表。全池 `CardTraits` 带 130 的卡 = **0 张**；数据里也没有授予 130 的 buff。⇒ 今天不可观测。**留着，别拿它当判据。**

4. **反噬 action 的入队 priority**
   `CardScript__TriggerUnitBacklashActions.c:181` 用的是 `*(int *)(globalVars + 0xbc)`（`BattleManager__get_globalVars` 拿到的那个对象）——**这个字段是哪个配置没解**（可能是「死亡动作优先级」）。它在 `NextActionInQueue` 的四道里落哪一道，会改变「反噬 vs 其它待结算动作」的先后。**去哪拿**：`GameplayVariables`/`VarsGlobal` 桩里 `+0xbc` 对应字段 + 数据表。

5. **`UpdateTriggerOnce` 的脏位 `+0x59` 由谁置 1**
   全量反编译 `grep "+ 0x59) = 1"` 只命中三个**无关类**（AssetBundleManager / PhotonTransformView / ComboBox）⇒ 写点的**类没被识别**（很可能是 `CardScript`/`BattleManager` 里 Ghidra 认错偏移）。⇒「trigger 200 什么时候重新武装」没钉死。

6. **链深上限**
   原版**没有找到**类似 `MaxEffectChain` 的数值闸（搜过 `0x3e8/0x2710`、`ActionsInQueue` 的使用点）。**不是「确定没有」**——只能说「本会话没找到」；若将来要照原版，需要把 `BattleManager.Update` 的完整循环（含 `ResolveAction` 递归路径）读完。

7. **`randomAbilityChoice` 的引擎侧实现**
   数据层已收（`CardDef.CardAnimTime.RandomChoice`），但结算侧**本会话没追**（`GOF12 Spanner` 5 条 logic 是「5 种加成随机 1 种」）。**去哪拿**：`EffectResolver` 的 `GiveRandomBonus` / `EffectText.ReRandomBonus` 那条链。
