## 逐条发现

### P1-1 · 猎杀标记（Hunt Mark）要求「有击杀者座位」——效果伤害 / 自伤致死一律不触发（存量缺陷，本批改到了这个块）

- **位置**：`Unity/MyGame/Assets/RuleEngine/Core/RuleCore.cs:7906`
  `if (u.Has("huntmark") && killer >= 0 && killer != p)`
- **一句话缺陷**：Hunt Mark 的结算是「**带标记的部队被摧毁**」就发生（与谁杀的无关），我们却把它挂在 `Hurt` 的 `killer`（座位号）上；而 `killer` 全仓只有 **主伤害 / Blast / Stomp** 三处传了（`RuleCore.cs:5610 / 5659 / 5693`），其余全是默认 `-1`。
- **触发场景（具体输入 → 错误结果）**：
  1. 给敌方部队挂 `Hunt Mark 2`（Space Wolves 一族 22 张卡会挂）；用**战术卡 `Deal 3 damage to an enemy`**（`EffectResolver.DoDeal:2008`，`killer` 未传）把它打死 ⇒ 原版：该部队主人的督军吃 2、对面督军回 2；**我们：两件事都不发生**（`killer = -1` 直接短路）。
  2. 同一发攻击里 **Shuriken**（`RuleCore.cs:5468`）或 **Markerlight**（`:5754`）打死带标记的单位 ⇒ `actingCard` 传了（Slay 会响），但 `killer` 没传 ⇒ **Slay 响、Hunt Mark 不响**（同一次死亡、同一份 `DamageInfo`，两套口径）。
  3. 己方效果打死**自己**带标记的单位（`killer == p`）⇒ 我们的 `killer != p` 直接跳过；原版**照样**结算（伤害给自己督军、治疗给**对面**）。
- **判据出处**：
  - `d:/2/tools/decomp_full/CardScript__TriggerOnMinionDeath.c:33-95`：Hunt Mark 那一支**只有** `0 < CurrentHuntMark(card)` 一道闸，**没有** actingCard / deathType / killer 任何判断；伤害打 `GetHero(card.isPlayer)`（= 死者主人），治疗给 `GetHero(card.isPlayer == 0)`（= **死者主人的对面**）。
  - 该函数只在「观察者 == 死者」时进入（`op_Equality(param_3, param_1)`；`param_3` = 死者 `local_308`，`param_1` = 观察者 —— 作者的 `W58_战斗结算_slay触发核查.md` §A1 也写了这条）。
  - 规则书 `:189`（非官方、仅旁证）同口径：「带猎杀标记的敌方部队被摧毁时：对敌方督军造成伤害并治疗我方督军」——**不看谁杀的**。
- **建议修法**：删掉 `killer >= 0 && killer != p`；治疗对象改成 `ctx.Players[1 - p].Warlord`（现在用的是 `Players[killer]`，正常击杀时两者相等，所以平时看不出来）。`actingCard` 不参与这一支。

### P1-2 · 加时判据从「能量」改成「全局回合号」——推翻了用户 2026-10-17 的明确拍板，落地前必须裁决

- **位置**：`RuleCore.cs:1544`（`ctx.Turn >= ctx.Vars.overtimeTurn.Value`）；口径历史在 `Core/GameplayVariables.cs:146-204`。
- **一句话缺陷**：这不是「照原版修 bug」而是**口径反向**：`GameplayVariables.cs` 原文记着 **用户 2026-10-17**「仍按【能量】决定，⛔ 不改成回合序号」；本批按任务书改成了回合序号，并在注释里自认「与用户记录方向相反、以最终确认为准」。
- **触发场景**：经典局在**全局第 10 回合**（后手第 5 个自己的回合、`MaxEnergy` 才 6）就进加时；按用户口径要后手第 9 个自己的回合（≈ 全局第 18）。**遭遇模式**的 `Overtime begins earlier` 文案也**不再由这条机制复现**（作者报告 §① 已列「未解」）。
- **判据出处**：原版实现面确实是回合号（`_NextTurn_d__395:191-207`，且 `turnCounter` 在**判之前**自增 —— 本审查已核，`ctx.Turn++` 后再比是对的，**没有差一**）；但**项目铁律 2 / 13·8：口径归用户**。
- **建议**：**落地前请调度台/用户裁决**。若仍按能量：把 `RuleCore.cs:1544` 改回 `Players[SecondSeat].MaxEnergy >=`，并把本批重写的 `TestOvertime` / `TestSkirmish ⑤` 的判别式一起回退（它们现在钉的是新口径）。**不要**把它当普通缺陷直接「修回去」再改回来。

### P2-1 · 死者自己的 Backlash / Unstable 打死人时，嵌套死亡的 `Die` 广播与 Slay **抢在外层死者之前**（本批 D4 重排新引入）

- **位置**：`RuleCore.cs:8106`（`FireTriggerAt(Backlash)`）→ `:8116`（`UnstableBlast`）→ `:8123`（`BroadcastWhen(Die)`）；再叠加 `FlushDeaths` 在 `CleanupDeaths` 之后才 `TryCreditKill`（`:8287-8288`）。
- **一句话缺陷**：`CleanupDeaths` 里跑 Backlash/Unstable 时 `_deferDeaths` 已经是 0（`FlushDeaths` 开头 `ReleaseDeferDeaths`），所以「被反噬打死的那个人」会**立刻递归**走完自己的整套 `CleanupDeaths`（含它自己的 `Die` 广播与紧随的 Slay），然后才回到外层，跑**外层死者**的 `Die` 广播 / Slay。
- **与原版相反**：原版每个死者的 death action 是队列里的一条；反噬里新死的人在**当前 action 执行中**被 `AddAutoActionToQueue` 入队 ⇒ 它的 80/81/90 一律排在**外层 action 的 `:144 BroadcastDeadUnit`（外层 90 / 外层 Slay）之后**。
- **触发场景**：两个单位 A、B 同批将死；A 的 `Backlash: Deal N damage to all enemies` 打死 C。观察者（`When a friendly unit dies`）收到的次序原版是 **A → C**，我们是 **C → A**；C 的 Slay 效果也会**先于** A 的 Slay 落地（交错方向被局部反转）。
- **判据**：`CardScript__TriggerUnitBacklashActions.c:181`（入队）· `_ResolveBacklash_d__451:88/94/144`（取出顺序）· 作者报告 `W58_战斗结算_多词条顺序判据.md` §二 D4。
- **建议**：跑死亡触发段时**临时重入一个「死亡批」**（`DeferDeaths`）把嵌套死亡攒住，在本死者 `BroadcastWhen(Die)` + `TryCreditKill` 之后再统一 flush；或先发外层 `Die` 再跑嵌套清理。⛔ 不能简单把 `BroadcastWhen(Die)` 挪回反噬之前（那会退掉 D4）。
