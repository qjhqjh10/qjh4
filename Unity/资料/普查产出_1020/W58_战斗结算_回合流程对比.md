> 代号 `W58-INV-TURNFLOW` · 2026-10-20 · **只读**：未改任何源码/正本，只写本报告。
> 判据优先级：**全量反编译 `d:/2/tools/decomp_full/`（第一权威）→ `dump.cs` 字段偏移 → 解包数据**。

## 结论（3 句）

1. **原版回合 = 动作队列驱动 + 两个协程**：`NextTurn(isPlayerTurn)` 一口气做完「turnCounter++ → 加时 → 能量/维护费 → 抽牌 → 逐卡 OnTurnSetup/OnTurnStart → 激活 → WhileInPlay → 起计时器」；`ResolveEndTurn` 依次做「TurnBeforeEnd → TurnEnd（逐卡）→ 战役附魔 → 双方 PlayerManager.OnTurnEnd → 双方手牌效果到期 → FinishResolvingAction → `StartCoroutine(NextTurn(对方))`」。我们的 `RuleCore.BeginTurn/EndTurn` 把这两段压成同步函数，**步骤与次序基本对上了**。
2. **可见差异集中在三处**：① 加时判据（原版 `turnCounter >= overtimeTurn`，我们按后手 `MaxEnergy >= 10` —— 用户 2026-10-17 拍板的**有意偏离**，但代码注释里那句「经典下等价」**不成立**）；② 牌库抽空（原版 `shouldReshuffle` 为真时把墓地洗回，我们**恒走疲劳**）；③ `Gain N Energy` 的语义（原版 `ManaBuff.createMana` → `AddNewMana` 会**永久抬高最大能量**，我们只回当前能量并封顶）。
3. **特殊流程**：原版**没有**额外回合/跳过回合；眩晕 = trait 100 + 「回合开始时已在状态」闸门（`+0x55`），**自己回合末摘**；超时 = **强制结束回合**（不投降）；投降 = 立即 `DeadHero`（不换回合）；掉线重连 = **同一个 BattleManager 实例保状态**（我们是「重放动作流」，结果等价）。这些我们都已对上，或只有实现路径差异。

### 1.2 回合结束

**玩家点结束**（`BattleManager__EndTurnClick.c`）：
- 闸门：`+0x290 == 0xE` 直接返回（结算中）；`!+0x245 && +0x244 && !WaitingForBlockingAction`（`:31-41`）
- 教程动作许可 + `CancelActionStates`（`:63-75`）
- **狂暴（berzerk）单位必须攻击**：若有 `GetPendingBerzerkUnit` 且**有可打目标**，弹提示并**拒绝结束回合**（`:78-125`）；时钟强制（`param_2=1`）可绕过
- `+0x245 = 1`、`StopClock`、`AddEndTurnAction(1)`（`:126-152`）

**`ResolveEndTurn`**（`BattleManager__ResolveEndTurn.c`）：
1. 若本地回合且还有待攻击的 berzerk 单位 ⇒ 先排队攻击，再重排一个 EndTurn（`:33-137`）
2. **`BroadcastTurnBeforeEnd`** → 全场在场卡 + **双方手牌** `OnTurnBeforeEnd`（= `OnTrigger(0x29)`）（`:385` · `BattleManagerSupport__BroadcastTurnBeforeEnd.c:20-60` · `CardScript__OnTurnBeforeEnd.c:5-10`）
3. **`BroadcastTurnEnd`** → 逐卡 `CardScript.OnTurnEnd`（`:433`）：
   - `cardState ∈ {3,0x11}` ⇒ `CancelAttack`；清高亮（`:57-70`）
   - 触发 `0x2B`（**该卡属于本地玩家时**）/ `0x28`（全场）/ `0x2D`（**本方回合**）（`:65,73,81`）
   - `regeneration`（trait 1030）> 0 ⇒ 治疗（`:84-108`）
   - `poisoned`（200）且本方回合且无 `resistant`（600）⇒ `DestroyUnit`（`:110-121`）
   - 残骸 `ShouldRemnantDestroyOnTurnEnd` ⇒ 摧毁（`:117-123`）

8. **`StartCoroutine(NextTurn(!isPlayerTurn))`**（`:856`）

### 1.3 胜负 / 收尾

- 伤害**不即时结算胜负**：等动作队列全空，`FinishResolvingAction` 才查督军 `+0x228 == 5` → `DeadHero`（`FinishResolvingAction.c:56-84`）。
- `DeadHero`：`battleStage = PostBattle(60)`、`StopBattleAfterBattleEnd`、`SendMatchFinished`、`BattleFinished`（`BattleManager__DeadHero.c:157-164,362`）。
- 胜者 = 没死的那一方；**取胜方督军自己也倒 ⇒ Draw(30)**（`DeadHero.c:244-269`）。
- 投降：`PlayerAction` 类型 `0x36` → `DeadHero(..., 2)`（`AddResignAction.c:33` · `ClickExitBattle.c:47-59` · `ResolveAction.c:4400,4447`）。
- 掉线判负：`ResignAction(1)+DeadHero(1,3)`（`FailedToReconnectAfterDisconnect.c:31-32`）。

## 四、问题清单（按严重度）

### P0 — 会改变对局走向 / 文档与事实冲突

**1. 加时需要按原版复核「等价」那句注释（口径本身是用户拍板，不改代码）**
- 现象：原版用**全局回合号** `turnCounter`（两人共用）比 `overtimeTurn`；我们用**后手方自己回合数×能量**。
- 原版值：`overtimeTurn` 是服务器字段（本地没有）；若为 10 ⇒ **全局第 10 个回合**（后手第 5 个自己的回合、能量 6）就进加时。
- 我们值：后手 `MaxEnergy ≥ 10` ⇒ 经典下是后手**第 9 个自己的回合**（全局第 18 回合）。
- 证据：`BattleManager._NextTurn_d__395__MoveNext.c:186-216`（`turnCounter +0x3F8`）· `GameplayVariables.cs:145-165,192` · `RuleCore.cs:1157`。
- 结论：**用同一个常数 10 时两种判据在经典下并不等价**；只有服务器真值恰为 18 时才重合。用户 2026-10-17 已拍板「按能量」⇒ **代码不动**，但 `GV:157,167` 那两句「经典下数学等价」应订正为「不等于，口径由用户拍板」。
- 还差：服务器 `overtimeTurn` 真值（否则无法判断原版实际的加时回合）。

### P1 — 可见行为差异（会影响局面）

**2. 牌库抽空：原版可洗回，我们恒疲劳**
- 现象：`_ResolveDrawCard` 先判 `GameplayData.shouldReshuffle(+0x48)`；真 ⇒ **把墓地可回收牌重建回牌库**（`+0x223`），假 ⇒ 疲劳。
- 原版值：字段在服务器；我们的 `GV:242` 注释自认「经典模式原版真值是 true（洗回）」。
- 我们值：`MoveDeckTopToHand` 无条件走疲劳（RC:2102-2127）。
- 证据：`BattleManager._ResolveDrawCard_d__432__MoveNext.c:63-95` · `GameplayVariables.cs:236-242`。
- 还差：`shouldReshuffle` 两个模式的服务器真值；实现「墓地洗回」这条支（铁律 11：要做，只有先后）。

**3. `Gain N Energy` 的语义：原版抬最大能量，我们只回当前能量**
- 现象：`ManaBuff.createMana(+0x16)` → 循环 `PlayerManager.AddNewMana` ⇒ `totalMana++`（`unusedMana` 也 +1）⇒ **永久提高最大能量**；`refillMana(+0x17)` 才是「把已花的补回来」。
- 我们：`DoEnergy` 只 `Min(MaxEnergy, Energy + n)`（EffectResolver.cs:8291-8301）。
- 证据：`BattleManager__ProcessManaBuff.c:38-62` · `PlayerManager__AddNewMana.c:30-48` · `ManaBuff` 字段表 `dump.cs`。
- 影响面：今天卡池只有 **DA61 `Plasma Generator`（防御卡，Gain 1 Energy）** 一张；长期局里每次用它都会差 1 点上限。
- 还差：确认该卡在原版走的是 `createMana` 还是 `refillMana`（`AbilityLogic` 的调用点是虚调用，反编译里没有静态调用点）。

**4. psychic / plasma 两种法力完全没建模**
- 原版每回合开始由场上 Psyker/Reactor 单位生成（`CardScript__OnTurnStart.c:203-253`），是独立货币（`PlayerManager` 的 `psychicMana +0x74` / `plasmaMana +0x88`）。
- 我们 `PlayerState` 只有 Energy / Faith / SpiritStones / QuestPoints。
- 今天卡池里 `psychic/plasma` 只出现在天赋文案（`Talent: A random Black Legion Psychic Power`），没有结构化消耗字段 ⇒ **可见影响待核**。
- 证据：`PlayerManager` 字段表（dump.cs）· `CardScript__OnTurnStart.c:203-260` · `RuleEngine/Core/PlayerState.cs:74-106`。
- 还差：确认「Psychic Power」卡的费用在原版是否走 psychic 货币；我们的数据管线是否把它折叠成了普通费用。

### P2 — 休眠/边角（今天卡池不触发，但机制缺）

**5. 开局 `initialHandModifier` / `initialManaModifier` / `initialPsychic/Plasma/SpiritStoneModifier` 未实现**
- 原版 `SetupInitialMana.c:20-46` 与 `AddCardsToMulligan:40-47` 会加督军这几个字段。
- 实测旧快照 1195 张：**五个字段非零数 = 0** ⇒ 今天不可观测。证据同上。

**6. `addedManaSecond`（后手一次性起始法力补贴）未实现**
- 原版 `_NextTurn:296-334` 在 `turnCounter == 1` 写 `savedMana`。值在服务器；我们 `GV.addedManaSecond = 0` 且不读。

**7. 伏击（Ambush）揭示时机：判据冲突**
- 我们：自己回合开始 `RevealAmbush`（RC:1170，依**粉丝规则书** `:166`）。
- 反编译：`SetAmbush(false)` 的调用点只有 `ResolveDamageDealt:173`、`ResolveUnitAttacked:111`、`_ResolveAttack:305`（受伤/被攻击）—— **没有回合开始的调用点**。
- 结论：要么原版用别的方式（activeEffect 到期回调）实现「下回合自动翻开」，要么规则书这条是实体版改编。**没查清**；建议按「原版行为优先」再核一次（不要仅凭非官方规则书改）。

**8. 回合开始「待死单位跳过触发」闸门缺失**
- 原版 `CardScript__OnTurnStart.c:130`：`IsUnit && EnoughPendingDamageToDie` ⇒ 整卡 return（连 TurnStart 触发都不跑）。
- 我们 `BeginTurn` 无此闸。我们伤害是同步 flush，正常局面到不了这个状态；若将来有「回合开始前残留 pendingDamage」的路径就会差。

**9. 回合开始的两条抽牌闸缺失**
- `sentinel`（trait 670）⇒ 不抽；`BuffType.skipCardDraw=7` 手牌效果 ⇒ 按次数/阵营不抽（`TurnStartCardDraw.c:24-46`、`PlayerHand__CanDrawTurnStartCard.c`）。
- 今天卡池：**0 张**带 `sentinel`、0 条 `can't draw` 文案 ⇒ 休眠。

**10. 手牌上限的「丢哪张」与原版不完全一致**
- 原版：`PlayerHand._AddDrawnCardToHand` 在**抽牌那一刻**判 `Count < MaxCardsInHand`，满了就把**刚造的这张**送墓地，手牌不动（`:113-140`）。
- 我们：先 `Add` 再 `EnforceHandLimit` 丢表尾（RC:2208）。正常局面表尾就是刚抽的那张 ⇒ 等价；**手牌已经超上限时会多丢**（我们自己的注释已承认，潮涌这类多入口可达）。

**11. 狂暴（berzerk）必须攻击才能结束回合**
- 原版 `EndTurnClick.c:78-125` + `ResolveEndTurn.c:33-137` 双重闸门；卡池当前 **0 张**带该 trait（`cards_engine.json` 全表扫描）⇒ 休眠。

**12. 维护费（maintenance）**
- 原版 `PlayerManager.TurnStart.c:68-124` 每回合扣场上单位的 `CurrentMaintenance`；卡池当前 0 张 ⇒ 休眠。

**13. 对手卡住看门狗**
- 原版人类对手回合约 100s 无进展 ⇒ 取消对局并判本地胜（`_InBattleFallbackCountdown:41-125`）。我们未查到对应物（联机体验差异）。

**14. `Your turn` 提示的 2s 等待**
- 原版在本地玩家回合的 TurnSetup/抽牌**之前** `WaitForSeconds`（`_NextTurn` case 2）。纯表现；我们的回合是同步推进的。

## 六、没查清的部分（+ 去哪拿）

1. **`overtimeTurn` / `addedManaSecond` / `shouldReshuffle` / 起手张数的服务器真值** —— 本地没有；来源只可能是线上 `PlayFab` 下发（已关服）。现只能按规则书/推断；**不要拿推断当原版事实**。
2. **`SendClearEndOfTurnEffects`（action `0x3D` / `ClearEndOfTurnEffects`）的调用点** —— 全量反编译里**零静态调用**（虚调用/Unity 消息），因此「`untilEndOfTurn` 到底在 TurnEnd 触发之前还是之后清」**未能定位**。我们的位置在 `EndTurn` 最前。
3. **伏击「下个回合自动翻开」的原版触发点** —— 只找到受伤/被攻击路径；**建议后续用 `CardScript__OnTurnSetup` 的 activeEffect 到期回调链继续挖**（`+0x35 → 0x32 → SendRemoveEffect` 那一段）。
4. **`Gain N Energy` 走 `createMana` 还是 `refillMana`** —— `ProcessManaBuff` 两条支都在，但 `AbilityLogic` 是虚调用，反编译没有静态调用点；需要按 `ManaBuff` 实例的字段值（卡 SO 里的 ability 数据）反查。
5. **psychic/plasma 费用是否被我们的数据管线丢掉** —— 需要引擎线核对 `cards_engine.json` 的 `cost` 是否合并了 psychic/plasma 费用（当前只有单一 `cost`）。
6. **`BattleManager._InBattleFallbackCountdown` 的阈值常量**（约 10 次 / ~100s）——只读代理给的是「约」，具体常量需再读 `DAT_` 常量表。
7. **`Your turn` 的 `WaitForSeconds` 秒数常量**（`DAT_1834b3090`）——未解。
