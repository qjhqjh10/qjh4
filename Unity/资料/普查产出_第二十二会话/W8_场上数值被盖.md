## 二、断言（宿主全部 = `BattleScene.Run`，新块 `⑤·b2`，调用点 `Editor/BattleScene.cs:1080` → `CheckBoardStatStack`（:21609））

1. **底光落在本卡队列段里**（:21626）—— 断 `TargetGlowQueue == SetQueue(q)`，**2962 与 2977 各建一张新卡**跑两遍。怎么红：删掉 `MakeGlow` 那句（第 1 遍就红）／写死一个号（第 2 遍红）。**灭自证对** = 两个不同的 q 值。

4. **数值离卡体正面 ≥ 0.05**（:21652）—— 怎么红：`BoardInfoZ` 调回 −0.09（实测只剩 0.011）。
5. **数值压在徽标之前**（:21657）—— 怎么红：`BadgeCounterZ` 调到比 `BoardInfoZ` 更负。
6. 🔴 **四个数值真的画在屏幕上**（:21725，新增的「渲图数像素」）—— 前置两条：战场相机要在（:21668）、四格都要落在 1920×1080 画面里（:21697，防「窗落在背景上、diff 恒 0」那种**假红**）。做法：探针卡渲进 RT → 读回 CPU → **逐格改值（3/2/1/5 → 8）再渲一次** → 那一格方窗里 `|Δ|>0.05`（0..1 三通道和）的像素要 **≥ 12**；窗半径按**卡在屏上的宽度**折算（`cardPx×0.10`，别写死像素）。**没变 = 那一格根本没画出来。** 怎么红：把四个数值层挪到卡体正面之后（z 更正直）⇒ 一个像素都不变。

## 四、顺手发现（只报不改）

1. **`_info` 与四个数值层共用 `BoardInfoZ`** ⇒ 同 z **共面**（场上 `_info` 烘出来是全透明，所以今天无害）。将来场上 `_info` 一开始烘东西，它就会和数字抢同一层 —— 建议那时给它单独一个 z（差 0.005 即可）。本次没改（DIAG 没列，改了就多一处偏离）。
2. 🔴 **间隙不是「已证实的因」**。按 24 位深度、相机 ~15 单位算，0.011 的间隙 ≈ 270 个量化步，**纯深度精度解释不了**；要出现「0.011 必翻、0.0255 不翻」这种阈值，得是 16 位深度那一档。我只把实拍状态与**各自的间隙**对上了：近战 0.0255 活 · 生命 0.0199 死 · 远程 0.0118 死 · 护甲 0.0114 死 —— 方向一致，**阈值来源没证**。
3. **原版实拍里也有空格**：`_tmp_view/diag_stats/09_原版卡_开局_ov.png` 上那张海军陆战队员场卡，红/紫/绿**三格都没有数**（同一张图里兽人卡的红格有「2」）⇒「某些卡的某些格没数」在**原版也见过**。**本条只记录、别当结论**，本批仍按用户口径「该有就得有」办。
4. **卡体 mesh 的计数器面板是凸起的**：四个数值格那一带的前表面在 −0.055…−0.079，卡面中段平在 −0.0115 ⇒ 数字是坐在凸起面板上的（近战格只有一部分压在上面）。这是 ② 那个量法的来源，备查。
5. `Core/Badges.cs` 只读看了 `SlotAt` / 底板 rect（§五·3 要用），**没改**。
6. 底光那两层挂在**卡根**（`transform`）而不是 `FaceRoot`（`2DCard` 内层）—— 场上倾摆是关的 ⇒ 今天无影响；手牌那条路上若有倾摆，底光不会跟着倾。
