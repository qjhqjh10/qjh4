## 结论

1. **N8 成立，且比账上写得更宽**：`BlockingOverlay.IsBlocking` 确实零消费者，但**它不是黑场本身**——真正的黑场是 `LoadingMenu.Panel`（`ShellRuntime.Loading`）。今天**没有任何生产代码**把「黑场可见」这一事实交给输入层，`PointerLayer` 的命中/滚轮/悬停/拖拽四条路都不问一句。
2. **原版怎么做，本地有硬判据**：黑图 `Panel` 的 `Image.m_RaycastTarget = 1`（场景 `MonoBehaviour_1960.json:22`；prefab 同值），且 `Game UI` 上有 `GraphicRaycaster`（`MonoBehaviour_2579.json`）+ `Canvas.m_ReceivesEvents = true` ⇒ **原版靠 uGUI 射线把整屏点击吃在黑洞图上**。同一条判据也证明：**原版不挡键盘**（`WindowsManager__Update.c` 的 ESC 分支里没有任何 loading 门槛）。
3. **最小修法 = 在 `PointerLayer.HitButton` / `HitScroll` 各加一句早退**（候选 A）——两处就是全部生产指针入口的收口点，`ClickAt/WheelAt/ButtonAt/PressAt/ReleaseAt` 自动继承；**ESC / 回车 / 文本框不受影响**（与原版同）。
4. 🔴 **前置缺陷（必须同批修，否则候选 A 会永久锁死输入）**：全仓**没有任何 `LoadingFade(false)` 调用点**（只有 `ShellRuntime.LoadSceneWithFade` 的 `true` 那一档）。`show=true` 完成后 `Panel` 一直 active、α=1 ⇒ 黑场**永不消失**，从壳进战斗/回主菜单之后都停在黑屏上。
5. **候选 C（黑场自己挂吸收层）最像原版，但单独做不够**：`HitScroll` 走的是独立的滚动区登记表，不经过 `HitButton`；而且 `LoadingMenu.QPanel = 4090` 会与 `ToastNotifications.QHit = 5004` 抢层级（后者更高），「toast 与加载黑场谁在上」本地判据仍然为空（`ToastNotifications.cs:75-78` 自己写着）。
6. **N9 两条仍查不到**，但各拿到一条新证据（见 §五）：(a) 0 缩放节点就是 `Game UI` 这个 **ScreenSpaceCamera Canvas 根**，`TransformScalerBySmallScreenUI` 被排除（0×k 恒 0）；(b) `Menu Dark Background` 是 `Holder` 的**唯一子件**，照抄「关」= `ShowLoading()` 什么都看不见 ⇒ 序列化值大概率不是运行期真相。

## N8 · 候选修法（按风险排序）

### 候选 A（推荐）：`PointerLayer` 在「黑场可见」时直接吃掉指针命中

**改哪几行（3 处，最少）**

```csharp
// Shell/PointerLayer.cs —— 新增（放在命中区那一段之前即可）
static bool InputBlocked
{
    get
    {
        if (BlockingOverlay.IsBlocking) return true;               // 降级件也接上（原零消费者）
        var rt = ShellRuntime.Instance;
        return rt != null && rt.Loading != null
               && rt.Loading.Panel != null
               && rt.Loading.Panel.gameObject.activeInHierarchy;   // ⚠️ 不是 IsShowing（alpha>0.001）
    }
}
```
- `HitButton`（`:1262`）第一句 `if (InputBlocked) return null;`
- `HitScroll`（`:1347`）第一句 `if (InputBlocked) return null;`

**判别式为什么用 `Panel.gameObject.activeInHierarchy` 而不是现成的 `IsShowing`**（`LoadingMenu.cs:101`）：
原版 `LoadingFade` 的第一句就把 α 设成与目标相反那个值（`show=true` ⇒ α=0）→ 补间到 1，完成后**不关** Panel；`show=false` 完成后才 `SetActive(false)`。**α=0 的那一帧射线靶依然在**（`m_RaycastTarget` 不乘 alpha、`m_RaycastPadding = 0`）⇒ 原版的拦截区间 = **Panel active 的整段**，`IsShowing`（α>0.001）会漏掉淡入起始与淡出末尾两段。⇒ 用 **activeInHierarchy**。

**影响面**
- **全壳每一颗钮**：黑场期间一律点不到、悬停退出、滚轮不滚。这正是要的效果。
- **拖拽进行中被遮黑**：`_dragScroll` 已经非空时 `DragTo` 仍会走一帧（`Update:322-331` 用的是按下时抓到的引用）—— 与原版近似（原版 `ScrollRect` 拿到的也是同一个 pointerId），可接受。
- **自检口**：`WindowButton.ClickForTest()` **完全不受影响**（它直调 `Click()`，不经过 `HitButton`）；`ClickAt/WheelAt/ButtonAt/ScrollUnder/PressAt/ReleaseAt` 在黑场期间会返回 `null`/`false` —— 目前**没有任何自检在黑场期间做指针动作**（`grep "LoadingFade" Editor/*.cs` = 0 命中）⇒ 零回归。
- **ESC / 回车 / 文本框**：不动 ⇒ 与原版一致（§四 判据）。
- **误伤风险**：只影响「生产指针路径」；改坏法 = 把谓词写成 `IsShowing`（淡入首帧/淡出末帧漏挡，且自检两态照绿）或只拦 `HitButton`（滚轮照滚，**静默**）。

### 候选 B：给 `WindowButton.Click()` 加全局闸（⛔ 不推荐）

**改哪几行**：`Shell/WindowButton.cs:827`，在 `absorbOnly` 早退（`:832`）之后插一句「黑场时 return」。

**影响面 / 问题**
- **拦不住**悬停、选中、滚轮、拖拽（那几样根本不经过 `Click`）。
- **会误伤与原版相反的东西**：`KeySubmit`（回车，`:735`）也走 `Click` —— 原版黑场期间 **Submit 照样能激活选中钮**（UGT 的 submit 不走射线），拦了就与原版不符。
- **会误伤自检口**：`ClickForTest()`（`:895`）= `Click()`，批处理里所有直调派发都会在黑场期间失效 ⇒ 一旦将来某条自检在黑场里点东西，**红的原因与它要验的事无关**。
- **`ClickAt` 仍返回 true**（命中了、只是没派发）⇒ 探针读出「点到了」而实际什么都没发生（假绿）。

### 候选 C：黑场自己挂一颗覆盖全屏的吸收层（最像原版，但不够）

**改哪几行**
- `Shell/LoadingMenu.cs:137` 之后（Panel 建出来那一段）：
  ```csharp

  wb.absorbOnly = true;          // 与 MenuDraw.Absorb 同一语义：吃掉、什么都不做
  ```
  （`absorbOnly` 让 `Click()` 在 `WindowButton.cs:832` 早退、`Select()` 在 `PointerLayer.cs:628` 按 `null` 处理、`Navigable` 排除它 `:1147`。）
- **仍必须**再加候选 A 的 `HitScroll` 那一句 —— 否则滚轮照样滚到黑场底下。

**影响面 / 风险**
- 指针这一侧**最忠实**：原版那颗全屏 `m_RaycastTarget = 1` 就是「最高层的一颗吃点击的 Image」。
- 队列碰撞：`LoadingMenu.QPanel = 4090`，而 `ToastNotifications.QHit = 5004` > 4090 ⇒ **黑场期间 toast 的命中区仍会被点到**。这不是 bug 而是**判据未定**：`ToastNotifications.cs:75-78` 白纸黑字写着「原版 toast（Canvas order 900）与加载黑场谁在上，本地没有判据，⛔ 不猜」。候选 A 会**一律挡掉**（与「黑场在最上」一致），候选 C 会**放行 toast**（与「toast 在最上」一致）—— **选哪个等于先拍一次这条未定的事**，必须如实记账。
- `ClickAt(x,y)` 会返回 **true**（命中了吸收层）——「点到东西了」与「点到了一颗真钮」在探针里不再可分；`ClickLog` 会写「窗内面板的吸收层」那一条措辞（`PointerLayer.cs:434`），用在黑场上会误导。
- 需要在 `Shell.unity` 里多一颗 `WindowButton`（由 `ShellScene.BuildAndSaveScene` 重生成即可）；`ShellScene` 的「建场」不跑 `Awake`，**必须像 `Loading.Build()` 那样显式建**（`ShellRuntime.cs:287` 已有那条注释）。

### 必须补的断言（写在 `Editor/ShellScene.cs` ④「压暗 / 遮罩」那一节，`:1109-1122` 之后）

1. **出厂态**：`shell.Loading.Panel.gameObject.activeSelf == false`，且 `PointerLayer.Instance.ButtonAt(<已知钮中心>)` **非 null**。
2. **黑场态**：`shell.Loading.LoadingFade(true); shell.Loading.TickForTest(2f);` ⇒ `Panel.activeInHierarchy` 为真、`ButtonAt(同一点) == null`、`WheelAt(<已知滚动区中心>, ∓120) == false`、`HoveredForTest == null`。
3. **灭自证（同坐标两态）**：`LoadingFade(false); TickForTest(2f);` ⇒ Panel 关、**同一个坐标**上 `ButtonAt` 恢复成那颗钮、`WheelAt` 恢复 true。
   ⛔ 只断第 2 条不断第 3 条 ⇒ 「`HitButton` 恒返回 null」也能全绿。
4. **键盘不被拦**（钉住 §四 的原版判据）：黑场期间 `KeyCancel()` 仍能关掉一扇 `closeOnEsc` 的测试窗（返回 true）。
5. **直调口不被拦**（钉住「只拦射线、不拦派发」）：黑场期间 `wb.ClickForTest()` 仍然派发（`onClick` 计数 +1）。
6. （若接了 `BlockingOverlay`）`StartSpinning()` 后 `ButtonAt == null`、`StopSpinning()` 后恢复 —— 把 `IsBlocking` 从「零消费者」变成有断言的接线段。
7. **前置缺陷的断言**：`LoadSceneWithFade` 那条链在 `show=false` 完成后 `BlocksPointer == false`（防「黑场永不消失 ⇒ 永久锁输入」）。

## N9 · 复核结果

### (a) 原版 `Loading Controller` 运行期姿态（父链 `localScale = 0`、赋值点查不到）

**结论：仍查不到赋值点；但新证据把范围收窄，并排除掉一个候选。**

新证据（逐条实读）：

1. **0 缩放只发生在 `Game UI` 这一层，而它是 Canvas 根**。父链逐级实读（`RectTransform_1083 → 1540 → 1114 → 1514 → 1314`）：
   `Loading Controller(1,1,1)` → `Safe area Only Horizontal(1,1,1)` → `MainMenu(1,1,1)` → `Main  Canvas(1,1,1)` → **`Game UI(0,0,0)`**。
   而 `Game UI` 的组件 = `RectTransform 1314` + **`Canvas 1077`（`m_RenderMode=1` Screen Space-Camera、`m_Camera=PPtr(602)`、`m_PlaneDistance=100`、`m_ReceivesEvents=true`）**
   + **`CanvasScaler`（MB 2577：`m_UiScaleMode=1`、参考 1920×1080、`m_ScreenMatchMode=1`、`m_MatchWidthOrHeight=0`、`m_ScaleFactor=1.2`）**
   + **`GraphicRaycaster`（2579）** + **`UISafeAreaManager`（2580）** + **`GeneralMenuController`（2578）**。
   ⇒ **引擎在 Screen Space 模式下自己驱动 Canvas 的 RectTransform**（这是 Unity 的行为，不是本仓可读的代码）——**若成立，序列化的 0 只是存盘值、不代表运行期姿态**。⚠️ **这条是推断，本地没有能证死它的资源**（没有主菜单运行期 dump）。
2. **旁证（同形态）**：`bundle_scenes_scenes_battlearena1` 里两个 ScreenSpaceCamera Canvas 根 —— `FrontCanvas` 的 `localScale = (1,1,1)`、`Canvas` 的 `localScale = (0,0,0)`。⇒ 0 缩放**不是这个场景独有的怪值**。
3. **排除 `TransformScalerBySmallScreenUI`**：`decomp_full/TransformScalerBySmallScreenUI__LateUpdate.c` 读 `transform.localScale` → **乘** `*(float*)(this+0x20)`（`menuScale`，构造器写 `0x3f800000 = 1.0f`）→ `set_localScale`，并把结果缓存进 `+0x24/+0x2c`。**0 × k 恒 0** ⇒ 它**不可能**是「把 0 变成非 0」的那一处。`Initialize`/`SetScale` 只碰 `+0x20` 那个 float。
4. **`UISafeAreaManager` 也不碰缩放**：`UISafeAreaManager*.c` 里对 RectTransform 的写只有 `set_anchorMin` / `set_anchorMax`（`ApplySafeZone.c:17,19`；`UpdateSafeArea.c:55,58`；`_CheckForUpdate_d__6__MoveNext.c:85,88`），**零处 `set_localScale`**。

⇒ **对实现的影响：无**。我们的 `LoadingController` 用 `SpinnerPx = 270.4389953613281f / 108` 直接给世界尺寸（`LoadingMenu.cs:217,276-278,304-306`），本来就没有「Canvas 缩放」这一层；这条判据继续按「未清」记账即可，不阻塞任何复刻。

### (b) `Menu Dark Background` 在场景里 `m_IsActive = false`、查不到谁开它

**结论：仍查不到赋值点；但新证据表明「照抄关」与 `ShowLoading()` 自相矛盾。**

新证据：

1. **它是 `Holder` 的唯一子件，而骷髅 + 齿轮是它的子件**（逐级实读）：
   `Loading Controller`(active) → **`Holder`(active，`loadingIndicator` = GO 41 / RT 1117)** → **`Menu Dark Background`(RT 1535，`m_IsActive = false`)** → `Animated Loading Image`(RT 1273，active) → `Cog`(RT 1183，active)。
   而 `MenuLoadingController.ShowLoading` 只对 `loadingIndicator` 做 `SetActive(true)`（`MenuLoadingController__ShowLoading.c`：取单例 → `SetActive(*(this+0x20), 1)`）。**子件的 `activeSelf=false` 不会被父件激活带起来** ⇒ 照抄的话 **`ShowLoading()` 之后屏幕上什么都没有**（骷髅/齿轮全在这条链下面）。这与「公会搜索会转圈」直接矛盾 ⇒ **序列化值大概率不是运行期真相**（或由本地没有的机制开）。
2. **GO 上 5 个组件没有一个负责开自己**：`RT 1535` + `CanvasRenderer 993` + `Image 2499`（黑 α0.4667、`m_RaycastTarget=1`）+ **`BackgroundCloseButton` 2475（`window = PPtr(0)`、`onClick` 为空）** + `MB 2572`（字段只有一个 `image → PPtr(2499)`，看着是「动画材质属性」那一族）。⇒ 即便它被显示，那颗 `BackgroundCloseButton` 也是**死的**（没有 window、没有回调）。
3. **`MenuLoadingController` 只有一个序列化字段**：`dump.cs:105764-105783` —— `private GameObject loadingIndicator; // 0x20`，方法只有 `Awake/ShowLoading/HideLoading/.ctor`。⇒ **类里根本没有暗底那根引用**。
4. **场景里唯一的 AnimationClip 与它无关**：`AnimationClip/AnimationClip_10.json` 的 `m_Name = "Level Up Card"`，10 条 float 曲线，`grep "Menu Dark Background"` 零命中。
5. **`JoinAllianceMenu` 那条唯一调用链也没碰它**：`JoinAllianceMenu__Initialize.c:22` 的 `SetActive(...,0)` 是它自己的面板；`:53` / `FillOpenAlliances.c:29` 是 `MenuLoadingController.ShowLoading()`；回调里 `HideLoading()`。

⇒ **我们的取舍（暗底随 `Holder` 一起开关，`LoadingMenu.cs:317-322`）在新证据下更有依据了**：不这么写，原版「加载件」在数据上就是不可见的。仍如实标 **判据未清**。
