## 一、结论（先给答案）

1. **三条红是同一个量：`numW`（`count` 的 TMP `preferredWidth`）实得 ≈ 53.53 设计 px，而断言用的是 50.29。**
   两个宿主（登录卡第 0 格 53.53 / 骷髅卡 53.57）互相印证 —— 确实是同一个量带出的三条。
2. **哪边错 —— 主要是【断言过期/过严】，不是本批新引入的实现缺陷：**
   - **实现是"照现行 px 口径"做对的**：`PreferredWidthPx` 量的就是 TMP 在 `m_fontSizeMax` 下的
     preferredWidth，先量后设框、顺序正确，第二次 `FitWindow` **没有缩字**（见 §三，日志实证）。
   - **断言把"原版 em 口径下的 numW"写成了字面量**，而本工程的 px 口径是
     `EmPerFontSize = WorldGlyphPerFontSize = 0.0948`（汉字墨高），实渲 em ≈ **1.055 × 名义 px**
     —— 这条口径差**早就在 `D1_桶A字号换算链.md` §五·2 记着**（"实渲出来 em ≈ 1.055×px，比原版 `m_fontSize` 大 ~5%"），
     它不是本批引入的，是**全仓级待拍板项**。只要口径不改，这三条字面量**永远不可能绿**。
   - **次一级的断言错**：50.29 这个数取的是**prefab 作者态占位文本**的宽（见 §四），
     而我们运行期画的是 `'100'` / `'200'`，正确值应是 **50.90 / 50.58**（差 0.6 设计 px）。
3. **修法（见 §五）**：本批**把三条断言改成"与原版同一条布局规则"的关系式（与 `numW` 无关）**，
   并把"口径 0.0948 vs 原版 em"继续挂在账上；⛔ 不要拿我们自己的 `numW` 当期望（自证）。

## 二、`numW` / `fontSize` / `preferredWidth` 实得（两档）

⛔ 本代理不许跑 Unity，**下列数值是从本轮日志的三条实测像素差反解出来的**（不是新量的），
但三条互相独立、且与字体资产的手算值一致（误差 0.3%），可以当"实测"用。

### 2·1 反解过程（逐式可复算）

登录卡第 0 格（`sidePadL = −20`、`sideGap = 5`、`sideAlignT = 1`、图标宽 55、格宽 162.5 设计、
`r.x1 − 卡左沿 = 9.7999` 设计）：

```
实测 ic0Cx − ax1 = 99.21 px ÷ 1.15 = 86.2696 设计
9.7999 + off2 + 27.5 = 86.2696          ⇒ off2 = 48.9697
off2 = padL + (r.W − padL − (55 + 5 + numW))×1 = 102.5 − numW
                                        ⇒ numW = 53.530 设计 px
```

登录卡两格间距（第 1 格 `MiddleLeft` + `padL 10`，与 `numW` 无关）：

```
实测 142.06 px ÷ 1.15 = 123.5304 设计
icon1 心 − 卡左沿 = 9.7999 + 162.5 + 10 + 27.5 = 209.7999
⇒ icon0 心 − 卡左沿 = 86.2696  ⇒ 与上一条逐位相同（自洽）
```

骷髅卡（`MiddleCenter`、pad 0、格宽 325、footer `pos.x = −1.5201`、`sideGap = 6`）：

```
实测 dx = −36.0 px ÷ 1.15 = −31.3043 设计
dx = (r.x1 + off2 + 27.5) − (r.x1 + 162.5 + 1.5201)，off2 = (325 − 61 − numW)/2
⇒ dx = −4.5201 − numW/2   ⇒ numW = 2×(31.3043 − 4.5201) = 53.568 设计 px
```

**两只宿主：53.530 / 53.568 ⇒ 同一个量 ≈ 53.55 设计 px（±0.05）。**

### 2·2 两档的 `fontSize` / `preferredWidth`

| 阶段 | `fontSize`（TMP 单位） | `FontPxNow`（画布 px） | `GetPreferredValues().x`（世界） | 折成设计 px |
|---|---|---|---|---|
| `Txt` 建完（第一次 `FitWindow`，框 = 图标右侧→格右，很宽） | **≈ 4.493** | **46.00** | **0.5700** | **53.53** |
| 第二次 `FitWindow(cLb, c2, …)` **之后** | **≈ 4.493（不变）** | **46.00（不变）** | 0.5700（不变） | 53.53 |

- `fontSize = 46.00 / (0.0948 × 108) ≈ 4.493` —— **`46.00` 有日志实证**：
  `rewards.log:3909`（骷髅卡 `count 1`）与 `rewards.log:4120`（登录卡 `count 0`）
  的「收敛值落在窗口内：实得 **46.00** px ∈ [11.50, 46.00]」。
- 即 TMP 收敛在 `m_fontSizeMax` 上（= `46` 画布 px = `40` 设计 px **按现行口径**），
  **第二次 `FitWindow` 没有把字压小**。
- `preferredWidth` 的实得 0.5700 世界单位来自 §2·1 反解的 53.53（× 1.15 ÷ 108）。

### 2·3 与"原版 em"的差 —— 这笔差的来源是口径，不是本函数

字体资产实读（`Resources/Fonts/Pragati-Regular SDF.asset`）：
`m_PointSize 95` · `m_Scale 1` · `m_CapLine 60`。
TMP 的 3D 档换算（`Label.cs:1228-1232` 引 `TMP_Text.cs:7183`）：

```
fontScale = fontSize / pointSize × faceInfo.scale × 0.1   ⇒ 1 em = 0.1 × fontSize（世界单位）
```

⇒ 本 label 的实渲 **em = 0.1 × 4.493 = 0.4493 世界 = 48.52 画布 = 42.19 设计 px**，
而原版 `m_fontSize = 40` 的 em = **40 设计 px** ⇒ **×1.055**。
这与 `D1 §五·2` 记的 1.055 **逐位一致**（`EmPerFontSize` 用的是 `'国'` 墨高 0.0948，不是 em 0.1）。

手算交叉验证（原版 `Pragati-Regular SDF.json` 的字形 advance，经 `Core/PragatiDigits.Data.cs`）：

| 文本 | 各位 advance（表内 px） | 折 font unit（×62.03/28） | @em 42.19 | @em 40 |
|---|---|---|---|---|
| `'100'` | 18.6277 + 17.9708 + 17.9708 = 54.569 | 120.89 | **53.69** | **50.90** |
| `'200'` | 18.2793 + 17.9708 + 17.9708 = 54.221 | 120.13 | **53.35** | **50.58** |

实测 53.53 / 53.57 vs 预测 53.69 / 53.35 ⇒ **0.3% 内**。⇒ 反解模型成立。

## 三、第二次 `FitWindow` 会不会把字号压小？（代码路径 + TMP 源码 + 实证）

**结论：今天不会；但这是一条"刀刃上"的写法，余量为 0。**

路径：`MissionsTab.cs:1960` `FitWindow(cLb, c2, …)` → `MissionsTab.cs:465` `lb.SetAutoFitBox(...)`
→ `Label.cs:1092` `SetWrapWidth(worldW)`（`TmpFont.cs:498-503`：`textWrappingMode = Normal` +
`sizeDelta = (width, 0)`）→ `Label.cs:1167` `ForceMeshUpdate()`。

1. **`numW` 是怎么来的**：`MissionsTab.cs:1943` → `PreferredWidthPx`（`:551-569`）→
   `TMP_Text.GetPreferredValues()`（`TMP_Text.cs:3584-3599`）→ `GetPreferredWidth()`（`:3676-3704`）：
   **字号取 `m_enableAutoSizing ? m_fontSizeMax : m_fontSize`（`:3684`）**、
   **margin = `k_LargePositiveVector2`、wrapMode = **NoWrap**（`:3691-3695`）** ⇒ 量的是"上限字号下的不折行宽"。
2. **框就是按这个宽度设的**（`MissionsTab.cs:1950`：`c2 = [dh2.x2+gap, dh2.x2+gap+numW]`）
   ⇒ 框宽 == preferredWidth（同一个字号、同一套度量）⇒ 理论上正好装得下。
3. **真压小的那条回路存在，但排在第二位**：`TextMeshProUGUI.cs:3616-3659`，在换行判定失败、
   `isFirstWordOfLine` 那一支里：
   - **先**压字距 `m_charWidthAdjDelta`（上限 `m_charWidthMaxAdj`，出厂 10%，`:3619-3634`）；
   - **再**才缩字号：`sizeDelta = max((m_fontSize − m_fontSizeMin)/2, 0.05)`、结果按 1/20 取整（`:3644-3652`）。
   ⇒ 若框比 needed 小一丁点，**先发生的是"字距被压 0.0x%"，字号不动**；只有压满 10% 还不够才掉字号（一次掉一截，不是一档一档）。
4. **实证**：`rewards.log:3909 / :4120` 两条收敛值都是 **46.00 = `fontSizeMax`** ⇒ 字号没掉。
5. ⚠️ **但余量是 0**：框宽与 preferredWidth 是**同一个浮点数**，任何一次度量口径漂移（字体资产、TMP 版本、
   `m_charWidthAdjDelta` 非 0 的残留）都会先落进"压字距"那一支。**建议在 `c2` 的宽上加 0.5 设计 px 余量**
   （或 `FitWindow` 之后再 `SetWrapping(false)` 那一下改成"先关折行再量"）—— 后者要动 `SetAutoFitBox`，不划算。

## 四、三条期望的重算

### 4·1 它们各自假设的 `numW`

| 断言 | 算式 | 假设的 `numW` |
|---|---|---|
| `RewardsScene.cs:1612-1616`（骷髅卡居中，窗口 ±34.5） | 原版 dx = `−4.5201 − numW/2`；`numW = 50.29` ⇒ **−29.665 设计 = −34.11 px** | 50.29 |

**三条都取 `numW = 50.29`；实得 53.53 ⇒ 差 +3.24 设计 px（+6.4%）。**
`102.94`、`138.33`、`34.5` 三个数本身算得对 —— 错的是它们背后那个 `50.29` 能不能代表**我们这一档的字号**。

### 4·2 `50.29` 是从哪来的 —— 它是**占位文本**的宽，不是我们画的文案

- `R_T07_剩余四项.md` §3·2 给的静态式：`Pragati 数字等宽，95px 下每个数字 39.812 ⇒ fs40 时 16.7632/位`，
  `'100' → 50.29`，并说"与登录卡 `count` 作者态 `sd.x = 50.2901` 逐位吻合"。
- **`Pragati 数字等宽` 这句不成立**：原版字形资产里各位 advance 不同
  （`Core/PragatiDigits.Data.cs`：`'0' 17.9708` · `'1' 18.6277` · `'2' 18.2793` 表内 px）。
  `3 × 39.812 × 40/95 = 50.29` —— **只有"三颗 advance 都等于 `'0'`"才得到 50.29**，
  也就是说 **prefab 作者态那颗 `sd.x = 50.2901` 对应的是等宽占位串（形如 `'000'`），不是 `'100'`**。
- **我们运行期画的是 `'100'`（登录卡 [0]）和 `'200'`（骷髅卡）**
  （`DailyData.cs:375` `_loginRewardCount = { 100, 20 }` · `:436` `SkullsRewardCount() = 200`）
  ⇒ 正确静态值 = **50.90 / 50.58 设计 px**（§2·3 的表）。
- 即使把口径修成 em（§五·B），三条正确期望也应是：
  **102.23 px / 139.04 px / dx = −34.28 px**（不是 102.94 / 138.33 / −34.11）。
  ⚠️ **骷髅卡那条窗口只有 0.22 px 余量**（`−34.28` vs 上限 `34.5`）—— 现在这条断言**本身就过紧**。

## 五、修法

### ✅ 推荐（本批最小、且不是自证）：把三条改成"与原版同一条布局规则"的关系式

三条要验的语义本来就是 **`MiddleRight` / `MiddleLeft` / `MiddleCenter` 三个 HLG 规则 + `padL`**
（`R_T07` §3·2 的 `pos = padL + (innerSize − totalPref) × alignAxis`），
**这三个规则的成立与否与 `numW` 无关**：

| 断言 | 改成 | 判据（原版字段） |
|---|---|---|
| 登录卡第 0 格 | **`count` 框右沿 == 格右沿**（`r.x2`，padR = 0） | `MiddleRight` + `padL −20` + `padR 0` ⇒ 块右沿贴格右（`R_T07` §3·2：count `112.21..162.50`，右边 = 格右） |
| 登录卡第 1 格 | **图标框左沿 == 格左沿 + 10** | `MiddleLeft` + `padL 10`（同一节：图标 `10..65`） |
| 骷髅卡 | **`(图标框左沿 + count 框右沿)/2 == 格心`** | `MiddleCenter`（同一节：块中心 = 162.5）+ footer `pos.x −1.5201` |
| 两格间距 | 由前两条自动推出（格宽 162.5 + padL 10 − 第 0 格块起点）；若仍要单独断，用「icon1 左沿 − icon0 左沿 == 格宽 + 10 − (numW0 那一侧)」不如直接断上面两条 | —— |

- 这三条与 `numW`、与字号、与字体面**全部解耦** ⇒ 口径拍板前后都稳。
- 鉴别力不变：`sideAlignT` 漏传 / `sidePadL` 不给（原来那两种改坏法）**照样红**
  （`MiddleRight` 会退化成左对齐 ⇒ count 右沿 ≠ 格右）。
- ⛔ **不许**改成「用 `lb.PreferredWidth` 自己算期望」—— 那是拿实现证明实现。

**同时（同批、不额外开销）**：把骷髅卡那条的窗口 `34.5` 换成原版推导值 `dx = −34.11 ± 2`
（三个输入全是原版字段：`gap 6` · `numW 50.29` · `footer pos.x −1.5201`），或者保留窗口但**放宽到 36**，
并在注释里写明"窗口只挡摆错边（左对齐 ≈ −157 · 两格排 ≈ −99）"。⛔ 现在的 34.5 连原版自己的值都只剩 0.39 px 余量。

### ⚠️ 备选（若调度台决定保留绝对字面量）：先改口径，再更新三条数

- **B（全仓级，需拍板）**：把 `Core/TmpFont.cs:239-242` 的 `EmPerFontSize` 从 `WorldGlyphPerFontSize`（0.0948）
  改成真正的 em 比 **0.1**（或 `0.1 × faceInfo.scale`，三份拉丁资产 `m_Scale` 全是 1）。
  Cjk 侧**绝不能**一起动（那是全仓 510+ 站点的版面基线，`D1 §四` 已论证）。
  改了之后：三条约 102.23 / 139.04 / −34.28 ⇒ **当前字面量能过（余量 0.7 / 0.7 / 0.22 px）**，
  但骷髅那条仍然太紧 ⇒ 仍需按上面放宽。
  ⚠️ 这条会动 478 处 `TmpFont.Face.Latin*` 站点（`Battle/*`、`Core/CardView`、`Deck/*` …），**不是最小修法**。

### ⛔ 不要做的

- 把 `numW` 拿来当期望（自证）。
- 为了对上 50.29 而把 `count` 的字号实参硬改成 `40×0.948`：`SetAutoFitBox` 的 min/max 是**按比例**折算的
  （`Label.cs:1126-1165`：`fontSizeMax = cur × maxPx/nomPx`）⇒ 只改 `fontPx` 不改 `autoMaxPx` 是**空操作**，
  三个一起改则会把 `CheckFontWindow` 的 `[11.5, 46]` 一起推翻（那些窗口是原版字段，不该动）。
