## 一、结论摘要

1. 这 12.5 s 是**一次性长停顿**，落在 **`SceneManager.LoadScene("Battle")` 那一帧**（`CardPresentation/Core/PlayerBoot.cs:317-332` `LoadSceneMatching` 是**同步** `LoadScene` ⇒ 该帧含「反序列化 + 全场景 `Awake/OnEnable/Start` + 首帧渲染」），**不是稳态帧率**（那归 `T08`，两者查法不同）。
2. 🔴 **我给出的排序里，前两名是（甲）该帧的「首次 GPU 程序创建 / 首帧渲染」与（乙）该帧里建的 `CardView`** —— **乙是本轮新增的量化线索**：`CardView.Create` 在收藏窗**实测 ≈ 2.5–2.9 s / 张**（`_tmp_view/player/s27_shell.log:90-97`，两页独立读数 2715 / 2886 ms 每格），而**换牌面板 / 手牌 / 场上督军全部走它**。
3. ⚠️ **但没有一条量到 ms 级**（player 日志无时间戳、Watch 只有 1 s 分辨率、`PlayerBuild.cs:190 = BuildOptions.None` 挂不上 Profiler）⇒ **「逐段占比」判不了、改哪也定不下来**。本文件给的是**按证据强度排的候选 + 每条该怎么量**。

## 二、候选根因（按嫌疑排序）

### ②-A 首帧「GPU 程序创建 / shader 编译」＋首次渲染 —— 置信度 **中高**（结构性差异唯一一条）
- **正向证据**：
  - 这一帧是 **`Battle` 场景的第一次渲染**（日志末行 `[Arena/Mirror] 渲了第 1 帧 …` 紧跟 `[PlayerBoot] 已到「Battle」`，`_tmp_view/wf_a1750/run.log`）；原版之后每一帧都不再付这笔。
  - 🔴 **我们与原版唯一结构性的不同** = **运行时从 StreamingAssets bundle 现取 117 个原版 shader**（`WarpforgeVFX/Runtime/WarpforgeShaderLoader.cs:85-144` `EnsureLoaded` → `:173-193` `LoadAllAssets<Shader>()`；日志 `[WarpforgeVFX] 共 117 个原版 shader 可用`）。原版把 shader 打进 build。
  - 🔴 **每次启动都卡**（不是只卡第一次）：同一 build 多份 watch 日志（`player/w_long.log:2-18`、`player/watch3.log:3`、`player/w_WF_NO_SETLINK=1.log:3`、`wf_a1750/watch.log:2-15`）**全部** `frame=1` 卡 ≈12.5 s ⇒ **不是驱动 shader cache 冷热那种一次性效应**，是**每次都跑的一段确定性工作**。
- **反证/排除到哪一步**：
  - ⚠️ **shader 的「磁盘加载」被排除**：`StreamingAssets/WarpforgeVFX/` 全部 bundle 合计 **8.5 MB**，其中 shader 那几个（`wf_shaders` 837 KB + `wf_shaders_extra` 700 KB + `wf_builtin` 91 KB + `wf_arena_*` 373 KB）**≈1.8 MB** ⇒ 读盘**不可能是 12.5 s**。**所以若这条成立，贵的是「编译」，不是「加载」。**
  - ⚠️ `cpu` 涨≈1 核（`wf_a1750/watch.log:2-15`：4.4→17.4，**12.5 s 烧 13 CPU 秒**）—— 这**既符合「主线程在算」，也符合「主线程阻塞、编译线程在烧」**（`Watch.cpu` = `Process.TotalProcessorTime`，**含别的线程**，见 `Core/Watch.cs:101`）⇒ **判不开**，别拿「单核 = 主线程在算」当定论。
- **未证**：没有一处直接量过 shader 编译耗时。

### ②-B 该帧里建的 `CardView`（≈2.5–2.9 s / 张，**实测**）—— 置信度 **中高**（对「换牌归零那 ~5 s」是**首选**）
- **正向证据（量化，硬）**：`_tmp_view/player/s27_shell.log:90-97` 的逐格探针读数（`Shell/CollectionWindow.cs:3826-3871` `BuildWatch`）：
  - `CardsTab`（18 格）：`① CardView.Create` = **48868.0 ms（均 2714.9 / 格）**；②`SetPose` 0.7 · ③`SetClipFromTree` 8.5 · ④`SetFace` 3.8 · ⑤命中区 7.0 —— **全卡的 2.7 s 全在 `CardView.Create` 里**。
  - `Alternate Art`（6 格）：`① CardView.Create` = **17316.7 ms（均 2886.1 / 格）**。
  - `单次文字重排`：**0.0 ms / 0.0 ms**（`s27_shell.log:97`）⇒ **本页里「TMP 字体现烘」那条假设被实测推翻**（`s27_shell.log` 的字体读数：图集 2048² Dynamic、已烘 207 字形）。
  - 🔑 **两页独立读数都是「×格数」**（18 格 2.7 s/格、6 格 2.9 s/格）⇒ **成本线性于建卡个数**，**不是「第一张贵、其余便宜」**。
- **入口（判据只此一处）**：`Core/CardView.cs:862` `Create` → `:1986` `Build` → 逐层 `:2768` `AddLayer`（**每层 `new Material(...)`**）· 文字 `:2362` `BuildTextLayers` · `:2644` `FitToBox`（**最多 8 次二分 × 每次 `:2662` `FitsBox` 里一次 `ForceMeshUpdate`**）。
- **反证/排除到哪一步**：
  - ✅ 排除了 **`SetPose` / `SetClipFromTree` / `SetFace` / 命中区**（上面读数全 ≤ 个位数 ms）。
  - ✅ 排除了 **TMP 单次重排**（0.0 ms，见上）—— ⚠️ 但那次量的是**已建好、已烘字形**的 TMP，**没覆盖「建卡时第一次现烘」**那条冷路径 ⇒ **不能据此宣布「字体不是因」**（探针自己也这么注明了）。
  - ⚠️ **`CardView.Create` 内部那 2.5–2.9 s 花在哪一段，我没查到** —— 子嫌疑（都**没量**）：15 份 `new Material` / 4 段 TMP（`ApplyOutline` 会克隆 `fontMaterial` + `UpdateMeshPadding`，`Core/TmpFont.cs:303-323`）/ `FitToBox` 的 8 次二分 / 每卡立绘 `Resources.Load`（`Core/CardArt.cs:743-750`，按名缓存；立绘 PNG 单张 **1.8 GB/2958 张 ≈ 610 KB**，import `maxTextureSize: 2048`）。**不猜。**

### ②-C 场景反序列化 + 全场景 `Awake/OnEnable/Start` —— 置信度 **中**
- **正向证据**：这一帧确实含这些（`Unloading 38 unused Assets … Loaded Objects now: 5350`，`wf_a1750/run.log`）+ `[Net]` / `[RuleEngine] 凑牌组` / `[Battle] 后期下游接上` / `Auto Zoom` / `[Arena/Mirror] Apply` 一串初始化日志**全在这一帧**。

- **未证**：这一段没量过。

## 四、换牌归零那 ~5 s 单独一条

- **实据（带面包屑）**：`_tmp_view/player/w_long.log:44-55` —— `MARK f=4236 t=44.98 换牌：倒计时到 0 自动完成`（这句 = `Battle/BattleDriver.cs:4685` `Watch.Mark`），随后**三段卡顿**：
  `t=44.98→47.32`（cpu +2.1）· `t=49.69`（+1.0）· `t=50.45→55.69`（**+4.0 ≈0.76 核**）⇒ 合计 **≈10 s**（不是 5 s，那一拍比记录里更长）。
- **它在干什么**：`TickMulligan`（:4676-4702）→ `_mulligan.HandleClick` → `OnMulliganDone`（:4834-4865）→ `RuleCore.Mulligan/EndMulligan` → `_mulligan.Close()` → `BeginBattleAfterSetup`（:4869-4889）→ **`RefreshAll()`（:11607-11626）**。
- 🔑 **`RefreshAll` = `SyncBoard`(双方场上卡) + `SyncHand`(手牌) + `SyncFoeHand` —— 全是 `CardView.Create`**（`SyncBoard` 唯一调用点 `:11725-11726`，内部 `:13025`/`:13288` 建卡）。
- ⇒ **与 §二·②-B 同一条根因**：**归零这一拍 = 建真手牌/场上卡的 `CardView`**。若 `CardView.Create` 恒 ≈2.5 s/张，**三、四张 ≈ 8–10 s**，**与观察到的三段卡顿量级吻合**。（⚠️ 仍是**推算**，没量。）
- 「cpu +3 ≈ 不到一核」（旧记录）与这里的 +4 ≈0.76 核一致 —— **像在等/加载而非纯算**（`Watch` 判据 `Core/Watch.cs:14-17`）；但同 §二·②-A 的理由，**`cpu` 含别的线程 ⇒ 判不开**。

## 六、怎么量

**能批处理量的（结构量 —— ⛔ 我给方案，不跑、不改自检）**
1. **调用计数**：给 `CardView.Create` / `WarpforgeShaderLoader.TryGetShader` 加**只自增的 `public static int`**（不改行为），自检里跑一局数出来 ⇒ 一局建几张卡 / 解析几次 shader。
2. **每帧分配**：`System.GC.GetAllocatedBytesForCurrentThread()` 夹住「建一张卡」/「一次 UpdateHud」（**纯 .NET API，`-batchmode` 也跑**）。⛔ 没跑过 ⇒ 给不出基线，只能做**回归式**。
3. ⚠️ **帧时间 / 首次编译 / 首传贴图批处理量不到**（无帧循环、`Update` 根本不跑）。

**只能真机的**

3. 🔴 **判别实验（最省事）**：临时加 `Shader.WarmupAllShaders()`（或对 117 个 bundle shader 逐个 `Material` 预热）到**加载屏期间**，看 12.5 s 是否塌下去 ⇒ **直接判「是不是 shader 编译」**（塌了=是；没塌=不是）。⚠️ 这是**量**不是修。

## 七、怎么修（按「改动大小 × 收益」给方向）

- **若坐实是（甲）shader 编译**：① 把预热挪出「进战那一帧」（原版等价物 = 加载屏期间后台预热；`Shader.WarmupAllShaders` / `ShaderVariantCollection`）——**小改、收益直取**；② ⛔ 别指望「改回打进 build」：本仓已记「bundle 里的 shader 落不了工程资产」（`WarpforgeShaderLoader.cs:1-6`）。
