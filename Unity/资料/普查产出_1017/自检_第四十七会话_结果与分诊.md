## 二、失败分桶（按「同一条根因」归，⛔ 不要把桶当结论）

### 桶 A（最大）：**字号/自适应窗口整体 ×0.912** —— `A1024` 换面后的换算口径
**证据（逐条都是「原版值 → 实得」）**：
- `42 → 38.312`（×0.9122）· `10 → 9.122` · `13.46 → 12.28` · `40 → 36.49` · `35 → 31.44` · `36 → 32.34` · `33 → 30.102` · `67.55 → 60.683`
  （Battle / Menu / Rewards / Shop 四处独立复现）。
- Shop 还有固定字号的同比例：`type 30 → 2.67`（期望 2.93）· `name 36.7 → 3.27`（期望 3.59）。
- Settings 的写法相反：断言要求「全窗 112 个 `Label` = 原版 × 0.9」，**6 颗是 32.84**（未过 0.9）。

**分诊方向（待只读诊断，⛔ 本文件不下结论）**：
1. `Label.SetFace` 之后的 `WorldGlyphPerFontSize / CapPerFontSize / ActGlyphPer` 与 `FontSizeToPx`、`SetGlyphHeight`、`SetAutoFitBox` 的**换算方向**是否一致
   （换面后字形变矮 ⇒ 同样物理高度应要**更大**的 fontSize，而实测是**更小**）。
2. `A1024` 批 0–§2·5 的「`SetFace` 排在 `SetGlyphHeight/SetAutoFitBox` 之前」是否**每一站都真的执行到了**（`Visible`/裁切早退会 `return null`）。
3. `SettingsWindow.Text` 的 `fs * RootScale(0.9)` 那条漏斗：**6 颗 32.84 的 Label 走了哪个口**（很可能是 A1024 新加的直接 `MenuDraw.Text` 没自己乘 0.9）。

### 桶 B：**ShellScene 崩** —— Toast 文字走点阵后端
