## 〇、一句话

**把「能不能打出、打完谁赢」从占位变成真实。**
卡牌基座第 1–7 步做完之后，卡能拖能放，但 `BoardLayout.IsSlotFree` 恒返回 true、卡面数值是造的。
本设计给出一个**能打完整一局的简单规则引擎** —— 核心循环完整、语义有权威来源可查、
不追求 61 个关键词全覆盖。

### ✅ v1 做

## 二、架构：引擎不依赖 UnityEngine

```
┌─ RuleEngine/Core/ ────────────── 纯 C#，零 UnityEngine 依赖
│    CardDef / UnitState / PlayerState / BattleContext / RuleEngine / RuleCodes
└─────────────────────────────────────────────────────────
              ▲                        ▲
              │                        │
┌─ Data/ ─────┴──────┐   ┌─ 表现层 ────┴──────────┐
│ CardDatabase       │   │ CardPresentation 的胶水层 │
│ （唯一碰 Unity 的   │   │ BattleDriver：            │
│   JsonUtility 的地方）│   │  引擎状态 → 卡牌/格位/描边 │
└────────────────────┘   └───────────────────────────┘
```

**为什么引擎不依赖 UnityEngine** —— 两条硬理由：

1. **对局必须可复现。** 随机数走 `System.Random(seed)`，不用 `UnityEngine.Random`（它有全局状态、会被别处消耗）。
   同样的种子 → 同样的洗牌 → 同样的对局。
   > 这是特效线用血换来的规矩：粒子随机种子没钉死，两遍扫描 60% 的行会变，**噪声和要测的改动一样大**。
   > 规则引擎比渲染更怕这个 —— 一个不可复现的对局，bug 根本没法查。
2. **换 UI / 加 AI / 写测试都不用动规则。** v1 的自检就是纯逻辑驱动，不进 play 模式、不建图形设备。

> ⚠️ **`JsonUtility` 只出现在 `CardDatabase` 里**，`Core/` 全是不含 Unity 的普通 C#。
> 想加 asmdef 隔离时要保证 `Core/` 能单独编过。

## 三、数据结构

对齐 `rule_core.gd` 的字段含义（**字段名可以变，语义不能变**）。

```csharp
// Core/CardDef.cs —— 静态卡牌定义（只读）
class CardDef {
    string Id, Name, Type, Desc, Rarity, Faction;
    int Cost, Attack, Health, RangedAttack;
    bool Has(string kw);          // 关键词归一化后查询
    int  KwValue(string kw);      // "Armour 1" → 1
}

// Core/UnitState.cs —— 场上单位（可变的实例状态）
class UnitState {
    CardDef Card; string Name;
    int Attack, RangedAttack, Armor, Health, MaxHealth, AttacksThisTurn;
    bool Exhausted, IsWarlord, HasShield, IsStunned;
    bool Has(string kw); int KwValue(string kw);
}

// Core/PlayerState.cs —— 一方
class PlayerState {
    List<CardDef> Deck, Hand, Discard;
    UnitState[] Board;            // 长度 9
    UnitState Warlord;            // == Board[4]
    int Energy, MaxEnergy, Fatigue, TurnCount;
}

// Core/BattleContext.cs —— 一局
class BattleContext {
    PlayerState[] Players;        // [0] 先手 [1] 后手
    int Turn, Active, Winner;
    Random Rng;                   // 种子化
    List<string> Events;          // 事件日志（自检/调试/将来接 UI）
}
```

### 关键词归一化

`card_stats.json` 里关键词是**带值的字符串**（`"Armour 1"` / `"Long Range"` / `"Can't Attack"`）。
归一化成 `小写去非字母数字` → 尾随数字当值：

| 原始 | 归一化名 | 值 |
|---|---|---|
| `Armour 1` | `armour` | 1 |
| `Long Range` | `longrange` | 1 |
| `Can't Attack` | `cantattack` | 1 |
| `Blast 2` | `blast` | 2 |
| `Shield` | `shield` | 1 |

## 五、公开 API

全部返回 `RuleCodes` 里的码（不抛异常 —— 非法操作是**正常流程**：拖到非法格位本来就该被拒绝）。

```csharp
// 开局
static BattleContext NewBattle(IList<CardDef> deckA, IList<CardDef> deckB, int seed = 0);

// 回合
static void BeginTurn(BattleContext ctx);        // 能量 / 抽牌 / 解疲劳（己方）
static int  EndTurn(BattleContext ctx);          // 能量作废 + 移交

// 出牌
static int  CanPlayCard(BattleContext ctx, int p, int handIdx, int slot);   // 只判不执行
static int  PlayCard(BattleContext ctx, int p, int handIdx, int slot);

// 攻击
static int  DeclareAttack(BattleContext ctx, int p, int atkSlot, int tgtP, int tgtSlot, bool ranged = false);
static int  IsValidTarget(BattleContext ctx, int p, int atkSlot, int tgtP, int tgtSlot, bool ranged);
static int  FieldAttack(BattleContext ctx, int p, UnitState u, bool ranged);

// 胜负
static int  CheckWinner(BattleContext ctx);      // 0 进行中 / 1 / 2 / 3 平局
```

`CanPlayCard` 存在的理由：表现层要在**拖拽过程中实时**知道「这张牌现在能不能打」，
不能等到松手才发现。和 `PlayCard` 走**同一份判据**，不是另写一份（基座那边同理：
`SimulateHover/Drag/Release` 和真实输入走同一套逻辑）。

### 表现层依赖的接口

```csharp
// Core/ICardProvider.cs —— 卡牌基座只依赖这一个
interface ICardProvider {
    string Id, Title;
    int Cost, Attack, Health, RangedAttack;
    bool IsUnit;
    IReadOnlyDictionary<string,int> Keywords;   // 规范化名 → X 值（armour→2、flying→1）
}
```

`CardDef` 实现它。「能不能打出」**不在这个接口里** —— 那需要上下文（谁的能量、哪一格），
是引擎的查询，不是卡的数据。

`CardView` 已经有 `id/title/cost/attack/health` 字段，接上去只多两个字段。

## 六、规则语义（逐条对齐权威来源）

以下每条都写明出处，**改之前先回去看 `rule_core.gd`**。

### 6.1 回合开始（`rule_core.begin_turn`）

```csharp
Turn++; TurnCount[active]++;
MaxEnergy = TurnCount[active] + 1;   // 先手第 1 回合 = 2 能
Energy = MaxEnergy;
foreach (己方单位) { Exhausted = false; AttacksThisTurn = 0; }
Draw(active, 1);
```

> ⚠️ **能量按「每方自己的回合数」算，不是全局回合数。**
> `rule_core.gd` 记着这条修正：「此前按全局回合数 → 后手首回合 2 能 / 先手第 2 回合 3 能，全对局能量曲线偏高」。
> 测试断言：`_test_begin_turn` 期望回合 1 能量 = 2。

### 6.2 打出单位（`rule_core.play_card`）

校验顺序**必须一致**（先费用后格位）：费用不够 → `ErrCost`；格位非法/被占 → `ErrSlot`。
测试断言：「非法格不扣费」「被占格拒绝」。

```
p 必须是 active                      → ErrNotTurn
handIdx 在范围内                     → ErrBadHand
cost > energy                        → ErrCost      ← 先判这个
slot ∉ [0,9) 或 slot == 4（督军格）   → ErrSlot
board[slot] != null                  → ErrSlot
扣费 → 从手牌移除 → 上场（Exhausted = true）
```

### 6.3 攻击（`rule_core.declare_attack`）

```
p 必须是 active                      → ErrNotTurn
攻击者存在且未疲劳                    → ErrNotUnit / ErrExhausted
未眩晕 / 有攻击力                     → ErrStunned / ErrNoAttack
目标合法（见 6.4）                    → 各种
攻击者：AttacksThisTurn++，Exhausted = true，Stealth 揭示
伤害 = 攻击力 → Damage() 结算
反击 = 目标的「近战攻击力」，除非攻击者是 Long Range
死亡检查
```

> ⚠️⚠️ **远程攻击默认也吃反击。** 只有 `Long Range` 免反击。
> 直觉上会写成「远程不受反击」，那是**错的** —— `rule_core.gd` 有明确修正记录：
> 「2026-08-21 修正：此前远程完全不吃反击，Long Range/Sniper 成死代码」。
> 测试：`_test_ranged_no_counter` 断言「远程未击杀 → 受目标反击 1 伤」。

### 6.4 目标合法性（`rule_core.is_valid_target`）

```
攻击者 Can't Attack      → ErrNoAttack
目标是自己               → ErrSelf
目标有 Stealth           → ErrTarget
敌方存在 Vanguard 且目标不是 → ErrTarget     ← 卡牌游戏的核心目标规则
近战 且 目标 Flying 且 攻击者非 Flying → ErrTarget
```

> ⚠️ **Flying 检查的是「目标」不是「攻击者」。** `rule_core.gd` 修正过方向：
> 「此前禁止飞行单位近战打地面、却允许地面近战打飞行」—— 正好反了。
> 正确语义：**飞行单位不能被近战打到**，远程正常，同为飞行可以。

### 6.5 伤害（`rule_core._damage_unit`）

```
Shield          → 免疫这次伤害并消耗掉，返回 0
Vulnerable X    → 伤害 +X
Armour X > 0    → 伤害 = max(1, 伤害 - X)     ← 最低 1，不是 0
Health -= 伤害
```

### 6.6 胜负（`rule_core.check_winner`）

```
督军 health <= 0 → 对方胜
双方督军同时 <= 0 → 平局（3）
```

### 6.7 疲劳（`rule_core._draw`）

```
牌库空 → Fatigue++；督军受 Fatigue 点伤害
```
> 疲劳伤害能杀死督军 → 每次 `Draw` 之后都要 `CheckWinner`。

## 六之二、技能与触发（2026-09-12 增补）

> 为什么要做：用户要的两类特效（**部队卡在场上发动技能**、**触发效果**）接不上 ——
> 不是特效的问题，是**引擎里根本没有这两种事件**，表现层无从得知。
> 落地情况见 `资料/规则引擎_进度与交接.md` 第七节。

### 6b.1 事件流：引擎说「谁在第几格做了什么」

```csharp
// Core/BattleEvent.cs
enum EvtKind { Deploy, Attack, Hit, Death, Ability, Trigger }

class BattleEvent {
    EvtKind Kind;
    int  Player, Slot;          // 归属方 / 己方第几格
    int  TargetPlayer, TargetSlot;   // 只有 Attack 用
    string CardId, Keyword, Effect;  // 卡名 / rally… / 效果原文
    int  Amount; bool Ranged; int Turn;
}
```

发射点（**全在 `RuleCore` 里，一处不少**）：

| 事件 | 发在哪 | 备注 |
|---|---|---|
| `Deploy` | `PlayCard` 放上场之后 | 之后紧接着 Rally |
| `Attack` | `DeclareAttack` **伤害之前** | 表现层才有「抬手 → 命中」的余地 |
| `Hit` | `ApplyDamage` + 疲劳那条路 | **护盾挡下发 `Amount = 0`** —— 「盾碎了」也要有反馈 |
| `Death` | `CleanupDeaths` | 督军倒下也发（槽位仍是 4） |
| `Ability` | `UseAbility` | 主动技能 |
| `Trigger` | `FireTriggerAt` | 五类触发，`Keyword` 说是哪一个 |

消费：`BattleContext.Signals` 累积，表现层 `DrainSignals(List<>)` **搬走并清空**。
「搬」而不是游标 —— 见交接文档第三节「事件流」那段的理由。

> ⚠️ **引擎不知道特效名。** 事件名 → 特效名的映射在表现层的 `CardPresentation/VfxMap.cs`。
> `RuleEngine/Core` 不许依赖 UnityEngine，也不该知道「Buff_Blue_SW」这种东西。

### 6b.2 效果：一个**封闭文法**，不解析 `desc`

```csharp
// Core/EffectSpec.cs —— `关键词: 动词 数值 目标`
EffectSpec.Parse("Damage 2 EnemyUnit")
//   Verb   ∈ damage / heal / draw
//   Amount = 省略则 1；负数判失败
//   Target ∈ Self / OwnWarlord / EnemyWarlord / EnemyUnit（Draw 不用写）
```

**为什么另起一套而不是解析原版 `desc`**：`rule_core._resolve_text` 有 670 行，是沼泽（见 §1）。
而我们这套卡是**自己设计的**，效果完全可以用封闭文法写清楚，写错了自检会当场抓到。

**解析不出来 = `null`，一律不猜**：`Damage 2` 这种没写目标的、`Deal 3 damage to an enemy`
这种自然语言的，全部判失败 → 记进 `CardDef.UnparsedEffects` → **卡面那个关键词打 `*`**。
不给默认值，是因为默认值会让效果变成「悄悄打了谁」—— 这工程最忌讳静默。

> `RuleCore.UnparsedEffects(cards)` 是给**卡池**用的诊断：原版那些
> `Rally: <一大段中文>` 会整片列出来。**关键词实现了 ≠ 这张卡的效果能跑**，两件事分开看。

### 6b.3 五个触发 + 一个主动技能

时机**逐条照抄规则书 :161 那张 61 关键词表**：

| 关键词 | 时机 | 实现位置 |
|---|---|---|
| `Rally` 集结 | 从手牌部署后 | `PlayCard` 末尾 |
| `Strike` 猛击 | 攻击后（本单位存活时） | `DeclareAttack` 末尾 |
| `Slay` 斩杀 | 攻击并**摧毁单位**后（本单位存活时） | 同上，只认部队（督军不算「被摧毁」） |
| `Backlash` 反噬 | 本单位死亡时 | `CleanupDeaths` |
| `Penitence` 忏悔 | 受到伤害但**未死亡**时 | `Hurt` |
| `Ability`（**本工程自定**） | 主动：花掉这个单位一次行动 | `UseAbility` |

> `Ability` 不是原版关键词 —— 原版的「替代行动」（职责 Duty / 狂暴 Ferocity / 祈祷 Pray /
> 议程 Agenda）是一族用法各异的东西，v1 先收成一条：「花一次行动换一个效果」。

### 6b.4 主动技能的规则

```
CanStartAbility：本方回合 / 在场上 / 有技能 / 没疲劳 / 没眩晕
CanUseAbility  ：CanStartAbility + 目标合法（只有 EnemyUnit 目标才要选）
UseAbility     ：Exhausted = true，AttacksThisTurn++，发 Ability 事件，结算效果
```

⚠️ **技能不是攻击**，所以攻击目标那三条限制里只有一条适用：

| 关键词 | 管不管技能 | 出处（原文） |
|---|---|---|
| 先锋 Vanguard | **不管** | 「其他单位不能被选为**攻击目标**」 |
| 飞行 Flying | **不管** | 「只能被…以**近战攻击**选中」 |
| 潜行 Stealth | **管** | 「不能被**任何方式**选中」 |
| 无法攻击 Can't Attack | **不管** | 只禁攻击 —— 0 攻单位能放技能，正是它的价值 |

**技能不吃反击**（反击是「被攻击」的结果），这是它相对平A的立身之本。

### 6b.5 递归与顺序

- **效果链是个环**：「受伤 → 打回去 → 那边也受伤 → 再打回来」（两个带忏悔的单位）。
  规则书 :237「同时触发」讲的就是它。用 `BattleContext.MaxEffectChain`（8 层）截断，
  **不指望「保证不会发生」**。
- **次序**：`Deploy → Rally`、`攻击伤害 → 反击 → Death → Slay → Strike`。
  斩杀排在猛击前面 —— 先结算「干掉了」这件更具体的事。
- **确定性**：触发类效果的 `EnemyUnit` 目标取敌方**槽号最小**的活部队，**不掷骰** ——
  种子只该影响洗牌。自检里有「同种子 → 事件流逐条一致」。

```
│   ├── BattleEvent.cs        **结构化事件流**（EvtKind + BattleEvent）
│   ├── UnitState.cs          场上单位
│   ├── PlayerState.cs        一方
│   ├── BattleContext.cs      一局 + 种子化随机 + Signals
│   ├── ICardProvider.cs      表现层唯一依赖
│   └── RuleCore.cs           核心规则 + 触发/技能
├── Data/
│   ├── CardDatabase.cs       JSON → CardDef（唯一碰 JsonUtility 的地方）
│   ├── DeckBuilder.cs        凑一副能打的 30 张牌组
│   └── Resources/cards_engine.json   精简后的卡表（构建器生成，见下）
└── Editor/
    └── RuleEngineTest.cs       纯逻辑自检（395 条断言）
```

**为什么要 `cards_engine.json` 这一道**：原始 `card_stats.json` 有 978 KB，
大头是 `art` / `voice` / `ocrSrc` 这些**引擎用不到的路径字符串**；而且数值字段大量为 `null`，
`JsonUtility` 遇到显式 null 不可靠。生成器一次解决两件事：精简到 **232 KB** + 把 null 归一化成 0。
放 `Resources/` 是为了运行时 `Resources.Load<TextAsset>("cards_engine")` 能取到。
构建器**幂等可重跑**，跟 `gen_effect_index.py` → `EffectLibraryBuilder` 一个套路。

**落地进度见** `资料/规则引擎_进度与交接.md` —— 下面原先列的六步（`Core/` → 精简卡表 →
纯逻辑自检 → 棋盘 7→9 → `ICardProvider` 接进表现层 → 脚本驱动打一局）**全部做完了**；
精简卡表能从原始卡池读出 **1211 张卡**。
