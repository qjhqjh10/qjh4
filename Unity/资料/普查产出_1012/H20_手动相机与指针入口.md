## 四、没查清 / 待判据（⛔ 不猜）

1. 🔴 **滚轮量纲那一除（`/120`）是我们挑的等价物**：原版读 legacy `Input.mouseScrollDelta.y`（Windows 一格 ±1），我们只能读新输入系统（`activeInputHandler: 1` ⇒ legacy 不可用），`Mouse.current.scroll.ReadValue().y` 一格 **±120**（同源口径 = `Shell/MenuScroll.cs:200`）。**⇒ 一格到底该走多少 zoom 只有真 Play 才量得准**（`zoomSensitivity = 0.1` 是照 legacy 单位定的）。真 Play 时若手感太快/太慢，改 `ScrollUnitsPerNotch` **一处**。
2. 🔴 **`zoomSpeed` 当 `SmoothDamp` 的 smoothTime 系数**（`smoothTime = Time.deltaTime × 12.5`）—— 这个**非标准用法**（一般 `smoothTime` 是个固定秒数）是我按 Microsoft x64 **位置制**把 `.c` 里那三个被吃掉的实参还原出来的（`:18060D00F` 那一处：`xmm0=current` `xmm1=target` `r8=ref` `xmm3=smoothTime` `[rsp+0x20]=+∞` `[rsp+0x28]=deltaTime`）。语义上与 `Vector2.SmoothDamp` 那一处**同构**（两处独立调用得出同一映射）⇒ 可信，但**没在实况里量过收敛速度**。
3. ⚠️ **`BattleCameraSreenSize`（TypeDefIndex 493）整件没做** —— `CombatCameraZoom` 那对事件的**触发源缺**（文件头 D）。它的序列化值（`sensorSizeXSmall 37.0` / `sensorSizeXBigScreen 41.0` / `animTime 3.0`）已读出来但**没用**。

## 五、顺手发现（⛔ 只报不改）

1. 🔴🔴 **六处「反编译器认错的操作数」，其中一处照 `.c` 抄会静默画错**（`CombatCameraZoom__ApplyZoom.c` 是本件最大的一处证据）：
   - `0x18060D22A/D232` 「贴近就吸附」那一句：`.c` 写成 `targetLensShift = vcamLensShift − desiredLensShift`（≈ 0 ⇒ 镜头每帧被拉回零点），**指令流里写的是 `[rbx+0x88]=xmm3 / [rbx+0x8c]=xmm4`，而 `xmm3/xmm4 = desiredLensShift`** ⇒ 正确语义是 `targetLensShift = desiredLensShift`。
   - `0x18060D00F` / `0x18060D314` 两处 `SmoothDamp` 的**三个实参**（`smoothTime = dt × zoomSpeed` · `maxSpeed = +∞` · `deltaTime`）—— `.c` 里只剩一个 `uVar5 = SmoothDamp()`。
   - `0x18060E4A3`（`GetWorldPositionUnderMouse`）那两个「`Vector2.one`」实为 **`Vector2.zero` 与 `Vector2.one` 两个不同的静态字段**（`zero@+0`、`one@+8`）。
   - `0x18060E4F8/0x18060E500`（`HandleDrag`）两条 rip 相对常量**同一个地址** `0x1834B2BC8` = **−1.0**（不是 +1）。
   - `0x18060E608`（`HandleManualControl`）那两个被认成 `WebSocketSharp…get_Count` / `UIElements…get_sizeType` 的调用 = **`Touch.get_phase`** 与 **`Touch.get_fingerId`**（RVA 共用桩）。
   - `0x18060D8ED-D91E`（`ClampShiftLimits` 尾段）证明它**就是调 `CorrectLensShift`**，且 x 用 `sensorSize.x`、y 用 `sensorSize.y`。
   > ⇒ **新知识（可复用）**：`Mathf.SmoothDamp`/`Vector2.SmoothDamp` 在 il2cpp 的 x64 调用是**位置制**：位置 2 的 `ref` 占 `r8`、位置 3/4/5 的浮点分别进 `xmm3` 与**栈** `[rsp+0x20]`/`[rsp+0x28]`。Ghidra 对这两个 API 的实参**系统性丢失**，不是偶发。
2. 🔴 **`CombatCameraZoom` 的 `SetZoomLevel(…, instant)` 里 `instant` 那一档，原版自己也没人走**：全反编译里 `SetZoomLevel` 只有**一个**调用点（教学 `BattleManager._TutorialStartSequence_d__592__MoveNext.c:149`，且传 `instant: false`）。我们拿它当「无帧循环」那一档的**同类**（但最后没用它，而是用 `SettleFraming` —— 因为 `instant` 只写 `currentZoomLevel`、**不落点**）。
3. 🟡 **`A422` 让我们这一档第一次真的动了 `lensShift.x`**：原来 `ApplyFraming()` 只写 `.y`，现在 `ApplyVirtualCameraLensShift` 写**整个 Vector2** ⇒ 世界边界那一条会把 `.x` 定到 **+3.873e-4**（= 视野矩形的 `xMin` 刚好贴回 `worldBounds.xMin`）。**这是原版的行为**（按原版 x=100/界=89.95 算出来同一个数）⇒ 视野中心偏 **0.0078 世界单位 ≈ 0.84 px**，量级可忽略，但它**不再恒等于烘进场景的 0**。后面谁做「重烘 `Battle.unity`」时别把这一格当成不一致。
4. 🔴 **A445 只对齐了「哪条链」，没有对齐「按下还是抬起」—— 而且这一条是驱动层的，不是这一行的。**
   判据（本件亲读）：`BattleDriver.HandleSettings` 是 `if (ClickedThisFrame() && !captured) SettingsClickAt(...)`，
   而 `ClickedThisFrame()` 是**按下沿 latch**（`bool down = PointerHeld(); if (!down) { _clickLatch = false; return false; } if (_clickLatch) return false; _clickLatch = true; ... return true;`
   —— 注释自己写着「用 latch 防止按住触发多次」）⇒ **`SettingsClickAt` 的四颗（Resign / Difficulty / Close / 本行）在我们这一档全部是「按下那一帧」**，
   而原版那四颗都是 uGUI `Selectable`/`Toggle` 的 `IPointerClickHandler`（**抬起**）。
   ⇒ **这不是 A445 的残件，是驱动层既有的一处全局差异**；要真做成「抬起」得动 `ClickedThisFrame`（会影响另三颗）、
   **本件不越界**，如实记并建议**单开一笔账**（铁律 11：先记录、之后完全复刻）。
   ⚠️ 另：A445 之后 A424 的断言**也分不出**按下/抬起（`SettingsClickAt` 是一次点击一次调用）⇒ 这一半只能代码审查或真 Play。
5. 🟡 **类型检查期间两次红都只在别人的在飞文件上**（判据 = 诊断全部集中在那两个文件、本件四个文件 0 条）：`Editor/RewardWindowFixture.cs` CS0246（缺 `RewardWindow`）、`Shell/MenuDraw.cs(993,30)` CS1503（`PxRect?` → `PxRect`）→ **都随后自愈**。
