## 三、连带：A175 的两个期望值（**并且原来那条「前提」是红的**）

### 3.1 算式（写在 `Editor/BattleScene.cs:9600-9612`，⛔ 不读被测实现）

```text
minY       = 249.9 / 1080                              = 0.2313889
maxY(zoom) = (1080 − 96.7)/1080 + PadMod(aspect)×PadByZoom(zoom)
           = 0.9104630 + PadMod(aspect) × PadByZoom(zoom)
arg        = (maxY + minY) × 0.5 ；lensShift.y = ViewShift(arg)
```

### 3.2 两档实算（本件用 Python 逐段 Hermite，独立于 C# 实现）

| 曲线版本 \ 宽高比 | 16:9（= 1.7777778，**实况**） | ≤1.77（`PadMod ≡ 1`） |
|---|---|---|
| **原版 / 订正后**，`zoom = 1` | **−0.21054205** | −0.21026461 |
| **原版 / 订正后**，`zoom = 0` | **−0.25083587** | −0.25079288 |
| 我们**抄错的**那版，`zoom = 1` | −0.20793118 | −0.20794265 |
| 我们**抄错的**那版，`zoom = 0` | −0.25054962 | −0.25055129 |

* ⇒ **订正前后差 0.00261 / 0.00029**（前者 **> 容差 0.001** ⇒ 曲线被改回旧值，A175 那条会红 —— 这就是它的「改坏法」）。
* H8 报告 §5·1 的 `−0.210265 / −0.250793` = **上表右列**（`PadMod ≡ 1`）⇒ 它没把「实况是 16:9、`PadMod = 0.9951903`」算进去。
  本件**取左列**（实况那一对）。
* 🔴 旧值 `−0.207943 / −0.250551` = **右下角那一格**（我们错曲线 × `PadMod ≡ 1`）—— H8 说的「那两条钉的是实现里那份错值」**逐位对上**。

### 3.3 🔴 顺带查出：那条「前提」断言**当场就是红的**

`Editor/BattleScene.cs` 原来第 ② 条断的是 `aspect >= 1.333 − 1e-4 && aspect <= 1.77 + 1e-4`，
注释写着「只有这一档下 `PadMod ≡ 1`，下面两个期望值才成立」。而：

* **实况 `driver.boardCam.aspect` = 16:9 = 1.7777778** —— `Shot()` 里 `cam.aspect = (float)1920 / 1080`（`BattleScene.cs` 的 `Shot`），
  而 `Shot` 在整轮里被调过几十次（第一次就是 `01_开局`），A175 段落在**行 9543**（远在其后）⇒ 到那一刻宽高比**恒是 16:9**；
  `ArenaBuilder.ConfigureBoardCamera` **不设** `aspect`（本件现读核过）⇒ 没有第二个写点。
* `1.7777778 > 1.7701` ⇒ **那条 Check 必红**（不是「随环境变」，是**写死了**必须红）。
* 而且 `verticalPaddingModifierByAspectRatio(16:9) = 0.9951903 ≠ 1`：曲线在**第 3 键 1.77 之后**才掉，16:9 已经进了下降段
  （H8 那句「这一档只在宽高比 > 1.77 时被采 ⇒ 16:9 看不出来」在**数值大小**上是对的（差 2.8e-4），但**前提本身仍然不成立**）。
* **本件改成**：断 `|aspect − 16f/9f| < 1e-4`（把实况钉住），并在注释里写明两个期望值是按 16:9 + `PadMod = 0.9951903` 算的。

## 七、顺手发现（⛔ 只报不改）

1. 🟡 **Unity 曲线的 wrap 模式：序列化编号 ≠ C# 枚举编号（实测）—— 所以「原版 `m_PreInfinity = 2` = `WrapMode.Clamp`」这句话不能按编号理解。**
   * **实测 A（两处独立命中）**：`WarpforgeArena1/Editor/SunFlareData.gen.cs` 里显式写 `preWrapMode = (WrapMode)2`（92 处；
     生成器 `工具/gen_sunflare_cs.py:73-75` 把**原版串化值**原样 cast 进去，`d.get("m_PreInfinity", 2)`）。这批数据走**两条消费路**：
     · `ArenaBuilder.EnsureSunFlareAsset()` → `flares/Sun Flare 1.asset`（`LensFlareDataSRP`）⇒ 曲线串化成 **`m_PreInfinity: 1`**；
     · `ArenaBuilder.cs:2475-2477` → 各战场 prefab 里的 **`LensFlareComponentSRP`**（就是 `ArenaPrefabs/*.prefab` 里那 36 处 `m_PreInfinity: 1`，
     `git` 侧本件现读：`battlearena1.prefab:22194` 那一块，`m_Script` guid `cc4d76f733087744991913c9d19d5274`）。
     ⇒ **`(WrapMode)2` → 串化 `1`**（两条路都验到）。
   * **实测 B**：我们代码建的、**没显式设过** wrap 的曲线，序列化出来是 **`2`**（`Resources/ArenaPrefabs/*.prefab` 里大量，单
     `battlearenatauviorla.prefab` 就 12727 处；`WarpforgeVFX/Prefabs/*.prefab` 里也是）—— 而清单 `Resources/arenas/*/*.json`
     **根本没有 `m_PreInfinity` 这个键**（本件 grep 过）⇒ 那些曲线只能是「按键数据现建、用默认值」的那一档。
   * **推论**：`m_PreInfinity/m_PostInfinity = 2`（原版 DLL 里那份）**与「我们代码建的曲线」是同一个值**
     ⇒ **我们那三条曲线用的默认 wrap 模式与原版一致**（这一条才是要紧的：**探针/复刻都不用去动它**）。
     ⚠️ 而 H8 在 `OriginalCameraSizeXCurve()` 里写的 `WrapMode.Clamp`（C# 枚举值 **1**）**按编号算不是 2** ——
     它**语义上**大概率等价（Unity 的默认就是 Clamp 语义），但**这两句话不是同一件事**，H8 的注释把编号当成了同一个，**未经证实**。
