## A1631：「半懂」现在丢在哪 · 改成什么 · 实测面改前/改后 · 能红的判据

### 病（改前）

`Core/CardDef.cs` 的 `AddTriggerOp`（收一条触发正文的唯一入口）原来写的是

```csharp
var ops = EffectText.Parse(body, out _, out _);   // ← 两个出参【都丢】
if (ops == null || ops.Count == 0) return;
_triggerOps[key] = ops;
_triggerText[key] = body;
```

⇒ 同一段正文里**解得出的那几句被收下、解不出的那几句不留痕**。
后果：任何「`TriggerOps(kw) != null` ⇒ 这条正文没问题」的判据在**半懂**那一档**报假绿**
（`CardDef.BodyResolves` · `UnitState.FxOps` / `EffectUnparsed` / `HasFx` 那一族）。

**改前实测**（离线探针，真池 1126 张）：

```
① 全池 `TriggerTexts` = 370 条 · 其中「半懂」= 1 条
   EC8/rally  un=1 [`Friendly Daemonette have Flank`]  pa=0
   而 BodyResolves(rally) = True      ← 假绿
② 引擎侧留痕： `CardDef.TriggerBodyGaps` ✗ 不存在 · `TriggerGap` ✗ · `BodyFullyResolves` ✗
   ⇒ 引擎对「半懂」**没有任何痕迹**
```

### 改成什么

| 位置 | 改了什么 |
|---|---|
| `Core/CardDef.cs`（`AddTriggerOp`） | 两个出参**接住**；`un`/`pa` 非空就记一条账（`NoteTriggerBodyGap`） |
| `Core/CardDef.cs`（新增，紧随其后） | `public class TriggerBodyGap { CardId · Keyword · Body · Unparsed · Partial · OpCount }`；静态总账 `TriggerBodyGaps` ＋ `ClearTriggerBodyGaps()`；实例查询 `TriggerGap(keyword)`；严格判据 `BodyFullyResolves(keyword)`（= `BodyResolves` ∧ 无半懂账目） |
| `Core/CardDef.cs`（`BodyResolves` doc） | 补一句「**它不管正文全不全懂**」＋ 指向 `BodyFullyResolves`（⛔ 不改它的语义：`TestA1618` 盯着它） |
| `Core/UnitState.cs`（`EffectUnparsed`） | 改问 `BodyFullyResolves` —— 半懂那一档**也如实打 `*`**（红线：不许静默失败） |

**「谁读、读到什么」** = 账目里那四格：`CardId` ＋ `Keyword`（**谁**）· `Body`（**读到的是什么**）·
`Unparsed` / `Partial`（**哪几句没懂**）＋ `OpCount`（**收下了几个 op**）。

⚠️ **只记「半懂」**（`ops.Count > 0`）。整条都不懂（`ops` 为空 ⇒ 句法上直接 `return`、`_triggerOps` 里没有那一格）
是**另一档**，它本来就被 `TriggerOps(...) == null` 如实反映（卡面打 `*`）—— 两档别混。

## A1455 / AM56：为什么筛不到 · 改法 · 改前/改后

### 为什么筛不到 —— **因为那条读数取自空卡池的夹具**

`CreatePool.Resolve` 是「造什么 / 部署什么」的**唯一**筛选口，它的第 1 句之后就是

```csharp
if (pool == null) { r.Why = "这一局没有卡池（`RuleCore.NewBattle` 没传 `cardPool`）"; return r; }
```

而上一批用的夹具 `RuleEngineTest.ProbeBattle` 传的是 **`cardPool: new List<CardDef>()`**（**空池**）
⇒ `FindByNameLoose(空池, "shock trooper")` 恒 `null`、`FindNearMiss` 也恒 `null`
⇒ 报「既不是原版卡名、也不是我们认识的兵种词（原版数据里没有这张卡）」，**而且连「最接近的是…」都没有**——
那句缺失正是「池子是空的」的指纹。

## 顺手发现

### ① 🔴 卡名索引「先造卡、后建索引」⇒ 同一份卡表第一次装载与第二次装载解析出不同的 op（**已修**）

- **判据链**：`CardDef` 的**构造函数**里就跑 `CollectTriggerOps` ⇒ `EffectText.Parse` ⇒ 目标解析
  ⇒ `TailCardName`（`Core/EffectText.cs:8122-8147`）⇒ `CreatePool.MatchCardName`（读**静态** `_nameIndex`）。
  而 `CardDatabase.Parse` 原来是「**先把 1126 张 `CardDef` 全造完**、最后才 `CreatePool.BuildNameIndex(list)`」
  （`Data/CardDatabase.cs` 的 `foreach` 之后那一句）。
  ⇒ **构造期读到的是【上一趟留下的】索引**：本进程**第一次** `Load()` ⇒ 索引**空**；之后每一次 ⇒ 上一趟那份。
- **实测（`load` 模式，真 `CardDatabase.Parse`）**：改前 **冷 ⇒ `UM_Angels_of_Death` 的 `codex` 目标 = `null`**、
  **热 ⇒ `name=Primaris Intercessor`**；冷/热两态下 `TriggerOps` 全签名不同的卡 = **1 张**（`UM_Angels_of_Death`）。
  改后：冷 = 热、**0 张**。
- **为什么算缺陷（两条红线都踩）**：① 卡面写的目标**静默丢掉**（`Target = null` ⇒ 结算层要么打宽、要么空过，
  两种都不是卡面写的那个）；② **同一份卡表、第一次装载 ≠ 第二次装载** ⇒ **对局不可复现**。
- **改法**：`CardDatabase.Parse` **先**用 DTO 里的名字建索引（`CreatePool.BuildNameIndexFromNames`，
  新增的「只给名字」形态；`BuildNameIndex(list)` 保留、逐字等价、幂等），**再**造 `CardDef`。
  ⚠️ **副作用面已量**：全池 1126 张、比 `TriggerTexts` / `WhenTriggers` / `SpiritOps` / `OathOps` /
  `FaithOps` / `AuraSpecs` / `Ability` 的**全部 op 与目标规格** ⇒ 只差 `UM_Angels_of_Death` 这一张。
  自检侧的风险：全仓 **0 处**断言提到这张卡（`grep Angels_of_Death` 只命中两条注释）。
- ⚠️ **它和 `A1631` 的实测面是同一件事的两半**：修掉它之后，`A1631` 的「半懂」从账上写的 2 条变成**真的 1 条**。
  ⇒ 我把它**一并修了**（铁律 14：新发现的问题插队）。**若调度台不认这一笔，回滚点很小**：
  `CardDatabase.cs` 那 23 行 ＋ `CreatePool.cs` 的 `BuildNameIndexFromNames` 拆函数。

### ② 上一批那份「`A1455` / `AM56` 部署不了」的读数**来自空池夹具** —— 建议顺手核一遍同一批的其它读数
