## 顺手发现

### ① 🔴 `A1494④` 那半句**与事实不符**（要就地订正 —— 我没有正本写权限，请调度台改）

`项目任务.md` / `任务_卡组卡牌战斗.md` 的 `A1494④` 写着：
「**`MainMenu.unity` 里带着 3 个 `WindowHolder` 且 `placement = None`**（场景里不该有，要查是谁写进去的）」。

**现读（`grep -c`，绝对路径 `Unity/MyGame/Assets/CardPresentation/Scenes/MainMenu.unity`）**：

```
WindowHolder   0
WindowsManager 0
Window Anchors 0
```

⇒ **那个场景里一个都没有**（`Shell.unity` 才是有的那份：`WindowHolder 3 · WindowsManager 2 · Window Anchors 1`）。

**那三条报错的真身**：`WindowsManager.MakeHolder` 里
`AddComponent<WindowHolder>()` 那一刻 `OnEnable` **立刻**跑（`WindowHolder` 带 `[ExecuteAlways]`），
而 `placement` 还是默认 `None` ⇒ `RegisterAnchor(None, …)` 报三条错。
**顺序可证**：真机日志 `_tmp_view/run_shell.log:78-80` 那三条**排在 `:81`
`[Win] 场景里没有 WindowsManager ⇒ 现建了一台 + 三个锚点` 之前** —— 而 `EnsureHost` 是
**先 `MakeHolder()` ×3、后建那台 WM 并打那句日志**。
**已修**（`MakeHolder` 改成「先关物体 → `AddComponent` → 赋 `placement` → 激活」⇒ 一条假报错都不出）。

> ⚠️ **这条值得单独记一笔**：那三条红字**看起来非常像「场景文件坏了」**（调度台这次就是照它推的），
> 而它其实是**我们自己的构造噪音**。同类先例在本仓已有多条（「只在失败时打日志 = 三种结局分不出」）。

### ② 🔴 `GetWindowAnchor(None)` 把原版**合法档位**当缺陷报错（已修）

原版 `MainMenuWindow` 的 `windowsPlacement = 0`（= `None`）是**显式写死的「不挂 Holder」**
（`bundle_scenes_scenes_mainmenuwarpforge/MonoBehaviour/MonoBehaviour_1927.json`）。
而本仓原来没有 `None` 那一支 ⇒ 走到 `找不到 None 的锚点 —— 场景里缺对应的 WindowHolder` ——
**与本文件 `RegisterAnchor` 里那句报错文案自相矛盾**（那句写着「`None` 只用于『不挂 Holder』的窗口，如 `MainMenuWindow`」）。
⇒ 已改成 `None` **早退返回 null、不出声**，并在 `AttachToAnchor` 对应早退。
⚠️ 与哨兵 `-1`（忘了赋值，必须出声）**不是一档**，注释里写明了。

### ③ ⚠️ 打进包里的美术**几乎全是未压缩的 `RGBA32`**（内存与加载时间的共同上游）

本机 UnityPy 现读 `_tmp_view/player/WarpforgePlayer_Data/resources.assets`（该文件 **4.55 GB** + `.resS` **2.21 GB**）：
