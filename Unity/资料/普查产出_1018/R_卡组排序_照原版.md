## 1. 结论

### 1·1 「杂乱无章」的根因 = 第二把键用了**码点序**，而原版用的是**当前文化比较**

改之前的实现是 `费用升序 → CardText.Name 的 CompareOrdinal（码点序）→ Id`。
**顺序本身是稳定、确定的**，问题在第二把键的语义：

- 🔴 **原版 `OrderBy/ThenBy` 没传 `IComparer`** ⇒ 走 `Comparer<string>.Default` ⇒ `string.CompareTo`
  ⇒ **`StringComparison.CurrentCulture`**（文化相关）。
- 我们的旧实现用的是 `CompareOrdinal`（UTF-16 码点序）。
- 对中文名来说，**码点序 = 按「字的 Unicode 编号」排**，既不是拼音、也不是笔画
  ⇒ 玩家看到的就是一列**读不出规律**的名字（直观上就是「乱」）。

**本轮先按用户要求改成过「按卡牌 ID」，随后用户 2026-10-18 拍板「照原版」** ⇒
现已改回 `费用 → 本地化名的当前文化比较 → Id`，并把 `CompareOrdinal` 这条偏离**删掉**。

### 1·2 原版判据（现读反编译，两个 lambda 体都在）

`d:/2/tools/decomp_full/`：

- `DeckListDrawer__Reorder.c`：`list.OrderBy(键1).ThenBy(键2).ToList()`，随后**显式钉回**：
  督军 `SetSiblingIndex(0)`、防御卡 `SetSiblingIndex(hero 存在 ? 1 : 0)`。
- `DeckListDrawer.__c___Reorder_b__22_0.c`：`*(int*)(*(longlong*)(行 + 0x78) + 0x78)`
  = **`RawCardScript.manaCost`**（费用；`+0x78` 偏移出处 `资料/AI_原版反编译_0917.md:42`）。
- `DeckListDrawer.__c___Reorder_b__22_1.c`：`RawCardScript__GetLocalizedCardName(…)`
  = **本地化卡名**。
- ⚠️ **比较器**：调用点**没传 `IComparer`** ⇒ 两把键都是默认比较器；键2 的 `T` 是 `string`
  ⇒ `Comparer<string>.Default` ⇒ 文化相关比较（**不是**序数比较）。

> 顺带订正（铁律 5）：`DeckRuntime.DeckEntries()` 原注释写「两个匿名函数方法体没反编译出来」——
> **不成立**，两个方法体都有独立文件（见上）。已在原处改掉并保留更正痕迹。

## 2. 新排序键的完整定义（**全序**）

实现 = `DeckRuntime.DeckEntries()` 里的 `cards.Sort(...)`：

1. **督军恒第 0 行、防御卡恒紧随其后**（有督军 ⇒ 第 1 行；没有督军 ⇒ 防御卡第 0 行）。
   这两行**不进排序**（原版也是排完再 `SetSiblingIndex` 钉回）。
   `WarlordId` / `DefensiveId` 也会先记进去重集合（防止 `CardIds` 里混进同一条时出两行）。
2. 其余卡：
   1. **费用升序**（`CardDef.Cost`）；
   2. **显示名**（`CardText.Name(c)`）的 **`StringComparison.CurrentCulture`** 比较；
   3. **`Id` 的序数比较** —— 只为保证**全序**（`List.Sort` 不稳定；池里 `Id` 唯一，1,127/1,127）。
3. ⚠️ **「文化相关」的含义**：顺序由**运行环境的当前文化**决定 ——
   本机（Windows 11 Home China，`CurrentCulture = zh-CN`）下汉字按**拼音**排；
   换成 en-US 等文化，汉字会按另一套 ICU 排序规则排（实测 en-US 下与码点序一致）。
   这正是原版 `Comparer<string>.Default` 的行为（复刻它，而不是钉死一个固定序）。

## 4. 文化比较 vs 码点序：真数据上的证据（**这就是修的那条**）

运行环境：`CultureInfo.CurrentCulture = zh-CN`（中文（中国））。

### 4·1 最直观的一对（演示牌自检 ⑥ 的判别式就抓这种对）

| 卡 | 名字 | 拼音 | 码点 |
|---|---|---|---|
| `ASH5` | 风暴守护者 | **feng** | 风 U+98CE |
| `ASH4` | 守护者防御小队 | **shou** | 守 U+5B88 |

- **文化序（zh-CN）**：`风暴守护者` < `守护者防御小队`（feng < shou）
- **码点序**：`守护者防御小队` < `风暴守护者`（U+5B88 < U+98CE）
- ⇒ 两把键**方向相反**，自检 ⑥ 会明确报出这一对。

## 6. 没查清的部分

1. **「原版那份实拍到底是哪个文化」没查清**。参考图上 `女 < 帷 < 突` 与我们 en-US 的结果一致、
   与 zh-CN 拼音序相反。若要求「与原版逐像素一致」，需要确定客户端实际运行的文化
   （或把比较器钉成某一个 `CultureInfo`）—— 这超出本笔授权，留主对话裁。
2. Unity/Mono 的 ICU 版本与 .NET 8 的 ICU 是否对每个生僻字都给同一顺序：未逐字验证；
   自检 ⑥ 用运行时重算规避了这个风险。
3. `DeckListDrawer__Reorder.c` 里 `param_1 + 0x30` 那个被 `SetSiblingIndex(1)` 的对象
   **没定位到具体字段**（推测是「防御卡槽位」占位件；防御卡本体另有 `hero?1:0` 的钉法）。
4. 本地化名的**语言分支**（官方 13 语言）在排序里的影响：本笔只确认中文档（`Loc.Current` 为中文）
   的自检路径；非中英语档下 `CardText.Name(c)` 走 `Card_Name/<id>`，排序会按该语种名排 ——
   这一路**没有断言覆盖**。

## 7. 顺手发现（⛔ 都没顺手改，留给主对话裁）

1. **旧注释是错的**（已在白名单内就地改）：`Reorder` 的两个 lambda 体存在，且 `ThenBy` **没传 comparer**
   ⇒ 原版第二把键是**文化相关**比较，旧实现的 `CompareOrdinal` 是偏离（也就是「看着乱」的根因）。
2. **一个潜伏的小缺陷（本轮顺带堵上）**：旧 `DeckEntries()` 的去重集合**只记 `CardIds`**，
   若 `WarlordId` / `DefensiveId` 同时也在 `CardIds` 里，同一张卡会占**两行**。
   本轮把这两个 id 先记进 `seen`，并在 `DeckScene` ⑧ 加「`ASH83` 只出现 1 次」的断言。
   （常规路径不触发：`TryAdd` 对 hero / defence 写的是两个独立字段。）
3. **127 张 32 位 hex id 卡基本进不了卡组**：`CannotAddToDeck` 现读判据 =
   `inventoryOptions != 0 || showInCollectionOptions != 5` ⇒ 其中 **113 张被挡**
   （`inventoryOptions = 10`、`showInCollectionOptions = 0`）；**14 张两列都是 `-1`（真值缺失 ⇒ 不挡）**。
   103 副预组**没有一副**带 hex id。（与排序无关，属数据侧知识。）
4. **卡池（`RefreshPool` / `VisibleCards`）仍是卡表原序**、不排序 —— 与卡组行排序是两件事，按边界没动。
