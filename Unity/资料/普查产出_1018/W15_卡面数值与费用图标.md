**全 150 个卡框的统计（旧常量 → 凹槽圆心）**：

| | 面像素位移 中位数 | p90 | 最大 |
|---|---|---|---|
| 近战 | **10.4 px** | 16.2 | 20.0（`frame_leviathan_strat`） |

| 血量 | 6.3 px | 12.3 | 14.2 |

> 换算：手牌卡宽 165 px 时 1 面像素 ≈ 0.64 屏像素；详情窗大卡（宽 ≈ 420 px）≈ 1.64 屏像素。
> ⇒ 10 面像素 ≈ **6～17 屏像素**，肉眼就能看出「数字偏在圈外」。

### 1.3 根因

1. 凹槽是**卡框贴图**里的画，落点 = `f(这张卡框的 uv)`：
   `FrameUv`（贴图 alpha bbox）→ 拉伸进**固定矩形** `FrameQuad`（2.2452×3.2572 @ y −0.03）。
2. 每个卡框的 alpha bbox 宽窄不同（`Resources/frame_uv.json` 里 `sw` **0.594～0.659**） ⇒ 拉伸比不同。
3. 于是**同一个凹槽**在不同卡框上落到不同卡单位：近战 x01 跨 **0.021～0.132（= 11% 卡宽）**。
4. 数字却用固定常量 ⇒ **只可能对一种卡框正确**，其余全偏。

（顺带：这也解释了为什么「每换一档卡框，数字就偏一点」。）

### 1.4 改法

新增 `FramePxAt01(frameTex, px, py)`：把**卡框贴图上的像素**按 `FrameUv` + `FrameQuad` 换成
卡面归一化坐标（**与 `FrameMesh` 画框那条链逐字同一套**，不另写一份）。
`FaceStatAt01(s, frameTex)` 用它算三个圈的落点；**没有卡框（占位卡面）时退回旧常量**。

| 底边 | **y = 235.5**（各阵营 225～248，均值 235） |

### 2.2 我们原来的位置

`CostAt = (0.8766, 0.3001)`（= 原版 `Cost Container` 位置） ⇒ 费用中心在卡单位 y = **+0.666**，

详情窗大卡约 **11 屏像素**，手牌卡约 5 px）。另外 **x 也偏右 0.04 卡宽**（徽记没和它同心）。

### 2.3 改法

`FaceCostAt01(frameTex)`：

```
徽记底边（卡单位）  = FramePxAt01(徽记圆心x, 徽记圆心y + 半径)
费用中心 y         = 徽记底边 − CostBadgeGap(0.02) − CostBgH/2
费用中心 x         = 徽记圆心 x
```

`CostBadgeGap = 0.02` 卡单位：原版实拍那道缝 5/595 × 3.3313 ≈ 0.028，扣掉费用图自己的
上缘透明边（`Card_Frame_Cost_Icon.png` 不透明 bbox 从 y=3 起，≈0.006）⇒ 取 0.02。

费用**底板**（`costBg` 那一层，`SpriteQuad` 把位置烘进网格）与**数字**（烘进 `_info`）现在
**同一份判据**，不会再分家。

## 五、没查清 / 仍开着

1. **更深一层的根因（未修，超出本单白名单）**：我们画卡框用的是**每张贴图自己的 alpha bbox**
   （`FrameUv`），而原版那批 sprite（`40k_Cardframe_*_SDF_tierN`）的 `m_Rect` 是**128×128 固定画布、
   `textureRect=(24,6,81,110)` 对所有阵营/所有 tier 完全一致** ⇒ 原版大概率是**固定画布映射**，
   凹槽在原版里是**不动的**。我们按 bbox 拉伸 ⇒ 连**卡框本身**每档的缩放都不同。
   ⇒ 本单只把「数字/费用」对齐到**我们实际画出来的凹槽**；要不要把卡框改成固定画布映射，
   是「卡框」那一段的活，需要单独一轮（会改动所有卡的框大小/位置，风险大）。
   判据与实测：各卡框 `sw` 0.594～0.659（`Resources/frame_uv.json`）。
2. **`PragatiDigits` 的 `bearingX` 从未生效**（`Core/PragatiDigits.cs:99-107`，`Glyph.bearingX` 存了却没用）
   ⇒ 数字的**墨迹中心**比传入的 `cx` 固定偏左 **≈1.4 面像素**（adv−w 的一半）。
   本次没改（那个文件不在本单白名单）。量级：0.5% 卡宽，肉眼几乎看不出；要修只需在
   `Draw` 里把 `x` 起点加上 `g.bearingX`。
3. **护甲数字 vs 盾牌**：`ArmourAt`（数字 y01 **0.7975**）比 `ArmourIconAt`（盾 y01 **0.80710**）
   低 0.0096（= 0.032 卡单位）；原版 `Armour Text` 只比 `Image` 低 0.01 卡单位。差 0.022 卡单位（≈0.7% 卡高）。
   不属于本次两条报障（盾是**我们自己的图**、卡框里没有它的凹槽），**未改**，列在这里待办。
   出处：`子代理读报_2dcard_0827.md` A2 表 `Armour Container` 两条子节点。
4. **徽记尺寸/位置各阵营不同**（半径 69～83、底边 225～248）：本单用**全体均值**（半径 77.5、底边 235.5）。
   最大偏差 ±12 贴图像素 ≈ 0.04 卡单位（≈1.2% 卡高）—— 具体到 `frame_blacklegion`（徽记小）、
   `frame_saimhann`（徽记大）会有 ±1～2 面像素的缝。要逐阵营精确，得给每张卡框存一份徽记 bbox
   （可以并进 `工具/gen_frame_uv.py` 的产物），本单没做。
5. **Necron（`frame_sautekh`）的生命框**画形与别家不同（绿光连通域 154×122 vs 常规 119×81），
   按像素量中心会被绿饰边带偏；目视复核后**仍用同一个常量 (734,916)**（框外沿中心 ≈ (735,910)）。
6. **没跑 Unity**（红线）：本单全部结论来自静态量测 + 离线合成；真机验收仍欠一次（进游戏看手牌/详情大卡）。

## 附：测量脚本口径（可复现）

```python
# 卡框贴图像素 → 卡面归一化（与 FrameMesh 同一条链）
u = (px + 0.5) / W ; v = 1 - (py + 0.5) / H          # PIL 行 0 在顶部；UV v=0 在底部
fu = (u - uv.u) / uv.sw ; fv = (v - uv.v) / uv.sh     # uv 取自 Resources/frame_uv.json
x  = (fu - 0.5) * 2.2452                              # FrameUnitW
y  = (fv - 0.5) * 3.2572 + (-0.03)                    # FrameUnitH / FrameUnitY
x01 = 0.5 + x / 2.0927 ; y01 = 0.5 - y / 3.3313       # CardUnitW / CardUnitH
```

* 近战：`r>140 & r-g>90 & r-b>80 & a>220`，窗口 x 180..340 / y 780..950，最小二乘圆拟合。
* 远程：`r>130 & b>130 & g<140 & |r-b|<90 & a>200`，窗口 x 265..430 / y 850..1010。
* 生命：`g>70 & g-r>25 & g-b>10 & a>180`，窗口 x 640..830 / y 840..1000，取 bbox 中心。
* 徽记：亮灰环（`lum>95 & sat<60 & a>220`，环带 62<r<100 于 (723,161) 附近）圆拟合。
