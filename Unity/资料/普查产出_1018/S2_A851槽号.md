## 2. 为什么这样就对（判据 + 那个索引是什么语义）

### 2.1 `materialReferenceIndex` 是**「这一份顶点数组归谁」**的槽号，不是装饰

**权威判据（TMP 自己的源码，本地就有）**：
`MyGame/Library/PackageCache/com.unity.ugui@27635d171b1a/Runtime/TMP/TMP_Text.cs:5524-5537`
`FillCharacterVertexBuffers(int i)`：

```csharp
int materialIndex = m_textInfo.characterInfo[i].materialReferenceIndex;
int index_X4 = m_textInfo.meshInfo[materialIndex].vertexCount;      // ← 从【那个槽】的水位开始切
if (index_X4 >= m_textInfo.meshInfo[materialIndex].vertices.Length)
    m_textInfo.meshInfo[materialIndex].ResizeMeshInfo(...);          // ← 长的也是【那个槽】
m_textInfo.characterInfo[i].vertexIndex = index_X4;                  // ← 存进去的是【槽内】下标
```

⇒ **`vertexIndex` 是「槽内偏移」**（同一函数 `:5575-5577` 的体积版、`:5663-5665` 的
`FillSpriteVertexBuffers` 逐字同形）。
🔴 **两个槽各自从 0 开始切**（各自读自己的 `vertexCount`）⇒ **同一个 `vertexIndex` 值在两个槽里
指的是两个不同的字**。
⇒ 写死 `meshInfo[0]`、拿别的槽里的字的 `vertexIndex` 去索引 ⇒ **读到的正好是 0 号槽里「同下标」
那个字的四边形** —— 落在数组内、量出来「像个数」、**不报错**。这就是那条静默缺陷。

**第二条判据（本工程里已经这么写的地方，改法不是我发明的）**：
- **生产侧（被量的那个东西本身）**：`Shell/MenuDraw.cs:1148-1150` `ClipTmpMesh` —— `int mi = ch.materialReferenceIndex; if (mi < 0 || mi >= ti.meshInfo.Length) continue; var mesh = ti.meshInfo[mi];`。
  🔴 这最要紧：**裁切写的是哪一份数组、量法就得读哪一份**，否则「量到的是没裁过的那一份」。
- 量法侧：`Editor/ShellScene.cs:248-250`（`SpanOfTmp`）· `:291-293`（同名 `TmpVertsAndAlpha`）·
  `Editor/CollectionScene.cs:6085` · `Editor/IconSizeProbe.cs:152` · `Editor/MainMenuScene.cs:10729` ·
  `Editor/Round1015Probe.cs:59` —— **全都是按槽取**。
- 改完，`ShellScene.cs:232-235` 那份「有意不收的同族」注释里点名的三处，
  **理由只剩「逐点序列 vs 外接框」一条**（那条确实成立、也确实不该收）。

### 2.2 「一个能用的槽都没有 ⇒ 回 null / −1」这条口径**没变**

原来判的是「0 号槽的 `vertices`（/`colors32`/`uvs0`）是不是 null」，现在判的是「**所有**槽里有没有
一个能用的」。单槽时两者**逐位同值**（0 号槽能用 ⇔ 有一个能用）；多槽且 0 号槽坏、别的槽好时，
新版会把「本来能读到的字」读出来 —— 那是**改好**，不是改坏。
⚠️ 「空串」那一种**一个字都没有**的情形两边都是回空数组 / `0`（**不是** null/−1），没动。
