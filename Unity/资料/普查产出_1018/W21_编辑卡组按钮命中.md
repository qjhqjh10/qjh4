# W21 · 「编辑卡组」按钮命中 —— 真机第六轮（2026-10-18）

> 结论先说：**不是命中区被吸收层压住，也不是命中区与视觉底错位 —— 那一下点在了按钮矩形【上面】16.5 设计 px（22 屏幕 px）的空白处。**
> 按钮的命中区 = 视觉底 = 原版 rect，队列 3129 **严格高于**吸收层 3128；同一颗钮在 2026-10-11 的真机日志里**被点中过并成功进了编辑**。
> 本轮改动 = **加一条一眼能分辨「压住了」还是「点偏了」的诊断日志** + 一处「命中 quad 没建出来」的静默失败告警。

## 一、根因（谁盖了谁，给队列与 rect）

### 1.1 队列：没有被盖住

| 件 | 队列 | 出处 |
|---|---|---|
| 三颗大钮的命中区（`Btn_Practice Deck` / `Btn_Edit Deck` / `Btn_Select Deck` 下的 `Hit` quad） | **3129** = `Q(QDIHit)` = `QBase 3120 + (3129 − 3120)` | `Shell/DeckInfoPopup.cs` 的私有 `Hit()`：`q.SetRenderQueue(Q(QDIHit))` |
| 面板吸收层 `AbsorbHit` | **3128** = `qContentMin − 1` = `QDIHit − 1` | `MenuDraw.Absorb()`（`Shell/MenuDraw.cs:2355` 起，档由函数自己算） |
| 压暗层 `BackgroundHit` | 3120 = `Q(QDI)` | `MenuDraw.ShadeHit(...)` |

⇒ **按钮 3129 > 吸收层 3128**，与点击记录里那两个候选（3128 / 3120）自洽：
`HitButton` 挑「队列大的先」（`Shell/PointerLayer.cs` 的 `HitButton`），只要点在按钮矩形里，赢家**必然**是按钮。
（历史旁证：2026-10-11 那两次点中时是旧梯子 `QDIHit 3123 > AbsorbHit 3122`，**相对次序与本轮逐位相同**。）

### 1.2 矩形：视觉底 == 命中区（构造上就是同一块）

三颗钮的 `Bg` / `Text` / `Hit` 都在 `Build()` 第 6) 段的那一个循环里建，
**`Bg` 与 `Hit` 传的是同一个 `PxRect r`、同一个 `basis`（`Buttons` 容器）**，
两者都走本文件的 `Local3(basis, …)`；`LayoutButtonRow()` 平移时按 `_parts[]` 把三件一起搬（`MoveButton`）。
`state=0`、`SelectButtonProvided=false` ⇒ `Select Deck` 藏 ⇒ 两颗右对齐：

| 钮 | 设计 px 矩形（左上原点 · y **向下**） | 屏幕 px（2560×1440） |
|---|---|---|
| 练习 `Practice Deck` | `x 1085.70 … 1410.20` · `y 885.81 … 965.91` | `x 1447.6 … 1880.3` · `y 1181.1 … 1287.9` |
| 编辑 `Edit Deck` | `x 1446.20 … 1770.70` · `y 885.81 … 965.91` | `x 1928.3 … 2360.9` · `y 1181.1 … 1287.9` |
| 选择 `Select Deck`（藏着） | 复位在基线第三格 `1446.20 … 1770.70` | 不参与命中（节点 `SetActive(false)`） |

**实测复核**（截图 `_tmp_view/shots/2026-10-18_第六轮/03_deckinfo.png` 逐像素扫）：
- 竖扫 `x=2010`：按钮金框上沿 **1184**、下沿 **1286**（rect 理论值 1181 / 1288，差的是贴图自身的内描边）；
- 横扫 `y=1200/1260`：练习 `1450 … 1867`、编辑 `1931 … 2356`（理论 1447.6…1880.3 / 1928.3…2360.9）。
⇒ **画出来的就是 rect，rect 就是命中区**，没有「视觉底和命中区错位」这回事。

### 1.3 那一下到底点在哪

`_tmp_view/click_log.txt` 末两条（用户点的「编辑卡组」）：

```
点击 #8  屏幕 (2010.0, 281.0) · 画布 (1507.5, 869.3)   命中 AbsorbHit  队列 3128
点击 #9  屏幕 (2010.0, 289.0) · 画布 (1507.5, 863.3)   命中 AbsorbHit  队列 3128
```

🔴 **读法（两个坐标系都容易被读反，这里写死）**：
- 日志里的「屏幕」是 Unity `Mouse.current.position` = **y 从屏幕【下】边算**（`Core/ClickLog.cs:114`）⇒ 屏幕 y = `1440 − 281 = 1159`、`1440 − 289 = 1151`；
- 「画布」= **y 从【上】边算**（`Core/ClickLog.cs:10` 写明 1920×1080 口径；旁证 = 点击 #1 头像 `画布 y 44.3` ↔ 截图上头像在顶部 `y≈59`）⇒ 与设计 px 同一帧，可直接比。

⇒ 点在设计 `y = 869.3 / 863.3`；按钮上沿是 `885.81` ⇒ **差 16.51 / 22.51 设计 px（22 / 30 屏幕 px）**，落点正好压在 **`Info Panel` 的下边线**（`PanelB = 868.10`）上。
所以候选表里只有 `AbsorbHit`（红底那块 82…1032）和 `BackgroundHit`，**按钮的命中 quad 根本不在这一点上**，
「这一下一条日志都没有」= 命中的是 `absorbOnly` 的吸收层（原版语义：这一下什么都不做），**不是按钮没接上**。

### 1.4 这颗钮是点得动的（历史真机证据）

### 1.5 顺带核「练习」

## 二、改动清单（白名单内，只动 `Shell/DeckInfoPopup.cs`）

1. **新增 `LogHitGeometry()`**（`Shell/DeckInfoPopup.cs:1013` 起），
   在 `ApplyControlStates()` **末尾**调用（`:992`）—— 那是本窗**最后一个动队列的地方**
   （上面第 ⑥ 段的 `ReassertButtonQueues()` 刚把绝对档钉回去）⇒ 打出来的就是玩家真点那一刻生效的值。
2. **私有 `Hit()` 补静默失败告警**（`:2841` 起）：`ImageQuad.Create` 取不到 `CardArt.Solid()` 时返回 null，
   而 `PointerLayer` 只认 `ImageQuad` ⇒ 那颗钮**真鼠标点不动**、节点与 `onClick` 却全在（自检直调 `wb.Click()` 照样过）。
   改前是**静默**的，现在出声（同族先例 = `MenuDraw.MakeHitQuad` 的告警）。

⛔ **没有**改任何 rect / 队列 / 吸收层 / 显隐逻辑 —— 因为它们本来就是对的（§一），改了就是偏离原版。

## 三、新增的命中区日志（真机下一轮直接看这一行）

`ApplyControlStates()` 末尾每次都会打（建窗一次；之后任何一次改 `State` 再 apply 也打）：

```
[DeckInfo] 按钮命中区：练习=(1085.70..1410.20, 885.81..965.91) q=3129 · 编辑=(1446.20..1770.70, 885.81..965.91) q=3129 · 选择=(1446.20..1770.70, 885.81..965.91) q=3129（藏着） · 吸收层=(134.50..1839.50, 82.00..1032.00) q=3128 ⇒ **按钮区在吸收层之上（点得到）**
```

判据怎么用（**一行分三种情况，不用再翻代码**）：

| 打出来的样子 | 含义 | 下一步 |
|---|---|---|
| `⇒ 按钮区在吸收层之上（点得到）`，且点击记录里的**画布坐标落在那一对 `(x1..x2, y1..y2)` 里** | 几何是对的，**点偏了** | 按日志里的矩形去点（别照截图目测） |
| `⇒ 🔴 按钮区【不高于】吸收层 ⇒ 真鼠标点不到` | 队列被压住（真缺陷） | 查 `QDIHit` / `MenuDraw.Absorb` 那一段 |
| `🔴 没有命中 quad` / `🔴 视觉底=… **与命中区不一致**` / `⚠三颗不同档` | A26 / A1814 / A85 那一族 | 按点名的那一处修 |

⚠️ 量法 = `MenuDraw.QuadRectPx`（设计 px · 左上原点 · **y 向下**），与点击记录里的「画布」**同帧同向**，可以直接拿坐标对；
但读的是 `q.WorldW/WorldH`（**不含父链缩放**）⇒ 小屏缩放开关打开（`M ≠ 1`）时它打的是**设计帧**，
那只是给人看的诊断，⛔ 别拿它当缩放态的判据（判据仍在 `PointerLayer.HitBoxPx` 的 A167 段）。

## 四、没查清 / 需要拍板

1. 🔴 **用户为什么会点在按钮上方 22px** —— 这不是代码能答的。两种可能：
   ① 目测偏了（那一下正好压在 `Info Panel` 的下边线上，视觉上离按钮只有 20 来 px）；
   ② 用户屏幕上的实际窗口与 `ScreenCapture` 出来的 2560×1440 有偏移/缩放。
   ⚠️ 现有证据**只能排除 ②** 的一部分：同一次会话里点击 #4 在 `画布 (1814.3, 96.8)` 精确点中了关窗钮
   （`CloseHit` 矩形 `1782.81..1857.19 × 63.20..138.80`，中心 `(1820, 101)`），
   说明**指针映射整体是准的、偏差不超过 ~17 设计 px**（否则那一下点不中钮、或者 869.3 那一下就该点中）。
   ⇒ **还不能 100% 排除**「指针映射有一个 ≤16px 的常值偏移」这种可能；要证伪得再点一次**按钮正中**
   （`(1608.45, 925.86)`）——点得中就是纯目测偏差。
2. **要不要把按钮的命中区往上放大**（盖住 868…886 那条 17px 的空档）：
   ⛔ **不建议** —— 原版这三颗钮的 `m_RaycastPadding = (0,0,0,0)`（`MenuDraw.Hit` 判据段），
   放大 = 偏离原版（铁律 11 的「只有原版本身没有/用户拍板」两种例外都不成立）。
   那条空档在原版里也是**吸收层**（红底 `m_RaycastTarget = 1`、父链无处理器）⇒ 点了同样什么都不做，**行为与原版一致**。
3. **没有跑任何 Unity / 自检**（红线）：本轮只做了秒级类型检查 + 截图逐像素量 + 日志复盘。
