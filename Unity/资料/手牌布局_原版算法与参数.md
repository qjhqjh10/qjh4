## 〇、一句话

**原版 `CardsHorizontalLayout` 把「第 index 张 / 共 total 张」算成一对 `(世界位置, 四元数)`；**
**「牌少」和「牌多」走的是同一条公式，差别全在两条「按总张数」的曲线 + 一条「装不下就压缩间距」的分支上。**

## 二、`GetPosition(cardIndex, totalCards, selectedCardIndex = -1)`

逐句读自 `CardsHorizontalLayout__GetPosition.c`；**变量名按 dump.cs 的字段偏移还原**（偏移已逐条对上，见 §五）。

```csharp
Vector3 basePos = transform.position;                    // 「容器」自己的世界位置
if (m_inverted) cardIndex = (totalCards - cardIndex) - 1; // 本例两份都是 0

float parentScale = m_elemetsParent.lossyScale.x;         // 我方 = Transform_1401 ⇒ localScale 108

float cap;                                                // = m_calculatedMaxLayoutSize（缓存回 +0x80）
if (!m_useViewportSize) cap = parentScale * m_scale;      // 四份实例都 =1 ⇒ 不走这支
else {
    cap = GameStaticData.smallScreenUI ? m_maxLayoutSizeSmallScreen : m_maxLayoutSize;
    var cam = renderCamera;                               // 四份实例都指向同一台：fov 40 / 非正交
    if (cam != null) {
        if (!cam.orthographic) {
            Vector3 d = transform.position - cam.transform.position;
            float halfFov = cam.fieldOfView * 0.5f * Mathf.Deg2Rad;
            float dist = Mathf.Sqrt(d.x*d.x + d.y*d.y);   // 只算 XY 平面距离
            cap = (maxLayoutSizeAspectRatioModifier.Evaluate(cam.aspect) + cap)
                * cam.aspect * (dist + dist) * Mathf.Tan(halfFov);
            //  ↑ = (m_maxLayoutSize + 宽高比修正) × 「该深度处的可见宽度」
        } else {
            cap = (cam.aspect*cam.orthographicSize + cam.aspect*cam.orthographicSize) * cap;
        }
    }
}
// ⚠️ 注意：cap **不是**「占屏比例」的原始值，它已经乘成了**世界单位**；
//    但因为乘的是「该深度处的可见宽度」，等价于「可见宽度的 m_maxLayoutSize 倍」。

float extra = 0, halfExtra = 0;
float spacing = parentScale * m_betweenElementsSpacing;    // ★ 世界单位！

// ---- 「选中一张牌 ⇒ 两侧让开」（我方 useExtraSpaceOnSelectedCard=1，敌方=0）----
if (useExtraSpaceOnSelectedCard && selectedCardIndex >= 0
    && selectedCardIndex != cardIndex && selectedCardIndex < totalCards) {
    int n = 0;                                            // 装得下几张？
    while (true) {                                        // 与 GetCardsInHandNumber… 同一个循环
        if (BattleManager.MaxCardsInHand() <= n) { n = 0; break; }
        if (m_maxLayoutSize <= n * spacing && n * spacing != m_maxLayoutSize) break;
        n++;
    }
    float k = Mathf.Max(0f, totalCards - n);
    // 曲线挂在 BattleManager 上（`GetPosition.c` 里那一跳），我们**还没取到它的关键字**
    halfExtra = battleManager.someCurve.Evaluate(k / (MaxCardsInHand() - n));
    if (cardIndex < selectedCardIndex) extra = -halfExtra;
    else if (selectedCardIndex < cardIndex) extra = +halfExtra;   // 由 `xor 0x80000000` 翻符号实现
}

float totalWidth = totalCards * spacing;
if (!allowSelectCardLayoutOverFlow) totalWidth += halfExtra + halfExtra;

// ---- ★ 装不下就压缩间距（**除 n，不是除 n-1**）----
if (cap < totalWidth) {
    float avail = cap;
    if (!allowSelectCardLayoutOverFlow) avail -= halfExtra + halfExtra;
    spacing = avail / totalCards;
} else {
    extra = 0f;                                           // 装得下 ⇒ 连「选中外扩」也取消
}

// ---- 出数 ----
float span    = (totalCards - 1) * spacing * 0.5f;        // 0.5 = .rdata 0x1834b2bb4 实读
float norm    = (totalCards == 1) ? 0.5f : cardIndex / (float)(totalCards - 1);
float yCurve  = m_yAxisCurve.Evaluate(norm);              // ← 弧线形状，逐卡
float hMod    = m_heightModifierBasedOnTotalCards.Evaluate(
                    (totalCards - 1) / (float)(m_numberOfCardsForMaxHeight - 1));  // ← 按张数
float z       = basePos.z + (useZOrder ? cardIndex * 0.001f : 0f);   // ← Z_OFFSET_BY_POSITION_INDEX

return new Vector3(basePos.x - span + extra + cardIndex * spacing,
                   basePos.y + yCurve * m_maxHeight * hMod,
                   z);
```

**要抓住的四件事**：

1. **x 按 `parentScale × m_betweenElementsSpacing` 铺开，y 只乘 `m_maxHeight`** ——
   两条轴的「单位」在原版里就**不一样**（x 带 108 的父级缩放，y 不带）。见 §四，**这不是 bug，也不是我们的错**。
2. **`norm = index/(total-1)`** ⇒ 首卡 t=0、末卡 t=1；**`total==1` 时 norm 固定 0.5**（居中，弧顶）。
3. **按总张数的两条曲线**：`hMod`（弧高）与 `rotMod`（张角，在 GetRotation 里），
   x 都是 `(total-1)/(m_numberOfCardsForMaxHeight-1)` ⇒ **牌越多，弧与张角越大，到 `numberOfCardsForMaxHeight` 张拉满**。
4. **压缩分支一旦触发，`extra` 直接归零**（装不下时连选中外扩都不要了）。

## 三、`GetRotation(cardPosition, totalCards)`（**输入是位置，不是序号**）

逐句读自 `CardsHorizontalLayout__GetRotation.c`；`.c` 里丢掉的三处浮点实参靠 `工具/disasm_va.py` 直读指令流补齐。

```csharp
if (!m_useRotation) return Quaternion.identity;           // 选牌/换牌两份 =0，直接返回单位四元数

Vector3 selfPos = transform.position;
Vector3 dir     = cardPosition - (selfPos + Vector3.up * m_verticalOffsetLookTo);
//                                        ↑ Vector3 类静态块 +0x18 = upVector（dump.cs:537036 实核）

Quaternion q = Quaternion.LookRotation(dir, Vector3.back)          // ↑ +0x54 = backVector
             * Quaternion.AngleAxis(90f, Vector3.right);           // ↑ +0x3C = rightVector
//             ↑ 角度 90 是 .rdata 常量 0x1834B2E04 实读
//             ↑ **乘法顺序 = LookRotation × AngleAxis**（按 Unity 的四元数公式逐项比对四个分量得出）

float t = m_rotationModifierBasedOnTotalCards.Evaluate(
              (totalCards - 1) / (float)(m_numberOfCardsForMaxHeight - 1));

Quaternion from = Quaternion.identity;
if (m_verticalOffsetLookTo > 0f)                           // 只有敌方（+74.5）走这支
    from = from * Quaternion.AngleAxis(180f, Vector3.forward);     // 角度 180 = 0x1834B2E9C 实读

q = Quaternion.Lerp(from, q, t);                           // ⚠️ 起点是 from、终点是 q

if (m_invertRotation)                                      // 只有敌方 =1
    q = q * Quaternion.AngleAxis(180f, Vector3.forward);   // 不参与 Lerp，最后再乘一次

return q;
```

**几何意义（这也解释了 `m_verticalOffsetLookTo` 为什么「应该是负的」）**：
`dir` 是「从「容器 + up×lookTo」指向这张牌」的向量。
我方的 lookTo = **−330** ⇒ 看向手牌**下方 330** ⇒ `dir` 基本朝上 ⇒ 配合 `AngleAxis(90°, right)`
正好把卡摆成**正面朝相机**；dx 越大 `dir` 越斜 ⇒ 卡越往外撇。
敌方的 lookTo = **+74.5** ⇒ 看向**上方** ⇒ 先乘 180°@forward 把基准翻过来，再用 `invertRotation` 翻第二次。

## 四、单位桥：**「两把尺」不是错，是原版就这样**（⚠️ 更正一条旧结论）

**事实**：原版 x 用 `parentScale(108) × spacing`，y 直接用 `m_maxHeight` —— 两条轴的单位确实不同。

**但它们不是同一个空间里的量**：
- `m_elemetsParent` = `S/Transform/Transform_1401.json`：`m_LocalScale = (108,108,108)`，父 `1296`（scale 1）。
  ⇒ 卡的**本地（设计）空间**每单位 = `108 × 上层缩放` 个世界单位。
- 手牌渲染相机 = `S/Camera/Camera_1462.json`：**fov 40**、透视、cullingMask 32、far 300。
  原版 UI 平面在相机前 **100** 处 ⇒ `1080 / (2×100×tan20°)` = **14.835 px / 世界单位**。
- 两个约束联立：**卡宽** = `2DCard 2.0927 × m_scale 0.73 × parentScale`（世界）→ 渲染出 **165 px**
  ⇒ `parentScale × pxPerWorld = 165 / (2.0927×0.73)` = **108**。
  ⇒ **`1 设计单位 = 108 px`**、**`1 世界单位 = 14.835 px`**，两者相差 `108/14.835 = 7.28`。

**结论**：
- `m_betweenElementsSpacing = 1.45` 是**设计单位** ⇒ `1.45 × 108 = 156.6 px`（= **0.95 卡宽**，牌几乎挨着）
- `m_yAxisCurve × m_maxHeight` 是**世界单位** ⇒ 满弧 `3.02 × 0.70 = 2.11` 世界单位 = **31.4 px**

🔴 **2026-09-25 更正 `项目任务.md` §三 第 12 条 第 4 项的原话**：
原文写「**间距按 108 px/单位、弧高却按 14.835 折算 ⇒ 差 7.28 倍**」——
**那是把两个不同的空间当成了同一把尺。** 108 与 14.835 的比值恰好就是 `parentScale`，
两者**本来就该差 7.28 倍**；我们现有实现用「间距×108、弧高×14.835」**是对的**。
**错因**：只读了两条公式的系数、没有回头解 `m_elemetsParent` 的 `lossyScale`（108）与渲染相机的距离。
**旁证**：用户给的那张 5 张手牌的实机图，粗量弧高 **≈8~10 px @1080p**，算出来是 **9.99 px**（见 §六）——两者对得上；
若按「同一把尺」重算只剩 0.68 px，**与画面矛盾**。

## 六、★ **按张数分档**（用户点名要的那一节）

**我方手牌**（`m_numberOfCardsForMaxHeight = 12`；间距 156.6 px = 0.95 卡宽；压缩阈值 **n ≥ 8**）：

| 张数 | 中心间距 | 跨度（首↔末中心） | 弧高（中↔端） | 外缘张角 | 备注 |
|---|---|---|---|---|---|

| 2 | 156.6 | 157 | 1.7 | 0.30° | 几乎是一条直线 |
| 3 | 156.6 | 313 | 4.0 | 1.15° | |
| 4 | 156.6 | 470 | 6.8 | 2.31° | |
| **5** | 156.6 | 626 | **10.0** | **3.47°** | ← 用户那张实机图的档位（图上粗量 ≈8~10 px，对得上） |
| 6 | 156.6 | 783 | 13.4 | 4.54° | |
| 7 | 156.6 | 940 | 16.5 | 5.49° | |
| **8** | **144.6** | 1012 | 19.8 | 5.93° | 🔴 **从这里起间距开始被压缩** |
| 9 | 128.6 | 1028 | 22.9 | 6.01° | |
| 10 | 115.7 | 1041 | 25.8 | 6.08° | = 经典手牌上限（`DeckRules.ClassicHandLimit = 10`） |

**「少」与「多」到底哪里不一样（这就是用户问的那件事）**：

1. **1～7 张**：间距**钉死**在 156.6 px（0.95 卡宽，牌几乎不叠）；跨度线性增长；
   **弧高与张角沿各自的「按总张数」曲线从小爬到大**（5 张时张角已到 94.8% 的满值，弧高才 31.9%）。
2. **8 张起**：`n × 间距 > 0.6026 × 屏宽` ⇒ 进入压缩分支 ⇒ **间距按 `可用宽度 / n` 缩**、
   **跨度被钳在 ~1012–1061 px**（封顶 ≈1157 px 的 92%）。**张角因此几乎停住**（5.9°→6.2°）。
3. **弧高不受压缩影响**，一路长到 12 张才拉满 ⇒ 「牌越多、越挤、但弧越明显」。
4. **两条曲线不同步**：`rotMod` 在 5～6 张就基本到顶（0.948→0.993），`hMod` 到 12 张才到 1.0。

**我方手牌逐卡形状（n=5，相对最高那张，px）**：`−10.0 · −1.9 · 0 · −2.5 · −10.1`
—— **两端陡降、中间三段几乎平**（不是抛物线；曲线的切线在两端很大）。

**敌方手牌**（`numberOfCardsForMaxHeight = 10`；间距 64.8 px；**永不压缩**，因为 `10×64.8 = 648 < 1157`）：
弧高 = `3.40 × 0.78 × hMod × 14.835` ⇒ 10 张满时 **39.4 px**，但 `m_maxHeight` 是**负的** ⇒
**中间往下凹**（两端反而高），配合 `invertRotation` 与 `lookTo=+74.5` = 「从屏幕上方垂下来」。

**选牌 / 换牌面板**：`m_useRotation = 0`（**所有卡都不转**）、`m_yAxisCurve` 平线 0（**没有弧**），
只有 `m_scale = 183.41` 与 `m_betweenElementsSpacing = 502.2` —— 一条**完全平直**的横排。

## 七、我们这一版（`Hand/HandLayout.cs`）逐条对账

| # | 项 | 原版 | 我们 | 判定 |
|---|---|---|---|---|
| 1 | 间距 | `parentScale × m_betweenElementsSpacing` = 156.6 px | `1.45 × (108 px/单位)` = 156.6 px | ✅ 等价 |
| 2 | 压缩分支 | `n×spacing > cap` ⇒ `spacing = cap/n`（除 n） | 同（`SpacingFor`） | ✅ |
| 3 | 压缩阈值 | n ≥ 8 | n ≥ 8 | ✅ |
| 4 | 弧线形状 | `m_yAxisCurve` **原始值** × `m_maxHeight` | `Arc01()` 把曲线**归一化到 0..1** 再乘满弧 | ⚠️ 形状同、但**整体抬高了「一个满弧」**（约 2.11 设计单位 ≈ 228 px），靠自定的 `baselineY` 抵掉 |
| 5 | 按张数的两条曲线 | `(total−1)/(numberOfCardsForMaxHeight−1)` | `CountFraction()` 同式 | ✅ |
| 6 | 张角 | `LookRotation(dir, back) × AngleAxis(90°, right)` → `Lerp(from, q, t)` → `×180°@forward` | `atan2(dx, lookToDistance)` 的**二维近似**，`invertRotation` 用取负号 | ⚠️ **dx 小的时候数值接近**（5 张：我们 3.29° / 构造式 ≈3.47°），但不是同一个函数；`m_invertRotation` 的两次 180° 只是取反号 |
| 7 | `useZOrder` 步进 | **0.001** | `zOrderStep = 0.08` | ❌ **差 80 倍**（我们有理由：卡内部各层 z 跨度 0.06，太小会让文字穿到邻牌上 —— 但原版**不是**这么解决的） |
| 8 | `useExtraSpaceOnSelectedCard`（我方=1） | 按 BattleManager 上一条曲线让两侧外扩，**装不下时归零** | 自造 `hoverLift 0.06 / neighborShift 0.018` | ❌ 未复刻 |

## 八之二、顺带更正的一条旧结论：**「张角是二维近似」也是错的**

原版那套三维构造 `LookRotation(dir, back) × AngleAxis(90°, right)` → `Lerp` → `×AngleAxis(180°, forward)`，
在 `dir.z ≡ 0`（`lookTo` 与卡同 z）时**代数上恰好退化成「纯绕 Z 滚一个角」**：

```
dir = (sinθ, cosθ, 0)、up 提示 = Vector3.back = (0,0,−1)
  ⇒ LookRotation(dir, back) 的三根轴 = ( (cosθ,−sinθ,0), (0,0,−1), (sinθ,cosθ,0) )
  ⇒ 它 = R_z(−θ) · R_x(−90°)
  ⇒ 再乘 AngleAxis(+90°, right) = R_x(+90°) ⇒ R_z(−θ) · R_x(−90°) · R_x(+90°) = **R_z(−θ)**
  ⇒ Lerp(identity, ·, mod) = R_z(−θ·mod)；敌方再 ×R_z(180°)
```

⇒ **二维 `atan2` 不是近似，是同一件事。** 唯一漏掉的是**分母里的弧高项**
（原版 `dir.y` = 「卡相对基准的 y 偏移」，不是常数）—— 2026-09-25 已补进 `HandLayout.RotationAt`。
