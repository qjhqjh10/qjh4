## 一、结论链（按发现顺序，每条都有实测支撑）

1. **`wf(8).log`（n6 · OnePlus · 19:16–19:21）**：6 次启动、`[MENU]` **全 0**（一次都没进主菜单）；
   **首次拿到「普通崩溃报告」**（设备上累计 111 份），5 份回显报告的故障 pc **全部**在 `libart.so` / `libc.so` /
   `boot.oat` / `boot-framework.oat`，故障线程横跨主线程 / UnityMain / 系统线程 / Google 后台线程。
   「真实服务器」假设基本排除（PlayFab 全本地、45 条 XFORM 零 miss、Unity 匿名登录已关、Photon 启动期 0 条）。
2. **`crash.zip`（外部 19:40 那轮 32 份）**：全是 `access-violation`，pc 全在 `boot-framework.oat` / `boot.oat` /
   `boot-core-libart.oat`，十几个不同线程踩同一段 framework 编译代码 ⇒ ART 层内存损坏，不是玩法模块。
3. **A 机活捉「卡住」**：画面卡 65%、`wf.log` 100 s 不动、进程活着、`adb forward` + `curl /__health` **超时**
   ⇒ **JS 事件循环停了**（监听口一直在，坑 561 的「监听口消失」不是必要条件）。
4. **「冻结」分两种形态**（坑 570）：
   - **A**：`gum-js-loop` **线程消失**，`[NATIVE]` 仍输出（Frida 运行时还活着）；
   - **B**：`gum-js-loop` **还在**（S、CPU 不涨）但 `[NATIVE]` 断流（JS 锁被某个卡住的原生调用占着）。
5. **大半可能是我们自己的探针**：CModule 版 `nativewatch` 打开后，每次冻结都留崩溃报告
   —— `illegal-instruction`、pc 在 `0x73c3a36xxx`（**CModule 代码页**）、「故障线程 gum-js-loop」
   其实是**我们建的原生线程**（Linux 新线程继承创建者 comm）。`nativewatch` 已永久 `ON=false`。
6. **二分（每组 8 次，A 机，判据 `/__health` 或 `[ALIVE]` 计数）** —— 健康/总数：
   - 无 `server.js` **8/8** · 服务端收包即断（**不读**）**8/8**
   - 读完请求即断 5/8 · 读完即断 + 读超时 6/8 · 读完**不回也不关**（HANG_ALL）6/8
   - 真实处理 + 串行化 3/8 · 真实处理（基准）5/10
   - gadget 17.26.4 / 17.27.4：7/10 · 5/10
   - **n1b 空壳载荷**（无 il2cpp / 无 socket）**5/5**
   - 禁用 `Il2Cpp.perform` 4/5 · perform + 全部 Interceptor 关 4/5 · 全功能 - `crash.js` 3/5
   ⇒ **触发条件就是「JS 去 read socket」这个动作本身**（不是回包、不是悬挂、不是 perform、不是钩子、不是 crash.js、不是 gadget 版本）。
7. **CModule 原生服务端判死**（坑 571）：
   - 走 libc `accept` → `SIGILL`，pc/lr 落在 `<anonymous:73c3a36000>`（**CModule 代码页**）；
   - 走裸 `syscall(202)` → **`SIGSYS / SYS_SECCOMP`（Android seccomp 禁止裸 accept）**；
   - 改「全程不阻塞」（`O_NONBLOCK + accept4 + sched_yield`）→ 约 0.5 s 后 **`SIGSEGV`**，地址仍在 CModule 页；
   - ⇒ **CModule 的代码页在这个环境里活不长**（阻断/不阻断都一样）。

## 四、新会话第一件事

### 4.1 主线：把 socket 搬出 Frida 进程内 JS（推荐 J1）

| 方案 | 做法 | 代价 |
|---|---|---|
| **J1（推荐）** | APK 加一个 **Java 类**（本机 `d8` 编进 dex），在应用进程普通线程做 `ServerSocket`；请求写文件队列、JS 只读写文件（文件 I/O 已验证稳定），JS 把响应写回文件由 Java 发出 | 中：~150 行 Java + 文件协议 + JS 轮询；**不需要 NDK** |
| J2 | 同上，Java 服务端跑在 `android:process=":wfsrv"` 独立进程 | 中上 |
| J3 | 单独 C ELF（PC 同款架构） | 大：本机**没有 NDK** |
| J4 | 保底：原生看门狗检测到 JS 循环死 ⇒ 杀进程让用户重开 | 小，体验差 |

- J1 的好处：**JS 侧业务逻辑全部保留**（模板、云函数、选秀/联盟状态），只把「socket 收发」换成「文件收发」。
- 第一步建议：先做「Java 端口转发骨架」——Java `ServerSocket` 收请求 → 写 `files/wfq/req_<n>.json` →
  JS 每 20 ms 扫目录 → 处理 → 写 `resp_<n>.json` → Java 读后回包、删除。先跑 `/__health` 打通，再套模板。

## 六、本会话新增坑（566–571）

- **566** 「JS 事件循环冻死」的判据：`adb forward`+`curl /__health` 超时 = JS 循环停；逐线程 CPU（`UnityMain` R 空转 / `gum-js-loop` +0）。
- **567** Frida 17.27 的 CModule 四个坑（`symbols` 不认 / 符号必须从 `libc.so` 取 / 可写静态数组 fault / CModule 被 GC ⇒ 代码页释放，必须全局持有）。
- **568** 「故障线程名」会骗人：Linux 新线程继承创建者 comm；冻结现场伴生一个 fork 子进程。
- **569** 「冻结」真身是「Frida JS 事件循环线程消失」（判据：`js_tick` 停 + `enumerateThreads` 找不到 `gum-js-loop`）。
- **570** 冻结两种形态（A 线程消失 / B 线程在但锁被占）+ 信号不是凶手（UnityMain 220 次/秒发 `sig=24`，但从不发给 JS 线程）+ 健康判据要用 `/__health`。
- **571** CModule 原生服务端判死：裸 `syscall` 被 seccomp 杀（`SIGSYS`）；libc `accept` 返回时 `SIGILL` 在 CModule 页；非阻塞版仍 `SIGSEGV`；
  抓这类崩溃的正确工具 = `adb logcat -b crash -d`（`debuggerd` 要 root，debuggable + `run-as` 都不行）。
