## 3 需要哪些字段（`TriggerCarrier` 的全部内容 —— 一个不多、一个不少）

依据：实测 `RuleCore.cs:12498-12982`（`FireTriggerAt` + `FireTriggerDeferred` + `FireTriggerAlways` 三段）里
对 `u` 的**全部**用法只有 6 个成员（`u.Card`×14 · `u.Name`×8 · `u.InstanceId`×3 · `u.FxOps`×2 · `u.Effect`×2 · `u.GrantedText`×1）。

```csharp
/// <summary>触发派发核心的**唯一**载体视图（原版 `RawCardScript.OnTrigger` 的 thisCard 那一格）。
/// 📌 **这不是「🔶 自己设计」**（`CLAUDE.md` 铁律 18 的「⛔ 不许打标记」第 ② 条：只改结构、不改语义
///    = 实现风格）：每个成员都是到既有实现的**转发**，行为恒等。
///    原版用一个 `CardScript` 通吃；我们棋盘/手牌是两种对象 ⇒ 抽一层窄视图。
///    （2026-10-28 B92-B5 就地订正：本单草稿原写着 `🔶 自己设计`，那会把「结构适配」误标成「我们编的」。）</summary>
public readonly struct TriggerCarrier
{
    public readonly CardDef Card;        // 卡定义：TriggerOps / AbilityTriggers / traits 全在这
    public readonly CardInstance Inst;   // 实例（棋盘单位也一定有：`UnitState.Instance`）
    public readonly int InstanceId;      // = Inst.Id；表现层配对 + 日志。手牌卡此前恒 0 ⇒ 要补
    public readonly string Name;         // 日志（`Card.Name` 不够时用单位名）
    public readonly int Owner;           // 归谁（棋盘：`OwnerOf(ctx,u)`；手牌：`p`）
    public readonly int Slot;            // 棋盘格号；手牌 = -1
    public readonly bool IsBoardPath;    // ⭐ 唯一分支开关：棋盘专属那几段只对它为真
    // 两个转发（⛔ 不许在别处重写「原生 or 挂上去」的取法）：
    public IReadOnlyList<EffectOp> FxOps(string kw);   // 棋盘 = UnitState.FxOps；手牌 = Card.TriggerOps(kw)
    public EffectSpec Effect(string kw);               // 棋盘 = UnitState.Effect；手牌 = Card.Effect(kw)
    public string GrantedText(string kw);              // 棋盘 = UnitState.GrantedText；手牌 = null（见 §7·3）
}
```

工厂（**只有两个**；✅ 2026-10-28 已按此**落地**）：

```csharp
public static TriggerCarrier From(UnitState u, int owner, int slot)  // IsBoardPath = true（**即使 u == null**）
public static TriggerCarrier From(CardInstance inst, int owner)      // IsBoardPath = false；Slot = -1
```

🔴 **`IsBoardPath` 由【工厂】决定，⛔ 不是 `Unit != null`** —— 今天存在 `u == null` 却**仍然跑棋盘那几段**的
调用点（例如「没有来源」的广播：`Enchantments.HasAny(null)` ⇒ false、`FindSlot(null)` ⇒ -1）。
若把手牌路判成 `Unit != null`，那些调用点会被**悄悄**改成「跳过棋盘段」。
（2026-10-28 B92-B5 落地时就按这条实现，doc 写在 `TriggerCarrier.From(UnitState)` 上。）

**为什么不用「给手牌卡造一个 `UnitState` 影子」**（这条要写进代码注释，免得下一个人走回头路）：
影子会带进 `Health / PlayOrder / keywords / buffs` 等棋盘态字段，任何一处「顺手读一下」都会读到
**伪造的默认值**，而且是静默的（本仓红线）。窄视图让「手牌路能读什么」在**类型层面**就定死。

## 5 `FireTriggerAt` 的签名怎么变（**三个阶段，每个阶段单独可交付**）

### 阶段 1 · 零行为变化的重构（**先做这个，别和功能混在一起**）

```csharp
// ① 现有调用点（100+ 处）一个字都不改 —— 它变成纯转发：
static bool FireTriggerAt(BattleContext ctx, UnitState u, string keyword, int owner, int slot, …)
    => FireTriggerAt(ctx, TriggerCarrier.From(u, owner, slot), keyword, owner, slot, …);
//    ⚠️ ⛔ 别用 `with { Slot = … }`：那是 C# 10 的语法，Unity 6000.3 只到 C# 9 ⇒ 走工厂重载。

// ② 新核心（原体逐字搬过来，只把 `u.X` 换成 `c.X`）：
static bool FireTriggerAt(BattleContext ctx, TriggerCarrier c, string keyword, int owner, int slot, …);
```

**放行条件（唯一）**：`bash 工具/ruleprobe.sh play check` 的指纹**逐字节相同**。
变了就是搬错了（`ctx.Events` 顺序、`InstanceId` 取值、`Owner` 反查任何一处差异都会变指纹）。

### 阶段 2 · 棋盘专属段用 `IsBoardPath` 收口（仍然零行为变化）

核心体里这三段只在 `c.IsBoardPath` 时跑（它们**都只吃 `UnitState`**）：
1. `Enchantments.HasAny(u)` / `Enchantments.Matching(u, keyword)`（`RuleCore.cs:12520` 一带）
2. `SnapshotBoardListeners(ctx, preCalled, preCalled2, …)` 的预调/排除
3. `slot` / `pinnedOwner` 那一族（`FireBoardWhenListener` 的入参）

```csharp
var ench = (c.IsBoardPath && only == null) ? Enchantments.Matching(c.Unit, keyword) : null;
```
⚠️ 手牌路**不做附魔那一趟**（`Enchantments.*` 只接受 `UnitState`）；这条写进 §7·3 的「还差什么」。

### 阶段 3 · 手牌入口（**唯一的语义入口，带闸**）

```csharp
/// 手牌卡自己的 abilityTriggers 派发（原版 = `CardScript.OnTrigger` 在 `context 10` 下的那一支）。
/// 🔴 入口先过 `IsRightContext` 的等价闸，⛔ 不许在核心体里再判一次（那会变成两份规则）。
static bool FireTriggerAtInHand(BattleContext ctx, CardInstance inst, int owner,
                                string triggerName, string keyword, UnitState subject = null, …)
{
    // ① 数据有这条 trigger 吗（三态，认不出 ⛔ 不猜）
    int presence = inst.Card.AbilityTriggerPresence(triggerName);   // CardDef.cs:1965
    if (presence != 1) return false;                                // 0/未知 ⇒ 不响（见 §6 去重规则）
    // ② `IsRightContext` 的等价闸（**复用现有唯一取值口**，⛔ 别另写一份）
    int ctxv = ActionPump.AbilityContextOfAbilityV14(inst.Card, triggerName, keyword);  // ActionPump.cs:707
    if (ctxv != CardDef.AbilityContextHand)                         // 只认 10；`-1` 未知也拒（出声一次）
    { Debug.LogWarning(...); return false; }
    // ③ 转核心（`IsBoardPath = false` ⇒ 棋盘专属三段不跑）
    return FireTriggerAt(ctx, TriggerCarrier.From(inst, owner), keyword, owner, -1, subject: subject, …);
}
```

⚠️ **`ActorMustBeInPlayForTrigger` 别传 `true`**：它对 `context 10` 返回 `false`（`!= Play`）⇒ 传了会被出队复核当成「载体不在场」取消。
手牌路的「载体在哪个区域」由上面那道 `== Hand` 闸负责，泵点复核保持 `false`。

## 6 去重规则（不写这条一定双响）

今天我们**同时**有两条手牌监听路：
- `BroadcastHandWhen`（`EffectResolver.cs:10776`）—— 扫 `CardDef.WhenTriggers`（**文本解析**出来的 `When …` 族）；
- `BroadcastHandTrapWhen`（`:10674`）—— 扫 `HandTrapWhens` / `ArmedTrap`。

而本单新增的是**结构化 `abilityTriggers` 路**。同一张卡的同一件事可能三条都能命中 ⇒ 必须按数据裁决：

```
AbilityTriggerPresence(triggerName) ==  1  ⇒ 只走【结构化路】，⛔ 两条文本路必须跳过
AbilityTriggerPresence(triggerName) == -1  ⇒ 维持今天：只走文本路（旧卡表/认不出）
AbilityTriggerPresence(triggerName) ==  0  ⇒ 什么都不做
```

判据：原版**只有一套** `abilities`（`+0x110`），文本那两条是**我们自己的替代品**（当年读不到 `abilityTriggers` 才从 `desc` 解析）。
⇒ 结构化有值就以它为准（`WhenTriggers` 只在 `-1` 时兜底）。**这一条要写进 `BroadcastHandWhen` / `BroadcastHandTrapWhen` 的早退条件里**，
否则 `Vengeance for Cadia` 这类会被叫醒两次。

### 7·3 本单**不做**的三件事（写清理由，别当漏项）

1. **手牌卡的附魔那趟**：`Enchantments.HasAny/Matching` 只接受 `UnitState`；原版 `TriggerAbilities` 的附魔块在
   `CardInstance.ActiveEnchantments` 上能不能落到，**本轮未核**（`CardInstance.cs:142` 确实有那个 List，但消费链没读）。
   ⇒ 手牌路先**不做**，并在代码里出声。
2. **`GrantedText` / `GrantOps` 的手牌版**：`_grantedOps` 在 `UnitState` 上（`UnitState.cs:1018` 一带）；
   `Give "…" to a troop in your hand` 这种在生产池里有没有，**本轮未查**。手牌工厂的 `GrantedText` 先返 `null`。
3. **`context 20 Deck` / `30 Cemetery` / `50 InPlayOrCemetery` 的「扫牌库 / 扫墓地」通道**：我们**根本没有**「扫弃牌堆找 abilityTriggers」这一趟。
   现读 90 那族有 **11 条 `context 50`** ⇒ 这是**另一条缺口**（不属本单），建议单开一条账。

## 8 验收口（断言怎么写 —— **必须能挡住「两边一起改回去」**）

新增宿主内的一个函数（`RuleEngineTest` 或 `RuleEngineTest_EngineE3.cs`，跟着现有 ability 断言走）：

**① 前提硬检查（先断前提，⛔ 不许 `if (x != null) Check(…)`）**
```
Check(AM56.Card.AbilityTriggerPresence("OtherUnitDeath") == 1, "前提：AM56 真有 90 这条 ability");
Check(ActionPump.AbilityContextOfAbilityV14(AM56.Card, "OtherUnitDeath", …) == CardDef.AbilityContextHand, "前提：AM56 的 90 是 context 10");
Check(某Play0卡.AbilityTriggerPresence(<某 trigger>) == 1, "前提：负例卡真有那条 ability");
Check(ActionPump.AbilityContextOfAbilityV14(负例卡, …, …) == CardDef.AbilityContextPlay, "前提：负例是 context 0");
```

**② 正例（`context 10` 在手 ⇒ 响）**
把 `AM56` 放进 P0 手牌 → 让棋盘上另一个单位死 → 断言 **`AM56` 的正文被执行过一次**
（断一个**可观测净量**，例如 `ctx.Log` 里的正文条目，或它那条效果的净改动；⛔ 别只断「有 `EvtKind.Trigger`」——
表现层事件不证明正文跑过）。

**③ 负例（`context 0` 在手 ⇒ 不响）**
同一件事，把负例卡放在手牌 → 断言它的正文**零次**执行（同一个可观测净量 == 0）。

**④ 🔴 结构断言（灭自证的核心；断的是「同一核心」而不是「结果对」）**
给派发核心加两个**只给自检用**的只读计数（`⛔ 引擎里零生产消费者`，照 `AbilityLevelCriteriaWarningsForTest` 的既有范式）：
```
TriggerDispatchCoreCallsForTest     // 核心（TriggerCarrier 那层）被调用次数
EnchantScanCallsForTest / BoardSnapshotCallsForTest   // 棋盘专属那两段的次数
```
断言：
- 走**棋盘**入口一次 ⇒ `Core += 1` **且** `EnchantScan + BoardSnapshot` 各 `+1`；
- 走**手牌**入口一次 ⇒ `Core += 1` **且** `EnchantScan / BoardSnapshot` **一次都不涨**。
⇒ 这两条**同时**成立，才证明「两个适配器走同一个 switch，且棋盘专属段没被手牌路走到」。
（只断「正例响」= 自证：复制第二套规则也能让它响。）

**⑤ 判别式（两边一起改会红 —— 灭自证）**
- 把 §5 阶段 3 的 `== AbilityContextHand` 改成 `true` ⇒ **负例变响 ⇒ 红**；
- 改成 `false` ⇒ **正例不响 ⇒ 红**。
⛔ 只写「正例响」那一条的话，把闸删掉照样绿。

**⑥ 不双响**
同一次广播里同一张手牌卡 ⇒ `TriggerDispatchCoreCallsForTest` **只 +1**（防「文本路 + 结构化路」双响，见 §6）。

**⑦ 端到端放行条件**
- 阶段 1/2：`bash 工具/ruleprobe.sh play check` 指纹**逐字节不变**；
- 阶段 3：`play all dump` 里**只有** §2·1 那 16 条会动（今天它们 0 次触发 ⇒ 预期**也不变**）；
  **指纹若变 ⇒ 说明 `context 0` 的手牌卡被误放行**，必须回查 §6 去重规则。

## 10 会伤到 `UnitState` 现有语义吗？（调度台要求的判定）

**判断：不会。** 三条理由：
1. `UnitState` **一个成员都不加**（§4）—— 只在 `From(UnitState)` 里**读**它已有的 6 个成员；
2. 棋盘那一路的行为由阶段 2/3 的**指纹逐字节不变**钉死，且棋盘专属三段用 `IsBoardPath` **显式保留**；
3. `UnitState.Instance` 本来就存在（`UnitState.cs:32`）、`InstanceId` 本来就是 `Instance.Id`（`UnitState.cs:48`）
   ⇒ 「卡实例身份」这条链**早就通了**，本单只是把派发核心从「必须 `UnitState`」松到「任何带 `CardInstance` 的载体」。

⚠️ **唯一要额外小心的三处**（都在阶段 2，`play check` 抓得到）：
- `EmitCardTrigger` 现在的 `instanceId: unit != null ? unit.InstanceId : 0`（`EffectResolver.cs:8337`）—— 手牌路要传真 id，别一律 0；
- `ctx.Log` **⛔ 手牌路不许写**（会改 `ctx.Events.Count` ⇒ 动 `Fingerprint`，本仓已记这条坑）；要出声就用 `Debug.LogWarning`；
- `ActorMustBeInPlayForTrigger` 在手牌路必须传 `false`（§5 末尾）。
