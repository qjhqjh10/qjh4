## §1 两套分母怎么合并

### 1.1 先纠两处事实（铁律 5）

1. **part TSV 是 20 份，不是 21 份**。`ls 判据/功能点索引_*_part.tsv | wc -l` = **20**；逐份数据行相加 = **180**（每行 16 列，`bad_colcount = 0`）。审计 §1.1 写的「21 份」与它自己列的 20 个域名矛盾 —— 21 是**账**的份数（20 域 + `泛型与启动链_补读.tsv`），不是 part 的。
2. **`功能点索引.md` 的 173 是「域桶」，不是功能点**。`gen_feature_index.py --dry` 现读：`功能点 173：主链 42 · 边角 111 · 暂停 20`、`兜底行 2,641 · 兜底类 871`。它的每一行是**一个域内的类/方法归并桶**（含「（域）其它」），⛔ 不能与 180 相加，也不能拿它当分母。

### 1.2 三种口径的现读值

| 口径 | 文件 | 现读 | 覆盖 |
|---|---|---|---|
| **账行** | `账/*.tsv` | **21 份 / 9,641 行**（A 5,786 · D 3,855 · B 0 · C 0 · E 0） | 逐行 `split('\t')` 取 `状态` 列；⛔ 非文本模式 |
| **域视图** | `资料/完全复刻/功能点索引.md` | **173 行**（§1 总表） | 由 `gen_feature_index.py` 从账机生成，**全部 9,641 行都有归属桶**（兜底 2,641 行 / 871 类） |

### 1.4 合并方案（逐字段，可直接照做）

**裁定：功能点验收的权威 = `判据/功能点索引_*_part.tsv`（180）；`功能点索引.md`（173）降级为「域规模视图」，⛔ 不再参与任何分母。**

理由（方案 §2.2 原文 `资料/完全审查与完全复刻_方案.md:79-84`）：第二层定义是「一行 = 玩家能做的一件事」，列里要有 ①②③；而 `功能点索引.md` 的 `最高档` 取的是**最高档**，设计文 `判据/功能点验收索引_设计与样板.md:41-46` 已写明「最高档 A 会骗人」（一个功能点挂着 42 条 B 仍写 A）。part TSV 取**最差档**、且带落点/验收口 —— 只有它能签收。

逐字段对照（左 = `功能点索引.md` 10 列，右 = part TSV 16 列）：

| md 列 | part 列 | 处置 |
|---|---|---|
| `#` | — | md 独有行号；不迁移 |
| `功能点` | `功能点名` | **两份名字 0 条精确相同**（现读：173×180 交集 = 0）⇒ ⛔ 不能按名字 join；以 part 为准，md 名只作阅读提示 |
| `主链/边角（我判）` | `主链/边角` | 以 part 为准；md 那列是「我判」，无一手判据 |
| `账推分类（P0⇒主链 / P1P2⇒边角）` | `优先级` | **不同语义**（md 从等级推、part 是人给的 P0–P3）⇒ 以 part 的 `优先级` 为准，md 该列废 |
| `域` | `域` | 同一闭集（现读 20 个），逐字一致，可直接用 |
| `挂哪些类.方法（前几个）` | `原版构成` | md 是**截断的前几个**，不可机检；以 part 的 `原版构成` 为准 |
| `方法数` | `构成条数` | **两边都不是去重行数**（part 该列按 token 展开有重复）⇒ 两列都必须由机检重算（见 §4） |
| `状态分布` | `状态分布` | 同格式 `A67·C1·D3`；**两份都过期**，统一由 `feature_index_check.py` 重算 |
| `最高档` | `等级` | **相反语义**（最高档 vs 最差档）⇒ md 的 `最高档` 列**改名 `最高档（仅参考，不作签收）`**；签收只认 part 的 `等级` |
| `备注` | `备注` | 两份人工注记都要留：part 为准，md 独有的句子用 `｜md注：…` 追加到 part 备注 |

**跨表 join 的唯一可行键 = 账行**（不是名字、不是序号）。做法（机检可复核）：
1. 给 `gen_feature_index.py` 加一个 `--emit-membership <out.tsv>`：输出 `账文件:行 → md行# / 域 / 功能点`。它本来就知道每行归哪个桶（§3「没归并进去的行」就是靠这份归属算的）。
2. 给 `feature_index_check.py` 加一个 `--emit-membership <out.tsv>`：输出 `账文件:行 → FP id`（`expand()` 已经在内存里算出了每个 token 的命中行，`feature_index_check.py:172-185`）。
3. 两份按 `账文件:行` 内连接 ⇒ `判据/功能点口径对照.tsv`（列：`账文件:行 | FP id | md行# | 域`）。
4. 派生一列「FP → 它落在哪个 md 域桶」= 该 FP 的账行在 md 里的**众数桶**；不一致的 FP 单独列出来给调度台判。

**验收（写完必须满足）**：
- `判据/功能点口径对照.tsv` 的账行集合 == `账/*.tsv` 的 9,641 行（逐行出现且仅出现一次）。
- 167 个玩家可见 FP 的 `构成条数`（重算后）之和 == 它们去重后的账行数；13 个桶同样。
- 全仓 `grep -rn "21 份" 判据/功能点索引*` = 0（改成 20 份）。

### 2.2 结构上做不到的那一半（必须写进 ② 的口径）

方案 §八 对 ② 的定义是「跑 `D:/2/unity_run_ref` **造同一局面**，比状态/数值/日志」（`资料/完全审查与完全复刻_方案.md:363`）。
**这个定义对战斗内状态做不到**，三条独立判据：
1. 手牌注入失败：`inj FAIL: empty Data`（CLAUDE.md 铁律 4 的表；另见 `判据/TraitEffectController_钩子层.md:594`、`报告/B8_M_敌方槽位镜像.md:214`、`报告/N13_TraitEffectController_第1轮.md:66`）。
2. 根因 = **卡 SO 在远端 Addressables（`allcards`），本机从没下过**（5 条证据见 `历史/§29d_已闭行_搬出_1032.md:6`）；`BattleDebugController` 在正式版被裁掉。
3. 因此原版能到达的状态只有「不需要任何卡数据的菜单 / 场景 / 开场」。

⇒ **② 的合法范围必须拆成两档**：
- **②A 可判**（原版状态可达）：菜单/场景/开场/特效 prefab/序列化字段/卡面真值。
- **②B 不可判**（战斗内局面）：只能记 `N/A`，原因写死「原版 inj 失败、卡数据在远端」，**⛔ 不许算成通过、⛔ 不许拿自检断言顶替**。

### 2.3 最小可行实现（可直接照做）

**新增两个文件（调度台批准后由写手落）：**

1. `判据/功能点_oracle规格.tsv` —— 一行 = 一个 FP 的一条 oracle 检查，12 列：
```
FP_ID | 功能点 | 域 | oracle类型 | 输入/命令 | 期望 | 读数来源 | 判定方式 | 覆盖档 | 证据(文件:行/资产路径) | 日期 | 备注
```
`oracle类型` 闭集（只有 8 个）：
| 值 | 含义 | 机检怎么做 |
|---|---|---|
| `asset_field` | 原版序列化字段 | 读 `assets_full/…/MonoBehaviour/*.json` 或 assetripper YAML 的 `字段`，与 `读数来源` 的常量比 |
| `code_const` | 我们代码里的常量/分支 | 读 `读数来源` 的 `路径:行`，逐字含 `期望` |
| `orig_run_dump` | 原版运行时 UI 树 | 读 `runtime_ui_dump_*.tsv` 的 `path/activeSelf/rect/text`，与我们的宿主输出逐节点比 |
| `effect_render` | 原版特效直渲 | 读 `资料/比对基线/sweep_{orig,exp}.tsv` 的同期比值；阈值外 = 红 |
| `card_truth` | 卡面真值/全池对拍 | 读 `B9_全池对拍_差异.tsv` 的 `判定`：`错`=红、`未验到`=琥珀、`对`=绿 |
| `anim_trace` | 原版演出表 | `compare_anim_trace.py --check` 的 rc |
| `manual_only` | 只能人看（观感/手感） | 必须有 `判据/功能点_并排比记账.tsv` 的 ✅ 行 + 证据图；缺失 = **红**（⛔ 不静默） |
| `impossible` | ②B（战斗内局面） | 固定 `N/A` + 原因 `inj FAIL: empty Data`；**不进分母** |

2. `工具/fp_oracle_check.py`（新脚本，⛔ 不改任何现有工具）：
```
python -I -X utf8 工具/fp_oracle_check.py --list
python -I -X utf8 工具/fp_oracle_check.py --only FP-CARD-001
python -I -X utf8 工具/fp_oracle_check.py --json _tmp_view/oracle/report.json
```
- 输入：默认 `判据/功能点_oracle规格.tsv`；只读原版档案与我们源码；只写自己的 `_tmp_view/oracle/`。
- 输出摘要行（固定格式，供机器读）：
```
=== FP oracle：机器通过 X / 机器失败 Y / 人工待签 Z / N/A W ===
```
- **红绿定义**：`rc=0` 仅当 `Y=0 且 Z=0 且 X>0`；`Y>0` 或 `Z>0` ⇒ `rc=1`；`X=0`（什么都没测到）⇒ `rc=2`（「没测到」不是绿）。
- ⛔ 不许把 `impossible` / `N/A` 计入通过数（汇总里单列 W）。

### 2.4 覆盖顺序（先把能真做的做完，再报 N/A）

| 批次 | oracle类型 | 覆盖 FP | 为什么先做 |
|---|---|---|---|
