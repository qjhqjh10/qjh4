# B170 · 诊断 · 降级/升级按钮文字 + 卡组里的特殊卡

> 2026-11-07 第一百四十四会话 · 用户报的三件事的取证与结论。**状态仍在 `资料/离线原版/任务_离线原版.md`**，本文件只放判据。

## 一、按钮文字写不进去（OFF-98 的收尾缺陷）

### 现象
`Content/Upgrade`（升级）与克隆出来的 `Content/Downgrade`（降级）两个按钮**没有文字**；
一度漏出来的是模板串 `将此张牌升级 至等级 {0}`（未本地化）。

### 两条已试过的路（都失败，实机日志为准）
| 路线 | 做法 | 实机结果（`phase0/upgradepanel.tsv`） |
|---|---|---|
| A 克隆原件 | 在 `panel.titleText` 上先写「降级」→ `Instantiate` → 恢复原件 | `SetTmpText` 自检**通过**（`set=降级 exc=none`），但副本渲染的仍是模板串 ⇒ **`Instantiate` 不继承运行时改过的文本** |
| B 新建节点 | `new GameObject` + `AddComponent(Il2CppType.From(TextMeshProUGUI))` | `LABEL-ADD 新建 TMP 失败：write(Component)=SetText=missing; textProp=set-fail` ⇒ **`AddComponent` 只回基类 `Component` 代理，写不进 `text`** |

### 关键事实（下一轮直接从这里接着做）
1. **面板字段 `titleText` 上的组件是真代理**：`ProbeUtil.GetMember(panel,"titleText")` 拿到的对象能读能写（`ReadTmpText` 回读一致）。
2. **克隆体 / 新建体的 TMP 代理拿不到**：`GetComponents<Component>()` 只回 `MonoBehaviour`/`Component` 基类；
   `Resources.FindObjectsOfTypeAll<MonoBehaviour>()` 同样只回基类（`FindTmpComponent` 三条路全 0 命中）。
3. **`SetTmpText` 的兜底 `SetTextInSubtree` 会返回「成功」但不生效** —— 它只写 `text` 成员、不校验渲染，**不可当判据**。
4. 因此**「预写 + 克隆」这条路整体作废**，⛔ 不要再回去调它的分支。

### 最终解法（2026-11-07 · 已实机验证）
1. `FindTmpComponent` 增加路径 ⓪：**非泛型** `Resources.FindObjectsOfTypeAll(Il2CppType.From(具体 TMP 类型))` + Transform 原生指针匹配
   ⇒ 克隆体的 TMP **终于能拿到真代理**（日志 `tmp=True`）。
2. `BuildLabel` 改成**一律在副本上写文字**（`SetTmpText(label, text)`），不再依赖「预写 → 克隆」。
3. 文字节点仍是**按钮的兄弟节点**（用户 2026-11-07 口径：文字挂在按钮上面，不塞进按钮里）。
- ✅ 实机结果：`LABEL ... text=升级`，截图 `_tmp_view/shots/1107_s144/161_buttons.png` —— **「降级 / 升级」都正确显示**。

### 下一轮建议（原计划保留，已不需要）

1. **非泛型 `Resources.FindObjectsOfTypeAll(_tmpType)`**（传**具体 TMP 类型**，不是 `MonoBehaviour`）→ 按 Transform 原生指针匹配 → 若拿到**具体类型代理**，就能直接写 `text`；新建节点也能走这条。
2. 若上一条仍只给基类：**不做新文本节点**，改为「把按钮做成**图片**」——用现成的「升级/降级」本地化**贴图**（若资源里没有中文贴图，则此路不通，如实记账）。
3. 最后兜底（要用户点头）：按钮文字用**英文** `Upgrade` / `Downgrade`（原版 `Button Text` 子节点本来就带英文文案，激活它即可，不需要写 TMP）。

## 二、卡组里的「特殊卡」（秘密/防御/破坏）

### 用户问题
「黑暗天使的秘密卡、帝皇之子的防御卡、基因窃取者的破坏卡，这些特殊卡应该能在卡组里看到吧？」

### 现读事实
| 类别 | 数量 | `inventoryOptions` | `showInCollectionOptions` | 玩家是否拥有 |
|---|---:|---|---|---|
| 防御卡 `spellType 210` | 39 | **5 = `CantAddToDeck`** | 5 | 是（`UserInventory` 2,590 件里都有） |
| 秘密卡 `spellType 150` | 5 | 10 = `NotInInventory` | 5 | 是 |
| 破坏卡 `spellType 230` | 4 | 10 = `NotInInventory` | 0 | 是 |

- 卡组编辑界面**有**专用槽位：prefab `Deck Editing Menu.prefab:1371` `Deck Selector Defensive Card Slot`，
  文案键 `MenuCollection/DefensiveDeckSlot`（"-- Defensive --"，我们这儿显示「-- 防守 --」），
  组件字段 `DeckListDrawer.defensiveCardInfoItem`；**空位只在 `!HasDefensiveCard` 时显示**（`DeckListDrawer.cs:1063-1070`）。
- 加卡判据（`DeckEditingWindow.__<GetCardCollection>b__32_1.c`）：
  ```
  if (inventoryOptions != 5) return true;        // 能加
  if (spellType != 210) return false;            // 不是防御卡 ⇒ 不能加
  if (deck.CustomGameModeEvent != null) { … }    // 只有「自定义模式事件」才给防御卡开口子
  throw NRE;                                     // 其余情况
  ```
  ⇒ **普通模式（Classic/Practice）下，防御卡既不在卡池里、也加不进卡组**。
- 原版预组数据（`bundle_prebuiltdecks_assets_all`）**没有 `defenseCard` 字段**（`PrebuiltDeck` 只有 `cardLibraryIds`），
  ⇒ 预组转成的玩家卡组**先天没有防御卡**。与记忆里「防御卡是我们补的」一致。
- 我们唯一带防御卡的卡组 = 服务端种子 `offline-deck-saimhann`（`defenseCard: ASH55`）。

### 结论
1. **特殊卡不是「丢了」，是原版就不让在普通模式里加**；卡组里没有 = 数据里没有。
2. 秘密卡/破坏卡 `spellType 150/230` 走**普通战术卡**那条路（`inventoryOptions=10` 表示「不在库存」的运行时判定，
   玩家实际拥有），它们**能不能进卡组**要看卡池里是否列出 —— ⚠️ 这一条还没在实机确认（卡池里没找到它们）。
3. 要让卡组里有防御卡，只有两条路：
   - ① **服务端给卡组补 `defenseCard`**（等价于原版预组/后端下发数据的形状，UI 本来就会画那一格）；
   - ② 改客户端数据让防御卡可加（`inventoryOptions` 改成 0）—— 这会偏离原版，需用户拍板。
   🔶 建议走 ①，并按「新卡组自动带上本阵营默认防御卡」实现（原版 UI 的槽位就是为这个准备的）。

### 已实施（2026-11-07 · 用户拍板走 ①）
- `server.py`：`DEFAULT_DEFENSE_CARD`（13 阵营 → 默认防御卡）+ `with_default_defense(deck)`；
  在 **登录下发 `_inject_decks`** 与 **`upsert_deck`（客户端保存）** 两处补齐。
- `state/player_state.json` 里 4 套卡组已补：`ASH55 / UM52 / ASH55 / UM52`。
- ✅ **实机验证**：卡组详情里第一行出现 **火力炮塔（UM52）**，即防御卡已在卡组内。

## 二·b、特殊卡「可见但不可加入」（用户 2026-11-07 追加口径）

- 卡池实测（`deckpool.tsv`）：`GetCardCollection()` 返回 **400 张**，其中 **防御/秘密/破坏 = 0** —— 确实完全不在池子里。
- 探针发现：`CollectionManager.AllCardCollection` 只有 **400 张**、只含 **12 张**特殊卡（ASH55/56 · BL57/58 · SOR59/60 · TL54 · SAU59 · GSC64 · DA 秘密×2 · GSC 破坏×1），
  **没有 UM 的防御卡**；完整表是 **`FullCardCollection`**（收藏页 1,005 张就是它）⇒ 追加时改用 `FullCardCollection`，取不到再退 `AllCardCollection`。
- 已实施（`Probes/DeckPoolProbe.cs`，探针兼补丁）：
  - `DeckEditingWindow.GetCardCollection` **postfix**：把**本阵营**的 `spellType ∈ {150 秘密, 210 防御, 230 破坏}` 追加进返回列表（按 `cardArmy` 匹配，去重）；
  - `CardDeck.CanAddCard` **prefix**：命中上述三类（含 200 进攻卡）一律 `__result=false` + 错误文案 `MenuDeck/Error/InvalidCard` ⇒ **加不进卡组**。
- ⚠️ **状态：代码已落、实机已验证（ASH 卡组）**：
  - `SCAN src=FullCardCollection army=30 allCards=400 specialAnyArmy=13 sameArmy=2` → `APPEND added=2`；
  - 卡池末尾出现 **支派神殿（ASH55）/ 鼓舞遗产（ASH56）**（截图 `1107_s144/156_bottom.png`）；
  - 拖进卡组 ⇒ `BLOCK card=ASH55 spell=210 term=MenuDeck/Error/InvalidCard text=尝试向卡组添加无效的张牌。`
- 🔴 **仍未解决的一条**：**UM（及部分阵营）的特殊卡根本不在 collection 里** ——
  `AllCardCollection` 与 `FullCardCollection` 都是 **400 张**，其中特殊卡只有 13 张，全是 ASH/BL/SOR/TL/SAU/GSC/DA/EC，
  **没有 UM52/53/54**（UM 的防御卡）。所以在 UM 卡组的编辑器里，**自己的防御卡看不到**。
  下一步要查：防御卡在 collection 装载时是不是被 `showInCollectionOptions/showInCollectionOptions` 之类过滤掉了，
  或 UM 的卡资产根本没被加载（bundle 未请求）。这条与「卡组里有没有防御卡」不同 —— 后者已由服务端解决。

### 阻塞（历史记录 · 已由上面的方案绕过）
其余两张防御卡**进不了卡池**，原因是**游戏根本没把它们加载出来**：
- `Resources.FindObjectsOfTypeAll(RawCardScript)` = **1,366** 个，但 `idFail=1180`、`armyHit=1`、`defensive=0`
  ⇒ 回来的多数是**基类代理**，读不到 `uniqueId/cardArmy/spellType`；
- `AssetBundle.GetAllLoadedAssetBundles()` 在 IL2CPP 下返回 **0**（`BUNDLES n=0`）；
- `CardsCollection` 实例 **0 个**（`CC instances=0`），`GetCardsInArmy` 无从调用；
- 资产确实在 `allcards_assets_all.bundle` 里（UnityPy 现读：`UM52 → m_Name=Z-UM-Firestrike Turrets`），
  但**没有被实例化进 CollectionManager**（`AllCardCollection` / `FullCardCollection` 都只有 400 张，特殊卡 13 张）。

⇒ 若要「每阵营 3 张都能在卡池里看到」，必须**自己把卡 SO 从 bundle / Addressables 取出来**（新增一条加载路径），
  这是独立的一块活，不能靠现有反射口绕过。**已向用户说明并列为下一件**。



- **启动后 10~12 秒点「收藏」会 `open-ret NULL`**（窗口建不出来）；等到 **~25 秒**再点就正常。
  ⇒ 以后实机脚本统一「主菜单出现后再等 20–25 秒」再点第一下。
