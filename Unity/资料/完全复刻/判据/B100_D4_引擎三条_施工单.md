## 三、C · 253/254 的 peek/reuse 退路：**原版「choose 之前有随机」时怎么算 options**

> 前置：`B99_R1_战斗6条终局.md` §一·253/254 ＋ `报告/B99_R1.md` §七 **已完成的部分不重查**（选法、随机消耗、归因、可达 1 张、A/B/C 三条件拆解）。本笔**只补它没答的那一问**。

### C·1 判据结论（原版的行为）

**options 没有「提前算」这回事 —— 就在 choose 那一刻现算，游标已包含 choose 之前的所有随机消耗。**

判据链（逐句现读）：
1. `decomp_full/BattleManager._ChooseCardMethod_d__449__MoveNext.c:10-41`（协程 state0）：
   先 `GetChoiceFullPool`（空池 ⇒ 直接回调 `0`、不开面板），再按 `isPlayer(+0x2c)` 调
   **`BattleManager__ChoiceOfCardPlayer(...)`** 或 `ChoiceOfCardEnemy`。
2. `decomp_full/BattleManager__ChoiceOfCardPlayer.c:25-27`：
   `UnpauseForAnim` → `CancelActionStates` → `UIstate(+0x290) = 0xe` → **`GetChoiceOptions(manager, actingCard, targetCard, 0, 0)`** ← **就在这一句里抽**。
3. `decomp_full/BattleManager__GetChoiceOptions.c:40-101`：
   `N = min(池, choicesDefinition.maxTargets)` → 循环 **每次 `GetRandomInt(0, pool.Count)` 抽 1 下** → `RemoveAll(同 uniqueId)` → 不够从副本头补齐；
   `:110-113` 玩家那一路（第 4 实参 0）再 `SortByCostAndName`。
4. `GetRandomInt` 是**按预烧表游标取**（`MatchData.cs:541-573`；我们 = `BattleContextRandom.cs:62-72`）：**不掷骰**，`maxExcl <= minIncl+1` 时不消耗。

⇒ 原版里「choose 之前有随机」**不是特例**：choose 之前那些随机已经推进了游标，`GetChoiceOptions` 从**当时**的游标往后取。
**我们的正确形状**因此是：**选项在结算那一刻（`TakePickCard` → `BuildChoiceOptions`）真抽** —— 就是今天 peek 复用失败后的回落行为。
**⛔ 绝不能把「算 options」挪到面板那一刻去消耗随机**（那会让「只跑面板的那一侧」多消耗、A/B 两端随机流分叉、`NetProtocol.Fingerprint` 与重放全错 —— 这一段 `EffectResolver.cs:20040-20065` 已写死）。

### C·2 那么「peek 失败」的残差到底有多大 —— **对它目前是零**

唯一可达的那张 = **`Author of the Codex`**（id `40667e346ae58a84dbda1033dff70ccb`，tactic，`cardType=20`）：

| 字段（`cards_engine.json` 现读） | 值 | 意义 |
|---|---|---|
| `choicesTargetsAffected` | **180**（`choiceResolution`） | 走 `GetChoiceFullPool` |
| `choicesMaxTargets` | **3** | `GetChoiceOptions` 的 N |
| `unitConditions[role="choice"].choiceSet.filterSpecificCards` | **3 个固定 id**（三张 Codicil） | 候选池 = **恰好 3 张** |

- `GetChoiceFullPool`（`decomp_full/BattleManager__GetChoiceFullPool.c:28-70`）：`targetsAffected==180` 且 `filterSpecificCards` **非空**时，**不**用 `manager+0x308`，直接用 `filterSpecificCards` 过 `Where(non-null && +0x38 != 0)`（`b__488_0.c`）⇒ **池 = 这 3 张**。
- ⇒ `N = min(3, 3) = 3` ⇒ 无论游标在哪，抽出来的 options **永远是那 3 张**（只是顺序随随机变）。
- 玩家那一路还要 `SortByCostAndName`（`GetChoiceOptions.c:110-113`）；我们的面板也照同一把尺排（`BattleDriver.cs:10699 CompareChoiceOptions`，判据已解出）。
- 我们的面板回落 `DrawForDisplay(cands, k)`（`BattleDriver.cs:10745`）在 `k = ChooseShowLimit = ChoicesMaxTargets = 3`、`cands = 3` 时也**摆满 3 张**；
  玩家答案按 `CardDef.Id` 回引擎在**完整候选表**里找（`EffectResolver.cs:4528-4541`）⇒ **顺序不影响结果**。

**⇒ `Author of the Codex` 的 peek 失败（`StartIndex` 因 codex 先跑随机而变）只做两件事：**
① 打一条 `UnityEngine.Debug.LogWarning`（`EffectResolver.cs:20231`；**不是** `ctx.Log` ⇒ 不进 `ctx.Events`、不动指纹、不影响 P2P/重放）；
② 引擎按**正确时机**真抽（消耗的格数与 peek 完全相同：3 张池 = 2 次消耗，第 3 抽 `maxExcl=1` 不消耗，`BattleContextRandom.cs:68`）。
**面板摆的 3 张 == 引擎抽的 3 张（集合）**，排序后顺序也相同 ⇒ **可观测差异 = 0**。

### C·3 精确改法：**不改**

| 项 | 结论 |
|---|---|
| 改随机流语义（让面板那一刻也算 options） | ⛔ **不做**（反原版，见 §C·1 末） |
| 让 `TakePeekedChoiceOptions` 在「游标已动」时**不回落、直接按 peek + 前推 `Draws`** | ⛔ **不做**（那才是「改随机流语义」：它会让选择结果变成「按 panel 时点算的那一份」，与原版在 choose 时刻算**不同**；今天只因为池=上限才恰好等价） |
| 面板/引擎那条 `LogWarning` | 保留（诚实出声；且不进指纹）。若嫌吵，可改成 `Debug.Log`，但**不建议**在本笔动（属表现层文件，且要重新审一遍判据） |
| 253/254 的账位 | **建议由调度台复核后可判 A**：方法本体等价 ＋ 残余（§C·2）**已被证明零可观测**；剩「真机核」按 `B99_R1` §五③ 非账项处理 |

### C·4 可达性（现读）

- **1 张**：`Author of the Codex`（`40667e3…`）**且**「Trigger the Codex ability of a friendly unit」兜到 `UM56` / `UM55` / `UM79` / `UM82` 这 4 张**带随机 codex 的单位**之一时才触发 `StartIndex` 失配（`B99_R1` §七·2 已扫，本笔不复核）。
- 其余 **62 张** `choosecard` 卡的 choose 都是**首个 op** ⇒ `StartIndex` 不变 ⇒ peek 复用成功。

### C·5 还差什么 / 什么时候要重开这一题

- **结构性前提**：若未来出现「**池 > maxTargets** 且 choose 之前有消耗随机的 op」的卡，则面板会摆一个**子集**、引擎抽另一个子集 ⇒ 那时才有可观测差异。
  ⇒ **写一条池扫描断言/工具**：`choosecard` 卡中「首个 choose 之前有 `GetRandomInt` 型 op」**且**「`GetChoiceFullPool` 可能 > `maxTargets`」的卡数**必须 = 0**；池一更新就重跑（`B99_R1` §七·2 的脚本可直接复用为判据）。
- **未核的一格（如实）**：`GetChoiceFullPool` 的 `Where(+0x38 != 0)` 我按「3 张 Codicil 都满足」处理（`+0x38` 是 `PlayerItem.uniqueId` 一类必填字段）；**没有逐张验证**这 3 个 id 的该字段。若担心，执行代理可加一条断言：`GetChoiceFullPool(Author)` 返回 `Count == 3`。
