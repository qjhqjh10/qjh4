## §1 目标形状（一句话）

**落点列 = 一个方法 + 一个 `文件:行号` + 一个括注方法名；其余一切（第二处方法、接线点、等价说明）放散文，且散文里不带行号。**

模板：

```
<相对路径>.cs:<行号>（<方法名>）· <可选：等价说明 / 第二个方法名（不带行号）>
```

允许的括注三形态（都不是方法时要在括号里说清楚）：

| 形态 | 例 |
|---|---|
| 方法 | `Shell/FastModeBaseEvent.cs:618（GetEventDeck）` |
| 嵌套类的方法 | `Shell/ChatPanel.cs:791（ChatMessageRow.Build）` |
| 属性 / 字段 / 类（原版那条本来就不是方法） | `Shell/LiveOpsEvent.cs:385（Priority getter）` · `Shell/ItemDrawer.cs:142（ItemSpec.Label 字段，非方法）` · `Shell/BadgeNotifications.cs:97（class CampaignBadge）` |

## §4 全库范式（5 条硬规则）

| 规则 | 内容 | 违反后会发生什么（都是实测过的） |
|---|---|---|
| **R1 一个** | 落点列**有且只有一个** `路径.cs:行号` | 多一个 ⇒ 机检按第一个判、第二个**永远不被检**（`check_ledger_points` 不评估括注里嵌的第二个 `文件:行`）⇒ 空转绿灯 |
| **R2 紧跟** | 该 `文件:行号` **紧跟** `（方法名）`，中间不插别的 | 不紧跟 ⇒ 提取器判「无方法名」⇒ 落进本批这种「没法核」的池子（125 条里 **41 条**是纯这一种） |
| **R3 不叠括号** | 括注之后若还要写说明，用 `·` / `；` 起头，**⛔ 不许紧接着再开一个 `（`** | `（Add<T>）（等价实现 = …）` 这种双括号会让提取失败（本批 **22 条**是这个形态） |
| **R4 散文不写行号** | `差异` / `备注` / 落点列散文段里**⛔ 不出现裸 `:NNN`**；要指第二个方法就只写方法名 | 裸行号不可机检，而且**最容易漂**（本条实例 3 个全落在注释行） |
| **R5 括号内容有白名单** | 括号里只许 `Name` / `Class.Name` / `Name getter` / `Name 字段，非方法` / `class X`；**⛔ 不写「等价实现 = …」** | 括号里写成散文 ⇒ 提取器把整段当方法名 ⇒ 判「方法名不存在」 |

**R5 的两个已知陷阱**（本轮 40+ 条踩过，人工核也要当心）：

- **单行体** `public override void Open() { Build(); }` —— 往回找「最近的方法声明」会**越过它**、指到上一个方法；
- **属性 getter** `public int Priority { get { … } }` —— 同样会被越过。
- ⇒ 正确判法 = **先判「这一行本身是不是声明」**（method / property / class / field），是就用它；不是才往上回溯。
- **const 行不能当落点**（`public const int MaxNameLen = 25;` 这种）。

## §5 可写成 lint 的机检规则（建议加进 `check_ledger_points.py` 或新开 `ledger_landing_lint.py`）

只跑**脚本 + 源码**、不需要 Unity，秒级。

| 代码 | 判据（对 `我们的落点` 列） | 报什么 |
|---|---|---|
| **L1** | `len(re.findall(r'[\w./\\-]+\.cs:\d+', land)) != 1` | 「落点必须恰好一个 `文件:行号`（现 N 个）」 |
| **L2** | 落点里出现 `.cs` 但**不跟** `:` 或 `：` | 「文件名后缺行号」（本条实例） |
| **L3** | 匹配 `[\w./\\-]+\.cs:\d+\s*（` 失败 | 「`文件:行号` 后没有紧跟 `（方法名）`」 |
| **L4** | 括注里出现 `（` 或 `）`（即双括号） | 「括注后又开了一个括号（R3）」 |
| **L5** | 落点**除第一个** `文件:行号` 之外，还出现 `:\d{2,}` | 「散文里有裸行号（R4）」（本条实例） |
| **L6** | 解析第一个 `文件:行号` → 该行**或其最近祖先**的声明名 ≠ 括注名 | 「落点声明名对不上」（本条实例：3 个行号都不是那三个方法） |

**L6 的解析要点**（本轮探针的实测结论，直接照抄即可）：

1. 二进制读文件、自己按 `\r\n`/`\n` 切（⛔ 别用 Python 文本模式）。
2. 先判 `AT 行` 本身：`class/struct/record/enum` → `class X`；`X { get` → `X getter`；`含 (…) ` → 方法名；`类型 名;` → `X 字段`。
3. 都不是才往上回溯（跳过 `if/for/while/return/new/foreach` 与含 `=` 的行）。
4. 名字比对允许 `Class.Name` 形态（取最后一段）。

**示例输出**（拿本条跑 L1–L6）：

```
战斗界面_HUD.tsv:761  L1 落点有 1 个"文件:行号"（BattleDriver.cs:36725）… 但文件名后无冒号 ⇒ L2
                      L2 `BattleDriver.cs` 后缺冒号
                      L5 散文里有 5 个裸行号（:36742 :36756 :15026 :14989 :13307）
                      L6 :36725 的声明名 = TutorialAnchorExtra ≠ HitFoeHand
```

## §7 落地顺序建议（省人力）

1. **先跑 L1–L5**（纯文本、不用源码）⇒ 得到「格式违规」清单。这一批**绝大多数可以脚本半自动改**（补冒号、去裸行号、拆双括号）。
2. **再跑 L6**（要读源码）⇒ 得到「行号漂移 / 指向别的方法」清单。**这一批必须人工确认**（`--fix` 那类按符号名重定位的工具只能改行号、改不了「指错方法」）。
3. **⚠️ 顺序不能反**：L1–L5 没治之前，L6 的解析会大量失败（文件名后没冒号 ⇒ 解析不到文件）。
4. **只改 `我们的落点`（+ `差异`/`备注` 各追加一句）**，`状态`/`等级`/`判据出处`/`判据要点` 一律不动 —— 落点规范化不是重新判定。
5. 改完必跑 `check_ledger_points.py --all-A`（那是行号闸）+ 本文这套 lint（那是形态闸）。
