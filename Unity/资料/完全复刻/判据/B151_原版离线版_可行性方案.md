## 1. 一句话结论

**有条件可行，而且比 HH:L 那边容易得多。**

条件只有三个，都能在阶段 0/1 里验掉：

1. **MelonLoader 的 Harmony 补丁能不能打到 IL2CPP 原生方法上**（本工程现有 mod 只用代理调用、**从没打过补丁** ⇒ 这一条**目前是零证据**，是整份方案的第一号前提）；
2. **登录响应能不能用一个本地 HTTP 服务伪造**（`PlayFabSettings.staticSettings.ProductionEnvironmentUrl` 可写 ⇒ 大概率能）；
3. **`AssetBundleManager.GetLoadedBundle` 的资产名映射**（本机 bundle 文件名与游戏请求的名字是否一一对上，阶段 0 打日志即知）。

主要代价：**要写一个「假 PlayFab + 假 CloudScript」的本地服务**，并把玩家档案的 JSON 形状对着 DTO 逆推出��；这不是「一个 hook 就完事」，而是**接口层的一小套服务端**。乐观估计 **3～5 个会话**能到「进主菜单 + 打一局 AI」，联机档另算。

**关键红利（比 HH:L 强）**：原版**全部内容资源 1.6 GB 已经在本地安装目录里**（`StreamingAssets/aa/StandaloneWindows64/` 84 个 bundle，与 `d:/2/新解包资源/assets_full` 的 84 个 game bundle **一一对应、无缺包**），**不需要像他们那样去归档远端包**。且**版本永不更新**。

### 2.3 到主菜单只需要 3 个服务端调用（这是本方案最重要的一条）

`Assembly-CSharp/CloudHandle.cs` 列了 **128 个云函数 id**（`onUserConnected=10` … `GetReadOnlyPublisherData=1121`）。但**登录到主菜单这条路上只用到 3 个**：

| # | 调用 | id | 代码证据 | 返回什么 |
|---|---|---|---|---|
| 1 | `PlayFabClientAPI.LoginWithSteam` | — | `CloudscriptHandler__LoginWithSteamAccount.c` | `LoginResult`（**整个玩家档案都在这一个响应里**） |
| 2 | `GetReadOnlyPublisherData` | **1121 (0x461)** | `PlayerDataManager._GetAllPublisherPlayerData_d__515__MoveNext.c`：`PlayfabWrapper__GenericCloudScriptHandler<object>(0x461, ...)` | `Dictionary<string,string>`（只有 2 个键：`Sunset` / `WarpforgeLivePlayed`，见 `PlayerPublisherDataKey.cs`） |
| 3 | `onUserConnected` | **10** | `PlayerDataManager._ProcessNewLogin_d__533__MoveNext.c`：`PlayfabWrapper__GenericCloudScriptHandlerAsync<object>(10, ...)` | 一个 JSON 对象，字段落在 `+0x10`(long) / `+0x18`(string) / `+0x20`(字典，会被合并进 `UserData`) / `+0x28`(列表) / `+0x30`(Nullable&lt;int&gt;)（`PlayerDataManager__ProcessNewLoginResult.c`） |

登录后的状态机（`cpp2il/out_cpp2il_dev_ilspy/LoginManager.cs:550-700`，`_ProceedSuccessfulLogin_003Ed__32.MoveNext`）：

```
ProcessLoginResult(success)
 └ ProceedSuccessfulLogin(loginResult)
     ├ playerData.FinishLogin(loginResult)            ← 把 PlayFabId/SessionTicket/InfoResultPayload 存进 PlayerDataManager+0x2a8
     ├ playerData.AsyncInitialization()               ← SetupPlayfabPublisherVariables → GetAllPublisherPlayerData(1121) → UnityServices → GameAnalytics
     └ currentState = successfulLogin
 └ CheckNewVersion()  ← 只读本地/login payload，不联网（PlayerDataManager__UnpackOnlineVersionData.c 读 OnlineData.GetServerVersion）
 └ CheckNewVersionSucceed() → UnpackPlayerData() → ProcessData()
     └ playerData.ProcessNewLogin() → onUserConnected(10) → ProcessNewLoginResult(...)
 └ TryCompleteLogin() → currentState = finished(50)
```

**「玩家数据在登录响应里」这条的判断依据**：`Assembly-CSharp/OnlineData.cs` 的**每一个**方法签名都吃 `PlayFab.ClientModels.GetPlayerCombinedInfoResultPayload`：

```csharp
public static ServerVersionConfig GetServerVersion(GetPlayerCombinedInfoResultPayload userInfo)
public static T GetPlayerOnlineData<T>(GetPlayerCombinedInfoResultPayload userInfo, PlayerDataKey key, bool checkPublicData = false)
public static T GetTitleData<T>(GetPlayerCombinedInfoResultPayload userInfo, TitleDataKey key)
public static int GetCurrency(GetPlayerCombinedInfoResultPayload userInfo, Currency currency)
```

而 `PlayerDataManager__FinishLogin.c` 把 `loginResult + 0x30` 存进 `playerData + 0x2a8`；`PlayerDataManager__UpdateCardCollection.c` 用同一个对象调 `InventoryManager.DeserializeInventory(items, virtualCurrencies)`。

⇒ **伪造一个 `LoginResult` ＝ 一次性把 51 个 `PlayerDataKey` + 30 个 `TitleDataKey` + 卡收藏 + 货币全都喂进去**。这比 HH:L 那种「逐字段写裸偏移」干净得多。

## 3. 技术路线

### 3.1 注入框架选型

| 维度 | **MelonLoader（已装、已跑通）** | **Frida（HH:L 用的）** |
|---|---|---|
| 本质 | .NET 运行时 + `version.dll` 代理加载 → 在 `il2cpp_init` 之后接管 | 独立进程外注入器，`spawn` 挂起 → `attach` → `create_script` → `resume` |
| 定位类/方法 | **编译期就有类型**：`Il2CppInterop` 生成了 157 个托管代理程序集，`LoginManager` 是个真 C# 类型，字段按名访问 | 运行时走 IL2CPP C API（`il2cpp_domain_assembly_open` / `class_from_name` / `class_get_method_from_name`），按「类名 + 方法名 + 参数个数」三元组 |
| 改托管字段 | ✅ 按**名字**（`player.FieldName = x`，私有字段走反射）—— 比裸偏移安全一个数量级 | ✅ 按**裸偏移**（`obj.add(0x304).writeS32(30)`），换版本即失效 |
| Hook 托管方法 | ✅ HarmonyX（`0Harmony.dll` + `Il2CppInterop.HarmonySupport.dll` 都在）—— ⚠️ **本工程从未验证过它能打到原生入口**（见 §6-U1） | ✅ `Interceptor.replace` / `attach`，被 HH:L 大量验证 |
| Hook 原生导出（`ws2_32.connect` 等） | ✅ `MonoMod.RuntimeDetour.dll`（在 `MelonLoader/net6/`）可对任意函数指针下 `NativeDetour` | ✅ `Interceptor.replace` 直接可用，HH:L 已用 |
| 拦 HTTP | 两条路都**不直接**拦 HTTP，靠「改 PlayFab 的 base URL」或「拦 `ws2_32`」 | 同 |
| 写代码的方式 | C#，**要编译 + 重启游戏**（迭代一次 ≈ 10–20 s） | JS，**改完只重启游戏、不编译**（`script.load()` 前替换源码即可），迭代更快 |
| 调试反馈 | `MelonLogger.Msg` → `MelonLoader/Latest.log` | `send()` → 启动器进程的 jsonl |
| 我们已有的先例 | ✅ 这个游戏上有 3.6 版 mod、能 dump UI/拍图/load bundle/调 Addressables | ⛔ 我们在 Warpforge 上零先例 |
| 依赖 | 已装好（`version.dll` 在客户端根） | 需要把 `frida-core` 打进包（HH:L 的 `_frida.pyd` 是 135 MB） |
| 发行形态 | 客户端目录旁边一个 `Mods/xxx.dll` | 一个 135 MB 的注入器 + Python 运行时 + 启动脚本 |

**推荐：MelonLoader。** 反证（为什么不用 Frida）：

- 我们**已经在跑** MelonLoader，且它**已经证明能在这个 IL2CPP build 上工作**（能调 `Addressables.LoadAssetAsync`、能 `AssetBundle.LoadFromFile`、能遍历 UI 树）。换 Frida 等于**从零重来**，而收益只是「迭代快一点」。
- Frida 的核心优势是「不依赖游戏的托管类型信息」—— **但我们有 157 个代理程序集、1,870 个签名桩、25,096 个方法体**，信息量远超 Frida 现场解析能拿到的。按名字访问字段 > 按偏移访问。
- Frida 的优势之二「改脚本不用重编译」—— 我们可以用**外部 JSON 配置 + 热重载**补偿（假服务器的响应就是外部 JSON，改它不用重编译）。

**唯一的翻车点**：如果 §6-U1 证明 HarmonyX 打不到原生方法，就退到 **`MonoMod.RuntimeDetour` 直接对函数指针下 detour**（和 Frida 的 `Interceptor.replace` 完全等价），仍不必换框架。

### 3.2 假服务端的形态：改 base URL，不搞 TLS 中间人

`PlayFab` 的地址是可写的（**这是本方案的技术支点**）：

```csharp
// d:/2/Warpforge_code/Scripts/PlayFab/PlayFabApiSettings.cs
public virtual string ProductionEnvironmentUrl { get; set; }
// d:/2/Warpforge_code/Scripts/PlayFab/PlayFabSettings.cs
public static readonly PlayFabApiSettings staticSettings;
```

`PlayFabSettings.GetFullUrl(apiCall, getParams)` 会拼出最终 URL。把 `staticSettings.ProductionEnvironmentUrl` 设成
`http://127.0.0.1:<port>/`，所有 `Client/*` 调用就打到一个本地 HTTP 服务上（**明文 HTTP，不需要证书、不需要改 hosts、不需要拦 TLS**）。

**反证**：为什么不去 `ws2_32` 层拦？
- HH:L 把 `connect/WSAConnect/sendto/WSASendTo` 全打成 `-1`（`probe.js:2662-2668`）—— 那是**因为他们决定整个服务端都不做**。
- 我们要做**一个假服务端**，就不能把 socket 打死。
- 但**其余出站**（Unity Analytics、Firebase、GameAnalytics、Photon、Steam Web API）**应该**拦 —— 拦在 `ws2_32` 层最省事，且这些都不是我们要回的。

⇒ **混合策略**：
1. PlayFab 走 **base URL 重定向**（要能回）；
2. 其余主机走 **`ws2_32` 打死**（回不了正好）—— 但要注意 `ws2_32` 打死是**全局**的，会连本地 loopback 一起打死。**必须先按目标地址放行 `127.0.0.1`**（HH:L 没这个问题是因为他们根本不需要回环）。这是**照搬会踩的坑**，见 §4.3。

## 4. HH:L 实现细节与可借鉴清单

> 本节是本轮**直接读 `E:/2hhl` 源码本体**得到的（不只看那两份结论报告）。所有 `文件:行` 都可复核。

### 4.0 他们的整体形状（一句话）

`start_offline.py` → `runpy` 跑 `probe.py` → `frida.spawn` 挂起 → `attach` → `create_script` → `load` → **`resume`**。

### 4.1 可直接照搬的做法

#### (1) 注入时机：**`il2cpp_init` 的 `onLeave`**

```js
// probe.js:2687-2690
if (n === 'gameassembly.dll') {
  Interceptor.attach(m.getExportByName('il2cpp_init'), { onLeave(){ installIL2CPP(m); } });
}
```
外面是 `Process.attachModuleObserver({onAdded(m){ ... }})`（`probe.js:2644`），按模块载入事件触发。

**为什么是这一刻、不是更早/更晚**：
- **更早**（进程启动时）：`il2cpp_*` 导出还没法用，`domain_get()` / `class_from_name()` 全返回 null。
- **更晚**（第一个场景 Awake 之后）：`LoginManager.Start` 已经在跑，来不及拦。
- `il2cpp_init` **返回**时元数据已加载、域已建好，但**任何 MonoBehaviour 都还没 Awake** —— 这正是唯一正确的窗口。

**我们用在哪**：MelonLoader **自带**这个时机（`MelonMod.OnInitializeMelon` 在 IL2CPP 就绪后、场景加载前调用）。
⇒ **不需要自己找时机**，这是 MelonLoader 相对 Frida 白送的一条。⚠️ 但要在阶段 0 用日志**确认一次**：
「在 `OnInitializeMelon` 里 `Il2Cpp.LoginManager` 能否解析、能否取到 `MethodInfo` 指针」。

#### (2) 按「类名 + 方法名 + 参数个数」解析，而不是写死偏移

```js
// probe.js:19-70
const api=(name,ret,args)=>new NativeFunction(m.getExportByName('il2cpp_'+name),ret,args,{abi:'mscdecl',...});
const assemblyOpen=api('domain_assembly_open','pointer',['pointer','pointer']);
const classGet   =api('class_from_name','pointer',['pointer','pointer','pointer']);
const methodGet  =api('class_get_method_from_name','pointer',['pointer','pointer','int']);
...
const game = imageGet(assemblyOpen(domainGet(), Memory.allocUtf8String('Assembly-CSharp')));
function klass(name){ return classGet(game, Memory.allocUtf8String(''), Memory.allocUtf8String(name)); }
function method(c, name, n=-1){ return methodGet(c, Memory.allocUtf8String(name), n); }
```
他们甚至做了 `MethodInfo` 缓存（`probe.js:53-62`，上限 2048 条，LRU 淘汰），并且**缓存 MethodInfo 而不是函数地址**，这样后续 re-patch 仍能看到。

**对我们有没有用？——结论：思路照搬，实现方式降级为「编译期类型 + 运行时兜底」。**

理由：
- 我们**版本永不更新**，所以「按名字解析」的最大好处（小版本间迁移）**对我们为零**。
- 但「按名字」还有第二个好处，**这个对我们同样有效**：**混淆过的方法名改起来只改一处字符串**。Warpforge 有大量 `CAMEJAFCOEB` / `PAJKAPBJHHD` 这种混淆名（`Assembly-CSharp/` 里满地都是）。
- **真正该照搬的是它拒绝「写死偏移」的纪律**，而不是它实现解析的手段。我们的等价物是：
  ```csharp
  // 公开成员：直接 typed（编译器帮你查错）
  var lm = Il2Cpp.LoginManager.instance;  lm.currentState = ...
  // 私有/混淆成员：反射拿字段，仍按名字
  var f = typeof(Il2Cpp.PlayerDataManager).GetField("playerObject", BindingFlags.NonPublic|BindingFlags.Instance);
  ```
  **绝不写 `+0x304`**。这一点我们比他们**强**：他们被迫写偏移，因为我们有 `Il2CppInterop` 代理。

#### (3) 裸 RVA 的**指令字节自检**（不符就抛错，不继续跑）

三处，每处都先验字节：
```js
// probe.js:1105-1112 —— 骑士详情查 playerData 的分支
// 先验三字节 8b 45 0c  (mov eax,[ebp+0xC])，不符即抛
// lan_runtime.js:332-335 —— 聊天「是否已连接」判定
// 先验两字节 84 c0 (test al,al)，只改 eax=1 后返回
```
**这是他们全篇最值得抄的一条工程纪律**：裸地址**可以写**，但**每个裸地址必须自带守门**，守门失败要**炸**，不是静默返回错误结果。
（对照我们自己的坑：CLAUDE.md 里记着「三处裸 RVA 都带字节自检」是好事，而我们在 `RuleCore.cs` 上踩过「代码落进 `//` 注释、`typecheck 0/0`、断言一条没跑」。）

**我们用在哪**：如果 §6-U1 失败、必须走 `NativeDetour(函数指针)`，那么「指针来源」本身也要带自检 ——
先 `Marshal.ReadByte(ptr)` 验首字节、或先用反射确认 `MethodInfo` 非空，**不符就 `MelonLogger.Error` 并放弃该 hook**，⛔ 不许「打不上就静默继续」。

#### (4) 网络层：**`ws2_32` 三个入口打成 −1** vs 更上层拦截

```js
// probe.js:2662-2668
replace(m,'connect'  ,'int',['int','pointer','int'],()=>-1);
replace(m,'WSAConnect','int',['int','pointer','int','pointer','pointer','pointer','pointer'],()=>-1);
replace(m,'sendto'   ,'int',['int','pointer','int','int','pointer','int'],()=>-1);
replace(m,'WSASendTo','int',['int','pointer','int','pointer','int','pointer','int','pointer','pointer'],()=>-1);
```

| | `ws2_32` 层 | 更上层（语义空桩） |
|---|---|---|
| 覆盖面 | **全部** socket 用户（PlayFab / Photon / Unity Services / 内购 / 遥测），一个都跑不掉 | 只覆盖你想到的那些类 |
| 副作用 | **任何**回环也被打死（含你要自建的假服务器）；库内部可能把 `-1` 当可重试 → 无限重试；某些库会走到 `send`/`WSASend`（**这两个他们没拦**） | 要逐个类找；漏一个就发出去 |
| 他们同时用了 | ✅ `ws2_32` + **上层空桩**（`LoginManager.Start`、`NetworkCustomManager.StartConnection`、`PlayerDataManager.IsLoggedIn` 恒真） | 同上 |

**关键观察（他们没说、但代码里能看到）**：他们**只拦了 `connect/WSAConnect/sendto/WSASendTo`，没拦 `send`/`WSASend`/`sendmsg`**。
这对他们是够的（`connect` 已经失败，就没有已连接的 socket 可用），但**如果我们按目标地址放行回环，那些放行出去的连接就能用 `send` 发数据** —— 这反而**正是我们要的**（PlayFab 走 HTTP）。
⇒ **我们可以原样照抄这四个，再加一条「目标是 127.0.0.1 就放行」**。

作用是：离线启动时一大堆 `null` 的子对象会让原版代码 NRE，他们一次性填满。
**限制（他们自己也写了）**：跳过 `UnityEngine.*` / `PlayFab.*` / `Firebase.*` / `Photon.*` 命名空间、跳过值类型、跳过 Unity 对象、跳过 `List`/`Dictionary` 泛型、跳过名字像 `Manager|Delegate|Action|Func|Task` 的；深度上限 3；`<lodgeDeckToCopy>` 字段**故意不填**（注释说：填了会让编辑器走 native create/import，反而不走「复制玩家的卡组」那条路）。

**我们用在哪**：**部分照搬，但优先级降低**。因为 Warpforge 的档案是**一个整包 DTO**（`GetPlayerCombinedInfoResultPayload`），不是几十个散字段 —— 构造一个 DTO 比 `fillDefaults` 更可控。

**必须照搬的那条纪律**：`<lodgeDeckToCopy>` 那类「填了反而坏事」的字段 —— 意味着**「把所有空字段都填上」不是无脑安全操作**。我们做同类兜底时也要能**白名单/黑名单**。

### 4.3 他们踩过、我们**能避开**的坑（从代码里读出来的）

| # | 坑 | 他们怎么暴露的 | 我们怎么避开 |
|---|---|---|---|
| 1 | `ws2_32` 全打死 ⇒ **自己也没法连本地假服务器** | 他们不需要回环，所以没暴露；**但我们要回环** | 在 `connect`/`WSAConnect` 钩子里**先判 `sockaddr_in` 的地址是不是 127.0.0.1/::1，是就放行** |
| 2 | `globalgamemanagers` 改过 ⇒ 完整性校验必须显式跳过 | `probe.py:44-45`：`if (relative.endswith('globalgamemanagers')) continue;  // The clone has its own company/product identifier.` | 我们如果改 `app.info`/`globalgamemanagers`，**在自己的校验脚本里同样要跳过**；如果不改（走 hook 重定向），就没有这个问题 |
| 3 | 只要 `Awake` 被换掉，`OnEnable` 仍会注册单例 ⇒ 之后每次 `Instance` 查询都会**新建一个 GameObject** | `probe.js:138-142` 注释（"OnEnable registers s_instance even when Steam is uninitialized. Preserve it..."） | 我们 stub `SteamManager` 时，**要么连 `OnEnable` 一起 stub，要么保留 `OnEnable` 让它注册单例** —— ⛔ 只换 `Awake` 会制造「每次查 Instance 多一个空 GameObject」的隐形泄漏 |
| 4 | 「本地找不到 bundle」时原版**只 LogError 不抛** ⇒ 表现为「界面空白/卡在某一步」，很难定位 | 他们挂 `GetLoadedBundle` 来兜（`probe.js:194-210`） | 我们挂同一个点，并**在未命中时自己打 Error 带上「请求名 + 我们有没有近似名」**（勿静默） |
| 5 | Unity 对象的托管 wrapper 还在、**原生对象已经被卸载** ⇒ 指针非 null 但不可用 | `probe.js:246-250` 注释（"A GC handle keeps the managed wrapper alive, but Unity can unload its native AudioClip. | 6 | `IL2CPP bool` 参数**只占一个字节**，x86 调用方可能把垃圾留在高位 | `probe.js:48-49`：`const nativeBool = value => !!(value.toUInt32() & 0xff);` | 我们用 typed 代理，编译器帮我们处理；但**如果走 NativeDetour 手写签名**，bool 必须 `byte` |

| 8 | 混淆名（`CAMEJAFCOEB` / `NDDIMFFGPKM` / `PAJKAPBJHHD`）会**随 build 变** | 他们把混淆名集中写在少数几处 | 我们**版本永不更新 ⇒ 混淆名可以写死**，但**必须在同一份「映射表」文件里集中管理**，并注明"此名来自 1.35.0 build 的 `dump.cs`" |
| 9 | 拦截失败**静默** | 他们几处 `try{}catch(e){send(...)}` 还行，但 `replace()` 里 `if (!addr) return;` **是静默的**（`probe.js:12-14`） | 我们的 hook 安装必须**逐个报告成功/失败**，失败就 `MelonLogger.Error` 并记进一份 `hooks_installed.tsv` |

| **版本是否会更新** | 会（V2.2 → V2.3，还在发） | **永不更新**（关服） | 🟢 **我们好**：不用做版本指纹、混淆名/偏移可以钉死、不用做迁移 |

| **反编译覆盖** | 未提，但他们大量用裸偏移 ⇒ 推测覆盖不足 | **25,096 个方法体 + 1,980 个 cpp2il .cs + 2,785 个 il2csharp .cs + 1,870 个签名桩** | 🟢 **我们好** |
| **注入框架先例** | 他们有成熟工具链（V2.3 迭代到 20k 行自有代码） | **MelonLoader 已装已跑通**，但**只做过「调用」没做过「打补丁」** | 🟡 各有千秋：我们有载体，他们有成熟度 |
| **写代码的语言** | JS（Frida），**改完不用重编译** | C#（MelonLoader），**要编译**（`bash 工具/typecheck.sh` 秒级，但真跑要重启游戏） | 🔴 **他们好**（迭代快） |
| **能按名字访问字段** | ❌ 只能按裸偏移（`add(0x304)`） | ✅ `Il2CppInterop` 生成 typed 代理，按名字 | 🟢 **我们好** |
| **对「服务端接口」的理解** | 他们要还原的是 Photon/自建大厅；PlayFab 直接掐死 | 我们要还原的是 PlayFab 的 **JSON 形状**（DTO 齐全，可以直接对着 `Assembly-CSharp/` + `PlayFab/` 的签名桩写） | 🟢 **我们好** |
| **反作弊** | 未在报告里提到 | 只有 `ObscuredTypes`，**无检测、无完整性校验** | 🟢 **我们好** |
| **一个「官方版本」当对照** | 他们有「原版」目录可逐字节比对 | 我们也有 `d:/2/unity_run_ref` 单份，**无第二份可比** | 🟡 差不多 |
| **起点** | 已经到 V2.3（联机/合作/自造模式全有） | **零起点**（没写过一行离线版代码） | 🔴 **他们好** |

**净结论**：我们在**数据/资源/反编译**上压倒性占优，在**工具链成熟度**和**迭代速度**上落后。⇒ **方案要尽量把工作放在「读判据 + 写 JSON」上，少放在「反复试错 hook」上**。这也是为什么 §5 把阶段 0 定成「先把请求/响应全录下来」，而不是「先写 hook」。

## 5. 分阶段施工（核心）

### 5.0 三档目标的边界（A 单机 / B 联机 / C 加新内容）

| 档 | 范围 | 对应阶段 | 工作量 | 卡点 | 建议 |
|---|---|---|---|---|---|
| **A 单机** | 进主菜单 + 打 AI + 收藏 + 组牌 | 0 → 1 → 2 → 3 → 4 | **6–10 个代理·会话** | ① Harmony 能否打原生方法（U1）② `LoginResult` / `UserInventory` 的 JSON 形状（U3/U4）③ `GetLoadedBundle` 的资产名映射（U7） | **做**。这是「有原版离线版」这件事的**最小完整形态** |
| **B 联机** | 两台机器 / 双开打一局 | 5 | 若自己重写一层：**≈ HH:L 的 856 行 JS + 4 个传输模块**的量 | 原版联机是 **Photon + PlayFab 匹配**，两条都死了；要重写 `BattleCommsManager` 的 `Send*` / 接收回调 | **不做**。我们复刻工程里 **P2P 联机已做完**，没有理由在离线版里重造一遍 |
| **C 加新内容** | 新模式 / 新卡 / 新战役 | 6 | HH:L 的「大叛乱」= **604 KB JS + 44 张自生成纹理** | 新内容一旦做进原版客户端，就**绑死在 1.35.0 的二进制**上，且和复刻工程**两套账** | **不做**。新内容做在复刻工程（`Unity/MyGame`）里 |

**版本不变量对三档的影响**：原版**永不更新** ⇒ A 档**不需要**做版本指纹、不需要做迁移、混淆名与裸地址**可以钉死在 1.35.0**；
但 B 档如果将来真做，**仍然要**有内容指纹（因为我们的离线版自己可能改卡表），那时再抄 HH:L 的 `sha256(脚本 + 卡表)`。

### 阶段 0 · 旁路记录（只读，不改行为）—— **必须先做，做完才知道后面怎么写**

**做什么**

1. 建**独立的离线版工作目录**：`d:/4/Offline/`（内部分 `mod/`（C# 源码）· `runtime/`（假服务端）· `profile/`（存档）· `logs/`）。
2. 建一个 **MelonLoader mod 骨架**（`WarpforgeOffline.dll`），只做三件事：
   - **`OnInitializeMelon` 里打印** `Il2Cpp.LoginManager` / `Il2Cpp.PlayerDataManager` / `Il2Cpp.AssetBundleManager` 能否解析；
   - **Harmony 打一个空 Postfix** 到 `LoginManager.TryLoginToPlayfab`（**只打日志、不改行为**），用来验证 §6-U1「Harmony 能不能打到原生入口」；
   - **`Application.logMessageReceived` 全量落盘**到 `d:/4/Offline/logs/unity.log`。
3. 在**客户端副本**上跑（⛔ 不动 `d:/2/unity_run_ref` 本体 —— 复制一份到 `d:/4/Offline/game/`）。
4. 跑一次「开 Steam → 正常启动 → 看到报错」，**记录**：
   - `LoginManager.currentState` 的完整时间线（每次 `OnLoginStateChanged` 打一行）；
   - `NetworkingPeer` / `UnityWebRequest` 层面的出站 URL（MelonLoader 里可以 Harmony 一个 Postfix 到 `PlayFab.PlayFabSettings.GetFullUrl`，**只打日志**）；
   - `AssetBundleManager.GetLoadedBundle` 的**每一次请求名**（Postfix 打日志，不改返回值）；
   - `AssetBundleManager.assetBundleCollection` 的实际内容（有多少条、名字长什么样）。

**验收判据**

- `logs/hooks_installed.tsv` 里 **§6-U1 那一行是 PASS**（Harmony Postfix 确实被调到，日志里能看到 `TryLoginToPlayfab called`）；
- `logs/unity.log` 里能读到**完整的 PlayFab 请求 URL**（至少 `Client/LoginWithSteam` 一条）；
- `logs/getloadedbundle.tsv` 里至少有一条真实请求名，且能看出它和本地 `.bundle` 文件名的对应关系；
- `logs/login_states.tsv` 里能看到状态从 `notStarted` 走到「失败」的**逐跳**（这决定阶段 1 的桩要打在哪一步）。

**回滚**：删 `d:/4/Offline/` 即可 —— 一个文件都没动到既有工程。

**风险**：本条唯一风险是**开 Steam + 起游戏**（会写 `LocalLow/Everguild/Warpforge/`）。**缓解**：先用阶段 1 的目录重定向（最简单的一步：改副本的 `app.info` 的 product 名），再启动。

**预估**：1 个执行代理 · 1 个会话（含编译 + 试跑）。

**这一阶段不做什么**：不写假服务端、不改任何行为、不 hook 返回值。

### 阶段 1 · 最小登录桩（**能进登录后的第一个界面**）

**做什么**

1. **`app.info` 改名**（只改**副本**）：`Everguild` / `Warpforge` → `Everguild` / `WarpforgeOffline`（product 改，company 保留 —— 这样 `persistentDataPath` 变成 `LocalLow\Everguild\WarpforgeOffline`，**与原版和我们复刻工程都不冲突**）。
2. **Steam 依赖摘除**（三选一，按难度递增）：
   - **1a 最省事**：不改代码，**要求用户开着 Steam**。阶段 0 已经证明这样能走到「连接服务器出错」，说明 Steam 这条通了。
   - **1b 推荐**：Harmony `SteamManager.Awake` → 改成 `Prefix` 返回 false（跳过整个初始化），并**同时 stub**：`SteamAPI.Init`→true、`SteamUser.GetAuthSessionTicket`→写一个固定 32 字节、`SteamUser.GetSteamID`→固定 id、`SteamUserStats.*`→0/false。
     ⚠️ 必读 §4.3-坑3（`OnEnable` 仍会注册单例，别把 `Instance` 查询变成每次新建 GameObject）。
   - **1c 反向**：`SteamManager.Awake` 全保留，只 stub `PlayerDataManager.GetSteamAuthTicket` → 返回常量串。**但 `SteamAPI.Init` 失败时后续 Steam 调用仍可能炸**，1c 只适合「有 Steam」的场景。
3. **起本地假服务端**（`d:/4/Offline/runtime/server.py`，纯标准库 `http.server`，⛔ 不引入第三方）：
   - 监听 `127.0.0.1:8765`；
   - 实现 `POST /Client/LoginWithSteam` → 返回一个**最小** `LoginResult` JSON；
   - 实现 `POST /Client/ExecuteCloudScript` → 按请求体里的 `FunctionName` 分发（阶段 1 只需要 `GetReadOnlyPublisherData` 与 `onUserConnected`）；
   - **每一个请求/响应都落盘**到 `logs/http/*.json`（这是阶段 2 的输入）。
4. **重定向 PlayFab base URL**：Harmony `Postfix` 到 `PlayFabSettings` 的静态构造/`get_staticSettings`，或在 `OnInitializeMelon` 里直接
   `PlayFabSettings.staticSettings.ProductionEnvironmentUrl = "http://127.0.0.1:8765/"`（**如果这个赋值在 IL2CPP 下生效** —— 阶段 1 第一个要验的点）。
5. **`ws2_32` 拦其余出站**（照抄 `probe.js:2662-2668` 的四个入口，**加回环放行**）。

**最小 `LoginResult` 要哪些字段（按 `PlayerDataManager__FinishLogin.c` 的读法反推）**

| LoginResult 偏移 | 被写进 PlayerDataManager 的 | 用途 |
|---|---|---|
| `+0x50` | `+0x328` | **PlayFabId** |
| `+0x28 → +0x10` | `+0x330` | EntityId |
| `+0x58` | `+0x338` | EntityToken |
| `+0x30` | **`+0x2a8`** | **`GetPlayerCombinedInfoResultPayload`** ← **最重要的一个** |
| `+0x48` | `+0x340` | `bool`（未定名，阶段 0 打日志确认） |
| `+0x30 → +0x28 → +0x70` | `+0x3e0` | 时间戳（Settings 用） |

`GetPlayerCombinedInfoResultPayload` 里**至少要**：`UserData`（`Dictionary<string, UserDataRecord>`，键 = 51 个 `PlayerDataKey` 的**字符串名**）、`UserInventory`（`List<ItemInstance>`，卡收藏）、`UserVirtualCurrency`、`TitleData`（30 个 `TitleDataKey`）、`PlayerStatistics`、`PlayerProfile`。

⚠️ **`UserData` 的键名到底是枚举名（`ProfileVersion`）还是数字（`"1"`）** —— 这是**必须实测**的（阶段 0 打日志 / 阶段 1 试两种）。

**验收判据**

- 游戏**不再弹「连接服务器出错」**；
- `LoginManager.currentState` 能走到 `processingLogin(65)` 或更后；
- `logs/http/` 里能看到**第二个请求**（`ExecuteCloudScript`），说明 `AsyncInitialization` 被触发了。

**回滚**：关掉 mod（移出 `Mods/`）+ 删 `profile/`。

**风险**：`LoginResult` 的 JSON 形状可能有客户端强校验（PlayFab SDK 会反序列化到 DTO，**未知字段会被忽略、缺字段会给默认值** ⇒ 风险低）。
**另一个风险**：`PlayFabSettings.staticSettings` 是 `readonly` 字段，但**属性可写**；如果 IL2CPP 层把 `PlayFabSharedSettings`（ScriptableObject）覆盖回来，要以「静态构造之后再写一次」为准。

**预估**：1–2 个执行代理 · 1–2 个会话。

### 阶段 2 · 进主菜单

**做什么**

1. 把 `GetPlayerCombinedInfoResultPayload` 的**每一个** key 填上（51 个 `PlayerDataKey` + 30 个 `TitleDataKey`）：
   - **能从本地解包数据填的**：`TitleData.ServerVersion`（给 `1.35.0`）、`TitleData.AddressablesConfig`、`TitleData.AssetBundlesDataPCWin`；
   - **必须自己造的**：`UserData.Decks` / `CurrentDeck` / `CosmeticData` / `TipsData` / `LevelData` / `PlayerSeason`…（原版这些在 PlayFab 上，本地从来没有过）。
2. **卡收藏**：`UserInventory` 里每条 `ItemInstance` 的 `ItemId` 要能让 `InventoryManager.Add(itemInstance)` 认出来。
   - **先验**：`InventoryManager.Add(ItemInstance)` 怎么把 `ItemId` 变成 `IIdentifiable`（`Assembly-CSharp/InventoryManager.cs:90`）—— 大概率是 `itemId == 卡的 uniqueId`（我们 `cards_engine.json` 里有 1,127 张的真 id）。
   - **兜底**：直接构造 `RawCardScript`（从本地卡定义）→ new `ItemInstance` → `inventoryManager.Add(...)`，**跳过 id 字符串解析**。
3. **`AssetBundlesDataPCWin` 从本地生成**：扫 `StreamingAssets/aa/StandaloneWindows64/*.bundle`，每条 `{bundleId: <文件名去 .bundle>, bundleVersion: 1, bundleSize: <字节数>, mandatoryBundle: true}`，外层 `{PCBundles: {bundlesList: [...], Version: 1}, ...}`。
   - 或者**更省事**：把 `CheckIfThereAreNewBundles` 恒返 false（Harmony Postfix），并把 `assetBundleCollection` 直接填好。
4. **挂 `AssetBundleManager.GetLoadedBundle`**（照抄 `probe.js:194-210`）：未命中时按名字去 `aa/StandaloneWindows64/<name>.bundle` 现 load，写回 `assetBundleLinks`，并返回。
   - ⚠️ 名字映射要按阶段 0 录下来的真实请求名做，**别猜**。
5. **`CheckNewVersion` 放行**：让 `TitleData.ServerVersion` 的 required version **≤ 1.35.0**（`PlayerDataManager__CheckUpdateRequired.c` 里 `Version.op_LessThan(当前, 需要)` 才判「需要更新」）。
6. **`onUserConnected` 返回**：`{...}` 五个字段（`+0x10`/`+0x18`/`+0x20`/`+0x28`/`+0x30`），**形状从阶段 0/1 的日志反推**（客户端会发一个 `payload`，我们在响应里按同样形状回）。

**验收判据**

- `LoginManager.currentState == finished(50)`；
- **主菜单出现**，且：玩家名显示、货币显示、卡组列表有卡组、`对战` 按钮可点；
- `logs/http/` 里 **没有第三个未知请求**（如果出现了，说明还有没覆盖的服务端调用 —— 这也是判据）；
- **不进战斗**（那是阶段 3）。

**回滚**：同上。

**风险**：
- `InventoryManager.DeserializeInventory` 对 `ItemId` 的格式有强依赖（**最高风险项**）；
- `ProcessNewLoginResult` 的 `+0x20` 字典会被 **merge 进 `UserData`**，如果形状错会静默覆盖（要打日志比对合并前后）；
- **`TitleData.AddressablesConfig` 的形状** —— `AddressablesConfig` 是 `ScriptableObject` + `IConfigData`，从 TitleData 的 JSON 反序列化，`Environment`/`Badges`/`remoteLabels` 三层。**形状必须试**（阶段 0 打日志看客户端请求了什么；如果客户端根本没请求它，说明它来自本地资产，那就更简单）。

**预估**：2–3 个执行代理 · 2–3 个会话（**主要时间在试 JSON 形状**）。

### 阶段 3 · AI 对战可用（**这是本方案真正的「成功」定义**）

**做什么**

1. 修 `GetLoadedBundle` 的剩余未命中（战场 bundle、卡 anim bundle、音效 bundle）—— 按阶段 2 的日志逐条补。
2. 打通 **练习局**（`PracticeOffline` 类型）：主菜单 → 对战 → 选练习 → 选卡组 → 进战场。
3. 验证原版 AI、结算、动画、音效**全部原生**（这是跑原版客户端白送的东西，不需要做）。
4. 查 `PlayerDataManager.SaveMatchWinnerInServer` / `onPracticeMatchFinished` 等**结算后写服务端**的调用 —— 这些会打到假服务端，需要在假服务端里**接住并落本地存档**（照 HH:L 的 `save_decks` 思路）。

**验收判据**

- 能**完整打一局 AI**（出牌 → 攻击 → 结算 → 回到主菜单）；
- 打完这一局，**重开游戏后进度还在**（存档闭环）；
- `logs/http/` 里每个请求都有对应的假响应，**没有一个 404/超时**。

**回滚**：同上。

**风险**：战斗里用到 `ObscuredInt` 的字段多（8 个文件），但**只读不写**的话没影响。
**主要风险**：`BattleCommsManager` 在单机局里是否也会走网络（Photon）；如果走，要在阶段 3 里 stub 掉。

**预估**：2–3 个执行代理 · 2–3 个会话。

### 阶段 4 · 收藏 / 组牌 / 详情窗

**做什么**

1. `InventoryManager` 里的收藏要**能筛、能搜、能显示**（这依赖 `UserInventory` 完整 + 卡的 `uniqueId` 对得上）。
2. 组牌保存：`PlayerDataManager.UpdateOnlineUserData` / `AddOrUpdatePlayerDeck` / `deletePlayerDeck` 这些调用全要接到假服务端 → 落 `profile/decks.json`（照 `probe.js:729-773` 的「置换成写本地文件」）。
3. 卡组编辑器、收藏窗、卡详情窗全部能开、能有内容。

**验收判据**：能建一个 30 张的合法卡组 → 存 → 重开 → 还在 → 拿它去打一局。

**预估**：1–2 个执行代理 · 1–2 个会话。

### 阶段 5 · 联机（**可选，且建议不做**）

**边界**：
- 原版的联机是 **Photon + PlayFab 匹配**，**关服后不可用**。
- HH:L 的做法是**自己重写一层**（`BattleCommsManager` 的 `Send*` 全换掉，动作结构体对拷）—— 那是 **856 行 JS + 4 个 Python 传输模块**的工作量。
- **我们有更便宜的路**：复刻工程里 **P2P 联机已经做完**（`CardPresentation/Net/`，铁律 §四 已记）。离线版的联机**没必要重造**。

**建议**：**阶段 5 不做**。要做也只做「同一台机器双开打一局」的自测（照 `probe.js:2648-2661` 改 Unity 互斥体名）。

**预估**：不做。

### 阶段 6 · 加新内容（**可选，且明确不建议**）

HH:L 自己写了 604 KB 的 JS「大叛乱」模式。**那是他们的产品形态**（他们只有离线版）。
**我们的产品形态是复刻工程**（`Unity/MyGame`）—— 新内容应该做在那边，**不是**做进原版客户端里。
**建议**：**不做**。

## 6. 关键未知清单（每条给「怎么查」的具体命令/工具）

| id | 未知 | 为什么重要 | 怎么查 | 判据 |
|---|---|---|---|---|
