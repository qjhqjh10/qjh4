## 0. 一句话结论

**原版没有「手牌施放者」这一层 —— 手牌卡和场上单位是同一个 `CardScript` 对象。我们的偏离是「拆成 `CardInstance` / `UnitState` 两个类型」，不是「缺了一个手牌施放者适配器」。**

落到两条账上，**推荐分开处置**：

| 账 | 裁定建议 | 理由（一句话） |
|---|---|---|
| `B141-HAND-CA100` | ✅ **不新增结构化执行器**；把该行从「Unsupported 缺口」改判成「**文本路已覆盖**」（零行为变化） | 全 1,351 张 SO 里手牌上下文 `ca 100` 只有 2 行；池内唯一那行（`Cult Propaganda`）**已经由 at-turn 文本路结算**。现在再写结构执行器 = **每回合双造一张**（证据 §4.3）。 |

## 1. 原版施放者模型（方法体级证据）

### 1.1 原版只有一个卡对象类型

| 断言 | 证据 |
|---|---|
| 原版**没有** `UnitState` 这个类型 | `ls D:/2/tools/decomp_full/ \| grep UnitState` = **0**；ILSpy 全目录 `ls \| grep -i unitstate` = **0** |
| 卡 = `CardScript : EntityScript : MonoBehaviour` | `cpp2il/out_cpp2il_dev_ilspy/CardScript.cs:22`（`public class CardScript : EntityScript`）· `EntityScript.cs:9`（`public class EntityScript : MonoBehaviour`） |

| 手牌卡就是 `CardScript`：造牌函数的返回类型 | `BattleManager.cs:39101` — `public unsafe CardScript AddNewCardToHand(RawCardScript createdCard, CardScript actingCard, bool isPlayer, Vector2 createAtPos, Vector2 moveToPos, int priority, CardEffect cardEffect = null, bool blockPlayerActions = false)`；体内 `battleCards.CreateCard(...)`，而 `BattleCardManager.cs:19` — `public unsafe CardScript CreateCard(RawCardScript rawCardData, Transform parent, bool isPlayerY, CardArmy mainArmy, bool armedTrap = false)` |

### 1.2 「施放者」在调用链上就是 `thisCard`（`CardScript`）

- `AbilityData` 的三个卡位全是 `CardScript`：`AbilityData.cs:5-7`（`public CardScript thisCard; public CardScript actingCard; public CardScript targetCard;`）。
- `CardAbility.CanTriggerAbility(AbilityTrigger trigger, BattleManager manager, **CardScript thisCard, CardScript actingCard, CardScript targetCard**, bool ignoreRandomTrigger = false)` —— `CardAbility.cs:30`。
- `AbilityLogic.GetTargets(BattleManager manager, TargetCriteria criteria, **CardScript thisCard, CardScript actingCard, CardScript targetCard**, bool checkMaxTargets = true)` —— `AbilityLogic.cs:723`。
- `AbilityLogic.PlayAbility(BattleManager manager, AbilityData abilityData, AbilityTrigger trigger)` —— `AbilityLogic.cs:451`。**全函数只用 `abilityData.thisCard` 的 `isPlayer`（+0x40）**，没有任何「必须在场」的前置闸。

### 1.3 「在不在手牌」只是一道闸，不是另一套对象

`AbilityContext.Hand = 10`（`AbilityContext.cs:5`）→ `CardAbility.IsRightContext` 的 Hand 支：

—— `cpp2il/out_cpp2il_dev_ilspy/CardAbility.cs:232-238`；`IsInHand()` 实现见 `CardScript.cs:20802`。

⇒ **「手牌卡能不能当施放者」的答案 = `IsInHand()` ∧ ability 的 `abilityContext == 10`**，别的没有。

### 1.4 手牌确实会收到同一套触发（不是只收表现层）

`BattleManagerSupport.BroadcastTurnEnd(BattleManager, bool)` 全文 74 行（`decomp_full/BattleManagerSupport__BroadcastTurnEnd.c`）：

| 行 | 动作 |
|---|---|
| `:17-43` | 先遍历棋盘卡（`list +0x470`），`CardScript.OnTurnEnd(card)` |
| `:44-52` | **`lVar4 = BattleManager.GetCardsInHandRef(param_1, IsPlayerTurn())`，逐张 `CardScript.OnTurnEnd(lVar3)`** ← 当前行动方**手牌** |
| `:53-65` | `GetCardsInHandRef(!IsPlayerTurn())`，逐张 `CardScript.OnTurnEnd(card, param_2)` ← 对手手牌 |

而 `CardScript.OnTurnEnd`：`CardScript.cs:16526` — `base.rawCardData__BackingField.OnTrigger(AbilityTrigger.TurnEnd, BattleMgr__BackingField, **this**, cardScript, cardScript2);`
⇒ 手牌卡把自己的 `CardScript` 当 `thisCard` 传进 `RawCardScript.OnTrigger → TriggerAbilities → PlayAbility`。

### 1.5 `checkIfCasterInPlay` 不是「必须在场」闸

`AbilityLogic.checkIfCasterInPlay`（`dump.cs` 的 `AbilityLogic` 字段 `+0x74`）在 `PlayAbility.c` 里**全部**是当实参传给 `Add*` 动作队列（`:558 :581 :652 :677 :859 :902 :938 :976 :1220 :1297`），**没有一处是 `PlayAbility` 自己的 early-return**。
⇒ 它是「动作入队后施放者还在不在」的**队列参数**，不是施放者模型的约束。

### 1.6 我们的偏离与既有解法

- 我们的三层模型写在 `Core/CardInstance.cs` 文件头（`CardDef` 模板 → `CardInstance` 手牌/牌库/弃牌堆 → `UnitState` 场上）。
- `Core/TriggerCarrier.cs` **就是**为这件事建的窄视图：文件头写明「原版只有一个 `CardScript`…我们拆成两个类型 ⇒ 派发核心被写成必须 `UnitState`」，并给出两个工厂：
  - `TriggerCarrier.From(UnitState u, int owner, int slot)`（`IsBoardPath = true`）
  - `TriggerCarrier.From(CardInstance inst, int owner)`（`IsBoardPath = false`；`Unit` 恒 `null`；`Slot = -1`）
- **现状（现读，订正该文件头「零调用点」那句）**：唯一生产调用点 = `EffectResolver.cs:19056`（`FireHandAbilityTrigger` 的文本正文取值），**没有**用于任何 `ca` 执行器。
- 所以「手牌施放者」这件事在我们这边的**正确形状已经有了**（`TriggerCarrier`），缺的是「执行器接受载体视图」这一层 —— 而这件事是否值得做，取决于具体 `ca` 是否真的可达（见 §4）。

### 4.2 为什么 `ca 100` 在**手牌**这一档尤其不值得写结构执行器

- 池内（`cards_engine.json` 1,142 张）手牌上下文 `ca 100` = **1 行**：`7c666a04…` **Cult Propaganda**，trigger 40（TurnEnd），ab0/lg0，`abilitySummon = {enemy:1, ids:["GSC6"]}`、`abilityTargets.ta = 0`。

- 而 `Cult Propaganda` 的效果**今天就是通的**：`ResolveAtTurn` 的手牌陷阱扫描 → `EffectText.IsHandTrap(c)`（`EffectResolver.cs:8932`）→ `EffectText.SplitAtTurn(c.Desc)`（`:8933`）→ `EffectText.Parse("create a Neophyte Initiate in your opponent's hand")` → `DoCreate`（`EffectResolver.cs:1140` 的 `{ "create", DoCreate }`；`DoCreate` 在 `:4169`，按 `Dest=enemyhand` 造到对手手牌）。解析链判据：`EffectText.cs:5660-5686`（`TryAtTurn` 的 doc 里点名这两张卡）。
- ⇒ **写了结构执行器 = 同一回合造两张**。

### 4.3 双发证据（施工前必须理解）

`ResolveAtTurn`（`EffectResolver.cs:8906` 起）在同一次调用里做三件事：

1. `:8926-8945` 扫**当前行动方手牌**，`IsHandTrap` 命中 ⇒ `handJobs.Add(...)`（文本 op）。
2. `:9031` / `:9112` **`BroadcastTurnEndHandHops(ctx)`**（`EffectResolver.cs:22196`）—— `B142_E24` 新接的 turn_end 手牌两跳。
3. 后者对每张手牌调 `FireHandAbilityTrigger(inst, "TurnEnd")`；`HandAbilityTriggerHasRows` 一旦把 `ca 100` 判成 `Owned` ⇒ 入队 ⇒ `DispatchHandAbilityRows` ⇒ 结构执行器。

两条作业**互不排斥**（`CardAbilityRowCoveredByTextLayer`（`CardAbilityDispatch_B116.cs:256`）只查 `card.TriggerOpsByNumber(trigger)`，而 `Cult Propaganda` 的 `CollectTriggerOps` 里**没有 `turnend` 键** —— `CollectTriggerOps`（`CardDef.cs:3722`）只从「带关键词前缀的句子」和 `keywords` 收，`At the end of your turn, …` 不是关键词前缀）。
⇒ B7 闸**抓不到**这一张 ⇒ **双发**。
