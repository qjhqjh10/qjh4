## 〇 · 一句话结论

**规模比预想的小得多**：全仓依赖 New Input System 的只有 **22 个文件 / 99 行代码**，
**没有** `InputAction` / `PlayerInput` / `ReadValue<>` / `.inputactions` 接线（= 没有资产层要重建），
而**原版那张 `InputManager.asset` 轴表我们已经有了**（30 轴逐名相同，只差一个 `m_UsePhysicalKeys`）。

⇒ **推荐路线 ①（整仓迁旧输入）**，代价可控、且**它同时也是 B132 `#102`（原版 `EverguildInput : StandaloneInputModule`）的唯一实现路径**。
**唯一真风险**（不是成本，是正确性）= 自动验收的**输入注入**那一条（`BattleAutoDrive`）没有旧输入等价物，必须换seam。

## 三 · 把 `activeInputHandler` 改成 0 的**确切后果**

`ProjectSettings/ProjectSettings.asset:936` 现读 `activeInputHandler: 1`；原版 `ExportedProject/…/ProjectSettings.asset:679` = `0`。

**编译：照样过。** Input System 是**包**（`Packages/manifest.json:7` `com.unity.inputsystem: 1.20.0`），
它的程序集**不因这个设置而被剔除** —— `ENABLE_INPUT_SYSTEM` 宏会消失，但**我们源码里 0 处用它**（§二），
`Mouse.current` / `InputSystemUIInputModule` 这些类型**仍然编译得到** ⇒ **`typecheck.sh` 会报 0/0，完全看不见这个问题**。

**运行时：静默失效。** 判据 = 包自带的原文（`Library/PackageCache/com.unity.inputsystem@7a4e1a2a8194/InputSystem/Editor/Debugger/InputDebuggerWindow.cs:197-203`）：

> "Platform backends for the new input system are not enabled.
> **No devices and input from hardware will come through in the new input system APIs.**"

⇒ 具体到我们的代码：

| 后果 | 依据 |
|---|---|
| `Mouse.current` / `Keyboard.current` / `Touchscreen.current` **全是 `null`** | 上面那句 |
| `InputSystemUIInputModule` **一个事件都收不到** ⇒ uGUI 点不了 | 它的事件从 `InputSystem` 来 |
| `BattleAutoDrive.cs:501` 的 `InputSystem.QueueStateEvent(Mouse.current, st)` **参数是 null ⇒ 抛/无效** | 同上 |
| **编辑器**里会有一次弹窗 "Input System native platform backend not enabled"（`InputSystemEditorInitializer.cs:443-470`，⚠️ `Application.isBatchMode` 时**不弹**） | 批处理/自检**不会**提醒 |
| **player 包里完全静默** | 无任何提示 |

⇒ 这是最坏的失败形态：**类型检查绿、自检可能也绿（自检多数走直接调用而非真实指针），但人一上手点不动**。
**所以必须整批一次做完 + 真机点击验收**，⛔ 不能「先翻设置再说」。

## 四 · 两条路线

### 路线 ① —— 整仓迁旧输入（**推荐**）

| 项 | 量 | 说明 |
|---|---|---|
| 轮询转换 | **99 行 / 22 文件** | 机械替换（§1·2 的对应表） |
| EventSystem 模块 | **2 处**（`BattleEventSystem.cs` 三条路由 + `Editor/BattleScene.cs` 1 条断言） | `InputSystemUIInputModule` → `StandaloneInputModule`。**这正好就是 B132 `#102` 的原版形状**（原版 EventSystem GO 上挂 `EverguildInput : StandaloneInputModule`）⇒ 两条任务合成一条，不是额外成本 |
| 轴表 | **0** | ✅ `ProjectSettings/InputManager.asset` 现读与原件**逐轴相同**（30 轴同名同序，归一化后**只差 `m_UsePhysicalKeys: 1` 一行**）⇒ 补那一行即可 |
| 动作资产 | **0** | 无人用 `.inputactions`；模板件可删 |
| `activeInputHandler` | 1 行 | 改 0 |
| 注入 seam | **1 处，唯一真难点** | `BattleAutoDrive.cs:501` `QueueStateEvent(Mouse.current, st)` —— 旧输入**没有公开的注入口**。三条候选：① 自动驱动改为**直接调 `CardInteraction` 的内部入口**（绕过指针，覆盖略降）；② 保留一条「用 `Touchscreen`/`Mouse` 设备模拟」的编辑器期路径（但后端关了就没有设备，不可行）；③ 用 `Input.SimulateMouseWithTouches`（只覆盖触摸语义，不覆盖精确坐标）。**① 最现实**，代价 = 拖拽那一格自动覆盖面下降，需在 `真Play待验清单` 里补一条真人拖拽 |
| **总风险** | 中 | 输入是全用户可见层；必须「全量改完 + `typecheck` + 真机点一遍（`wf_click.py`）」一次性过，⛔ 不半途提交 |

### 路线 ② —— 保持 New Input System，只做「行为等价」

| 项 | 量 | 说明 |
|---|---|---|
| 代码 | **0** | 什么都不用改 |
| 代价 | —— | ① **`#102` 永远做不了**（`StandaloneInputModule` 在新后端下收不到事件，B132 明确说「挂 `StandaloneInputModule` = 一个事件都收不到且不报错」）；② `activeInputHandler` 与 #102 会**每轮审计都被重新翻出来**；③ 与铁律 11「与原版不符的都要做、只有先后」冲突 —— 这一条**不是服务器相关**，不在 `18·0` 的自设计豁免里 |

### 推荐

**路线 ①**。理由三条，按权重：

1. **它把 `#102` 一起解决** —— 那不是「顺便」，是**同一次改动的自然产物**：复刻原版模块类型 ⇒ 必须是旧后端。
2. **成本已经被前置条件压到很小**：轴表已有、动作资产为零、双路条件编译为零、只有 99 行轮询。
3. **路线 ② 省不下多少、却留下一个永久审计噪点**，且永远挡着 #102。

**建议的落地形态**（降低一次性风险）：

* 分两拍：**第一拍**把 `activeInputHandler` 设成 **`2`（Both）** + 代码全部改用旧输入 ⇒ 新后端仍活着，任何漏网的一处不会立刻死；
  **第二拍**（真机验收通过后）再把 `2` → `0`，并把 `InputSystemUIInputModule` 换 `StandaloneInputModule`。
  ⚠️ `2` 是**过渡态**，⛔ 不是终态（原版是 `0`），必须写进账里并在同一任务内收口。
* 验收：`typecheck` + **真机 `wf_click.py` 点一遍**（拖卡/出牌/点按钮/滚轮/键盘）+ `-wfdrive` 跑一局。
* 规模建议：**一个写手独占**（输入散在 22 个文件、且 `BattleDriver.cs` / `PointerLayer.cs` / `CardInteraction.cs` 都是热点），
  按「文件所有权」切 3 份反而会撞 —— 这条不适合并行。

## 五 · 顺手发现（都不是本任务范围，但立项前必须知道）

1. **`ProjectSettings/InputManager.asset` 已经基本等于原版** —— 归一化（去空白 + 去 `serializedVersion` 行序差异）后
   **只差一行**：原版末尾有 `m_UsePhysicalKeys: 1`，我们没有。
   ⇒ 迁移时**补这一行即可**，⛔ 不需要重建轴表。`m_UsePhysicalKeys: 1` = `Input.GetKey` 走**物理键位**（不受键盘布局影响），
   这正是「原版行为」，漏了会让非 QWERTY 布局的键位跟原版不一致。
2. **`Assets/InputSystem_Actions.inputactions` 全仓无引用**（grep 只命中它自己）—— Unity 新建工程带的模板件，
   迁移后可以删（⚠️ 删之前确认 `ProjectSettings` 里没有 `m_ActiveInputHandler` 之外的引用）。
3. **`CampaignScriptRunner.cs:1099` 是当前的潜伏运行时异常**：在 `activeInputHandler = 1`（New-only）下访问
   `UnityEngine.Input` 会抛 `InvalidOperationException`（Unity 的已知行为）。该路径一旦被走到就崩。
   ⇒ **无论走哪条路线，这一处都该现在就修**（改成 `Mouse.current.position.ReadValue()`，与全仓口径一致）。
4. **`Touchscreen` → `Input.GetTouch` 这一步是「更还原原版」**：反编译侧原版就是
   `Application.isMobilePlatform && Input.GetTouch(0)`（`TapParticleController__Update.c`、`CombatCameraZoom` 注释里都引过原文）。
   我们现在是「照原版写出来但用新 API」⇒ 迁移后与判据**逐字一致**。
5. **`Editor/BattleScene.cs:43244-43247` 那条断言方向要反过来**：它现在断「输入模块**必须**是 `InputSystemUIInputModule`、
   **没有** `StandaloneInputModule`」—— 迁移后要断「**必须**是 `StandaloneInputModule`（原版 `EverguildInput` 的基类）、没有新模块」。
   ⇒ 同一处断言，改一行期望值。
6. **`BattleAutoDrive` 是验证路径不是产品路径**（`-wfdrive` / `-wfhuman`，由 `Core/PlayerBoot.cs:155` 挂上）
   ⇒ §四-① 里那个「注入 seam」的风险**不影响玩家**，只影响自动验收覆盖面。
