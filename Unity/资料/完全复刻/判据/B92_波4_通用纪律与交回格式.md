### 3·3·a 🔴 **「ILSpy 有体」≠「能逐句对过」（2026-10-28 N2 实测，新增口径）**

- **实参全是 `0` / `default` / `false`**（ILSpy 把常量丢了，照抄会把有行为的调用做成空转）；
- 体里只剩一句转调、而形参一个都没用上（`cpp2il` 会静默丢字段赋值）。

**处理**：① 先看 `d:/2/tools/decomp_full/*.c`；② 再看 `out_il2csharp`（它的异步体与常量往往更全）；
③ 泛型类看 `d:/4/_tmp_view/decomp_b91/` 与 `d:/2/tools/decomp_generic_trial/out/`；
④ 都没有 ⇒ **判据未闭合，保持 B**，并在 `差异` 列写「ILSpy 体降级（原样贴出标记）+ 还差哪一份产物」。
⚠️ 同类已知坑：`MissionEvent` 的 6 条就是「账里写『真体实读』、实际是降级体」的错记（N2 已就地订正）。

### 3·3·b 🔴 **同一个原版方法出现两行账时：取「判据更硬」的那行，⛔ 不是「有 A 就取 A」（2026-10-28 调度台裁定）**

## 四、账补丁格式（`账/_parts/B92_<代号>.tsv`）

**列结构 = 账主表的前 11 列，逐字照抄表头**：

```
域	原版类	方法	判据出处	判据要点	状态	我们的落点	差异	等级	轮次	备注
```

- 编码 **UTF-8 with BOM**，行尾 **CRLF**，写文件用 `io.open(p,'wb')`。
- 🔴 **读写一律裸 `split("\t")`**，⛔ 别用 `csv` 模块（会把 `Assets\…` 的反斜杠吃掉）。
- 🔴 **`方法` 列必须是完整签名、带 `(...)`**（裸名会被合并工具拒）。
- 🔴 **写补丁前必须按 `(原版类, 方法)` 扫全 21 张主表，确认这一行到底有没有既有行**（2026-10-28 `B92_B6` 实测踩坑：它只查了 `战斗逻辑驱动.tsv`，漏了 `菜单_外壳.tsv:25` 的同类行 ⇒ 差点**新增一行**、把已有 A 行留在原地，同一个方法两行账）。⚠️ **主表的 `方法` 字符串可能与 ILSpy 签名不同**（少了 `= 0` 默认值之类）⇒ **必须用主表那一行自己的字符串做键**，⛔ 别自己重写。
- **只写你动过状态/落点/差异的那些行**；没动的行不要抄进来（抄了会盖掉别人的新判）。
- `我们的落点` 写 **`文件.方法`** 或 `文件:行号（方法名）`；⚠️ 行号会漂，**首选写方法名**。
- 🔴 **一个落点列只写一个 `文件:行`**（2026-10-28 `B92_N4c` 实测：`check_ledger_points` **不评估括号里/第二个 `文件:行`** ⇒ 写错了闸照样绿，只能靠回读代码发现）。第二处落点放进「等价实现 = …」的散文里、**不带行号**。
- 状态列只写 `A` / `B` / `C` / `D` 单字母。

## 六、这个项目最容易踩的 10 个坑（都真实发生过）

1. **ILSpy 会把实参常量反编译成 `default`** —— 看到「一整排实参全是 `default`/`false`/`null`」一律回 `decomp_full/*.c` 复核。
2. **ILSpy 会丢掉异步状态机体 / `= true` 的写点** —— 判「0 调用 / 死格」必须三源合判（`.c` + `out_il2csharp` + `assets_full` 字符串引用）。
3. **`decomp_full` 的文件名可能与内容不符** —— 拿一份 `.c` 当证据前，先看它首行的函数名是不是它自己；首行是 `FUN_` 也可能只是名字含 `", "`，**先读体再下结论**。
4. **ILSpy 把私有 setter 反编译成 `obj = value`，字段名丢了** ⇒ ⛔ 别用「搜不到赋值点」证明「没人写」。
5. **`RVA 0x4B33B0`** = 全局共享空方法桩（机器码 `ret 0`）⇒ 比读 `.c` 更快判「原版这方法是空的」。
6. **新增成员一律追加到类尾**（或确认下游没有账的 `文件:行号` 落点）—— 插在中间会让整文件行号下移，落点闸立刻报漂移。
7. **改文件前先看行尾**（`git show HEAD:<路径> | file -b -`）；⛔ 别用 `sed -i`（会整篇翻 LF）。
8. **`io.open(p,'wb').write(<表达式>)` 会先截断再求值** —— 先把内容算进变量再 write。
9. **账 `.tsv` 一律裸 `split("\t")`**；⛔ `csv` 模块 + `escapechar` 都会污染真反斜杠路径。
10. **同一原版方法可能在两张账里各有一行**（主题表 + `泛型与启动链_补读`，签名写法不同导致合并不去重）
    ⇒ **当一条做，两行都更新状态**，别做两遍。
10·0 🔴🔴 **「扫 `.text` 得 0 命中 ⇒ 没人调用」是错的 —— 48 MB 的游戏代码在 `il2cpp` 段，不在 `.text`**（2026-10-28 `B8` 实测）：`GameAssembly.dll` 的 **`.text` 只有 4.9 MB（引擎侧）**；**`il2cpp` 段 48 MB 才是游戏代码**。B8 自写真 xref（扫 il2cpp 段所有 `E8 rel32`，目标 == 方法 VA）一次就找到了 `warlordStartSizeFactor` 的**唯一消费者**（`CardScript.<HeroLandIntoField>d__318.MoveNext` 的 `movss xmm2,[rax+0x30]`）—— 而它**第一版只扫 `.text` 得 0 命中，差点误判「没人调用」**。
  ⇒ **凡「E8 计数 = 0」的结论都要先问一句：扫的是哪个段？**
10·a 🔑 **`guard 检测法`（2026-10-28 `B10` 实测，对「0 调用点怪案」基本一击必中）**：每个方法有私有的 C++ 静态初始化 guard `if (DAT_xxxxxxxx == '\0') {…; DAT_xxxxxxxx = '\x01';}`。**在 `decomp_full` 全树建一张 `DAT_令牌 → 文件` 索引**（30,295 个令牌，一次扫 82 MB），**某方法的 guard 出现在别的 `.c` 里 ⇒ 那个 `.c` 就是内联点**。⚠️ **必须排掉共享 class-init guard**（阈值：该 guard 出现在 >20 个文件即判共享）。
  🔴 **普查的四个计数（E8/lea/dec/il）看不见五类入口**：① C++ 内联（无 call 指令）② **方法组委托** `Callback = OnX;`（不带括号）③ 虚调用/override（callvirt 间接）④ **按字符串名起协程** `StartCoroutine("X")` ⑤ Unity 魔法方法。
10·b 🔴 **`B88_死代码普查.tsv` 的 `il=N` 列基本是撞名噪声，⛔ 不能当「有人引用」的证据**（2026-10-28 `B11` 实测 90 条）：`.Update(` / `.Initialize(` / `.Refresh(` 在 ILSpy 里到处出现。**改用四路复判**：① 类声明（MonoBehaviour / override / 接口）② `decomp_full` 里的**内联展开指纹** ③ 委托 / 字符串注册点 ④ **AssetRipper 全库组件附着**（class → `.cs.meta` guid → prefab/scene 引用）。
  ⚠️ 同批实测：`BattleManager.ResolveAction` 是「符号层 0 调用」的**高频藏身处**（累计 `ResolveJamUnit` / `ResolveTriggerSacrifice` / `ResolveBloodThirstAnim`）⇒ **判死代码先搜它**。
  ⚠️ 「0 附着 + 无 MonoScript 的第三方库类」（如 Unity UI Extensions 的 `Countdown`）要与业务码**分开判**。
11. 🔴 **`decomp_full` 跨类同名方法也会撞**（2026-10-28 `N8` 实测）：`:441` `MissionChallenge.GetLocalizedDescription` 被认成 `MissionChallengeProgress__GetLocalizedDescription.c`（42 语句 / 3 分支），而它自己的 `.c` **只有四条语句** ⇒ **认体前先看首行函数名的「类名段」，不只是方法名**。
11·b 🔴 **`decomp_full` 的同名重载会互相覆盖**（2026-10-28 N1 实测）：`LiveOpsManager__GetEvent.c` **只有 1 个形参**
    ⇒ 它只是 `GetEvent(string)` 的重载，**⛔ 不能拿它当 `GetEvent(Type,string)` 的判据**。
    判法 = **比 `.c` 的形参个数**（同名文件只留了一份体）。
12. 🔴 **判「落点指向哪个方法」不能「往回找最近的方法声明」**（2026-10-28 `N7` 实测）：遇到**单行体**（`void Open() { Build(); }`）和**属性 getter** 会**越过它、指到上一个方法** ⇒ 实测 40+ 条 `FastModeBaseEvent`/`LiveOpsEvent`/`PlayEvent` 的落点会全指错（指到 `IsActive` / `OpenWindow` / `ChangeState`）。**必须先判「那一行本身是不是声明」**。
13. 🔴 **「原版类.方法」列常写【外层类】，真身是嵌套类型**（`N7` 实测 7 例：`StateOption` · `GameObjectElementsStateDefinition` · `EventProgressBarScoreObject` · `ChatMessageRow` · `RewardContainerLogic` · `CardSell` · `DraftRunRepair`）⇒ **机检按外层类名做子串匹配会假红**；应判「落点那一行 / 它最近的**祖先声明名**」。
14. 🔴 **`ImageQuad` 没有 `fillAmount` —— uv 裁剪 ≠ uGUI `Image.fillAmount`，⛔ 不要建通用替代**（2026-10-28 `N5` 实测）：原版进度条是 **`Image.Type = Sliced`**（`Core/CostCurveDrawer.cs:163` 记「端帽不缩放、中段拉伸」），用 uv 裁剪会**把端帽一起压扁**。底层已有 `ImageQuad.SetUvRect(Rect)`（`Battle/ImageQuad.cs:534`）。**分工**：非九宫简单图才可用 uv 裁剪；**九宫进度条必须走 `MenuDraw.Nine` 的中段拉伸**。将来要收口，收的是「按九宫中段拉伸实现 fillAmount」那一层。
15. 🔴 **判 D 前先找现成的「档位清单」**：`判据/服务器与账户_不复刻清单_第2轮.md:104` 已把 `PlayerDataManager` 219 个方法逐个分档 ⇒ 比现场读 `.c` 快、也不会误伤。⚠️ **反过来，同一份清单里「⛔ 不许判 D」那一半更危险** —— 三条 save/load 若没人钉住，很容易被后来的代理当成「服务器存档」一键判 D，**把现有本地存档链整条删掉**。
16. 🔴 **「往类尾追加」≠「零漂」——正解是 `partial` + 文件尾追加**（N1 / N4 同一天各自独立验证）：
    往 `LiveOpsHandler.cs` 类体插 19 行 ⇒ **9 条账漂移 + 1 失败**；`SettingsWindow.cs` 也是同类（后面还有 4 处落点）。
    正确做法 = **类声明那一行就地加 `partial`**（同一行、零行数变化），新成员放进**文件末尾的第二个 partial 块** ⇒ 账一个字不用改。
    ⚠️ 前提：**下一个类有没有账行**要现查，不能想当然。
