## 2. 🔴 顺序与原版相反（1 处，已标注）

| 项 | 内容 |
|---|---|
| 落点 | `Shell/DailyRewardPopup.cs` 的 **`ESCPressed()` 覆写**（`:292-300` doc 自陈） |
| 现状 | **先关窗、再收**（先把基类 `ESCPressed()` 的关窗那一跳走完，才补 `DailyRewardAutoCollect()`） |
| 原版 | **收完再关**：`LiveOp.TryCollect(action)` 的续作才是 `base.Close()` |
| 为什么不照原版 | 两条生产路径共用 `Close()` 这个**程序性口**，把「收」挂进 `Close()` 会连 `CloseAllWindows()` 一起收（文件里那一整段理由） |
| 可观测后果（源码自陈） | 差异只在「那扇领奖窗**在底窗回位之后**才弹」这一拍；终局（窗关掉 + 收进 `Wallet` + 领奖窗在最上面）逐条相同 |
| 判定 | 🔴 但**已被如实标注**（铁律 3/11 口径：是已知偏离，不是漏做）⇒ **要不要改成原版次序，请调度台裁定**（改法会把「程序性关窗也发奖」引回来，需要另加一个「只关不收」的口） |

## 4. 边界（⛔ 别把「没报」当成「全对」）

1. **成就领取**：`Shell/AchievementsMenu.cs` 与 `Shell/MissionInfoDisplays.cs` 里**没有找到领取的执行口**（只有 `CanCollect` 这个显示位 + `CanCollect` 的判据）。
   执行口可能在 `Shell/MissionEvent.cs`（`UpdateSaveGame`）/ `AchievementTally` 那一族，**本单没打开** ⇒ ❓ 判不了（要补的话：搜 `Claim(` 在 `MissionEvent` 全链）。
2. **只扫了 6 条链**：商店购买 / 开包 / 成就 / 每日 / 战役 / 收件箱 + 快模式领取。**其余**（锻造厂领奖 `ForgeTab` → `ForgeRewardItemContainer.ClickClaim`、排行榜奖励、活动奖励窗 `RewardWindow`
   `ShowCollected`、排位奖励 `RankedRewardEventWindow`、战斗结算 `EndPanel` 的 `Continue`）**没有逐个打开核** ⇒ 它们里若有「关窗紧邻发奖」的一段，本单没覆盖。
3. `HidePopUp` 的生产调用点在全仓只有 **1 处真生产**（`Deck/DeckRuntime.cs:5935` —— 卡组编辑的离开确认弹窗，**与发奖无关**）⇒ 说明本仓绝大多数窗走的是 `Close()`（`GameWindow`）而不是 `HidePopUp`，
   所以本单把「关窗」按**语义**（`Close()` / `HidePopUp()` / `_popupMgr.HidePopUp()`）一起算，而不是只搜 `HidePopUp`。

## 5. 建议

1. **不需要动代码**：唯一 🔴（每日奖励 ESC）是**已标注的设计取舍**，且终局一致 —— 改成原版次序要引进「程序性关窗也发奖」这个更糟的口子；建议**保持现状 + 在账里写明**而不是改。
2. 若将来要收口，统一口径应是：**「发奖」动作只挂在「用户主动领取」那一条路上，`Close()` 永远纯关**（这正是 `DailyRewardPopup` 现在的形状）—— 与 `FastModeCollectPopup` 的「先关后发」**不矛盾**：
   那里关的是**模态等待窗**，这里关的是**领奖窗本身**，两者语义不同（模态 = 进度提示、发奖前必须收；领奖窗 = 业务窗，收完再关）。
3. 补扫建议：`ForgeTab` / `RankedRewardEventWindow` / `RewardWindow` / `EndPanel` 四条（本单未覆盖）。
