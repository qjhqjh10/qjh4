# B93_Q8 · 开包（BoosterPack）过滤判定 + 施工单

> 受托问题：`Shell/BoosterPackOpenWindow.cs` 的 `RollPack`（现读 `:1220-1257`）**不筛任何卡**，
> 池内 `showInCollectionOptions=0` 的 **124 张**（以及另外一批）会不会被开包开出？原版到底按哪些字段筛？
>
> **结论先说**：会开出来，而且比账上记的更严重（现读 **168 张**）。但**判据不是 `show`/`inv`** ——
> 原版的判别字段是 **`cantBeRandomlyCreated`**，而它的"卡池"不是运行时算的，是一张**本地就有的 drop table 白名单**。
> 白名单逐张核过：**== 阵营卡池 − `cantBeRandomlyCreated==1`**。

## 判定（原版筛哪些字段 / 我们漏了哪几个）

### 1. 原版开包**没有运行期字段判断** —— 客户端只负责展示

- 开包窗的入口只有一处：`ContainerService` 拿到服务端回的 `RewardInfo` 列表 → `OfType<RawCardScript>()` → 交给
  `BoosterPackOpenWindow.Initialize(cardsToOpen, prefab)`（`out_cpp2il_dev_ilspy/ContainerService.cs:369`、`:871`、`:975`）。
  **进来的 `List<RawCardScript>` 就是最终结果**，窗口只做 `ListExtensions.Shuffle` + 逐张 `CardInBoosterPack.Initialize`
  （`decomp_full/BoosterPackOpenWindow__Initialize.c:63` / `:116` / `:120`）。
- 真正"摇"的落点在服务端：`DropTableContainer.Open` → `PlayfabWrapper.UnlockContainerV2`
  （`out_cpp2il_dev_ilspy/DropTableContainer.cs:183`；`decomp_full/DropTableContainer__Open.c:26`）。
  ⇒ **原版客户端里不存在"开包过滤"这段代码**，所以我们原来那条"原版走服务端 drop table ⇒ 判不了"的记账只能算半对。

### 2. 但 drop table **本地就有**（这条推翻了旧记账）

`assets_full` 里有完整的掉落表链（**34 份 `DT *` + 11 个 Booster 容器**，全部可读）：

| 层 | 资产（绝对路径） | 内容 |
|---|---|---|
| 容器 | `D:/2/新解包资源/assets_full/bundle_menus_assets_all/MonoBehaviour/Booster Pack Ultramarines.json` | `dropTableItems` **5 条**：`[DT Ultramarines All R2+, DT Ultramarines All ×4]`；`expansion=5`、`army=10`；**没有** `dropTableItemsWeight` ⇒ 5 条全部各授 1 件 |
| 中间表 | 同目录 `DT Ultramarines All.json` | `dropTableItems` = `[R1,R2,R3,R4]`，`dropTableItemsWeight = [2600, 200, 97, 4]` |
| 中间表 | 同目录 `DT Ultramarines All R2+.json` | `dropTableItems` = `[R2,R3,R4]`，`dropTableItemsWeight = [1500, 110, 1]` |
| **叶子表** | `D:/2/新解包资源/assets_full/bundle_cosmeticsso_assets_all/MonoBehaviour/DT Ultramarines R1..R4.json` | **`obtainableItems` = 具体卡 id 清单**（R1 38 张 / R2 33 / R3 23 / R4 18），`obtainableItemsWeight` **全 10000（等权）** |

另有 `bundle_duplicateassetisolationso_assets_all`（`DT Ultramarines R3/R4` 重复件）与
`bundle_cosmeticsso_assets_all` 里 **4 个阵营**（Ultramarines / Goff / EmperorsChildren / SpaceWolves）共
`R1..R4` + `All` + `All R2+` + `* Expansion Only`；容器侧共 11 个（含 `Booster Pack Legendary *` 与 `* Expansion` 变体）。

### 3. 白名单 == 阵营卡池 − `cantBeRandomlyCreated==1`（**逐张相等，两路互证**）

核法（只读，可复跑）：把 34 份 `DT *` 的 `obtainableItems[].targetId` 全取出来，与
`Unity/MyGame/Assets/RuleEngine/Resources/cards_engine.json` 的卡表逐张对。

| 核的内容 | 结果 |
|---|---|
| 白名单里去重后的卡 id 总数 | **329**，全部能在我们卡表里找到（缺 id = **0**） |
| 这 329 条的 `showInCollectionOptions` | **全部 = 5 (Show)**（0 条 `Hide`） |
| 这 329 条的 `inventoryOptions` | **全部 = 0 (InInventory)**（0 条 5 / 10） |
| 这 329 条的 `cantBeRandomlyCreated` | **全部 = 0**（0 条 = 1） |
| 每个阵营：卡池里**任何一张 DT 表都没出现过**的卡 | Ultramarines **22** / Goff **18** / EmperorsChildren **12** / SpaceWolves **10** |
| 上一条那批卡的 `cantBeRandomlyCreated` | **全是 1**（22/22 · 18/18 · 12/12 · 10/10） |
| 反向：按 `!cantBeRandomlyCreated` 从卡池筛出来的集合，与白名单并集比 | 4 个阵营 **计数完全相等**（112 / 101 / 58 / 58） |

⇒ **判据：原版卡包里能出现的卡 = 该阵营卡池里 `cantBeRandomlyCreated == 0` 的那批。**

### 4. 为什么判据是 `cantBeRandomlyCreated`、**不是** `show` / `inv`

- `show` / `inv` 只能"顺带挡住"一批：`show=0` 的 124 张**恰好全部** `inv=10` 且 `cbrc=1`（嵌套关系成立）。
- 但池里有 **44 张 `show=5` 却 `cbrc=1`** 的卡：**39 张 `defence`（战场环境卡，`inv=5`）** + **5 张 DarkAngels 的 `special` 战术卡（`inv=10`、`show=5`）**。
  **只按 `show`/`inv` 筛会漏掉这 39 张环境卡**（它们 `show=5`，但 4 个阵营的白名单里**一张都没有**）。
- 反过来 `cantBeRandomlyCreated` 是**原版自己的字段**，而且原版**唯一的运行期读取点**（全量反编译只命中 `AbilityLogic`）
  就是"随机生成一张卡"的池子：`!rawCard.cantBeRandomlyCreated ∧ !rawCard.IsHidden()`
  （`out_cpp2il_dev_ilspy/AbilityLogic.cs:786` 与 `:1439`，两处同形）。
- 同族的**包类随机池**先例（轮抽卡包）也是同一套口径：`DraftEventBase` 把卡池逐张筛成
  `inv != NotInInventory ∧ !IsHidden() ∧ !IsAlternateArt()`
  （`out_cpp2il_dev_ilspy/Everguild.LiveOps/DraftEventBase.cs:3358` / `:3366` / `:3374`）—— 注意它用的是 **`inv != 10`**，
  与"白名单 == cbrc=0"在 124 张 `show=0` 上**同解**，但它**不会**挡住那 39 张环境卡（`inv=5`）。
  ⇒ 对卡包这种"整包产出"的池，**`cantBeRandomlyCreated` 是更严、且与原版白名单逐张吻合的那一条**。

### 5. 我们漏了什么

`RollPack` 现在**一道闸都没有**（`:1223` 只按阵营过滤，`CardDatabase.OfFaction` 只排除 `enchantment`，
`Unity/MyGame/Assets/RuleEngine/Data/CardDatabase.cs:3227-3233`），于是：

1. 池内 **168 张 `cantBeRandomlyCreated=1`** 全部可被开出（含 124 张 `show=0`、39 张环境卡、5 张 DA special）；
2. 概率模型也不是原版的（原版是"先按权重抽稀有度档，再在档内等权抽卡"，我们是"直接等权抽卡 + 1 张 rare+ 等权"）；
3. 同一包内原版**是否允许重复卡**无判据（我们是**去重**的，🔶 自设计）。

### B（P1 · 概率模型对齐原版 · 同一方法、判据齐全、建议一起做）

现读 `RollPack` 是"1 张 rare+ 等权 + 4 张全池等权"，原版是**两级权重**：

| 槽 | 取自 | 权重 | 折成概率 |
|---|---|---|---|
| 第 1 张 | `DT <Army> All R2+` | `[1500(R2), 110(R3), 1(R4)]` | rare 93.11% / epic 6.83% / legendary **0.062%** |
| 第 2~5 张 | `DT <Army> All` | `[2600(R1), 200(R2), 97(R3), 4(R4)]` | common 89.62% / rare 6.894% / epic 3.344% / legendary 0.138% |

- 4 个阵营的这两组权重**完全一致**（`All` 恒 `[2600,200,97,4]`，`All R2+` 恒 `[1500,110,1]`）⇒ **与阵营无关，可以写死**。
- 档内等权（`obtainableItemsWeight` 全 `10000`）⇒ 实现为"按权重抽稀有度档 → 在该档的 `!cbrc` 卡里等权抽一张"。
- 由此 `P(整包含传奇) ≈ 0.612%`（可作断言用的量级检查）。
- ⚠️ 同一包内是否允许重复卡**无判据**（原版 5 个槽是 5 次独立抽取）⇒ 维持现状"去重"时必须留
  `🔶 自己设计（非原版）` 标记，或在账里记成"判据未定"。

## 没查清的部分

1. **同一包内能否重复**：原版 5 个槽是 5 次独立抽表，`UnlockContainerV2` 的服务端实现本地没有 ⇒ **判据为空**。
   我们现在的"去重"是自设计（需打 `🔶 自己设计`）。
2. **9 个没有本地 DT 表的阵营**（AstraMilitarum / BlackLegion / DarkAngels / Genestealers / SaimHann / Sautekh /
   Sororitas / TauEmpire / Leviathan）：只按 4 个阵营的规律**外推**（4/4 逐张相等）。这 9 族当前**没有商品在售**，
   但真机若上架、或将来做"战役奖励 drop table"，需要先把它们的 `DT *` 从远端包挖出来复核。
3. **`IsHidden()` 那一层我们没有等价物**：原版随机池还有一道 LiveOps `FeatureConfig` 闸
   （`expansionsHidden` / `armiesHidden` / `CardsSpecialConfig.cardsToHide`），运营可远程隐藏卡。
   我们没做 LiveOps 配置 ⇒ 这一层**不存在**（不影响本缺陷，但严格说原版池比"`!cbrc`"还要再小一点）。
4. **`Booster Pack Legendary *`（`legendaryContainer`）**：原版还有一档"保底 1 张 R4"的传奇包
   （`dropTableItems = [DT <Army> R4, DT <Army> All ×4]`），我们的商店**没有**这个商品 ⇒ 未实现（属另一笔账）。
5. `expansion=5` / `Expansion Only` 变体（`Booster Pack * Expansion`）与我们"全解锁"的边界（用户 2026-09-17 定）如何对应 ——
   我们所有卡都解锁，所以按 `All` 表走是自洽的；**没有**逐商品核过。

1. 🔴 **`RollPack` 有一个空表崩溃**：`:1239` 只在 `rare.Count > 0` 时往 `pick` 放卡，`:1242` 却无条件读 `pick[0]`
   ⇒ 某阵营 `rare+` 为 0 时抛 `ArgumentOutOfRangeException`。现读每阵营 `rare+ ≥ 38`（不可达），
   但 `:1233-1235` 那条告警明确写着"这种情况会发生" ⇒ 告警与实现自相矛盾，顺手一起改（见施工单 A）。
2. `:1230` 的 `rest` 列表**建了从来没被读**（死变量，只用于分流）。改的时候可以顺手删掉或注明。
3. 🔴 **"VIP Booster Cache"（`40K_shop_offer_booster_generic`）的 `Army=null` ⇒ `list = pool` = 全 1129 张**

   要么照原版不提供泛用卡包。**本判定只覆盖"卡该不该出"，不覆盖"这一包是哪个阵营"**，但那一条同样要记账。
