**③ 的推荐做法：自动生成「字段桩」（不是拷 EXP 的桩，也不映射到我们现有类）**

先说为什么另外两条不行：

- **(a) 直接拷 EXP 的 1,869 个桩** —— 三个硬问题：
  - **122 个类名与本工程现有类同名**（`DeckEditingWindow` · `BaseOfferPopup` · `ChatPanel` · `CardHighlight` · `AutoCardRotation` · `AnimFXController` · `FactionScore` …）⇒ duplicate class，**编不过**；
  - 桩里带 `using DG.Tweening / Newtonsoft.Json / NaughtyAttributes / Everguild.LiveOps / Scaffold.Core.Events / I2.Loc` ⇒ 这些包本工程**没有**，整批编不过；
  - 桩里的**方法体是空的**（`Awake(){}`、`GetModifiedMaterial()=>null`）⇒ 行为仍然没有，只是白背 1,869 个文件的编译成本。
- **(b) 把 guid 映射到我们已有的实现类** —— 字段名/类型**对不上**（我们的类是重写的，不是照抄原版字段），Unity 反序列化时**静默丢字段** ⇒ `mTerm`、图标引用、`PriceDisplay` 的 icon/text 全丢，而**不报错**。⛔ 这条最危险。

**推荐 (c′)：只为「要被导入的那几屏」自动生成「字段桩」**，规则四条：

1. 类名一律 `Orig_<原类名>`（如 `Orig_Localize`、`Orig_EverguildTextController`）⇒ **122 个同名冲突自动消失**（Unity 只认 `.meta` 的 guid，不认类名）；
2. `.cs.meta` 的 `guid` **写成原版的 guid** ⇒ prefab 的 `m_Script` 原样就能绑上；
3. 字段**只声明需要保数据的那几个**（`mTerm`、`mText`、`sprite`、`color`、`icon`…），类型取 `int/float/string/bool/Color/Vector2/UnityEngine.Object` 六种 —— **不带任何 `using`，不引用第三方包**，绝不会编不过；
4. **方法体一个都不写**（组件是「数据容器」，行为由我们的 `UiNext` 驱动器负责）。

生成器本身就是一个脚本：读 EXP 的 `.cs` 桩（那里已经有正确的 `[SerializeField]` 字段名和类型）→ 过滤到「本次要装的 prefab 用到的类」→ 出 `Orig_*.cs` + 同名 `.meta`（原 guid）。**每个屏 3～42 个文件，全自动。**

## 二、三条路线与判定门槛

### 路线 X1 · 原版 prefab 直接装入（**第一方案**）

**做什么**：把 EXP 的 `.prefab` / `.unity` 子树，连同闭包资源（`.mat`/`.png`/`.asset`/字体）按**原 guid** 拷进 `Assets/UiOriginal/`，`m_Script` 按 §1·4 三张表改写，Warpforge 脚本用自动「字段桩」保数据；运行时由新栈 `UiNext` 实例化 + 按**节点路径**绑定 + 挂我们的交互驱动器。

**收益**：布局/尺寸/颜色/文案键/图的**原样继承**，不靠人抄；C 档 16 条**机制层一次性消失**。

**代价/风险**：三张映射表的正确性（闸 1 验）· 兄弟序保真（闸 3 附加验）· 焙平的公共件 · 每屏几十个资源文件入库。

### 路线 X2 · 原版数据驱动生成 uGUI 树（**第二方案 / X1 死时用**）

**做什么**：不导入 YAML。用脚本读 EXP，出**我们自己的中间 manifest**（`节点树 + 每个节点的组件与字段`），再由 C# 生成器 **`UiNextBuilder.BuildFromManifest`** 在运行时（或编辑器里）**逐节点 new + 赋字段**。
这正是战场线已经在跑的形态（`gen_arena_manifest.py` → `ArenaBuilder.BuildFromCLI`），**工具链与经验都现成**；差别只在「战场线生成 3D 场景，X2 生成 uGUI 树」，而 uGUI 的组件类型少得多（~15 种）。

**收益**：完全不依赖 Unity 的 YAML 导入行为；字段是我们写的，**不会静默丢**；好调试（manifest 可读可 diff）。
**代价**：要自己实现 15 种组件的「建 + 赋」；`m_Children` 顺序、`RectTransform` 四件套、`LayoutGroup` 的父子关系要写对（写错不报错，只是布局歪）。

### 旧栈回退（**不是路线，是保险**）

旧栈（`MenuDraw` / `ImageQuad` / `LayoutSpace` / `PointerLayer` / `ViewportClip` / `MenuWindowBase` / `HudCanvas`）**整份保留、一行不删、一行不改**，通过运行期开关切回。见 §五。

### 门槛表

| 条件 | 判定 |
|---|---|
| 闸 1/2/3 **全过** | **走 X1**，按 §六 分期 |
| 闸 1 过、**闸 2 或闸 3 不过** | 先定位：是「工具/映射」问题还是「Unity 导入」问题。**能修的修，修完重过闸**；修不动 ⇒ **X2** |
| 闸 1 就不过（prefab 根本导入不出可用树） | **直接 X2**，并在账里写清「Unity 版本对 AssetRipper YAML 的不兼容点」 |
| X1 与 X2 都判死 | **旧栈回退**，并把结论交用户裁定（这是唯一需要回头问的情形） |

### 2·4 量化对比：X1 vs X2 vs 「逐族手写迁移」

| 维度 | **X1 prefab 装入** | **X2 数据驱动生成** | 逐族手写（原路线 A） |
|---|---|---|---|
| 要动多少新文件 | 工具 3 个 + 新栈运行时 8 个 + 断言 2 个 + 资产（每屏 10～40 个） | 工具 2 个 + 生成器 2 个 + 新栈运行时 8 个 + manifest（每屏 1 个 JSON） | 不改文件数，但**要改 100+ 个窗口类** |
| 要改多少**现有**文件 | **很少**：只改「每屏入口那一处调用」（把 `MenuDraw` 建树换成实例化 prefab）+ 帧相关 5 处 | 同上 | **Shell 62 文件 + Battle 30 + Deck 1 = 93 个文件、806 个 `LayoutSpace` 站点** |
| 期数 | 8 期（0 / 1 / 2a / 2b / 3 / 4 / 5） | 同 8 期，期 0·b 换成「生成器试点」 | 同 8 期，但每期要把一族从零画出来 |
| 保真度 | **最高**（布局/颜色/文案键/图原样） | 高（同源数据，但由我们重放，字段可能漏） | 低（人抄，已多次证明会错） |
| 中途并存 | **可以**（按屏开关，一屏一整窗） | **可以**（同一个 `UiNextRouter`） | 只能按族，会有半成品态 |
| 会让哪些宿主红 | 只在该屏切换时红**那一屏的宿主**（§六末表） | 同 X1 | 全程大面积红（C-09 评估原话「数周」） |
| 主要风险 | Unity 导入行为 / 兄弟序 / 映射表 | 生成器写错不报错 | 人抄错 + 返工 |
| 回退 | 一行开关 | 一行开关 | 只能回滚提交 |

⇒ **X1 的「改现有文件」面比逐族手写小两个量级** —— 因为它把「画」换成了「装」。这也是它值得先试两天的理由。

### 5·2 开关（三级，全部**运行期**，⛔ 不用编译宏）

1. **总闸**：环境变量 `WF_LEGACY_UI=1` ⇒ **整份回旧栈**（自检与真机都能一键复现旧行为）。
2. **按屏开关**：`UiNextRouter` 里一张表 `screenId → (legacy, next)`；每屏独立切换，默认 = 该屏迁完后置 `next`。
3. **强制档**：`UiNextRouter.ForceLegacy(screenId)` / `ForceNext(screenId)`，供断言在**两个方向**各跑一遍（灭自证）。

⛔ **不用 `#if`**：旧栈必须**始终参与编译**，否则「回退」就要重新编译，出问题时来不及。

### 5·3 回退动作与副作用

- **一键回退**：`set WF_LEGACY_UI=1` 后重启（自检宿主同样生效）。**不需要改代码、不需要回滚提交、不需要重建场景。**
- **代码级回退**：单屏改 `UiNextRouter` 那行即可（`git checkout -- Assets/CardPresentation/UiNext/UiNextRouter.cs`）。
- **资产级回退**：`Assets/UiOriginal/**` 是**纯增量**，回退时**不用删**（没人引用就不参与运行）；要彻底清就 `git clean` 那一目录。
- **存档 / 资源副作用：无**。理由：新栈只换「视图构建 + 命中」，状态仍在原有 `DailyData` / `DeckEditorState` / `BattleDriver` 里，**不新增存档字段、不写 playerPrefs**（开关只读环境变量）。
  ⚠️ **唯一要盯的**：如果某屏在迁移中顺手改了**状态模型**（例如把 `SetActive` 改成 `anchoredPosition` 时动了可见性状态），那就会跨开关残留 —— **纪律：迁屏时⛔ 不许改状态模型的语义**，只改表现。
- **场景副作用**：新栈**运行期实例化 prefab**，⛔ **不把 prefab 实例烘进 `.unity`**（避免 CLAUDE.md 那条「跑一次宿主整个场景被重写」的老坑）。

### 5·4 旧栈什么时候才允许删

四个条件**全部**满足，才允许开「删旧栈」那一期：

1. **每一屏**都过 §6 的验收（三档分辨率 + 交互点 + 真机点）；
2. **`WF_LEGACY_UI=1` 已连续两个会话没被用过**（自检与真机都走新栈）；
