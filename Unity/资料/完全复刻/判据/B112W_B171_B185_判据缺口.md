## B-171：FMOD 的 Vorbis setup header 到底长什么样

### 一、结论（三条，全部有实测支撑）

1. 🔴 **那条 setup header 根本不在 bundle 里** —— 不是"不带 7 字节前缀"，也不是"放在别的偏移"。
   全量扫过 **30 个音频 resource（2,549 个 AudioClip / 1,823 条 Vorbis）× `\x05vorbis` = 0 命中**；
   再把 `StreamingAssets/aa/StandaloneWindows64` 的 **84 个 bundle（1,646,774,084 字节）**整份按字节扫一遍，**同样 0 命中**。
2. ✅ **bundle 里存的是它的 CRC32，不是本体** —— FSB5 的 **sample header 偏移 `0x0C`** 是一个 `uint32`，
   它**正好等于**「该 clip 所用 Vorbis setup header 整包（含 7 字节 `\x05vorbis` 前缀）的 zlib CRC32」。
   这条**已证死**（见 §三），不是推测。
3. ✅ **codebook 是 FMOD 的共享库，按这条 CRC32 索引**。`vgmstream-cli.exe r2168` 内嵌着 **160 条** setup，
   按 CRC32 建索引后：**本游戏全量出现过的 16 种 CRC32 取值，16/16 全部命中**（见 §四）。
   ⇒ 二波报告里「AssetRipper 猜的 setup ≠ FMOD 那条」这个前提，**对那 450 条并不成立**（§五）。

### 二、FSB5 的真实结构（实测，纠正旧记录里 48 字节的假设）

`FSB5` 头是 **60 字节**（不是 48）：

| 偏移 | 字段 | 实测 |
|---|---|---|
| `0x00` | magic | `FSB5` |
| `0x04` | version | `1` |
| `0x08` | numSamples | `1`（本游戏全是单 subsound） |
| `0x0C` | sampleHeadersSize | **`36 + 32k`**（见下） |
| `0x10` | nameTableSize | `0` |
| `0x14` | dataSize | 音频包区总字节 |
| `0x18` | mode | **`0xF` = Vorbis** / **`0x7` = VAG** |
| `0x1C` | — | `1` |
| `0x20..0x3B` | hash 等 | 与本问题无关 |

- **sample header = `36 + 32k` 字节**（实测出现 `36 / 68 / 100 / 964 / 996 / 1028 / 1060 / 1156`，全部符合 `36+32k`）。
  `k` = 后面追加的 32 字节「定位/索引块」个数（长音频才有，BGM 能到 30 多块）——**它也不是 setup header**（最大 1.1 KB，setup 本体 3~6 KB）。
- sample header 头 16 字节的四个 `uint32`（**这是本次新查到的关键**）：

| 偏移 | 实测含义 | 证据 |
|---|---|---|
| `0x00` | 按 (声道数, 采样率) 分组的配置序号 | 单声道 16k/22.05k/24k=`9/11/13`、32k=`15`、44.1k=`17`、48k=`19`；立体声 44.1k=`49`、48k=`51`（语义未证） |
| `0x04` | **`numSamples × 4`** | `Draft Mode GainSkull`：63,463×4 = 253,852 = `0x3DF9C` ✅ |
| `0x08` | 高位恒 `0x1600`，低位随 k 变 | 未查清语义 |
| **`0x0C`** | **setup header 的 CRC32** | 见 §三 |

- **数据区 = 纯 `u16 长度 + 包`**：`Σ(2+包长)` 逐字节吃掉整个 `dataSize`，**没有任何位置能放下一条 3 KB 的 setup**。
  抽样 `Sautekh_Orikan_gen3.fsb`：`dataSize 33,280`，解析出 304 个包、消费 33,407 字节、文件 33,408 字节（尾部 1 字节）。

### 三、`0x0C` = setup header 的 CRC32（已证死）

```
zlib.crc32(<setup 整包，从 0x05 'v' 'o' 'r' 'b' 'i' 's' 开始>) == sample_header[0x0C] (uint32 LE)
```

三条独立验证，**全部 100%**：

| 验证 | 对象 | 结果 |
|---|---|---|
| ① 已知函数关系 | `vgmstream-cli.exe` 内 160 条 setup，哪一条对 `Draft Mode GainSkull`（f3=`0x988e56d5`）无损重封后 corr=1.0 | 该条 CRC32 **正好 = `0x988e56d5`** |
| ② 全量取值覆盖 | 全游戏 1,823 条 Vorbis 的 `0x0C` 取值（按 (ch,freq) 分组去重）= **16 种** | 16/16 都在 vgmstream 的 160 条里**按 CRC32 命中** |
| ③ 与真实 .ogg 对齐 | 二波那 **450 份「重编码前」备份**（`_tmp_view/b112_r1w_backup/mono_setup/`）里每条 ogg 的第 3 个包（setup） | **450/450** 的 CRC32 == 对应 FSB5 的 `0x0C` |

> ③ 的**反向对照**更能说明问题：磁盘上**没被动过**的 **1,329 个 `.ogg`，1,329/1,329 全部相等**；
> 而不相等的那批（450 + 32）**全部是重编码过的**（`.ogg` 里换成 libvorbis 自己的 codebook）⇒ CRC 判据干净可用。

**提取方法（可复现，纯只读）**：

```python

pos = [i for i in range(len(b)) if b.startswith(b'\x05vorbis', i)]   # 161 处
# 每条取 p..下一条起点，rstrip(b'\x00')，再按 zlib.crc32 建索引 ⇒ 160 条唯一 setup
```

### 四、本游戏全部 16 种取值（现读，供下次直接用）

| (声道, 采样率) | `0x0C` CRC32 | 覆盖条数 | 在 vgmstream 表里 |
|---|---|---|---|
| (1, 16000) / (1, 22050) / (1, 24000) | `0x6a5436bf` | 45 | ✅ 3,528 B |
| (1, 32000) | `0x704fb87e` | 219 | ✅ 3,006 B |
| (1, 44100) | `0x84199294` | 1,133 | ✅ 3,006 B |
| (1, 48000) | `0x910d8ea5` | 389 | ✅ 3,006 B |
| (2, 48000) | `0x30efa143` | 1（`OvertimeStart`） | ✅ 3,484 B |
| (2, 44100) | **12 种**（BGM/长音频逐条不同） | 36 | ✅ 全部命中 |

⚠️ **单声道逐条固定、立体声 44.1k 逐条不同** ⇒ `0x0C` **不是**按 (声道,采样率) 定死的查表键，
而是**编码时实际选用的那套 codebook 的指纹**（短 VO 同批编码选到同一套，长 BGM 各选各的）。
⇒ ⛔ **别拿「声道数+采样率」去猜 setup**（这正是 AssetRipper 出错的方式）；**一律读 `0x0C`**。

### 五、🔴 就地订正：那 450 条**不是** setup 猜错

`报告/B112_R1W.md` §10.3 / §11.6 写的「`.ogg` 里的 setup ≠ FMOD 那条」「vgmstream 用的不是我抠出来的 160 条之一」——
**§三 ③ 已证 450/450 的 setup CRC 与 FSB5 完全相等**。所以：

- ❌ 「setup header 找不到 / 猜错」**不成立**；
- ✅ 真正的偏差**在第 1→2 个音频页的边界上**（见下），**不是** codebook。

**实测（`VO_SaimHann_Ghaelyn_vs_Tyranids`，mono 44.1k，在 450 名单内）**：

| 检查 | 读数 |
|---|---|
| FSB5 `0x0C` vs 备份 ogg 的 setup CRC | `0x84199294` == `0x84199294`（同一条） |
| 音频包逐包比（ogg 300 包 vs FSB5 前 300 包） | **300/300 逐字节相同** |
| 与 vgmstream 的 FSB5 解码比 **前缀** corr @1k/10k/50k/100k | **1.00000000（全部）** |
| **第一处不同** | **样本 146,880**（= 第 2→3 页边界） |
| 该 ogg 的第 2 页 | `nseg=250`，**granule = 31,872**（而该页实解 ≥146,880 样点） |
| 全量统计 | 450 份备份里 **450/450** 的第 2 页都是 `(250 段, granule 31,872)` —— 一个**常数** |

⇒ 分歧点**精确落在页边界**，不是从头就错 —— 这与"setup 错"不相容（codebook 错会从第一块就分叉）。

### 六、还差什么（B-171 剩下的那一步）

🔴 **「页 granule」这条线索还不足以定案**，因为存在反例：
全量 527 个「>3 页」的 `.ogg` 里，**另有 43 个**同样是 `(250 段, granule 31,872)`，却**不在 450 名单**（即与真值 corr ≥0.999）。
⇒ 这 43 个的第 2 页可能真的只解出 31,872 样点（250 个**短块**包，127.5 样点/包），而 450 那批是**长块**包被写成了短块 granule。

**下一步该用的手段**（按性价比排序，都不需要跑 Unity）：

1. **用 libvorbis 真算逐包样点数**：`vgmstream` 自带 `libvorbis.dll`，或直接用 `libsndfile` 分页解码，
   把每页「真实累计样点数」算出来，与 ogg 里写的 granule 逐页比 —— 这一步能一次性判定 450/43 的分界。
2. **无损重封可行性验证**（有价值的前景）：若只是 granule 写错，则 `450 条`可以**只改 granule、不动任何包**地修好，
   不必像现在这样用 q8/q10 重编码（那次 `16.38 MB → 41.11 MB`、且是**有损二次编码**）。
   备份就在 `_tmp_view/b112_r1w_backup/mono_setup/`（450 份，是"改完 granule 但未重编"的那一版）。
3. 若第 1 步证明 granule 不是全部原因，再查 **id header 的 `blocksize_0/1`**（实测这 450 条是 `8/11`，
   把它暴力试过 6..12 各档，`8/11` 已是与真值最贴的一档 ⇒ **不是 blocksize**）。

#### ① `Gauss Rays`（256×128）—— **真差异（我们偏），成因未坐实**

成因**查不到确定结论**；最可疑的是 GPU 回读链（`Blit` 的采样/写回）与规格解码不等价，但**没能证明具体是哪一步**。

#### ③ `NoiseNRM`（128×128）—— **真差异（我们偏），成因查不到（但源数据铁证如山）**

| 项 | 读数 |
|---|---|

| 导出路径 | 应走 `ReadableCopy` 开头「**直接返回 src**」那条（`EffectExporter.cs:4594-4600`），**压根不该经过 `Graphics.Blit`** |

| 差异量级 | 掩码 RGB MAE **5.432**、p99 **23**、max **34**（A 通道 MAE 3.79） |
| 差异形态 | **白噪声**：lag1/2 自相关 ≈ **−0.005 ~ +0.005**（全方向）、`(y%4,x%4)` 均匀、**与亮度无关、与 alpha 无关** |

- 不同源 / 不同构建（bundle 原始字节 == `assets_full`，两处 100% 一致）、
- 预乘 alpha 往返（误差与 alpha 无关）。

**建议的下一步（要么给出确定答案、要么给出确定的反驳）**：

- 若 `GetPixels()` 就已经不一致 ⇒ 是 Unity 把这张**RGBA32 可读纹理**读回来的值本身不同（那就与 bundle 数据无关，是运行时侧）。

## 顺手发现

1. 🔴 **`assets_full` 不是唯一的原版判据来源了 —— `UnityPy` 解出来的才是可机读、可批量的那一份。**
   `UnityPy 1.25.3` + `texture2ddecoder`（本机已装）能把 BC1/BC3/BC4/5/6/7、ASTC、ETC、PVRTC 全部 CPU 解码，
   实测两张 BC7 **100% 逐字节**复现 AssetRipper 的 PNG。⇒ 以后 484 张（乃至 `ArenaOriginalPrefabs`）**可以批量机检**，
   不必再靠"和某一张 PNG 比 MAE"来猜。

2. 🔴 **二波那 450 条 `q8/q10` 重编码很可能是白做的**：它们的 setup header 本来就是对的（450/450 与 FSB5 的 CRC32 相等），

   （现状：`16.38 MB → 41.11 MB`，且是**有损二次编码**，corr 0.999~0.99994）。
   备份 `_tmp_view/b112_r1w_backup/mono_setup/`（450 份）还在，随时可以重走无损路。

4. **FSB5 头是 60 字节，不是 48**；`sampleHeadersSize` 是 `36 + 32k`（k = 追加的定位块个数），
