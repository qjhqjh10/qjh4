## 四、判据已定、但本代理**没改**（要动白名单外的文件 / 要裁定）

### 1 · 悬停缩放：原版是**绝对值 1.3**，我们是**乘 1.3**（0.73 → 0.949，差 1.37 倍）

- 判据：`CardScript.cs:4939-4942`（`ShowCardInHand`）`Quaternion vector = Vector3.oneVector * varsDevice.cardInHandShownScale; this.transform.localScale = vector;`
  —— **`Vector3.one × 1.3`**，而静止档是 `GetCardInHandScale()`（`:5062-5085`）= `Vector3.one × m_scale` = **0.73**
  ⇒ 悬停/静止 = **1.78 倍**，不是 1.3 倍。
- 我们：`HandLayout.cs:800` `scale *= hoverScale` ⇒ `0.73 × 1.3 = 0.949` ⇒ 悬停那张宽 214 px（原版 **294 px**）。
- ⛔ **没改的原因**：三条既有断言把「乘」这一档钉死了，而它们都在本代理白名单外 ——
  `Editor/BattleScene.cs:3721-3731`（AL-1049：`sHover / sRest == 1.3`）·
  `Editor/B117F11_Assert.cs:135`（`wantScale = cardScale × Scale × hoverScale`）·
  `Editor/CardBaseDemo.cs:5791-5795`（只断两个字段值，不受影响）。
  ⇒ **改法**：`HandLayout` 里把悬停那支写成 `scale = hoverScale * LayoutSpace.Scale;`（绝对值；`LayoutSpace.Scale` 只在小屏 <1），
  同时把上面 **两处** 断言的期望值改成「与未悬停那张的**比值 = 1.3 / 0.73 = 1.7808**」，或直接断绝对 `1.3`。
  ⚠️ **视觉后果（真机要让用户看一眼）**：1.3 档的卡高 468 px，卡心在基准线上 ⇒ **卡底会切掉 85~190 px**（取决于 §四·2 取哪一档 y）。

## 五、判据未定 / 本轮未复核

1. **敌方手牌卡的「卡背朝向」是不是靠 `invertRotation` 那次 180° 转出来的** ——
   `GetRotation.c:103-129` 与 `:138-164` 两处 `AngleAxis` 的**轴与角度都在 `globalVars`（`DAT_1842da2a8`）
   那个静态块里**（`+0x48..0x50`），`.c` 读不到、`out_il2csharp` 也写成 `unknown`。
   我们的 `RotationAt` 沿用 2026-09-25 的结论（「代数退化成纯 Z 滚，敌方再 ×R_z(180°)」，
   见 `资料/手牌布局_原版算法与参数.md` §八之二），**本轮没有重新推导**。
   ⇒ 若那根轴其实是 `up`（⇒ `R_y(180°)`，翻面看卡背），我们的敌方**张角正负号**就可能是反的。
   **建议**：等战场线恢复后进原版看一次敌方手牌两端的倾斜方向即可定案（本轮无实拍、无判据，⛔ 不猜）。
2. **`GetRotation` 里那两处 `AngleAxis` 的触发条件不是一个** ——
   第一处看 `0.0 < m_verticalOffsetLookTo`（符号），第二处看 `m_invertRotation`。
   我们两处都绑在 `invertRotation` 上（对我方/敌方这两份实例**等价**，因为 `lookTo` 与 `invertRotation` 同号），
   但若将来出现「`lookTo > 0` 且 `invertRotation = 0`」的实例就不等价了。⇒ 如实登记，暂不改（全库 52 份里没有这种组合）。
3. **`m_useRotation = 0` 的两份（选牌 4052 / 换牌 4881）我们没有对应物** ——
   那两份的 `m_scale = 183.41`、`m_betweenElementsSpacing = 502.2`（**同一套 3D 世界单位**），
   我们换牌区是 `MulliganPanel` 自己摆的平排（另有代理在管）。⇒ 不在本条范围。
