**本子片新增真缺口 3 条**（详见 §4·④ 与 §5）：

1. **`DeclareAttackCore` 调 `IsValidTarget` 时没把 `forced` 透传成 `allowAutoActions`** —— 原版 `ResolveForceAttack` 那条路传的是 `allowAutoActions=1`。⇒ 强制/脚本攻击打督军时会被「召唤病 + flank」那道闸**误拒**（Gap-A，**有真实可达性**）。
2. **`AttackDamageEntries` 的标记光取值取【被打方】** —— 原版 `RecordAttackPendingDamage` 取的是**攻方**（`CardScript__RecordAttackPendingDamage.c:68`）。真实结算（`_ResolveAttack…:1278`）取被打方，与我们一致 ⇒ **只有「致死预判」这一路与原版不同**（今天零可观测，见 §4·④-a）。
3. **`DoForceAttack` 的打法选档用严格 `>`（平手取近战）** —— 原版 `AddScriptedAttack.c:65` 是 `(melee <= range) + 1`（**平手取远程**）。今天池内 12 张相关卡**没有一张 melee == range** ⇒ 零可观测（见 §4·④-d）。

另有 **2 条账落点错误 / 过期**（不是缺口，是账要改）：`MightAttackBuffedCard`、`GetRandomAttackTarget`（见 §5）。

### ③ 灭自证（一条「两边一起改回去就变红」的断言）

**建议断言 `TestB149AttackSequenceOrder`**：构造一局 —— 攻方 `blast 2` + `stomp` 且 melee/range 都 ≥1、守方 `markerlight 2` 且 maxHealth 2（主伤害必杀）、守方左右各有 1 个可参战单位、远程打法。

断言**事件流严格次序与量**（读 `ctx.Events`，不读实现内部变量）：

1. `Hit`(Shuriken 若有) → `Hit`(主伤害) → `Hit`(Blast)×2 → `Hit`(Stomp) → `Hit`(Counter) → `Hit`(Markerlight) 的 `Kind` 序列**逐位相等**；
2. `Counter` 那条的 `Amount` == **受伤前**的守方 `FieldAttack(ranged)`；
3. `Markerlight` 那条的 `Amount` == **被打方**（不是攻方）的 markerlight 值；
4. 守方被主伤害打死时，`Counter` **仍然出现**（原版 `:145` 的初生者例子），但 `Markerlight` **不出现**（`:1254` 的 `EnoughPendingDamageToDie` 守卫）。

**为什么它能灭自证**：这 4 条期望值全部写在 `.c` 行号旁（`:618/721/999/1030/1089/1142/1254/1278`），**不由实现推导**。任何「把次序改回旧的（爆裂/践踏排在反击之后）」或「把标记光取值改成攻方」的改动，都会让 ①/③ 变红；而**只改实现不改断言**（或只改断言不改实现）也必然有一侧红，因为期望值是**常量表**而不是从被测代码取。

### ④ 口径冲突（以 `.c` 为准，单列，⛔ 不混进逐条表）

**(a) 标记光数值到底取谁 —— 原版自己有两条不一致的路**

- `CardScript__RecordAttackPendingDamage.c:66-71`：**条件看被打方**（`get_CurrentMarkerlight(param_3) > 0`）、**取值看攻方**（`get_CurrentMarkerlight(param_2)`，`param_2` = attacker）。
- `_ResolveAttack_d__438__MoveNext.c:1251-1256 / 1275-1281`（**真实结算**）：**条件与取值都看被打方**（`param_1+0x130` = `_finalTarget`），额外要求 `attackType == 2`（`param_1+0x58`）。
- ⇒ **以结算 `.c` 为准 = 被打方**（这是玩家实际看到的伤害）。我们真实结算已对（`RuleCore.cs:7400` `target.KwValue`）；**只有 `AttackDamageEntries`（致死预判）取了被打方**，与原版 pending 路的「攻方」不同。
- 影响面：仅当**攻守双方 markerlight 值不同**时，「这一刀会不会打死它」的预判会偏；由于预判只喂 `CounterAttack.Classify` / `Strike` 闸 / `targetWillDie` 表现分支，**不直接改血量**。今天池内 markerlight 只能靠效果授予、且一次只给一方，实测组合极少 ⇒ 记为**待拍板**（照抄原版这条不一致 vs 保留我们的一致口径）。

**(b) `CheckIfAttackKillsTarget` 与 `RecordAttackPendingDamage` 用不同的攻击力口径** —— 前者 `GetCombatDamageWithType(1)/(2)`（**无条件**近战/远程），后者 `GetCombatDamage(attacker, attackType)`（**本次打法**）。两个都是「会不会死」的预判，但轴不同。我们照此分裂实现（`AttackKillsTarget` 用两种打法各判一次；`AttackDamageEntries` 用本次打法），**与 `.c` 一致**，不算缺陷，记在这里防止后人「统一」成一个。

**(c) `ShouldTriggerStompDamage` 的 `target+0x68 < 0`**：`.c` 只给出一段 `ObscuredInt` 五字结构，**读不出是哪一格**；字段名来自 `out_il2csharp/BattleManager.cs:7460-7488`（`targetCard.__field_currentHealth`）。⇒ 结论是「`.c` 结构 + 第三方命名」合判，**不是单一来源**。同一格的用量 `abs(currentHealth)` 在 `.c:1089` 有符号提取式佐证，两条互相印证。

**(d) `AddScriptedAttack` 的打法选档有两个原版公式**：

- `BattleManager__AddScriptedAttack.c:62-65`：`iStack_1e0 = (melee <= range) + 1` ⇒ **平手取远程(2)**；

## 5. 顺手发现（越界的也报，⛔ 我没改）

1. **账落点错位（2 条）**
   - `MightAttackBuffedCard` 账里落点写 `SimpleAI.cs:2095（ShouldDisableTweak）` —— 那是 **matchType 闸**（`RankedBot/ClosedDeckBot/FastModeBot`），与本方法无关。真实现是**类尾** `SimpleAI.cs:2180 MightAttackBuffedCard`（2026-10-26 `B8_E` 建、2026-11-05 `B144_R2` 订正）。⇒ 账要改落点，否则下个会话会判「没做」。
   - `GetAvailableAttackTargets` 账里落点写 `RuleCore.cs:5509（IsValidTarget）` —— 那只是它内部用到的闸；**真正的等价物**是类尾 `RuleCore.cs:17365 AvailableAttackTargetsDesc`（倒序枚举，语义正确）。⇒ 同类误判风险。

2. **`GetRandomAttackTarget` 的 `D` 档理由要改**：账写「无同名路径」，实际是**原版本身零生产调用点**（`grep -rl` 只命中定义文件；`GetAvailableAttackTargets` 的两个调用点是 `EndTurnClick` 与它，都不是内联源）。⇒ 判 D 成立，但理由必须写成「原版无调用点」，否则将来有人按「我们缺」去补一个死函数。

3. **`AttackDamageEntries` 的 `Has("shuriken")` 是 `B148-W2` 那批 `KwValue>0` 的漏网**（同文件 `DeclareAttackExecute` 的 blast/sentry 两处已改成 `KwValue`，标记光那一处没改）—— 见 §3.2。

4. **`PendingBerzerkUnits` 的 `CanActNow` 与原版 `CanAttackCard` 不同源**：`CanActNow` 是 `CanAttackNow(近战) || CanAttackNow(远程)`，而原版 `CanAttackCard` 的闸集是另一组（见逐条表）。今天 `berzerk` 池内 0 张 ⇒ 零可观测；一旦有狂暴卡，这里会**比原版宽/窄**，要复核。

5. **`AttackKillsTarget` 只传伤害数值、不传伤害类型**：原版 `CheckIfAttackKillsTarget.c:30-61` 建的是**两条平行表**（`List<int>` 数值 + `List<int>` 类型=4）；我们 `WouldKillByEntries(u, int[])` 没有类型形参。⇒ 若将来出现「按 DamageType 免疫/易伤」的防御（现在没有），两口径会分叉。

6. **`DeclareAttackExecute` 的标记光广播目标是 `target`，而原版被广播的是 `_finalTarget(+0x130)`、被 `ReceiveDamage` 的是 `targetCard(+0x30)`** —— 替身改向那一记两者会不同。我们的「就地改目标」把两者合并成同一个 ⇒ 在「改向攻击 + 标记光」这条组合上与原版**可能差一个目标**（今天唯一替身卡 `SAU33` 不带标记光，且被授予标记光的单位需要是改向后的目标才会现形）。**未核到底，记为疑点**，不要当作已对齐。

7. **`ResolveMultiDamage` 的「不在场就打 `LogWarning` 并跳过」我们只静默跳过** —— 与「不许静默失败」那条红线擦边，建议补一条 `ctx.Log`。

8. **`ResolveFatigue` 原版方法体第一句是 `Debug.LogWarning("Fatigue is not implemented")`**，而伤害照打。这条记下来是为了防止后人「看到 warning 以为原版没做」而去删我们的实现。
