## §一 结论

### 1·1 一句话（三条，按重要性排）

1. **这 318 条里，没有一条的「业务逻辑」是丢在 `Method not found` 那个洞里的。** 洞的全部含义 = **「这里有一次调用/一次类型转换，反编译器没认出目标」**。97 个不同的 VA 全部被判了性质：**70 个能反查到名字**（其中大半是 `List<T>` / `Dictionary<K,V>` / 委托 ctor 这类**框架泛型共享体**）、**26 个是 il2cpp 运行时跳板**（类初始化 / `isinst` / `memset` / 栈探测）、**1 个是空方法共享桩**。
2. **但这 318 条里只有 42 条「洞之外可读」。** 剩下 276 条的 Cpp2IL 体被**另一个族的注记**打烂了 —— `Unmanaged memory load`（本文件合计 **2,479** 处）：它把**每一次字段读写都替换成 `0`**（`object obj = this + 120;`、`if ((nint)0 != 0)`）。⇒ **「顺着 MNF 的 VA 反汇编去补齐 322 条」这条路，对 87% 的条目补不回逻辑，因为洞不在那里。**
3. **那 276 条怎么补？有确定的路，而且本轮已经把方法证明到可执行**：UML 注记里**带着字段偏移**（`this @ rcx (X)+30`），而**具体实例的 Ghidra `.c`**（`decomp_full/*.c`）里同一个字段是**裸偏移**（`*(longlong *)(param_1 + 0x20)`）—— 两边一对，`+0x30` 就变成 `clearFiltersButton`。见 §二·4 的实证（`CollectionFilterController` 的 9 个字段全部对上）。**这条路的成本是「一个类半天」，不是「读不出来」。**

## §二 方法学（可复现）

### 2·1 怎么把 318 条挑出来

1. 取 G1 的 `_tmp_view/g1/methods_raw.json`（699 条真方法 + 每条在 Cpp2IL 里的候选体位置）。
2. **重扫 Cpp2IL 文件本体**（`scan322.py` 复用 G1 `extract.py` 的 `scan_file`：处理「一个文件多个顶层类型」「IL2CPP 名字转义 `_003C_`」），对每个候选体抽全部 `Cpp2ILHelpers.NoteDecompilerIssue("…")` 字符串。

### 2·2 洞的 VA 怎么定性

`RVA = VA − ImageBase(0x180000000)`；`d:/2/tools/il2cpp_out/script.json` 的 `ScriptMethod[].Address` **就是 RVA**。三段证据按顺序用：

1. **`script.json` 反查名字**（`resolve_vas.py`）→ 得「可能的名字」；
2. **同址方法数**（`dupaddr.py` / `va_dict.py`）→ **这是本轮最重要的一个坑**，见 §2·3；
3. **`disasm_va.py` / `disasm_bulk.py` 直读机器码**（`D:/2/unity_run_ref/GameAssembly.dll`，capstone）→ 反查不到名字的那 28 个，逐条读前 8–24 条指令定性。

> 自检（照 `资料/战斗规则与数值_出处.md` §三）：头几条必须是合法函数序言（`push` / `sub rsp,??` / `jmp`）；出现 `(bad)` = RVA 映射错了。

### 2·3 🔴 坑一：`script.json` 里 **13,991 个地址被多个方法共用**

`script.json` 有 **354,653** 条方法记录，只落在 **216,881** 个不同地址上 —— **IL2CPP 会把「机器码相同」的方法折叠到同一个地址**（空方法、空 ctor、属性 getter、`List<T>.GetEnumerator` 这种泛型共享体都是）。

| `0x1804B33B0` | **6,376** | 空方法（top = `Dispose`） |
| `0x1804B3630` | 1,931 | 属性 getter（读一个字段返回） |

### 2·4 🔴 坑二（也是路）：C 档的 154 条怎么补 —— **offset → 字段名**

`Unmanaged memory load` 的 payload **自带字段偏移**：

```
Unmanaged memory load: [this @ rcx (CollectionFilterController`1<T>)+30]
```

`dump.cs` 里泛型类的字段**不显示偏移**（全是 `// 0x0`），但**具体子类的 Ghidra `.c` 里是裸偏移**。把两边一对就还原了。**实证**（`CollectionFilterController<T>`，9 个字段全部对上）：

| 偏移 | 字段（`dump.cs:71354-71373` 的声明序） | 对上的证据 |
|---|---|---|
| `+0x20` | `List<CollectionFilter<T>> filters` | `CardCollectionFilterController__SetFiltersToDeck.c:31` —— `param_1 + 0x20` 被当 `List<T>` 取枚举器 |
| `+0x28` | `Transform filterIconHolder` | （未在样例体里出现） |
| `+0x30` | `EverguildButton clearFiltersButton` | Cpp2IL `SetupFilters` 的 `this+30` 上做 `gameObject.SetActive(false)` + `AddListener` |
| `+0x38` | `Vector2 hiddenPosition` | `SetupFilters` 末尾 `+38` 读出的 `Vector2` 赋给 `+58` 的 `anchoredPosition` |
| `+0x40` | `float animationTime` | （未出现） |
| `+0x48` | `List<CollectionFilterToggle> toggleOptions` | （未出现） |
| `+0x50` | `Vector2 originalAnchorPosition` | （未出现） |
| `+0x58` | `RectTransform rectTransform` | `SetupFilters` 里 `+58` 上取 `anchoredPosition` |
| `+0x60` | `Action OnFilterChanged` | （未出现） |

**四步补法**（下一批执行代理照这个做）：
1. 打开该类的 Cpp2IL 体，把每处 `NoteDecompilerIssue("Unmanaged memory load: [this @ rcx (X)+NN]")` 的偏移抄出来；
2. `dump.cs` 找同类（**泛型基类查基类声明序；具体子类查 `TypeDefIndex`**），按声明序排出 `+0x18/0x20/…`（**基类实例头 = 0x20 起算**，本例实测）；
3. 找**任意一个具体子类**在 `decomp_full` 的 `.c`（例如 `CardCollectionFilterController__SetFiltersToDeck.c`），确认 1–2 个偏移**真的对上**（这一步是自检，别跳）；
4. 回填后重跑一遍：**每一处 `(nint)0` 都应该变成一个有名字的字段**；还剩 `0` = 还有没解出来的偏移。

> ⚠️ 边界：**泛型参数 `T` 自身的字段**（例如 `item.Name` 里的 `Name`）**不在本类的偏移表里**，它由具体实例的类型决定 ⇒ 这类位置**只能读具体子类**（G3 §3·C 的做法：`AllianceBadgeDrawer__GetItemName.c`）。
