**口径与残余风险**（照实写）：

1. 本扫描覆盖 `[reg+disp8=0x38]` 与 `[reg+sib+disp8=0x38]` 两种主编码；**没有**覆盖 `mod=10`（disp32 编码成 `38 00 00 00`）—— 编译器对 `0x38`（<128）一律用 disp8，实际风险≈0，但**未穷举**。

- **原版客户端一行都不写 `highestValue`**（VA 级扫描 0 处非栈写 + 唯一写 API 的机器码只写 0x3C + ctor 不初始化）。
- 它只从 **`PlayerDataManager` 的在线数据 JSON 反序列化**进来；而进度是通过 **`CloudHandle.UpdateAchievement(1040)` / `UpdatePooledAchievements(1041)`** 交给服务器的 ⇒ **这一格由服务器（云脚本）维护**，客户端的读口统一走 `Math.Max(current, highest, 0)`。
- 我们现在的 `Math.Max` 口径（`ProfileData.AchievementHighestValue` / `SetAchievementValueAtLeast`，`Shell/ProfileData.cs:1658-1700`）是**关服后的本地等价物**：
  - 它**满足**四个读者的语义（「曾经达到过」），否则连登断签会让成就重新变「未完成」，那是原版读者代码明显不想要的行为；
  - 它与原版**唯一的分歧前提**是「服务器到底有没有把 highest 抬到 current」—— 云脚本已随关服消失，**本机无法证明**。若不抬，则 `GetHighestValue ≡ max(current,0)`，两者只有在**当前值会回退**的成就（连登一类）上才可分辨。
  - 按其性质属于 **`🔶 自己设计（非原版）`· 服务器相关**（铁律 18·0 允许的唯一门类），理由应写：**「服务器已关服，`highestValue` 的唯一写点在云端反序列化/云脚本，本机判据为空」**。

### 1.5 还差什么

- 云脚本本体（`UpdateAchievement` 1040 的实现）**本地不存在** ⇒ 「服务器是否 `highest = max(highest, current)`」**永久不可证**。要在账里把这一点写成「判据在远端」，而不是「已复刻」。

### 3.2 我们现在的样子

### 3.3 最小补法（不动其它逻辑）

```csharp
void OnEnable()
{
    if (text == null) text = GetComponent<TMP_Text>();
    if (text == null) return;
    WarpText();                                              // 原版：先弯一次
    TMPro_EventManager.TEXT_CHANGED_EVENT.Add(ReactToTextChanged);   // ← 新增
}

void OnDisable()
{
    TMPro_EventManager.TEXT_CHANGED_EVENT.Remove(ReactToTextChanged); // ← 新增，且必须在 text 判空之前
    if (text == null) return;
    text.ForceMeshUpdate();
}
```

- 方法组转换每次生成新委托，但 `FastAction<A>` 内部用 `Dictionary<Action<A>, …>`，`Action<T>` 的相等性是「target + method」⇒ `Remove` 能正确摘掉。
- `FastAction.Add` 本身对重复键幂等（`lookup.ContainsKey` 直接 return）⇒ 即使 `Configure()` 与 `OnEnable` 都触发也不会重复挂。
- 编辑模式下 `AddComponent` 不派 `OnEnable`（工程已知坑）⇒ 生产路径（实例化 prefab）才会真的订阅，自检仍走 `Configure()`。两者不冲突。

### 4.4 要接哪 / 缺什么（按「先接什么才有意义」排序）

1. **补 `IPlayEventDeckSource` 的实现并注入 `PlayEventDecks.Source`**（这是所有 `GetEventDeck` / `ValidateEventDeck` / `GetEventDeckPredicate` 的前置）：
   - `Count` / `IdAt(i)` / `ArmyAt(i)` / `GameModeAt(i)` 走 `CollectionData`（`Shell/CollectionData.cs`：`DeckInfo.Name` 兼作 id、`Warlord(i)` 出阵营）；
   - `IsPlayableAt(i)` = `RuleEngine.DeckRules.Validate(...)` 通过（隐藏卡那一跳本机无等价物，须在实现里明说）；
   - `IndexOfId(id)` = `CollectionData.IndexOf`；
   - 注入点建议放**启动期单点**（`MainMenuRuntime` 或 `CollectionData` 静态构造），并在句柄 null 时**出声**。
2. **补两钮弹窗口**：`PlayEvent` 现有 `OnErrorPopup` 是单钮；要么加 `OnTwoButtonPopup(string textKey, string okKey, string cancelKey, Action onOk, Action onCancel)`，要么在 `StartMatch` 里直接调 `WindowsManager.ShowPopUp` 的五参重载（已有）。⚠️ 但要**先定口径**：`PlayEvent` 这一层现在**没有 `WindowsManager` 依赖**（它刻意只留静态口），直接调会把它绑到壳上。
3. **决定这条链挂在哪条生产路径上**：`PlayEvent<,>` 要与 `LiveOpsEventWindow` 二选一——
   - (a) 让 `LiveOpsEventWindow` 持有/委托一个 `PlayEvent` 实例，`StartMatch` 走校验 + 弹窗 + `StartMatchNoCheck`；
   - (b) 把两跳（`ValidateEventDeck` / `HasDefensiveCards`）**移植进** `LiveOpsEventWindow.StartMatch`，`PlayEvent` 继续只做框架与自检。
   现状是 (b) 的一半都没有：`LiveOpsEventWindow.StartMatch` 不做卡组校验。
4. **别顺手做「自动分配防御卡」**：原版没有这个行为（见 4.2）。若将来要做，那是 `🔶 自己设计`，且**不在**这条 popup 上。

### 4.5 还差什么（判据侧）

- 原版 `LiveOpsEventWindow` 的对应物（原版里叫 `SearchingMatchWindowDemo` 一族 / `MatchMakerManager.StartMatch`）**还没逐句对过**：我们现在的窗口 `StartMatch` 是自建链（注释里也写着「本地入口是我们定的」）。这一层要不要也做卡组校验，需要先查原版窗口侧有没有等价的前置检查（`grep` 到 `MatchMakerManager.StartMatch` 是另一条链，`BattleDriver.cs:4585/4607/4618` 有现成注释）。
- 原版 `CardDeck.AddDefensiveCard` / `TryAddDefensive` **真实调用点 0**（ICF 掩盖了唯一疑似点）—— 若将来要做「防御卡自动分配」，判据得从**远端云脚本**或 UI 侧另找，本地没有。
