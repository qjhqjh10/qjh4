## 二 原版消费形状（逐条带出处）

### 二·1 100 个整数是【怎么烧的】

- **`MatchData__GenerateRandomNumbers.c:19`**：`uVar3 = FUN_1803f37c0(DAT_1842934a0, 100)` = `new int[100]`，存 `MatchData + 0x20`。
- **`:26`**：逐格 `uVar2 = UnityEngine_Random__Range(0, 1000, 0)` ⇒ **`[0, 1000)` 的整数**（上界开、不含 1000）。
- **`:20`**：烧完把游标 `MatchData + 0x28` **清 0**。
- **种子**：原版用**全局 `UnityEngine.Random`**（不种、（进程内）不可复现）。
  ⇒ 我们换成 `System.Random(seed)`（`BattleContextRandom.cs:48` `Rng.Next(0,1000)`）—— 已标 `🔶 自己设计`，理由=工程红线「同种子同局」。**表/游标/取法照原版**，只有数源不同。

### 二·2 下标【怎么推进】（用满 100 之后怎么办）

- **`MatchData__GetRandomInt.c:24`**：`uVar3 = *(int *)(param_1 + 0x28) % *(int *)(lVar2 + 0x18)` —— `% Count(=100)` **取模回绕**。
- **`:27`**：`*(int *)(param_1 + 0x28) = *(int *)(param_1 + 0x28) + 1` —— **每消费一次游标 ++**。
- **`:34`**：`return param_2 + iVar1 % (param_3 - param_2)` = `min + v % (maxExcl − min)`。
- **两条不消耗**：`param_3 <= param_2 + 1`（区间空/单值）⇒ **直接返回 min、游标不动**（`:22-23`）；数组 null ⇒ LogError + 0（`:18-21`）。
- **一张表**：`BattleManager__GetRandomInt.c` 只是转发到同一张 `MatchData` 表 ⇒ **全引擎一条流、一个游标**。
- 我们的 `GetRandomInt`（`BattleContextRandom.cs:62-70`）逐条对应（含「不消耗」与「取模」），**已对齐**。

### 二·3 🔴 三问·第 3 问：同一次结算里多条 90 档是否取同一个数？

**不是同一个数。每「一次伤害落地」各掷一次，且掷点不在数值计算里，而在伤害调整里。**

证据链（`decomp_full` + ilspy）：

1. **数值计算（`AbilityLogic__GetValueFromCriteria.c`）对 90 档【不掷骰】**：
   - `:33-42` 的 `param_7 == 0`（`Normal`）支：`min != max` 时 **`BattleManager__GetRandomInt(manager, min, max+1)`** ⇒ Normal 的区间值**在这一步掷一次**（多目标时**共用**）。
   - `:200-204` 的 `param_7 == 0x5a`（=90）支：**`return uVar6`**（= `param_3` = **min**）⇒ 90 档**返回 min、不掷骰**。
2. **掷骰在 `CardScript__GetAdjustedDamage.c:23-30`**：
   ```
   if ((damageType < 0xd) && ((0x1420 >> damageType) & 1))     // 位掩码 = {5,10,12}
       damageValue = BattleManager__GetRandomInt(manager, dmgInfo.damageValue, dmgInfo.secondaryValue + 1);
   else damageValue = dmgInfo.damageValue;
   ```
   `DamageInfo`（`DamageType.cs`：`Normal0 Ranged1 … Random5 … RandomPoison10 … RandomAbility12`）⇒ **`damageType ∈ {5 Random, 10 RandomPoison, 12 RandomAbility}` 才在这一步掷**。
   `DamageInfo` 字段序（`out_cpp2il_dev_ilspy/DamageInfo.cs`）：`actingCard@+0x10`、`damageValue@+0x18`、`damageType@+0x1c`、`secondaryValue@+0x20` ⇒ 掷法是 `GetRandomInt(damageValue, secondaryValue+1)` = **min..max**。
3. **`damageType` 何时还活到这一步**：`AbilityLogic__PlayAbility.c:1488-1504`（`case 10/0xd`）与 `:1655-1671` 两个伤害支：
   ```
   DamageInfo__ctor(dmgInfo, target, /*value*/min, /*type*/damageType, /*secondaryValue*/max, …);
   if (criteria.valueOptions != 0x5a) {                 // 不是 90
       if (criteria.damageType == 5) { LogError(); dmgInfo.damageType = 0; }   // 逼回 Normal
   }
   ```
   ⇒ **`damageType==5` 只有在 `valueOptions==90` 时才不被抹掉**（`valueOptions==0` 的 `(0,5)` 会退回 0、不掷第二遍）。
   （`case 0xc` 那支 = `DealMultiDamageVariable`，**没有**这条 `!= 0x5a` 闸 —— 见 §五 未查清 ③。）
4. **「每目标掷」= 在目标循环里调 `GetAdjustedDamage`**：
   `BattleManager._ResolveMultiDamage_d__456__MoveNext.c:136` 在**逐目标循环**里对每个目标
   `uVar15 = CardScript__GetAdjustedDamage(targetCard, uVar15, 1)`。
   ⇒ **一个 90 伤害打 N 个目标 ⇒ 消费 N 个随机数**（各目标各拿一个）。
   单目标 N=1；`AM53`（2 个）、`BL53`/`GOF44`（3 个）、AoE（全部命中）各按实际目标数消费。

**结论：**
- **不是「一次 ability 只取一次」**，也不是「一次 op 取一次」—— 是 **一次「伤害落地」(op × 目标) 取一次**。
- 90 档在 `GetValueFromCriteria` 里**一次都不取**（只拿 min）；取数全在 `GetAdjustedDamage`，**逐目标**。
- 对照：`Normal(0)` 区间值**在 `GetValueFromCriteria` 取一次**，多目标**共用**（且 `damageType` 被逼回 0，`GetAdjustedDamage` 不再取）。
  ⇒ **「共用」是 `Normal` 的形状，「逐目标」才是 `90` 的形状** —— 我们当前把两者都做成「共用」，所以 **90 的多目标行错**、`Normal` 区间行对。

## 四 会影响哪些断言 / 指纹

| 面 | 会不会动 | 说明 |
|---|---|---|
| `ruleprobe play check`（≈5 秒，非 Unity） | **会** | 16 个多目标行的伤害值变；**且因游标是全局的，赛程后段的随机抽取会整体后移** ⇒ 同一局的后续读数可能连带变（见下「级联」）。 |
| `PlayProbe.PinnedPlayMd5`（`PlayProbe.cs:4057`） | **要重钉** | 基线文件同步重生成；哨兵是源码常量，只能手改。 |
| `RuleEngineTest.Run`（Unity，3m53s） | **必跑** | 动了 `RuleEngine/Core` ⇒ 按铁律 12「动引擎必跑」。新增断言见下。 |
| `BattleScene.Run` / 其它宿主 | **不因本改动必跑** | 本改动只动引擎结算；按铁律 12 三条判据，只动引擎 ⇒ 跑 `RuleEngineTest.Run` 即可（真机并排另说）。 |
| `NetBattleTest.Run` | **视情况** | 若有联机回放/终局哈希断言（联机走同一 `BattleContext`）可能在多目标 90 卡局里变；CI 绿灯以同步点为准。 |

🔴 **级联警告（施工的人最容易漏）**：随机表是**一局一条流、一个游标**（§二·2）。把某个多目标 90 结算从「消费 1 次」改成「消费 N 次」后，
**这一局之后的所有 `GetRandomInt` 都会移到不同的格子** ⇒ `play all dump` 里变化的可能**远不止那 16 张卡**。
这不是回归，是「同一局的随机序列整体平移」。重钉前必须 A/B 隔离：
单开这一处改动、其余全关，跑 `play all dump` 对指纹，再归因哪些行变、为什么。

**建议新增断言（灭自证写法，见 `CLAUDE.md` §三）：**
- **主判别式**：造一个「90 打 2 个目标」的夹具，`RandomNumbers` 手填成 `{a,b,…}`，断言**两个目标各拿到 `f(a)`、`f(b)`（不同）**；若实现退回「共用一掷」，两个目标值会相同 ⇒ 该断言必红。
- **对照臂（灭未改错）**：同一夹具换成 `Normal` 区间（`valueOptions=0`），断言**两个目标值相同**（共用）⇒ 挡住「一律改成逐目标」的过度修正。
- **游标计数**：断言该次结算后 `RandomNumbersIndex` 增量 = 目标数（90）/ = 1（Normal）；并断言单值区间（min==max）**不消耗**（`maxExcl<=min+1` 那条）。
