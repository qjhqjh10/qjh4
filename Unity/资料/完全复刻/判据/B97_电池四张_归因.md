## 一 逐卡证据

### 一·一 SOR69（`Zephyrim Superior` · `Pray: Draw a troop`）

**卡数据**（`MyGame/Assets/RuleEngine/Resources/cards_engine.json`）：`keywords = [Flying, Flank, Pray]` · `hasActiveAbility = 1` · `activeAbilityLogic = [{trigger:400,…}]` · `enchantment = [{trigger:655, buffType:15(抽牌), token:"9218576f…"(一张 troop)}]`。⇒ 「pray」这条效果 = 触发 655 时抽那张 token（troop）。

**差异是**：`steps` 两版**只差一处**——④b 的 `aa`。
- 基线（`out_play_baseline.txt`）：`…,alt(pray)=0,`**`aa=0`**`@tgt2/rng+0/pray1/exh1,atkM=6,atkR2=0,kill=0@2M/gone@tgt5`
- 现在（`play SOR69` 实跑）：`…,alt(pray)=0,`**`aa=6`**`@tgt2/rng+0/pray1/exh1,atkM=6,atkR2=0,kill=0@2M/gone@tgt5`
- 其余 `steps`（play/oath/selfChip/softAtk/chip2/tactic/troop2/end0/enemyTactic/friendDies/end1/collect/draw/abil/atkM/atkR2/kill）**逐字相同**。

**少的那张牌 = `aa` 那一次 pray**：
- 基线净差 10 条，抽了 `filler12`＋`filler13`＋`filler26`（3 张）；
- 现在净差 8 条，抽了 `filler26`＋`filler12`（2 张）。
- **差的就是 `filler13`**，而它只能来自「④b `aa` 成功（`aa=0`）→ 又 pray 一次 → 抽一张」。`aa` 一变成 `6`，那张就不抽了。

**为什么现在是 `6`（`ErrExhausted`）** —— 我们这一侧：
- `RuleCore.UseAlternativeCore`（`RuleCore.cs:12051-12052`）：④ `alt(pray)` 成功时 `u.Exhausted = true; u.AttacksThisTurn++;`。
- `RuleCore.UseActiveAbility` → `CanStartActiveAbility`（`RuleCore.cs:15346`）：`if (u.Exhausted) return RuleCodes.ErrExhausted;`（`ErrExhausted = 6`，`RuleCodes.cs:21`）。
- ④ 已经把单位「用掉本回合那一次行动」⇒ ④b 的这一发**本就应该**被拒。

**原版判据**（`d:/2/tools/decomp_full/`，逐文件现读）：
- `BattleManager__CanUseActiveAbility.c:46-93`：读 `param_2 + 0x230`（`canAct`）→ `op_Implicit(&local_48,0)`；`canAct` 假 ⇒ 直接 `return 0`（拒）。⇒ 原版**真的**用 `canAct` 挡主动能力。
- `CardScript__UsedActiveAbility.c:20`：`if (非 oath) *(param_1 + 0x48) = *(param_1 + 0x48) + 1;`（+0x48 = `AttacksThisTurn`）。
- `CardScript__ActivateMinion.c:14-42`：`canAct` 由 `+0x48`（`≠0` 且无 `0xdc` 或 `≠1` ⇒ false）+ `+0x58`（召唤病）+ trait 派生。
- `BattleManager__FinishResolvingAction.c:105/115` → `MinionManager__ActivateMinions`（每个动作收尾都重算 `canAct`）。

⇒ 一个单位用掉动作（`AttacksThisTurn` 增）之后，`canAct=false`，第二次主动能力被拒——**现在 `aa=6` 与原版一致**；旧基线 `aa=0`（放行）是陈旧/错误值（与调用方已结案的「旧基线 exhausted 陈旧」同一族）。

**残余（见 §三）**：`BattleManager__ResolveTriggerPray.c`（pray 那个动作 `ResolveAction.c:7416` 的 `case 0x52`）**本身不写** `+0x48`/`+0x4C`，只 `RawCardScript__OnTrigger(…,0x28f=655,…)` 再 `FinishResolvingAction`。所以「pray 消耗动作」这一步在反编译里是**间接**成立的（走主动能力那条 `_ResolvePlayActiveAbility` → `UsedActiveAbility` 的 +0x48++），不是在 pray 解析本身里。

### 一·二 ASH63 / ASH80 / SAU6（同一根因：翻成残骸）

**差异是**（`playcheck_after_remfix.txt` ①-b，三张完全相同）：
- `atkCount`：旧基线 `‖`（空）→ 现在 `P0[2]=1 ‖`；
- `exhausted`：旧基线 `P0[2]=1 ‖`；**改前版（12:26）**是 `‖`（空）；现在回到 `P0[2]=1 ‖`。
- 而 `steps` **两版逐字相同**，其中就有 `kill=0@2M`（槽 2 = 被测单位出手击杀）⇒ 槽 2 明明出过手，旧读数却 `atkCount` 空 = 自相矛盾。

**根因 = 被测单位在电池里翻成了残骸**（不是「预扣不退还」）：

1. **36/38 张 `atkCount` 变动的卡都是 Waystone/Remnant 单位** —— 我把 `playcheck_b97sor69.txt` ①-b 里所有带 `· atkCount` 的卡抽出来对 `cards_engine.json`：**38 张里 36 张**关键词含 `Waystone` 或 `Remnant`（`ASH5/6/7/8/11/12/13/15/17/19/23/62/63/69/70/75/77/78/79/80` ＋ `SAU2/3/4/5/6/7/9/10/12/14/15/17/18/20/67/69`）；唯一两张例外是 `EC53` / `GOF47`（`tactic` 型，属另一族，不在本任务）。这个**36/36 的族相关**不可能用「预扣不退还」解释（那与阵营/关键词无关），只能用「残骸路径」解释。
2. **实跑证明这三张在尾部已经是残骸**：`play <id> preset selfdies=1` 里第 ⑦ 步 `HurtWithSourceForTest(自己, 999)` 之后，`Aftermath` 对**活着的 Waystone** 会给 `rem`（同实例翻成残骸），对**已经是残骸**的给 `gone`（残骸再死就离场、不再翻）。实测：
   - `ASH63 / ASH80 / SAU6` → `selfDies=999/`**`gone`** ⇒ 它们在 ⑦ 那一步**已经是残骸**（不是活单位）。
   - 对照 `SOR69`（无 Waystone/Remnant）→ `selfDies=skip(dead)` ⇒ 它早就死了（gone，无残骸），所以 `atkCount` 空是正常的（`‖`，两版都空，不在本差异里）。
   （`Aftermath` 判据 → `工具/ruleprobe/PlayProbe.cs:2852`：`ReferenceEquals→live` / `同Instance且IsRemnant→rem` / 否则 `gone`。）
3. **改前为什么空**：残骸是**新造的 `UnitState`**（`RuleCore.cs:9871 var rem = new UnitState(u.Instance, false){…}`）。改前它的初始化**没搬** `AttacksThisTurn`/`SummonSickness` ⇒ 残骸 `AttacksThisTurn=0` ⇒ ① `atkCount` 读 `AttacksThisTurn` 读到 0（空）；② 每个动作收尾的 `RecomputeActAndAttack`（`RuleCore.cs:3545-3547`：`actedOut = AttacksThisTurn >= ActionQuota; Exhausted = displaySummonSickness || actedOut`）算出 `canAct=true` ⇒ 把残骸初始化时的 `Exhausted=true`（`RuleCore.cs:9884`）**冲掉** ⇒ `exhausted` 也变空。这正是 remfix 注释里写的那句「不搬则残骸被算成 `canAct=true`（旧账的 `Exhausted=true` 被冲掉）」。

**原版判据**：
- `D:/2/tools/decomp_full/CardScript__TransformIntoRemnant.c`（全文 84 行）**只有一处写**：`:29 *(undefined2 *)(param_1 + 0x65) = 1;`（残骸标志）。**不碰 `+0x228`(cardState)、不碰 `+0x48`(AttacksThisTurn)、不碰 `+0x58`(SummonSickness)`** —— 残骸是**同一个 `CardScript` 对象**，这些值原样保留。
- `CardScript__ActivateMinion.c:14-42` 每动作后重算 `canAct` 时读的正是 `+0x48`/`+0x58` ⇒ 原版残骸**保留** `AttacksThisTurn`，所以原版 `atkCount` 是非空的。
- ⇒ `RuleCore.cs:9881` 那句 `PlayOrder = …, DeployedTurn = …, `**`AttacksThisTurn = u.AttacksThisTurn, SummonSickness = u.SummonSickness`**「把这两个搬过去」**正是照原版**；现在 `atkCount=P0[2]=1`、`exhausted=P0[2]=1` 与原版一致。

**结论**：这三张**不是回归**，是**此前我们实现的一个真缺陷**（残骸丢 `AttacksThisTurn`/`SummonSickness`）被 2026-10-29 的 remfix 修好了。「终局那个实例是不是出手那个」→ **是同一个 Instance（`u.Instance` 原样沿用），只是翻成了残骸（`IsRemnant=true`）的新 `UnitState`**。所以「自相矛盾」的旧读数（出手了但 `atkCount` 空）本身就是那个缺陷的症状，现在消失了。

## 二 若判「回归」：最小修法

## 三 没查清的部分

1. **SOR69「pray 是否消耗本回合那一次行动」—— 只到间接，未端到端闭合。**
   - 间接成立的一面：`CanUseActiveAbility.c:46-93` 用 `canAct` 挡主动能力；`UsedActiveAbility.c:20`（`+0x48++`）是「用主动能力」那条 `_ResolvePlayActiveAbility` 协程调的（`BattleManager._ResolvePlayActiveAbility_d__479__MoveNext.c`）；SOR69 `hasActiveAbility=1`，其主动能力会触发一次 pray（`aa` 后 `pray1`）。
   - 反证的一面：pray 的**解析**（`BattleManager__ResolveTriggerPray.c`，被 `ResolveAction.c:7416` 的 `case 0x52` 调）**只**发 `OnTrigger(655)` + `FinishResolvingAction`，**不写** `+0x48`/`+0x4C`；而替代动作的 `CardScript__ResolveActiveAbilityPlayed.c:29-30` 写的是 `+0x50++`/`+0x4C=1`（**也不是 `+0x48`**）。`ActivateMinion` 的 `canAct` 只吃 `+0x48`/`+0x58` ⇒ **如果 pray 走的不是主动能力协程、而只是 `case 0x52`**，那原版**不会**因 pray 而 `canAct=false`，`aa` 在原版里**会成功**，那么旧基线 `aa=0` 反而是对的、现在 `aa=6` 是回归。
   - **没法在本机闭合的原因**：要判定原版「先 pray 再用主动能力」到底可不可行，只能进原版实测（原版已关服，进不去；本地反编译只到上面这些，`Case 0x52` 的入队点/是否先经 `_ResolvePlayActiveAbility` 没能从 `decomp_full` 里唯一定到）。⇒ **这一条如实标「查不到」，倾向判「旧基线错」是基于 `hasActiveAbility=1`＋`canAct` 闸＋我方 `UseAlternativeCore` 建模，不是逐跳坐实。**

2. **ASH63/ASH80/SAU6 的「残骸是哪一步翻的」没逐卡钉死。** 已证明它们在电池尾部**是残骸**（③ 的 `selfDies=999/gone`），但具体在 `selfChip`／`softAtk`／⑤ 攻击的反伤／⑥ `kill` 哪一步死的，没有逐步快照（探针 `PrintEvents` 不打印电池终局棋盘）。不影响判定（36/38 Waystone·Remnant 关联＋`gone` 已足够），但如实标着。

3. **`EC53` / `GOF47`（`tactic` 型，也在 `atkCount` 变动名单里）不属于本任务的 4 张**，未查。它们没有「被测格」、不走残骸，属另一族（大概率 `BroadcastActivateMinions` 重算那一族）。
