## 一 · 多组 `605` 的「先算后贴」取哪个目标？

**原版结论：逐组各发一条，每组用【自己那条 abilityLogic 的 targetCriteria】算目标；组内按目标逐个播。不是「取某一组」也不是「取整卡第一个目标」。**

| 场景 | 目标怎么取 | 证据（`d:/2/tools/decomp_full/`） |
|---|---|---|
| 一张卡有多组 605 | 外层遍历 `cardAbilities`，**每条独立**过 `CanTriggerAbility`，通过就 `TriggerAbility` ⇒ **每组一条** | `RawCardScript__TriggerAbilities.c:59`（`while (lVar2 = *(card+0x110))` 遍历）· `:66-67` 取项 · `:207` 闸 · `:231` 触发 |
| 605 的门槛 | `GetCurrentFaith >= ability.triggerValue(+0x20)`，且 `thisCard == actingCard` | `CardAbility__CanTriggerAbility.c:113-129`（`param_2 == 0x25d` 支 → `:127` `iVar2 < *(param_1+0x20) ⇒ return 0`） |
| 每条 ability 的正文 | `AbilityData.SetNewData(thisCard, actingCard, targetCard, …)` → `PlayAbility` | `RawCardScript__TriggerAbility.c:31` |
| 一条 ability 有多条 logic | `ability.randomAbilityChoice(+0x48)` 为真且 `logic.Count > 1` ⇒ `GetRandomInt` **抽一条**播放后 return；否则**逐条**播放 | `RawCardScript__TriggerAbility.c:75`（读 `+0x48`）· `:82-90`（抽一条）· `:100-103`（逐条） |

| 组内多目标 | **逐目标** `GetPos` + `AddCardAnim`（一个目标一份动画） | `AbilityLogic__PlayAnim.c:178`（逐个目标循环）· `:194/203/215`（GetPos）· `:232`（AddCardAnim） |

- 605 的生产点（战术路）：`RawCardScript__OnCardPlayedWithTarget.c:59-84`（`:66` 600 → `:73` 605，只对 `cardType ∈ {0x14 Tactic, 0x28 Whispers}`）。单位路：`CardScript__ResolveUnitSummoned.c:51`。

### 我们该改哪（「先算后贴」helper 的落点）

1. **不要动 `EmitAbilityUseTrigger`/`EmitFaithAbilityUseTriggers` 的发射时机**（`EffectResolver.cs:8652-8674`），它现在是「结算完再发」；改到结算前会改 `ctx.Signals` 顺序。
2. 在 **`FaithAbilityDeferred`**（`EffectResolver.cs:9485`，605 组结算体）里加一个**逐组**的 helper：
   - **切组** = 与 `ChargePaidGroups` **同一份判据**（`EffectResolver.cs:709-750`）：组首 = `Cost > 0 && !CostShared`，组体 = 紧随的一串 `Cost > 0 && CostShared`（`FaithOps` 里只存带 cost 的 op ⇒ 每个付费组自己就是可结算切片）。
   - 对第 i 组：`var scratch = new BattleEvent{Kind=EvtKind.Trigger, …}` → `ResolveWithTriggerTargetSink(ctx, scratch, () => ResolveOps(ctx, owner, unit, groupOps, "信仰能力"))`（helper 在 `EffectResolver.cs:20984`）→ 结算完调 `EmitAbilityUseTrigger(..., abilityIndex: idx[i])` → 把 `scratch.TargetPlayer/TargetSlot/TargetCardId` 抄进真事件（`NoteTriggerTargetSink` 只写这三格，`EffectResolver.cs:1415-1424`）。
   - 单组卡（23/26 张）必须逐字节等价：仍只发一条、`AbilityIndex = -1`（保持 `CardDef.FaithAbilityGroupCount < 2` 那一支）。
3. **单位侧 600**：`SpiritAbilityDeferred`（`EffectResolver.cs:9311-9318`）同一个 helper 包一次 `ResolveOps` 即可（单组）。
4. **战术侧 605/600**：`PlayTacticBodyDeferred` 里 `EmitTacticAbilityUseTriggers` 的调用在 `ResolveOps` 之后（`EffectResolver.cs:2870`，`ResolveOps` 在该函数靠前）。同理：按 `ChargePaidGroups` 的组切片，逐组 arm scratch + 结算 + 抄目标；`spirit` 那一半（`:8626`）单组。
5. ⛔ 别在 `FireTriggerDeferred`（`RuleCore.cs:12913`）统一改 —— 那是关键词触发族（本题是 605/600 ability-use），两条路判据不同。

### 还差什么

- **组内多目标**：我们 `BattleEvent` 只有一套 `Target*` 标量（`BattleContext.cs:1092`）⇒ 只能取该组**第一个**目标（既有口径，`NoteTriggerTargetSink` 的判据 ①）。原版是每个目标一份动画 ⟹ 这是**已知的结构差**，不在本 helper 能解决的范围内。
- **`NoteTriggerTargetSink` 会跳过「就是施放者自己」的目标**（判据 ②，`:1419`）。对 605 的「目标 = 自己」（如 `ASH24`「Gain Armour 2」）⇒ 事件 `Target*` 留空；但 `EmitAbilityUseTrigger` 已经带了施放单位的 `Player/Slot`，表现层仍落在自己身上 ⇒ **可接受**，需在断言里钉住「Target 空 + Slot = 自己」。
- 战术侧 `EmitTacticAbilityUseTriggers` 现在拿的是 `ops`（整条正文）+ `paidFlags`（`EffectResolver.cs:8604-8630`）：切组后「哪几条 op 属于哪一组」只有 cost 前缀可判；**无 cost 的正文**（如 SOR56 的「Give +2 Health to your units」）不属于任何 605 组 ⇒ 不进任何组的 sink（原版它也不在 605 的 ability 里，正确）。

## 二 · `opt 8` 与 `healthValueOptions 17` 的语义

**原版结论：两者都不是 `ChooseValueOptions` 的成员（26 档无 8/17），原版代码对它们走各自的「未知值」兜底，而且两条兜底不同：**
- `opt 8`（`DamageCriteria.valueOptions`）：**返回 `minDamage`（在 value 层不掷骰）**；区间由 **`DamageType.Random(5)`** 在受伤那一步掷。净效果 = `minDamage..maxDamage` 均匀随机。
- `healthValueOptions 17`（`CardEffect.healthValueOptions`）：**打一条日志后返回原始 `healthChange`，且不乘 multiplier**（≠ `Normal(0)`，0 会乘）。

| 事实 | 证据 |
|---|---|
| 枚举 26 档无 8/17 | `cpp2il/out_cpp2il_dev_ilspy/ChooseValueOptions.cs:1-29`（同 `Warpforge_code/Scripts/Assembly-CSharp/ChooseValueOptions.cs`） |
| `GetValueFromCriteria` 对 `< 0xb` 的非 0/10 一律 `return minValue`（8 落这里） | `AbilityLogic__GetValueFromCriteria.c:37`（`< 0xb`）· `:46-47`（`param_7 != 10 ⇒ return uVar6`）· 其它未知值同形出口 `:75/84/114/131/134/141/165/178/196/203/224/330/364` |
| `DamageType.Random` 才是「区间随机」那一跳 | `CardScript__GetAdjustedDamage.c:22-27`（`damageType < 0xd` 且位掩码 `0x1420` 命中 ⇒ `GetRandomInt(damageValue(+0x18), secondaryValue(+0x20)+1)`）；`0x1420` = bit5 Random / bit10 RandomPoison / bit12 RandomAbility |
| `secondaryValue` = `maxDamage` | `AbilityLogic__PlayAbility.c:1483-1489`（`DamageInfo(actingCard, GetValueFromCriteria(min,max), damageType, maxDamage, …)`） |
| `NewBuffStat` 对未知档（17）走 default：`Log("NewBuffStat behaviour undefined for valueOption N")` + **返回 `minValue`（不乘 multiplier）** | `AbilityLogic__NewBuffStat.c:271-279`（`:277` 日志 · `:279` `return param_4`） |
| 对照：`Normal(0)` 返回 `minValue × multiplier` | `AbilityLogic__NewBuffStat.c:64-68`（`uVar10 = (param_4 != 0) ? param_4 * param_6 : param_6`；`:66-68` `param_3 == 0 ⇒ param_4 = param_4 * param_6`） |
| AI 评分口径对未知档取**区间均值** | `AbilityLogic.GetAverageValue` 的 `default:`（`cpp2il/.../AbilityLogic.cs:2955-2965`，`(min+max)*0.5` 取整） |
| 数据规模（现读 `cards_truth.json`） | `valueOptions == 8`：**38 行 / 24 卡**，`damageType` 全 = 5（Random），min/max 分布 `3-5`×31 · `1-2`×3 · `1-3`×2 · `2-4`×1 · `0-10`×1。`healthValueOptions == 17`：**8 行 / 5 卡**（Attack Squig · Cloud of Smoke · Gretchin Mob · Grot Bomb · Scrag 'Em），有值的 `healthChange = 3` |

**关键反例（钉死 17 ≠ 0）**：`Gretchin Mob` 的 `abilityMultipliers` = `fm:[3]`（`cards_engine.json` 现读）。原版 opt 17 走 default ⇒ **+3**；若当 0 处理 ⇒ **+9**。

### 我们该改哪

1. `opt 8`：**保持现状**（`EffectResolverPartial_B141VO.cs:74-84` 已把它排除在 26 档表外）。我们的伤害路 `DoDeal` 在 `AmountMax > Amount` 时掷 `[Amount, AmountMax]`（`EffectResolver.cs:3102`），而伤害 op 的 Amount/AmountMax 来自正文「Deal 1-2」⇒ 与原版 opt-8 的净效果**一致**。⚠️ 别把它送进 `default => min`：那会把 min 同时写进 Amount/AmountMax（`EffectResolver.cs:21739` 那种折法）⇒ 区间丢失。
2. `healthValueOptions 17`：**不用改** —— `FoldBuffStatValueOptions` 只折 80、其余原样（`EffectResolverPartial_B97W2.cs:840-846`，`FoldOneBuffStat` 的 `if (opt != 80) return raw;`）⇒ 17 已经是「原始 healthChange、不乘 fm」= 原版 default。⛔ 别按 0 补乘。
3. 建议把 `B141VO` 文件头「❓ 语义来源未查清」与本条对齐（结论已查清：**代码层兜底已定死**，见上表）。

### 还差什么

- 「8/17 是不是**更早版本枚举**的成员 / 数据残留」——**没有旧版 metadata 可查**（搜过 `d:/2/Warpforge_code/Scripts/Assembly-CSharp/` 当前 build 桩、`cpp2il/out_cpp2il_dev_ilspy/`、`decomp_full`）。但当前 build 的行为已由 `.c` 定死，**不影响落地**。

## 三 · 20/240（WhileInPlay / WhileInPlayVariable）正文 op 的 `FxOps` 键

**原版结论：原版没有「正文层 vs 光环层」两套数据 —— 只有一套 abilityLogic 正文；「光环」是 `extrinsic` 标记 + 每个动作边界重跑同一份正文的结果。20 与 240 走同一条路，差别只有两个标志位和 240 的「闸不过就摘掉」。**

| 事实 | 证据 |
|---|---|
| 每个动作收尾广播一次：场上逐张 + 双方手牌逐张，`IsInPlay` 且 `HasWhileInPlayAbility` ⇒ `UpdateWhileInPlay` | `BattleManagerSupport__BroadcastWhileInPlay.c:22-44`（场上）· `:45-80`（手牌）；调用点 `BattleManager__FinishResolvingAction.c:91` |
| `RawCardScript.UpdateWhileInPlay` **连发 20 与 240 两档** | `RawCardScript__UpdateWhileInPlay.c:13`（`TriggerAbilities(0x14=20)`）· `:16`（`0xf0=240`） |
| 两档都进同一个 `TriggerAbilities → TriggerAbility → PlayAbility`（= 正文） | `RawCardScript__TriggerAbilities.c:59/207/231` · `RawCardScript__TriggerAbility.c:31/100-103` |
| `extrinsic` / `extrinsicVariable` 真实来源 | `AbilityLogic__PlayAbility.c:1193-1196`：`effect.extrinsic(+0x30) = whileInPlay(+0x40) ∨ whileInPlayVariable(+0x41)`；`:1196` `extrinsicVariable(+0x31) = whileInPlayVariable` |
| 两个标志位由 trigger id 置位 | `RawCardScript__TriggerAbility.c:36`（trigger 0x14 ⇒ `+0x40 = 1`）· `:40`（0xf0 ⇒ `+0x41 = 1`） |

| 我们的覆盖现状 | `CardDef.cs:6170-6180`：20 族 13 卡 19 段里 **11 段**被 `Auras.TryParse` 收下；240 族 33 卡 42 段里 **27 段**；其余是印刷关键词或同卡其它 trigger 的一次性效果 |

### 键名 / 触发名在原版怎么拼

- 原版只有**整数 trigger**（20 / 240）与枚举名 `AbilityTrigger.WhileInPlay` / `WhileInPlayVariable`；**没有字符串键**。
- 我们的约定：`FireTriggerAt` 用**小写关键词串**取正文（`RuleCore.cs:12716` `u.FxOps(keyword)`），再把它翻成原版枚举名（`RuleCore.cs:12841` `_kwTriggerName = TriggerNameOfKeyword(keyword)` → `ActionPump.cs:1081` 的 switch → `default` 转 `ExtraTriggerName`，`ActionPump.cs:1894-1912`）。
- `CardDef` 的名字表里**两条都已在**：`{"WhileInPlay", 20}`（`CardDef.cs:1918`）· `{"WhileInPlayVariable", 240}`（`:1927`）⇒ 只差「小写关键词 → 名字」这一跳。
- `ExtraTriggerName` 现读 8 条（`:1906-1911`）：`SpentAllMana` · `Courtesy` · `Relentless` · `TriggerOnceIfBoardCriteria` · `Requiem` · `Backlash` · `Penitence`；`:1912` `return null;`。

**该补的两条（加在 `ActionPump.cs:1912` 之前，同一行内追加 = 零行数变化）：**

```csharp
if (keyword == "whileinplay") return "WhileInPlay";                 // 20
if (keyword == "whileinplayvariable") return "WhileInPlayVariable"; // 240
```

键名字符串固定为 **`"whileinplay"` / `"whileinplayvariable"`**（小写，与 `u.FxOps(keyword)` 的键空间一致；⛔ 别在 `TriggerNameOfKeyword` 的 switch 里加 `case` —— 那会插行导致账漂移）。

### 链路自证 —— ⚠️ **只补两条映射【不会】让 `DoGive` 在这两族被调用**

正向链（补完映射后）：`FireTriggerAt(u, "whileinplay")` → `u.FxOps("whileinplay")`（`RuleCore.cs:12716`）→ 非空才入队 `FireTriggerDeferred`（`RuleCore.cs:12750` 的空闸）→ 入队时 `_kwTriggerName = "WhileInPlay"`（`:12841`）→ `AbilityContextOfAbilityV14` / `abilityTrigger` 那道闸有名字可判（`:12897`）→ 队列体 `ResolveOps`（`:12932`）→ `DoGive`（`EffectResolver.cs:11916`）→ `AddEffectCasterGates(..., extrinsic: ctx.ResolvingExtrinsic)`。

**断点（决定性）**：全仓没有任何地方给 `_triggerOps` 挂 `"whileinplay"` / `"whileinplayvariable"` 键。
- `CollectTriggerOps`（`CardDef.cs:3722`）只从：① `desc` 的 `<正文关键词>:` 头（`TriggerBodyAt`）② `keywords` 带前缀的条目 ⑤ **裸写正文**（`CollectBareKeywordBody`，`CardDef.cs:3863`；要求该词在 `_keywords` 里且 `IsBodyKeyword`）。
- 而 20/240 的卡：卡面**不写** `WhileInPlay:`（现扫 1,142 张 `desc` 中 `"whileinplay"` = **0**），`keywords` 里也没有这个词（样本：`Winged Autarch` = `Waystone/Flying`、`Baneblade Tank` = `Armour 2/Duty`）；它们的光环句只被 `CollectAuras`（`CardDef.cs:4445`）收进 `AuraSpecs`，**不进 `_triggerOps`**。
- ⇒ `u.FxOps("whileinplay")` 恒 `null` ⇒ `FireTriggerAt` 在 `RuleCore.cs:12750` `return false`，`DoGive` **一次都不会被调用**（这就是 R3 报的「净可观测 = 0」）。

**要真让 `DoGive` 被调用，还差一个「正文 op 供给」**，两条可选（都需要调度台裁结构）：
- (a) 在 `CollectAuras` 收下某段的同时，把同一段也注册进 `_triggerOps[键]`（键按这张卡 `abilityTriggers` 里实际有的 id 选；两个 id 都有时按 ability 行分不出来 ⇒ **出声、不猜**）。
- (b) 走数据路：让 `MapTriggerOpsByNumber`（`Data/CardDatabasePartial_B98H7.cs:129-200`；它的 `body` 只从 `RoutableTriggers` 拼，`:141-160`）能为 20/240 产出 op，然后用 `FireTriggerByNumber(20/240)` + `ResolveWithTriggerTargetSink` 消费。

**另外，修法①必须同时做**（R3 §四·1）：在 `FireTriggerDeferred` 里按 keyword 置 `ctx.ResolvingExtrinsic = true`：
```csharp
bool prev = ctx.ResolvingExtrinsic;
if (keyword == "whileinplay" || keyword == "whileinplayvariable") ctx.ResolvingExtrinsic = true;
try { … 原 ResolveOps … } finally { ctx.ResolvingExtrinsic = prev; }
```
否则 `DoGive` 即使被调用，`extrinsic` 仍为 `false` ⇒ `UnitState.Extrinsic` / `IsExtrinsicSource` 标不上，属性在来源离场时**不撤**（静默）。

### 还差什么

- 「46 张 20/240 卡里，有多少张的光环句真能被 `CollectAuras` 收下」只核过 5 张样本（R3 §四·5）⇒ 决定 (a) 的覆盖率，**未逐张核**。
- 「20/240 的正文 op 该不该由文本路产生」= **结构性决策未定**（R3 已标）⇒ 本代理不裁；不接供给这一层，补两条映射的**净可观测仍为 0**，只能附一条纯函数断言（`TriggerNameOfKeyword("whileinplay") == "WhileInPlay"` + `FireTriggerDeferred` 期间 `ResolvingExtrinsic == true`）。
