## 〇 一句话：它和已有的那份 `功能点索引.md` 是什么关系

`资料/完全复刻/功能点索引.md`（**144 条**，2026-10-25 由 `工具/gen_feature_index.py` 生成）**已经在**，
但它**不是第二层账**，三个硬缺口：

| 缺口 | 旧 `功能点索引.md` | 本索引要求 |
|---|---|---|
| **列** | 只有 `功能点 / 主链边角 / 域 / 挂哪些类.方法 / 方法数 / 状态分布 / 最高档 / 备注` | **必须有 `我们的落点`（文件:行）与 `验收口`（断言 / 读数命令）** —— 这两列才是「验收」二字 |
| **等级取法** | **最高档**（A > B > C > D > E）⇒ 该表自己 §5 就写着「『最高档 A』会骗人」 | **最差档**（E > C > B > A，D 中性）⇒ 只有全部构成行都到 `A`/`D` 才能签收 |
| **能否机检** | 不能 —— 手写散文，没有一条断言能自动比 | 五道机检（见 §1.2），`构成条数`/`状态分布`/`等级` **三列由账重算、手写对不上就红** |

⇒ **本索引不替代它**：旧表是「**按域看规模**」的视图（144 行覆盖全部账行，含「（域）其它」兜底行）；
本索引是「**按玩家动作看能不能验收**」的视图。**两者并存**，但**「能不能验收」只认本索引** ——
因为只有本索引带落点和验收口，也只有它取最差档。

## 一 Schema（一张 TSV，一行 = 一个功能点）

### 1.1 十六列

| # | 列 | 填什么 | 约束（机检怎么做） |
|---|---|---|---|

| 3 | `域` | 20 个域名之一（`账/*.tsv` 的 `域` 列现读集合，**不是 18**：另有 `其他/基础设施`、`未分类/其他`） | 必须 ∈ 现读集合 |
| 4 | `优先级` | `P0/P1/P2/P3`（方案 §五 优先级总纲） | 闭集 |
| 5 | `主链/边角` | `主链` = 玩家一定会走到；`边角` = 次要/低频/纯观感 | 闭集 |
| 6 | `原版构成` | `;` 分隔，三种形状：`类.*`（该类全部账行）· `类.方法`（**同名的所有重载都算进来**）· `类.方法(全签名)`（只要那一个重载） | 每个条目必须能在 `账/*.tsv` 展开成 ≥1 行，否则**失败** |

| 9 | `等级` | 功能点级 = **最差档**；有 `存疑行` 时带 `?` 后缀 | 等于 `worst_of(构成行的状态)`；`?` ⟺ `存疑行` 非空 |
| 10 | `我们的落点` | `;` 分隔的 `路径:行号（声明名）`，**只放声明行** | 文件存在 · 行号不越界 · **该行逐字含那个名字**（沿用方案 §4.1 的落点纪律） |
| 11 | `验收口` | `;` 分隔。两种：`路径:行号（唯一子串）` 或 `cmd:<脚本> <子命令>` | 断言型：**该行逐字含那个子串**；命令型：脚本文件存在 |
| 12 | `跑法` | 怎么把 11 列那些读数跑出来（`bash …` / `Unity -executeMethod X.Y`） | `-executeMethod X.Y` ⇒ `X.cs` 存在且含 `void Y(` |

| 14 | `存疑行` | `账文件:行号（一句话为什么存疑）`，无则 `—` | 该账行存在；非空则 `等级` 必须带 `?` |
| 15 | `轮次` | `R5` / `R6` … | 非空 |
| 16 | `备注` | 边界、口径、与旧索引的差别 | 自由 |

### 1.2 三个决定性的设计选择（为什么不能换）

**(a) `等级` 取【最差档】而不是最高档 —— 这是第二层存在的理由。**
`A` 的定义（方案 §4.1）是「逐条对过、行为一致」；一个功能点只要还有一条 `C`（该做没做）或 `B`（没核完），
就**不能签收**。旧表取最高档 ⇒ 「出牌与目标选择」写 `A`，而它下面挂着 42 条 `B`。
⇒ 本表 `worst_of`：`E > C > B > A`，`D`（原版不适用）**中性**（不影响等级）。
`D` 中性有据：方案 §4.1 里 `D` 也算「复刻完成」。

**(b) `原版构成` 必须**从账里展开**，⛔ 不许直接写类名散文。**
方案 §2.2 说第二层是「类账与玩家视角之间的桥」。桥的两端都要能机检：
6 列的一头落在账行上（可核「这条功能点到底由哪些方法构成」），10/11 列的一头落在源码上。
⇒ 「构成条数」「状态分布」**不是人写的**，是账算出来的 —— 人改了构成，三列自动跟着变（脚本重算时）。

**(c) `验收口` 必须是 `文件:行（唯一子串）`，⛔ 不能只写断言代号。**
实测：`CardPresentation/Editor/BattleScene.cs` 里 **3,484** 条 `★` 断言，而代号**不唯一** ——
`★ A964/` 出现 **52** 次、`★ W63/` 35 次。只写「A964」等于没写。
⇒ 格式与方案 §4.1 的落点纪律同源：**行号 + 逐字子串**，这样断言被挪走/改文案时**能被机检抓到**。

> 🔴 **`验收口` ≠ `判据`（这一条不写清，第二层就变成自证）**：
> `判据出处` = **原版怎么做的**（反编译 / 解包字段）；`验收口` = **我们怎么发现「自己改坏了」**（我们的断言 / 我们的探针读数）。
> 方案 §一.2 明写判据不许来自我们自己。所以：**`验收口` 只用来挡回归，⛔ 永远不能当「复刻对了」的证据。**

### 1.3 一条硬规矩：**一行账只能有一个 primary owner**

一个方法可能服务多个功能点（`Auras.Recompose` 既服务「光环重算」也服务「召唤」），
但**分母要干净 ⇒ 每行只归一个功能点**；别的功能点要引用它，写进 `备注`（`交叉引用 = FP-xxx`），⛔ 不复制条目。
机检会把「被 ≥2 个功能点认领」的行列成告警（`多认领`）。

### 2.1 `FP-PLAY-01` 出牌结算

- **构成怎么挑的**：从「手牌打出去」这件事**顺着入口走一遍**，五个环节各取一个原版入口：
  合法性总闸 → 面朝下那一支 → 能力结算 → 效果入队 → 手牌效果核销。
  不是「把所有含 Play 的方法都抓来」—— 那样会把 `AddPlayFromHand` / `AddAutoPlayFromHand` 那类
  **自动打牌**的入口也吸进来，它们属于另一个功能点。
- **为什么是 B 不是 A**：`CanPlayCard` 返回 `int` 错误码、原版返回 `CustomError` 枚举 ⇒ **逐码对表没做**；
  `AbilityLogic.PlayAbility` 2,878 行只读到 `:308/:324/:668`。
- **`存疑行` 抓到一处真漂移**（⛔ 本代理不改账，交调度台）：
  `战斗逻辑驱动.tsv:233` 写着落点 `RuleCore.cs:3235（CanPlayCard）`，
  而 **3235 现读是 `EnforceHandLimit` 的注释行**，真声明在 **`RuleCore.cs:3273`**。
  ⇒ 这条账行**过不了落点闸**（`check_ledger_points` 会判「像注释行 = 失败」）。
- **验收口怎么选的**：
  · `cmd:工具/ruleprobe.sh play check` = **结算层全池指纹**（引擎侧最硬的一根针，任何结算变化都改指纹）；
  · `RuleEngineTest_BoardModel.cs:56`「每侧仍然连续无洞」= 落位不变量（放牌的落点是「插入推人」模型，方案外但见 MEMORY `warpforge-board-contiguous-model`）；
  · 两条 `★` 断言：错误码映射 / 「打出去的是原样搬一份、不是新造一份」（后者是**灭自证型**判别式）。

### 2.2 `FP-AURA-01` 光环与 WhileInPlay 重算

- **构成**：原版这一机制**没有单一入口** —— 它是「**摘掉重加**」撒在四个类上的一族方法
  （`CardScript` 摘／查，`BattleManager`／`BattleManagerSupport` 广播与重挂，`EntityScript` 查附魔状态）。
  ⇒ 这正是第二层要解决的形状：**一个功能点 ≠ 一个方法**。
- **为什么 `C`**：唯一 C = `BattleManagerSupport.BroadcastWhileInPlay`（P1）。残余两条写死在该账行里：
  ① **手牌那半没扫**（原版对双方手牌也逐张触发，我们只做全场重算）；
  ② **基线待重钉**。⚠️ 它**不是**「整体没做」—— 接线在 `ActionPump.cs:143` 在位。
- **`存疑行` 的作用**：把「C 是因为没做」和「C 是因为一条可辩护的残余」分开 —— 带 `?` 之后，
  这两个比率的分子不会把它算成 A，但人一眼能看出该不该先修它。
- **验收口为什么必须有 `play check`**：`★ 光环机制账` 那条断言只证明「认下来的光环都有消费分支」，
  **不证明重算时机与原版一致**（这正是 2026-10-25 那次「幂等 ≠ 无副作用」踩到的形状）。

### 2.3 `FP-FACE-01` 卡面装配与渲染

- **构成用 `类.*` 的场合**：卡面是「一个类一族方法」的典型（`Card2DController` 11 · `CardTextsController` 11 ·
  `CardTextCountersController` 12 · `CardHighlight` 10 · `BoardTraitIcon` 9 · `CardImageController` 9 · `UICardInfoItem` 9）。
  逐个列名会写出 71 个 token、且每次账改动都要跟着改 ⇒ 用 `类.*`。
- **为什么 `C`**：唯一 C = `CardImageController.ToggleMask`，而该账行的 `差异` 列自己写着
  「`ToggleMask` private ＋ 全库 0 调用点（死代码）；**同一套 SoftMask 体系的活路在 `ChangeState(Big)`**」
  ⇒ 这行**疑似该判 `D`**。已进 `存疑行`，⛔ 不越权改账。
- 🔴 **这就是第二层的价值**：旧 `功能点索引.md` 的同名行写「A64 · C10 · D11 / **最高档 A**」——
  一个带着 10 条 C 的功能点在旧表里显示 `A`；本表显示 `C?`。
- **部分覆盖必须写明**：本行认领 `卡牌面/渲染` 域 **71/167** 行，其余 96 行属别的功能点
  （插图服务 / 卡框 SO / 战役环境条件 / 词条说明 UI…）。⛔ 不写这句就等于宣称「整域已覆盖」。

### 3.2 每块给代理什么（简报必须自包含，八件套之外再加四样）

1. **`--manifest` 里自己那一行**（域 + 行数 + 在哪些文件）—— ⛔ 别让它自己 `find`。
2. **该域在账里的全部行号清单**：`grep -n "" 账/<域>.tsv` 不行（一份文件里有多个域）——
   用 `check_ledger_points.py` 同款读法，或直接给 `域\t行号` 清单（原型脚本能打印）。
3. **该域的「我们的落点」候选目录**：方案 **附录 A** 那张表逐域写了（例：战斗逻辑驱动 = `RuleEngine/Core/**` + `RuleEngine/Data/**` + `Battle/BattleDriver.cs`）。
4. **该域的验收宿主**（见 3.1 最后一列）—— 这一列不给人，代理就会随手编一个断言名。

简报里必须写死的三条（否则一定拿回散文）：
- **⛔ 不许改账**（第一层账是另一批代理的写手在改）；只写自己那块 `<域>_part.tsv`。
- **⛔ `原版构成` 只许抄账里已有的 `类.方法`**，抄不到就写 `备注 = 账未覆盖` 并在报告里点名 —— ⛔ 不许自己加方法。
- **⛔ 判据出处只许原版**（`decomp_full/` `cpp2il/` `assets_full/`）；指向我们代码的一律红。

### 3.3 防撞车（沿用方案 §六.2 + 账补丁那套）

- **写手 = 文件**：每块只写 `资料/完全复刻/判据/功能点索引_<块>_part.tsv`（16 列同构）。
  **主表只有调度台在合并时写**（与 `账/_parts/` 完全一样的纪律）。
- **不撞的机制 = `功能点ID` 前缀**：`FP-<块>-NNN`（K1 → `FP-K1-001`），跨块天然不重号。
- **重叠区先定归属**：同一行账只能被一块认领。跨块的类（`Auras.Recompose` 服务战斗与特效）在
  **派活时就把「这一行归谁」写进两份简报**（⛔ 别让代理自己判 —— 它们看不见对方）。

## 四 两个比率怎么从这张表算（复用方案 §2.4 的口径）

| 比率 | 在功能点层怎么算 | 注意 |
|---|---|---|
| `(A+D)/总` | `count(等级 ∈ {A,D}) / 功能点总数` | `D` 中性、`?` 不改变等级（只在人读时提示） |
| **真复刻率 `A/(A+B+C)`** | `count(等级 == A) / count(等级 ∈ {A,B,C})` | 分母**剔除 `D`**（原版不适用不该进分母），这是「真」字的来源 |

⚠️ 两层比率**不能互相换算**：方法级 `A` 多不代表功能点级 `A` 多（一个功能点挂 71 行，一行掉档整条掉档）。
⇒ 引用时**必须写清是哪一层**（方案 §2.4 那张表是**方法级**）。

## 五 这套索引**答不了**什么（边界，⛔ 别拿它当验收通过）

1. **答不了「复刻对了没有」** —— 它只回答「这件事由哪些原版方法构成、我们在哪实现、改坏了哪个读数会红」。
   正确性只认方案 §八 的三法（判据签收 / oracle / 并排比）。
2. **`验收口` 是我们的断言 ⇒ 天然自证** —— 断言只挡回归，不证明与原版一致。方案 §一.2 那条红线在这儿最容易破。
3. **答不了「账里没有的东西」** —— 功能点是从账里长出来的；账没覆盖的方法不会凭空出现。
   ⛔ 因此「索引 100% 认领」只等于「**账里每一行都有归属**」，不等于「原版每个行为都进了账」。
   已知账的边界 = 方案 §2.4 那四类 + 第五条「有登记无实物」。
4. **`最差档` 会继承错行** —— 一条账行判错（例：`ToggleMask` 那条死代码判成 C），整个功能点就跟着降档。
   ⇒ 这是 `存疑行` 存在的原因，也意味着：**第二层的可信度上限 = 第一层的可信度**。
5. **答不了时序/手感/观感** —— 「光环什么时候重算」这种「时机」类问题，`play check` 的指纹只能告诉你「变了」，
   不能告诉你「对不对」；那要 oracle 或原版实拍（铁律 3/4）。
6. **答不了跨功能点的相互作用** —— 一行只归一个 owner，所以「出牌 + 光环 + 特效」三者的联合行为没有归属行。
   这类要单独开「组合功能点」，本 schema 未支持（见 §7 待办）。
