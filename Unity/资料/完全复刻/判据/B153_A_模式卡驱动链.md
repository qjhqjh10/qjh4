## 一、结论（先看这 8 行）

1. **模式卡 = 运行时实例化的 prefab**：`Base Game Mode Container 1x1 / 1x2 / 1x1 Claim / 1x2 No Timer / 1x2 Raid or Army Release`，根组件是 **`LiveopMenuContainer`**（`UiContainer<LiveOpsEvent>`）。
2. **挂在主菜单的 `MainMenu/GameModes/Content` 节点下**（`MainMenu Warpforge.unity`：GameModes 节点在 `:920`，Content 在 `:601`，网格 `rows: 2 / columns: 20 / itemSize 535×414.4` 在 `:69500-69502`）。
3. **谁来画**：`MainMenuWindow.RefreshLiveOpContainers()`（`MainMenuWindow.cs:405`）→ `LiveOpsManager.GetEventsForDisplayingInMenu()`（`:2075`）→ 逐条 `InstantiateLiveOp`（`:694`）→ `ContainerBuilder<LiveopMenuContainer>.MakeContainer(event, ContainerRef, anchor)`（`:699`，`ContainerBuilder.cs:76`）。
4. **卡片数据 = `InitializeLiveOps` 云脚本响应里的 `HandlerData`**，不是 `GameModesConfig`、不是本地 SO 扫描。`LiveOpsManager.Unpack(HandlerData)`（`LiveOpsManager.cs`）→ 每个 handler 用 `LiveopsHandlerData.RawEvents` 造事件（`LiveOpsManager._BuildHandler_d__17__MoveNext.c`）→ `events` 列表（`LiveOpsHandler.cs:1323`）→ `GetAllEvents()` 汇总（`LiveOpsManager.cs:1793`）。
5. **筛选条件只有两条**：① `ILiveOps.ShowInMainMenu`；② `EventState ∈ {OnPreview(1), Active(2), Finished(3)}`（`LiveOpsManager.__c___GetEventsForDisplayingInMenu_b__19_0/1`）。对 `IPlayEvent` 还有一层：`PlayEvent.ShowInMainMenu` = `baseData.showInMainMenu && EventState == Active(2)`（`PlayEvent.cs:260`）。
6. **数据为空时**：面板**不隐藏**，`GameModes`（active=1）与 `Content` 保持激活，只是 `Content` 没有子节点 ⇒ 一片空白（正常现象，`MainMenuWindow.RefreshLiveOpContainers` 不会 `SetActive(false)`，也不会 `ToggleScroll(false)`；`ToggleScroll` 全仓只有定义、无调用者）。
7. **本地有没有真实模式卡数据**：**没有**。本地 `assets_full` 里带 `EventComponents` 的 `LiveOpsEventData` 只有 **16 份**（5 ParentEvent / 4 ScoringEvent / 4 ShopOfferEvent / 2 Campaign / 1 RewardsMenu），**一张 PlayEventData（Classic/Skirmish/Draft）都没有**。⇒ 模式卡数据必须自造（属服务器侧，符合铁律 18·0）。
8. **但本地有 2 张真实可上主菜单的 ParentEvent SO**（`ExpansionUM1` / `SWRelease`，`showInMainMenu=1`，且其 `MainMenuContainer` 指向真实可寻址 prefab）。⇒ 想「先用真实素材长出一张卡」有现成材料（见 §五 B 方案）。

### 2·4 反序列化的判别字段（关键）

- `RawEvent`（`RawEvent.cs`）：字段 `Data`（`LiveOpsEventData`）+ `Persistence`（`LiveOpsEventPersistence`）。
- `LiveopsHandlerData`（`LiveopsHandlerData.cs`）：`SharedData`（JObject）+ `RawEvents`（`List<RawEvent>`）。
- **`RawEvent.Data` 是抽象类 ⇒ 必须带 `$type`**：
  - `TypedSerializer.ReadJson`（`TypedSerializer.cs:97`）读 `JObject["$type"]` → `ReflectionHelper.GetTypeFromString`（`ReflectionHelper.cs:511`）→ `Type.GetType(typeName, false, ignoreCase:true)`。
  - 该字段是客户端**自己写出去**的同一个判别串（`SerializationHelper.cs:48` `TYPE_PROPERTY = "$type"`，`WriteJson` 在 `:288` 写 `jObject["$type"]`）。
  - **写法**：`"<完整类名>, Assembly-CSharp"`（`Type.GetType` 认这个；无程序集后缀的同程序集写法也可能成立，但带程序集最稳）。
- 未知字段被忽略；字段名**大小写敏感**（`SerializationHelper.ReadJson` 用 `JObject.TryGetValue(member.Name)`），所以必须用 C# 字段原名。

### 4·1 `SharedData` 为什么不是 `{}`

## 五、`ParentEvents` 与模式卡的关系（可选加分项）

**有关系，但不是模式卡的必要条件**：`GetAllEvents()` 汇总**所有** handler 的事件，所以 `ParentEvents` 里 `showInMainMenu=1` 的事件**也会排进同一行卡片**（同一个 `MainMenuWindow`、同一个 Content、同一个 `Base Game Mode Container`），并且 `ParentEventHandler.BeforeRefresh` 还会顺带刷新左侧导航面板的 Event 页签。它和 `GameModes` 是**并列的两个数据源，不是上下游**。

### 方案 B（用真实素材先长一张卡）

本地确有两份**真实**、且 `showInMainMenu=1` 的 ParentEvent SO：

## 七、可复用的取证脚本（查「某个 prefab 的真实 Addressable GUID」）

```python
# 输入：bundle 名 + GameObject 名（assets_full 里的文件名）
# 输出：该 prefab 在 Addressable catalog 里的真实 GUID
import io, json, os
base = 'bundle_menus_assets_all'          # 换成目标 bundle
name = 'Base Game Mode Container 1x1'
cont = json.load(io.open(f'{base}/AssetBundle/AssetBundle_1.json', encoding='utf-8'))['m_Container']
cmap = { (e[1].get('asset') or {}).get('m_PathID'): e[0] for e in cont }
g = json.load(io.open(f'{base}/GameObject/{name}.json', encoding='utf-8'))
for c in g['m_Component']:
    pid = c['component']['m_PathID']
    mp = f'{base}/MonoBehaviour/MonoBehaviour_{pid}.json'
    if os.path.exists(mp):
        root = json.load(io.open(mp, encoding='utf-8'))['m_GameObject']['m_PathID']
        print(name, '->', cmap.get(root))
        break
```

## 九、顺手发现（与本任务无关但值得记）

1. 🔴 **AssetRipper 导出的 `.meta` GUID 与真实 Addressables GUID 不一致**（抽样扫了 19,174 个 `.meta`，与 `catalog.bin` 的 GUID 集合交集 = **0**）。以前所有「按 .meta 的 guid 去填 AssetReference」的做法都会失败。真实 GUID 只能从 bundle 的 `AssetBundle.m_Container` 反查。
2. `LiveOpsContentPanel.Initialize`（`LiveOpsContentPanel.cs`）是个**未完成的桩**：Ghidra `LiveOpsContentPanel__Initialize.c` 显示它 `new LiveopMenuContainer[0]` → `Log("Loading {0} events")` → **直接 throw**；且全仓没有任何 prefab/scene 引用它。**别把它当模式卡驱动**（名字很像，是个陷阱）。
3. `EventLabel.Args` 为 null 时 `GetLabel` 会抛 `ArgumentNullException`（`LiveOpsAssetUtility.cs:606` 对 null 序列做 `Enumerable.Select`）⇒ 手写事件 JSON 必须给 `"Args": []`。
4. `GameModes.InitializeHandler` 在 `SharedData` 缺 `HighestPosition` 时抛 NRE（被 per-handler 捕获并 `LogError`，不挡登录，但日志会脏）。
5. 三张「专用模式容器」（Draft / Ranked / Skirmish 1x2）在 menus bundle 里**存在但不可寻址**：它们只能是别的 prefab 的嵌套依赖，不能当 `AssetReference` 目标。
6. `MainMenuWindow.ToggleScroll` 全仓无调用者 ⇒ 空列表时滚动条/滚动不会因「没内容」被显式关掉（空态就是空 Content）。
