## 五 启动链判据

### 5.1 `SceneInitializer`（16 条，全 C · P1 为主）

**原版语义（按方法体实读）**：

1. `Awake` 把两个静态钩子指向自己（`OnInitializableQueued = QueueInitializable` / `OnCompletionCallbackRegistered = OnInitializationComplete`）→ `FetchAllInitializables()` → 对预先登记的 `IBeforeInitializationHandler` 先跑一遍 → `StartCoroutine(InitializeBehaviours())`。
2. `FetchAllInitializables`：`FindObjectsOfType<MonoBehaviour>(fetchInactiveBehaviours)` **与**已有 `initializables` 做 `Union`（去空）⇒ 既支持「场景里摆着的」，也支持「代码里先登记的」。
3. `InitializeBehaviours`（协程）：按 `InitializationPriority` 逐组：
   - 日志 `Initializing Group {priority}`
   - `InitializeDefaultBehaviours(group)`：组内 `IInitializable` 逐个调**同步** `Initialize()`
   - `InitializeAsyncBehaviours(group)`：组内 `IInitializableAsync` 逐个 `StartCoroutine(AsyncInitialization(x))`
   - 日志 `Waiting for group {priority} complete Initialization`
   - **等这一组所有 `IInitializationComplete` 完成**（`IsInitializationComplete`）才进下一组
4. 全部组跑完 → `TriggerCompletionCallbacks()`：清空等待表 → 调 `OnComplete`（一次性）。
5. 错误：`OnInitializableError` → `Debug.LogError($"Failed to initialize behaviour: {name}
Error: {msg}

{stack}")` → `status = Error` → **首次**弹本地化窗 `CustomErrors/FailedToInitializeServices`（`{0}` = 组件名）。**不中断**其它件。
6. 运行期新增：`QueueForInitialization` → 若 `Initializing` 中则 `needToRestart = true`；若已 `Initialized` 且 `allowInitializationRestart` → `Restartinitialization()`（日志「Restarting initialization due to new behaviours added」）。

**我们该怎么做**：见 §三 #5 + §四 `SceneInitializer` 段（接口已给）。
**最小落地顺序**（P1，一步就能用）：
① 先只做「优先级 + 同步 `Initialize()` + 完成回调」三件（不做异步/重启）；
② 把 `ShellRuntime.Build()` 里**现在一次建完**的那些件按优先级拆开（壳 → 安全区 → 窗口管理器 → 主菜单）；
③ 补 `IInitializationComplete` 的等待（`MainMenuRuntime` 依赖 `CardDatabase`/`Loc` 就绪）；
④ 异步与重启留到 P2。

**⚠️ 我们当前的缺口**：`ShellRuntime.Build()` 是**同步一把建完**，`PlayerBoot` 只是**命令行调试口**（不是游戏启动链）。所以「原版每个场景第一个脚本」这一层，我们**整个没有**。

## 七 给调度台的顺手发现（不在本账范围，但会影响别人）

1. **账本 `n_nt` 口径与实际方法表有偏差**：`DynamicList<T>` 账本记 12，dump 里非平凡只有 9（账本把 `get_Item` 这类访问器算了进去）；**接口类**账本记 0，但 dump 里有声明方法（本账按「接口声明 = D」补了 24 行）。
   ⇒ 下一轮重跑 `gen_replica_ledger.py` 时，建议把「访问器/事件 add-remove/接口声明」的取舍写进脚本注释，否则 774 这个数每次都会飘。
2. **`PlayEvent.MatchFinished` 把平局记成 `2.0`**（不是 0、不是 1）。这条**极易写错**，且直接决定里程碑推进几格（`FastMode` 的「平局按 2 格推进」也是同一套）。
3. **两条现成的错误文案 key**（我们可直接接）：`MenuDeck/Error/InvalidDeck` · `MenuDeck/Error/HasNotAssignedDefensiveCard`；初始化失败窗的 key = `CustomErrors/FailedToInitializeServices`（带 `{0}` = 组件名）。
4. **`LoginManager.CheckDataLoaded` 会等 Steam**（`SteamManager.Initialized`，每 0.3s 重试并打 `Waiting for Steam to load`）—— 这解释了「普通启动必须先开 Steam」；离线替代不需要这一跳。
5. **`LiveOpsHandler.ScheduleEventPopups` 用 `Dictionary<string, MenuActions.Action>` 去重**：同一活动只排一次弹窗。我们做弹窗排期时必须带这个去重表，否则每次刷新都会重弹。
6. **`SceneInitializer` 的两个静态钩子在「场景没就绪」时会出声**（`LogWarning`「…queue too early」/`LogError`「…register too early」），而不是静默丢弃 —— 我们若实现，别写成静默 return。
7. **第三方 FancyScrollView（EnhancedScroller）那一族 70 条**：原版**所有列表**都用它（含 cell 回收池）。我们的 `MenuScroll` 覆盖了滚动/裁切/拖拽，但**没有 cell 回收**；如果以后列表条目变多（成就/排行/聊天），这是性能上的已知差异，不是画面差异。
