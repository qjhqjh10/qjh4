## 0. TL;DR

1. **登录自然链在现有 74 轮里【一次都没到过 50】**。49 次 `SetProgress = 50` 的下一行（≤9 ms）必然出现 mod 的
   `[WFP][FINISH] …`——全部是 `WF_OFFLINE_FINISH=1` 强推的。state 20 之后卡住是**常态，不是偶发**。
2. **游戏自己的转场在现有 74 轮里也【一次都没进过主菜单】**。15 次 `scene=MainMenu Warpforge` 的心跳，
   **每一次都**在同一毫秒（≤5 ms）跟着一条 `loadmenu.tsv … status=Succeeded`（= 我们手动 `Addressables.LoadSceneAsync`）。
   ⇒ **B152 §五「游戏自己的转场也能走到菜单」是误判**（见 §3·3）。
3. **转场卡点已定位**：`EverguildSceneManager.WaitSceneLoad` 的 **无超时轮询** `SceneInitializer.status == 2 (Initialized)`；
   主菜单场景的 `SceneInitializer` 因为 `GeneralMenuController.Initialize` / `AchievementsManager.Initialize` 抛 NRE，
   **永远到不了 2**（初始化协程的 group-wait 死循环，见 §2·B）。
4. **两者同源（高置信）**：强推 `TryCompleteLogin()` 发生在 `PlayerDataManager.UnpackUserInfo` 的 `Task.WhenAll` **完成之前**，
   而 `configs.Unpack / liveOps.Unpack / UnpackUserProfile / UnpackInventory` 全在它**之后**（§2·A 第 9 步）
   ⇒ 菜单是在**半截玩家数据**上初始化的。这正好解释菜单初始化为什么必然抛 NRE。
5. `Unloading the last loaded scene …` 是 **Unity `SceneManager` 的警告**，来自 `LoadTransition` 的 **state 7**
   （卸载 `Simple Transition`）。它只在「菜单没加载上」的旧年代出现 = **症状不是原因**；现年代（12:27 之后）链根本没走到 state 7，所以没有这条警告。

**卡在 state 4 的 `WaitSceneLoad("MainMenu Warpforge")`**：

- `WaitSceneLoadAddressables`（`d__30`）把菜单**以 Additive 方式**加载：
  `Addressables.LoadSceneAsync(sceneName, LoadSceneMode.Additive, true, 100, 0)`
  （`out_il2csharp/EverguildSceneManager.cs:1100`；Ghidra `_WaitSceneLoadAddressables_d__30__MoveNext.c:29-85`）。
- 加载完成（Succeeded）后，`WaitSceneLoad`（`d__29`）进入**死轮询**：
  `FindObjectOfType<SceneInitializer>()` → `while (sceneInitializer.status != 2) yield return null;`
  （Ghidra `_WaitSceneLoad_d__29__MoveNext.c:63-90`；ILSpy `EverguildSceneManager.cs:568-644`）
  **没有超时、没有放弃条件**。
- `InitializationStatus`：`Pending=0 / Initializing=1 / Initialized=2 / Error=-1`（`InitializationStatus.cs:1-7`）。
- 主菜单场景**有** `SceneInitializer`（`MainMenu Warpforge.unity` 命中脚本 guid `ad3c0ece…` 1 次；
  `Simple Transition.unity` **0 次**，`Intro.unity` 也 0 次）⇒ 这一跳只在菜单上生效。

**为什么它永远到不了 2**：菜单的 `SceneInitializer.InitializeBehaviours` 的 group-wait 条件是
「本组所有 `IBaseInitializable.Status == Initialized(2)`」（`SceneInitializer.cs:322-349`），
而 `InitializeDefaultBehaviours` 抓到某个 behaviour 的异常后调用 `OnInitializableError`，
后者把**该 behaviour 的 Status 置为 -1（Error）**（Ghidra `SceneInitializer__OnInitializableError.c:57`
`FUN_180001f00(2, DAT_184299908, param_2, 0xffffffff)`），并同时把 `SceneInitializer.status` 置 -1（`:58-59`）。
⇒ -1 永远不等于 2 ⇒ **group-wait 死循环** ⇒ `SceneInitializer.status` 永不置 `Initialized`
（置 2 的那行 `SceneInitializer.cs:439` 永远走不到）⇒ `WaitSceneLoad` 永远轮询 ⇒ 转场永远停住。

### 1.3 两者是不是同一个根因（高置信、但未 100% 证实）

`PlayerDataManager.UnpackUserInfo`（`d__522`）的顺序是：

```
:4466  UnpackRawUserData()
:4467  task = InitializeLiveOpsAndConfig()
:4471  task2 = UnpackAddressables(progressCallback)
       task5 = EntityObjectsManager.Unpack()
:4548  await Task.WhenAll(task2, task5, task)

:4572  await liveOps.Unpack(result.HandlerData)

       … AlliancesManager.Initialize / PreloadLeaderboards …
```

（`cpp2il/out_cpp2il_dev_ilspy/PlayerDataManager.cs`）

⇒ 一旦 `WhenAll` 里的任何一条卡住/抛异常，**`:4570` 之后的一切都不会发生**，而 mod 的
`WF_OFFLINE_FINISH=1` 会在 ~15.5 s 时**强行** `TryCompleteLogin()`（实测每轮从 `SetProgress 20` 到强推恰好 **15.4–15.6 s**）。
菜单就是在「configs / liveOps / profile / inventory 都没 unpack」的状态下被初始化 ⇒ `GeneralMenuController.Initialize`
与 `AchievementsManager.Initialize` 抛 NRE 是**可以预期的**。

> ⚠️ 这条是**因果假设**，不是已证事实：要证实得让登录自然走完（或让 `WhenAll` 完成）再看 `INIT-ERR` 是否消失。
> 探针方案见 §5。

## 4. `Unloading the last loaded scene …` 是谁发的、影响什么

原文（`unity.log:187-188` 等，共 **20 组**、每组同一毫秒出现两行，时间跨 07:44:29 – 12:26:16）：

```
Warning  Unloading the last loaded scene Assets/Data/Scenes/Transition Scenes/Simple Transition.unity(build index: -1),
         is not supported. Please use SceneManager.LoadScene()/EditorSceneManager.OpenScene() to switch to another scene.
```

- **发送者 = Unity `SceneManager`**（不是 Addressables 自己的措辞）：调用 `UnloadSceneAsync` 且目标是**当前唯一已加载场景**时拒绝执行。
- **本工程的唯一调用点 = `LoadTransition` state 7** → `UnloadScene("Simple Transition", false)`
  → `IsAddressableScene` 为真 → `UnloadSceneAddressables` → `Addressables.UnloadSceneAsync(SceneInstance)`
  （`EverguildSceneManager.cs:398-419`）。
- **它只在「菜单没加载上」的旧年代出现**（07:43–12:26）。语义：走到 state 7 时场景里只剩 `Simple Transition`，
  ⇒ state 4 的菜单加载**失败了**（那年代 `loadmenu.tsv` 也全是 `Failed`），于是「转场正常结束、但没有菜单」。
- **与现年代的卡死无因果**：12:27 之后这条警告**一条都没有**，说明链根本没走到 state 7（卡在 state 4）。
- ⚠️ 断言口径：这条警告是**症状探测器**（= 菜单没加载上），不是我们需要「修掉」的东西。

## 6. 修法候选（≥2，各带风险与判据）

### 修法 ①【最窄 · 直接解死锁】`OnInitializableError` 后把该 behaviour 的 Status 补成 `Initialized`

- **做什么**：Harmony postfix `SceneInitializer.OnInitializableError(IBaseInitializable, Exception)` →
  `initializable.Status = InitializationStatus.Initialized`（2）。原版语义里错误已经弹过窗（保留弹窗），
  这里只是让 group-wait 能退出。
- **效果**：`InitializeBehaviours` 的 `Any(i.Status != 2)` 退出 → `SceneInitializer.status = Initialized` →
  `WaitSceneLoad` 的轮询满足 → 转场按原版流程走完（state 5/6/7/8/9）。**不动 Addressables、不动场景、不另开加载。**
- **风险**：被标记 Error 的 behaviour 会被下游当「已初始化」使用（它本来就是半初始化状态）。
  这是 🔶 自己设计的桩，必须在代码里按铁律 18 打标；并且它**掩盖**了真正的数据缺陷（见修法 ③）。
- **判据**：T1 的 `state` 从 3 走到 8；T3 status 出现 1→2；心跳 `scene=MainMenu Warpforge` **且 `loadmenu.tsv` 无新行**。

### 修法 ②【治本】让登录自然走完（修 `WhenAll` 里卡住的那条）

- **做什么**：先用 §5·A 的 L5/L6/L7 定位到具体 await，再修根因。两个具体怀疑：
  - **CRC Mismatch**（每轮必现，12:31 起）：`localization_assets_all.bundle` 的 catalog CRC 与本地文件不符
    （`Provided af20d7fe, calculated 318560ed`）⇒ Addressables 拒绝加载。若这条失败落在 `LoadLibraries` /
    `DownloadContentUpdate` 里，Task 会 fault ⇒ `WhenAll` fault ⇒ 被 `ProcessLoginResult` 的「只拿不 await」**静默吞掉**
    （`StepProbe.cs` 头注释已把这个失败模式写死）。**修法**：换一份 CRC 对得上的 bundle（从关服前存档/APK 远端包），
    或在 mod 里屏蔽这一条 bundle 的 CRC 校验。
  - **`Caching.ready` 恒假**（`_UpdateCatalogs_d__16__MoveNext.c:37-95`）：如果它是假的，`UpdateCatalogs` 会 100 ms 一轮
    无限重试且**零日志**。用 L7 直接读 `UnityEngine.Caching.ready` 判。
- **效果**：登录自然到 50 ⇒ `configs/liveOps/profile/inventory` 全部 unpack ⇒ 菜单初始化大概率不再 NRE ⇒ 转场自愈，
  **一个桩都不用打**。
- **风险**：工作量最大，且要动资源（bundle）；如果 root cause 在远端包缺失，可能只能退到修法 ①。
- **判据**：`login_states.tsv` 出现 **不带 `[FINISH]` 紧跟**的 `SetProgress = 50`；`INIT-ERR` 条数 = 0。

### 修法 ③【治标+数据】把两个必抛的初始化项补好

- `ResourcesBarController.GetCounter`：NRE 发生在 `currentCounters` / `container` / `resourceCounterReference` 之一
  （`ResourcesBarController.Initialize` 里 `currentCounters != null` 分支，`GameCurrency[]` 逐个 `GetCounter`）。
  现有 stub 只盖了 `CurrencyExtensions.GetOwnedCount`，**没盖住这个 NRE**（13:50 那轮 `COUNTER … ok` 之后 2 ms 仍抛）。
- `AchievementsManager.Initialize`：需要成就定义（`AssetReferenceTyped<AchievementsList>`）+ 玩家成就数据；
  `onUserConnected` 里 `Achievements` 为空只会打 warning（`PlayerDataManager.cs:11774`），真正 NRE 在 `Initialize` 内部。
- **风险**：仍是桩；且如果修法 ② 成立，这两条会自己消失。**优先做 ②，①作兜底。**

### 修法 ④【兜底 · 有已知副作用】看门狗 + 手动 `LoadSceneAsync`

- **做什么**：mod 里每 2 s 检查 `IsTransitioning && 当前 active scene != MainMenu` 持续 > 20 s ⇒ 调
  `Addressables.LoadSceneAsync("MainMenu Warpforge", LoadSceneMode.Single)`（就是 `WF_OFFLINE_LOADMENU=1` 那条 100% 成功的路）。
- **风险（实测）**：**与游戏转场同时跑会把主线程卡死**（窗口「未响应」）—— 所以只能在**证明游戏链已停住**时触发，
  且触发后不要指望 `EverguildSceneManager` 的 `isTransitioning / currentTransition / EventSystemController` 状态会自愈
  （它们是 private static，需要一并复位）。
- **判据**：只允许在 T1 停在 state 3 且 T3 status≠2 时触发；否则不动。

## 7. 没查清的部分 + 顺手发现

**没查清（写清搜过哪里）**：

1. **13:57 那轮 `ProcessData` 的续体为什么没跑**。已确认：`ProcessNewLogin` 完成（trace 有）、`ProcessData`
   再没被记录（`steps.tsv` 13:57:59.014 之后没有 `MoveNext _ProcessData_d__36`）。
   已排除：ProbeLog 线程安全（`ProbeLog.cs:77` 有 lock）、线程池枯竭（心跳 `threads` 3–5、`pending=0`）。
   未排除：续体（`TaskAwaiters.ForceAsync` → `ForceAsyncAwaiter` → `TaskScheduler.Default` 线程池）
   跑了但**在写日志之前**抛异常并被 ContinueWith 的返回 Task 吞掉。**需要 L2 + L10 才能定论。**
2. **`Addressables.CheckForCatalogUpdates(true)` 到底卡在哪一步**。`settings.json` 的远端 catalog 指向
   `http://127.0.0.1:8765/aa/catalog_main.hash`，假服务器 `_serve_aa` 把它映射到 `aa/catalog.hash`
   并带 `Content-Length`（`server.py:484-500`），**看起来**应该很快返回；但没有该 URL 的请求日志（假服务器只记 PlayFab 请求）。
3. **CRC 到底是不是登录卡死的根因**：时间上高度吻合（每次都在 allcards/localization bundle 请求后 ~30 ms 报错），
   但没有 `Can't load scene`/OperationException 的日志——`unity.log` 对游戏侧 `Debug.LogError` 的捕获**不完整**
   （实证：`SceneInitializer` 的 `Debug.Log("Initializing Group …")` 一条都没被捕获到），所以「日志里没有」不能当反证。
4. **`Intro` 是否在 `scenesInBuild` 里**（决定 state 3 走 `UnloadSceneInBuild` 还是 `UnloadSceneAddressables`）。
   两种都不会卡（未加载场景 `UnloadSceneAsync` 返回 null），对结论无影响，但没读到 `EverguildSceneManager` 实例的序列化值。

**顺手发现**：

- `steps.tsv` 12:35 与 13:57 两轮的 STEPPROBE **会扰动登录时序**（`StepProbe.cs` 自己写着：
  `mode="addr"` 专用是因为「挂 LoginManager/PlayerDataManager 那批实测会扰动登录链时序」）⇒
  **任何 STEPPROBE=1 的登录结论都要用 STEPPROBE=0 复测一次**。
- 有 3 轮 `TryCompleteLogin` 自身抛异常（`TargetInvocationException` 07:40:26 / `NullReferenceException` 07:41:39），
  但 mod 仍然把状态推到 50 —— 说明「强推」这条路也不是无条件的。
- `WaitSceneLoadAddressables` 的 `readyPredicate` 是**死代码**（只调用、不用返回值），原版这里应该有「等转场动画播完」的语义，
  实际没有；排障时别把它当等待条件。
- `MainMenuWindow.Initialize` 一进来就 `Time.timeScale = 1.0`（`read_literal 0x1834b2bb8 = float 1`），
  而 `BattleManager.StartBattleManager` 会置 0 ⇒ **「DOTween 卡住」这条备选解释基本排除**（转场期间没人把 timeScale 置 0）。
