## 七、方法与误判边界

**1. 「有值卡数」为什么取非默认值**：`cards_engine.json` 是稠密表（1,142 张卡每张都带全部键，默认值 `0`/`""`/`[]`），若把 `0` 也算「有数据」，全部叶子列都会被 1,142 张卡携带，没有判别力。`cards_truth.json` 是稀疏表（缺键 = SO 默认值）。两源各算「非默认值卡数」，取 `max`。⚠️ 因此 `0` 是合法值的那类列（如 `playerTurn=0`）在「有值」口径下会低估 —— 这是刻意的。

**2. 代码命中怎么数**：先剥 `//`、`/* */` 注释与字符串/字符字面量（本项目注释极多，不剥会大面积虚增），再按整词 `\b`、**大小写不敏感**匹配。大小写不敏感是必须的：JSON 是 `targetsAffected`，真正的消费端读的是 `TargetsAffected`。

**3. 四个桶**：
- **生产端** = 不在 `Editor/`、不在 DTO/模型拷表层、不在生成器的 `.cs`。**只有它算「已接上」。**
- **测试端** = 路径含 `/Editor/`（自检断言会大量引用字段名，不能当功能消费）。
- **DTO** = 整份 `CardDatabase.cs`（JSON→模型拷表）；`CardDef.cs` **按行判**（声明行算 DTO、逻辑行算生产端 —— 该文件里既有 `public int TargetsAffected;` 也有 `case 75: return "summon"`）；其他文件里类头 300 字符内有 `Serializable`、或类名以 `Dto/Row/Spec/Data/Set/Entry/Json` 结尾的类体。⚠️ **2026-11-05 R2 订正**：把整份 `CardDatabase.cs` 归 DTO 会把 `Map*`（如 `MapBoardGate`，决定 `CardDef` 取值）一并埋掉 ⇒ `hasNormalAbilityBoardCriteria` / `abilitySummon.*` 一族系统性假阳性；这一类应按「`Map*` 函数体算生产端」判。
- **生成器** = 文件名 `gen_*.cs` / `*.gen.cs`；本次扫描命中 **0 个**（仓里 3 个 `*gen*.cs` 都在 `Editor/` 下、已归测试桶，且都不是卡表生成器）。

**4. 已知假阳性（脚本会误报「0 读取」）**：
- **原版本身就不读的字段**：`includeWeapons` / `includeHeroParts` 等 36 格里原版 `CardTypeOptions` 只有 4 值，B145 已判「原版一次都不读」。这类报 0 是**正确的**，不是缺口。
- **仅 truth 侧的内部形状**（§三）：`_trait` / `_traitValue` / `m_PathID` / `actingCardCriteria` / `boardCriteria` / `multiCountCriteria` 等，主卡表用**另一个名字**承接（`cardTraits` / `enchantment` / `abilityActingCriteria` / `normalAbilityBoardCriteria` / `unitConditions`），不是真缺口。
- **改名承接**：DTO 里只做一行映射、之后改用另一个字段名消费（`goesSecond` → `GoesSecondId`、`startingCardInHand` → `StartWithNames`、`fullHeroSpriteReference` → `CardArt.TryDeckHero` 的旁挂表）⇒ 本列判 0、真消费在别名上。这是本脚本最大的结构性假阳性来源。
- **反射 / 字符串拼出来的键**：本项目表装载走 `JsonUtility` 直绑字段名，没有反射拼名；但如果将来出现 `GetField("xxx")` 形式，脚本看不到。

**5. 已知假阴性（脚本会漏报）**：
- **同名不同义**：命中按「名字」而非「语义」，`type`/`name`/`id`/`army` 这类通用名会被无关代码命中 ⇒ 真缺口被掩盖。报告里 `名字过泛` 就是给这类打标。
- **枚举值用命名常量消费**：本仓多数是数字字面量（`ta = 50`、`case 0x16`），但 `TargetsAffected.any` 这类命名常量出现时，`case N` 统计看不到 ⇒ 枚举值级可能高估「0 消费」。
- **枚举值只在这条口径下算准**：强命中 = `case N` / `== N` / `N =>`；**弱命中** = 函数实参里的 `f(46)` / `f(a, 46)`（只收 ≥ 40 的值，避免坐标/尺寸噪声）。两条都为 0 才判「0 消费」——否则 `OnTrigger(0x2e)`、`HasCurrentTrait(0x29e)` 这类**实参式消费**会被误报。
- **同一数值跨列共用**：枚举值统计不区分列（`90` 既可能是 `trigger` 也可能是别的），因此「非 0 命中」里混着别的列的用法 ⇒ 枚举值级整体偏乐观。
- ⚠️ **2026-11-05 R2 订正（枚举行口径）**：表里的「有值卡数」实际是 **`cards_engine` + `cards_truth` 两源出现次数合计**，不是卡数（例 `spellType=265` 表写 6，按卡数现读 **3 张**）⇒ 引用前先换算回卡数。
- **字段只在别的字段的 doc/注释里出现**：注释已剥，因此「只写在注释里」= 0 命中，这正是我们要的口径。

**6. 与账的分工**：本普查只出「候选缺口清单」，**不判定要不要补**。每条都要按铁律 11 回源核「原版读不读」，再决定派活；⛔ 别直接把 🟠 当缺陷修。
