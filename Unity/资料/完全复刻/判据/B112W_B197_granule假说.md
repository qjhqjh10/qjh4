## 一、结论（**是**）+ 一句话

**那 450 条 q8/q10 重编码是不必要的。** 备份里那 450 份的 **Vorbis 包与 FSB5 真值是同一份音频**；唯一的缺陷是 **AssetRipper 给「非末页」写的 granule 错**（§二·2·3）。把中间页的 granule 就地改成真值（**每份只改 5–14 个字节、文件大小不变**），三条互不相干的解码路径**全部**解出 **`corr = 1.000000`**：

| 解码器（容器逻辑） | 备份**未修改** | **只改中间页 granule** |
|---|---|---|
| **vgmstream r2168**（libvorbis） | 0.291–0.999（中位 0.858，30 抽样） | **1.000000（93/93 份）** |
| **libsndfile**（libvorbis） | 0.488–0.997（中位 0.818，10 抽样） | **1.000000（10/10）** |
| **ffmpeg native Vorbis** | ≈1.000000（30/30，**它根本不看中间页 granule**） | ≈1.000000（27/27） |

⇒ **不需要重编码、不需要 +24.73 MB、不需要二次有损。**

📌 三条必须写清的口径：

1. **末页 granule 早就是对的**（B450 **450/450**、C43 **43/43** 都 == `len×freq`，第三波的成果）。错的只有**中间页**（4 页文件 = 第 2 页；5 页文件 = 第 2、3 页）。
2. 🔴 **「中间页 granule 没人看」是错的** —— 实测**两条主流实现都会看**：`vgmstream` 与 `libsndfile`（后者就是 libvorbis 的标准用法）都按它裁样点，于是同样解错。**只有 ffmpeg 的 native Vorbis 解码器忽略它**。所以「用 libvorbis 解就没事」这个说法**不成立**，本轮已就地订正。
3. 但**包流本身没坏** —— 这一点由「只改 granule 就三分之三全中」直接证明（若有任何一个包被改过，改 granule 不可能回到 corr 1.0）。

### 2·2 三个量怎么算

1. **FSB5 真值**：`clip_index.json` 的 `len × freq`，并用 **vgmstream 解 FSB5** 核对 —— B450 **450/450**、C43 **43/43** 都和末页 granule 相等。
2. **「页边界实解累计」（不看 granule 字段）**：把 ogg **截断到该页末尾**，把该页 granule 设成 `10,000,000`（远大于实解）+ 打 EOS + 重算 CRC，**用 ffmpeg native Vorbis 解码** ⇒ 输出长度 = 该页为止**实际能吐出的累计样点数**。
   - 这条能用 ffmpeg native，正因为**它忽略中间页 granule**（§一·2）。
   - ⚠️ **vgmstream 用不了这条**：granule 大于实解时它会**补静音**（实测 `gran=10,000,000` → 吐出 10,000,000 样点），量到的是 granule 不是实解。
   - 这个数**与解码器无关**：每包产出多少样点由包内 `blockflag` 决定，是码流自身属性。
3. **修法（只改 granule）**：把每个**中间页**的 `granule_position`（8 字节）改成第 2 步的值，**重算该页 CRC**（多项式 `0x04C11DB7`、初值 0、无反射），**其它字节一个不动**。
4. **corr**：逐样点 Pearson，取两边前缀最小长度（与 `refix_verify.py` / `B112_R1W.md` §11.3 同口径）。

### 2·3 根因（顺带查实，可直接写进账）

拿第三波**之前**的原始备份（**1,778 份**）逐页验：

> **每一条音频页的 granule == `(段数 − 1) × 128`，2,294 / 2,294 页 100% 命中，0 例外。**

- 全部 1,778 份的 Vorbis ID 头都是 **blocksize_0 = 256 / blocksize_1 = 2048** ⇒ `128 = blocksize_0 / 2`。
- 页内**没有一条 255-lace 段**（2,294 页里 0 条）⇒ 段数 == 包数。
- 所以 AssetRipper 的 Ogg 写出器是：**按「每个包都是短块（128 样点）、且第一包贡献 0」算每页样点数，并且逐页重置、不当累计写**。
  - 250 包/页 → 249 × 128 = **31,872**（这就是那个「固定的 31,872」的来历）；
  - 5 页文件第 3 页也写 31,872（不是 63,744）⇒ 证明**非累计**。
- 真实块长混着长块（2048 → 每包 1024 样点），所以真累计**通常远大于它**（B450 实解最小 47,552，也比 31,872 大）。

## 四、那 43 个反例为什么「正常」

**它们不正常 —— 它们有完全相同的缺陷，只是错的那一段恰好是静音。** 证据三条：

1. **同形同错**：43/43 都是 page2 = `(250 段, 31872)`，实解累计 97,280–215,104，全部 ≫ 31,872。把中间页 granule 改对之后 **43/43 → `corr = 1.000000`**。
2. **它们在名单外只是「刚好过线」**：vgmstream 改前 corr = **0.999129 – 1.000000**（中位 0.999915），**全部 ≥ 0.999** ⇒ 没过 `corr < 0.999` 的入选门槛。**不是**「解码器对它们走了别的分支」。
3. **为什么过线 —— 位移那一段是静音**：统计「第一个损坏页边界之后的音频能量 / 全曲能量」：

| 组 | 尾部能量占比 min / 中位 / max | 占比 > 0.1% 的条数 |
|---|---|---|
| **B450** | 0.067% / **15.18%** / 77.70% | **447 / 450** |
| **C43** | 0.000% / **0.0043%** / **0.0785%** | **0 / 43** |

   实例（`VO_SaimHann_Zephyrblade_gen1`，总 198,624，边界 175,680）：从 176,128 起的各 4,096 窗口 **rms 全是 0.0000（数字静音）**，窗内 corr 虽降到 −0.03~0.04，但对全曲相关几乎无贡献 ⇒ 全局 corr = 0.99999999。

   ⇒ **分界线不是「有没有缺陷」，而是「坏掉的那段有没有声音」。**

## 六、还差什么（⛔ 不许拿本轮的结论当「Unity 里一定没问题」）

1. 🔴 **Unity/FMOD 对「中间页」granule 的行为没测**（本轮按红线不跑 Unity）。已知的只有：**末页** granule Unity 认（第三波 §7 的控制件判定）。本轮实测到的分布是「**两条主流实现（vgmstream / libsndfile）会看，ffmpeg native 不看**」⇒ FMOD 属于哪一类**仍然是未知**：
   - 若 FMOD **像 ffmpeg native**（不看中间页 granule）⇒ 那 450 份**在游戏里本来就是对的**，第四波整批（含 +24.73 MB）属于多余 —— 这比「只改 granule 更好」还强；
   - 若 FMOD **像 vgmstream / libsndfile**（会看）⇒ 那 450 份在游戏里**确实播错**，必须修（用 granule 修，而不是重编码）。
2. **建议的最小验收（Unity 侧，一条就够）**：把同一条音频的三个变体（①备份原样 ②只改中间页 granule ③现在的 q8）放进同一个场景，比较 `AudioClip.samples` 与导出的 PCM。若 ① 与 ② 相同 ⇒ FMOD 属「不看」类；若 ① 与 ③ 相同、≠② ⇒ 属「看」类。
3. **本轮没做、也不该由我做的**：是否回滚第四波（`_tmp_view/b112_r1w_backup/mono_setup/` 的 450 份原样拷回 + 打 granule 补丁）。那是调度台/用户的决定，且**应先有 §6·2 的读数**。
4. **与本条相邻、本轮未碰的**：`B112W_B171` 已证「FSB5 sample header `0x0C` 的 CRC32 == setup 整包 CRC，450/450 命中」—— 与本轮结论**一致**：既然包流是同一份，错的当然不是 setup，而是 granule。
5. **本轮的 corr 尺子**：真值取自 **vgmstream 解 FSB5**（与既有报告同口径）。三条解码路径在被修好的文件上**同时**给 1.0，所以「真值」本身不受某一路解码器偏好影响。
