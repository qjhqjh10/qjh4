## 一、原版两层架构（`.c`/`.cs` 行号）

```
                    ┌──────────────────────────────┐
   云端（权威）      │ PlayFab user data（51 数据 key）│  ← 每 key 一份 JSON（+3 个字符串 key，见 §四·1）
                    │  PlayerDecks / Decks / TipsData│     JsonWrapper(Newtonsoft)
                    │  LevelData / PlayerSeason / …  │     读：OnlineData.GetPlayerOnlineData<T>
                    └──────────────────────────────┘     写：UpdateOnlineUserData(字典) / CloudScript
                              ↑ 登录时一次性拉进 userInfo__BackingField（内存缓存）
                    ┌──────────────────────────────┐
   本地（只设置）     │ persistentDataPath/          │  ← 一个文件，BinaryFormatter
                    │  PlayerDecks{dataVersion}.dat │     只含 LocalPlayerData（设置+凭据）
                    └──────────────────────────────┘
```

**关键事实（容易看错的三条）**：
1. 本地档**不叫** `PlayerDecks.dat`，是 **`PlayerDecks{dataVersion}.dat`**（`:10160` / `:10178` 都是 `+ "/PlayerDecks" + dataVersion + ".dat"`）。⇒ **版本号是文件名的一部分**。
2. 本地档**不含玩家进度**（等级/货币/卡组/库存都不在里面）—— 只有 `GameStaticData` 那批设置 + 加密后的 `loginName/loginPassword/deviceId`。
3. 云端读**只读内存缓存** `userInfo__BackingField`（`OnlineData.cs:145`），**不发网络请求**；网络请求只在登录与 `UpdateOnlineUserData`。

## 五、d) 「没有赋值点」的字段 —— 方法学 + 已确认的几个

### 5.1 🔴 **先纠正一个方法学错误（这条比答案本身重要）**
⛔ **不能靠反编译里的 `字段 = ` 反查「有没有人写」**。ILSpy 把**私有 setter** 反编译成：
```csharp
private set
{
    object obj = this + 160;
    obj = value;          // ← 字段名丢了，只剩「对象 + 偏移」
}
```
（实例：`PlayerDataManager.cs:5365-5371` 的 `loginManager` 属性 setter）
⇒ **所有经属性赋值的 backing field 在文本里都看不到写点**。本文件第一次自动扫描得出「167 个字段里 119 个没有赋值点」，**那个数字是假的**，已作废。

**可靠办法只有两条**：
1. `d:/2/tools/decomp_full/` 的 `.c` —— 按**字段偏移**看写点（`*(undefined4 *)(param_1 + 0xNN) = …`），配合 `il2cpp_out/dump.cs` 的字段偏移表；
2. **运行时探针**（`d:/2/unity_run_ref/` 的 mod）—— 直接把对象序列化出来。

## 七、迁移路线（**目标形态 = 中央存档 + 按活动分表**）

> 原则：**分步可停**，每一步都能单独验证；**旧档必须能读进来**（G2 的迁移不能靠「删档重来」）。
> 每步都**不阻塞**其它线：新增的统一层先**只接管新数据**，旧文件继续被读（双写期）。

### Step 0 —— 立规（1 天，纯文档 + 常量）
- 建 `存档键表`：**照抄原版 `PlayerDataKey` 的 51 个数据 key + 3 个字符串 key（共 54 个数据槽）**（判据 = `PlayerDataKey.cs:1-55` + `PlayFabReadOnlyDataKeys.cs:1-17`），并给每个 key 标注「我们对应哪个现有文件 / 目前空缺」。
- 定 `schemaVersion` 策略：**每个 key 的 JSON 顶层加 `_v`（int）**，从 1 开始。
- **验证**：键表与本文件 §四·1 逐条对得上（52 行）；空位写明「我们没做」。

### Step 1 —— 建中央层（纯新增，不动任何现有文件）
- 新建 `Shell/SaveCenter.cs`（名字自定）：`Get<T>(key)` / `Set<T>(key, value)` / `Flush()` / `RegisterMigration(key, from, Action<JObject>)`。
- 落盘：**一个根目录** `persistentDataPath/WarpforgeSave/`，每 key 一个 `<key>.json`；**统一 tmp+rename 原子写**（照 `DailyData.cs:1934` 那条路）。
- **验证**：① 单元级——写一个 key → 重开（`ResetForTest` 那种）读回一致；② **断电模拟**：写 tmp 后不换名，主文件必须仍是旧版本（这条是 G3 的正向断言）。

### Step 2 —— 迁移旧档（**读进来，不丢**）
- 为每个现有文件写一个 **`LegacyReader`**（映射表见 §六，判据 = 各旧档的落盘常量）：`WarpforgeDaily/daily.json` → `DailyCounters`；`WarpforgeDraft/run.json` → `ActiveEvent`；`battlelog.json` → `BattleLogData`；**`WarpforgeDecks.json` → `PlayerDecks`**；**`WarpforgeRanked/ranked.json` → `PlayerSeason`**；**`WarpforgeCardLevels.json` → `_ours_CardProgress`**；**`WarpforgeInventory/<name>.json` → `_ours_Inventory.<name>`**；`profile.json` → `CosmeticData`（**只取 2 个字段**，见 §六·1）。⛔ **不进**：`WarpforgeReplays/`（引用已在 `BattleLogData`）· `WarpforgeNet.json`（设置层）· 语言/音量 `PlayerPrefs`（设置层）；⚠️ **教程进度例外**（`PlayerPrefs` 但**该迁**，见 §六·2）。
- 迁移时机：**首次启动时**（`Load()` 里）：`if (!Exists(<key>.json) && Exists(<legacy>)) Import();` ⇒ **一次性、幂等**（导入后写 `_v`，下次不再导）。
- **旧文件保留不删**（用户要回滚时能退）。
- **验证**：拿一份**真旧档副本**跑一遍，逐字段比「导入前的内存态」与「导入后 `Get<T>()`」（用 `SaveCenter` 的 dump）。
- ⚠️ `PlayerPrefs` 那几项（语言/音量）**不迁** —— 原版也说它们属于「设置」不在中央存档里（见 §一·2），**留在 `PlayerPrefs` 才对**。

### Step 3 —— 补「缺字段 / 坏 JSON」的兜底（照原版形态）
- `Get<T>()` 里：**缺 key ⇒ 返回 null 并出声一次**（照 `OnlineData.cs:172` 的 `Log("No player data found for key X")`）。
- **JSON 损坏 ⇒ 捕获异常 + 回退到 `.bak` + 出声**（原版**没有**这一档，这是**我们比原版强**的地方，要标注「原版无此兜底」）。
- **逐 key 的 `RegisterMigration(key, from, …)`**：照 `CheckForTutoriaDoneAndDataFix`（`:11229`）的形态 —— 「探测旧字段 → 补新字段 → 不认识的忽略」。
- **验证**：三条负例各一条断言 —— ① 删 key ② 写坏 JSON ③ `_v` 比当前大（未来版本档）。第三条必须**拒绝覆盖**并出声（否则降级会毁档）。

### Step 4 —— 逐子系统切到中央层（**一处一 PR 级**）
顺序（按风险从低到高）：`InventoryStore`（新、字段少）→ `BattleLogData` → `DraftModeWindow` → `DailyData`（有原子写，切完要保住这个性质）→ **`TutorialV2`（从 `PlayerPrefs` 搬，见 §六·2）**。
每切一个：**双写期**（同时写旧文件 + 新 key）跑一轮自检，再删旧写入。
- **验证**：切之前先 dump 一份该子系统的全字段；切后 dump 比**逐字段相等**。

### Step 5 —— 关掉双写、删 LegacyReader（**只在 Step 4 全绿之后**）
- 保留 `LegacyReader` 至少一个版本（用户可能从旧版回滚）。

### 每步「不许做的事」
- ⛔ 不许在 Step 1 就改任何现有子系统的写入点（那是 Step 4）。
- ⛔ 不许删旧文件（Step 5 之前）。
- ⛔ 不许给 `PlayerPrefs` 那几项加中央层（原版把它们归「设置」，不进中央存档）。
