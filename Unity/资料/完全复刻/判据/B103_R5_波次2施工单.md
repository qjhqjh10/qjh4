#### 两个参数各管什么（本账这一个调用点，`0.3f / 0.3f`）

- **`timeToDraw`（`+0x30`）**：state 1 的 **`DOScale` 时长**；`changeVisibility == false` 时**还**是
  `TurnCardAround` 的时长。本账 `changeVisibility = true` ⇒ **它只管那条 0.3 s 的缩放补间**，
  **不产生任何等待**。
- **`stepTime`（`+0x34`）**：**两段等待的基数** —— `stepTime × 0.66` 与 `stepTime × 2.6`。
  **阻塞的主体全在这里**（0.3 × 0.66 + 0.3 × 2.6 = **0.978 s**，占总时长 91 %）。

#### 阻塞时长（真值）

```
0.1（state0 等） + 0.3 × 0.66（=0.198） + 0.3 × 2.6（=0.78） = 1.078 s
```
`DOMove` 那 0.15 s **不额外增加**（0.1 就往下走了，它还剩 0.05 s 在 state 1 里跑完）。
⇒ **账里写的「0.6 s」是错的**（多半是把 `0.3 + 0.3` 两个实参直接相加了）。
🔴 **建议调度台按铁律 5 把 `账/战斗逻辑驱动.tsv` 的两处「0.6 s」就地订正为 `1.078 s`**：
  ① 账 :1383 的「差异」列；② 同名账在 :506 的备注（若有同句）。

#### 阻塞的是**谁**

1. **`ResolveCreateHandCard` 自己剩下的三步**（进手 / `BroadcastCardCreated` / `AddEffect`）；
2. 通过 `FinishResolvingAction`（`.c:128`）⇒ **下一个动作能不能开始**。

⇒ 所以「牌已经先进手了」不只是顺序问题，它同时意味着**那一整段演出没有占住动作队列**。

#### 失败 / 取消怎么办

- **原版没有优雅取消**：协程每一步都写 `if (this != 0) {…}`，落空就 `goto` 到
  `FUN_1803f47a0()`（`.c:120-122`，`/* WARNING: Subroutine does not return */`）—— 那是 IL2CPP 的
  **null 检查桩（抛 NRE）**，不是「安静返回」。ILSpy 同一处渲染成 `return (byte)(int)new NullReferenceException();`。
  ⇒ 语义 = **卡被销毁时这条协程会炸/挂住**，原版没有兜底分支。
- **没有超时、没有取消令牌**；`WaitForSeconds` 走 `Time.timeScale` ⇒ 暂停就一起停。
- ⇒ 我们**不需要**新造「取消」逻辑（那会造出原版没有的行为）；但**「建不出载体」时要不要仍然占这 1.078 s**
  要明确写死（见下面施工 S2 的备注）。

## 附录 E · 顺手发现 ⑤：一条可复用的读法

`FUN_1803f47a0()` 在 `.c` 里出现时带 `/* WARNING: Subroutine does not return */` ——
那是 **IL2CPP 的 null 检查桩（抛 NRE）**，对应 ILSpy 的
`return (byte)(int)new NullReferenceException();`。
⇒ 以后在 `.c` 里看到「方法尾巴 `goto` 到一个不返回的 `FUN_`」，**别读成「这里有个错误分支/优雅退出」**，
它是编译器的空检查，不是业务分支。
