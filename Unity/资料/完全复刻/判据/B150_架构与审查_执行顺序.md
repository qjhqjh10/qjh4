## 〇·b · 全局顺序（用户 2026-11-05 定：**先清零散，再做大任务**）

```
① 8 宿主全绿 + 四闸绿
   ↓
② 零散任务清零（用户原话：「先把零散的任务解决好，之后干净的解决那些大任务」）
   2a 离线零散：工具/账务/文档 16 · 引擎/机制 12
                · 两条跨切普查落地（断言直读存档 12 · 固定种子手牌 9）
                · 表现/渲染残余（BATTLE-ALPHA 余项 · C11-OBLIQUE）
   2b 字体波次 5 条（单开一波、跑全 8 宿主；**必须在 X1 之前**）
   2c 已核销不再排：W133 真机 · 战场线 T01–T08 · 远端 3 条 · QUALITY-TIERS · 活动-②
       （已写进活状态表并附理由）
   出口：清单清零，或逐条写清「移到哪」；四闸绿
   ↓
③ 四类重建资产彻底解决（判据/B150_重建资产四类_施工单.md，6–9 天）
   ├ 窗口 1 离线：覆盖核对 / 映射表 / 判定
   ├ 窗口 2 离线：拷 controller+clip · 改 .mat · 改 shader
   └ 窗口 3 一次 Unity：13 场 manifest → ArenaBuilder → 逐场重建 → 全量 sweep
       ＋ 同一窗口顺带收「Unity 窗口批次」那 12 条独立项（纹理导入烘焙 · 场景重存 · Audio Mixer · URP 第二 renderer · 输入后端）
       ＋ 顺带收 `B139-Y2`（ArenaBuilder 字段写入）与 `B139-H1`（sprite mipmap），⛔ 不另开窗口
   ↓ 窗口 3 之后 **重跑 BattleScene**（prefab/材质/动画变了，判定会动）
   ↓
④ 架构重构 X1（本文件 §一）
   ↓
⑤ 系统性审查 19 片（本文件 §二）
```

**「零散先清」的三条理由**：

1. 零散项**判据已定、改动小**；清掉后大任务期间不再混着小修，避免「改一点、验一点」的碎片化。
2. 其中**字体波次**与**两条跨切普查**会影响后续所有验证 —— 不先清，大任务每跑一次宿主都会被同一批假红干扰。
3. 零散项里有几条会**改变宿主读数**（删死方法、`cond` 对齐、`RankedEventWindow` 结构统一），必须在大任务开始前把基线稳住。

**为什么资产排在架构之前**（三条理由，都是硬约束）：

1. **X1 期 0 会把原版 prefab 装进工程，而 prefab 引用的是原版材质与 shader 的 guid** —— 材质/shader 没对齐，装进来就是一屏紫块/白块，分不清是「导入失败」还是「资产缺失」。
2. **资产工作判据明确、机械、风险低**（原版数据 100% 在本地，缺的只是接线与逐参数核对）；先清掉它，后续只剩「架构」与「逻辑」两个变量。
3. **审查的 P2/P3（卡牌动画 · 特效生命周期）需要资产基线正确** —— 否则审出来的差异会混着「动画没接线」这类资产问题，等于返工。

⚠️ **唯一例外可以并行**：审查 E1–E6（引擎域）是**只读**，不占写手槽，可以在 ② / ③ 期间同时推进；但它们产出的**缺口修复**要排到 ⑤。

## 一 · 架构重构（X1：原版 prefab 直接装入）

### 1·1 总原则

| 项 | 口径 |
|---|---|
| 终态 | **新栈整体替换**；⛔ 不做「就地修补旧栈」 |
| 旧栈 | **一行不删**，作为回退；退役要过 §1·5 四条判据 |
| 切换粒度 | **一次一整屏 / 一整窗**，⛔ 不许混合态 |
| 开关 | 每屏一个运行期路由（`UiNextRouter`）；全局回退 = 环境变量 `WF_LEGACY_UI=1`，⛔ 不用编译宏（旧栈始终参与编译） |
| 失败退路 | 期 0 任一闸不过 ⇒ 转 **X2（数据驱动生成器）**，⛔ 不回旧栈修补 |

### 1·2 分期与出口条件

| 期 | 内容 | 出口条件 | 回滚 |
|---|---|---|---|
| **0** | 基线 + **三道闸**：tooltip（5 节点/3 类/9 guid）→ 每日连胜（28/13）→ 设置窗（324/28/85）+ **兄弟序比对**（`runtime_ui_dump` 的 1,243 行比 5 个父节点子序） | 节点路径 / rect / 锚点 / 兄弟序**逐项一致**；三档分辨率截图 | `git tag` 基线 |

### 1·3 文件所有权（架构期硬约束）

- **四个大件永远独占一个写手**：`Battle/BattleDriver.cs`（非 `partial`）· `Shell/MenuDraw.cs` · `Deck/DeckRuntime.cs` · `Shell/WindowsManager.cs`。
- 架构期**并发上限 4 个写手**（按文件切，不按屏切；一个屏往往跨多个文件）。
- 派活前先读 `资料/完全复刻/文件所有权_当前.md`；撞车就出补丁交回，⛔ 不硬改。

### 1·4 每屏固定四条验收（缺一不算过）

1. 16:9 / 4:3 / 21:9 三张截图；
2. 该屏交互点清单逐个点（真人点或 `wf_click.py`）；
3. **新旧两栈各跑一遍**该屏的宿主；
4. 该屏旧入口 `grep` 归零（谁也不再调旧构建函数）。

### 1·5 旧栈退役四条判据（全中才删）

每屏验收过 · 连续两个会话没人用回退 · 每个旧入口消费者 grep 归零 · 打 `git tag pre-ui-retire`。

## 二 · 系统性审查（19 片 / 7 域 / 5,846 方法）

### 2·1 单片流程

```
只读代理（一片一个）
   → 三态判定（已对齐 / 已实现未核 / 缺）+ 四个必答
   → 产出 判据/B149_审查_<片>.md（每片一份，含真缺口表 + 未审范围）
   → 按「修复形态」三分：
        机器可批   → spec 表 + 工具/apply_param_spec.py，一次改完一整类
        需人工实现 → 按文件所有权切块派写手，一个代理 3–5 件连着做
        需拍板     → 调度台裁定；拍不了汇总成决策表报用户
```

### 2·2 三个必答（缺一条就不算审过）

1. **可达性数字**：池内多少张卡 / 多少条数据能走到这条分支（⛔「可能有」）。
2. **灭自证反例**：建议改断言时，给一条「两边一起改回去就变红」的反例。
3. **消费者链**：这段行为 / 这个资产，谁在生产路径上触发它。

### 2·4 纪律（踩过的坑，写死）

- 审查代理**只产出文件，不改代码**；缺口进 `活状态表` **只留一行指针 + 总数**，逐条明细留在各片的 `判据/` 文件里。
- **「池内 0 张」≠「不可达」**：还有第二条数据面 `enchantment_templates.json`（230+ 条触发型模板）。凡「池内 0 张 ⇒ 休眠」的结论，必须按 **trigger id** 再对一遍。
- **「0 调用点」可能是内联假象**：先在 `BattleManager__ResolveAction.c` 这类巨型 switch 里搜体特征，再下结论。
- 判据与 `.c` 冲突时**以 `.c` 为准**；执行代理发现判据自相矛盾 ⇒ **零改动 + 交反证**，⛔ 不许硬做。
- 查完到用掉不超过 2 天，或跨过一次重同步点就重核。
