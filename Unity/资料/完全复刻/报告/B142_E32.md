## §1 `B141-HASACTIVE-KEY` —— 能力闸两列的显式 0 被吞掉

### 1·1 改前（问题）

`gen_cards_engine.py` 的 `ability_gate_of()`：

```python
        if v != 0:
            out[col] = v
            if bump:
                report[bump] += 1
```

`hasActiveAbility` / `hasAlternativeAbility` 是**三态**（`1` = 有 · `0` = 明确没有 · `-1` = 坏值/真值缺卡），
但 `if v != 0` 把 `0` 当「默认值」吞掉 ⇒ JSON 里「明确没有」与「这一格不存在」**同形**。

改前读数（`--check` 干跑，池 1,142 张）：

```
能力闸       `hasActiveAbility=1` 87 张 · `hasAlternativeAbility=1` 1 张 · ...
```

### 1·2 判据（原版真值）

`d:/4/Unity/资料/普查产出_1018/allcards_1350/cards_raw.json` 的 `full_raw` / 顶层字段，**1,351 张逐张读**：

| 列 | `=1` | `=0` | 缺键 |
|---|---|---|---|
| `hasActiveAbility` | **88** | **1,263** | **0** |
| `hasAlternativeAbility` | **1**（`SW21`） | 1,350 | 0 |

⇒ 原版**每一张卡都有这一格**，`0` 是明确取值、不是「没填」。
（原版 88 vs 我们 87 的差额 = `Tempestus Scion`（`uniqueId 66486b3f61682ab42ba2ce0fa921002f`，`cardArmy 100`）**不在我们的 1,142 张池里** —— 不是丢数据。）

**为什么必须修**（这不是「形式上更整齐」）：`CardDto.hasActiveAbility` 现在是裸 `int`（默认 `0`），而语义上「未知」是 `-1`（`CardDef.GateUnknown`，DTO 注释也写着 `-1` = 真值里没这张卡）。今天缺键恰好落 `0`、和显式 `0` 撞值，**但那只是 DTO 默认值的巧合**：一旦默认值改成 `-1`（或换任何非 JsonUtility 的消费方），这 1,055 张会**静默变成「未知」**，而数据上看不出是谁的锅。

### 1·3 改法（选型：**显式落 0**，不另开独立列）

- 两列改成**每张卡都落**：`out[col] = v`（`0` / `1` / `-1` 三态），并给报告加 `has_active_zero` / `alt_zero` 两个计数。
- **为什么不选「落一个独立列」**：那会把同一个事实写两遍（铁律 6「数字只留一处」），而 DTO 字段本来就在、`0` 本来就是它的合法值 ⇒ 多一列纯属冗余，还会多一处要维护的同步点。
- **13 张自设计变身卡**（`TRANSFORM_<FACTION>`，`transform_card_entry()`）不走 `ability_gate_of`，所以同一批给它们补了 `"hasActiveAbility": 0, "hasAlternativeAbility": 0`（写在同一行，行数不变）—— 否则「每张卡都落」就有 13 个例外，读数还会与产物对不上。
- 其余四列（`activeNeedsLoading` / `alternativeNeedsLoading` / `quest` / `questTimes`）**维持稀疏**：它们的 `0` = 「没有这条」，与缺键在语义上不冲突，且全池真值全 0；本账只点名两支闸列。
- 头部「落值口径」长注释**就地订正**（原写「`1` 才落」，已过期），摘要行 `能力闸 …` 改成**直接从产物 `doc["cards"]` 现算**三个数（`=1` / `=0` / 缺键），避免「打印读数」与「真实产物」两处各说一套。

### 1·4 改后读数（`--check` 干跑）
