## 四、`GetOwnedCount` 的放行条件与兜底策略（逐条）

`Pre_GetOwnedCount` 按 `currencyType` 分三档，**每档都写了为什么**：

1. **`cur == 72`（energy）** —— 原方法走 `SharedEventDataManager.GetContext<EnergyContext>()`，**不依赖 manager**。
   - 能读到 `EnergyContext.energyData` 非空 → 用 `GetCurrentEnergy()` 的真实值；
   - 否则（离线 `SharedEventData = {}`，context 可能缺失或没 unpack）→ **100**（= `EnergyConfig.maxRechargeableEnergy` 默认值）。
   - 这是**唯一一种「永远不调原方法」**的情况；因为原方法在 context 缺失时会 throw，在 `energyData` 空时会返回 0（不是离线想要的初始值）。

2. **`cur ∈ {0,10,20,60,70,71}`** —— 先读 `PlayerDataManager.singletonManager.userInfo.UserVirtualCurrency[code]`。
   - 读到 → 直接返回（真实值：gold 2000 / crystals 500 / blackStones **100** / 其余 0）；
   - 读不到（`singletonManager` 为 null / `userInfo` 为 null / 字典里没这个键）→ 进第 3 档。

3. **兜底** —— `manager`（`__args[0]`）非 null ⇒ `return true` **放行原方法**（读真实库存）；
   `manager` 为 null ⇒ 原方法必 throw ⇒ 返回 0，并写 `stubs.tsv` 的 `FALLBACK` 行。

4. **finalizer（`Fin_GetOwnedCount`）** —— 第 3 档放行后原方法仍抛（例如 `Inventory<ICurrency>` 键缺失）时，
   兜底成 0（energy 为 100）并写 `FALLBACK-EXC`，**吞掉异常，不冒进游戏**。

**⚠️ 什么情况下仍会兜底 / 显示 0：**
- `singletonManager` 为 null，且 `manager` 参数为 null ⇒ 0；
- `userInfo.UserVirtualCurrency` 还没被填入（登录未完成就开菜单 —— 实测时序上不会：`UnpackInventory` 12:40:23 早于资源条 12:40:39）；
- 第 3 档放行且库存里确实没有该 Currency 条目 ⇒ 原方法返回 0（这正是 §一 里那条偏差的由来，正常路径已被第 2 档覆盖）。

**⛔ 不再出现的东西**：旧桩的 `GetOwnedCount HIT currency=N -> 硬编码`（`stubs.tsv` 里那 9 条/轮）。

## 七、顺手发现

1. 🔴 **「顶栏数字是假的」的根因不止一个桩**：即使把 `GetOwnedCount` 放行，原始链路也会折在
   **虚拟货币键（`gold/...`）与 Currency 资产 `code`（`C1/C2/C3/C5`）对不上**这一步
   （`AssetLocator.GetAsset<ICurrency>` 取不到 → `Add<T>` 静默丢）。⇒ 要「真复刻」这条链，
   得让离线档案用 `C2/C3/C5` 这类真键，或给 `CurrencyConfig.currencies` 补齐 gold/energy（**数据侧，归别的写手**）。
   目前 mod 侧的做法是绕到源头读 `UserVirtualCurrency`，等价且不依赖资产解析。
2. `CurrencyFixProbe.Codes` 里 `{0,"gold"} / {10,"crystals"} / {20,"blackStones"}` 这套 code 是**离线档案的键**，
   不是原版资产的 `code`。它只影响合成 Currency 的 `GetID()`（本路径已不走库存），**建议保留**，但别再拿它当「原版 id」。
3. `CurrencyExtensions.AddCurrency` 对 `type==72` 有特判：`context.SpendEnergy(amount)`（`CurrencyExtensions.cs:201-212`），
   用的是同一个 `EnergyContext` —— 将来做「花能量」时这条链也是断的（context 可能为 null）。
4. `PlayerDataManager.singletonManager` 是 **public static 字段**，比 `SingletonBehaviour<T>.Instance`（泛型基类属性，
   反射容易取不到，`InventoryProbe` 的 `no-InventoryManager` 大概率就是栽在这里）更好用 —— 以后读全局管理器优先用它。
