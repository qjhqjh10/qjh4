### `FindDamagePopNear` 为什么不是自证

- 它挑「哪一颗」用的是 **`PopDamageIcon` 子件**（生产 `PopNumber` 的建法）与 **位置**；而断言随后量的三件事分别用**独立**期望值：
  - 卡身中点 = `body3D` 网格包围盒 + `CardView.Height`（⛔ 不读 `PopOffset`）；
  - 血痕局部 y（`PopNumber` 的 −0.104 卡单位）；
  - 离 2D 行线 `SlotPosition` 的距离（两个基准的真实间距 0.0379）。
- 位置选择本身用 radius=1.0：**远小于**两行卡之间的距离 2.42（不会挑到攻方那颗），**大于**「3D 投影点 vs 2D 行线」的 0.0379（`SlotPosition` 回归档仍能被挑到 ⇒ 由 `dLinePop` 那条判红，鉴别力保住）。

## 二 · #19 的核实结论（要求「先核实是录像侧还是引擎侧」）

**结论：都不是生产缺陷，是断言的量点选错了（δ 类）。** 证据链：

1. 日志现读：`battle.log:924661` = `座位0 30 张 / 座位1 32 张`； `:924674` = `座位 0 少 1 张（UM52，须为 defence）`**绿**；`:924687` = `座位 1 少 1 张（GOF8 ...）`**红**。
2. 查卡表 `RuleEngine/Resources/cards_engine.json`：`UM52 = Firestrike Turrets · defence`、**`GOF8 = Hornhelmz' Boy · unit`**（Goff 单位，**不是**防御卡）。
3. 所以 #19 **不可能是**「先手那张防御卡」那条机制（报告 §一 #19 的推荐改法是基于这个假设，**该假设不成立**）：那一条只会在 `missIsDefA2` 上是 defence 时成立，而它连 `CardDatabase.FindById` 都没命中成 defence。
4. `RuleCore.BuildPlayer`（`RuleCore.cs:624-632`）逐卡只做三件事：第一张 `hero` 进 `warlordCard`、第一张 `defence` 进 `defenceCard`、**其余全部 `p.Deck.Add(...)`** ⇒ **结构上不可能丢掉一张单位卡** ⇒ GOF8 不是建牌库时丢的。
5. 座位 0 丢的正好是 defence（= 它是**先手**：`getsDefenceCard: ctx.FirstSeat == 1`，先手那一方的防御卡只分流不发）⇒ 先手契约本身**自洽**，#19 与 #17 不是同一根因。
6. 那只剩一个解释：**这一局打了 43 条动作**，GOF8 在对局中离开了 `Deck/Hand/Discard/Board/督军` 这五个计数区 —— 引擎里真有这类路：移出游戏（`RuleCore.RemoveCardFromHandToRemoved` → `ctx.Removed` 记账、**不进弃牌堆**，原版 `PlayerHand.RemoveFromGameCard`）· 手牌变身（`EffectResolver.cs:3603` 换实例、卡 id 变）· 被偷（`ResolveStealFromDeck` 挪到对面）。

**修法选择**：把量点从「打完一整局之后」挪到「开局换牌走完那一刻」。这样这条断言量的正是它自己 doc 写的那件事（`ReplayRecord.hostCardIds` 记的牌 == 引擎真建出来的那副），而且**结构上只有防御卡一条差异**（先手那方少一张 defence）。

⚠️ **残留风险（如实写）**：如果调度台认为「一张单位卡在整局里彻底消失」本身可疑，那要另开一条**引擎账**去查（本次没查：查它需要跑引擎探针，超出本文件白名单）。本报告**不断言**那张卡是被偷/变身/移出游戏中的哪一种 —— 只证明「不是建牌库丢的、也不是先手契约」。
