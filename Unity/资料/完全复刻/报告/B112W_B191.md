`Read(Texture2D t)`（改前 `:109`，新 `:109`）是 `Compare()` 唯一的像素入口，**两条路**：

| 路 | 条件 | 返回的是什么坐标系 |
|---|---|---|
| A `GetPixels()`（`:113`） | `t.isReadable` | **存储的原始纹素值**（不做 sRGB 解码） |
| B GPU 回读（`:114-125`） | 不可读 | 改前：`RenderTextureReadWrite.sRGB`（`:115`）+ `new Texture2D(..., RGBA32, false)`（`:119`，第 5 参默认 `linear:false` = sRGB） |

改前 B 路的实际语义（推导，见 §三 的模型说明）：

- 源是 **sRGB 颜色图** ⇒ 采样解码 + 写回编码，两次抵消 ⇒ 返回 `≈ 原始纹素值`（与 A 路一致，只差 ≤1/255 量化）；
- 源是**线性数据图**（原版序列化 `m_ColorSpace: 0`：法线 / 遮罩 / Noise） ⇒ 采样**不解码**、写回**照编一次** ⇒ 返回 **`sRGB_encode(原值)`（偏亮）**，**与 A 路不一致**。

⇒ **同一个函数的两条路返回两种坐标系**。这就是「拿它比线性数据贴图时读数会假」的确切机制（后果见 §三）。

### ② `MeshSanityProbe.cs` —— **核过：这一处「写死 sRGB」是对的，故意不改**

`Shoot(name, m)`（定义在 `:60`，RT 在 `:84` → 新 `:91`）渲的是**一个网格**，管线是：

```
new GameObject → MeshFilter.sharedMesh = m
MeshRenderer.sharedMaterial = new Material("Universal Render Pipeline/Unlit")   :70
    _BaseColor = white   :71
    _BaseMap   = null    :72      ← 没有任何贴图参与
Camera → RenderTexture(ARGB32, sRGB) → RenderPixels → Texture2D(RGBA32, linear:false) → EncodeToPNG
```

⇒ **本方法里根本不存在「源贴图」**，也就没有「源的 `m_ColorSpace`」可跟 —— 简报里「拿它们比线性数据贴图」这个前提，对这一处**不成立**。
而它产物是**给人看的 PNG**（判「网格形状/顶点坏没坏」，见文件头 `:1-11`），要的正是**显示就绪的 sRGB**：

| 工程色彩空间 | `sRGB` RT 的实际行为 | 产物 PNG |
|---|---|---|
| Linear | 着色器输出线性值，硬件**写 RT 时编码**成 sRGB 存储 | 字节 = sRGB ⇒ **看的时候亮度正确** ✅ |
| Gamma | 整链不转换 | 字节 = 原值（gamma 空间）⇒ **亮度正确** ✅ |

⇒ 若按简报「改成 Linear」，**Linear 工程下 PNG 会变成未编码的线性字节（肉眼偏黑）**，反而让人误判「这个网格做暗了」—— 那才是把工具改坏。

**本单对它做的唯一动作** = 在 `:84` 上方补 7 行注释把上面这条钉死（⛔ 防止下一个人拿同一张施工单再"修"一次），并把 `:88` 的
`new Texture2D(512, 512, TextureFormat.RGBA32, false)` 的第 5 参**显式**写成 `false`（行为完全相同，只是把「与 RT 同为 sRGB」这个配对约束写进代码，避免有人只改一半）。

## 三、改动前后读数差异（哪些输入会变、哪些不变）

### 先说模型（⚠️ 本单**没有跑 Unity**，这条是推导，不是实测）

`Graphics.Blit` 的一次往返 = 「**采样时按源贴图的 sRGB 标志解码**」+「**写入时按 RT 的 sRGB 标志编码**」；
`ReadPixels` 把 RT 存储拷进目标纹理，**目标纹理的 `linear` 标志与 RT 一致时不做转换**。
Linear 工程下这两次转换真实发生；Gamma 工程下整链不转换（⇒ 只会错在一边）。这条模型与 `B-184` §二 用的是**同一个**（该单同样未实跑，见其 §六 第 3 条）。

### 改后的不变式（这是本单要达到的东西）

> **`Read()` 的两条路现在都返回「贴图存储的原始纹素值」**（不做 sRGB 解码/编码）。
> **改前**只有 A 路（可读）满足这条不变式；B 路对**线性数据图**返回 `encode(原值)`。

### 变 / 不变 对照表

设 `v` = 原件存储的纹素值，`E()` = sRGB 编码函数（`E(v) > v`，中间调差得最多）。

| # | 输入 | 改前读数 | 改后读数 | 结论变没变 |
|---|---|---|---|---|
| 1 | **源是颜色图**（`isDataSRGB=1`，含本工具现挂的 `Glow`/`LightningTrail`/`Lightning_Burst_Random`） | B 路 = `E⁻¹` 再 `E` ≈ `v` | **逐字同一条代码路径**（`SrcIsSrgb` 返 `true` ⇒ `sRGB` / `linear:false`） | **一个数字都不变** |
| 2 | **两边都可读**（`isReadable=1`） | 从不走 RT，`GetPixels` 原值 | 同左（`if (t.isReadable)` 在 RT 之前就 return） | **完全不受影响** |
| 3 | **源是线性数据图 + 导出 PNG 是对的**（PNG 字节 = `v`），且 PNG 的 `.meta sRGBTexture: 1`（= `B-184` 重跑前的现状，`:82` 现读 `RippleSubtle`/`EarthCrackNormal` 就是这档） | 源→`E(v)`，PNG→`≈v` ⇒ **报「有差」**（比值 >1、源侧偏亮）⇒ **假差异**（会让人去"修"一张本来正确的图） | 源→`v`，PNG→`v` ⇒ **报「一致」** ✅ | **变了，而且是变对** |
| 4 | **源是线性数据图 + 导出 PNG 被编码过**（字节 = `E(v)`，即 `B-184` 那 22 张） | 源→`E(v)`，PNG→`E(v)` ⇒ **报「完全一致」** ⇒ **假通过**（正是这个 bug 当年没被这个工具抓到的一部分原因） | 源→`v`，PNG→`E(v)` ⇒ **报「有差」** ✅ | **变了，而且是变对** |
| 5 | **源是线性数据图 + PNG 的 `.meta sRGBTexture: 0`**（= `B-184` 重跑之后的正确状态，PNG 字节 = `v`） | 源→`E(v)`、PNG→`E(v)` ⇒ 判「一致」（**判对了，但读数是编码空间里的数**，MAE/比值不可当原值看） | 源→`v`、PNG→`v` ⇒ 判「一致」**且数值是真的原值** | **结论方向不变，数值会变**（两个数都会降一个"编码"的量） |
| 6 | PNG 是**可读**导入（`isReadable: 1`）+ 源是线性数据图 | 源 `E(v)` vs PNG `v` ⇒ **假差异**（最常见的一种） | 源 `v` vs PNG `v` ⇒ 一致 ✅ | **变了，而且是变对** |

**一句话**：「什么情况下读数会被修正」= **只要比的两边里有一边是「不可读的线性数据贴图」**（第 3/4/6 档）；
「什么情况下不变」= **颜色图**（第 1 档，本工具现挂的 3 张全在此）· **两边都可读**（第 2 档）· 第 5 档只是数值换成真值、结论方向不变。

⚠️ **对现有产出的影响 = 0**：`TexCompare.cs:18-21` 的 `Names` 只有那 3 张 `sRGB=1` 的图 ⇒ **改前改后跑出来的表逐字相同**。这一单修的是「**别人把数据贴图加进来时**」的读数正确性（也修掉了 `B-184` 报告 §七 第 3 条那笔账）。
