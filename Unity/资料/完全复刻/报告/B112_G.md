## ③ 迁移设计（判据 / 挂点 / 为什么）

### 3·1 「坏」的判据

`amount == 1`（`Inventories.BadCardAmountSentinel`）。

**为什么 1 一定是坏的**：全解锁口径下基准量 = `DeckCap(rarity) + (NeedCopies[MaxLevel] − NeedCopies[1])` = `CardProgress.Owned` 的「给足」档，**恒 ≥ 10**；而且本工程**没有任何扣卡路径**（`CardDetailPopup.DoDowngrade` 的注释原文：「不消耗任何东西……升级那一路本来就只做『够不够』的检查、不真扣」）⇒ 合法值不可能掉到 1。1 只可能来自 `B-14` 修之前那条「第一次开收藏窗前领卡」的坏写入。

### 3·2 「该有多少张」的判据 —— ⛔ 没有第二份算法

**不自己算**。做法是三步：

1. 把坏条目从 `Inventories.Cards` **摘掉**（新加的 `Inventory<T>.RemoveEntryForMigration`，只给迁移用）；
2. **原样调一次** `Inventories.SeedCardsAllUnlocked(pool, c => CardProgress.Owned(c.Id, c.Rarity))`
   —— 与 `Shell/CollectionWindow.cs:903`（`CardsState` getter）**逐字同一句**，连 `amount` 回调都是同一个；
3. 条目不在背包里 ⇒ `Owned` 走它的「给足」分支 ⇒ 拿到基准量（11 / 10）。

**为什么不用施工单那种「把已有条目补到 n」**：`Owned` 对**已在背包里的**条目直接回条目数量 ⇒ `n` 就是那个 `1`，**补了等于没补**（`判据/B110_V2` 四① 的实证，`B111_S2` 的 A4 🧨 一栏也把这条写死了）。

**卡池来源**：`RuleEngine.CardDatabase.Load()`（进程级缓存、返回浅拷贝）。它与 `DeckEditorState.Pool` 是**同一份来源**（`CardsState` 就是 `new DeckEditorState(CardDatabase.Load())`）—— ⚠️ 这里**故意不**去摸 `CollectionWindow.CardsState`：那会在「`Load` 早于 `CardsState` 构造」时**递归回 `Load`**（那条链是 `CardsState → ShowInCollectionOnly 设置 → Seed → Load`）。播种口径本身一个字没变。

### 3·3 挂在哪儿 / 为什么

`Shell/Inventory.cs` 的 `InventoryStore.Load`，在 `inv.RestoreAmounts(am);` **之后**、`return extras;` **之前**，**同一物理行追加**（⛔ 不新增行 ⇒ 全文行号零漂移）：

```csharp
inv.RestoreAmounts(am); if (inv is CardInventory) Inventories.MigrateBadCardAmounts(am);
```

**选这一拍的三条理由**：

1. **它就是「读盘之后、任何消费者之前」**：`CollectionWindow.CardsState`（`:903`）的顺序是「`_cardsState = new …` → `SeedCardsAllUnlocked` → `InventoryStore.Load` → 返回」，迁移完刚好把值交出去 ⇒ 收藏格「xN」/ 卡组编辑池计数 / `CardProgress.Owned` 拿到的**已经是修好的值**。
2. **只有卡背包受影响**：`inv is CardInventory` 挡掉 `Inventory<ShopItem>`（商店）/ 异画 / 万能卡三份背包。
3. **天然继承两道安全门**：`Load` 开头已有 `if (!StoreOn) return extras;` ⇒ **批处理 / 自检（没注入 `OverrideDir`）一个字节都不碰玩家真档**。

`diskAmounts` 用的是**刚从盘上读出来的** `am`，不是读背包 —— 因为 `RestoreAmounts` 的契约是「已在的改、不在的跳过」，读背包会把「盘上是 1」和「内存里是 1」混掉。

### 3·4 三条硬要求怎么落地

| 要求 | 实现 |
|---|---|
| **幂等** | 修完的条目 ≥ 10 ⇒ 第二遍找不到 `amount == 1` ⇒ **连 `Save` 都不调**（文件逐字节不变）。另有进程级 `_cardsAmountMigrationDone` + 重入位 `_cardsAmountMigrating`。 |
| **可回滚** | 写盘前把**要改的那几份档**各复制一份 `<档>.B112G-bak-<UTC 时间戳>`（**同目录** ⇒ 回滚 = 改名回来）：旧档**总是**备份；中央档**只在 `SaveCenter.StoreOn` 为真时**备份（那时 `SaveThroughLegacy` 才会写它）。**备份失败 ⇒ 整次迁移不动**。 |
| **只动坏的** | `amount != 1` 的条目一条都不碰；**一条坏记录都没有时连 `Save` 都不调** ⇒ 正确档**逐字节相同**。 |

**另外两道保守闸**（都是「宁可这轮不修，也不许毁数据」）：

- **行集守恒闸**：`InventoryStore.Save` 写回的是 `SnapshotAmounts()` ⇒「盘上有、背包里没有」的 id 会被**静默丢掉**。发现这种行 ⇒ 整次迁移不动 + `LogError`（列出是哪些 id）。
- **修不好就不写**：播种之后若仍 ≤ 1（例：`WarpforgeCardLevels.json` 的 `owned` 把它压成 1）⇒ 那几条 `LogError` 出声、**不写盘**；一条都没修好 ⇒ 整次不写。

### 3·5 失败一律出声（不静默）

| 情形 | 行为 |
|---|---|
| 卡池为空 / `Inventories.Cards` 为 null | `LogError` + **不动**（且**不置「已跑过」位**，下次还有机会） |
| 某个 `amount == 1` 的 id 在卡池里查不到 | `LogError` 列出这些 id + **这几条不动**（⛔ 不猜稀有度） |
| 备份失败 | `LogError` + **整次不动** |
| 落盘失败 | `LogError`（带 `InventoryStore.LastStoreError` + 备份路径）⇒ **内存已修好**（本次运行可见）、盘上仍旧；下次启动再试 |
| 抛异常 | `LogError` + 整次放弃（备份若已生成会写明路径） |
