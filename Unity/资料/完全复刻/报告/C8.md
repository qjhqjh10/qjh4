## §二 逐件判据（现读，⛔ 不重抄判据文件）

### ② 410 去重
- **字段**：`CardAbility { trigger @0x10; abilityContext @0x14; priority @0x18; playIcon @0x1C; **triggerValue @0x20** }`（`dump.cs:20340` 起）⇒ `.c:158` 的 `*(int*)(lVar2+0x20) == 1` 就是它。
- **语义**：一趟 `TriggerAbilities` 里 `obj = null`；逐件附魔 → 逐条 ability：
  `if (附魔卡 != null && obj == 附魔卡) continue;`（`.c:136-137`）→ `if (trigger == 410 && triggerValue == 1) obj = 附魔卡;`（`.c:148/158/163`）→ 派发（`.c:184-186`）。
  ⇒ **同一件附魔**本趟派过一条 `410 ∧ val==1` 之后，**它后面的 ability 全跳过**（比的是 `CardScript` 引用 ⇒ 同卡的后一次挂载也跳）。
- **只在广播 trigger == 410 时可能生效**：`CardAbility__CanTriggerAbility.c:71` 已要求 `ability.trigger == 广播 trigger`。
- **现读可达性（我自己重算，不照抄）**：`资料/普查产出_1018/allcards_1350/cards_raw.json` 1,351 张 / **1,496 条 ability 全带 `triggerValue`**；非零 **59 条**（与判据 §2 的 59 一致）；其中 `trigger==410 ∧ triggerValue==1` **仅 1 条** = `Hallowed Martyrs`（`752141bbf0543314987e3b9afed938af`）⇒ `enchantment_templates.json` 里它的 `abilities = [{"trigger":130,…}, {"trigger":410,…}]` ⇒ **410 在末位、后面没有可跳的** ⇒ **结构性存在、零可观测**。
  ⚠️ 判据 §3 写「该模板**不在池**」—— 现读 `owners = [{'id':'SOR57','buffType':12,'trigger':0,'inPool':True}]` ⇒ **挂载者 SOR57 在池**；「不在池」指的是**模板本身**不是可玩卡。另外 `CardDatabase.LoadEnchantmentTemplates` 至今**没挂** `AttachTriggerAbilityIndices`（判据 §3「还差什么」）⇒ 即便挂上，它的 ability 行也读不到。

### ③ `enchantmentCardId`
- `AbilityData { … blockPlayerActions @0x48; **enchantmentCardId @0x4C** }`（`dump.cs:19556`）；`TriggerAbility(…, RawCardScript enchantment, **int enchantmentCardId = -1**)`（`dump.cs:23484`，`.c:72` `*(AbilityData+0x4c) = param_9`）。
- 实参读的是 **`ActiveEnchantment.enchantmentCardID // +0x18`**（`RawCardScript__TriggerAbilities.c:184-186`；交叉 `out_il2csharp/RawCardScript.cs:1136`）⇒ **不是能力下标**。载体自己那趟传 `-1`（`.c:231/257`）。
- 值 = `bm.enchatmentsUsed`（本局第几件挂上去的附魔）—— 我们 `Enchantments.Attach` 早已同源写了 `ActiveEnchantment.EnchantmentCardId`。
- 下游唯一消费 = `CardEffect.enchantmentCardId` 当**合并/去重键**（`CardEffect.IsSameEffect` / `CardScript.AddEffect` 合并循环）⇒ 我们从不合并 ⇒ 零差异。

## §六 没查清 / 留给后来人

1. **`HasTriggerAbilityWithValue` 的「列未知 ⇒ 不闩」是我按「保持旧行为」选的**，⛔ 不是原版判据（原版恒有 `cardAbilities`）。理由：列未知时我们判不了，猜「有」会**凭空少派**。若将来判据要求别的口径，改这一个 `return false` 即可。
2. **粗粒度 vs 细粒度**：原版逐 **ability** 判，我们一件附魔**一发信号**。若某张卡出现 `[410(val1), X(同 trigger)]` 这种「标记后面还有同卡 ability」的形状，**原版会只跳到 X、我们整件只发一次**（等价）；但若出现 `[X, 410(val1), Y]`（标记在中间），**原版 X 照发、Y 跳**，我们的「一发」无法表达 ⇒ 那时必须改成逐 ability（`B109_R2` §4.3 A5 那一笔）。现池无此形状。
3. **`Hallowed Martyrs` 的 ability 行仍旧读不到**：`LoadEnchantmentTemplates` 只挂 `AttachCardType / AttachWhileInPlayAnim / AttachPermanentBuffs`，没调 `AttachTriggerAbilityIndices` ⇒ 即便重跑生成器把模板表的 `triggerValue` 写进去，**引擎侧仍拿不到**（判据 §3「还差什么」已记，建议另立一笔）。
4. **模板表 `abilities[]` 今天零消费者** —— 补 `triggerValue` 是备料，不改变行为。
