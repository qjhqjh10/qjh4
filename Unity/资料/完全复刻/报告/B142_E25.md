### 为什么框高取 `clamp(自然高, 90, 200)`

原版那颗 TMP 的**容器高**不是常数 —— 它由同一 GameObject 上的 `ContentSizeFitterMinMax` 每帧写成
`clamp(排版后的首选高, 90, 200)`（反编译 `ContentSizeFitterMinMax__ClampSize.c`：先 `get_sizeDelta`，再把 x/y
各夹进 `[widthMin,widthMax]` / `[heightMin,heightMax]`）。面板高 = 该框高 + 上下各 10（布局组 `GetChildSizes`
在 `ChildControlHeight=0` 时取 `child.sizeDelta[axis]` 作 min，`HorizontalOrVerticalLayoutGroup.cs:226`）。

所以「框高」的两个界**就是** `MinH − 2×PadY = 90` 与 `MaxH − 2×PadY = 200` —— 我们**直接由面板常量推**，
⛔ 不另写一对 90/200（两处写同一个判据迟早不一致）。断言 `A2/A3` 把这个同源关系钉住了。

收敛形状（与原版一致）：自然高 ≤ 200 ⇒ 框 = 自然高（装得下）⇒ 字号仍是 28；
自然高 > 200 ⇒ 框 = 200 ⇒ TMP 在 `[10, 28]` 里二分开、缩到装进 200 为止；缩到 **10 px 仍超高** ⇒ 停在 10、
正文照样画出去（`m_overflowMode: 0`），面板被 `MaxH` 夹在 220 —— 这两档与原版逐条同形。

### 棘轮坑（简报点名的那条）—— 为什么这里**不会**棘轮

`SetAutoFitBox` 的二分上下限是从 `cur = TmpFontSize()` **折出来的**，而 `TmpFontSize()` 读的是
`_glyphHeight`/`_capHeight`（`Battle/Label.cs:1499-1512`）—— 那是**调用方要的那个字号**，
**不是** `_tmp.fontSize` 的收敛结果。我们每次 `Layout` 都先 `SetScriptHeight(wrapped, 28, UnitPx)`
（`Tooltip.cs:603`）把这两个值重新钉回 28 px，再调 `SetAutoFitBox` ⇒ 每次都从 28 重新二分。

旁证（TMP 侧）：`OnPreRenderObject` 每次开头都 `if (m_enableAutoSizing) m_fontSize = Mathf.Clamp(m_fontSizeBase,
m_fontSizeMin, m_fontSizeMax)`（`TextMeshPro.cs:2145-2146`），而 base 由 `SetAutoFitBox` 每趟重写成
`cur × (basePx / nomPx)`（这里 basePx = 28 = nomPx ⇒ base = cur）⇒ **结构上不会「只缩不回升」**。

### 两条顺带的正向变化（都是**朝原版靠**，不是副作用）

1. **`textWrappingMode` 从 `NoWrap` 变成 `Normal`** —— `SetAutoFitBox` 内部必调 `SetWrapWidth`，而它写死
   `Normal`（`Core/TmpFont.cs:659-664`）。原版正文就是 `m_TextWrappingMode: 1`（`prefab:497`），
   我们原来是「只靠手折行」，现在是「手折行 + TMP 自己在 468.9 px 框里兜底」。⚠️ 见 §四·3 的残差。
2. **正文框第一次真的有了 `sizeDelta`**（`468.9 × 90…200`）—— 原来那颗 TMP 的 `sizeDelta` 是 `(0,0)`。

## 二 · `B142-TOOLTIP-OVERFLOW`：**判据本身错**（⛔ 未改代码）

简报的前提是「原版正文挂 `VerticalLayoutGroup` 往下排 ⇒ 超高**向下**溢出；我们标签锚在面板中心 ⇒ 上下对称」。
**前半句不成立。** 反证三份判据、逐条可复核：

1. **正文的竖直对齐是 Middle**：`prefab:489` `m_VerticalAlignment: 512`（TMP 枚举 `Top=256 / Middle=512 / Bottom=1024`）。
   TMP 的 Middle 档把**整块字的竖直中心**放在**容器矩形中心**：
   `TextMeshPro.cs:4202-4205`
   `anchorOffset = (corners[0] + corners[1]) / 2 + new Vector3(0, −(m_maxTextAscender + …) / 2, 0);`
   —— 溢出时**上下对称**，不是「从顶往下排」。
2. **容器矩形在面板里是居中的**：布局组 `ChildAlignment = 4`（MiddleCenter，`prefab:233`）、
   padding 上下各 10（`:228-232`），而 **`ChildForceExpandHeight=1` 不影响高度**、`ChildControlHeight=0`
   让布局组的 min 高 = 子件自己的高（`HorizontalOrVerticalLayoutGroup.cs:226`），
   `Generic Popup Background` 上的 `ContentSizeFitter(VerticalFit=1, MinSize)` 再把面板高设成「子件高 + 20」
   ⇒ `GetStartOffset` 里的 `surplusSpace = 0`（`LayoutGroup.cs:193-200`）⇒ 子件顶边正好落在 padding.top = 10
   ⇒ **子件矩形在面板里竖直居中**。
3. **主证据只需要 1+2**：矩形居中 + 字块在矩形里居中 ⇒ 字块中心 = 面板中心 ⇒ 超高时**上下对称溢出**，
   与我们今天的行为**同一形状**。所谓「跟着布局组往下排」只在「面板高 > 内容高」时表现为「内容居中偏上」，
   而面板高**恒等于**内容高 + 20（fitter 就是那么算的），所以那个现象在这颗 prefab 里根本到不了。

⇒ **不改代码**（简报要求「结构上做不到就停手给反证，⛔ 别自创方案」，这里更进一步：**判据本身不成立**）。
断言 `B5` 改成**钉反证**：超长（= 溢出那一档）时**正文标签中心 = 面板中心**；
🧨 哪天有人把它改成顶锚（真正的「向下溢出」写法），`B5` 立刻红。

## 四 · 顺手发现（⛔ 本代理未改，建议立账 / 需裁定）

### 1. 🔴 **运行时 `m_fontSizeMax` 不是 28，是 34** —— 短路 tooltip 在原版多半渲 **34 px**

`BasicToolTip` 的 `Text (TMP)` 上还挂着第三颗组件 **`EverguildTextController`**（guid `cea14885…`，
序列化 `maxFontSize: 34` / `minFontSize: 10`，`prefab:554-558`，`m_GameObject = 1703437598541787` = `Text (TMP)`）。
它的 `Awake`（**只在 `Application.isPlaying` 下生效**）做的是（`d:/2/tools/decomp_full/EverguildTextController__Awake.c`）：

```c
if (maxFontSize > 0) { TMP_Text t = GetComponent<TMP_Text>();
                       if (!t.enableAutoSizing) t.fontSize   = maxFontSize;
                       else                     t.fontSizeMax = maxFontSize; }   // ← 28 → 34
if (minFontSize > 0)   t.fontSizeMin = minFontSize;                               // 10
```

⇒ **运行时**那一颗是 `enableAutoSizing=1 / min=10 / **max=34** / base=28`。序列化里的 `m_fontSizeMax: 28`
被 Awake 覆盖掉了（铁律 5·c「一个值 ≠ 全部情况」的又一个正例）。

**后果（推演，未真机验证）**：那颗 fitter 是**自指**的（框高 = 文字首选高），所以每次布局都「正好装得下」
⇒ TMP 的自适应会**一路涨到 `fontSizeMax`**。⇒ **短文案（几行以内）在原版是 34 px**，只有长文案才会缩。

**本批为什么没照做**：
① 我们的框高是**固定**的（= 自然高 at 28），这种框下 `max=34` 与 `max=28` **收敛到同一个结果**（28 附近）——
真正的差在**框高的来源**（原版自指、我们固定），不是那一个参数；
② 照做要复刻那条跨帧的布局反馈回环（TMP 自适应 ↔ `ContentSizeFitterMinMax` ↔ 布局组），属于**新机制**，
且会把「普通文案 28.00」这条**基线**整体抬到 34（+21%），牵动 `B141_W19_Assert` / `B142_E6_Assert` 与所有
以 28 px 为基准的读数 —— 超出本代理简报，按「⛔ 别自创方案」交回调度台裁定。
⇒ 建议新账：**`B142-TOOLTIP-AUTOSIZE-34`**（判据齐，缺「布局反馈回环要不要复刻」的裁定）。

### 2. 🔴 **`B142_E6_Assert` 的 `B9` / `B9b` 会因本批**失效**（该文件不在本代理白名单）

- `B9`：`Near(面板高, 220, 0.5)`；`B9b`：`正文高 > 200`（钉的是「超高就溢出」那一档）。
- 它们的夹具是 **240 个汉字 = 15 行**。15 行落到 **10 px 地板**时约 **194 px**（CJK 行盒 ≈ 1.2933 em，
  `报告/B142_E6.md` §四·3 的数）⇒ **装得进 200 px** ⇒ 自适应会缩到 ~10.3 px、面板 ≈ **214**、正文 ≈ **194**
  ⇒ 两条都会红。
- **不是缺陷，是那两条断言钉的是「还没有自适应时的行为」**。改法建议：夹具换成**更长的文案**（例如 480 字，
  见本批 `B6`），或把 `B9b` 改成「正文高 ≤ 200 **或** em 已到 10 px 地板」。
- `B142_E6_Assert` 的其余条目**不受影响**（`B1` 的 40 字 = 3 行，缩与不缩都在 ±0.4 容差内；`B6/B7/B8/B10/B11` 与本批无关）。

### 3. ⚠️ **`textWrappingMode` 现在是 `Normal`** ⇒ 手折行的「16 字/行」可能被 TMP 再折成 15

`SetAutoFitBox` 必调 `SetWrapWidth`，后者写死 `Normal`。若 `报告/B142_E6.md` §四·3 那条残差成立
（CJK 单字步进其实是 ≈29.5 px 而不是 28 px），则 **16 字 = 472 px > 468.9** ⇒ **TMP 会把它折成 15 字**
⇒ `B142_E6_Assert` 的 `B8`（`最长行 == floor(468.9/28) = 16`）会红，而**画面其实更贴原版**（原版就是 TMP 在
468.9 px 里自己折）。⇒ 建议新账：**`B142-TOOLTIP-WRAP-TMP`**（真机量一次 16 字文案的正文宽即可定；改法是
`MaxCharsPerLine` 那一个商，`Tooltip.cs:613`）。

### 4. 未验证面（如实记）

- 本代理**没跑 Unity / 没跑任何宿主** ⇒ `em` 的实际收敛值、`B9` 那类边界的真实数字**都还没有实测**。
  断言写的是**关系式**（区间 / 相对量），不是本轮量出来的字面量。
- `_h` 用的是 `_body.WorldH`（**墨迹高**），原版 fitter 用的是 TMP 的 `preferredHeight`（行盒口径，通常略大）
  ⇒ 多行文案在我们这里的框可能比原版**紧几像素**，表现为「多行文案的 em 比 28 小零点几个 px」。
  视觉可忽略，但断言 `B1` 只钉**单行**（框被 90 兜住，不受这个差影响）。
