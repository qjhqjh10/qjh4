## 〇、一句话结论

🔴 **三张（`NoiseNRM` / `Gauss Rays` / `Lighting Trail`）不是「sRGB 编码」，也不是「BC7 解码器差异」——
它们的 PNG 是 `DXT5(原版)`：整张图被**一次 BC3/DXT5 编解码**过。**
原版原件（UnityPy 从 bundle 解码 vs `assets_full`）**MAE 0.000 / 100% 逐字节相同**，
所以那层 DXT5 是**我们这一侧**加上去的；而全链路上**唯一**能产生 DXT5 的地方 = **Unity 的导入器**
（这批 PNG 的 `.meta` 是 `textureCompression: 1` ⇒ RGBA 被导成 DXT5）
⇒ **`ImportTexture` 拿到的是「我们自己已经导好的那张工程资产」时，落盘就是把导入器的有损结果写回 PNG。**

已按这个机制加了防护（`AlreadyOurs`）与探针（`WF_TEX_PROBE=1`）。

## 一、逐张：已排除 / 定位到的写法 / 改法 / 未定部分

### 共同的新证据（三张一套，逐张复算过）

| 检验 | 读数 | 说明 |
|---|---|---|
| 每 4×4 块**不同 G/B 值的个数** | `≤4`，且 `{v0,v1,v2,v3}` 满足 **1/3 · 2/3** 关系：`NoiseNRM` **2048/2048 块**、`Gauss Rays` 1116/1120、`Lighting Trail` 739/762 | 这是 **BC1 四色调色板** `{c0, c1, (2c0+c1)/3, (c0+2c1)/3}` 的定义式 |
| 每 4×4 块**不同 A 值的个数** | `≤8`，且落在 **k/7** 上：**1024/1024 块** | 这是 **BC3(DXT5) 的 alpha 块**（8 级插值） |
| **alpha 块内 min/max vs 原版块内 min/max** | 三张**全部 `mean 0.00 / std 0.00`** | DXT5 的 alpha 端点是 8-bit 原值 ⇒ 说明这层编码**是对原版像素做的单次编码**，不是二次压缩 |
| 端点是否落在 **RGB565 网格**上 | `NoiseNRM` G **50.9%** / B **54.5%**（随机 25% / 12.5%） | 4 个值里 2 个是端点（565 网格）、2 个是插值 —— 与 BC1 一致 |
| 原版原件本身 | `UnityPy(bundle 原始字节)` vs `assets_full` 的 PNG = **MAE 0.0000 / exact 100.00%**（三张逐一复算） | 原件是干净的，**差异 100% 在我们这一侧** |

⇒ 之前 `B112W_B184` 看到的三条「已排除」都成立，只是**没排除掉「DXT5 往返」这一项**：
**lag1 自相关 0.66~0.87「空间平滑」与 `(y%4,x%4)` 均匀，在 DXT5 上也完全成立**（小块只有 4 级、
误差在块内是 4 个台阶、看不到 BC7 那种 16 级块结构）—— 所以当时判「不是 BC7 解码器差异」是对的，
但**不能反推「不是块压缩」**。

### ① `NoiseNRM`（128×128）

- **已排除**（沿用 B-184，全部复核仍成立）：sRGB 往返、逐值量化/LUT、重采样/平移/模糊、BC7 块结构、不同源、预乘 alpha。
- **定位到**：`DXT5(原版)`。白噪声形态是因为原图本身就是噪声，DXT5 对高频图最吃亏（MAE 5.43 的来源）。
  `R ≡ 255` 保持不变是 DXT5 的必然：RGB565 里 R=31 两端点、插值后仍是 255。
- **未定部分**：**具体是哪一次调用把「工程资产」传进来的**（见 §二 的探针设计；静态读代码追不出来）。

### ② `Gauss Rays`（256×128）· ③ `Lighting Trail`（128×128）

- **决定性对照**：`Gauss Rays` 与 **`Gauss Rays Noise`** 在 bundle 里**每一项属性都相同**
  （`BC7 · 256×128 · mip 9 · m_IsReadable=False · m_ColorSpace=1`），
  但 `Gauss Rays Noise` 落盘**完好**（4×4 块 ≤4 值的比例只有 **0.13**），`Gauss Rays` 是 **1.00**。
  ⇒ **差异不在格式、不在 `ReadableCopy` 的哪条分支**（两张走同一条 GPU 回读），
  而在「传进来的那个 `Texture2D` 到底是谁」。
- **已排除**：BC7 解码器差异（同一解码链的 `Gauss Rays Noise` 就是好的）、RT 色域（B-184 已改，且改前改后都是本形态）、平移/模糊/通道置换/mip。
- **定位到**：同 ① —— `DXT5(原版)`。

### 改法（已落盘）

`EffectExporter.ImportTexture` 开头：

```csharp
if ((TexCache.TryGetValue(tex, out var c) && c != null) || AlreadyOurs(tex as Texture2D))
    return c ?? (tex as Texture2D);   // 🔴 B-185
```

`AlreadyOurs(t)`：**当且仅当** `AssetDatabase.GetAssetPath(t) == "{TexDir}/{Sanitize(t.name)}.png"`
（= 这张贴图**就是我们要写的那个文件**）时返回 `true` ⇒ **直接返回它，不再编码**。
⛔ 判据故意写成「路径完全相等」而不是「有没有资产路径」——后者会把战场树 / 图集切片那些**该导的**
工程资产全挡掉。

⛔ **不能改成「先 `ReadableCopy` 再 `Encode`」**：工程资产本身在工程里就是 DXT5 压缩的，
`ReadableCopy` 解出来的还是 DXT5 像素，照样把坏值写回盘。

## 二、探针（已加，默认不出声）

```csharp
static void TexProbe(Texture2D src, Texture2D readable)   // ImportTexture 里只加一行调用
```

- 开关：环境变量 **`WF_TEX_PROBE=1`**（`0` / 空 = 关）。平时**一条都不打**，⛔ 不留永久日志噪声。
- 每张打一行：
  `[TEXPROBE] <名字>：实例 <GetInstanceID> · 资产路径 `<AssetDatabase.GetAssetPath(src)>` · fmt= · isReadable= · mips= · 走 {直取 src | GPU 回读} · 像素指纹 <FNV-1a(8bit RGBA)>`
- **打算看的**：
  1. **`资产路径` 是不是 `Assets/WarpforgeVFX/Textures/<同名>.png`** —— 如果是，就当场坐实「第二次是从工程资产重编的」；
     防护生效后应当**再也看不到**这种行（`AlreadyOurs` 提前返回，探针都到不了）。
  2. **`像素指纹` 前后不变** —— 重导一次，同一张贴图如果出现两行且指纹不同，就说明中间被改过。
  3. **`走` 这一列** —— 三张里 `NoiseNRM` 应当显示「直取 src」（`m_IsReadable=True`），另两张「GPU 回读」。
- 指纹用逐像素 8-bit 量化的 FNV-1a（`PixelFingerprint`）。
  ⚠️ 刻意**没用** `Buffer.BlockCopy(Color[], …)` —— `Color[]` 不是基元数组，那句会抛
  「Object must be an array of primitives」（`Color` 是 4×float 的结构体）。

## 五、顺手发现

1. 🔴 **`B112W_B184` 那 22 张「ENCODE」和这 3 张「OTHER」很可能是同一族的两面**：
   都要求「从工程里那张**已经过导入器处理**的贴图」重编一次。B-184 的解释（RT 色域）对**首次**编码成立，
   但**第二次**编码会同时带上色域往返 + DXT5。**建议重导之后，用 §四 的脚本把 484 张整体复算一遍**，
   看编码类是否也一起清零 —— 这一步能一次性判定 B-184 的修法够不够。
   （本报告**不**声称 B-184 的结论错，只标「需要用重导后的读数复核」。）
2. ⚠️ **「一张贴图在一次 Run 里被 import 5 行 ≠ 一定坏」**：本次 484 张里有 **32 张**是 2 次写 + 1 次 TEXFIX；
   但只有 3 张坏。原因是这 32 张里大多数**源本来就是 DXT5**（bundle 里就是 DXT5，全目录 **326/467 张**带 DXT5 块结构，
   那是原版的、对的），再压一次看不出来 ⇒ **别拿「写了两次」当缺陷判据**。
3. 🔴 **`WarpforgeVFX/Textures/` 下的 `.meta` 一律 `textureCompression: 1`（Compressed）**：
   这对**显示**没错（原版也是压缩的），但它意味着**任何一次「读工程资产 → 写回 PNG」都会永久损失精度**。
   以后再加任何「重导 / 修补 / 后处理」贴图的入口，都要先问一句「读的是 bundle 原件还是我们自己的工程资产」。
4. ⚠️ `Gauss Rays` 在**同一次 Run 里被写了两次**，两次的调用栈都是 `DefIndex`（`:2016` 走 trail 材质、`:2031` 走渲染器材质），
   说明**同一个纹理名被两张不同材质引用**、且 `TexCache` 两次都 miss（`AssetDatabase.LoadAssetAtPath` 返回 null ⇒
   `TexCache[tex] = null` ⇒ 那句 `c != null` 短路掉缓存）。这条**不是**本次的病灶，
   但它是「同一张图被处理两遍」的放大器，**值得单独立一条账**（改法：写完之后用 `AssetDatabase.LoadAssetAtPath`
   拿不到就 `AssetDatabase.Refresh()` 再取一次，取到才写缓存）。
5. 📌 **本报告里的所有数字都可复跑**（脚本在 `_tmp_view/b185/`，只读 `d:/2`，未改任何字节）。
