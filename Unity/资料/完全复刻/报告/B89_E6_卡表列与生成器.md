## §3 顺手发现（⛔ 没自己改）

1. 🔴 **L1044 真正的消费者看不到那 3 张附魔模板** —— 这条决定该条能不能收口：
   `HasEnchantmentWhileInPlay` 读的是**附魔卡自己**的 `whileInPlayAnim`，而真值里为 `1` 的附魔卡正好是
   `Undying Legions`（`eab54e4c…`）· `Hive Fleet Leviathan`（`a5960475…`）· `Everstorm`（`7c06b811…`）的
   `m_Name` 尾 `_enchantment` 模板 —— **三张全不在池**。原因 = v30 入池闸是**两条合取**
   （`cardType == 20` **∧** 名字含 `enchant`，`gen_cards_engine.py` 的 `build_enchantment_entries` §③），
   而这三个名字里没有 `enchant`。它们确实**被池内卡挂载**（`SAU53` → Undying Legions · `TL47` → Hive Fleet Leviathan 3 行 ·
   `SW64` → Everstorm，而 `SW64` 自己不在池）⇒ 数据链是通的，只是入池闸拦住了。
   ⛔ 我**没有**动入池闸（会改 `count`，与本批验收冲突）—— 这需要另行裁定：要么放宽入池判据（按 PPtr 挂载而不是按名字），
   要么把 `HasEnchantmentWhileInPlay` 的读数改成「按 PPtr 查真值表」。
2. **`CardDatabase.AttachAbilityDamage` 把 `null` 折成空数组** ⇒ `HasAbilityDamage` 对「旧表 / 未知」**恒真**，
   与它自己 doc 里「`null` = 未知、`[]` = 明确没有」的说法相反（v36 遗留）。我新加的 `AttachPermanentBuffs` **没有照抄**这个行为
   （`null` 保留 ⇒ `HasPermanentBuffs == false`），并在 doc 里写明了这处刻意的不同。**要不要回头修 v36 那个，请调度台裁。**
3. **同名不同物**：真值快照里 `Living Icon` 有**两张** —— 本体 `GSC51`（`cardType 20`）与附魔模板 `0474b163…`（`m_Name` 尾 `_enchantment`、同 `cardType 20`）。
   `permanentBuff` 只在前者的**挂载对象**（后者）身上。⚠️ 任何按**卡名**做 join 的脚本都会把两者混起来 —— 我第一版就是这么读出「0 条」的。
   （同族：`资料/完全复刻` 的「按类名/名字搜不到 ≠ 不存在」那几条。）
4. **`whileInPlayAnim` 在真值里是 `int 0/1`，不是 bool**（1,351 张：`0` = 1,310 / `1` = 41）。落列时按整数判，`bool` 也兼容（`_tri_bool`）。
5. **主动能力费用在池内几乎恒 0**：`manaCost` 只有 `0`（1,095 张）与 `2`（34 张）两档，`psychic`/`plasma` **全 0**。
   ⇒ 「主动能力收费」这一档在今天的卡池里基本是**免费**；`plasmaCost` 与账 L1018 的「等离子死功能」结论一致。
6. **L847 的形状限制**：我们的手牌效果记录（`CardInstance.HandEffect`）不带 `(ab, lg)` 下标（它是从**卡面文本**解析出来的 op）
   ⇒ 逐行版 `PermanentBuffAt` 在 L847 那个消费点**用不上**，只有卡级汇总能判 ⇒ 加了 `HasPermanentHandCostBuff`（🔶 自己设计，已打标 + 写了裁定与理由）。
