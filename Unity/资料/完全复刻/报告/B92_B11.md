## §6 顺手发现（执行代理视角，供调度台分流）

1. **普查表的 `il=N` 列不可单独作证据**（方法名撞名）。本批 90 条里 `il=121` 全是 `.Update(`、`il=352` 全是 `.Initialize(` 的撞名。⇒ 后续若再跑同类普查，**应把 `il` 改成「限定接收者类型」的计数**，否则 470 条本批之外的「内联可疑」同样不可信。
2. **`BattleManager.GetUnitSizeRatio` 的返回值来源**是 `globalVars+0x74`（玩家的那支走常量）。我们 `Board/ArenaSlots.cs` 已有同名；**建议核一下「isPlayer 分支取常量、非玩家取 globalVars 字段」这条口径是否对齐**（原版对两侧用不同值）。
3. **`Countdown` 是 Unity UI Extensions 的库类，游戏没用**（0 附着）。同类「库类误入普查」可能还有——建议普查时对 **0 附着 + 无 MonoScript 的非游戏类**先归「库类」，别与业务码混判。
4. **`ShowStatusWhenConnecting` / `DragButtonInfoInt` / `InRoomChat` / `Reporter` 是 Photon 演示脚本**，`ShowStatusWhenConnecting` 0 附着已确证；`DragButtonInfoInt` 也 0 附着但它那套 `SendMessage(clickedMessage,…)` 反射分发**是 `OnTouchUpAsButton` 家族的机制来源**（业务层别的类仍在用这套命名约定）。
5. **`UIResourceCounter.Initialize` 在 ILSpy 里是 `Decompilation failed: Stack state not settling!`**（Cpp2IL 未复原体），必须读 `decomp_full/UIResourceCounter__Initialize.c` 才看得到接口派发；这是「ILSpy 丢体」的又一例，落点判断不能只看 ILSpy。
6. **`MissionChallenge` 有 25 条本批行** —— 它的 `OnInitialize/OnReset` 是**信号注册/注销**的成对钩子（`Signal.Register` / `Signal.Unregister`）。我们的 `AchievementTally.cs` 若只做「计数」没做「按需注册/注销」，则**挑战被禁用后仍会继续计数**（原版 `DisableChallenge()` 会 `Signal.Unregister`）。建议核对。
7. **`BattleManager.ResolveAction.c` 又确认一例内联**（`ResolveBloodThirstAnim`）。此前已知 `ResolveJamUnit`/`ResolveTriggerSacrifice` 也在里面 ⇒ 这个巨型 switch 是「符号层 0 调用」的**高频藏身处**，后续判死代码应先搜它。
