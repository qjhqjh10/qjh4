## §一 A · 解码口径（逐字）

| 资产 | 源 json | 尺寸 | `m_Format` | `m_DataSize` 实解 | 每体素 | 我们建的 `TextureFormat` | wrap | filter |
|---|---|---|---|---|---|---|---|---|
| `vectorfield` | `Texture3D_-5601361985474094491.json` | 64×64×64 | 8 | **1,048,576 B**（也 = 262,144 体素 × 4） | 4 B | `RGBA32` | `Repeat` | `Bilinear` |
| `SDF_Test` | `Texture3D_-6523327969514304178.json` | 31×31×64 | 45 | **123,008 B**（= 61,504 × 2） | 2 B | `RHalf`（R16_SFloat） | `Clamp` | `Bilinear` |

- 偏移 / 步长：**`image data.$bytes` = base64 直解，无头、无对齐填充**；`m_StreamData.size = 0` ⇒ 数据**内联**、没有外部 `.resS`。
  两条 `m_MipCount = 1`、`m_ColorSpace = 0`（linear）、`m_IsReadable = true`、`m_TextureSettings.Aniso = 1`。
- **行序：不翻转、不重排。** 原始字节就是 Unity `Texture3D` 原生内存序（**x 最快 → y → z**），`SetPixelData` 直接吃。
- 为什么敢这么说（实测，不是推理）：把原始字节按 `png_row = z*H + (H-1-y)` 排进 AssetRipper 的 PNG 里，**mean|Δ| = 0.0000**；
  另三种排布分别是 **5.8867 / 7.0232 / 6.0833** ⇒ 只有「z 正序 + 每切片上下翻转」那一种能对上 PNG
  ⇒ **PNG 才需要翻转，原始字节不需要**。复算命令：
  `python -I -X utf8 d:/4/Unity/工具/build_texture3d.py --verify --png-verify`
- `SDF_Test` 的 PNG 是 **8 bit 可视化**（首像素 26,0,0,255，而原始 half 首值 0.1052）⇒ ⛔ 拿它当数据会掉精度。
- ⚠️ **`m_Format` 的数值编号本轮没查清**（见 §五·3）：8 与 45 在两套常见枚举里都不直接等于「RGBA8 / R16_SFloat」。
  但**不影响落地**：格式靠**字节数与数值分布**双证 —— vectorfield 的 alpha 262,144 个全 = 255、RGB 中心 128（有符号向量场的偏置编码）；
  SDF 的 61,504 个 half **全有限**、范围 −0.1639~0.2888、无 NaN/Inf。引擎侧传的是**具名常量** `TextureFormat.RGBA32 / RHalf`，不靠编号。

**已跑读数**（本轮实跑，`--verify`）：`✓` 两条 sha256 = `b57190b203aa4236…` / `bbf5d826bdae8957…`。

## §五 没查清的部分

1. **`.asset` 能不能真建出来**：本轮按红线**没跑 Unity**；`SetPixelData<Color32>` / `SetPixelData<ushort>` 的**运行时**行为
   （尤其 `ushort` 对 `RHalf` 是否被接受）没实测 —— 所以脚本自带 `SetPixels` 兜底 + 逐字节回读校验，**失败会红、不会静默**。
2. **`RHalf` 的 `GetPixelData<byte>` 是否可用**：验证改用 `GetPixelData<ushort>`（按位比），若该 API 也被拒 ⇒ 自检会打
   `VERIFY-API-UNAVAILABLE` 而不是假装通过。
3. **`m_Format` 数值编号**（8 / 45）：两套常见枚举（`TextureFormat` / `GraphicsFormat`）里都**对不上**「RGBA8 / R16_SFloat」，
   本轮没把 Unity 安装目录的枚举常量实读出来。**结论不受影响**（靠字节数与数值分布双证），但这是**真没查**，不是「查了没有」。
4. **L0 的实际覆盖**：插桩点来自静态识别（1 层直调 + 「把形参喂给包装口」的第 2 层），
   跨文件的动态数据流（`var s = table[i].f; Load(s)` 中间隔了几跳）仍可能漏 ⇒ L0 的读数是**下界**。
5. **两个 Texture3D 的消费端**：AssetRipper 只导出了展平后的 PNG，**没有** `Texture3D.asset`（所以也没有 `.meta` guid 可回写）；
   真正的引用方是还没导入的 `Gargoyle Swarm` VisualEffectAsset ⇒ 「绑回」这一步本轮无从下手。
