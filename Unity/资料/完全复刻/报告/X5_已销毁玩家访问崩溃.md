## ② 运行期会不会也崩：**不会**（只在编辑/批处理下抛）

依据（三条，全部是静态可核的判据）：

1. `WFModuleAnimation.AnimationExitEnd()`（`WFModuleAnimation.cs:223-224`）按 `Application.isPlaying`
   选销毁方式：**运行期 `Destroy(gameObject)`（帧末生效）**，编辑/批处理才 `DestroyImmediate`（同步）。
2. Unity 语义：`Destroy` 之后到帧末之前，对象仍然"可读"——`this == null` 还是 false、
   `transform` 还能取到值。⇒ **同一帧内读 `transform` 不会抛**。
3. 跨帧也安全：`OnDestroy`（`:827-834`）在帧末把 `_destroyed` 置真，而 `Tick`（`:485`）第一行
   `if (_destroyed) return;` 会挡住之后任何一次调用；运行期的 `Update()`（`:475-480`）本身也随对象一起没了。

⇒ **严重级别：只在编辑模式 / 批处理自检宿主里炸**（`AnimFXCheck` / `VFXWhiteboard` 这类手工推 `Tick` 的宿主）。
⚠️ 两条如实交代：**本代理没跑 Unity**，所以"运行期不崩"是上面三条判据推出来的，不是实测；
另外运行期仍留一个**语义瑕疵**（不抛、不影响正确性）：宿主被判死的那一帧，剩下的 `Tick` 还会推一次音效/计时
（原版那一帧 `AnimFXController.Update` 跑没跑过是执行顺序决定的，两种都可能）。

**为什么这次才炸（简报里"extras 刚挂上"这个猜测不成立，已排除）**：
- `_sounds` / `_modules` 与 `WFEffectExtras` **无关**：前者来自 `animfx_modules.json`
  （`AnimFXController.sounds[]`），后者是"非 AnimFX 模块"的补挂。⇐ 与本崩溃无因果。
- 真正的开关是 **R24 断言在 2026-10-25 改过形状**（`AnimFXCheck.cs:693-699`）：
  - 旧形状：`p.Tick(AutoLifetime + 0.01f)`（这一拍进 `Exit()`）**再** `p.Tick(exitClip.length + 0.05f)`。
    第一次 Tick 就把两条音效消费掉了（`sounds[0].time = 0` / `exitSounds[0].time = 0` ⇒ `played = 1 = total`），
    第二次 Tick 销毁宿主后 `TickSounds()` 里 `played >= total` 直接 `continue` ⇒ **根本不碰 `transform`**。
  - 新形状：`p.Exit(); p.Tick(1.08f)` —— 只有一次 Tick，两条音效**都还没播** ⇒ 销毁之后正好走到 `PlayOneSound`。
- 旁证（同族、过去一直没炸）：R23 的 `Pray_Idle` 走的是同一类"模块在 Tick 内销毁宿主"
  （`WFModuleDoDestroyAnimation`，`p.Tick(1.5f)`），但它 `sounds/exitSounds` **一条都没有**
  ⇒ 从来进不到 `PlayOneSound`。⇒ **这条修的是"模块在 Tick 内销毁宿主"这一族，不是 R24 专用。**

---

## ③ 根因（一句话）

`Tick` 把"控制器 Update + 各模块 Update"收口进了**一次**调用，而模块可能**在这次调用内部**把宿主
（= 这个 `WarpforgeEffectPlayer` 所在的根节点）销毁；`Tick` 在模块广播之后没有重新判活，
继续读已销毁组件的 `transform`（编辑模式 `DestroyImmediate` 是同步的，所以当场就抛）。

---

## ④ 改了什么（1 处，零行数变化）

`WarpforgeVFX/Runtime/WarpforgeEffectPlayer.cs` 的 `Tick`，在**模块广播 + 额外组件广播之后、后续任何步骤之前**加一条判活：

```csharp
if (_destroyed || this == null) { Debug.Log("[WarpforgeVFX] 跳过一次对已销毁特效的 Tick 尾部（宿主已被模块销毁 —— 正常收场，不是错误）。"); return; }
```

- 它同时挡住下游四步：`DestroyByTime` 销毁、`_lifetime` 销毁（这两步会读 `gameObject`，同样会抛）、
  `TickSounds()`、`Exit` 计时销毁。
- `this == null` 是 Unity 的"假 null"语义（判据：本项目踩过的同形坑——`_ownerWatch != null`
  在持有者被销毁时恒 false，见 `:499-506` 的注释）。`_destroyed` 由 `OnDestroy`（`:827-834`）置真，
  与它**两条一起判**是为了覆盖"组件被销毁但 `OnDestroy` 没跑"的极端情形；两条都是零成本。
- **出声**：这条日志只在"本帧被模块收掉"时打一次（`Tick` 入口的 `if (_destroyed) return;`（`:485`）
  已经把"跨帧/入口处就死了"的情况提前挡住了）；运行期这个分支进不来（销毁帧末生效），所以不会刷屏。
  日志文案里写明"正常收场，不是错误"，避免以后被当成告警去查。
- 顺手把 `_lifetime` 那个 `if { … }` 块压成一行（本文件已有同样的 `{ DestroyAtLifetime(); return; }` 写法，
  见 `:533`），**目的是保住文件行数 882 不变**——账里 8 处 `文件:行号` 落点
  （`:541 TickSounds` `:556 Exit` `:581 DestroyAtLifetime` `:609 DoDestroy` `:632/:660 OnAnimationEndEvent`
  `:777 TickSounds` `:801 PlayOneSound` `:853-880 SwarmAnimationEnded`）**全部原地不动**，不需要 `--fix`。
  已核：改后 `:541/:556/:581/:609/:660/:777/:801` 逐行仍是原来那个声明。

## ⑤ 为什么没用 `try/catch`

- 这里不是"意外"，是**正常收场**：模块销毁宿主本来就是原版语义（`AnimationExitEnd`），
  `try/catch` 会把"这一次"和"以后那些真错误（表缺条目、节点解析失败、材质没贴图）"混在一个口里，
  正是本项目红线禁止的"静默失败"。
- 正确做法是**在访问前判活**：对象已经判死，本帧剩下的活本来就不该干（原版那个对象也不再有 `Update`）。
- 也没有选择"在 `PlayOneSound` 里再判一次"：同一条规则写两处迟早不一致（本项目已立的规矩），
  而 `Tick` 是 `TickSounds()` 的唯一调用点。

1. **没跑 Unity**：`AnimFXCheck.Run` 需由调度台复跑确认 rc=0、断言合计恢复。
   预期：R24 那条 `Check(mod == null || modGo == null)` 仍然绿（模块确实销毁了宿主），
   日志里会多出一行 `跳过一次对已销毁特效的 Tick 尾部`（**属预期，不是告警**）。
2. **运行期结论是推理**（见 ② 三条判据），没有真机读数；若要实测，观测量 =
   在一个状态动画 `Exit` 的同一帧不出现任何 `MissingReferenceException`，
   且 `WarpforgeEffectPlayer.ActiveCount` 照常回落。
3. **账**：本代理**没有**改 `账/`（含 `_parts/`）。理由：原版 vs 我们的**差异没有变化**
   （`特效动画.tsv:8` 那条 `AnimFXController.Update() → WarpforgeEffectPlayer.cs:483 (Tick)` 仍然成立，
   落点行号也没漂）。是否要在该行补一句"模块可在 Tick 内销毁宿主 ⇒ 我们补了判活"，
   由调度台按账的写法统一决定（避免与既有同名行的合并冲突）。
4. **没做**：`TickSounds` 循环内部若"播一条音效"本身导致销毁（当前无此调用链），没有额外防御 ——
