### ① 减价光环被 `numericOnly` 打掉

**改哪儿**：`RuleEngine/Core/Aura.cs:652`（`RecomposeCore` 的 ① 段）。原来：

```csharp
for (int i = ctx.CostMods.Count - 1; i >= 0; i--)
    if (ctx.CostMods[i].Tag == GrantTag) ctx.CostMods.RemoveAt(i);
```

改成 `for (int i = ctx.CostMods.Count - 1; i >= 0 && !numericOnly; i--)`（**同一行**加一个条件 + 行尾长注释；总行数 **1019 → 1019，零漂移**）。

**判据链**

1. F1 的推断**成立、且是唯一原因**：`numericOnly` 只跳过 **② 费用登记**（`Aura.cs:668` 的 `for (... && !numericOnly; ...)`）与 **②·b 誓约授予**（`:710`），但 ① 段那两行**没有跟着 `numericOnly` 分叉** ⇒ 费用记录被清、不再重加。
2. **为什么选「不清」而不是「清完再登记」**（两种都能修好那个读数，我按口径挑前者）：
   - `CLAUDE.md` §三 明写「**重算必须零副作用（不改 `Health`、不重登记费用、不重授誓约）**」——「不重登记费用」是**写死**的口径，不是我的取舍；
   - 费用档注册是 `f(棋盘, ctx.Active, AuraSpecs)` 的**纯函数**（`Aura.cs:668-688` 只读这三样），而棋盘变动那 12 处写入点**都已经挂过 `Recompose`** ⇒ 动作边界上棋盘没变 ⇒ 「不清」与「清完重登记」**观测等价**，但前者零副作用。
   - 补一条**原版旁证**（不是判据，只说明「不清」不会漏刷）：原版 `BroadcastWhileInPlay`（`BattleManagerSupport__BroadcastWhileInPlay.c:66-125`）**确实会扫双方手牌**再 `UpdateWhileInPlay` ⇒ 费用类 while-in-play 效果在原版确实会在动作边界被重挂。我们的费用档在**棋盘变动**那一趟已经重算过，覆盖同一批状态。
3. ⚠️ **`numericOnly` 现在整层不碰费用档** ⇒ 它与 `Recompose` 的差别从「跳两层」变成「**跳三层**（费用 / 誓约 / 手工费用记录）」，`RefreshInPlayNumericAndKeywords` 的 doc 已同步（它写的就是「跳过费用登记 + 誓约授予」）。

### ④ 相邻锚点丢失 ⇒ 静默空过（本批唯一的**行为改动**）

**根因（比 F1 的推断更准，已坐实）**

F1 的推断是「`FindSlot` 失败 ⇒ 空过」。现读判据 `MinionManager__GetAdjacentUnits.c:52-70`：

```text
在 MinionManager +0x60（己方部队列表）里 **按引用** 找锚点（op_Equality(item, param_2)）
命中 ⇒ 取 i-1（贴列表头就把督军顶上来）与 i+1
没命中 ⇒ 返回空列表（原版**也不**退回整个池子）
```

⇒ 关键不是「锚点在不在棋盘上」，而是「**锚点还在不在那条列表里**」。原版里一个单位 `CheckIfDead` 之后、`MoveToCemetery` 之前**仍在列表里**（`IsInPlay` 那一档 `cardState` 还是 2）⇒ **原版照打邻居**。我们多挂的那道 `anchor.IsAlive` 把这一整类挡掉了。

**改动**（`EffectResolver.cs:1714-1716` 与 `:1746-1753`）
1. 去掉 `anchor.IsAlive` 闸，改成「锚点还在棋盘上（对象引用命中）就用它那一格」；
2. 引用找不到时，按 `RuleCore.BoardOccupantByInstance(ctx, anchor)` 映射（**只认 `Instance`**：锚点翻面成残骸后棋盘上是**另一个对象**；先例 = 眩晕那条 `A1224`；⛔ 不按格号 —— 同批别人真死会让连续列表内移）；
3. 空过支加 `WarnAdjacentAnchorMissing(...)`（`Debug.LogWarning`，每种 `(锚点档, 施放者)` 一次）。⛔ 没有新增 `ctx.Log`（那会改 `ctx.Events.Count` ⇒ 动 `NetProtocol.Fingerprint`，见 `DoStun` 那段同名提醒）。
