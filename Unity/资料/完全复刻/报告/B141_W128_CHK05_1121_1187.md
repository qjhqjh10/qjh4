## 1. L1187 · `PlayerHand.RemoveHandEffectAt(int index)` —— 已修

### 1·1 原版语义（判据全文，`decomp_full/PlayerHand__RemoveHandEffectAt.c:30-40`，2026-11-04 现读）

原版方法体只有三件事，**全程不读 `numberOfUses` / `limitedUses` 任何一个**：

1. 遍历 `currentHand(+0x50)`：若该卡的 `activeEffects(+0x108)` **`List.Contains`** 到 `handEffects(+0x48)[index]` 那**一个对象**
   ⇒ `CardScript.RemoveEffect(该卡, 那条)`；
2. 循环结束后 `activeEffects(+0x48).RemoveAt(index)` —— **按下标、无条件**；
3. 没有别的支路（无早退、无 `Uses == null` 之类的闸）。

配套那一跳的闸：`CardScript__RemoveEffect.c` **首句**是 `if (permanentBuff(+0x74) != 0) return;`
⇒ **永久条只影响「牌身上摘不摘」，不影响「记录表摘不摘」**。

调用点（`grep -rn PlayerHand__RemoveHandEffectAt decomp_full/`，共 5 处）：
`PlayerHand__UpdateCardEffects.c:332`（到期清扫）· `RemoveEffectsFromCard.c:104` · `RemoveFromGameCard.c:39` ·
`CanDrawTurnStartCard.c:86`（`skipCardDraw` 次数核销）· `CardPlayedWithEffects.c:44`（打出核销）。

### 1·2 缺口是什么（账 1187 原文经现核成立）

我方记录身份是**从 `HandEffect.Uses` 那个共享计数盒借来的**：

- `RemoveHandEffectFromHand(ctx, owner, uses, why)` 首句 `uses == null ⇒ return 0`；
- 而 `Uses == null` 正是**不限次档**（`EffectResolver.MakeHandBuffUses(limitedUses)`：`<= 0 ⇒ null`），
  且**今天卡池的全部情况**都是这一档（`GrantHandBuff` 传 `MakeHandBuffUses(0)`、`AttachHandEffectToInstances` 只有自检会传正数）；
- 于是门面 `RemoveHandEffectAt`（`RuleCore.cs:16112`）原来那句 `if (rec == null || rec.Uses == null) return 0;`
  ⇒ **对不限次记录恒空转**（返回 0、表不动）⇒ 原版「谁都能按任意下标摘任意一条」这个出口，我们只覆盖了限次档。

### 1·3 修法（照原版，最小面）

`RuleCore.cs:16118-16120`（3 行 → 3 行，**零行数变化**）：

```csharp
            if (rec == null) return 0;
            if (rec.Uses == null) return RemoveHandEffectRecordAt(ctx, owner, index, "原版 `PlayerHand.RemoveHandEffectAt(" + index + ")` 按下标摘（不限次档）");
            return RemoveHandEffectFromHand(ctx, owner, rec.Uses, "原版 `PlayerHand.RemoveHandEffectAt(" + index + ")` 按下标摘（限次档）");
```

新增 `static int RemoveHandEffectRecordAt(BattleContext, int owner, int index, string why)`（`RuleCore.cs:18842`，
**类尾**，见文件里的 `✅ 已复刻（2026-11-04 · B141_W78 · …）` 标记）：

1. `HandEffectRecords.RemoveAt(index)` —— 原版 `:36-39` 那句，**按下标、无条件**；
2. 逐张手牌 `inst.HandEffects.RemoveAll(e => e != null && !e.Permanent && (ReferenceEquals(e, rec) || (rec.RecordId != 0 && e.RecordId == rec.RecordId)))`
   —— 原版逐手牌 `CardScript.RemoveEffect`；`!e.Permanent` = 那条首句闸；
3. 出声（`ctx.Log`，非静默）。

**为什么身份是 `RecordId`（而不是 `Uses`）**：`CardInstance.HandEffect.RecordId` 是「**同一次挂载**」的记录号
（`EffectResolver.RegisterHandEffectRecord` / `AttachHandEffect` 按号去重 ⇒ 一次挂载一条记录），
而原版的 `List.Contains` 是**对象引用相等**、`RemoveAt` 是**按下标** ⇒「同一对象」和「同号副本」都要覆盖：

- `ReferenceEquals`：首次挂载直接贴在牌上那个对象（表里与牌上是**同一个 `entry` 对象**）；
- `RecordId`：**后来进手牌**的那几张拿的副本（`AttachHandEffectCopy` 照抄 `RecordId`）—— 原版那几张也带着同一个 `CardEffect` 引用。

⛔ 没有改成「按 `Source` 名匹配」（两个来源可以同名）。

**为什么限次档继续走老路**：`RemoveHandEffectFromHand` 已经覆盖它（按盒子引用摘记录 + 按 `ids` 摘牌身），
零行为变化优先 ⇒ 只在「不限次档」这一支分流。**没有**动 `RemoveHandEffectFromHand` 的那句 `uses == null ⇒ return 0`
（它的语义入口 = 次数用尽/到期/载体离场，全部是限次语义）。

## 2. L1121 · `MinionManager.GetNextSlotPos` 的「残余①」—— ⛔ 判据本身错，**不是缺口**

> 账里原文（`战斗逻辑驱动.tsv` L1121 `差异`/`备注` 末段）：

> ⇒ 恒走中性支；原版那一档传 `MousePositionDebug.GetMouseClickPosition`）」。
> **那句话的「事实」对、「结论」错** —— 原版那一档确实传 `GetMouseClickPosition`，但那个函数在 shipped player 里**恒返回 `(0,0)`**。

### 2·1 原版分支矩阵（`decomp_full/MinionManager__GetNextSlotPos.c` 全文，2026-11-04 现读）

`required == 1`（坐标半，`:178-276`）逐支：

1. **右满**（`posA.Count <= rightCount`）：
   - **左也满** ⇒ 督军 `GetEffectAnchor().position`，并**跳过**末尾 `+ ExtraYOnBoard`（`goto LAB_18062a7d7`）；
   - 否则 ⇒ `GetLeftSlotPos(leftCount)`。
2. **右不满、左满**（`leftCount >= posB.Count`）⇒ `GetRightSlotPos(rightCount)`。
3. **两侧都不满** ⇒ **这里才读 `(float)local_48`（= `pos.x`）**：
   - `pos.x < 0` ⇒ 看 `AvailableLeftSlot()`（= `leftCount < posB.Count`）⇒ **恒真**（本支前提就是左侧不满）⇒ 左；
   - `pos.x > 0` ⇒ 看 `AvailableRightSlot()` ⇒ **恒真** ⇒ 右；
   - `pos.x == 0` ⇒ `leftCount < rightCount` ? 左 : 右（平手走右）。
   ⇒ **「鼠标在哪侧就去哪侧」**。注意两支的「否则去另一侧」兜底在本支里**结构上不可能触发**（前提已保证两侧都有位）。

> ⚠️ 这一条我逐句核过 `AvailableLeftSlot/RightSlot`（各自全文 = `count < posList.Count`，`:1-28`）：它们读的正是
> `posB`(0x20/0x30) / `posA`(0x28/0x38) 那两张表 —— 与第 3 步的前提用的是同一批表 ⇒ 兜底支是死支。

### 2·2 三重反证：那两支在 shipped player 里**恒不可达**

**反证 ①（输入恒零 · 硬证据：二进制反汇编）**
唯一会传**非零** `pos` 的调用点是 `BattleManager__GetAnimTransform.c` 的 `case 0xe (14)`：
`MinionManager__GetNextSlotPos(minionMgr, MousePositionDebug.GetMouseClickPosition(...), 1)`
（另一调用点 `AbilityLogic__CreateTempAbilityTransform.c:49` **恒传 `Vector2.zero`**）。

`dump.cs:637653` 给 `MousePositionDebug.GetMouseClickPosition(float ScreenHeight)` 的 **RVA = 0x4F0EC0**。
`工具/disasm_va.py` 反汇编（`D:/2/unity_run_ref/GameAssembly.dll`）得到的是：

```
1804F0EC0  sub rsp, 0x28 / cmp [classinit] / call il2cpp_class_init
1804F0EE0  mov rax,[rip+…]            ; Vector2 的 Il2CppClass*
1804F0EE7  mov rcx,[rax+0xb8]         ; = static_fields
1804F0EEE  movss xmm0,[rcx+4] · movss xmm1,[rcx] · unpcklps · movq rax,xmm1 · ret
```

而 `Vector2.get_zero`（RVA `0x3004080`，`dump.cs:537755`）反汇编出来是**逐指令同形**的同一段
（同样 `[class+0xb8]` → 读静态区 offset 0 的 8 字节）；`Vector2` 的静态区 offset 0 正是
`private static readonly Vector2 zeroVector`（`dump.cs:537610`）。
⇒ **`GetMouseClickPosition` 在 shipped build 里的方法体就是 `return Vector2.zero;`** ——
即 SRP core 源码里 `#if UNITY_EDITOR … #else return Vector2.zero; #endif` 的 `#else` 那一支
（本机两份 SRP core 副本 `com.unity.render-pipelines.core` 的实现逐字如此；`Build()`/`Cleanup()` 在 player 里
编译成**全局空桩 `0x4B33B0`**，编辑器那半的 `OnSceneGUI` 与嵌套类 `GameViewEventCatcher` 在 player 的 `dump.cs` 里**根本不存在**）。
⇒ **`pos` 恒 `(0,0)`**。

**反证 ②（池内形状：14 档只出现在召唤件）**

  ⇒ 选项 14 在池内**只由召唤能力拍用到**，走的是 `AbilityLogic.GetPos(14)` → `CreateTempAbilityTransform(isPlayer, 0, 1)`
