## ② 判据（全部亲读，不是推断）

### 2·1 根因：`JsonUtility` 把 `null` 物化（不是「非空结构体」）

| 事实 | 证据 |
|---|---|
| 清单里**明确写着** `"anchor": null` | `python -I -X utf8 -c "import json;d=json.load(open('…/battlearena1_manifest.json',encoding='utf-8'));print(repr(d['tapHits'][0]['anchor']))"` ⇒ **`None`**；20 条 `tapHits` 里带 anchor 的 = **0** |
| 字段是 **class 不是 struct** | `ArenaBuilder.cs:542` `[System.Serializable] public class TapAnchorEntry` · `:529` 同 `TapColliderEntry`（**所以「结构体所以恒真」那个猜想是错的**） |
| 但 `!= null` 依然恒真 | 项目记忆 `jsonutility-null-subtree`（2026-09-22 实测：`"velocity": null` 等四格解析回来**都不为 null**，且 `velocity.x` 也不为 null）。同一句话写在 `CLAUDE.md` §三 与 `MEMORY.md` 顶部索引：**「JsonUtility 把 null 物化成整棵子树 ⇒ 任何 `!= null` 判据都恒真」** |
| 症状与观测**逐格吻合** | 建场日志报「**锚点 0 条接上 / 失败 20**」= arena1 的 20 条**全部**走进了那个分支；13 场 `tapHits` 里真带 anchor 的只有 **13 条**（arena2 1 / arena3 3 / blacklegion 7 / sororitas 2），其中 arena3 那 3 条有 1 条挂在「无碰撞体」条目上（不进循环）⇒ **循环里只有 12 条** |

### 2·2 第二个出口（同一个 bug，N16 与调度台都没记）

`ArenaBuilder.cs:4275` 原来是 `if (e.collider == null)`。arena3 那条 `Battle Arena 3 Baked` 的 `"collider"` 在清单里是 **`null`**，解析回来是个 `type == null` 的实例 ⇒ 判据恒假 ⇒ 它**没有**走「无碰撞体跳过」分支，而是进了 `AddTapCollider` ⇒ `switch(null)` 落到 `default` ⇒ 打了一句

```

```

### 2·5 为什么旁挂 `nodes[]` 里没有那 5 条（读生成器，不是猜）

`工具/gen_arena_groups.py` 的口径（`:21`、`:560`、`:568`）：`nodes[]` = **`want` 里每条路径的「祖先链 + 子树」− `targets[]`**，而 `want` = **本场清单里每一条会建出来的对象**（`meshes[]` / `particles[]` / 灯）。逐条核：

- **#1 `Squig Anchor`**：父 `Rubble` 在 arena2 的 `meshes[]` 里且 **`"worldBaked": true`**（arena2 共 33 条 worldBaked，全项目只有这一场有）。`wanted_paths()` 把 worldBaked 挡在 `want` 之外（`gen_arena_groups.py:59` 那条「只有一条有意排除」），**它的子树也就没人展开** ⇒ `Squig Anchor` 进不了 `nodes[]`。此外 `ApplyGroupNodes` 还会把 worldBaked 的对象加进 `frozen`（`ArenaBuilder.cs:3102-3105`，不许改挂）。
- **#2–#5 blacklegion**：4 个父 `Grill collision` / `(1)` / `(2)` / `(3)` 在原版的组件是 **`Transform + MeshFilter + BoxCollider + MonoBehaviour(5926791653216923474 = TapHitMaterialDefinition)`** —— **没有 `MeshRenderer`**，是**隐形命中盒**。manifest 的 `meshes[]` 只收**要渲染的**网格（`黑名单` 那套闸门），所以这 4 个父**不在 `want`** ⇒ 子树不展开。**它们本身是我们从 `tapHits[]` 建的**（`hasMesh:false` ⇒ `new GameObject` + BoxCollider），但那是 `BuildTapHits` 干的、比 `ApplyGroupNodes` **晚**（`ArenaBuilder.cs:3005` vs `:3009`）。

> ⚠️ 顺带否掉一条「看着最省事」的方案：**只改生成器把 5 条塞进 `nodes[]` 不行**（见 §⑥ 第 2 条）—— blacklegion 那 4 条的父在 `ApplyGroupNodes` 那一刻**还不存在**，节点会被挂到**场根**并带着原版 local TRS（pos 全 0）⇒ **粒子会跑到世界原点**，比现在更糟。

### 4·3 第三行「Read/Write Enabled」怎么算的、为什么是「预期 N 行」

- 只在**真的要用一颗 convex `MeshCollider`、而那颗网格的 `.obj.meta` 还是 `isReadable: 0`** 时才打（`ArenaBuilder.cs:4593-4610`）。打了会顺手改 `.meta` + 重导 ⇒ **同一颗网格只会打一次**（`_meshReadableDone`）。
- 我的算法：把每个 convex `Mesh` 条目的 `collider.mesh` 按**代码里那套归一化**（空格→下划线 / 小写 / 去末尾 `_数字`）对上 `arenas/<场>/Models/*.obj`，再查那份 `.meta` 的 `isReadable` 现值 ⇒ 数出「仍是 0」的有几颗。
- ⇒ **这是「预期行数」不是硬判据**：真跑时如果某条走了「退回第一个 MeshFilter」（网格名对不上）或宿主匹配方式不同，行数会差 1~2。**只要不出现「重导失败」的告警就不算问题**。

## ⑥ 顺手发现（⛔ 都没改，只报）

### 1. 🔴 `ScaleClose` 拿「清单的模长」比「Unity 带符号的 lossyScale」⇒ 镜像节点恒不匹配 —— ✅ **已按调度台裁定落地**（见「追加轮」）

- **判据**：清单的 `scale` 由 `gen_unity_arena_manifest.py:895 world_scale()` 算 —— `sqrt(sum(M[i][j]**2))`，**是模长、恒 ≥ 0**。而 Unity 的 `Transform.lossyScale` 在**镜像链**（localScale 有负数、行列式为负）上会给**负分量**。
- `ArenaBuilder.cs:4437 ScaleClose(a,b)` 逐轴比 `|a-b| ≤ 1%·max(1,|b|)` ⇒ **符号不同就必假**。
- **实测影响（1 条）**：`battlearena3` 的 `Scenario/Battle Arena 3 Baked/Monolith Front Right/Tap Particles Anchor`，`localScale = (-0.025694, -0.025694, -0.025694)` × 父 `44.0796` = **lossyScale (-1.1326, -1.1326, -1.1326)**，而清单写 **(+1.1326, +1.1326, +1.1326)** ⇒ `ScaleClose` 必假 ⇒ 锚点判失败（而它其实**建出来了**）。⇒ **N16 §⑥ 表 arena3 那格「2 / 0」要改成「1 / 1」**。
- 全 13 场核过：**只有 arena3 有负缩放节点**（5 个：那颗锚点 + 4 个 `LightShafts/…/Rotation`），**只有这 1 条锚点受它影响** ⇒ 影响面很小，但**它会让 arena3 那一场出现一条「这是偏差」的假告警**。
- **建议改法**（一行）：`ScaleClose` 里三处比较改成 `Mathf.Abs(Mathf.Abs(a.x) - Mathf.Abs(b.x))`。⚠️ 它**同时**管 `tapHits` 宿主匹配 ⇒ 会改变 13 场 prefab 的内容（少数原本「另建空宿主」的条目会改成挂到已建节点上）。⇒ ✅ **调度台 2026-10-25 已批准并落地**（见「追加轮」）。
- 复现：`python -I -X utf8 d:/4/_tmp_view/q2/probe_anchor.py`（§②·4 那张表就是它的输出）。

### 2. 🔴 「只改旁挂把 5 条锚点塞进 `nodes[]`」这条路**走不通**（省得下一个人白试）

`ApplyGroupNodes`（`ArenaBuilder.cs:3005`）**早于** `BuildTapHits`（`:3009`）。blacklegion 那 4 条的父 `Grill collision (0..3)` 是**只有 `BuildTapHits` 才建**的宿主 ⇒ 旁挂建节点那一刻父**还不存在** ⇒ `ResolveGroupParent` 失败 ⇒ 节点挂到**场根**、带着**原版 local TRS（pos = 0,0,0）** ⇒ **粒子会跑到世界原点**（比现在「退回世界点 + 法线」更糟）。arena2 那条虽然父 `Rubble` 已建（worldBaked 只是不改挂），但同一个生成器改动会**同时**影响 blacklegion ⇒ 不能只改一侧。

### 3. ✅ 方案：在 `BuildTapHits` 里「找不到就按清单世界 TRS 自建锚点」（约 +25 行，只动我这份文件）—— ✅ **已按调度台裁定落地**（见「追加轮」）

清单里**已经有全部所需数据**（`anchor.go` / `pos` / `rot` / `scale`，都是**世界口径**，由生成器的 `world_trs()` 给出）。`root` 是 identity ⇒ `ApplyTransform` 写 local 就等于写世界，**与原版节点世界位姿逐字段一致**。而原版 `PlayParticle`（`TapHitMaterialDefinition.ParticleCollisionDefinition__PlayParticle.c`）只做 `SetParent(anchor)` + 本地零位 ⇒ **只要世界位姿一致就等价**，不依赖层级路径。

```csharp
// 放在 `:4321` 那个分支里、`nAnchorFail++` 之前
if (def.targetAnchor == null && e.anchor.pos != null && e.anchor.pos.Length >= 3)
{
    // 原版这颗锚点我们没建出来（父可能是 worldBaked 网格 / 不可见命中盒 ⇒ 旁挂 nodes[] 里没有）。
    // 清单给的就是**世界** TRS，root 是 identity ⇒ 写 local 等于写世界；原版只拿它 SetParent + 本地零位。
    var anchorGo = new GameObject(e.anchor.go);
    anchorGo.transform.SetParent(root, false);
    ApplyTransform(anchorGo.transform, e.anchor.pos, e.anchor.rot, e.anchor.scale);
    def.targetAnchor = anchorGo.transform;
}
```
- 覆盖 **5 条**（arena2 1 + blacklegion 4）；**第 6 条（arena3 镜像）不在这个方案里**，它要的是 §⑥-1 那个 `ScaleClose` 绝对值化。
- 命名：原版叫 `GameObject` 的那两颗就照原版叫 `GameObject`（`FindBuilt` / `FindBuiltByGo` 都是「同名取最近」，新建的这颗就在原版位置上，不会抢错）。若嫌脏可加后缀，但**那就不是「照原版」了**，建议照原版。
- 验收：这 5 条不再出「锚点找不到」的 warning，`锚点 接上 / 失败` 变成 arena2 `1/0` · blacklegion `7/0`（再叠上 §⑥-1 则 arena3 `2/0`）。
