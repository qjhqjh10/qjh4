## 四、`BT12`（δ）—— 负控**保留**，改成「删一张引擎真用过的牌」

### 4·2 旧做法为什么没有分辨力（结论采用 `W20AS` §三 的实测，我又把根因读到了 id 级）

旧代码是 `tamperedA2.clientCardIds.RemoveAt(1)` —— 删**固定下标 1**。实测那一趟「按 31 张重建」之后，
**11 回合演完的终局指纹与逐条全量指纹全同** ⇒ 删掉的那张**对整局没有任何影响**。

根因（我读到的，不只是推断）：

- `RuleCore.BuildPlayer`（`RuleCore.cs:613-623`）遍历卡组列表时把**第一张 `hero` / 第一张 `defence`
  单独分流**（`else if (defenceCard == null && c.Type == "defence") defenceCard = c;`），**不进 `p.Deck`**；
- 再往下 `RuleCore.cs:678-684`：`defenceCardOut = getsDefenceCard ? defenceCard : null;` —— **先手**那一方
  连手牌都不发（原版语义：防御卡是**后手**补偿），只打一句 `Debug.Log`。
- ⇒ 录像头里 `clientCardIds` 的形状是「督军 + 防御卡 + 牌库」，下标 1 ≈ **防御卡**；
  删它 ⇒ 重建出的引擎牌库**一张不差** ⇒ 指纹当然全同。
- ⚠️ 这也解释了本节上面那条断言为什么**明确允许差 1 张且必须是 `defence`**（`:43341-43345`）——
  那一局确实存在一个「录了但没进牌库」的位置。

### 4·3 新做法

```
候选 = 「录像这一列（clientCardIds）里记了」∧「UsedCardIds(ctxA2, 1) 里有」
       ∧「CardDatabase 查得到 ∧ Type != "hero" ∧ Type != "defence"」
     → 按 StringComparer.Ordinal 排序 → 取第一张
```

- **为什么用 `UsedCardIds`**：它（本文件 `:47454`）统计的是该座位**所有实例**的 `Card.Id` ——
  牌库 + 手牌 + 弃牌堆 + 场上 + 督军。命中它就等于「这张牌**真的进了引擎那一局**」。
- **为什么排除 `hero`**：删督军会让 `BuildPlayer` 的 `warlordCard` 落空、退回 `FallbackWarlord`
  （`RuleCore.cs:631`）—— 那是**另一种**篡改，量的不是「牌表这一列」。
- **为什么也排除 `defence`**（⚠️ 这一条是我在自审时补上的，理由值得记）：
  防御卡有**两条旁路**，删掉它**不保证**改变引擎状态 ——
  ① **先手**那一方根本不发（`RuleCore.cs:682-684`）；
  ② **电脑侧**发牌时会**丢掉卡组那张**、改用「阵营防御池随机」或「督军自带」
     （`RuleCore.cs:674-677` · `A1070`）⇒ 若替代那张**正好是同一个 id**，引擎状态一个字都不变，
     负控又会静默失去分辨力。
  ⇒ 排除 `hero` + `defence` 之后，剩下的候选**必然进 `p.Deck`**：`BuildPlayer` 只把第一张 `hero` /
  第一张 `defence` 分流，其余一律 `p.Deck.Add(ctx.NewInstance(c))`（`RuleCore.cs:613-623`）。
  ⇒ **删它必然少一张牌库** —— 这是这条负控「一定改得动局面」的硬保证，不是"大概"。
- **为什么定序**：`Ordinal` 取第一张 ⇒ 同一份录像每次挑**同一张**，负控可复现（⛔ 不用字典序以外的序）。
