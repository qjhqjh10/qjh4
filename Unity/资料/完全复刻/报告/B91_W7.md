## §二 判据依据（这一批最值钱的两处）

### 1. `GetMatchmakingFilter` —— 账里的判据本身是错的（不只是实现错）

判据件：`d:/2/tools/decomp_generic_trial/out/FastModeBaseEvent_object__object___GetMatchmakingFilter__1a10120.c`
＋ 同族**非泛型** `decomp_full/Everguild.LiveOps.RankedV3Event__GetMatchmakingFilter.c`（可读、同形状）
＋ `cpp2il/out_cpp2il_dev_ilspy/FastModeBaseEvent.cs:856-944`（给出 `Math.Min` / `tryCount != 2` 的名字）

三条硬结论：
1. **下标 = `param_3 % 3`**（除以 3 的魔数 + `imul esi` 乘回 3），**不是 `% arr.Length`**。
2. **`param_3` = `tryCount`**（第 2 个实参），不是 `gamesLost`。依据：IL2CPP 实参序 = `(currentElo, tryCount, gamesLost)`（`PlayEvent.cs:679` 声明同序）；`param_2` 既做 `currentElo±delta` 的基数，故 `param_3` = `tryCount`、`param_4` = `gamesLost`（`param_4` 正好被传进 `GetSqlFilter` 的**第 6 参**，而 cpp2il 给那一参的名字就是 `gamesLost`）。⇒ 账 row 265 的「差异」列写的「`delta=arr[gamesLost%len]`」是**当年的误读**。
3. **收紧上界支**（原来判「实参读不出、没搬」）其实读得出：`if (tryCount==2 && LegendaryElo <= currentElo) { max = MaxEloCap; min = Min(min, LegendaryElo) }`。两量的身份由 **字段偏移**钉死：`RankedBaseData` 字段序 `seasonNumber / leaderboard / legendaryElo / maxEloCap / ratingDifferenceForMatchMaking` 与 Ghidra 的 `data+0x98 / +0x9c / +0xa0` **逐一对上**（`d:/2/Warpforge_code/Scripts/Assembly-CSharp/RankedFastModeData.cs` + `FastModeData.cs` 字段序交叉验证）。
   ⚠️ 且 `FastModeData`（非 ranked）**没有** `LegendaryElo` —— 原版这一支取的是 `GetData<IRankedData>()`，**普通快模式 = null ⇒ 整支跳过**（这正好解释了泛型版多出来的那个 `if (lVar5 != 0)` 空判）。我们的 `FastModeData` 也不实现 `IRankedData`（本仓无 `RankedFastModeData`）⇒ 本地恒走「跳过」这一支，与原版对普通快模式一致。

### 2. `Expire` 的 `<虚方法 0x758>` —— 从「推断」变「坐实」

- `Expire__1a0f700.c`：`if (SaveGame+0x30 == 0 && virt(0x758)() == 0) { base.Expire(); return; }`
