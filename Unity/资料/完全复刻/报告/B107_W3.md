## 二、查我们的调用点

### 2·1 生产路径上 `GameWindow.Hide()` 只有一个调用点

`grep -rn "\.Hide()" Assets/CardPresentation/` 逐条判过：绝大多数是 `Tooltip.Hide()` / 战斗面板 / `AttackSelector` / `MenuTutorial` 指针等**非 `GameWindow`** 类型。

| 调用点 | 形态 | 判「那一刻可能 inactive 吗」 |

| `Shell/GameWindow.cs:802`（baseMenu 支） | `Close()` 的 baseMenu 支直接 `Hide(); return;` | **可能**：baseMenu 被 `ToBackground()` 压背景后就是 inactive —— **原版同形**（原版 `MainMenuWindow.ToBackground` 也 `SetActive(false)`：`d:/2/tools/decomp_full/MainMenuWindow__ToBackground.c:8-12`），且原版 `CloseWindowCO.c:78-79` 也是「Hide + return」 |

⇒ **没有「对已 inactive 的 `GameWindow` 再 `Hide()`」的额外生产调用点**；唯一的 inactive 档来自 `ToBackground()`（下一小节）。

### 2·2 我们的 `ToBackground()` 族（原版只有 base 那一档）

原版 `GameWindow.ToBackground()` = **只写 `state = Background`**（`out_il2csharp/…/GameWindow.cs:254`）；原版只有 `MainMenuWindow` 覆写它并额外 `SetActive(false)`（`MainMenuWindow__ToBackground.c:8-12`）。

本仓的覆写共 5 处：

| 文件:行 | 是否额外 `SetActive(false)` | 性质 |
|---|---|---|
| `Shell/MainMenuWindow.cs:77-83` | ✅ | **照原版**（原版 `MainMenuWindow.ToBackground` 就是这么做的） |
| `Shell/CardDetailPopup.cs:1006-1011` | ❌（只切顶栏 overlay） | 我们自己的表现层动作 |
| `Shell/ExpansionPassEventWindow.cs:524-528` | ✅ | **我们挑的**（`GachaEventWindow.cs:365-371` 的 doc 写明理由：扁平 quad + 显式渲染队列，不关物体弹窗会被盖住；doc 自陈「⚠️ 这是【我们挑的】处置，不是原版 base 的行为」） |
| `Shell/GachaEventWindow.cs:373-377` | ✅ | 同上 |
| `Shell/RaidEventWindow.cs:433-437` | ✅ | 同上 |

⇒ 这 3 扇窗是「我们多出的 inactive 档」。它们与 `Hide()` 的交互：`HideAllWindows()` 对 `state == Background` 的它们调 `Hide()` ⇒ 首句早退、`state` 停 `Background`；原版（它们不置灰）会走完整 `Hide()` 写成 `Closed`。
**净效果分析**：两条路的**物理结果都是「物体不活」**；回程时
- 原版走 `TryOpen` 的 `Closed` 支（`SetActive(true)` + `state=Open` + **`Open()` 重建内容**），
- 我们走 `Background` 支（`SetActive(true)` + `state=Open` + `ToFocus()`，**不重建**）。
因为物体从未被销毁、内容原样还在，**玩家可见结果等价**；`OnCloseWindow` 那一跳我们不触发（该事件全仓**今天零订阅者**，`GameWindow.cs:693-696` 自陈）⇒ **当前零可观测差异**。

### 2·3 为什么 B106_W79 的「僵尸链」不成立（逐环拆）

被指控的链：「`Hide()` 早退不写 `Closed` ⇒ `ReapClosedWindows` 里 `w.CurrentState == Closed` 不成立 ⇒ 从待收表静默摘掉、不销毁 ⇒ 再 `TryOpen()` 走 `Open` 支 ⇒ 既回不来也销毁不掉」。

1. **`Hide()` 根本不进 `_pendingDestroy`。** 入表唯一入口 = `Shell/GameWindow.cs:805` 的 `Manager.QueueDestroyOnClose(this)`（全仓唯一调用点；`WindowsManager.cs:1652-1656` 只做 `Add`）。而 `:805` 只在 `Close()` 尾部、`:758 CurrentState = Closed` **之后**执行，且 `baseMenu` 支在 `:802` 已 `return`。
2. **`Close()` 自己对 inactive 窗早退**（`:734`），所以在「inactive」状态下调 `Close()` 连入表都到不了。
   ⇒ **待收表里的每一项，入表时都已经是 `Closed`**。要让它离开 `Closed` 只能被重新打开（`TryOpen`，它同时 `SetActive(true)`）；而重新打开那一拍 `OpenWindow` 会先跑 `ReapClosedWindows(keep: win)`（`WindowsManager.cs:292`），`w == keep` 那一档撤销、不销毁（`:1668`）。⇒ **`!= Closed` 那一档只会命中「真的被重新开回来的窗」，「不销毁」是对的**，不存在「该销毁却被静默豁免」。
3. **「再 `TryOpen()` 走 `Open` 支」需要 `state == Open`**；而生产路径上 inactive 的窗只会是 `Background`（2·2 那一族）。`Open + inactive` 这个组合在本仓**只能**来自绕过 `Close()`/`Hide()` 直接改激活态 —— 这正是 `:543-549` 与 `:736-742` 两处守卫**自己点名**的非法档，不是这条链造出来的。

⇒ **结论：该指控描述的现象在本仓不可达**（静态）；`Hide()` 的守卫是照抄原版，⛔ 别改。

## 五、没查清 / 只报了没做

1. **3 扇活动窗（ExpansionPass / Gacha / Raid）的 `ToBackground` 置灰**：这是**我们挑的**（z 序），已在 `GachaEventWindow.cs:365-371` 写明；它让 `Hide()` 在「别的全屏窗压上来」时早退，`state` 停在 `Background` 而非 `Closed`。**静态判净效果等价**（物体未销毁、回程 `Background` 支会 `SetActive(true)`；`OnCloseWindow` 零订阅者），但**未跑运行期验证**。⛔ 不建议为此改 `Hide()` 守卫（那会偏离原版）；若调度台想对齐账，只能在 `WindowsManager.HideAllWindows`（`WindowsManager.cs:454-463`，**不在本代理白名单**）或三处 `ToBackground` 上做，且需要先裁定。
2. **原版 `CloseWindowCO` 的销毁口径与我们不同**：原版**只销毁 `automaticallyLoadedWindows` 缓存命中的窗**（`CloseWindowCO.c:36-47`），其余「摘账不销毁」；本仓把**所有** `Close()` 过的窗延后统一销毁（`WindowsManager.cs:1632` 已标 **🔶 自己设计**，理由 = 收割时机）。**销毁范围**这一格的偏离没有在本报告里进一步核（不在本件范围，且落在 `WindowsManager.cs`）。
3. **`CloseAllWindows()` 的过滤**（`WindowsManager.cs:710` 只摘 `null` / `Closed`）会把上面那 3 扇「inactive + `Background`」的窗**留在表里** —— 它们在原版那一刻会因 `Hide()` 写成 `Closed`、随后被原版的无条件 `List.Clear()` 清掉。本仓这条组合（`CloseAllWindows` 时恰好有活动窗被弹窗压到背景）**未验证可达性/后果**，只把它记在这里，供调度台决定是否另派。⚠️ 这条**不是**本件指控的那条链，别混为一谈。
4. **`MainMenuWindow.Hide` 的烘焙次序**：原版 `MainMenuWindow__Hide.c:5-6` 是「先 `UIBakeScreen.Toggle(true)` → 再 `base.Hide`（含首句守卫）」；我们把 `SetBake(true)` 放在守卫**之后**（`GameWindow.cs:702-703`）⇒ 对**已 inactive** 的常驻主菜单调 `Hide()` 时，原版会再烘一次、我们不会。`ToBackground` 那一侧已经烘过、且 `Hide()` 对 non-baseMenu 是空操作 ⇒ 目前无可观测差异，**只记不改**（若要对齐须先确认 `UIBakeScreen.Toggle(true)` 幂等性对快照的影响）。
