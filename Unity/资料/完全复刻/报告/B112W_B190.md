**原版为什么不矛盾**（本次现读实据）：

- 原版 `EverguildButton.m_Transition = ColorTint` → uGUI `Graphic.CrossFadeColor` → `CanvasRenderer.SetColor`
  ⇒ **走的是顶点色**，不是材质 `_Color`。
- 这支 shader 的字节码（`PYTHONIOENCODING=utf-8 D:/2/Warpforge_tools/py312/python.exe d:/4/Unity/工具/disasm_dxbc.py "Sprite HUE Color change" --stage vs|ps` 现读）：
  - **VS 输入签名**里有 `COLOR 0 xyzw register 4`，`dcl_input v4.xyzw`；
  - VS 体末段 `mul o2.xyzw, r0.xyzw, v4.xyzw`（`r0 = cb0[130] * cb1[43]`）⇒ 把 `COLOR` 转给 PS 的 `v2`；
  - **PS**：`dcl_input_ps linear v2.xyzw` … 末句 **`mul o0.xyzw, r0.xyzw, v2.xyzw`** ⇒ **最终乘顶点色**。
- 另外 PS 开头 `eq r1.x, r0.w, l(0)` + `discard_nz` 用的是**贴图 alpha**（乘顶点色之前）
  ⇒ 顶点色 alpha 改小**不会**触发 discard（不会把整块丢掉）。

⇒ 缺口 = 「我们把原版的顶点色通道换成了材质色」。

## 二、选了哪条路 + 取舍

**选 A：给 `ImageQuad` 加顶点色染色通道。**

| | A（顶点色，**采用**） | B（另写一支带 `_Color` 的等价 shader） |
|---|---|---|
| 与原版一致 | ✅ 原版 uGUI 色偏**本来就是顶点色**，这支 shader 的 PS 末句就是乘 `v2` | ❌ 会给原版材质参数表**多塞一格 `_Color`**（原版属性表里没有它） |
| 判据 | 反汇编 + 原版 `CrossFadeColor` 路径 | 我们自己造的等价物 ⇒ 要打 `🔶 自己设计`（铁律 18·0：只有跟服务器有关才允许自设计） |
| 额外资源 | 无 | 要新建/维护一支 shader 资产，且 `MenuFxMaterials` 的挂载路径要分叉（那是别的代理在用的文件） |
| 风险 | 改共用件 `ImageQuad`（已用 opt-in 开关压到零影响，见 §四） | 两个 shader 会不会画出同一个颜色**没有判据**，只能靠肉眼 |

⇒ B 路与「照原版复刻」（铁律 18·0）相悖，且要多一支没有判据的资产；A 路是原版机制本身。选 A。

**A 路里的三个必答项（简报要求）**：

1. **目标着色器是否消费 `COLOR` 语义** → ✅ 消费，见 §一 的 VS 签名 + `dcl_input v4` + PS 末句 `mul o0, r0, v2`。
2. **顶点色与 `_Color` 会不会双重相乘** → ✅ 不会。新通道**只写顶点色、不写 `_Color`**；目标 shader 本来就没有 `_Color` ⇒ 顶点色在全管线只被乘一次。
   （即使 `MenuFxMaterials` 取不到 shader、退回 `Sprites/Default`（它**有** `_Color`），也只在 `_vertexTint` 为真时走顶点色，
   而 `_Color` 停在 `MenuDraw.Nine(..., Color.white, ...)` 给的白 ⇒ 仍是乘一次。）
3. **既有 `SetTint` 调用点是否受影响** → ✅ 不受影响，见 §四。

## 四、对既有调用点的影响（逐个点名）

**结构性保证**：`_vertexTint` 默认 `false` ⇒ `SetTint` / `Tint` / `RebuildMesh` 三处走的都是**原来那一句**
（`CornerColorsWithTint` 在通道关闭时**原样返回入参**，连数组都不分配）。只有显式调用
`SetVertexTintChannel(true)` / `SetVertexTint(c)` 的 quad 才换路。全仓翻了一遍：

| 调用点 | 是否受影响 | 为什么 |
|---|---|---|
| `WindowButton.ApplyTint`（`:739` `_tq[i].SetTint(...)`） | **受影响，且正是目标** | `_tq` 里既有 HUE 底的九块（`_vertexTint=true` ⇒ 走顶点色），也有图标等 `Sprites/Default` 块（`_vertexTint=false` ⇒ 走 `_Color`）。**逐块分派**，两条路互不干扰 |
| `WindowButton.Collect` / `OnTransformChildrenChanged`（读 `q.Tint` 记基准色） | 语义一致 | 通道开着时 `Tint` 返回 `_vertexTintColor`（出厂 **白**）⇒ 基色 = 白，与原版 `m_NormalColor = 白` 同义 |
| `ImageQuad.SetTint(Color.white)`（`ToastNotifications.cs:1212` `RebuildBackground`） | 不受影响 | 这一句在 `ApplyOrangeButtonToPurple` + `SetVertexTintChannel(true)` **之前**跑 ⇒ 那一刻通道还是关的，走 `_Color` |
| `MenuFxMaterials.ApplyProto`（`q.Tint` + `if (HasProperty("_Color"))`） | 不受影响 | 它在通道打开**之前**读 `q.Tint`；且不写不存在的 `_Color` |
| `MenuDraw` / 其余 **182 处** `SetTint(` 调用行 | **零影响** | 从未调用新的两个方法 ⇒ `_vertexTint` 恒 `false` |
| `ImageQuad.SetGrey` / `EnsureGreyCapable` | 零影响 | 走的是 `_GreyScale` 那一支，与本通道无交集 |
| `ImageQuad.SetCornerColors` / `ForceAspect` 等重建几何的入口 | 组合正确 | `RebuildMesh` 会重新把 `_vertexTintColor` 乘进四角 ⇒ 重建后色偏**不会丢**（这是必须走 `RebuildMesh` 而不是只改 mesh 的原因） |
| `SetFillAmount`（`ChatPreview/Container`） | 零影响 | 它不开通道；`UploadVertexTint` 也显式对 `fill<1` 退回重建 |

**唯一一处「值会变」的**：`WindowButton.RefreshGray` 的 `_grayMats[i].color = qs[i].Tint;`
—— 若哪天 toast 真被置灰（`SoftDisabled` / `Interactable=false`），这里读到的是顶点色（白），
而不是材质色。两条 toast 的按钮**从不置灰**（见 `ShowInternal` 只赋 `onClick`），今天零影响；
写在这里是因为它是「同一颗钮上两条路认的不是同一组图形件」那个老病的同族。
