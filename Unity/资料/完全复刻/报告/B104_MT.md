## §四 语义（照原版，逐条）

1. **建池**：`20`→`[施放者]`；`30`→`[点选目标]`（这两档**不过滤**，与原版同）；`10`→按
   `friendlyUnits/envemyUnits` 取那一方棋盘（`AddSide`，跳过已死），再按 `includeHero/includeMinions/includeRemnants` 白名单裁；
   `110`→目标所在一方的左右紧邻格（锚点自己不算；邻居**不看死活**）；`150`→`ctx.PreviousAbilityTargets`。
2. **逐候选筛**：`ta 10/110/150` 三档统一走 `TargetCriteriaEval.Matches`（`cond` 传 `null`：
   现读**全池 `(ab=-1/-2, lg>=0)` 的 `role="target"` 条件行 = 0 条**，唯一那条是 `SW9` 的 `lg=-1` **ability 级**闸，
   属另一条账 → 见 §六）。判不了（`null`）⇒ **保留候选 + 出声**（本版约定）。
3. **截断**：`maxTargets >= 1 && pool.Count > maxTargets` 才进；`7` 表头取 N · `5` 表尾取 N ·
   `1` `OrderBy(isRemnant)→ThenByDescending(max(近战,远程))` · `6` `OrderBy(CurrentIntrinsicHealth)` ·
   `default(0/4)` = 逐个 `ctx.GetRandomInt(0, Count)` 抽并删。排序档加了「平手按池序」的稳定化（LINQ `OrderBy` 是稳定排序）。
4. **三态返回值**：`null` = 本版判不了/没接（调用方退回改前单数路）；**空表** = 原版这一档确实选不出目标。
5. **多行挑一行**（裁定 ①：按行独立、不合并）：`ActiveAbilityTargetCriteriaForPlan` 先挑
   `ta ∈ {10,110,150}` 的行（**只有这三档会产出 >1 个目标**，也就是唯一需要逐目标播放的那一批），
   没有就取第一行有 criteria 的。⚠️ 这是**表现层近似**（我们一条 `EvtKind.Ability` 只有一张表），已在方法 doc 里写明**不是原版语义**。

### §五·b 夹具修正（第一轮 `RuleEngineTest` 复跑后：B1/B4 红，rc=6）

- **现象**：`B1（前提）主动能力跑出了 EvtKind.Ability` = False（rc=**6**），`B4` 期望 1 实得 0（级联）。
- **根因（夹具，不是产品）**：`RuleCodes.ErrExhausted = 6`。`UnitState` 构造函数末尾是
  `Exhausted = !RuleCore.HasDeployExemption(this)`（`UnitState.cs:916`，= 原版「部署当回合不可行动」），
  而夹具用 `Put` 手摆的是一张**刚落地**的牌 ⇒ 它默认**疲劳** ⇒ `CanStartActiveAbility` 在
  `if (u.Exhausted) return RuleCodes.ErrExhausted;` 那一句直接拒 ⇒ `UseActiveAbilityCore` **在发事件之前**就返回，
  `EvtKind.Ability` 一条都不会有（`B4` 跟着变 0）。
- **修法**（只改 `B104_MT_Assert.cs`）：`SectionB_EndToEnd` 里 `Put(...)` 之后加 `caster.Exhausted = false;`
  （= 「这张牌本回合开始前就在场」），并加一条**前提断言 `B0-d`**：
  `C(RuleCore.CanStartActiveAbility(ctx,0,3), RuleCodes.OK, …)` —— 把「入口闸放行」单独钉出来，
  以后再红就不用靠 B1 的级联去猜。**⛔ 未放宽 B1/B4 断言、未改任何产品语义。**
- **预期读数**：`B0-d` = `0`(OK) · `B1` = True · `B4` = **1** · `B3` = **4**（己方督军+2 部队+施放者）。

## §七 对 `play check` 指纹的**预期**影响（调度台跑 + 重钉）

1. **`AbilityTargetList` 本身不进指纹**（`BattleEvent` 不进 `.json`；`NetProtocol.Fingerprint` 只看局面 + `Events.Count`）。
   本批**没有**任何 `ctx.Log`（出声一律 `UnityEngine.Debug.LogWarning` + 去重表）⇒ `Events.Count` 不变。
2. **会变的是随机流**：命中 `maxTargets >= 1 && pool.Count > maxTargets && targetSelectMethod ∈ {0 random, 4 cardTarget}`
   时**消费一格 `ctx.GetRandomInt`**（原版 `:1258` 同位置也消费）。现池里**同时**满足「`ta` 在本批五档」+「`maxTargets>0`」+「method 0」的卡：
   `SW5 Hunting Wolf` · `SW29 Sons of Morkai Eliminator` · `SW21 Wulfen Pack Leader`（两个能力对象各一行，
   `ta=10 max=1`）· `AM59 Astropath`（`lg=1 ta=150 max=1`）· `SOR37 Triumph of St. Katherine`（`lg=1 ta=150 max=1`）。
   ⇒ **只有当探针真的驱动到这几张的主动能力、且候选数 > 上限**时，随机表游标才会前进、指纹才会变。
   `DA13 Librarian`（method=7）与 `SW9`（`ta=20`，池恒 1 张）**不消费随机**。
3. ⇒ **预期**：若 `play all` 驱动主动能力，**指纹会变、需要重钉**；若不驱动，则**逐字节不变**。
   **本代理没跑 `play check`，上面的名单是静态扫描的预测，请以实跑为准。**
4. 另外两处会被 B104 同批改动影响（不是本代理）：`BattleDriver`/`EffectResolver` 的并行改动 ⇒ 重钉时请**一并**处理。
