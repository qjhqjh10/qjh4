## 四、判读表（实机后照这张表对 `phase0/battlelogprobe.tsv`）

### 4·1 数据到底进没进来（先看这一组）

| 日志 | 含义 | 下一步 |
|---|---|---|
| `SET-BATTLELOGDATA count=3 first={...}` | 登录 unpack **确实**把 3 条写进了 `battleLogData` | 数据侧 OK，问题在渲染侧 → 看 4·2 |
| `SET-BATTLELOGDATA value=NULL` / 完全没有这一行 | 数据**根本没写进** `PlayerDataManager`（尽管 `playfab.tsv` 响应里有） | 查 `UnpackRawUserData`（`PlayerDataKey.BattleLogData=26`）的键名/类型是否对得上；⚠️ 与 `R1/D1` 的 UserReadOnlyData 口径相关 |
| `ONOPEN-IN data{count=3 ...}` | 打开页时字段里确实有 3 条 | 正常 |
| `ONOPEN-IN data{count=0}` 或 `list=NULL` | 打开页时已经空了（被别处清掉，或进的是另一个 `PlayerDataManager` 实例） | 对比 SET 的时间戳与 `pdm=NULL/ok` |

> 首条字段直接给 `ownHeroName/enemyHeroName/matchType/win/lose/...`，可与
> `E:/warpforge/05_工具/server/responses/fragments/playfab_profile.json` 的 `UserReadOnlyData.BattleLogData` 逐字对照。

### 4·2 渲染侧（`OnOpen`）

| 日志 | 含义 | 下一步 |
|---|---|---|
| 有 `ONOPEN-IN`、**没有** `ONOPEN-OUT`、且有 `ONOPEN!EXC` | `OnOpen` 抛了（窗口链会吞异常，所以 `errs.tsv` 看不到） | 按异常栈定位；常见：`logPrefab`/`holder` 为 null、`holder` 被销毁、`Where` 谓词里 `ownHeroName` 结构不对 |
| 有 `ONOPEN-IN`、**没有** `ONOPEN-OUT`、也没有 `ONOPEN!EXC` | 方法**没跑完**（多半是协程/异步被中途掐断，或 IL2CPP 侧异常未被 finalizer 截住） | 看 `n=` 是不是卡在同一个值、`unity.log` 同一时间点有没有报错 |
| `ONOPEN-IN logPrefab=NULL` / `holder=NULL` | 序列化引用丢了（预制体/场景没填） | 回 `Player Profile Window.prefab` 核 `BattleLogTab` 的两个字段 |
| `ONOPEN-OUT holderChildrenAfter=0 itemInitCalls=0` **且** `data count>0` | **数据有、循环没产出** ⇒ 全被 `Where` 过滤掉了（`ownHeroName` 为空或 `"0"`） | 看 `first={...ownHero=...}`：若 `ownHero=null`/`""`/`"0"` ⇒ 是**数据字段**问题，不是渲染问题（原版也这么过滤，见判据 2） |
| `ONOPEN-OUT holderChildrenAfter=N itemInitCalls=N`（N>0） | 列表**已经建出来了** ⇒ 「整页空白」是**别的层**的问题（`holder` 布局/裁切/在屏外/被遮住/父节点未激活） | 查 `holder` 的 rect / 父链 activeInHierarchy / CanvasGroup；另派布局审计 |
| `ONOPEN-OUT holderChildrenAfter=0 itemInitCalls=N`（N>0） | Instantiate 过但子件又被销毁/挂到别处 | 看 `BattleLogItem` 是否 `SetParent(null)` / 被 `DestroyAllChildren` 二次清掉 |

### 4·3 列表项

| 日志 | 含义 |
|---|---|
| `ITEM-INIT-IN n=1 match={...}` | 第 1 条确实进 `BattleLogItem.Initialize`，入参已展开 |

### 4·4 `GET-BATTLELOGDATA`（辅助）

`OnOpen` 走的是 **backing field 直读**，正常路径**不该**触发 `get_battleLogData`（探针自己也优先读 field）。
若这一行出现了，说明**有别的代码在走属性**（例如 `SaveMatchRecording` / UI 刷新），可作为旁证，不是主线。

## 五、盲点 / 未查清

1. **没跑实机**：本报告只给判定方法，不给根因。
2. `battleLogData__BackingField` 这个**生成名**来自 ILSpy（`cpp2il/out_cpp2il_dev_ilspy/BattleLogTab.cs`）；若实际代理名不同，探针会回退读 public 属性（`via=prop`），**不会崩**。若 `via=` 两路都失败会打印 `list=NULL(field+prop 都读不到)` —— 那是「读法不对」，⛔ 不能当「数据为空」的证据。
3. `holder.childCount` 读的是 `Transform` 的 `childCount` 属性；被销毁的 Transform 会返回 `?`，**不猜 0**。
4. 「列表建出来了但看不见」这一支本探针**量不到**（布局/裁切/渲染顺序），需要另派 UI 布局审计。
5. 任务里的「实例化/Draw 方法」在 `BattleLogTab` **不存在**（判据 3）；若要逐次 Instantiate 计数，只能 hook 全局 `Object.Instantiate`（噪声大，本轮不做）。
