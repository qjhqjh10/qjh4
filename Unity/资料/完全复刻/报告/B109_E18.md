⇒ 实现与断言**一律以 `menu_dump` 的实测绝对矩形 (142.8,216)-(570.0,540) 为准**；

## 六、没查清 / 有把握不足的部分

1. **同队列的父子排序（唯一实质风险）**：`Random Image` 圆底与子件 `Icon` 都用 `st.QArt`。
   Unity 透明队列内同队列的排序靠「到相机的 3D 距离」，两件 `localPosition.z` 都是 0 ⇒ **纯靠后建者后画**。
   本仓既有先例 `BoosterInfoPopup`（圆底盘 + 黄面 + 叉，同队列）就是这么跑的，所以**按先例走**；
   但**没有真机截图**证明「问号一定压在圆底之上」。要彻底消掉这个不确定性，得给 `Icon` 一个 `QArt+1`
   （可那样在某些调用方会撞 `QText`，见 `CampaignRewardWindow:935` 那种 `QItemIcon` 兼任 `QText` 的档）。
   ⇒ 建议真机验收时**盯一眼中立档的随机卡格**（`Shell` → 商店/奖励里带 `DT` 的随机卡包）。
2. **判据 §1 的 rect 与 prefab 实测不一致**（§1·1 已订正）。实现取实测值；若调度台认为应以判据文档为准，改
   `RandomIconX1/Y1/X2/Y2` 四个常量 + 断言里的同名常量即可（两处都只有一行）。
3. **`Icon.m_RaycastTarget = 1`** —— 原版这颗**吃射线**。我们今天**没有**给 `Icon` 建命中区
   （`MenuDraw.Rect` 只建图，不吃射线；抽屉整格的点击是另一条路，`ItemDrawerView` 的节点层）。
   ⇒ 「这颗问号自己能不能被点」取决于抽屉格的命中区覆盖范围（那一层早已存在），**本件没有改命中**，
   也没有断言。如果以后要做「问号单独响应」，那是另一条活（`MenuDraw.Hit`）。
4. 判据 §1 的「断言要点 ④ 灭自证：删图 ⇒ 出声计数 +1」—— 见 §4·1，换了等价前提。
