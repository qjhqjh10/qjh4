## §二 逐条改动

### ① `ActionPump.AbilityLevelCriteriaAllows`：第三道闸 `boardCriteria(+0x38)`

**判据（逐句现读，两份产物一致）**
`d:/2/tools/decomp_full/CardAbility__CanTriggerAbility.c:127-140`：
```
cVar1 = CheckIfMeetsCriteria(param_4, param_5, param_6, *(this + 0x28), 0);          // acting
if (cVar1 && CheckIfMeetsCriteria(param_4, param_6, param_6, *(this + 0x30), 0)     // target
          && BoardAnalysis.MeetsCriteria(param_3, *(this + 0x38), param_4, param_5, param_6,
                                         param_7 /*ignoreRandomTrigger*/, 0)) return 1;
return 0;
```
⇒ **一条 `&&` 链**：`acting → target → board`。改前 `AbilityLevelCriteriaAllows` 只判 target，
`+0x38` **一次都没求值**。

**改了什么（`ActionPump.cs`，4 处）**

1. **`set == null && why == null` 那一支不再直接 `return true`** —— 原版「第二道闸没有条件」=
   `CheckIfMeetsCriteria` 回真 ⇒ **第三道闸照样要判**。改前这一支直接放行 ⇒「有 board 条件、
   没有 target 条件」的 ability **从来没判过第三道闸**（现读 99 条 `role="count"` 行里 **25 条**
   `targetsAffected = 0`）。现在：`return BoardLevelCriteriaAllows(...)`。
2. **target 之后接 board**：`if (ok == false) return false;`（原版短路，board 不求值）→
   `bool? board = BoardLevelCriteriaAllows(…)`；`false` ⇒ `why = bwhy; return false;`；
   `null` ⇒ 与 target 的缺口一起写进 `why` 后 `return null`（调用点出声 + 放行）。
3. **新增 `public static bool? BoardLevelCriteriaAllows(ctx, owner, thisCard, card, triggerName, out why)`**
   （类尾，铁律「新成员追加类尾」）：
   * 定位 `ab` 的口径**复用** `CardDef.UniqueAbilityIndexForTrigger`（⛔ 没另写一份）；
   * 取行 = `AbilityLevelConditionRowAt(card, ab, "count")`（现成三态口）；
   * 组 `CardDef.BoardGateSpec{ CountOption, StatOption, ReferenceValue, CountSet }` → `CountEval.MeetsBoardCriteria(…, ignoreRandom: false)`；
   * 三态：`row == null` ⇒ **true（明确没有 board 条件，不出声）** · 旧表哨兵 / 没有 `countSet` ⇒ **null + why** ·
     求值结果原样返回（`null` 时把 `gap` 写进 `why`）。
4. **调用点日志**（`ActionPump.cs:514` 那一块）：标题从「`targetCriteria` **不满足**」改成
   「ability 级触发条件 **不满足**」，并把 `why` 打出来（board 那一档现在也会走到这里）；
   判据串补上 `:127-140` 与 `BoardAnalysis.MeetsCriteria(…, *(ability+0x38), …, ignoreRandomTrigger, 0)`。

**为什么生产上今天零命中（重要，别当成「没接」）**
`EnqueueAbility` 只在 **7 个事件族**传 `abilityTrigger`（`EffectResolver.AbilityLevelGateTrigger`）：
`UnitAttack(50)` / `OtherUnitDeath(90)` / `UnitReceivesMarkOfChaos(510)` / `Reanimated(570)` /
`UnitReceivesMarkerlight(515)` / `UnitDamaged(60)` / `UnitStunned(291)`。
而 `role="count"` 的 **99 行**所在的 ability trigger ∈ `{0,40,610,30,410,300,240,600,10,41,31}`
（`op ∈ {0,1,2,3}`，**没有 8**）⇒ **两边不相交** ⇒ 这一跳今天不会改变任何已观测行为。

### ② `CountEval.MeetsBoardCriteria`：`bool ignoreRandom`（原版第 6 实参）＋ `int cond`（`countCriteria.conditionsFilter`）

  `CardDef.UsesAlternativeAbility` 那条卡级调用**逐字不变**）。
* `RandomChance(8)` 那一支按原版闸 `(ignoreRandom == 0) && triggerIf == 8 && referenceValue > 0` 拆开：
  `referenceValue == 0` ⇒ true（原版前置不成立，照旧）· `ignoreRandom == false` ⇒ **null + gap**
  （掷法仍未实现，见 §四）· `ignoreRandom == true` ⇒ **整段跳过**，落到「数个数」那一半。

* 🔴 **`cond` 形参（顺手补的，不改就不忠实）**：原版数的候选由 `GetTargets(manager, countCriteria, …)` 选出，
  而 `countCriteria` 这个 `TargetCriteria` 对象**自带 `conditionsFilter(+0x38)`**。改前本方法**恒传 `cond = 0`**
  （注释也写着「条件就是 criteria 自己」）—— 那只对 `cond == 0` 的行成立。现读 99 条 `role="count"` 行里
  **6 条非 0**（`221`×2 / `331`×2 / `222` / `243`）⇒ 现在由 `BoardLevelCriteriaAllows` 传
  `row.Condition`，卡级老调用点仍传 `0`（行为不变）。⛔ 不传 = 把「只数带条件的候选」静默变成「全数」。
* 文件头那段「RandomChance 本版未实现 / 没有额外的 cond」的注释按事实改写（含第 6 实参的判据与今天池内 0 命中的现读）。

### ③ `CardDef.AbilityLevelCriteriaRowsForTrigger`（按 trigger 遍历 ability 级 criteria）

**判据（必须照抄的一点）**：原版 `CardScript__HasWhileInPlayAdjacentEffect` 读的是
**ability 级** `CardAbility.targetCriteria(+0x30)`，⛔ **不是** `AbilityLogic.targetCriteria(+0x28)`。
两份产物逐字一致：`out_cpp2il_dev_ilspy/CardScript.cs:6865-6919`
（`cardAbility.targetCriteria.targetsAffected != adjacentToSelfIfMeetsCriteria ⇒ continue`）·
`decomp_full/CardScript__HasWhileInPlayAdjacentEffect.c:1-45`
（`*(int *)(*(longlong *)(lVar2 + 0x30) + 0x10) == 100`）；
偏移 = `dump.cs:20340-20355`（`CardAbility.targetCriteria` `+0x30`）· `EntityScript.rawCardData` `+0x28` ·
`RawCardScript.cardAbilities` `+0x290`。

**为什么需要「遍历」而不是「唯一定位」**：`AbilityLevelCriteriaForTrigger` 的契约是「**唯一**定位一条 ability」，
同 trigger 撞车（实测 89 张）只能回「不唯一」；而**存在性**判定（「这张卡有没有某类 ability 级条件」）
只需逐行扫。新入口返回 `List<KeyValuePair<int, CountSetSpec>>`（`Key` = `cardAbilities` 下标、按升序），
三态与既有访问器同一套：空表 + `why == null` = **明确没有**；空表 + `why != null` = **判不了**（列没落 / 认不出 trigger 名 /
有行的 `trigger` 未知；现读全池 `trigger = -1` 的行 **0** 条）。

> 🔴 **顺手查出的硬事实（会影响 F4 的相邻谓词，别当没看见）**：现读 v30 卡池
> `abilityLevelCriteria` 共 **86 行 / 76 张卡**，`targetsAffected ∈ {10:62, 30:8, 20:8, 90:7, 55:1}`，
> **`ta == 100` 的行 = 0**；`ta == 100` 的 **17 行 / 17 张**（`cards_truth.json` 1351 张口径下 18 行 / 18 张）
> **全在 logic 级**（`abilityTargetCriteria` 列）。⇒ **照原版逐字判 `HasWhileInPlayAdjacentEffect` 会恒 false**
> （`requiem(760)` 那一支池内也是 0 张）。`F4`/`G3` 报的「池内可达 18 张」是**按 logic 级**数的，
> 而原版那个方法读的是 ability 级 —— 这不是我猜的，上面两条判据行号可供复核。
