# B110_M2F · `ItemDisplayWindow.Context` 剩下两个生产者（每日奖励 / 连登）

## 一句话结论

**两处都接上了。** `DailyRewardPopup.OpenItemInfo` 与 `DailyStreakPopup.OpenItemInfo` 现在都按原版实参
`ItemDisplayWindowContext(item, quantity)` 补齐 **`Amount`（= 那一天/那一格的数量）** 与
**`ShowAmount`（= 物品窗里那一刻现挑的**主档**抽屉画不画数量行）**；两处 doc 里那句
「`ItemDisplayWindow.Context` 没有 Amount 字段」已就地订正（铁律 5）。
🔴 关键判据是这一批**新查出来**的一条：**物品窗里的抽屉不是奖励列表里那颗** ——
`ItemDisplayWindow__Open.c:35-46` 用 **`override = 0`** 调 `ItemDrawer.Draw(holder, item, amount, 0)`，
`GetDrawer.c:19-33` 的 `override == 0` 支**直接取主档** ⇒ 列表里摆的 `Icon Currency Drawer Variant`
（`quantity`/`label` 全 null、自己不画）**不决定**窗里画不画；窗里现挑的是主档 `Currency Drawer`（有数量槽）⇒ **画**。

## 六、顺手发现（⛔ 均未改，超出本件白名单/口径）

1. 🔴 **两处 `BuildPreviewHit` 都少了原版第一道闸 ⇒ 卡包那一格会「点出窗 + 播一声」，原版什么都不做。**
   `ItemDrawer_object___OnPointerClick.c:14`（`if (*(char*)(param_1 + 0x44) != '\0')`）—— **`showItemInfoOnClick == 0` 时整条方法直接 return**（无窗、**无声**）。
   而 `DailyRewardPopup.cs:1248-1263` / `DailyStreakPopup.cs:1021-1039` 的 `else` 支**无条件**挂 `OpenItemInfo` 且**无条件** `clickCue = ButtonClick1Cue`；
   卡包那两天的 `RewardClickable` 是 **false**（`ShowItemInfoOnClickForType("Everguild.LiveOps.ShopContainer") == false`）⇒ 今天点卡包抽屉会开出一扇原版不会开的窗、还响一声。
   ⇒ 建议另开账：`else` 支前置 `if (!DailyData.RewardClickable(...)) return null;`（两处 `BuildPreviewHit` 各一处），并补断言。
   ⚠️ 本件**没动** —— 它会改掉 `B109_E23` / `C3_Assert` 里那条「点一下 ⇒ 必开窗 + 必响一声」的既有读数口径，需要调度台统一裁定后再改。

2. 🔴 **`B110_F2` 那一跳（`ItemDrawer.cs:1689`）在 `Icon` 档会 \*\*少画\*\* 一个原版会画的数字。**
   它传的是**视图自己的族**（`ItemDrawerView.Drawer` = `PickDrawer(item, drawerOverride)` 的结果，`ItemDrawer.cs:1567`）；
   而物品窗**永远是 `override 0` ⇒ 主档**。两者只在 4 个「Icon 档是另一个类」的类型上分叉：
   `Wildcard`（`WildcardIconDrawer`）· `ForgePoints`（`ForgePointIconDrawer`）· `VIPPremiumItem`（`PremiumIconDrawer`）· `CosmeticItemTitle`（`TitleIconDrawer`）。
   例：`ForgePointIconDrawer` 的 `quantity` 是 null ⇒ 我们给 false；窗里现挑的主档 `ForgePointDrawer` quantity 非 null ⇒ **原版画**。
   ⇒ 修法（小）：`ItemDrawer.cs:1689` 把族先按「Icon 档 → 主档」归一（四对各一格静态映射）再调 `HasQuantitySlot`；`B110_F2` §五-3 那条「按 override 判」的 caveat 说的其实是这件事，方向写反了。

3. **`ItemDisplayWindow.Context.ShowAmount` 的 doc（`ItemDisplayWindow.cs:156-158`）已不完整**：它写「今天能走到的两族都是 false（… `Icon Currency Drawer Variant` 的 `quantity`/`label` 全 null ⇒ 原版不画）」——
   那句描述的是**奖励列表里那颗抽屉**；物品窗会另挑主档，本批之后这两处是 **true**。该文件不在本件白名单，未改。

4. **图标 → 原版类型那张映射现在有第二份**：`DailyData.ItemTypeNameOfIcon`（`private`，`:3044`）与 `DailyRewardPopup.RewardItemTypeOf`（本件新建）。
   ⛔ 不是「顺手抄一份就完了」—— 这是本仓明令「两处写同一条规则 = 迟早不一致」的形状。
   根因：那份是 `private` 且 `DailyData.cs` 不在本批白名单。
   ⇒ 建议把 `ItemTypeNameOfIcon` 改成 `public static`（或加一个 `DailyData.RewardItemTypeOf(art)` 转调门面），然后把 `DailyRewardPopup.RewardItemTypeOf` 改成转调它、删掉 switch。

5. **每日奖励 mock 表里「名字里的数」与「数量」对不上（疑点，未改）**：
   `_rewardFreeName` / `_rewardFreeCount`（`DailyData.cs:773/779`）：第 4 天名字 `"20 Skulls"`、数量 **160**；Premium 第 4 天 `"40 Skulls"`、数量 **320**；第 2 天 `"1 Booster pack"` / 数量 20、Premium `"2 Booster packs"` / 40。
   卡包那两组（1↔20、2↔40）像是「包数 ↔ 卡数」，但骷髅那两组（20↔160、40↔320）差 8 倍、看不出同一个解释。
   影响：`CollectReward` 按 `RewardAmount` 发钱、本批物品窗按同一个数印 —— **玩家会在窗里看到 160 而卡片上写着 20 Skulls**。
   ⇒ 本件不改数据（`DailyData.cs` 不在白名单），建议调度台核一下这张 mock 表当初是怎么定的。
