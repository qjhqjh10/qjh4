## §0 一句话结论

`FireTriggerByNumberWithSink`（= `FireTriggerByNumber` 的唯一实现）过去**只跑载体自己那张卡**的正文、
**整条不查 `ActiveEnchantments`** ⇒ 挂在单位身上的附魔卡靠**数据位 trigger** 派发的那一拍**永远不发生**。
本笔按原版 `RawCardScript__TriggerAbilities.c:49-197` 的**内联附魔趟**补齐：
载体自己那趟之后，对**每件附魔**按「`ability.trigger == 传入 trigger 数值`」再派一遍，
发一条 `EvtKind.Trigger`（`CardId` = **附魔卡名**、锚点 = **载体**）。

**唯一改到的既有代码 = `EffectResolver.cs` 的 2 行（行内替换，文件仍 21047 行 ⇒ 下游账零漂移）。**

## §5 如实差异 / 没查清（⛔ 不许自己发明口径）

1. 🔴 **原版没有「数据位 ability 只发信号、不跑正文」这条分支**（B109_R2 §1.6）。原版过闸一律
   `TriggerAbility → PlayAbility`。我们的数据行（`chosenAbility 340` 等）**没有通用执行器在本口** ——
   它们的**效果**已由手写等价物承担（`RuleCore.ApplyDamageCore:9067` 的 `EnqueueRemovePray`、
   `GrantPrayEnchantmentFaith:1636`）。⇒ 本口 = 发信号 + 跑**文本 op**（`TriggerOpsByNumber`）；
   ⛔ **不许在这里执行那行数据**（会与手写等价物**双发**）。
2. **已知次序差异（今天零可观测）**：原版是「载体自己那趟先、附魔随后」（`:202` 的 `goto` 落进共享尾块）；
   我们这边附魔趟在**载体 `EnqueueAbility` 之前**被调用 ⇒ 有文本 op 时入队序会反过来。
   今天不可观测：现池唯一可达附魔 `Pray Enchantment` 的 `TriggerOpsByNumber(60)` = **null** ⇒ 不产生队列项。
   ⛔ 将来若出现「有文本 op 的附魔」，要把调用点挪到载体入队之后。
3. **`param_11 = dontResolveEnchantments`（= 跳过附魔趟）没有建模**：全库 12 个调用点里唯一传 1 的是
   `AbilityLogic__PlayAbility.c:2038/2051/2063` 的 **Oath** 支（经 `OnTriggerAlt`）。数值路今天走不到那一支
   ⇒ 本笔不建；另立账。
4. **`abilityActingGate: true` 是第一道（acting）闸**：原版 `CanTriggerAbility.c:127-130` 对**所有** trigger 都判，
   本口按原版打开（宿主卡 = 附魔卡、`actor` = 载体）。⚠️ 今天唯一可达附魔（Pray）的 `abilityActingCriteria`
   是空数组 ⇒ 判不出 ⇒ 放行（不改变行为）。
5. **`AbilityData +0x4c`（能力下标）我们没对应格**：`BattleEvent.AbilityIndex` 是 `cardAbilities[i]` 下标，
   原版 `param_9` 传的是 `ability + 0x18`（同 `+0x44`）。两者是否同一物**没查清** ⇒ `EmitCardTrigger` 留 `abilityIndex = -1`（不猜）。
6. **主表 `战斗逻辑驱动.tsv:1285` 备注的一句字面出入**：它写「`param_8`(isEnchantment) 体内从未使用，`.c`/ILSpy 双源一致」，
   而 `.c:43-47` 现读是**写了又读**（`if (!HasCurrentTrait(jam)) param_8 = 1;` 然后 `:47` 判它）。
   **语义（jam 只挡自己那趟）两边一致**，只是字面表述对不上 —— 已写进账补丁备注，交调度台核（本代理不改主表）。
7. **`Pray Enchantment` 三条 logic 行上的 `buff {buffType:3, trait:1170 markerlight, traitValue:2}`**：
   是不是真效果**没查清** ⇒ ⛔ 不实现（属「数据行执行器」那一笔）。
