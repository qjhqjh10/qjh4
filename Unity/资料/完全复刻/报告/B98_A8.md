## 1 （甲）三层遮挡顺序 —— 判据结论

### 1·1 方向（A5 卡住的那一格）：**local −z 恒 = 朝相机 = 更近**

| 证据 | 值 | 出处 |
|---|---|---|
| 主菜单相机旋转 | **恒等**（`{0,0,0,1}`）⇒ 视线沿 **+z** | `bundle_scenes_scenes_mainmenuwarpforge/Transform/Transform_575.json`（`Camera/Camera_602.json` 的 `m_GameObject`=47 → 该 Transform） |
| 相机投影 | **透视** `orthographic:false` · fov **40** · near 0.3 · far 1000 | `Camera/Camera_602.json` |
| 原版全部画布旋转 | `m_LocalRotation` **恒等**（逐颗）· scale 1 | `bundle_scenes_scenes_mainmenuwarpforge/Canvas/Canvas_1073..1081.json` |
| ScreenSpaceCamera 根画布 | `m_RenderMode=1` · `m_PlaneDistance=100` · `m_Camera`=602 | `Canvas/Canvas_1077.json` |

**推导**：`ScreenSpaceCamera` 画布由 Unity 摆在「相机前方 `planeDistance`」且**旋转 = 相机旋转** ⇒ 画布 local **+z ≡ 相机 forward（远离相机）**
⇒ **local −z ≡ 朝相机 = 更近**。WorldSpace 画布（原版其余全部）`m_LocalRotation` 恒等 ⇒ 其 local 轴 ≡ 世界轴，相机又沿 +z 看 ⇒ **同样 −z 更近**。
⇒ 两种档**结论一致**：**−z 一律朝相机**。A5 那句「原版画布是 ScreenSpaceCamera、相机不在我们手里 ⇒ 拿不到」**不成立**（已就地订正，铁律 5）。

### 1·2 三层的 z（窗口 prefab，逐字实读）

| 节点 | `m_LocalPosition.z` | 出处 |
|---|---|---|
| 窗口根 `Booster Pack Open Window` | 0 | `bundle_menus_assets_all/RectTransform/RectTransform_1342405282582379555.json` |
| `Booster pack Background` | **0** | `RectTransform_-3732186878130897885.json` |
| `Booster Animation Parent`（= `boosterPackAnchor`） | **−202**（scale 0.87626） | `RectTransform_-3486917825874871261.json` |
| `Cards`（`Booster Animation Parent` 的唯一子） | 0（5 张卡在其下，clip 再动画他们自己的 z） | `RectTransform_5277752990758616099.json` |

⇒ 包实物相对背景 = `−202 + (−14.145×0.87626) ≈ **−214.4`（画布单位）⇒ 比背景 `0` **更负 = 更近 = 在前**。

### 1·3 顺序：**背景(远) → 包实物(中) → 5 张卡(近/最上)**

- **包在背景前**：包面是**不透明**网格（3D `MeshRenderer`，`m_SortingOrder=0`、材质 `m_CustomRenderQueue=-1` ⇒ 走 shader 默认几何队列、写深度）；
  背景是 UI `Image`（透明队列）。两者同 z 时透明背景后画会盖住不透明网格（这正是 A5 必须分开 z 的原因）。原版包 z 更负 ⇒ 包在前，**层次正确**。
- **卡在最上 —— 不是 z，是画布排序**：`Cards` 节点带一颗 `Canvas`：
  `m_RenderMode=2(WorldSpace)` · **`m_OverrideSorting=1`** · **`m_SortingOrder=2`** ·
  `m_PlaneDistance=100` · `m_Camera=null`
  （出处 `bundle_menus_assets_all/Canvas/Canvas_938644307404471331.json`；该 Canvas 的 `m_GameObject` 指 `Cards` 节点）。
  ⇒ 5 张卡是**一个独立的排序画布批次**，按 `sortingOrder=2` 叠在其父画布内容之上（含包面 mesh）。
- **反编译里没有任何运行期改排序**：`BoosterPackOpenWindow__*.c` / `BoosterPackVisualItem__*.c` / `CardInBoosterPack__*.c`
  `grep -i "sorting\|SetSiblingIndex\|SetAsLast\|renderQueue\|depth"` = **0 命中** ⇒ 排序**全由 prefab 序列化 + Unity 默认**决定，无运行期干预。

### 1·4 我们怎么落地 —— **量值仍是我们的，保留 🔶**

原版的「卡在最上」靠**画布排序**，我们的 UI **没有画布/排序罐**（纯 quad + 渲染队列 + 深度测试）⇒ 只能等价成「把 `Cards` 摆得比包面更近」。
原版绝对 z 也不可搬：`Canvas_1077` 的 `m_LocalScale` 序列化 = **(0,0,0)**（运行时由 Unity 按分辨率定）⇒ 画布像素→世界的换算在资产里拿不到。
**结论**：A5 的 `VisualItemZ=−0.25 / CardsFrontZ=−0.5`（−0.5 < −0.25 < 0，越负越近）**顺序正确**，**不改值**；
但把注释从「拿不到判据」改写成「方向已查实 + 卡走画布排序 + 量值是我们的」，并**新增顺序不变式断言**。

> 为什么不把 `VisualItemZ` 改成 −1.985（= `−214.4 ÷ 108`）：本工程相机**正交**（`LayoutSpace.Apply`，可见高度固定 10 单位）
> ⇒ z **不改变尺寸、只决定谁压谁** ⇒ 只要「背景 < 包 < 卡」的相对次序对，绝对深度画面上**零差异**；搬一个更深的数只增风险（无收益）。

## 2 （乙）开包时间线早 2 s —— 判据结论

### 2·1 判据（哪个 clip / 哪个事件 / t 的含义 / 接收者）

| 项 | 值 | 出处 |
|---|---|---|
| clip | `Booster Open Standard`（`AnimationClip_7302051762796698856`）· `Booster Open Sororitas`（`AnimationClip_5156805757413551419`） | `bundle_boosterpacks_assets_all/AnimationClip/*` |
| legacy | `m_Legacy = True`（靠 `Animation` 组件播，不是 Animator） | 同上 |
| 自动播放 | prefab 根 `Animation.m_PlayAutomatically = True` · `m_WrapMode=0` · 1 条 clip（**17 份逐颗 True**，spot-check 全 True） | `bundle_boosterpacks_assets_all/Animation/*.json` |
| 事件 | `m_Events[0]`：`time = **2.0**` · `functionName = **StartCardAnimationEvent**` · `stringParameter = null` · `floatParameter=0` · `intParameter=0` | 两条 clip 的 `m_Events` |
| **t=2.0 的含义** | **clip 内相对时间**（从 clip t=0 起算的秒），**不是绝对世界时间**。Standard clip 末关键帧 `2.3667 s`（事件在中间）；Sororitas 末帧 `2.0 s`（事件正在结尾） | 两条 clip 关键帧末时刻 |
| 接收者 | `stringParameter=null` ⇒ 事件打在**同一 GameObject** 上的组件 = 包根那颗 `BoosterPackVisualItem` | `m_Events` 字段语义（无接收者参数 = 本 GO） |
| 接收方法体 | `StartCardAnimationEvent()` → `boosterPackOpenWindow.BoosterPackOpen()` → `windowAnimation.Play()` + `backgroundAnimation.Play("Booster Window - Background Shake On Open")` | `decomp_full/BoosterPackVisualItem__StartCardAnimationEvent.c` · `BoosterPackOpenWindow__BoosterPackOpen.c` |

**时序**：包被 `Instantiate` → 其 `Animation` 因 `playAutomatically=1` 从 t=0 自动播 `Booster Open <阵营>` → **t=2.0**（包炸开那一拍）打 `StartCardAnimationEvent` →
`BoosterPackVisualItem.StartCardAnimationEvent` → `window.StartOpenAnimations()`（我们现在这一份）。⇒ 开包动画**整整比我们晚 2 s**。

### 2·2 施工步骤（若调度台批准）

1. **`Build()` 不再自动起播开包时间线**：`Advance(dt)`（`BoosterPackOpenWindow.cs:900`）里「① 开包 clip」那段加闸 ——
   新增 `bool _openStarted`（默认 `false`）；`_openStarted == false` 时**不**推进 `_openT`（卡的缩放停在初始 157.58，不进入 `WindowOpenScale` 曲线），
   `StepBgShake` 同理不自起（原版背景 shake 也是 `BoosterPackOpen()` 那一刻才 `Play`）。
2. **`StartOpenAnimations()`（`:1664`）= 第一次把时间线点火**：`_openStarted = true; _openT = 0f; _bgShakeT = 0f; OpenAnimStarts++;`；
   现有的「已 `WindowOpenDone` 就不重播」改成「**已 `_openStarted` 且已 `WindowOpenDone`** 才不重播」（区分「第一次点火」与「第二次事件」）。
3. **批处理 / 自检（无帧循环，`Animation` 不推进 ⇒ 事件永不到达）必须显式补这一拍**：测试里改成
   「先 `_win.VisualItem.StartCardAnimationEvent()`（模拟 t=2.0），再 `Advance(...)`」。真机上由 clip 自然打，不用管。
