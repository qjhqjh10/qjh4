### 4·1 载荷（`Net/NetProtocol.cs`）

| 消息 | 新增四格 | 是谁的值 |
|---|---|---|
| `MsgDeck`（客机→主机） | `draftPropsVer, draftC1, draftC4, draftC5` | **客机自己**那三个 |
| `MsgStart`（主机→客机） | 同上 | **主机自己**那三个 |

**🔴 为什么比简报说的「各加 3 个 int」多一格 `draftPropsVer`**：`JsonUtility` 对**缺字段**一律填默认值
⇒「对面没带」与「对面带了、恰好 `0/0/0`」在线上**完全同形**。而简报的硬约束是
「老客户端/老存档缺这 3 个 int ⇒ **出声 + 用默认**，⛔ 不许静默当 0」—— **没有在场标记就判不出来**。
`draftPropsVer`（0 = 没带 · 1 = 有效）就是那个**可判别**标记；老报文里它本身也不存在 ⇒ 读出来 0 = 没带，正好是想要的语义。

⚠️ **不 +`NetProtocol.Version`**：只**新增字段**、没改任何既有字段的形状或语义 —— 与
`MsgChat` / `MsgDesync` / `MsgModeMismatch` 同一口径（先例理由写在那几条的 `NetKind` 注释里）。
旧端收到新字段直接忽略；新端收到旧报文走 `ver == 0` 那一支。

### 4·2 消费方 = **今天就一个日志**（如实记）

原版那三个键的**唯一用途**是 Photon **SqlLobby 的过滤串**（`GetMatchmakingFilter` 拼 `C1 < max AND C1 > min`）。
我们是**单对单直连、没有匹配池** ⇒ 过网之后 `Debug.Log` 一行，**没有功能消费方**。
这与 `Shell/FastModeBaseEvent.cs:543` 那句「这些键写进对象也没有消费方（算对了、用不上）」是**同一口径**，
⛔ 不为了「让它有消费方」发明一个假过滤池。

**今天线上三个值会是多少**：
- 补丁（§二）落地前 ⇒ `draftPropsVer = 0`，三格不成立（见 §一 的表）；
- 落地后 ⇒ `C1 = 本 run 的胜场`（`DraftRunSave.matchesWon`）· `C4 = 0`（`currentELO` 传 0 + 新手档清零，**服务器值本地无真值**）·
  `C5 = GameModesHandler.LossStreak`。⚠️ 后两项**在原版里也是各自的账户值**，两端天然不同 ⇒ 只可能进日志。

### 4·3 🔴 三格**绝不进** `Fingerprint`

`NetProtocol.Fingerprint` / `StateHash` 只吃 `BattleContext`。房属性是**每人自己的**值 ⇒ 进指纹**必然分叉**，
而且会以「打到一半 desync」的形式现形。本实现里它们只落在 `NetMatchmaking` 的**四个静态格**上，
**不放进 `NetPendingBattle`、也不放进 `BattleContext`**（施工单 §3·1 第 9 行的原话：只读不判）。
