## ② 判据

### R1 判据（怎么把 905 个「解不出」变成有归属）

1. **先复现这 905 个**：照 `extract_full.py` 的每个对象 try 块**逐句复刻**（连「名字读取抛异常也算 fail」都复刻），
   六个文件分别得 616/182/73/29/4/1，合计 905 —— **数字对上才算复现成功**。
2. **拿到类名**：`parse_monobehaviour_head()` 读 MonoBehaviour 头，`m_Script` PPtr → `MonoScript.m_ClassName /
   m_Namespace / m_AssemblyName`（905 个里 897 个是 MonoBehaviour，**全部 897 个类名都拿到了**）。
3. **生成布局**：`TypeTreeGeneratorAPI(unity_version='6000.2.6f2')` + `load_il2cpp(GameAssembly.dll,
   global-metadata.dat)` → `get_nodes(<assembly 不带 .dll>, <命名空间.类名>)`。
   🔴 **坑**：UnityPy 1.24.2 的 `get_nodes_up` 会自动补 `.dll`，补了之后**每一次查询都返回
   `failed to dump nodes raw`** —— 必须用不带 `.dll` 的裸程序集名（`Assembly-CSharp`、`UnityEngine.UI`…）。
4. **自己读**：`ttread.py` 按 Unity 布局规则实现（`Array` 子节点=数组；`string` 带 Array 子节点且 data 是
   `string` = `List<string>`；`m_MetaFlag & 0x4000` → 4 字节对齐）。**校验方式 = 必须恰好消费 `byte_size` 字节**。
   - 与 UnityPy 自带读法在 879 个可比的已解对象上**逐字段比对：878 个完全一致**，唯一差异是 `AssetBundleManager`
     的 `backgroundsBundle`（空 `List<string>`：UnityPy 给 `''`，`ttread` 给 `[]` —— 后者才符合声明类型）。
5. **分档**：名字/类名/所属 GameObject 层级三项齐了才判「无关」，理由必须能指到事实（`DebugUICanvas` 预制体、
   `Reporter` 调试台、Unity 构建设置、关服后端）。**说不清的一律留在①，不往②里塞。**

### R0 判据（怎么判「没用上」）

见 `R0_未使用清单.md` §0，要点：
- **搜过哪几个包**：7 个内置序列化文件 + 84 个 bundle = 91 个有对象的文件，**逐个文件与 `_stats.json` 对账**。
- **哪种引用形式**：① PPtr（929,851 条）② **UnityEvent 的 `m_Target`/`m_ObjectArgument`（1,669 条，单独复核
  全部在图里）** ③ Addressables 容器表（13,432）④ `AssetReference.m_AssetGUID`（3,235 条）⑤ 场景根。
  ⛔ 没有只凭「C# 里 0 引用」下结论。
- **「我们有没有用」五档**：U1 精确同名命中 `MyGame/Assets`（最硬）> U1b 命中 `素材/Warpforge原版` >

## ⑤ 没查清 / 不能下结论

1. **「已用（数据表）」不等于运行时会加载**（16,794 条）。它只证明名字以整串出现在我们的表里 ——
   尤其 1,449 个精灵里有相当一部分可能只是被 `_atlas_rects.json` 这类清单带进去的。要逐类核。
2. **「原版不可达」934 个里有 779 个我们反而用了**（工程内 646 + 数据表 128 + 素材库 5），
   说明**还有按名加载的路径没建模**（`Resources.Load("…")`、`AssetBundle.LoadAsset(name)`）——
   静态图看不见。要坐实只能上运行时探针（原版能离线跑）。
3. **GameObject 13,086 个「没用上」不能直接当缺口**：它们多是预制体内部节点，我们的复刻件是「重建」的不是
   「同名导入」，按名字匹配天然对不上。要不要逐个核，取决于该预制体是否已经复刻过。
4. **URP 管线资产**（4 档画质 + RendererData + GlobalSettings + 一堆 Volume 后处理件）已解出字段，
   但**我们工程走内置管线**，这些参数能不能当复刻尺子还没验（战场线的光照/后处理是另一条链）。
5. `PlayerSettings` 只有 AssetRipper 的 YAML 版（UnityPy 的 tpk 在 6000.2 上少 4 字节），
   **没有用我们的读法逐字节验过**。它本身与游戏内容无关，没继续追。
6. `r1_decoded2` 里的字段名来自 IL2CPP 反推，**字段顺序/类型对得住 byte_size 校验，但个别 `List<T>` 泛型名的
   展开可能与真类型树有细微差别**（未逐类比对真类型树，因为内置文件本身没有类型树）。

## ⑥ 顺手发现（都够格进账）

1. 🔴 **69 个 `CardTrait` SO 现在全解出来了**（`sharedassets0.assets` #458–#526），字段含
   `_traitIcon / _hasInPlayAnim / _hasIcon / _isInPlayIcon / _stackable / _aIScore / customObject / _traitEffects`
   （`_traitEffects` 里是 `TriggerOnPlay` 这类效果链）。**这是词条/关键词的权威定义**，之前只在我们自己的表里对过。
   → 建议派一条「用 69 个 CardTrait 反查我们关键词实现」的活。
2. **13 个 `CosmeticItemCardback`** + 2 个 `PlayerAvatar` + 2 个 `AllianceBadge` 也解出来了（卡背/头像/徽章定义）。
3. **8 个 `RawCardScript` 在 `sharedassets0.assets` 里**（不是卡牌包）—— 另有 1 个 `AlternateArtCard`、1 个
   `AlternateArtStyleIconsSO`；我们一直在卡牌 bundle 里找卡 SO，**Resources 侧还有一份**。
4. **`globalgamemanagers` 与 `globalgamemanagers.assets` 在 `assets_full/` 里写进了同一个目录**
   （`extract_full.py` 用 `os.path.splitext` 切文件名，`.assets` 被当扩展名切掉）—— 4590 个对象和 20 个对象混在一起。
   本轮已按对象逐个归属，但**那份导出件的目录结构本身是错的**，别人引用它时要知道。
5. **AssetRipper 导出工程（`d:/2/tools/assetripper_out/ExportedProject`）与 `assets_full` 是同一个 build**，
   可以当**第二解码器**（本轮 12 个对象就是靠它）。对 IL2CPP 生成树失败的类（URP/UIElements/DOTween/GUISkin 除外）
   它能给出完整 YAML。
6. **`TypeTreeGeneratorAPI` 必须用裸程序集名**（不带 `.dll`）；UnityPy 1.24.2 的 helper 会补 `.dll` 导致**全部失败**。
   这条不写下来，下一个人还会以为「IL2CPP 反推不可用」。
7. **`ttread.py` 修的 `List<string>` 读法**：UnityPy 生成的类型树里，`List<string>` 是「`string` 节点 + Array 子节点
   + data 是 `string`」，UnityPy 的 `read_value` 先命中 `string` 分支 → **只读第一个字符串然后跑飞**
   （`PrebuiltDeck.cardLibraryIds` 就是这么坏掉的）。**只有「没有类型树的内置文件」会踩到**，bundle 里的对象有真类型树，
   现有 `assets_full` 的 bundle 导出件不受影响（已抽 `bundle_prebuiltdecks` 抽样验证：`cardLibraryIds` 是正常数组）。
8. **24 个 ComputeShader 里 23 个我们没用上**（`VFXCopyBuffer`、`GenSdfRayMap`、`[Aeldari Portal] [System] …` 等），
   而它们是 VFX Graph 的底层 —— 特效线若要逐效果复刻，这批是判据。
9. **30 个 SpriteAtlas 里 28 个没用上**（`Forge Icons`、`Army Icons`、`0_GeneralUI Atlas`…）——
   我们按「切好的单图」导入，图集本身没用；但如果要复刻原版的图集切分/图集加载行为，这 28 个是入口。
10. **934 个对象原版不可达**，其中 **779 个我们反而用了** —— 反向证明「不可达 ≠ 死资源」，见 §5.2。
