## 6 顺手发现

1. 🔴 **我自己第一版判据有 3 条误判，已就地订正（附录 B-9）** —— 都是「只读了一段 `.c` 就下结论」：
   · `BroadcastActivateMinions` 的「实参座位被忽略」：`_NextTurn_d__395__MoveNext.c:382-384` 传的就是 `isPlayerTurn`，**恒取 `ctx.Active` 是对的**；
   · `AllowResolveAttack` 的「缺 `hasAvailableActions`」：它的体 = `+0x48 == 0 || (HasTrait(0xdc) && +0x48 == 1)` ⇒ 与 `ActionQuota` **逐值同构**；
   · `CanPlayCard` 的「缺两个侧闸字段」：`+0x244 = isPlayerTurn` / `+0x246 = !isPlayerTurn` **每个回合开头被写**（`_NextTurn:382-384`）⇒ 两格合起来 = 「是不是这一侧回合」= `p != ctx.Active`。
   ⇒ 教训：**`BattleManager` 里读「状态位」的闸，要顺手回查「谁写这个位」**（这一轮三条误判全是漏了这一步）。
2. 🟡 **`get_hasAvailableActions` 与 `ActivateMinion` 里的 `+0x48` 闸是同一件事的两处写法** —— 原版自己就有两份（一份是 getter、一份在 `ActivateMinion:19-22`）。我们要新增读点时**只认 `ActionQuota`**，⛔ 别再造第三份。
3. 🟡 **`CardScript.CancelAttack` 的第一句在状态闸之前**：它先清 `+0xF8` 那个 List（待结算伤害），**然后**才判 `cardState ∈ {3,0x11}`。⇒ 「状态不对 ⇒ 什么都不做」是**错的读法**：待结算伤害照样被清。将来补 `CancelAttack` 别把顺序写反（我们目前没有那个 List，所以模型上无差）。
4. 🟡 **主表里 `BroadcastSacrificeResolved(CardScript unitSacrifice)` 有一对同名不同类的行**（`BattleManager.` 与 `BattleManagerSupport.`）—— 按 `方法` 字符串做键会撞。我的补丁脚本因此**把 `方法` 单键升级成「先按类过滤」**：本轮 B92_B1 已把 `BattleManager.` 那行同步成 A（主表现读 **两行都是 A**），所以 B1b **不再重复写它**（幂等）。⚠️ 后续任何按 `方法` 做键的补丁工具都要注意这一对。
5. 🟡 **`play` 探针用 `GameplayVariables.Classic`（`ruleprobe/PlayProbe.cs:807`），`battle` 探针用 `Skirmish`（`BattleProbe.cs:192`）** —— 这一条直接决定了本轮能量结转改动的归因面（见下节）。以后凡是碰 `manaAccumulation` / 起始手牌 / `startingMana*` 的改动，都可以先查这两个字面量就知道该重钉哪个探针。
