## 二、方法（这是本轮最值钱的部分 —— 不这么做会刷出 1.5 万行假差异）

### 2.1 三个数据源各管一段

| 源 | 用途 | 坑 |
|---|---|---|
| `assets_full/*/ParticleSystem|ParticleSystemRenderer|GameObject|Transform/*.json` | **一手**。GameObject 按 `m_Name` 命名、组件按 `PathID` 命名；Go 的 pathID 要**用它的 Transform 反查**（`Transform_<id>.json` 的 `m_GameObject.m_PathID`） | 同名 GameObject 会被写成 `<名>_<pathid>.json`；`Shader` 的 `m_Name` 是**空串**，真名在 `m_ParsedForm.m_Name` |
| `d:/2/tools/assetripper_out/ExportedProject/Assets/*.prefab` | 二手，但**树结构完整**（1386 个 prefab，**976 个**与我们同名；另 2 个是我们独有的名字：`Explosion Hand UI 0,5s delay`（AR 把逗号换成下划线）与 `Vanguard Frame Animated VAT`（AR 没有，见 §六）） | ⚠️ AR 会给同名资产加 `_0` 后缀；⚠️ AR 会**重排子节点次序** |
| 我们工程 `WarpforgeVFX/Prefabs/*.prefab` | 被测对象 | Unity 自己写的 YAML ⇒ **默认值也写全** |

### 2.2 「缺省 = 默认值」归一化（不做这一步，**单个** prefab 就能刷出 3.4 万行假差异）

原版（AR 与 assets_full 两份都一样）**省略等于默认值的字段**，我们的 prefab 是 Unity 写的、**把默认值写全**。
所以对差必须按语义化：`m_Curve` 的 `inSlope/outSlope/tangentMode/weightedMode/inWeight/outWeight/m_PreInfinity/m_PostInfinity/m_RotationOrder` 缺失一律按默认补；
`minMaxState ∈ {0,3}` 时 `maxCurve/minCurve` 是常量值的冗余表示 ⇒ **整对剪掉**（`minMaxState == 1` 时 `minCurve` 同样剪掉）。

### 2.3 同名兄弟必须按【内容】配对 —— ⛔ 不能按 pathID、也不能按树次序

原版 prefab 里同名兄弟很常见（`BulletImpact_1hit_trail_ork` 下**三个 `Smoke`**、`Cut Wulfen SW Double` 下两个 `Embers`），
而**两边的次序是反的**（实测同一组三个 `Smoke`：我们 `[delay0/cycle5, delay0/cycle1, delay0.4/cycle1]`，AR `[delay0.4, delay0, delay0]`）。
按次序配对 ⇒ 值在两边**互相颠倒**，刷出一大片「原版 0 / 我们 0.15」「原版 0.15 / 我们 0」这种**方向成对**的假差异。

**本轮的配对法**（`vfx_diff2.py` 的 `pair_nodes`）：① 先按**整棵节点内容哈希**精确配对（含 TRS：位置/缩放/**旋转四元数**）；
② 剩下的按**字段差数最小**贪心配对（`node_dist` = 两侧字段名对称差 + 值不同的叶子数）。
**代价**：一次全量 978 个 prefab ≈ 7 分钟。
**收益**：全量差异行 **21,933 → 15,229**，而剩下这 **15,229 行 100% 是 §四·5 那 3 个字段**（Unity 序列化默认 / 纯编辑器 / 等价）
⇒ **真实参数差异 0 行**。⛔ 不修配对逻辑，任何一次全量对差都会给出「上千处不一致」的假结论。

### 2.4 防自证：比较器本身做了「变异检出」测试

拿我们的 `AcidSpraySweepAttack` 与它自己的深拷贝，人为改两处（`startLifetime.scalar` / `ShapeModule.radius.value`），
比较器**准确报出这 2 条**且不多报。⇒ 「0 差异」不是比较器失灵。

### 2.5 交叉验证：AR 与一手 JSON 必须对得上

对 AR 一开始找不到的 13 个 prefab，先用**一手 JSON 重建整棵树**（`raw_tree.py`：GameObject 名→组件→Transform 父链）比了一次，
后来发现它们其实在 AR 的 `Assets/GameObject/` 子目录里、两套判据结论一致（§六）；
另外抽查 AR 侧的 `BacklashEffect / Flames`（同名双子）与 `AcidSpraySweepAttack`，AR 值与一手 JSON 逐字段一致。

## 四、结果：逐项

### 4.1 `ParticleSystem` 全模块 —— 0 差异

978 个可比 prefab 内 **14,007** 个粒子系统，逐模块逐字段（含所有 `m_Curve` 的**键时间/值/切线/权重**、所有 `gradient` 的**8 个色键 + 8 个时间刻度**、所有 `burst` 的每一条）**无一处不同**。

### 4.2 `ParticleSystemRenderer` —— 0 差异（3 个字段见 §四·5）

`m_RenderMode` · `m_SortMode` · `m_SortingFudge` · `m_MinParticleSize` · `m_MaxParticleSize` · `m_Pivot` · `m_Flip` ·
`m_LengthScale` · `m_VelocityScale` · `m_NormalDirection` · `m_ShadowBias*` · `m_ApplyActiveColorSpace` ·
`m_AllowRoll` · `m_EnableGPUInstancing` · `m_UseCustomVertexStreams` / `m_VertexStreams` / `m_TrailVertexStreams` ·
`m_Mesh` · `m_Materials`（含**指派到的材质名**，§四·6）

### 4.3 结构 —— 0 差异

978 个 prefab 的**每一个节点路径**（含同名兄弟编号）两边一一对应；`我们缺整个节点` / `我们多一个节点` 各 **1 条**，
且是同一个原因：原版 GameObject 名 `Orbital 5 repeat `（**尾随空格**）vs 我们的 `Orbital 5 repeat` ⇒ 同名节点错位，内容一致（§五·4）。
`我们缺整个组件` / `我们多一个组件` = **0**。

### 4.4 `SubEmitters`（PPtr 指向）—— 0 差异

参数对差里 `subEmitters[i]` 的 `type` / `properties` / `emitProbability` 全一致；
另外单独做了一次**「解 PPtr 看指到哪个节点」**（`pptr_check.py`）：把 `SubModule.subEmitters[i].emitter` 解析成节点路径再比。

规模：**568** 个 prefab 开着 `SubModule`，共 **5,977 条**子发射器。
其中 **5,112 条（85.5%）指到 prefab 内的同一个子节点 —— 0 处不同**；
**865 条（14.5%）指向 prefab 外部**（嵌套 prefab 实例 / 跨 prefab），两侧**同样落空**且其余字段一致（⛔ 但「外部具体指哪一个」本轮验不了，见 §八·1）。
全量里唯一的 **14 条**告警全部落在 `Orbital 5 repeat`，且都是 §4.3 那个尾随空格造成的（`Orbital 5 repeat/Glow init` vs `Orbital 5 repeat /Glow init`）——
**子节点名逐字相同，指错 = 0**。

### 4.5 三个「看起来是差异、实际不是」的字段（⛔ 下个代理别再报）

| 字段 | 行数 | 形状 | 裁定 |
|---|---|---|---|
| `m_StitchLightmapSeams` | **14,624** | 原版 `0` / 我们 `1`（**全部**渲染器统一） | **Unity 工程序列化默认**：原版包体没序列化它（=0），我们工程的默认是 1。粒子不受光贴图缝合影响（**14,006** 条是 `ParticleSystemRenderer`、328 `SpriteRenderer`、133 `SpriteMask`、133 `MeshRenderer`、13 `TrailRenderer`、11 `Skinned`）⇒ **视觉无影响** |
| `m_SelectedEditorRenderState` | **328** | 原版 `3` / 我们 `0` | **纯编辑器**字段（SceneView 的遮挡剔除预览），不参与运行 |
| `m_MaskInteraction` | **277** | 原版 `<无>` / 我们 `0` | **等价**（`<无>` = 未序列化 = 默认 `None` = 0） |

### 4.6 材质指派（材质名，不 guid）—— 见 `matassign2.tsv`

> 逐条明细在 `_tmp_view/v1tmp/matassign2.tsv`（只写差异行）。
> ⚠️ 首个版本刷出 **38 条**「材质不同」，逐条回核**全部是假差异**，两个来源：(a) 同名兄弟错配（值成对颠倒，如 `Lighting Trail`↔`Embers`）
> (b) AR 的内建材质 guid（`0000…f0…` = Unity 内置 `Default-Particle`）+ `WaterRipplesParticle_0`（AR 的同名去重后缀）。
> 改用与参数对差**同一套节点配对**、并按「去掉 `__<hash>` / 去 AR 的 `_<n>` 去重后缀 / 内建 guid 一律视为等价」后复跑。

**结论：0 处真实差异。** 全量 **977** 个走 AR 的 prefab（964 根目录 + 13 子目录）**每一个渲染器的每一条 `m_Materials[i]`**都比过（另 1 个 `Vanguard Frame Animated VAT` 按「父 prefab 的子节点」单独比，见 §六），
只剩 **2 行**，且都是 `Orbital 5 repeat` 那个**尾随空格**造成的同名节点错位；两侧材质名去后缀后**逐字相同**
（`ParticlesUnlit` + `Wispy_Trail_Orbital`；我们是 `Wispy_Trail_Orbital__1b482545`，`__<hash>` 是导出器对「撞名不同源」的变体后缀，
判据 = `EffectExporter.ResolveVariantPath` / `WarnCollision`）。
⇒ **`m_Materials` 槽数不一致 = 0；指派到错误的材质 = 0；内置材质**（AR 用 `0000…f0…` 内建 guid，我们落成 `Default-Particle.mat` 等）**视为等价**。

### 4.7 材质数值（`_Color` / `_EmissionColor` / 贴图 / 队列 / 关键字）—— 静态值不同，但**运行时由 binder 接管**

这一层最容易误判，先把「静态 `.mat` 不是运行期真相」的证据摆出来：

| 项 | 静态 `.mat` | 运行期 | 判据 |
|---|---|---|---|
| `renderQueue` | 101 个材质与原版不同 | **按原版值覆盖** | `WarpforgeEffectBinder.cs:573` `if (!SkipRenderQueue && d.renderQueue >= 0) m.renderQueue = d.renderQueue;`；`d.renderQueue` 来自 `EffectExporter.TruthQueue`（`EffectExporter.cs:2999`）= **原版材质队列，缺省则原版 shader 的默认队列**（表 `数据/游戏数据/shader_renderqueue.tsv`，133 条） |
| 关键字 | 318 个材质与原版不同（125 `_SURFACE_TYPE_TRANSPARENT` · 51 `_EMISSION` · 41 `_SOFTPARTICLES_ON` · 41 `_FADING_ON` · 33 `_NOISECHANNEL_R` · 32 `_COLORADDSUBDIFF_ON` · 18 个 `BOOLEAN_*` 哈希 …） | **按原版 `m_ValidKeywords` 重开** | `WarpforgeEffectBinder.cs:500-540`（逐条注释写了「以原版材质的 `m_ValidKeywords` 为唯一真值」）；`_EMISSION` 另按「逐效果实测标记 × 原版材质带不带」取交集（同文件 `:178-200`） |
| 属性值 / 贴图 | 我们缺 **969** 个纹理槽（**27** 个属性名；其中 **861** 条是 Standard shader 的 `unity_Lightmaps`/`unity_LightmapsInd`/`unity_ShadowMasks` **死值**；真 VFX 属性是 `_Noise`(20) · `_MainTex`(16) · `_MatCap`(11) · `_BumpMap`(6) · `_EmissionMap`(6) · `_ExtraSine`(6) · `_CardImage`(5) …） | **按 `WFMatDef` 逐属性重建**（原版材质**自己保存的属性表**驱动，不是 shader 反射），且 shader **优先取原版原件**（`WarpforgeShaderLoader.cs` 三个包：`wf_shaders.bundle` 45 个 / `wf_shaders_extra.bundle` 33 个 / `wf_builtin.bundle` 15 个） | `EffectExporter.cs:3004-3030`（`DefIndex` 注释逐条写了为什么不能用 shader 属性表）；`WarpforgeShaderMap.cs:161-230`（白名单里逐条写了哪些走原件、哪些是 `Replacements` 近似） |

**对「共有纹理槽」的严格判定**：在**两边都存在的**纹理槽上，**「原版有贴图 / 我们没有」= 0，「原版空 / 我们有」= 0**。
⇒ 丢掉的那 969 个槽，**全部**是「我们的替换 shader 不声明这个属性」⇒ 属 **shader 语义**问题（走原件的那批不受影响），不是数据丢失。

队列的 101 条里，**88 条**是「原版 `-1`（用 shader 默认）/ 我们显式 `3000`」，而原版 shader 的默认队列**就是 3000** ⇒ 等价；
**13 条**的真差也已在运行期被 `WFMatDef.renderQueue` 覆盖（逐条列在 `判据/B9_特效参数对账.tsv` 末尾，带原版 shader 名与生效队列）。

### 4.8 动画 / 时序层 —— 0 差异
