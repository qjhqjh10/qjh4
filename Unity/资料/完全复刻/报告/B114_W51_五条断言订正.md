### 2·3 为什么这才是对的判据

**① 原版是 PA=1（一手 prefab）**
`d:/2/tools/assetripper_out/ExportedProject/Assets/Title Drawer Horizontal Variant.prefab` → `Content/Image` 的 `!u!114 Image` 是 **`m_PreserveAspect: 1`**；
基础档 `Title Drawer.prefab` 同一路径 `Content/Image` **也是 1**。→ 「主图按自己比例内接、居中」，**不是拉伸**。

**② 我们生产那一句本来就是对的，本批没改过**
`Shell/ItemDrawerPartial_B114W32.cs:113` → `DrawerImage(content, imgR, tex, …)` →
`Shell/ItemDrawerLayout.cs:313-321` **第 318 行恒传 `keepAspect: true`** →
`Shell/MenuDraw.cs:1641-1650` 的 `keepAspect` 支 → `CardbackFace.Fit(tex, x2-x1, y2-y1, …)`。
`B-284` 改的是 `DrawerBackground` 的**形参默认值**（`:248`），**不是** `DrawerImage` 的函数体 —— 诊断 §二 #4 已把这条猜测排除。

**③ 期望值仍然不自证**
`FitBox` 走的是与生产**同一条** `CardbackFace.Fit`（唯一一份实现，`Core/CardbackFace.cs:90-119`），
而喂进去的**框**是本文件自己那批**独立 prefab 常量** `HImgX1..HImgY2` + `k`（手算 `min(300/370, 600/1028)`）——
⛔ 没有从 `Metrics()` / `FrameOf` / `ItemDrawer` 的任何常量反读。
「同一条算式」在这里是**必要**的：uGUI 的 `PreserveSpriteAspectRatio` 是两段（先按 `m_Rect` 定框、再按 `padding` 内缩挪位），
自己重写一份就会在**有 `m_Rect` 登记的贴图**上分叉（`MenuDraw.cs:1641-1647` 那段注释就是在记这个坑）。

**④ 四条必须一起改**
B5d/B5e 的旧期望之所以绿，只是因为**高是受限那一维**（内接后上下沿正好等于框沿）。
换非方图 / 换比例时，它们会给出**误导性的绿**（诊断 §六-1 的原话）。现在四条共用同一条内接算式，
「碰巧」的那一半被消掉了。

## 三、C · `B114_W38_Assert.cs:314` 的 D5（诊断 #6）

```csharp
Tr(iconHasBadge != baseHasTrophy, "D5 ★★ 结构反证：Icon 档 = … / 基础档 = … ⇒ 两档的节点名不是同一个");
```

`iconHasBadge` = Icon 档根下有 `Badge`（D2 断言它为真）· `baseHasTrophy` = 基础档根下有 `Trophy Icon`（D4 断言它为真）。
D2 / D2b / D4 / D4b **全绿**（日志 `:194912 / :194929 / :194963 / :194980`）⇒ 两项**都 true** ⇒ `true != true` **恒 false**。

### 3·2 改后（现读 `B114_W38_Assert.cs:313-323`）

```csharp
Tr(!iconHasTrophy && !baseHasBadge,
   "D5 ★★ 结构反证：Icon 档**没有** `Trophy Icon`（实得 …）· 基础档**没有** `Badge`（实得 …）⇒ 两档各自一套名字");
```

### 3·3 为什么这才是对的判据

原意是「**两套 prefab 各带自己那一份名字**」—— 这是一个**交叉缺失**命题（A 有的 B 没有、B 有的 A 没有），
而原来的 `!=` 只在「A、B 恰好互斥」时成立。这里两项恰恰**不互斥**（按设计**都该为 true**）。
改后的形态与 D2b / D4b **方向一致**，且用一个合取把「改名被做成一把刀切 / 改出一份副本」直接钉住。
`D2 / D2b / D4 / D4b` **一个字未动**。

### 3·4 预期复跑读数
