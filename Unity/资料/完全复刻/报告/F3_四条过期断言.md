## 怎么防止下次再过期（可复用经验）

**一句可复用的话：改「会发事件的引擎行为 / 会改计数的数据表」时，`grep` 一下断言里有没有把那个数字写死。**

具体三条，都是这四条共同的形状：

1. **引擎行为改动 ⇒ grep 断言里的写死计数**。判据：`grep -rn "CountOf(\|恰好 \*\*[0-9]" RuleEngine/Editor/`。这类断言的价值全在「**数字与文案逐字对得上当前实现**」，所以**改发出点/读点的人必须在同一个提交里改它**（本次 (1)(2) 就是 2026-10-28 删读点时漏改；而 2026-10-27 那次加读点是改了的，反证这条纪律本身可行）。
2. **数据表 `version` ⇒ 把「改生成器 return」与「改断言期望」写进同一张施工单**。`gen_cards_engine.py` 的 `"version"` 与 `RuleEngineTest_EngineD4` 的期望是**一对**，任何加列/加卡的账都该带一句「bump 断言」，否则每次都会留一条红（本轮 v38 就是 `B3` 加 `enchantment` 列时漏的）。
3. **改「失败路径要不要回滚」时，先分清那条断言是【直调】还是【走 UI/Business 层】**。同一件事在两条路上结果不同（本次：`DeleteDeck` 直调 ⇒ 少一套；经 `DeckInfoPopup` ⇒ 原版退回 ⇒ 不变）。写法上建议在断言文案里直接标 **「（直调）」/「（弹窗）」**，这样下一个人看到就知道该往哪条路上对。本次已在 `CollectionData.cs` 的注释里按这个口径订正。

另附一条**元经验**：这四条的实测数字（2 / 3 / 38 / 17）都在日志里，但**日志不会告诉下一个人「为什么」**——所以每条期望值旁边必须留「**判据出处**」（本次：`RuleCore.cs:14893-14900` + `:16191` / `gen_cards_engine.py:6140` / `DeckInfoPopup.cs:2441-2442` → `DeckLibrary.cs:206-212` → `DeckInfoPopup___DeleteDeck_b__27_3.c:18-26`）。没有出处的期望值，下一个人只能选择「再信一次」或「再查一遍」。
