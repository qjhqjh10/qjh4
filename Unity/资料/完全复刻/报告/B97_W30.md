## 四 消费侧闸（为什么是 **`extrinsicOnly`** 而不是无条件加闸）

原版**只有 `CardScript.RemoveExtrinsicEffectsFrom` 这一个口**按 extrinsic 筛；它**没有**「通用按来源撤」这种东西。而我们的三个原语（`RemoveBuffsFromCard` / `RevertGrantsFrom` / `RevertGrantsCastBy`）是**多读者**的通用口：

| 原语 | 别的读者 | 若无条件加闸的后果 |
|---|---|---|
| `RevertGrantsFrom` | `ClearAuraGrants`（2 处）· 黑暗契约换契约 · `RuleEngineTest.cs:31081` · `RuleEngineTest_EngineB94B2.cs:287/291` · `RuleEngineTest_S23_Resolve.cs:627` | **这几处全红/全废**（它们给的记录 `Extrinsic=false`） |
| `RemoveBuffsFromCard` | `EffectResolver.cs:3128`（dispel / 按卡名撤限时增益） | 那条通用口一夜之间不再撤任何东西 |
| `RevertGrantsCastBy` | `B97_W1_Assert.cs:69`（直接调用） | 同上 |

⇒ 三处都加**缺省 `false` 的可选形参**，只有 `UnitState.RemoveExtrinsicEffectsFrom` 传 `extrinsicOnly: true` —— 既落地原版那道闸，又不改动任何既有读者。**⛔ 别把它改成无条件**（那会把「通用按来源撤」整个废掉，等于用一条闸换一个新缺口）。

闸口清单（`UnitState.cs`，全部**就地改条件、零新增行**）：

1. `RevertGrantsFrom(source, extrinsicOnly)` → `if (g.Source != source || (extrinsicOnly && !g.Extrinsic)) continue;`
2. `RevertGrantsCastBy(caster, extrinsicOnly)` → 同上，键是 `Caster`
3. `RemoveBuffsFromCard(cardName, extrinsicOnly)` → 同上，键是 `SourceCard`
4. `RemoveExtrinsicEffectsFrom` 的 `_statMods` 那一圈 → `|| !_statMods[i].Extrinsic`
5. `ContainsExtrinsicEffectsFrom` 三本账各加 `&& …Extrinsic`（**必须与 1–4 同口径**，否则「先查说有、再摘没有」= 白入队一条动作）

`Aura.RemoveExtrinsicBySource` **不需要再判一次** —— 它调的就是 `UnitState.RemoveExtrinsicEffectsFrom`（闸在下面那层），⛔ 别在两处各判一次。

## 六 指纹影响预判（⚠️ 本代理**没跑** `ruleprobe` —— 简报红线）

**本批（白名单内）预期零变化**，理由链：

1. 新列只被**读**不产生新行为：`Extrinsic` 的写点今天仍只有 `IsExtrinsicSource(GrantTag)` 那条（光环）—— 生产侧补丁（§三）没落地前，`_buffs` / 普通 `_grants` / 普通 `_statMods` 恒 `false`。
2. 闸只会让 `RemoveExtrinsicEffectsFrom` **少摘**。它今天的两条现实路径：
   · `Aura.RemoveExtrinsicBySource` —— **全仓 0 调用点**（`B97_W21` 现读复核）⇒ 无影响；
   · `EffectResolver.RemoveExtrinsicEffectsFrom` —— 唯一生产调用 = `WhileInPlayVariablePass`（240 跑不起来的卡），`B97_W21` 实测**净 0** ⇒ 无影响。
3. `ClearAuraGrants` / 黑暗契约 / dispel 走的是**缺省 `extrinsicOnly: false`** ⇒ 逐字不变。

**⚠️ 唯一需要盯的一格**：`ContainsExtrinsicEffectsFrom` 由真变假时，`EffectResolver.RemoveExtrinsicEffectsFrom` 会**少入队一条** `removeEffectsFrom(47)`。若池内真有「240 卡的同名非 extrinsic 记录」，`play check` 的动作条数会变。**建议调度台在 `--fix` / 同步点那趟跑一次 `ruleprobe play check` 对指纹**（我按红线没跑）。

## 九 没查清 / 没做的（如实）

1. **`_traitEffects`（第四本账）没进「按来源撤」** —— 它**已经有 `Extrinsic` 列**（`TraitEffectRecord.Extrinsic`，作合并键用）与 `Source`，但**全仓没有「按来源 / 施放者摘一条 trait 记录」的口**。硬把它并进 `ContainsExtrinsicEffectsFrom` 会造出「查说有、摘不掉」⇒ **本批不并**，等有摘口再两条同批。判据侧：原版 `RemoveExtrinsicEffectsFrom` 摘的是 `activeEffects` 里**全部** `CardEffect`（含 `addTrait` 3 / `addTraitRemnant` 90）⇒ 这是一个**真缺口**（铁律 11：要做，只是要先有摘口）。
2. **`buffType` / `baseEnchantmentCard` 两个筛没建模**（合取 ③④）—— 唯一调用点恒传 `0/0`，模型上等价；**将来若有 `param_3 != 0` 的调用点，本谓词会少筛**。
3. **`Aura.ApplyAura` 没传 `caster: src.Name`**（原版 `enchantingCard = AbilityData.thisCard` 明显是光环源卡）。不传的后果 = `RemoveExtrinsicEffectsFrom(光环卡名)` 摘不到那些光环赠予。
   ⚠️ **本批刻意不动**：一加上，`ContainsExtrinsicEffectsFrom(光环卡名)` 会由假变真 ⇒ `WhileInPlayVariablePass` 那条链可能在 `play check` 上多出动作。这是**该做的**（原版就摘），但必须与一次指纹重钉同批 ⇒ 交调度台排（判据已齐：`PlayAbility.c:1198` 的 `enchantingCard = param_3+0x10`）。
4. **没跑 Unity / `ruleprobe`**（简报红线）⇒ 上述「零可观测」全部是**静态推理 + 前序代理的实测引用**，不是本代理复跑。
5. `extrinsicVariable(+0x31)`（= `whileInPlayVariable`）我们**没有这一列**；池内无消费者（`B97_W21` / 本批 grep 均 0 命中消费方）⇒ 未建。
