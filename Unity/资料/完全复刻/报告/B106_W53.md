## ④ 顺手发现

1. 🔴 **「坏 858 份」少算了 27 份**：`globalgamemanagers.assets` 那批 `m_FileID` 真值本来就是 **0**，
   错位后仍是 0（`m_PathID` 才是错的）⇒ **按 `m_FileID` 判会漏这 27 条**。
   真实口径：**885 份（全部）都坏**。以后引用 `B106_W36` 那句「858」时**要写清是 `m_FileID` 口径**，别当成总数。
2. **pass1（`r1_decoded/`，880 份）也是 880/880 `m_Script` 垃圾** ⇒ 原脚本末尾那句
   `AGREEMENT with pass1: 0/879 identical` 是**预期值、不是回归**（两条路都是同一棵 IL2CPP 生成树读出来的）。
3. 🔴 **`d:/4/_tmp_view/wfres/r1_decode2.py` 仍在原处、且仍是有 bug 的那份**（不在我白名单，**没改**）。
   谁再照原样跑它，会把 885 份重新写回垃圾值（而且现在还会因为 `ttread` 搬走先崩）。
   **建议**：删掉那份，或把 `sys.path` 指到 `Unity/工具/` 并把它改成调用新脚本；由调度台定。
4. **externals 的路径有陷阱**：`globalgamemanagers` 的 externals 里写的是 **`Library/unity default resources`**，
   而构建产物里**没有 `Library/` 目录**，真文件在 `Warpforge_Data/Resources/unity default resources`
   ⇒ 按字面 `os.path.join` 会「找不到文件 / 解析失败」。新脚本用 `data_path()` 兜住（先试原路径，再试 `Resources/<basename>`）。
5. **MonoScript 盘存**（`--probe` 现读）：`globalgamemanagers.assets` **4453** 个 · `Resources/unity default resources` **19** 个 ·
   其余 4 个主文件 **0** —— 所以凡是 `m_FileID = 1` 的 `m_Script` 都在 `globalgamemanagers.assets` 里查。
6. **pass3 / pass4 的产物不受这个坑影响**：它们 `m_Script` 走的是 YAML 的 `fileID/guid` 键（JSON 里是 `m_FileID: null`），
   是另一套写法，**不需要重跑**。
7. 原脚本写盘用的是 **文本模式**（Windows ⇒ CRLF）。新脚本**显式写 CRLF**，否则 885 个文件会被整体翻成 LF，
   「修前 vs 修后」的 diff 会被行尾噪声淹掉（本项目行尾纪律踩过多次）。
