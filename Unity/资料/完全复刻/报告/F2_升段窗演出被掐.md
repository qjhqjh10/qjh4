## 二、选了哪个方案 + 为什么不选另一个

**选了方案②**（给 `StopAnimation()` 加闸），改法一行：

```csharp
if (_promoteDelay < 0f) StopAnimation();
```

**为什么不选方案①（`OpenRankedDivisionChange` 里删掉 `win.Show(ctx)`）** —— 现读核实后它会造成**另一个真缺陷**：

1. 复用支（窗还开着）时，`OpenByRef` 只走 `wm.OpenWindow` → `TryOpen` → **`GameWindow.cs:544-550` 早退，一个字段都不写**（原版行为，逐字对齐）。
2. 也就是说 **`Show(ctx)` 是复用路上唯一把新 `ctx` 铺到树上的入口**。删掉它 ⇒ 「同一扇窗、新段位数据」将永远显示旧内容。
3. `WindowsManager.cs:901-906` 的注释正是为这件事写的：「这 8 条入口的窗……如果内容需要每次重进都刷新，那它们得像原版那 7 个 `TryOpen` 覆写一样自己补一条刷新」。`Show(ctx)` 就是升段窗补的那一条。
4. 删 `Show(ctx)` 并不违反原版（原版没有这条入口），但它会**拿一个缺陷换另一个缺陷**；而方案② 两个都不丢。

**方案② 的正确性论证**：

- `_promoteDelay` 的生命周期是干净的：`StartSequence()` 置成 `1.40`（≥0），promote 起播那一跳（`:832`）立刻置成 `-1f`，`StopAnimation()` 也置 `-1f`。
  ⇒ `_promoteDelay >= 0f` **正好等价于**「序列还停在 promote 之前」。
- 所以闸的实际语义 = **「只在序列已经走过 promote 那一拍时才允许停播」** —— 这正是 `Show()` doc 原本想要的「换内容不重播演出、停在出厂姿态」，只是原实现把「序列还没起播」也一并掐了。
- 判据站在这边：原版 `Open()`（`RankedEventDivisionChangeWindowNewSystem__Open.c:228-240`）之后**没有任何「再关一次动画」的入口**；`StopAnimation` 是我们为「复用换内容」自补的一跳。序列还没起播就掐 = **把原版会播的那段整段吞掉**，不是「停得更早」。
- `Build()` **照旧每次都跑**（换内容必须重建）。重建不影响进行中的序列：`Build()` 会清 `_nodeCache`（`:257`），而 `SampleAnimation` / `ApplyChannels` / `NodeAt` 全部**按 path 每帧重解析**；原生 `Animation` 只是旁路（批处理里它本来就推不动，见 `PlayClip` 的 `WarnChannel`）。
