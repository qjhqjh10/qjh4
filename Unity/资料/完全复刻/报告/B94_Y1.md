## 一、结论

`TroopKilled`（挑战/成就「击杀部队数」的发射端）**改对了口径**：原版在每一次小兵死亡结算时**无条件**发（只受「凶手卡非空」这一道约束），而我们把计数挂在 `TryCreditKillCore` 里、带 **6 道闸** ⇒ **少计三类**。现把计数口移到 `CleanupDeaths` 的**两处离场点**（正常离场 `leftPlay = true;` + 残骸被摧毁 `if (u.IsRemnant)` 支），**只按凶手座位**记（`killer` 座位，缺失时取 `actingCard` 的主人 = 消费者 `TroopsKilledCount` 读的 `killer.isPlayer`；`AddTroopKilled` 的 `SeatOk` 兜底 ⇒ 凶手为空 `-1` 时自然不计，等价施工单的 `killer∈{0,1}`）。

- ✅ 补上三档：① **凶手不是当前行动方** · ② **凶手已死** · ③ **被摧毁的是残骸**。
- ✅ 督军倒下 / 幸存者留场**不计**（计数点排在那两个 `return` 之后）。
- ✅ **零净行数变化**（16,982 → 16,982），只就地改 3 行。
- `ActivateHero` 式的**整条 `TryCreditKillCore` 不搬**：Slay / `Kills` 广播仍依赖它的闸，只把 `AddTroopKilled` 那一句移走。

## 六、没查清 / 风险（如实标）

1. **「凶手卡为空」到底是哪一张卡**：本代理按 `.c` 偏移（`BattleAction` 布局 = `actionType@0 · actingCard@0x08 · targetCard@0x10`，见 `out_il2csharp/BattleAction.cs`）算出 `ChallengeLogMgr__TroopKilled.c:86` 的 `local_1f8` = **targetCard（死者）**，与 F1 记的「凶手卡」在**字面**上不一致；但两者对**本改动无影响**（`_ResolveMinionDeath` 里 targetCard 已非空 ⇒ 实际每次都发）。⇒ 本代理**沿用 F1 的施工口径**（闸 = `killer∈{0,1}`），并把实现写成「凶手座位 / 缺失取 actingCard 主人」，两种解读都能覆盖。
2. **凶手已死 + 座位又不显式传**的边角：若干**效果伤害**路径（如 `EffectResolver.DoDeal` → `Hurt(..., actingCard: ctx.ActingUnit)`）**不传 `killer` 座位（缺省 -1）**、只传 `actingCard`。若这个 actingCard 在同一「同时伤害批」里也死了、且已离开棋盘，`OwnerOf(actingCard)` 会 `-1` ⇒ 该档（凶手已死且无座位）仍可能漏记。**攻击路**会传 `killer` 座位 ⇒ 常见的「同归于尽」能覆盖。这是 `UnitState` **不带 owner 字段**的根本限制（`FindSlot`/`OwnerOf` 只能扫棋盘）。**没查清**：原版这一档用 `CardScript.isPlayer` 直接读（卡对象还在），我们靠座位反查 ⇒ 边界不逐字等价。
3. **残骸分支无 `Test` 级单元覆盖**：断言③用「直接摆一个 `IsRemnant` 的 `UnitState`」验，未走「真部队先翻面成残骸、再被摧毁」的完整链（那条链要部署 + 打两下，夹具成本高）。引擎逻辑上 branch B 对两者一视同仁（都按 `u.IsRemnant`），风险低但**未端到端**验。
