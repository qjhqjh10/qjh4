## 四、变体 B 是怎么来的（⛔ 不在 C# 里做）

`B-197` 的 §六·2 要求「把三个变体放进同一个场景比 `samples` 与导出的 PCM」。**B 必须先在离线侧造出来** ——
Ogg 页解析 + granule 改写 + CRC 重算是离线脚本的活（宿主简报也明令 C# 不许自己解容器）。

**做法**：新建 `d:/4/_tmp_view/b114_w4/gen_b.py`，算法**逐字复用** `_tmp_view/b112w_b197/batch2.py::fix_all`
＋ `exp1.py::patch_page_gran / crc`（同一套多项式 `0x04C11DB7`、初值 0、无反射）：

1. 对每个中间页（4 页文件 = 第 2 页；5 页文件 = 第 2、3 页）：把 ogg **截断到该页末尾**、该页 granule 设成 `1<<40`、打 EOS、重算 CRC；
2. 用 **ffmpeg native Vorbis** 解那个前缀 —— 它**忽略中间页 granule**，所以解出的帧数 = 该页为止**真实可解的累计样点**；
3. 把这个数写回原文件的该页 granule，**只重算该页 CRC**，其它字节一个不动；
4. 写进 `d:/4/_tmp_view/b114_w4/fix/vo/<同名>.ogg`。

**跑出来的实测（450 份全量）**：

| 量 | 结果 |
|---|---|
| 成功 | **450 / 450**（0 失败） |
| 总字节 | **17,178,808 B** —— 与备份**一字不差**（备份 `du -sb` 同样是 17,178,808） |
| 每份改动字节数 | **最大 14**（4 页 5–7 · 5 页 12–14），与 B-197 §5·2 一致 |
| 页数分布 | 4 页 427 · 5 页 23（与 B-197 §三 全量统计一致） |
| 耗时 | 4.7 秒（8 线程） |

**复现命令**（改了目录或想重跑时）：

```bash
cd /tmp && python -I -X utf8 d:/4/_tmp_view/b114_w4/gen_b.py --all      # 450 份
cd /tmp && python -I -X utf8 d:/4/_tmp_view/b114_w4/gen_b.py --n 20     # 抽样
```

## 六、没查清的部分 / 判读时必须知道的事

### 6·1 🔴 **`AudioClip.samples` 判不出 A 与 B 的差别 —— 必须看 PCM**（本波实测，会直接影响判读）

我在动手前先用 **vgmstream**（= libvorbis 口径）对 3 份做了预检：

| 文件 | vgmstream 解 A 的帧数 | 解 B 的帧数 | A vs B 的 corr | 首个不同样点 |
|---|---|---|---|---|
| `Sautekh_Orikan_gen3` | 208,000 | **208,000** | **0.806474** | 第 164,352 帧 |
| `VO_CSM_EC_Lucius_Backup3` | 246,625 | **246,625** | **0.604494** | 第 137,472 帧 |
| `Tutorial1_prebattle3_Calgar` | 265,763 | **265,763** | **0.294586** | 第 99,392 帧 |

⇒ **总样点数两边完全相同**（都按末页 granule 收尾），差别全在**中间那一段内容被前移**上（首个不同样点正好落在 page2 边界附近）。
**所以「`clip.samples` 相等 ⇒ FMOD 不看 granule」这个推论是错的** —— 宿主为此改用 **FNV-1a 64 PCM 校验和 + 逐样点 corr**。
（⚠️ 顺带：这三份也说明 **vgmstream/libvorbis 这一类解码器确实看中间页 granule**，与 B-197 §一·2 一致，这一条在本轮**再次独立复现**。）

### 6·2 还没查清的

1. **FMOD 到底属于哪一类 —— 这就是本宿主存在的唯一理由，仍未测**（要调度台跑）。
2. **Unity 会不会在导入时重编码 `.ogg`**：现有 `vo/*.ogg.meta` 现读是 `compressionFormat: 1 (Vorbis)` · `quality: 1` · `sampleRateSetting: 0` · `loadType: 1`。
   （宿主把拷进临时目录的文件**统一强制**成 `DecompressOnLoad` + `PreserveSampleRate`，所以三个变体走的是同一套导入设置，可比。）
   **我的判读假设**：Ogg Vorbis 源 + Vorbis 目标格式时 Unity **直接用源文件、不转码**，所以 `GetData` 出来的是 FMOD 对该 ogg 的真解码。
   ⚠️ **这一条我没有独立验证**（要验证得比对 Unity 导出的 PCM 与 ffmpeg/vgmstream 的 PCM 逐样点相关）。
   宿主已经把**实际生效的 importer 设置打印出来**（`B204 IMPORTER …` 那一行），如果 `compressionFormat` 不是 Vorbis 或 `quality` 被改，那行会露馅。
   📌 **若调度台想要一条交叉证据**：跑完后把 A 的 `fnv` 与离线 ffmpeg-native 解 A 的 PCM 校验和比一次（ffmpeg native **不看**中间页 granule）；两者一致 ⇒ 说明 Unity 解的就是源文件。
3. **`-b204all` 的实际耗时与内存没测**（见 6·4）。
4. **C（q8）的原始编码参数**我没核（q8 还是 q10、bitrate 多少）—— 只按字节数确认它是重编码产物（样例 ×1.80 / ×2.04，落在 B-197 §5·2 的 ×1.62–3.32 区间内）。

### 6·3 判读口径（照 B-197 §六·1 的二分）

| 读数 | 结论 | 该做什么 |
|---|---|---|
| `AvsB hash_identical == compared` | **① FMOD 不看中间页 granule** | 450 份在游戏里本来是对的 ⇒ **整批回滚**（`mono_setup/vo` 原样拷回，白赚 24.73 MB + 去掉二次有损） |
| `AvsB` 有任一份不同 | **② FMOD 看** | 450 份确实播错 ⇒ **改用 B（只改 granule）**，仍优于 C（无损 + 体积不变） |
| `BvsC corr ≈ 1` | 现有 q8 在**时间轴**上已把错位移修过来了 | 只说明 C「能用」，不影响①②的判定 |

### 6·4 `-b204all` 的代价

450 份 × 3 = **1350 次导入 + 1350 次 `GetData` 全解**。宿主已做两件事减压：
① 每个文件读完就 `Resources.UnloadAsset` 并丢引用；② `Abort` 阈值 `MaxSamplesPerClip = 5e7`（防异常头字段把分配撑爆）。
但**编辑器侧仍可能缓存**，且导入 1350 个音频要时间。**建议先跑默认 20 条**；20 条若「一份都不同」或「一份都相同」，其实已经能定二分。
