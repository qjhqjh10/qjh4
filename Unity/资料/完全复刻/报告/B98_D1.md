## 二 `triggerOpsByNumber`：为什么**不能**出（附反证）· 以及真缺的那一格已经落了

### 2.1 消费端要什么（先读消费端）

- `CardDef.AttachTriggerOpsByNumber(Dictionary<int, List<EffectOp>>)`（`Core/CardDefPartial_B96CA.cs:80`）：键 = **trigger 数值**，值 = **引擎的 `EffectOp` 列表**（文本解析产物，`Core/EffectText.cs` 的 `EffectOp` 类，50+ 字段）。
- 该文件 `:37` 自己写着数据半的形状 = `[{"ab":<cardAbilities下标>,"lg":<abilityLogic下标>,"trigger":<数值>}]`，并写明「`CardDatabase` 解析时**按 `(ab,lg)` 找出该 logic 正文 op** 并调 `AttachTriggerOpsByNumber`」。
  ⇒ **这一列的名字应当是 `triggerAbilityIndices`（三元组），而不是把 op 本体塞进 JSON**。

### 2.2 源里有没有「op 列表」

- `full_raw` 的 **116 个键**里，与效果相关的只有：`cardAbilities` / `activeAbility` / `alternativeAbility` / `normalAbilityBoardCriteria`；
  `cardAbilities[i].abilityLogic[j]` 里是 **`damageCriteria` / `buffEffect` / `summonCriteria` / `handBuff` / `manaBuff` …**（原件 `criteria` 对象），**没有任何一条是引擎 `EffectOp`**。
- ⇒ 想从源直接拼 `List<EffectOp>` = 在数据侧**重写一遍 `EffectText` 解析器**（50+ 字段、分句 / 触发头 / 代价句的归位规则）。那正是任务书 ⑥ 说的「消费端期望的格式在源里找不到对应字段 ⇒ 停手写报告，⛔ 别造格式」。
- 顺带一条独立证据：`EffectOp` 的 `AbilityIndex / LogicIndex` 是**运行期**由 `EffectText.AssignAbilityIndices` 按「`unitConditions` 的 `role=target` 行」**带闸门推断**出来的（`Core/EffectText.cs:213-233` 白纸黑字：`cards_engine.json` 里**没有**「每条 ability 的正文」，文字顺序 = ability 顺序**没有数据保证**）⇒ 连原版那一跳的输入都不是源数据里现成的。
