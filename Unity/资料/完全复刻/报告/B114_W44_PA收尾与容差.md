### 为什么选 1.0f、不选「期望改成 `1080f*328f/498f`」

1. **B3b 的职责不是判 PA** —— 它属 `B114_W20`（账 `B-252`），那一段的主题是「`Content` 左右各留 0.4（根 712.8 / Content 712）」，B3b 是 A3（`ContentX2−ContentX1 = 712`，容差 1e-3）的**画出来那一版**。PA 只是让「画出来的 quad」不再等于 `Content` 的框（差 0.675 px），并不改变它要证明的事。
2. **同一块底板的同族断言已经就是 1.0f**：`B114_W27_Assert:440-445` 的 F2/F2b 量的是**同一个 `DrawerBackground` 画出来的同一块底板**（`fr.Map(DrCx1, 0, DrCx2, DrRootH)`）、同一张 328×498 的图，用的就是 `1.0f`，文案同样是「宽 = `Content` 宽 712」。两处口径统一 ⇒ 后人不会一边 0.6 一边 1.0 地反复调。
3. **不制造「同一条规则两处写」**：PA 的期望值（`1080×328/498`）已经在 `B114_W43_Assert` 的 F1/F3 和 `B114_W38_Assert` 的 C3/C5 里有**唯一的一份**（它们才是 `B-284` 的账）。若这里再硬编码一次 sprite 尺寸，就是把同一条判据抄第三份 —— 换图时两处必须同时改，早晚不一致（CLAUDE.md「两处写同一条规则 = 迟早不一致」）。
4. **鲁棒性**：`B114_W20` 与「底图是哪张、多大」无关；把 328×498 嵌进来，将来换一张导出的底图就会让一条**关于 0.4 偏移**的断言因无关原因变红。

### 我核算过的连带影响（都没红，已逐条算）

| `B3` 左沿 = 0.4 | 0.4 + 0.3375 = **0.7375** | 0.6 | 🟢 偏 0.3375 |
| `B3` 右沿 = 712.4 | **712.0625** | 0.6 | 🟢 偏 0.3375 |

**算式为什么是 711.325**（不是估的）：`MenuDraw.Rect(keepAspect:true)` → `CardbackFace.Fit`：这张图**没登记**在卡背表里 ⇒ 走兜底「把贴图自己当 `m_Rect`、padding 0」⇒ `spriteRatio = 328/498 = 0.658635 < boxRatio = 712/1080 = 0.659259` ⇒ **高定宽缩**：`fw = 1080 × 328/498 = 711.3253`。
✅ 另核了**兜底用的是 `Texture2D.width/height`（PNG 本体）**，实测 PNG IHDR = **328×498**（与 prefab 的 sprite 尺寸逐值相同）⇒ 兜底路与 uGUI 路同值，算式成立。
