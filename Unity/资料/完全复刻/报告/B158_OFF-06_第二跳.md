### 2·2 `messageTemplate` 为什么是**裸字符串**（这是本轮最容易写错的一格）

任务简报要求「两种形状都试，选能反序列化出 `targetId` 的那个」。**源码只支持一种**，三条独立判据：

1. **原版自己写出去的就是裸字符串**（round-trip 铁证）——
   `LoadableReference.WriteJson()`（ILSpy `LoadableReference.cs:780-793`）：

   ```csharp
   public JToken WriteJson()
   {
       if (reference != (T)(object)0) { ... targetId = reference.GetID(); ... }
       return new JValue(targetId);      // ← 裸 JValue 字符串
   }
   ```
2. **读的时候只认字符串** —— `LoadableReference.OnBeforeRead(JToken rawJson)`（`:795-806`）：
   `JTokenType type = rawJson.Type; if (type == JTokenType.String) { targetId = rawJson.Value<object>(); }`，
   **其它类型一律不赋值**。
3. **字符串这条路的调用链成立** —— `SerializationHelper.ReadJson`（Ghidra `SerializationHelper__ReadJson.c`）：

   ```
   uVar6 = ReflectionHelper.New(type);                       // new LoadableReference<DLCMessageData>()
   lVar7 = cast(obj, typeof(IBeforeRead));
   if (lVar7 != 0) FUN_180001f90(...)                        // → OnBeforeRead(rawValue)
   if (rawValue is JObject) { ...逐成员读... }                // 字符串走不进这支
   if (lVar7 != 0 && <是 IBeforeRead>) return obj;            // ← 直接返回（targetId 已被写好）
   ```

   ⇒ **`{"targetId": "…"}` / `{"m_AssetGUID": "…"}` 两种都不是这条路**（前者会被当成「拿 JObject 去逐成员读」，
   而 `LoadableReference` 的成员只有 `genericObjectReference` / `targetId` / `reference`，其中前两个带 `[JsonIgnore]`；
   后者是 `AssetReferenceTyped<T>` 的形状，不是 `LoadableReference<T>`）。

> 结论：`"messageTemplate": "dlc_message_offline_demo"` —— **裸字符串**，判据 = `LoadableReference.cs:780-806` +
> `SerializationHelper__ReadJson.c`。

### 2·3 `steamDlcId` 必须是什么（整数还是字符串？）

`ShopConfig.GetDlcBundle(string steamDlcId)`（ILSpy `ShopConfig.cs:66-89`）的谓词是 **`ic.steamDlcId == steamDlcId`**（纯字符串相等）。

调用方 `DlcMessageProvider.GetEvents()`（Ghidra `Everguild.LiveOps.DlcMessageProvider__GetEvents.c:104-108`）：

```
puVar1 = (undefined4 *)(lVar8 + 0x10);        // SteamDlcEntry.dlcId（uint，见 SteamManager.ctor 写 +0x10）

...

```

`SteamManager.SteamDlcEntry`（stub `SteamManager.cs:10-15`）= `{ public uint dlcId; public string dlcName; }`，
而 `SteamManager__GetAvailableDlcs.c:44-45` 把 `local_res18[0]`（`SteamApps.BGetDLCDataByIndex` 出来的 AppId）写进 `+0x10`、
把名字写进 `+0x18` ⇒ **`+0x10` 就是 `dlcId`**。

⇒ **`DlcBundle.steamDlcId` = 那个 uint 的十进制字符串**。本轮取 `9000001` ⇒ `"9000001"`。

### 2·4 Steam 桩：为什么必须返回**非 null**、以及为什么返回类型不能自己造

- 返回 null 会直接炸：`DlcMessageProvider__GetEvents.c:70-73` —— `lVar8 = SteamManager__GetAvailableDlcs(0); if (lVar8 != 0) {...}`，
  否则落到函数末尾 `FUN_1803f47a0()`（= 抛 `NullReferenceException`）。
- 原版真身要真 Steam：`SteamManager__GetAvailableDlcs.c:29` 第一句就是 `Steamworks_SteamApps__GetDLCCount(0)`（native），
  Steam 未初始化时会抛 `InvalidOperationException`。**所以这条以前大概率是「Inbox 刷新整体炸」，不是「没有 DLC」**（推理，未实机）。
- 签名（stub `SteamManager.cs:75` / ILSpy `SteamManager.cs:171`）：`public static List<SteamManager.SteamDlcEntry> GetAvailableDlcs()`
  —— **无参 / 静态 / 返回引用类型**，**形参表里没有 `Nullable<T>`**（铁律那条 NRE 风险不适用；这条方法本来也没有形参）。
- **返回类型必须从方法签名取**：Il2CppInterop 会把 `System.Collections.Generic.List<SteamManager.SteamDlcEntry>` 生成成
  `Il2CppSystem.Collections.Generic.List<SteamManager.SteamDlcEntry>`。自己 `typeof(List<>).MakeGenericType(entryType)` 造出来的
  是**另一个类型**，Harmony 把 `__result` 写回返回槽时会 `InvalidCastException`。
  ⇒ 代码里用 `_getAvailableDlcs.ReturnType` 现取；只在「拿不到 ReturnType」且「它 AssignableFrom 备用类型」时才退回 `List<>`。

## 四、没查清 / 卡住的部分（都带理由）

1. 🔴 **运行时构造 `Il2CppSystem.Collections.Generic.List<SteamDlcEntry>` 未验证**（本轮不能起游戏）。
   这是**唯一**可能让第二跳不成立的点。代码里已经做了三层兜底 + 三条日志：
   `steamoffline:GetAvailableDlcs`（hook 装没装上）· `steamoffline:DlcList`（WARN 按返回类型构造失败 / FAIL 列表或 Add 找不到）·
   `steamoffline.tsv` 的 `DLC` 行（`dlcId` / 名字 / **字段写入 ok/ok** / **列表真实类型名**）。
   **下一步查什么**：起客户端后先看这三处。
   - `DLC` 行出现且 `字段写入=True/True` ⇒ 桩成了。
   - `WARN 按返回类型构造失败` ⇒ 说明 `Activator.CreateInstance(Il2CppSystem.List<T>)` 不行，改用
     `Il2CppInterop` 的 `new Il2CppSystem.Collections.Generic.List<T>()`（需要在 mod 里加 `Il2CppInterop.Runtime` 的编译期引用，
     或用 `Il2CppSystem.Collections.Generic.List<>.GetConstructor` 显式取 ctor）。
   - `FAIL` ⇒ 把 detail 里的异常名贴进下一轮简报。
2. 🔴 **`ReflectionHelper.Clone` 在真机上的行为没验**。它 = `JsonWrapper.SerializeObject` → `DeserializeObject<DLCMessageData>`
   （ILSpy `ReflectionHelper.cs:1989-1999`）。理论上：
   - `dates` **不会是 null** —— `LiveOpsEventData` 的 ctor 里 `*(param_1 + 0x28) = new EventTimeData()`
     （Ghidra `Everguild.LiveOps.LiveOpsEventData__.ctor.c:34-40`），而 `DlcMessageProvider__GetEvents.c:128-133`
     在 `dates == null` 时就是 `throw`。⇒ 只要 clone 走得通，`startDate/endDate` 一定写得上。
   - `messages`（`List<LocalizedMessage>`，`[SerializeField] private`）会跟着 `$type` 一起 round-trip。
   **没验的是**：真机上 `SerializeObject` 会不会因为 `ScriptableObject` 基类/`drawData` 之类的引用类型抛异常。
   **判据**：看 `phase0/probe.log` / `unity.log` 有没有 `DlcMessageProvider` 相关的异常。
3. ⚠️ **`canClaimReward` 被原版强制改成 `true`** —— `DlcMessageProvider__GetEvents.c:118` `*(undefined1 *)(lVar8 + 0x88) = 1;`
   **不管 `Templates` 里写什么**（我们写的是 `false`）。而 `Rewards` 是 `[]` ⇒ 消息会带一个**领取按钮、但奖励为空**。
   这是**原版行为**（DLC 消息本来就该能领），**本轮照抄、没改**。
   ⚠️ 风险：真点「领取」时 `Rewards` 空数组怎么走没验（大概率是空转或弹一个空奖励窗）。若实机点它炸，
   **下一步 = 给模板补一条真奖励**（`Rewards: [{"…":…}]`，形状查 `RewardInfo`），不是去掉 `canClaimReward`。
4. ⚠️ **`showInMainMenu` 我们显式写 `false`**。ctor 里 `+0x22 = 1`（`LiveOpsEventData__.ctor.c:24`）说明原版默认可能是 `true`。
   写 `false` 的理由：主菜单那套 banner/tile 离线版还没接，`true` 只会多一个我们撑不住的面。
   **若想让它在主菜单也露脸**，把这一格改 `true` 即可（同一份 JSON 里）。
5. ⚠️ **同一条消息每次刷新都会重建**：`eventId` 固定为 `"dlc_message_$9000001"`（`GetEvents.c:110` `String__Concat`），
   所以即使重复产出，按 id 也只会是一条（`RawEvent` + `GameMessagePersistence{IsNew=1,IsActive=1}`）。
   **没验**的是「72 小时窗口过期后会不会又立刻变活」（因为每次 `GetEvents` 都把 `startDate` 重置成当前 ServerTime）。
   若实机看到它永远存在 ⇒ 这就是原版形状（本地消息本来就不是持久化的），**不是 bug**。
6. ⚠️ **`Inbox Menu` 这扇窗由谁打开没查到**：`WindowsManager` 是按 `OpenWindowButton` + `TypedWindowReference` 开的，
   而全工程 **没有任何地方按 guid `9ff6bf342310ff14bbd7531a59150ab7` 引用 `Assets/Inbox Menu.prefab`**
   （已 grep `*.prefab` / `*.unity` / `*.asset`，0 命中）。⇒ 那个按钮**很可能在没被导出的主菜单 prefab / bundle 里**。
   **这意味着**：本报告只能保证「消息产生了」，**不能保证离线版主菜单有进入邮件窗的按钮**。
   若实机没有入口 ⇒ 那是**另开的 UI 接线任务**（`OFF-18` 一类），不是本轮的数据问题。
