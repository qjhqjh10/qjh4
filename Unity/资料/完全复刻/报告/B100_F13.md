## 五、为什么「改这一行就够」+ 为什么「不需要改断言」

### 5·1 一行够 —— 因为 104 张图与**已在生产运行**的旧卡框**逐字节相同**

```
md5  clan/frame_clan_40k_Cardframe_stratagem_Sororitas_tier4.png          = 8fa963b8c3665248590a128a92e80eaf
md5  frame_sororitas_strat_tier4.png                                     = 8fa963b8c3665248590a128a92e80eaf
md5  clan/frame_clan_40k_Cardframes_stratagem_Astra_Militarum_tier4.png  = 842bc7f9cbb6926a138fc9abb3e3fbe1
md5  frame_astramilitarum_strat_tier4.png                                = 842bc7f9cbb6926a138fc9abb3e3fbe1
```
**全量比对：104 / 104 张 clan 图的 md5 都等于某张旧的 `frame_*.png`。**

⇒ 修好之后这批图的**源像素**与旧卡框完全相同，**导入参数**（烘焙后）也完全相同
（旧 150 张现读 = `isReadable:1 / mipmap 0 / nPOTScale 0 / wrap Clamp / 1024 / CompressedHQ`）
⇒ 运行期 `GetPixels32()` 拿到的数据**与旧卡框逐字节同** ⇒ 掩码 / 画窗边**必然**等于旧卡框那组数。
这就是「一行够」的根据：**修的是入口条件，不是算法**。

### 5·2 不需要改断言 —— `K2` 的两个字面量会**自动**转绿，⛔ 不许动

`CardPresentation/Editor/CardBaseDemo.cs:812`：

- 这两个数由 **frame PNG 的像素**按画窗口径离线算出（`CardBaseDemo.cs:807-808` 明写「不是从运行时抄的」）；
  `B100_F7` §2·2 已用 clan 图复算，结果与它们**逐位相同**。
- 现状之所以红，是 `FrameArtWindow` 返回 `Rect.zero`（掩码丢了）⇒ 实测 ±0.8718 = 立绘板整块；

`③b` 断的仍是「铺满画窗」（`CardView.cs:11364-11388` 的逐行条带 / `:11391` 矩形兜底），
