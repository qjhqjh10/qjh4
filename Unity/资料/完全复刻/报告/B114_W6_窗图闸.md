## 3 C：把「壳」带进出图宿主要改什么（**只评估，没动代码**）

### 3·1 现状：`MainMenuScene` 宿主是怎么建场的

`MainMenuScene.Build()`（`Editor/MainMenuScene.cs:620-638`）只有三件：
① `NewScene(EmptyScene)`；② 一台 `MainCamera`（`clearFlags = SolidColor`、`backgroundColor = black`、`orthographicSize = DesignHeight/2`）；③ `MainMenuRuntime` + `rt.Build()`。

**没有** `ShellRuntime`、**没有** `UIBakeScreen`、也**没有** `WindowsManager`（后者是第一次开窗时由 `EnsureHost` 现建的）。
⇒ 所以 `MainMenuRuntime.Build()` 走的是它自己的「**独立场景档**」（`MainMenuRuntime.cs:409-414` 的 `shell == null` 分支）：两个安全区节点就地建，顶栏/左栏/聊天挂在 `_root` 下自建的 `Safe area Only Horizontal` 上。

`ShellScene.Build()`（`Editor/ShellScene.cs:800-828`）则多两步：相机多几个参数 + `ShellRuntime.Build()`。
`ShellRuntime.Build()`（`Shell/ShellRuntime.cs:681`）一口气建：两个安全区 + `WindowsManager.EnsureHost` + **`UIBakeScreen`（`:732`）** + 音乐双源 + 四条压暗边 + `LoadingMenu` / `PointerLayer` / toast / 场景钩子订阅 + **`BuildIntro`（`:811`，全屏 `Intro Video` quad，队列 3100）**。

⇒ **`ShellRuntime.Instance == null` 完全不妨碍**：只要场上有一件被 `Build()` 过的 `UIBakeScreen`，`b != null`，`Toggle` 走的就是它。

1. `EnsureHost(HostKind.MainMenu)` 里，`MainMenuScene.BuildForWindowShots()` 之后加一句

2. `GameWindow.cs` **一行都不用改**（`UIBakeScreen.Current` 这条链今天就在）。

**风险（按严重度）**

- **R1 · 批处理下 `Screen.width/height` 未知（最需要先量）**：`UIBakeScreen.CreateRT()` 用 `Screen.width × 0.25`。若批处理里是 0，代码会把 RT 兜到 1×1（只打一条 Warning）⇒ 底就是「整屏平均色」，**亮度对、观感不对**，而且**不报错**。判据：出图后看那 31 张有没有形状（1×1 会是一块纯色）。
- **R2 · 快照里的顶栏/左栏**：`DisplayQueue = 2895` 低于顶栏 `2986–2998`。出图宿主里顶栏没被藏 ⇒ 会被烘进快照、又被自己清晰地画在上面。**净观感与壳里一致**；与原版实拍（顶栏也是糊的）仍差一层 —— 那是 R-1 顺手发现 #5，**不是本方案引入的**。
- **R3 · 静态 `UIBakeScreen.Current` 跨宿主**：同一进程跑两趟 `RunFromCLI` 时，旧对象被 `NewScene` 销毁后 Unity 的伪 `null` 判据仍成立 ⇒ 不会误用（`UIBakeScreen.OnDestroy` 里的 `Current = null` 在编辑期可能不派，但伪 null 兜住了）。这条我**静态判**，没实跑。

### 3·3 方案 B：真把壳建出来

1. 新建 `ShellScene.BuildForWindowShots()`（抄 `Build` 的相机段 13 行 + `AddComponent<ShellRuntime>()` + `Build()`），
2. **必须**再补 `shell.SkipIntro()` —— 否则 `BuildIntro` 那只全屏 `Intro Video` quad（队列 **3100**）会盖住一切；
3. **不能再调 `LoadMainMenu()`**（`ShellRuntime.cs:1148`：`!Application.isPlaying` 直接 return，批处理里**不切场景**）⇒ 只能在壳里**手工**再建一棵 `MainMenuRuntime`（`MainMenuRuntime.Build()` 的 `FindFirstObjectByType<ShellRuntime>()` 兜底会让它走「有壳档」，把 `Safe area All` 搬进窗里）。

**成本** ≈ 70 行 / **2 个文件**（`Editor/ShellScene.cs` + `Editor/WindowShots.cs`）。

**额外风险**

- **B1** 建出来的**不是今天那棵树**：`MainMenuRuntime` 走「有壳档」⇒ 顶栏/左栏/聊天挂在**壳**的 `safeH` 下、`SafeAreaAll` 被搬进窗里；所有窗的渲染队列环境也变了 ⇒ **33 条要逐条重新人工核**（今天这 33 张是「独立场景档」的产物）。
- **B2** `ShellRuntime.Build` 的副作用一堆：两个音乐 `AudioSource`、`PointerLayer`（真鼠标那套）、toast、**三条场景钩子的静态订阅**、`LoadingMenu`。出图宿主里这些都白建，而且静态钩子在编辑期**不会**被 `OnDestroy` 摘掉（CLAUDE.md 已记这条）。
- **B3** 壳建完 `ShellRuntime.Instance != null` ⇒ `MainMenuRuntime.Build` 与 `GameWindow.SetBake` 都改走壳支路，行为与方案 A 不同（A 是**只用** bake 这一件）。

### 3·4 结论

**先 A**（小、可单独回退、只影响「底」这一层），出图后核 R1 那条（1×1 兜底）；如果批处理下 `Screen` 尺寸确实不可用，再谈 B —— 因为 B 也绕不开同一个 `CreateRT` 依赖（`UIBakeScreen` 就那一份实现）。
B 的唯一额外收益是「壳的其它常驻件」，而**当前出图宿主已经从 `MainMenuRuntime` 那里拿到了顶栏/左栏**（`main_menu` 那张 96.87% 非黑就是证据）⇒ B 的边际收益低、风险高。

- 下限 = **60×34** = 目标帧 1920×1080 的 **1/8**；正常档 RT = 帧 × `RENDER_TEXTURE_MULTIPLIER`(0.25) = **480×270**（下限的 8 倍）。
- RT 任一边低于下限 ⇒ 打一条 Warning，写明「底下只是**一块整屏平均色**、不是模糊的主菜单；成因 = `Screen.width/height` 很小/为 0，
  `CreateRT` 兜到 1×1（那是它原有兜底，**本轮没改**）」。
- **每一行** `_index.tsv` 的 `说明` 列都会带三种之一：
  - `模糊底 RT 480×270（Screen 1920×1080 × 0.25）` ← 正常
  - `⚠️ 模糊底**退化**：RT 1×1（…）< 下限 60×34 ⇒ 底是一块整屏平均色，不是模糊主菜单` ← 需要看的那一档
  - `模糊底：**没建成**（image == null）` / `模糊底：**建不出来**（异常）` ← 也应该报警的那两档

### 7·3 跑完之后怎么判（给调度台）

1. **先看 `_index.tsv` 的 `说明` 列**（32 行 MainMenu 宿主都会带这一项）：
   - 出现 `模糊底**退化**` 字样 ⇒ R1 成立 ⇒ 模糊底只是「亮度对、观感不对」；这时才值得评估改 `UIBakeScreen`（不在本批白名单）。
   - 出现 `RT 480×270` ⇒ R1 不成立，底是真的 1/4 分辨率快照。
2. **看 `ranked_new_season.png` / `ranked_season_ended.png` 这两张**（原 rc=1）：中心区 (700-1200, 500-800) 的均值应从 **0.0** 升到
