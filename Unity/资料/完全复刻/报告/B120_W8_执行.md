## 一、表定义（逐档区间 + 理由）

### 1.1 判据先说清一个关键量纲（本轮新查实）

`MatchData.GetNormalBotConfig` 里与 `minRank/maxRank` 比的那个值**不是段位号**，而是**排位分（`CurrentScore`）**：

- `decomp_full/MatchData__GetNormalBotConfig.c:54`：`iVar3 = FUN_1800021f0(1, DAT_1842ab5f0, <activeEvent>)`
  = **接口槽 1** 调用；`d:/2/tools/il2cpp_out/dump.cs` 的 `IPlayEventWithLeaderboard`：槽 0 `get_LeaderboardKey`、**槽 1 `get_CurrentScore`**
  （`IRankedEvent : IOwnDeckPlayEvent : IPlayEventWithLeaderboard`）。
- `.c:60-67` 随后直接拿它比 `minRank/maxRank`（`iVar2 = GameModes.LossStreak` 比 `minLossStreak/maxLossStreak`）。
- 我们侧的等价 = `RankedData.Points`（`long` → 夹到 `int`）。

⚠️ **旧账/施工单只写「rank」**，容易被读成 `RankedData.CurrentDivision.Number`（段位号）—— 那是另一个量纲，喂进去会让所有档位判错。

### 1.2 Normal 表（6 档）

| # | rank 区间（排位分，闭区间） | lossStreak 区间（闭区间） | 难度档 | 旋钮（只在 `KnobsOf`） |
|---|---|---|---|---|
| 0 | 0 – 1499 | 0 – 0 | `Normal` | 30% / 最多砍 1 |
| 1 | 0 – 1499 | 1 – 2 | `Easy` | 60% / 最多砍 2 |
| 2 | 0 – 1499 | 3 – `int.MaxValue` | `SuperEasy` | 90% / 最多砍 3 |
| 3 | 1500 – `int.MaxValue` | 0 – 1 | `Hard` | 0% / 不砍 |
| 4 | 1500 – `int.MaxValue` | 2 – 3 | `Normal` | 30% / 最多砍 1 |
| 5 | 1500 – `int.MaxValue` | 4 – `int.MaxValue` | `Easy` | 60% / 最多砍 2 |

**设计口径（🔶，判据不足时的推断）**：

1. **连败越多越简单** —— 原版这两个字段名就是 `minLossStreak/maxLossStreak`，语义不用猜；
2. **排位分越高越难**；
3. **分界 `1500`** = 本作 `LegendaryElo 2500`（`RankedData.LegendaryEloFallback`）与 `newbieELO 800`
   （`DraftEventBase` 的 `newbieELO = 800`，判据 `.c` 里 `GameState.newbieELO`）之间的中位；
   本地 `RankedData.Points` 在服务器不给 delta 时**恒 0**（`RankedData.WhyNoPointDelta`）⇒ 默认落在「低分段」那一半，
   这是本地真实状态、不是兜底值。
4. **连败门槛取 3**（低分段）/ 4（高分段）：3 连败已足以说明「这一段他在挨打」，再多就一律给最简单的档 ——
   与「越简单 = 砍得越狠」的结构一致（`KnobsOf` 的 90%/60%/30%/0%）。

**覆盖性（断言逐点钉住）**：两档 rank × 三段 loss = **9 格满覆盖、互不重叠**；
且 low-rank × loss 0 与 high-rank × loss 2–3 都落 `Normal`（同一档出现两次是刻意的：连败 1–2 段与段位上位各抵一次）。

### 1.3 FastMode 表（6 档）

结构与 Normal **完全同构**、**独立数组**（原版就是 `BotList` 与 `BotListFastMode` 两张表）。
🔶 值暂与 Normal 同（两份远端值都拿不到）。

> 🔴 **它今天没有消费点，这是照原版**：见 §六·1（反证）。

### 1.4 FTUE 表（4 档）

| winCount | 难度档 |
|---|---|
| 0 | `SuperEasy` |
| 1 | `Easy` |
| 2 | `Normal` |
| 3 | `Hard` |

口径：引导期**胜场越多越难**；`winCount > 3` 时 `IsInFtueState` 已经返回 false（原版那道 `≤ max(表内)` 的闸），走不到兜底。

## 二、挑选算法（逐句照原版）

```
AssignAiDifficultyForThisMatch():
  aiDifficulty = Normal                       // 兜底 = 字段初值
  if (Ctx == null || Ctx.BotSeat < 0) return  // 没有电脑对手：AI 不驱动，值不生效
  winCount = CurrentModeVictories(playMode)   // <0 = 取不到
  mt = MatchTypes.Effective(Ctx)              // 翻转后的 matchType（原版 SetBotOpponent 之后读同一格）
  if (IsInFTUEState(mt, winCount))            // 排除集 7 档 + winCount ≤ max(表内)
      return SelectFtue(winCount)             // winCount 精确相等；全不命中 ⇒ [0]
  loss = LossStreak                          // <0 = 取不到
  if (winCount < 0 || loss < 0) return 出声兜底(Normal)
  rank = RankedData.Points (夹 int)
  return SelectNormal(rank, loss)            // first-match；全不命中 ⇒ [0]
```

对应判据：

| 环节 | 判据 |
|---|---|
| `SelectNormal` / `SelectFastMode` | `decomp_full/MatchData__GetNormalBotConfig.c:60-78` / `__GetFastModeBotConfig.c`（双边闭合、first-match、全不命中 ⇒ `[0]`） |
| `SelectFtue` | `decomp_full/MatchData__GetFTUEBotConfig.c:46-72`（`winCount ==` 精确相等；全不命中 ⇒ `[0]`） |
| `IsInFtueState` | `decomp_full/MatchData__IsInFTUEState.c:25-60`（排除集 `{10,20,110,120,170,180,150}`；`winCount ≤ max`） |
| 消费口 | `decomp_full/AI__TweakAvailableActions.c:65-71` → `MatchData.GetBotConfig{Min,Max}Skips/SkipChance` |

**取不到数据时的行为**（如实、出声，⛔ 不静默）：

| 取不到什么 | 现象 | 我们的处理 | 原版会怎样 |
|---|---|---|---|
| `GameModesHandler` 未注册 / `RankedSharedData` / `ResultCounterData` 为 null | LiveOps 没 `SetupEvents`（自检 / 批处理） | 退回 `Normal` + `LogWarning` **一次**（`WarnBotConfigUnavailable`） | **NRE**（`MatchData__GetNormalBotConfig.c:39-45` 的 `FUN_1803f47a0` = 「不返回」） |
| `winCount` 取不到（-1） | 同上 | `IsInFtueState` 返回 false（不把 -1 当 0 胜） | — |
| 排位分 | `RankedData.Points` 恒 0（服务器不给 delta） | 按 0 挑（**本地真实值**，不是兜底） | `activeEvent.CurrentScore`（服务器值） |

> ⚠️ 副作用口径：`GameModesHandler.ResultCounterData.ResultCounter` 用 **`TryGetValue`** 读，不用 `GetValuesForMode`
> —— 后者**取不到就新建一条空记录**（`ResultCounterSharedData__GetValuesForMode.c`）⇒ 会给共享数据塞格子。
> 读「胜场」两种读法**值相同**，用前者避免污染。
> ⚠️ `LiveOpsManager.GetHandler<T>()` 在未注册时自己会 `LogWarning`（`Shell/LiveOpsManager.cs:151-159`）⇒
> 一局最多 2 条（每个 match 一次，不是每帧）。这是原版那条 warning 的行为，没吞。

## 五、🔴 与施工单不一致的一处（反证，按「判据与代码冲突时停手写反证」）

施工单第 4 条写「快速模式走 `SelectFastMode`」。**现读判据不支持，本代理没有那样接**：

1. `AI.TweakAvailableActions` 是难度旋钮的**唯一消费口**，它读
   `MatchData.GetBotConfigMinSkips / MaxSkips / SkipChance`（`decomp_full/AI__TweakAvailableActions.c:65-71`）；
2. 那三个入口**只分 FTUE / Normal**：
   `MatchData__GetBotConfigSkipChance.c:17-27` = `IsInFTUEState() ? GetFTUEBotConfig() : GetNormalBotConfig()`；
3. `BotListFastMode` 只在 `MatchData.GetFastModeBotConfig()` 里被查，而那条链服务的是**挑牌**（`MatchData.GetBotDeck` 一族），
   **不喂难度旋钮**；
4. 另有一层：`IsInFTUEState` 的排除集**不含** `200 FastMode / 210 FastModeBot` ⇒ 快速模式在 FTUE 期走的是 **FTUE 表**，
   不是 FastMode 表。

⇒ 把 Skirmish 接到 `SelectFastMode` 会**造出原版没有的行为**（难度变成「按排位分/连败」而不是新手档）。
处理：`SelectFastMode` **实现**（结构照原版、独立表），但**不接**；断言 F-4 把它钉成「驱动里必须 0 处」。
若调度台裁定要接，改动点是 `AssignAiDifficultyForThisMatch()` 里加一条 `mt == MatchType.FastMode/FastModeBot` 分支 —— 但请先回源复核上面 4 条。

## 六、行为变化（如实记，便于验收时判断）

1. **`aiDifficulty` 不再是常量**：每条 bot 对局在 `Begin` 时现挑一次（此后本局不变）。
2. **练习 / 遭遇等非排除档的对局会进 FTUE**：本地 `ResultCounter` 里这些模式通常**没有记录**（`Won = 0`）
   ⇒ `winCount = 0` ⇒ `SelectFtue(0) = SuperEasy`。这是**照原版的**（原版 `IsInFTUEState` 就是这么判的），
   但如果验收时觉得「练习局的 AI 突然变傻」，根因在这里，**不是 bug**。
   注：`Classic`（→ `MatchType.RankedBot`）在排除集里 ⇒ 经典对战**不会**进 FTUE，仍按排位分/连败挑（本地排位分恒 0 ⇒ `Normal`）。
3. **净随机流不变**：`AssignAiDifficultyForThisMatch` 不掷骰、不写 `ctx`、不发事件 ⇒ `play check` 指纹不受影响
   （难度只在 `TweakAvailableActions` 里消费，那本来就是按 `AiRng` 掷的，且只在 AI 回合）。
