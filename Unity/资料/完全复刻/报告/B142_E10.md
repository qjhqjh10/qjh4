## 五、⛔ 阻塞修复（本单唯一超出施工单的代码改动）

### 1. `verify_ocr_fix()` 的陈旧前提 —— 生成器**在我开工前就跑不动**

- **现象**：开工第一次 `--dry` 直接抛：

  ```
  AssertionError: OCR_NAME_FIX[Gauss Warrior (tutorial)]=SAU4（Gauss Warrior）在 card_stats.json 里没有 `ocrName` ⇒ 判据不成立
  ```
- **根因**：该函数的**第一跳**是「池内卡名 == `card_stats.json` 的 `name`」。而 2026-10-14/15 池名换官方表名后，
  `card_stats.json` 仍留旧名（`Gauss Reaper Warrior` / `Tesla Carbine Immortal`，其 `ocrName` 才是新名）
  ⇒ `ocr_of[pool_name]` **恒空** ⇒ 每次重跑都在**最后一步**（`:880` 的 `ocr_fix_lines` 那次 `_verify_ocr`）抛。
  `card_stats.json` 的 `id` 列 1,213/1,213 全是 `null`（`gen_cards_engine.py:776`），没法按 id 落位。
- **修法**（`:342-359`）：**保序补第二跳** —— 池内卡名**本身就是**某行的 `ocrName` 时（`pool_name in by_ocr`），直接拿它当 `ocr`。
  判据强度不变：仍要求「该字面名与 SO 名按 `norm` 相等」，`cid` 仍由调用方从池里按 id 取。实测两条都过。
- **影响面**：只影响 `ocrNameFixes` 那段说明的 `ocr` 文本；不影响任何 `ourId` / tier。

> 这条 **不是**本单的活，但**不修就一条读数都拿不到**（`--dry` 也抛）。如需回退，改动只在那一个函数体内。

### 2. 顺手发现（**未做**，留给调度台分流）

1. **`allcards-no-pool` 是静默档**：若某 pid 在 allcards 查得到、但 `uniqueId` 不在池里，ref 会得 `tier=allcards-no-pool`，
   而 `unresolvedNoName`/`unresolvedNotPool` 两个清单**都不收它**（`no_name` 只筛 `"no-name"`、`not_pool` 只筛 `"no-hit"/"ambiguous"`）。
   **当前 0 例**，但这是一条会静默的口子（`gen_tutorial_stages.py:857-858` 那两个筛子）。
2. **施工单 §八·2 的根治建议仍待办**：`cards_raw.json`（67 MB）在 `.gitignore:274` 里 ⇒ 换机器上这一档自动降级。

3. **剩下 5 个 `unresolvedNoName` pid 也能解**（施工单 §八·1 已列表）：其中 4 个池内直接命中，
   1 个（`8223774895360888806` = `Aggressor Sergeant (tutorial)`）**名字带 `(tutorial)`，数值可能是另一版**。
   ⛔ 本单**故意没动它们** —— 把 `pidname` 全局填上会改变 `ScriptedCardMatches` 的匹配严格度，要单独裁定 + 单独复跑。
