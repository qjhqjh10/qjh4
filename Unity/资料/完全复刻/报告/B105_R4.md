## 三、逐 matchType 的本地分支（这一节决定「离线长什么样」）

`PlayerDataManager.ProcessMatchEndResult`（ILSpy `out_cpp2il_dev_ilspy/PlayerDataManager.cs:8475-8560`）逐支判过：

| MatchType | 分支 | 回调拿到的东西 | Rewards |
|---|---|---|---|
| Ranked 10 / RankedBot 20 | 直接 `inventoryOpsThisSession = 0; return` | **不回调** | — |
| Tutorial 100 | `RecordTutorialFinished` + `CreateTutorialResult` | 非 null | **空** |
| Replay 160 | `LogWarning` + `CreateTutorialResult` | 非 null | **空** |
| TutorialReplay 140 / Scene 190 | — | **null** | — |
| PracticeOffline 50 / Practice 90 / EventAI 80 / Undefined 0 / Unranked 170·180 / FastMode 200·210·211 | `LogError("Not recording yet match results for playMode X")` | **null** | — |

`null` ⇒ `grantedResult == null` ⇒ `SetupDoor.c:104 if (param_5 != 0)` 不成立 ⇒ **`ShowRewards` 一次都不执行**。
⇒ 原版离线态 = 整个奖励块（骷髅 / 奖励 / 评分）全藏。**我们「不喂 + 整行藏」正是这一态。**

## 五、顺手发现（照报）

1. **`decomp_full/MatchResultData__get_GameMode.c` / `__set_GameMode.c` 的「文件名与内容不符」** ——
   `get_GameMode.c` 里是 `AlternateArtCard__get_CardImage`，`set_GameMode.c` 里是 `PlayerHand__set_currentHand`。
   形状与已知的「文件名与内容不符」族一致（`.c` 只有一句 return / 一句赋值）。本判据没依赖这两个文件（`GameMode` 那一格用 `dump.cs` 偏移 + `ShowFinishScreen.c:88` 的写入点交叉证实），但这**又是一例**，可并进「已知 6 例」的清单。

2. **`EndBattleDoors.HideRewardsObjects`（私有）三源 0 调用点** —— `decomp_full` / `out_cpp2il_dev_ilspy` / `out_il2csharp` 都只有定义。
   它的内容与 `SetupDoor.c:78-102` 内联的那串 `SetActive(false)` 几乎逐句相同（`allRewardsGroup → rewardHolderPrefab → skullHolderObj → rewardsHolderObj → ratingObj → skullsObjs`）。
   ⇒ 要么是死代码，要么靠动画事件/反射调用（**未验**，不阻塞本判据）。

3. **`RewardsHolder`（`RectTransform_3458`，495.2×49）在场景里有两颗子件**：
   - `3481` = **`RewardHolder`**（140×50）—— 就是 `EndBattleRewardsHolder` 预制实例那一格；
   - `3228` = **`HolderRating`**（186.9742×45，GO `m_IsActive: true`，组件只有 `RectTransform` + `MonoBehaviour_4922` = 一个 `HorizontalLayoutGroup`：`m_ChildAlignment 4` / `m_ChildForceExpandHeight 1`）。
   这与 `EndPanel.cs` 类尾那段注释已经记过的一致（「原版 `RewardsHolder` 里还有第二颗子件 `HolderRating`…单条奖励时我们居中、原版偏左」）。
   **补一条增量**：`HolderRating` 的 GO 在**场景序列化里是 `activeSelf = true`**，且 `EndBattleDoors` 的字段里**没有任何一格指向它**
   ⇒ 它的显隐**只能**由 `SetupDoor` 隐藏 `rewardsHolderObj(+0x50)` 那一刀连带（父级关掉）。对「整行显隐」的判断没有影响，但补 `HolderRating` 时要知道**它没有独立的控制点**。

4. **场景序列化里 `AllRewardsHolder` / `RewardsHolder` / `SkullsHolder` 三个 GO 都是 `m_IsActive: true`** ——
   但 `SetupDoor.c:78-102` 在调用 `ShowRewards` 之前**无条件**把它们全 `SetActive(false)`，所以「预制体初值亮着」不代表玩家看得到。
   ⚠️ 这条值得记一句：**别拿 prefab/scene 的 `m_IsActive` 当「原版这一屏长什么样」的判据**（同族：铁律「判原版交互不能只看 prefab 序列化字段」）。

5. **`ProcessMatchEndResult` 里 `Ranked(10)` / `RankedBot(20)` 是「不回调」而不是「回调 null」** ——
   ILSpy 版 `:8527 goto IL_02fe`（只做 `inventoryOpsThisSession = 0; return`），与 `.c` 版 `:107 if ((iVar1 == 10) || (iVar1 == 0x14)) goto LAB_180760ebb;` 一致。
   ⇒ 这两个模式的结算回调由别处给（`GameModes.CombatFinished` 那条 LiveOps 路），**⛔ 别把「不回调」当成「结算面板不出现」**。

6. **我们这边已经有 `🔶 自己设计` 的 `OnlineMatchResult` 子集，且注释明写「故意没搬 `Rewards`」**
   （`Shell/PlayEvent.cs:284-305` · `:306-315` `EndMatchData` 只搬 `NewRating` / `ArmyStats` / `RatingBoostState`）。
   本次判据与那个设计**一致**，不需要回头改；若将来要模拟奖励，**改点就在那里**（判据文件 §3 已写明）。

7. **`BattleDriver.cs:32476 if (!_matchResultProcessed)` 那格被注释成「离线等价恒真」** ——
   注释里写「形状留着是为了将来接上真回执时只翻这一格」。本判据给这条注释补了**判据出处**：
   `RankedMatchResult.finishedProcessingResult(+0x1c)` 由 `BattleManager__FinishedProcessingMatchResult.c:33` 写入，
   而那个方法**只有服务器成功回调会调**。⇒ 那句注释是对的。
