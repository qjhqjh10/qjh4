## 一、头像：`avatarUrl` 两条链路 + 根因 + 修法

### 1·1 格式与解析（**只有一条 URL、一个解析点，两半共用**）

- 格式 `<avatarId>#<borderId>`。
- 生产：`PlayerAvatarDataManager.PackPlayfabAvatarAndBorderData`（ILSPY `PlayerAvatarDataManager.cs:1655-1680`）＝ `GetID() + "#" + PlayerAvatarBorderID`（缺参时补当前值/默认值）。
  · `SavePlayerAvatar`（`:1681-1722`）与 `SaveAvatarBorder`（`:1724-1765`）都调 `PlayFabClientAPI.UpdateAvatarUrl`；**请求体字段名是 `ImageUrl`**（不是 `AvatarUrl`），抓包 `logs/live-20261107-201014/0022_UpdateAvatarUrl.req.json` 吻合。
- 解析：`PlayerDataManager.UnpackUserProfile`（ILSPY `PlayerDataManager.cs:11386-11421`；**权威 DEC `PlayerDataManager__UnpackUserProfile.c:73-107`**）：
  `PlayerProfile.AvatarUrl.Split('#')`；len==1 ⇒ `(array[0], 默认边框 36ae26bb…)`；len==2 ⇒ `(array[0], array[1])`；其它 ⇒ `LogError("Invalid Playfab Avatar URL format.")` + 默认头像 `d151b095…` + 默认边框。
  随后**同一个代码块里连着两次** `SetCurrentItemNoSave<PlayerAvatar>(item)` 与 `SetCurrentItemNoSave<CosmeticItemAvatarBorder>(item2)`
  —— ⚠️ ILSPY `:11418/:11421` 把实参打成 `null`/`default`（已知丢常量），**DEC 里是 `DictionaryEntry` 的两段**，别信 ILSPY 那两行。
- 另有一份同名解析 `UnpackPlayfabAvatarAndBorderData`（ILSPY `PlayerAvatarDataManager.cs:1607-1653`），逻辑同上。
- 🔴 **`UserData`/`userData` 里没有 avatarId**，也没有第二个字段；`GroupMember.avatarId/avatarBorderId` 是**别人**（联盟成员）的字段（`server.py:747`）。
  ⇒ **「URL 只被用在边框那一路」这个假设是错的**：头像与边框走同一个字符串、同一个 `UnpackUserProfile` 分支。

### 1·2 头像从哪个集合来

`SetCurrentItemNoSave<T>(string id)`（ILSPY `:1144`）→ `GetItemWithId<T>(id)`（`:751`）→ `GetAllItems<T>()`（`:1129`）＝ `PlayerDataManager.singletonManager.fullCosmeticCollection.OfType<T>()`（该 List = `CollectionManager.FullCosmeticCollection` 的转发）。
🔴 **`GetItemWithId` 的兜底（关键）**：DEC `PlayerAvatarDataManager__GetItemWithId_object_.c:24-224` —— 先按 id `FirstOrDefault`，**查不到就按「该类型默认 id」再 `First`**（头像 `d151b095…` / 边框 `36ae26bb…`）；连默认件都没有 ⇒ `First` 抛 `InvalidOperationException`（＝ OFF-11 那条 `Sequence contains no matching element`）。

### 1·3 为什么「边框变了、头像没变」——已排除 URL，问题在**喂给显示层的那一个值**

**运行时证据（模型两半都对）**：`avatarprobe.tsv`
· 20:21:20.685 `PADM.PlayerAvatarBorderID = bf2f8e5c…`（新边框）
· 20:21:38.883 `PADM.PlayerAvatarItem = 2c8553… Avatar_UM_Premium_Primaris Techmarine`（新头像，`type=PlayerAvatar`）
· 20:21:38.883 `REFRESH-OUT ... selected=2c8553…`，`displays=400`
⇒ 内存里的 `PlayerAvatarItem` / `PlayerAvatarBorder` **都已换成新的**；`state.avatarUrl` 也正确。

两条消费链：

| | 头像 | 边框 |
|---|---|---|
| 取值 | `PlayerAvatarItem`（`:443`，`LoadableReference.Reference`） | `PlayerAvatarBorder`（`:510`） |
| 喂给 | `AvatarTab.RefreshDisplays`（`:404-458`）/ `OnAvatarClick`（`:460-477`）/ `PlayerProfileUIController.SetProfileAvatar` / `PlayerInfoDisplay.Initialize`（`:233-260`，走 `GetItemWithId`） | 同左 |
| 落地 | `AvatarDisplay.ChangeAvatar`（`:232-260`）→ `avatarImage.sprite = avatar.Image` | `AvatarDisplay.ChangeBorder`（`:262-290`）→ `avatarHolder.sprite = border.Image` |

🔴 **唯一的结构性不对称**：两者**都**是 `if (avatar != null) {…}` / `if (border != null) {…}` —— **传 null 时直接跳过、保留旧图**。
所以只要某处喂的 `avatar` 是 null、而 `border` 不是 null，画面就**恰好**是「框变了、头像没变」。

**已证实的第一处（顶栏，mod 侧）**：`E:/warpforge/05_工具/mod/WfOfflineProbe/Probes/ProfileFixProbe.cs:131-136` 取的是
`DefaultAvatarItem` / `DefaultAvatarBorderItem`（**默认件，不是当前件**），`:168-169` 再 `SetProfileAvatar/SetProfileAvatarBorder` 打进去，且 `_done` **一次性**。
时间线坐实：`profilefix.tsv` 20:10:39.012 `PlayerAvatarItem=1d2e2245`（正确的那个）→ **0.2 秒后** 20:10:39.219 `FILLED` 用默认头像把它**覆盖**。⇒ 顶栏从启动起就是「起始头像 + 默认边框」，与玩家选谁无关。

**第二处（未证实，最可能的“资料页/其它按 id 查”路径）**：`PlayerInfoDisplay.Initialize` 走 `GetItemWithId<PlayerAvatar>(PlayerAvatarID)`；id 不在 `GetAllItems<PlayerAvatar>()` 里时会**静默回落成默认头像**（1·2 的兜底），而边框 id 可能查得到。
**第三处（可能性低）**：`avatar.Image`（`imageReference.Load()`）加载失败 → `ChangeAvatar` 里 `avatarImage.enabled = (sprite != null)` ⇒ 图直接消失（不是「保持旧图」）。静态判据不支持它：`cosmeticavatarsimages_assets_all.bundle` 在 `game/Warpforge_Data/StreamingAssets/aa/StandaloneWindows64/`（33 MB），两个头像的 sprite GUID 都在 catalog 里、`assets_full/.../Sprite/Avatar_UM_Premium_Primaris Techmarine.json` 也在。

### 1·4 修法

- **数据侧：不用改**。`state.avatarUrl = "<avatarId>#<borderId>"` 已完整；登录注入点已存在（`server.py:1634-1638` 写 `InfoResultPayload.PlayerProfile.AvatarUrl`）。⛔ 不要为了“让头像生效”另造一个 `userData.avatarId` —— 客户端不读它。
- **mod 侧（必改）**：`ProfileFixProbe.FillTopBar` 改取 `PlayerAvatarItem ?? DefaultAvatarItem` / `PlayerAvatarBorder ?? DefaultAvatarBorderItem`；并去掉 `_done` 的一次性闸（或挂 `OnAvatarChanged`/`OnAvatarBorderChanged` 重刷）。判据：`PlayerAvatarDataManager.cs:443/510`、事件在 `SavePlayerAvatar` 成功回调里**先于**写引用触发（DEC `PlayerAvatarDataManager.__c__DisplayClass31_0___SavePlayerAvatar_b__0.c`，实参就是新 avatar）。
- **一次收口的探针（3 行）**：hook `AvatarDisplay.ChangeAvatar/ChangeBorder`，落 `avatar=<id|NULL> sprite=<name|NULL> imgEnabled=?`。跑一次即可把上面 ② / ③ 分清（模型已证，缺的只是“喂进去的是谁”）。

## 二、战斗记录回放

### 2·1 判据链（全部现读）

1. **置灰判据**：`BattleLogMatch.recordingIndex`（ILSPY `BattleLogMatch.cs:39`）→ `BattleLogItem.Initialize:319-321` `interactable = (recordingIndex != "-1")`。
2. **点击**：`BattleLogItem.ClickReplayButton`（`:346-370`）→ `PlayerDataManager.RecoverMatchRecording(recordId, cb, …)`（`:8620`）；回包 `null` ⇒ 弹 `CustomErrors/ErrorLoadReplay`，否则 `MatchMakerManager.StartReplayMatch`（`Everguild/MatchMakerManager.cs:416-436`：`new MatchData(PlayModes.Replay,…)` + `SetMatchRecording` + 起战斗协程）。
3. **录制从哪来**：`PlayerDataManager.ProcessMatchResult`（`:9470-9478`）把结算回包里的 `BattleLogData` 存内存，紧随调用 `SaveMatchRecording(list, matchType, cancelled)`（`:9500`）：
   `recordName = battleLogData[0].recordingIndex`；`BattleRecordData(matchData, currentServerTime)`（`BattleRecordData.cs`，字段 `type/gameMode/rngNum/oppId/playerEnviromentalCard/enemyEnviromentalCard/oppData/playerData/first/forceFirst/playerLog/enemyLog/playerMulligan/enemyMulligan/ts`）；
   CloudScript **430** payload `{recordName, battleRecord, cancelledMatch}`（`:8563`/`:9500`）。**录像是客户端整包上传的**。
4. **回取**：CloudScript **440** payload `{recordId, targetPlayerId, enemyName}` → `ProcessMatchRecording`（`:8682`）读 `FunctionResult["Recording"]` → 反序列化 `BattleRecordData`。
5. **存储位置**：**服务端 blob（按 recordName 存）**，不是本地文件。`BattleLogData` 本身是 `UserReadOnlyData` 的 key 26（登录下发）。
6. 现状：`server.py:170-221` 三条记录 `recordingIndex="-1"`（当年**故意**的），`saveMatchRecording.json` 注释也写明「离线版不保存录像」；520/380 模板的 `BattleLogData` **故意给 `[]`**（因为非空会立刻触发 430）。

### 2·2 最少要补的四块（+ 风险）

1. **`server.py` 新增 430 handler**：读 `FunctionParameter.Data.{recordName, battleRecord, cancelled}`，把 `battleRecord` **原样**存 `state/recordings/<recordName>.json`（或 `player_state.json.recordings`），回 `{"FunctionResult":{}}`（客户端不解析）。
2. **`server.py` 新增 440 handler**：读 `Data.recordId`（= 模板里的 recordName），回 `{"FunctionResult":{"Recording": <整包>}}`；查不到回 `{}`（客户端 `LogError("Missing recordingData")` + 弹错误框）。
3. **`onPracticeMatchFinished`(520) / `onRankedMatchFinished`(380) 的 `BattleLogData` 改成真列表**：在**第 0 位**插入一条新记录（其余保留），`recordingIndex` = 新记录名；整表落盘，登录下发 `UserReadOnlyData.BattleLogData` 用同一份。请求里已有 `playerHeroId/opponentHeroId/ownName/opponentName/hasWon/ReplaysVersion`（抓包 `logs/live-20261106-203153/0095_ExecuteCloudScript.req.json`），足够拼 `BattleLogMatch`。
4. **三个口必须同刻改**：520/380 一旦回非空 `BattleLogData` 就会立刻打 430（`:9476-9478`）；430 没就绪 ⇒ 走 `removeNotSavedBattleRecord`(650) 把这条删掉。

风险：
- **payload 很大**（双方完整 action log + 两副序列化卡组）。`server.py` 现在把整个 body 写 `.req.json`，日志会暴涨 ⇒ 430/440 只记 `body_length`。
- `SaveMatchRecording` 的 matchType 闸（`:9500-9540`，DEC 里是位测试）只放行部分模式；按 `.c` 推断 Practice(90)/Ranked(10)/FastModeRanked(211) 在内，**未逐字节证明** —— 用日志 `Record match data` 核。
- `StartReplayMatch → StartBattleWithDelay` 要走正常建战；离线版练习局能打，这条链应可复用（**未实机验证**）。
- 老条目 `recordingIndex="-1"` 保持不动（原版「无录像」语义），⛔ 不要伪造。
- 服务端自制存储 = `🔶 自己设计（非原版）：服务器已关服，录像原本存在 LiveOps 后端`，账里要标。
