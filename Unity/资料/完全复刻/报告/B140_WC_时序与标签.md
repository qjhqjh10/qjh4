### 1.2 判据（为什么是 0.9167 + 0.4，而不是 0.55 + 0.4）

- 原版：`_ResolveRecallToDeck_d__543__MoveNext.c:126` `yield return TransformUnitInPlayToCard`（内部 `PlayBackToHandAnimation`，只等 clip 的 **AnimationEvent 0.55**）→ `:350-356` `WaitForSeconds(MoveToDeck(card,1,0))` = **0.4** ⇒ 队列 **0.95**；clip 的尾巴（0.55→0.9167）与第二段**重叠**。
- 我们：`BattleDriver.PlayReturnFeel`（`BattleDriver.cs:25692`）把第二段挂在 `CardFeel.ReturnToHand` 的 `onDone` 上，而那条补间的总长 = `CardFeel.HandToBoardEnd` = **0.9167**（`CardFeel.cs:1905` `AppendInterval(HandToBoardEnd)`）⇒ 第二段**只能**在 0.9167 之后起（`ReturnFeelArrived`，`BattleDriver.cs:42040` 传 `EventTiming.MoveToDeckTotal` 0.4）。
- ⇒ 队列要覆盖的是 **0.9167 + 0.4 = 1.3167**。算式的第一段**替换**（不是相加）：`0.55 + 0.9167 + 0.4 = 1.8667` 会把下一条事件**多**推后 0.55 s，已写进 doc 与断言（A3d）。
- 其它分支逐项未动：回手 `0.55 + 0.2 = 0.75` · `teleport` 两档各 +0.55 · `Slot < 0` 三档（0.3 / 0.3 / 0）· **`DurationOf(EvtKind.Return)`（拿不到事件那条重载）仍是 0.75**。

### 1.3 ⚠️ 「不把下一条事件推后」这条口径 —— 如实反证（未按字面做到）

派活原文要求「确认**不**把下一条事件推后（只缩短第二段的等待，不动第一段补间）」。**这两半在现有白名单里无法同时成立**：

- 第二段的**起播时刻**由 `CardFeel.ReturnToHand` 的 `onDone` 固定为 **0.9167**（改它就等于改第一段补间，而「不动第一段补间」是硬约束）。
- 要「不推后」（总量仍是 0.95），第二段就只剩 `0.95 − 0.9167 = 0.0333 s` 可排 ⇒ 只能把 `MoveToDeckTotal` 压成 0.0333，**而这会把 `CardFeel.ReturnToDeck` 的飞回补间本身压成 33 ms**（原版 0.4 s 的飞行），是比「推后」严重得多的偏离。
- ⇒ 取「总量 = 两段真实时长之和」，代价 = 同一批里后续事件比旧值晚 **0.3667 s**（相对原版则只差「我们没有 AnimationEvent 截断点」这一条既有差异，`B124_W31b` 报告 :43 已记它「不在那笔范围」）。
- **没有偷加**别的东西：`MoveToDeckTotal` 仍是 0.4（断言 A4 钉死）、无事件重载仍是 0.75（A9）、`DelayBetween` 未动。
