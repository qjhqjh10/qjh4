## 3. 最小修法

### ✅ 主修（已实测：`play check` 完全回到基线）

**文件**：`d:/4/Unity/MyGame/Assets/RuleEngine/Core/CardPoolCriteriaFilter.cs`
**行**：`:73`（`IsCardPoolTargetsAffected` 的 `case 180:`）

```csharp
// 删掉这一行：
                case 180:  // choiceResolution          （`:123`，全卡池回落）
```

（顺带把文件头 `:23` 的 `· 180 choiceResolution （:123，全卡池回落 —— 那一支原版直接调 CheckIfRawCardMeetsCriteria）` 那条射程说明一起改掉，
并订正 `:41-50` 的「现池影响面」：那一节只统计了「带四组数值 stat 过滤」的行，漏掉了 **43 行**「全默认格 + `includeSpells=0`」的 `ta=180` 行。）

**为什么（判据，第一手）**：

`BattleManager.GetChoiceFullPool`（ILSpy 可读版 `d:/2/tools/cpp2il/out_cpp2il_dev_ilspy/BattleManager.cs:25622`）：

```csharp
RawCardScript rawCardScript = ((EntityScript)actingCard).rawCardData__BackingField;
List<CardScript> targets = AbilityLogic.GetTargets(this, rawCardScript.choicesDefinition, actingCard, actingCard, cardScript, checkMaxTargets);
TargetCriteria choicesDefinition = rawCardScript2.choicesDefinition;
List<RawCardScript> list = choicesDefinition.filterSpecificCards;
if (choicesDefinition.targetsAffected != TargetsAffected.choiceResolution) { …从 targets 投影… }
else if (choicesDefinition.filterSpecificCards == null || list._size == 0) { list = cardsTargetedInChosenResolution; }
```

两条硬结论：

1. **喂给 `AbilityLogic.GetTargets` 的 criteria 是 `rawCard.choicesDefinition`（卡自己的 `ChoicesDefinition`），不是 `abilityLogic.targetCriteria`。**
   ⇒ 我们的 `op.TargetCriteriaSet`（来自 `abilityTargetCriteria` 列 = `AbilityLogic.targetCriteria`，见 `gen_cards_engine.py:2111`）
   **本来就不该筛「选牌候选池」** —— 候选池归 `ChoicesDefinition`（我们的 `choicesTargetsAffected` / `choicesSpecificCardIds`）。
2. **`ta == 180` 且 `filterSpecificCards` 非空时，池子就是那张表本身，一格 36 格筛都不跑。**
   EC59 的 `choicesSpecificCardIds` 恰好就是那 6 张 Elixir（`5a8a11b2…` 等，实测逐张对得上）⇒ 原版池 = 6 张、原样给出去。

补充正文判据（`d:/2/tools/decomp_full/AbilityLogic__GetTargets.c:85-88`）：`ta == 0xb4` 的全卡池回落支
带一个前置闸 `(param_2 + 0x70 == 0 || Count == 0)` —— **`filterSpecificCards` 非空就不进这条支**。
所以即便从 `GetTargets` 那一侧看，EC59 这类卡也不会走「全卡池 × `CheckIfRawCardMeetsCriteria`」。

### ⚠️ 建议一并做（同样有第一手判据，当前池上零差异）

`CardPoolCriteriaFilter.cs:74` 的 `case 190: // lastPlayedIfMeetsCriteria` **也不该筛**：
`AbilityLogic__GetTargets.c` 的 `iVar6 == 0xbe`（190）支建完池后 `goto LAB_180818485`，
而 `LAB_180818485:` 就是 `return *puVar13;`（`GetTargets.c:1378-1380`）—— **直接返回，不过末尾那道
`FilterMethods__CheckIfMeetsCriteria` 循环（`:1095`）**。
实测：把 180 和 190 一起删，`play check` 仍然逐字节等于基线（主档 1129 · 电池 1073）。

### 🛡 建议加的第二道闸（防同一类崩，可选但强烈建议）

`Apply` 目前**允许把非空池筛成空**，而 `DoChooseCard` 的早返只看 `FilterChoose` 的 `why`（`EffectResolver.cs:4803`）。
`ta ∈ {50,51,52,60,65}` 那几档（手牌/牌库/墓地）今天还留着同一条通路 —— 一旦某个 criteria 把池筛空，
就是**一模一样的 `cands[0]` 越界**（静默 → 崩溃）。做法二选一：

- 在 `EffectResolver.cs:4791` 之后加：`if (outp.Count == 0) { why = "…36 格 criteria 把候选池筛空了（原版不该到这）"; return outp; }`，让 `DoChooseCard:4803` 的早返如实报出来；
- 或在 `TakePickCard:4520` 进函数时 `if (cands == null || cands.Count == 0) return null;`，并让 `DoChooseCard` 处理 `pick == null`（记为 `unresolved`）。

⛔ **不许**用 `try/catch` 包住 `TakePickCard` 了事（那是吞掉，不是修）。

## 5. 排除掉的三个假设（都**不是**原因）

1. **`RarityOf` / `rar.Value`（`TargetCriteriaEval.cs:1098-1100`）—— 不成立。**
   `RarityOf` 在 `:630` **有** `case "special": return 5;`；而且 `:1099` 有 `if (rar == null) { … return null; }` 的 null 检查。
   更直接：EC59 的 `rarityFilterOption = 0`（`NotApplicable`）⇒ `RawStat` 在 `:1131` 就 `return true`，**压根没走到稀有度那一格**。
   且抛的是 `ArgumentOutOfRangeException`，不是 `InvalidOperationException`。
2. **`Apply` 原地 `pool.Clear()` —— 本次不是元凶。**
   `CreatePool.FilterChoose` 在 `CreatePool.cs:347` `var outp = new List<CardDef>();` —— 返回的是**新表**，
   `:4791` 传进去的 `outp` 与 `ctx.CardPool` / 任何别的持有者**不是同一个对象**（`ctx.CardPool` 实测仍是 1129 张）。
   原地改本身没毒，毒在「改完可以是空的、而调用方没接」。
3. **`:4707` 那一处 —— 不成立**（二分表里「只还原 `:4707`」仍红、且 `op.ChooseSrc` 实测全是 `pool`）。
