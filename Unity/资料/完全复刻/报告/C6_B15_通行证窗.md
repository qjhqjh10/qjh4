## 四 顺手发现（⛔ 我没动手，交调度台分流）

1. 🔴 **`ExpansionPassEvent` 的 `IsLimited` 与 `LimitRewardQuantity` 有一个原版自带的坑**：
   `ExpansionMilestone` 把 `IsLimited` **override 成恒 `true`**，而 `IsMilestoneCollected` 的判定是
   `RewardClaimCount(index) >= LimitRewardQuantity`。若某档 `limitRewardQuantity == 0`（远端数据里有可能），
   原版会**恒判「已领取」**。我按原样照抄、把我们的构造默认值定成 **1**，并在注释里写死「⛔ 别加 `>0` 补丁去修」。
   → 建议：真接远端里程碑表时，**先抽验一次 `limitRewardQuantity` 的实际取值分布**。

2. 🔴 **`C2` 的 `Shell/ScoringEvent.cs` 与我的文件有过一次重名冲突（已按调度台指令解决）**：
   我原先自带 `ScoringDataInfo` / `ScoringMilestoneState` 两个类型，与 C2 的重名（CS0101/CS0111）。
   已**删掉我那份、改用 C2 的**。形状差异（**只记录、我没改 C2 的文件**）：
   - C2 的 `ScoringDataInfo` 是 **3 参构造 + 只读属性**（我原来那份是公开字段 + 无参构造）。我这边只读、只用 3 参构造 ⇒ **零适配**。
   - C2 的 `ScoringMilestone` 是**抽象基类**（`SetRaw(score, limit)` 是 `protected`，`Rewards` 是抽象属性）。
     为免出现「两套里程碑层级」，我把 `ExpansionMilestone` 改成**继承 C2 的那个基类**（`SetRaw` + `override IsLimited => true` + `override Rewards`）。
     ⇒ 结论：**C2 那份可以直接当我的基类用，不需要他改任何东西**。唯一不便：`ScoreToUnlock` / `LimitRewardQuantity` 变成只读属性，
     所以 `ExpansionMilestone` 用构造器写；自检若要在外部改分数，得走 C2 的 `SetRaw`（`protected`）⇒ 只能通过构造。
