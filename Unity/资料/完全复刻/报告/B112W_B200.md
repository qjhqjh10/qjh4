> 结论一句话：**我们是对的 —— `all friendly units` 在原版确实包含督军；第 2 个对象 = 己方督军（槽 4）。`queued=2` 不是缺陷。**

## 一、结论（我们错 / 我们对我们错在夹具 / 查不到）

**我们是对的，不是缺陷、也不是夹具错。** 那个「多出来的对象」就是**己方督军**，原版卡面写的是 `units`（不是 `troops`），
且原版该条 `targetCriteria` 明写 `includeHero = 1` ⇒ **督军本来就在目标池里**。
B-127 报告 §五·2 那条疑点（「`Give Armour 2 to all friendly units` 还给了别的对象」）**关闭**：
`queued = 2` = 「1 个自己人 + 己方督军」，**完全正确**；当时的疑点来自「没查 `includeHero` 那一格」，不是实现缺陷。

## 六、顺手发现

1. **B-127 §五·2 的疑点关闭**：`queued=2` = 「自己人 + 己方督军」，是原版行为。
2. **全池交叉核对（只读，`cards_raw.json` × `cards_engine.json`）**：
   - `desc` 含 `friendly units` / `your units` / `all units` 的卡 **61 张** —— 能从原版 logic 级 criteria 取到 `includeHero` 的，
     **没有任何一条是 0**（取值只出现 `1` 或「取不到」）；
   - `desc` 含 `friendly troops` / `your troops` / `all troops` 的卡 **38 张** —— 37 张 `includeHero = 0`；
     唯一「1」= `GOF104 Drag it Down`，它同一张卡里混着「for each friendly **unit**」（count 行，`includeHero=1`，正确的）
     与「all friendly **troops** in hand」（另一条 logic 行）⇒ **不是反例**。
   ⇒ **本仓「units ⇒ 含督军 / troops ⇒ 不含」的口径，原版数据支持**（`CLAUDE.md` §二 那条）。
3. **`AddSide` 自己不筛残骸**（`EffectResolver.cs:3030-3041` 没有 `IsRemnant` 闸），而 DA53 原版 `includeRemnants = 0`。
   今天不外显：`op.TargetCriteriaSet` 被贴上了（探针实测 `rem=0`），`ApplyTargetCriteriaFilter` → `TargetCriteriaEval.Matches`
   （`TargetCriteriaEval.cs:289`：`if (!FlagOn(set.IncludeRemnants) && candidate.IsRemnant) return false;`）会剔掉残骸。
   **但**这只覆盖「criteria 贴得上」的 op —— 走 `logic-gate` / `no-row` 降级的 op 拿不到 `TargetCriteriaSet`，
   那时「all units」类正文会把残骸也算进去。**未查清**：全池有哪些 op 会落到这两档降级（没做全池遍历）。
   ⇒ 建议立一条账，**不阻塞**本结论。
4. **日志措辞会误导排查**：`play DA53` 打了一行「ability 级 `targetCriteria` 判不了 ⇒ 本次不筛 … `abilityLevelCriteria` 列没落（旧表 < v26）」。
   实测 DA53 的 `abilityLevelCriteria = []`（原版 ability 级那一格本来就是**全 0**）⇒ **行为上无事**；
   但这句把「这一格本来就没有条件」说成「旧表没落」，会让排查者以为数据缺失。**未查清**：生成器对「全 0 的 ability 级 criteria」
   应当落一行全 0、还是保持空数组（这是日志/口径问题，不是本条的结算缺陷）。
