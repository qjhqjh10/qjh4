- **日志两条**：`Check` 文本里带全部计数；额外一条 `Debug.Log` 明写「不适用（空集）+ 原因 + 不覆盖范围」，
  人翻日志时不会再把它读成「没验到」。

## 🔴 为什么不照「`hc` 沿 +x 平视」那一版（我在上一版报告里给的补丁已作废）

`forward = (1,0,0)` 靠的是「方向与两个平面法线**精确**垂直」。但 90° 旋转在 float 里**不精确**：
`Quaternion.LookRotation(±x)` 转 `(0,0,1)` 得到的是 `(0.99999994, 0, 5.96e-8)`（我手算了这一步），
`dir.z = 6e-8` 会让敌兵平面 `vdot = −6e-8 ≠ 0` ⇒ `enter = 4/6e-8 ≈ 6.7e7 > 0` ⇒ **判命中**。
这正是本文件 B 段旧注释里记的那个实测坑（`Euler(-90,0,0)` 的 `forward.y = 0.99999996` ⇒ 落点 `(0, 47171730, −4)`）——
**换一个轴同样的病会再来一次**。

**改用「两个平面都穿过相机」的摆法**，机理与方向、与残差**完全无关**：
- 射线原点 = `相机位 + forward × nearClip`（Unity `Camera.ScreenPointToRay` 的定义）；
- 平面过相机位 ⇒ `distance = −dot(相机位, normal)`；
- ⇒ `ndot = −dot(origin, normal) − distance = −vdot × nearClip` ⇒ **`enter = −nearClip < 0`** ⇒
  `Plane.Raycast` 的 `return enter > 0` 不成立 ⇒ **恒打空**；
- 万一 `vdot` 恰好为 0，走的是 `vdot ≈ 0` 的平行分支，同样 `return false`。

⇒ 两条平面**结构性地**打空，不需要任何浮点巧合。`floorY / enemyRowZ` 直接取相机位的 y / z 来表达这条不变量
（代码里写的是 `ret.floorY = hc.transform.position.y; ret.enemyRowZ = hc.transform.position.z;`，读的人一眼看得出「过相机」）。
