## ④ 顺手发现（都写进 §8 了，这里列要点）

1. 🔴 **`_tmp_view/wfres/r1_decoded2/` 里 885 份 JSON 中 858 份的 `m_Script` 是垃圾值**。
   根因：**TypeTreeGeneratorAPI 从 IL2CPP 元数据生成的 MonoBehaviour 类型树，`m_Enabled` 节点没有
   `kAlignBytes(0x4000)`** ⇒ 紧跟其后的 `m_Script` PPtr **早读 3 字节**（Unity 在 `m_Enabled` 后真有 3 字节填充）。
   实测 `#1430` 读出 `{16777216, 76420218880}`（真值 `{1, 4555}`）、`#544` 读出 `{33554432, 201343369216}`（真值 `{2, 12001}`）。
   **影响面很小但要知道**：`m_Script` 后紧跟 `m_Name`（string，4 对齐）⇒ 读口自愈，**其余字段不受影响**；
   R1 表 `类名` 列也不受影响（那一列是 `parse_monobehaviour_head()` 直接读字节得到的）。
   **修法**（已进 `工具/r1_residual_decode.py:_align_fix()`）：给 `m_Enabled` 节点 `m_MetaFlag |= 0x4000`。
   **没做**：没有重跑那 886 条去刷 858 份 JSON（那属 `r1_decode2.py` 重跑，不在本波清单）。
2. **复核给 R1-02 的建议是错的**（不是"走 tpk 的 GUISkin 类型树"，tpk 里没有这个类）；正确的走法是
   **IL2CPP 元数据 + 模块程序集名 `UnityEngine.IMGUIModule`**。附带结论：**Unity 原生类也能从 IL2CPP 元数据出类型树**，
   前提是**程序集名要对**（`UnityEngine` 查不到，`UnityEngine.IMGUIModule` 才查得到）。
3. **`resources.assets #1427` 与 Addressables `localization` 包里的那份 I2Languages 不是同一个字节流**
   （10,764,793 vs 10,764,841 B）—— 但**解出来的词条表几乎一样**（仅 1 条 + 版本戳不同）⇒
   **K07 用包那份是对的**，本 build 内置那份是更早的修订。
4. `r1_decode2.py` 的 `>4 MB 不落盘` 阈值是**静默**的（`dumped=False` 只写在 status json 里）——
   这正是 R1-04 被记成"产物缺失"的来源。建议将来重跑时给它加一行 `print('[skip dump] …')`。
