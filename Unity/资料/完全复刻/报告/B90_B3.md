## §一 数据列设计

### 1·1 列名 / 形状 / 出处

| 项 | 值 |
|---|---|
| 列名 | `enchantment`（卡表的**逐 ability** 稀疏列；卡表版本 **v37 → v38**） |
| 形状 | `[{"at":"buffEffect","ab":i,"lg":j,"buffType":n,"trigger":t,"ta":k,"token":"<模板 uniqueId>"}, …]` |
| 缺值语义 | `[]` = **明确没有**（真值有这张卡、没有任何附魔挂载行）；**缺列 / `null`** = 未知（旧表 / 真值快照里没这张卡）—— 与 `permanentBuffs` / `alternateArts` **同一套三态口径** |
| `at` | 效果挂在哪个对象上（现读 58 行**全是** `buffEffect`；`handBuff.cardEffect` 0 行） |
| `ab` / `lg` | `cardAbilities` / `abilityLogic` 下标（**只用于排查**，⛔ 不参与判据） |
| `buffType` | 原版 `CardEffect.buffType`（`+0x38`）；只落 `12 / 15 / 16` 三档 |
| `trigger` | 原版 `CardAbility.trigger`（`AbilityTrigger`）—— **挂载时机就是它**：`0 = ThisCardPlayed` · `655 = Pray` · 20 / 410 / … |
| `ta` | 原版 `abilityLogic.targetCriteria.targetsAffected`；**载体是谁**由它定：`50 = inHandFiltered`（选中的手牌） |
| `token` | 被挂上去那张模板的 `uniqueId`（= 第二张表 `enchantment_templates.json` 的 `id`） |

**判据（第一权威，逐行读过）**

- `d:/2/tools/decomp_full/CardScript__AddEffect.c:826-828`（`switch (*(int *)(param_2 + 0x38))`）：
  ```
  case 0xc:            /* 12 */
  case 0xf:            /* 15 */
    CardScript__AddEnchantment(param_1, param_2, 0);   break;
  case 0x10:           /* 16：内联等价（同一段 append 逻辑）*/
  ```
  `param_1` = 载体 `EntityScript`，`param_2` = `CardEffect`；模板引用取 `*(param_2 + 0x88)`，
  最终写 `+0x110 (activeEnchantments)` 与 `+0x108 (activeEffects)`。
- `d:/2/tools/decomp_full/CardEffect__IsEnchantment.c:9-12`：`buffType != 0xc && != 0xf ⇒ buffType == 0x10`（= 三档）。
- `d:/2/tools/decomp_full/CardScript__AddEnchantment.c`：`enchantmentCard == null ⇒ LogWarning + return`（⛔ 不是静默）；
  无去重、无合并 ⇒ 同一条 logic 每结算一次就 append 一条。

### 1·2 为什么**不**把 `buffType 0/1/3` 的行落进来（分母订正的核心）

真值快照（`资料/普查产出_1018/allcards_1350/cards_raw.json` 的 `full_raw`）现读：

| 口径 | 行数 | 卡数 | 池内卡 |
|---|---:|---:|---:|
| `buff.enchantment.m_PathID != 0`（松散口径 = B89 报的 130 行） | 130 | 114 | **63** |
| 其中 `buffType ∈ {12,15,16}`（**真挂载口径**） | **115** | 102 | **54** |
| 其中 `buffType ∈ {0,1,3}`（PPtr 非零但**原版不挂**） | 15 | 12 | **9** |

⇒ 池内真实挂载者 = **54 张**（不是 63）。另外那 9 张是「键在、值非零、但不属附魔三档」的死引用
（例：`UM82 Sergeant Gadriel` / `GOF104 Drag it Down` 的 `buff` 里只有 `{"enchantment": {...}}`、没有 `buffType` ⇒ 0；
`GOF90 Wurrboy` 是 `buffType 3`(addTrait) + 一个 PPtr）。

### 1·3 与第二张表 `owners[]` 的关系（为什么不会两处打架）

- `owners[]`（`enchantment_templates.json`，B89/E6c 生成）= **反向视图**，覆盖全部 1,351 张真值卡；
- 卡表 `enchantment` 列 = **正向视图**，只覆盖池内卡；
- 两者由生成器**同一次扫描**（`enchantment_grants_of` 与 `build_enchantment_templates`）得出，
  并有一条**硬断言** `_assert_enchant_index_consistent()`：`owners[]` 里**每一条 `inPool` 的行**都必须在正向列里找到，
  否则 `sys.exit`（⛔ 一个字节都不落盘）。现读：**池内双向一致**，且正向列**没有**多余指向。

### 1·4 ⚠️ 一处必须记住的口径

`ta == 50 (inHandFiltered)` 的那一行（`DA42 Reconnaissance Mission`）**载体是选中的那张手牌**，
不是场上单位 —— 它有自己的专属链 `Enchantments.AttachDA42ToChosenHandCard`（`Enchantment.cs:1230`，已接线）。
本钩子的 `chosen` 是**场上单位** ⇒ 我在挂载端加了一道闸把它让开（否则 = **挂错人 + 双发**）。

## §五 没接上的与原因

1. **`GOF56 Deffkopta`**（部队 · `trigger 0`）：原版单位打出时同样调 `AddEffect` ⇒ 该挂。
   我们的 `PlayTacticCore` 只管战术；单位那条在 `RuleCore.PlayCard`（**B1 独占**）⇒ 见 §七。
2. **`GOF91 Beastboss on Squigosaur`**（部队 · `trigger 20 WhileInPlay`）：载体是「进场后常驻」，
   要一个「单位进场/常驻成立」的钩子（同样在 `RuleCore.PlayCard` 那一带）。
3. **`SW56 Let Loose`**（战术 · `trigger 410 FollowUpResolution`）：要续攻/后续结算的钩子；
   `EffectResolver` 里有没有现成的 410 派发点**没查**（⛔ 不猜）。
4. **多目标**（§3·3）：一次只挂一个目标，`ta=0/65/120` 那几档可能是多目标/全体。
   要修得在挂载端拿到「这条 logic 解析出来的目标集合」—— 那不在 `PlayTacticCore` 的 `chosen` 里。
5. **模板自己的 ability 仍不派发**：`LoadEnchantmentTemplates` 只灌
   `spellType / cardType / whileInPlayAnim / permanentBuffs`（B89 §五·2 已记）。今天这 27 张
   新挂上去的模板 `whileInPlayAnim` 全 = **0** ⇒ 肉眼**看不出来**（唯一可观察的是
   `ActiveEnchantments.Count` 与 `TargetCriteriaEval` 的 `excludeEnchantments` 那一档开始生效）。
   ⚠️ **将来把模板 ability 接上派发时，必须先摘掉 `SAU53` 那条自设计的 `PersistentEffects` 残骸分支**
   （否则双发）—— B89 已登记，本笔未动。
6. **`SW64`**（`owners[].inPool = false`，休眠）：数据列里没有它（不在池）⇒ 靠白名单兜底那一支仍留着它。

## §顺手发现

1. **`data.enchantment.m_PathID != 0` 不能当「这张卡会挂附魔」的判据**（池内 9 张反例）——
   判据是 `switch (buffType)`。这条如果不写下来，下一轮还会有人把 63 张当分母。
   已在生成器长注释里写死。
2. **`TL47` 的 3 条 logic 都是同模板**（`ab0/lg0,1,2`）⇒ 若照数据逐行挂，`activeEnchantments`
   会多出 2 条原版**不会**多出来的记录（原版靠「每条 logic 结算给不同目标」分开）。
   已在本钩子做**同批去重**（H5 钉着）。
3. **`owners[]` 与卡表 `enchantment` 列在「非池内卡」上本来就不完全一致**（正向列只覆盖池内卡），
   所以交叉断言只核 `inPool` 那半边 —— 写清楚免得下一个人误以为「正向列缺行」。
4. **`EffectResolver.cs:2655` 那一句的注释已经过期**（写着「白名单」）：实现已改成数据驱动，
   但那是 B1 的文件 ⇒ 本代理没动，请下一棒顺手把注释里的「白名单」换成「数据源（卡表 v38 `enchantment` 列）」。
   （代码本身不用改：签名与返回值形状一个字没动。）
5. **`EnchantmentTemplateCheck` §G 的 G3（灭自证）在新实现下仍然成立**：摘掉
   `EnchantmentTemplatesProvider` ⇒ `FindEnchantmentTemplate` 返回 null ⇒ `Attach` 不被调用 ⇒ 0 条。
   （我一开始担心「白名单兜底会把它挂上」，实际不会：兜底只决定「挂哪张模板」，模板查不到还是 0。）
