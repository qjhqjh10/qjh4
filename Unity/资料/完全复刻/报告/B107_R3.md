## ⑧ 顺手发现（不在本单范围，但下个会话该知道）

🔴 **`工具/cmp_mesh_vertices.py` 的 stride 计算对「多 stream 网格」是错的。**
- `mesh_positions()`（`:164-175`）与 `read_mesh_asset()`（`:217-260`）都取 `max(c.offset + item_size(...) for c in 所有通道)` 当 stride；**正确做法是只取 `stream == 0` 的通道**（Unity 的 `m_VertexData.m_DataSize` 按 stream 分块存，stream 0 的位置在块首、步长 = stream 0 通道字节和）。
- 实测：`Cone.001`（pid -4292304064909405024）n=1601、`m_DataSize` 96080 B；真步长 **24**（stream 0 = 位置 12 + 法线 12），工具算出 **32**（被 stream 2 的 `offset 16 + 16 B` 顶上去）⇒ **第 2 个点起全错**（例：点 1 真值 `(-0.2441,-0.0937,-0.4615)`，工具读成 `(-0.4615,-0.9808,-0.1951)`）。
- 影响面：**R2-01 的 169 行都是流式环境网格，抽样 10 条全是单 stream（`stride_s0 == allmax`）⇒ 结论不受影响**；但**任何将来用它比「特效网格」（多 stream）的用法都会静默得到错位置**。本报告 §④ 的 26 条重建判定已用**修正后的 stream-0 步长**重算（26/26 exact），A 路覆盖另有**逐字节相同**兜底，结论不依赖该工具的正确性。
- 建议：把 `mesh_positions` / `read_mesh_asset` 的 stride 改成 `sum(item_size(c) for c in ch if c.stream==0 and dim)`；改完重跑 `--all` 应仍是 169/169（单 stream 不受影响）。
