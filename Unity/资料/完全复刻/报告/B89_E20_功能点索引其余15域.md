## 四 顺手发现（⛔ 本代理不改账，全部交调度台）

1. **商店试点块与现账已漂移 50 条（这是本批最实的一条）**：`商店.tsv` 在 10-28 02:11 被更新后，试点的三列、落点行号、验收口行号全部过期。
   已按**现账**重算并重定位，`商店` 现在 **0 失败 / 351 行全认领 / 45 落点 / 23 验收口**。
   ⚠️ **8 个功能点的分布/等级变了**，其中三条值得注意：
   `FP-SHOP-006` **C→A**、`FP-SHOP-007` **A→B**、`FP-SHOP-011` **D?→A?**（`D50` 现读 `A1·D49`）。
   试点原文里「50 行全 D」「等级 C 的唯一来源 = …」这类散文已**就地补一句**「[E20 2026-10-28 重算] 现账 = … ⇒ 等级 …；上文若写旧的分布/等级，以本句为准」，未删历史。
   ⇒ **教训**：`构成条数/状态分布/等级` 必须每次从账重算，**散文里写死分布 = 一定会过期**。
2. **「状态 D / 备注保持 C」的口径冲突仍在**（全域 78 行的同款）：本批机器扫到并写进 `存疑行` 的有
   `本地化.tsv:11`、`其他_基础设施.tsv:44/45/717/718`、`社交_聊天.tsv:131/133/213/214`、`未分类_其他.tsv:215/216/752/753` 等。
   这些行的 `等级` 列已是 `D`、`备注` 却写「保持 C，等用户裁定（⛔ 别顺手判 D）」⇒ **需要调度台统一裁一次**，否则第二层永远带 `?`。
3. **`判据出处` 有两种写法会过不了 C5 的前缀映射**（schema/工具缺口，建议补）：
   ① `il2cpp_out/dump.cs:NNNNN`（编译器生成物 / 第三方类的唯一出处）—— 真实文件在 `D:/2/tools/il2cpp_out/dump.cs`，但 `feature_index_check.py` 的 `JUDGE_ROOTS` 没有这一条；
   ② `cpp2il dev X.cs`（账里常见的口语写法）。
   本批在索引里**改写成了绝对路径 / `cpp2il/out_cpp2il_dev_ilspy/…`**才过闸。
   ⇒ 建议给 `工具/feature_index_check.py` 的 `JUDGE_ROOTS` 加 `("il2cpp_out/", "D:/2/tools/il2cpp_out")`，并让 `abs_path` 认 `cpp2il dev ` 前缀 —— 否则下一个代理还要再踩一次。
4. **账的 `我们的落点` 行号漂移是普遍现象**（本批重定位了相当一部分；另有一批只写了**文件名、没有行号/符号**，如 `Core/Loc.cs`）。
   对后一类，索引按**该文件的主类声明**落点（`Core/Loc.cs:3421（T）` 就是原账里那个 `（T）`），并在本报告留痕。
   ⇒ 建议账侧统一成 `文件:行（声明名）`；否则「落点可机检」这条永远只能靠代理每次重定位。
5. **账的落点有时指向基类/等价实现**（例：`BoosterInfoPopup` 的 `Close` 落到 `Shell/GameWindow.cs:714（Close）`）。
   这是账自己写明的「等价实现」写法，**机检只能验「该行含该名」**，区分不了「本类实现」与「基类实现」⇒ C3 绿不等于「这个类自己实现了」。
6. **跨域类必须用全签名 token**：`特效动画` 与 P0 三域共享 6 个类（`BattleManager` / `CardScript` / `EntityScript` / `AbilityLogic` / `AiScripted` / `RemnantBody`）。
   写 `类.*` 会把 `战斗逻辑驱动` 的行也吸进来（越域 + 多认领）。本批生成器对「类在别域也有行」的情况**自动降为 `类.方法(全签名)`**。
7. **`验收口` 的真伪分三档，本批只给到第二档**：① 专为该功能点写的断言（少）；② **同一窗口/同一功能面的 ★ 或 `Check(` 断言**（多数）；③ 没有可信探针 ⇒ `—`。
   ⚠️ **第二档只挡「这块代码被改坏」，不证明「与原版一致」** —— 与设计 §1.2 的红线一致（`验收口 ≠ 判据`）。
   本批 22 个 `—` 全部是 P3/调试件/编译器生成物/第三方库，**如实标空**而不是拿不相干的断言凑数。
8. **`未分类/其他` 是天然的兜底大桶**（1,183 行 / 436 类）：其中 **约 200 行是编译器生成的匿名类型**（`<>f__AnonymousType*` / `<Module>`）。
   若按「一类一功能点」会产出 400+ 条无法命名的行 ⇒ 本批按**语义桶**（15 桶）+ 显式「兜底桶」处理，并在桶名里写明「无玩家可见入口」。
   ⚠️ 这是 schema 的一处结构性缺口（同商店试点发现的「P3 必然产生一个非玩家可见的大桶」）：**建议 schema 加一列 `可见性`（玩家可见 / 内部）**，否则最差档会把整桶的内部件算进「复刻率」。
9. **`E19` 的五份 part 已在目录里**，与本批拼满 9,623 行 —— 建议调度台合并时**先跑一次总数校验**（`180 FP / 9,623 行 / 未认领 0`），这一步能一次抓出「某份 part 漏合并」。
10. **本批 15 域里 `D` 的分布很集中**：`其他/基础设施` 3 个、`未分类/其他` 3 个、`日常/奖励` 2 个、其余各 0~1 个 —— 说明 P1/P2 面（菜单/外壳、特效、日常、社交）**大多数功能点仍有 B/C 项待做**，不是「没判 D 就等于做完了」。
