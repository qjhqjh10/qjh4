## 二、三条待裁项的答案（含证据）

### 2·1 `FP-NET-05`（联机·接受邀请开关）⇒ **判 D（P3 服务器）；且语义是「公会邀请」不是「P2P 邀请」**

**原版它是什么（回源到手）**：

- 方法真身 = `OnlineData.DoesPlayerDataAcceptInvites(GetPlayerCombinedInfoResultPayload userInfo)`。
  - `d:/2/tools/decomp_full/OnlineData__DoesPlayerDataAcceptInvites.c:1-60`（VA 反汇编）＋
    `d:/2/tools/cpp2il/out_cpp2il_dev_ilspy/OnlineData.cs:390-455`（ILSpy，**这次可读**）。
  - 逻辑：读 `userInfo.PlayerProfile.Tags`（PlayFab `PlayerProfileModel.Tags`），对每个 `TagModel.TagValue` 做 `Split('.')`，
    **任一 token == 字面量 `"NotInv"` ⇒ 返回 false（不接受邀请），否则 true**。
- 配套证据（同一套语义）：`PlayerDataKey.GuildInvites = 25`（收到的公会邀请，`dump.cs:78441`）·
  `CustomError.PlayerCantBeInvitedNotAccepting = 82`（`dump.cs:46000`）·
  `CloudHandle.InvitePlayerToGroup = 1078`（`dump.cs:77123`）·
  本地化键里 6 条 invite 相关**全是公会/联盟**（`CustomErrors/PlayerCantBeInvited*`、`SocialMenu/Alliances/InvitePlayer`、`MainMenu/Guild/PlayerInvited`）。
- ⇒ **这是玩家档案（PlayFab tags）上的一个「别人能不能邀请我入公会」的开关**，**不是 P2P 对局邀请**。TSV 把它挂在 `FP-NET-05`（联机域）是域归属，但实体语义属社交/公会。

**我们这边**：`AcceptInvite` / `AllowInvite` **全仓 0 命中**（`grep -n` 现读，含大小写变体）。
`Shell/SettingsWindow.cs:5971 RefreshOnline` 是🔶自己设计的 P2P 联机页（用户已拍板），**与此开关无关**。

**结论**：判 **D** —— 数据在 PlayFab 玩家档案 tags，`d:/2` 与本地离线 build 都取不到「我的 tags 是什么」；
关服后无法读、也无法写。若将来要做，只能做**本地等价开关**并打 `🔶 自己设计（非原版）：公会邀请开关 · 判据在 PlayFab profile tags（已关服）· 调度台 2026-10-31 裁定`。
⚠️ **不要把它当成「P2P 接受对局邀请」去实现** —— 那会造出原版没有的功能。

### 2·2 `FP-ENG-017`（`GetGameState` 生产 0 调用）⇒ **判 D / 零改动 + 反证（联机同步专用，已有等价物）**

**原版谁调它（3 处，全是联机/同步路径）**：

- `decomp_full/BattleManager__ParseEnemyAction.c`（接收对手动作时拼状态串）
- `decomp_full/BattleManager__ReceiveEnemyDesync.c`（检测到不同步时重传状态串）
- `decomp_full/BattleManager__CancelMatchWithVictory.c`（取消对局时同步终局状态）
- 定义 = `dump.cs:31564 private string GetGameState()`；ILSpy `out_cpp2il_dev_ilspy/BattleManager.cs:17705 / 18271 / 19714 / 19738`。

**我们这边**：`RuleEngine/Core/RuleCore.cs:15059 public static string GetGameState(BattleContext ctx)` 有实现，**全仓 0 调用**（现读）。

**结论**：这不是「漏接的生产链」，而是**原版把它当联机状态串用**；我们的 P2P（`CardPresentation/Net/*`）用的是
**局面指纹 `Fingerprint` / `PlayerHash`** 这一套等价物（CLAUDE 已记「两端指纹不一致 = 3844 差异」那条）。
⇒ **判 D：零改动 + 反证**（样板 = `B9_W69ENG4`），并在账里写清「原版 3 个调用点全在 ParseEnemyAction / ReceiveEnemyDesync / CancelMatchWithVictory 三条联机路径，我们以指纹机制等价覆盖」。
⛔ **不要**去给 `GetGameState` 硬加一个本地调用点（那是造原版没有的行为，且会与指纹机制两处写同一条规则）。

### 2·3 `FP-CAMP-05`（按战役进度开战入口）⇒ **原版战役页【没有】开战入口 ⇒ 判「非缺口（等价）」**

**直接证据（去 `decomp_full` / ILSpy 找 `CampaignTab` 的方法体）**：

- ⚠️ 原版类名是 **`CampaignWindowTab`**（不是 `CampaignTab`；`dump.cs:68005` TypeDefIndex 1705）。
- 它的**全部方法**（`dump.cs` 逐条）：
  `OnSetup / OnOpen / ToggleChooseArmyText / LockArmySelectorByArmy / ToFocus / GetTutorialTrackArmyNode /
  SetFirstTutorialTrackArmyNodeDone / OnClose / ClickChangeArmy / ChangeArmy / SetActiveCampaign / OnNodeClicked / TryCollect`
  —— **没有 `StartMatch` / `ToBattle` / `GoToBattle` / `StartBattle` 任何一个**。
- 方法体（ILSpy `out_cpp2il_dev_ilspy/CampaignWindowTab.cs:676` OnNodeClicked、`:765` TryCollect）：
  - `OnNodeClicked(node)` **唯一动作** = `WindowsManager.OpenWindow<CampaignRewardsWindow>(context)`（开奖励窗）。
  - `TryCollect(node,tier)` = `currentCampaign.CollectRewards(...)`（领奖）。
  - 两者都**不开战**。
- 再往上一层：**`Campaign` 的基类是 `LiveOpsEvent<CampaignPersistence, CampaignEventData>`（`dump.cs:124921`），不是 `PlayEvent`**
  ⇒ 它**没有 `StartMatch()`**（对比：`PracticeEvent`/`RankedV2Event`/`TutorialEvent` 都是 `PlayEvent` 且都 override `StartMatch`，`dump.cs:130481/131279/134446`）。
- `CampaignNodeData` 字段只有 `NodeId / unlocks / nexts / Cost / Rewards / IsRepeatable`（`dump.cs:52397+`）——
  **没有任何 mission/battle 引用**。

**结论**：战役 = **点数奖励轨道**（点节点→开奖励窗→领奖），**原版战役页根本没有「按进度开战」这条链**。
TSV 里我们「生产里不存在」的状态 = **与原版一致** ⇒ 应判 **非缺口（等价）**，⛔ 别再当「缺一跳」去补。
（我们已有的「事件窗选卡组/选阵营→开战」= `Editor/MainMenuScene.cs:8873/9665`，那是通用 LiveOps 事件窗，与战役页分开，本身成立。）
