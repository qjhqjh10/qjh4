# X7 · B-211 —— 「触发按 `chosenAbility` 执行」的生产口

**结论（一句话）**：**没接。** 不是因为难，而是**对账 B-211 的前提质询不成立** ——
「`AM54`/`GOF93`/`GOF104` 的 380 只活在 `cardAbilities(trigger 410)` 里」**是错的**：
三张卡的 380 **都在 `trigger 0 (ThisCardPlayed)` 那条 ability 上**，410 那条 ability 的 `chosenAbility` 分别是
**30 / 235 / 30**。全池 1,351 张真值里 `chosenAbility == 380` **只有 3 行，全部 `trigger == 0`**。
⇒ 「给 `FireTriggerByNumber` 补一条按 chosenAbility 执行的路」**修不到那三张卡**，
而且能影响的面只有 **37 行 / 33 张**（见 §四）。按施工纪律「查完发现前提不成立 ⇒ 停下给反证，别硬做」处理。

## 二、反证 ①：380 到底挂在哪一行

判据源 = `Assets/RuleEngine/Resources/cards_truth.json`（每卡 `abilities[ab].trigger` + `logic[lg].chosenAbility`），
`trigger` 名表 = `CardDef.cs:1913-1948`（`{"ThisCardPlayed", 0}` / `{"FollowUpResolution", 410}`）。

| 卡 | ability 下标 | `trigger` | 各 logic 的 `chosenAbility` |
|---|---|---|---|
| `AM54` At All Costs | 0 | **0 (ThisCardPlayed)** | **0, 380, 320** |
| | 1 | **410 (FollowUpResolution)** | **30**（`ta=200`） |
| `GOF93` Hunta Rig | 0 | **0** | **250, 380, 320** |
| | 1 | **410** | **235**（`ta=201`） |
| `GOF104` Drag it Down | 0 | 0 | 380 |
| | 1 | 0 | 260, 320 |
| | 2 | **410** | **30**（`ta=50`） |

⇒ 380 **在 trigger 0 那条 ability 上**；410 那条是「后续结算」那一条（`buffOthers` / 强制攻击）。
原版语义也自洽：**打出时** `380 setReferenceCard` 把目标记进引用表 → `320 followAfterResolution` 推迟 →
**410 那条**才把 buff 落到引用表上。（这正是 `AbilityLogic` 的 `setReferenceCard → followAfterResolution → followUp` 三连。）

**错因**（给下一个人）：
`cards_engine.json` 的 `chosenAbility` 列**不是逐行的**，它是 `工具/gen_cards_engine.py:1605-1640`
`chosen_abilities_of()` 产出的 **`sorted(set(所有 abilityLogic[].chosenAbility))`（去重集合）**；
而 `abilityTargets` 是**按 ability** 列的 `[{trigger, ta[]}]`。两条并排看，很容易读成
「380 + 有个 trigger 410 的条目 ⇒ 380 在 410 上」—— **那是把「集合里有」当成「这一行是」**。

## 三、反证 ②：原版的触发到底怎么选 ability

`d:/2/tools/decomp_full/RawCardScript__TriggerAbilities.c`（现读全文）：
`:199-231` 遍历 `cardAbilities(+0x290)` → `CardAbility__CanTriggerAbility(ability, trigger, …)`
筛出与本次触发匹配的 ability → `RawCardScript__TriggerAbility(...)` 跑**这条 ability 的全部 logic**
（每条 logic 的 `AbilityLogic.PlayAbility` 再按 `chosenAbility` 分派）。
⇒ 原版是「**按 trigger 选 ability → 跑它的 logic 链（chosenAbility 驱动）**」，
不是「按 trigger 选一条 chosenAbility」。我们的正文 op 路是它的**等价物**，不是缺口本身。

## 五、去重判据（设计好了，但这次没落地 —— 缺数据面）

若将来要做，唯一安全的判据是「**只在正文 op 为空时才走 chosenAbility**」：

1. `ops = u.Card.TriggerOpsByNumber(triggerNumber)`（`EffectResolver.cs:21069`）；
2. `ops != null && ops.Count > 0` ⇒ **与今天逐字相同**（不碰、不叠加）；
3. `ops == null || ops.Count == 0` ⇒ 再看 `u.Card.TriggerAbilityRowsOf(triggerNumber)`
   （`CardDef.cs:9254`，返回 `(Ab, Lg)` 行）；
4. 每行取 `ca`，`ca <= 0` ⇒ 跳过；`ca > 0` ⇒ 走已被 `UseActiveAbilityCore` 用过的那张分派表
   （`RunActiveRowOpsOrGrantedTrigger`，`EffectResolver.cs:18767/18773`），**⛔ 不另写一份 handler 表**。

这样「全池 1,129 张的触发」在 `ops` 非空时**一个字节都不变**（今天 410 有正文 op 的卡走的就是这一支）。

**为什么这次没落地 —— 缺的那一格数据在三个白名单外的文件里**：

| 缺什么 | 在哪个文件 | 是否本代理白名单 |
|---|---|---|
| `CardDef.TriggerAbilityIndexSpec` 没有 `Ca` 字段（现只有 `Ab/Lg/Trigger/TriggerValue`，`CardDef.cs:9222-9229`） | `RuleEngine/Core/CardDef.cs` | ⛔ 不在 |
| `CardDatabase.MapTriggerAbilityIndices` 不填 `ca`（`CardDatabase.cs:4813-4840`） | `RuleEngine/Data/CardDatabase.cs` | ⛔ 不在 |
| `cards_engine.json` 的 `triggerAbilityIndices` **没有 `ca` 这一列**（生成器 `trigger_ability_indices_of` 只落 `ab/lg/trigger/triggerValue`） | `Unity/工具/gen_cards_engine.py` | ⛔ 不在 |
| 每行 `ta`（`abilityTargets` 只按 **ability** 给 `[{trigger, ta[]}]`，能对上 `lg`，可勉强用） | 同上 | ⛔ 不在 |

⇒ **在 `EffectResolver.cs` 里写不出这条口**：运行期**根本没有**「卡内某条 `cardAbilities` 行的 `chosenAbility`」这个数
（`cards_truth.json` 里有真值，但**引擎运行期不加载它** —— 全仓 `Resources.Load` 只读 `cards_engine.json`）。
硬要凑只能在 `EffectResolver` 里 `Resources.Load<TextAsset>("cards_truth")` 另起**第二份卡数据源**，
那是「两处写同一条规则」＋运行期多一份 1,351 卡的大树 ⇒ **不采纳**。
