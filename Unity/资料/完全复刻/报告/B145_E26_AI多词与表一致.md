### 1·1 原版怎么处理「一条载荷里的多个关键词」

`AI__ScoreFromBuff.c`（现读，全文 154 行）只读**两个**字段：

```
void AI__ScoreFromBuff(undefined8 param_1,longlong param_2,longlong param_3)
{

  if (param_3 != 0) {
    iVar1 = *(int *)(param_3 + 0x38);            // buffType
    if (iVar1 < 4) { if (iVar1 == 1) return; if (iVar1 != 3) return; }
    else { if (iVar1 == 0xc) return; if (iVar1 == 0xf) return; if (iVar1 != 0x5a) return; }
    iVar1 = *(int *)(param_3 + 0x3c);            // ← **一个 buff 只有【一个】 trait id**
    ...（按 iVar1 逐档返回分值；+0x3c 就是唯一的分派键）

```

⇒ **`ScoreFromBuff` 拿到的是一条 buff，而一条 buff 只带一个 trait**（`+0x3c` 一个 int 字段）。
「一条卡面效果给好几个关键词」在原版里是**多条 buff / 多条 scoring criteria**，不是一条 buff 里塞多个 trait。

`AI__ScoreFromPlayingNow.c`（现读）把它们**逐条算、累加**：

```

        fVar6 = (float)AI__ScoreFromCriteria(param_1,param_2,param_3,param_4,uVar3,0);
```

`AI__ScoreFromCriteria.c:247` 那条 `case 0xb`（option 11 = `ValueOfBuffing`）也是「**逐目标 × 每条 buff**」
调一次 `ScoreFromBuff(param_1,uVar6,*(undefined8 *)(param_5 + 0x48),0)`。

**结论（口径）**：`+1 attack and unstoppable` 这类载荷 = 「两份独立的 buff」⇒
**每一项各计一次分，再相加**。⛔ 不是「只按第一个词算一份」，也不是「取最大值」。

改后（**行数守恒 26→26**，账按 `文件:行号` 引用 40+ 处）：

```csharp
string s = payload.Trim().ToLowerInvariant().Replace("[", "").Replace("]", "");
float sum = 0f;
foreach (string seg in SplitPayloadSegments(s))   // 先 `, ` 再 ` and `（与 GivePayload.Parse 同源）
```

`PayloadSegmentScore(seg)`（新分册 `Data/SimpleAI.TraitScore.cs`，**该文件 0 条账落点**）：

1. 段内数字求和；段内**有属性词**（`attack/melee/ranged/health/armour|c/ cost`）⇒ `系数 × max(1, 数字和)`；
2. 否则 `GivePayload.Parse(seg)` 归一成关键词（`blood thirst`→`bloodthirst`、`[Shield] Shield`→`shield`、
   `wings flying`→`flying`）再查 `TraitScore`；**Parse 成功就不再兜底**（哪怕 0 分）——
   嵌入效果文字（`"backlash: …"`）必须留在 0，不能被兜底当成「授了 backlash 关键词」；
3. `GivePayload` 认不出 ⇒ 退回**改前的口径**（第一个非数字词查 `TraitScore`）。
   🔴 **这一档必须有**：`GivePayload` 的 `GiveKw` 只收「能被授予」的 ~60 个词，
   **不含** `unstoppable` / `ward` / `tainted` / `coward` / `relentless` / `transient` / `resolution` /
   `terror` / `psyker` / `reactor` / `requiem` / `landing` / `survivor` / `firststrike` / `precognition` /
   `sneakattack` / `sacrifice` / `poisonous` / `bastion` / `maintenance` / `mutation` / `berzerk`
   **21 个只有分值表的词**（本会话实核：逐个 `grep '" <词>"' GivePayload.cs` 全是 0 命中）。
   缺了这一档，`unstoppable` 会从改前的 1.0 **掉成 0**（回归）—— 第一版草稿就栽在这里，已改。
4. 都认不出 = **0 分**（⛔ 不猜）。

⚠️ 属性系数（1.0 / 0.7 / 0.6 / 0.5）与「`+`/`-` 当符号噪声、取量值」都是**我们配的**（改前即如此，
不是本轮引入）。原版 `addStats` 出口是**带符号**的 `healthChange + rangeAttackChange + meleeAttackChange`；
`PayloadScore` 不知道这一下打自己人还是打敌人（方向由调用方给的 op 决定）⇒ 维持量值口径，**行为不变**。
该处已按铁律 18 标 `🔶 自己设计（非原版）`。

### 2·4 覆盖边界（如实写）

1. **比的是「无单位上下文」的静态投影**：`TraitAiScore(null, id, 0)` 与 `TraitScore(lower(name))`。
   带单位的那 4 个（220/370/850/780）由 B5 补；**`blast(350)` / `shuriken(1120)` 不比**：
   原版读 `e.traitValue`（buff 自带），字符串入口拿不到 buff 对象、退回 `t.KwValue(关键词)`，
   **两者本来就不相等**（B6 把这条边界显式钉住，⛔ 别当成不一致）。
2. **「池内 trait 名」用的是 `DefinedTrait` 枚举（134 条）这个标识域**，不是 `cards_engine.json` 里
   `cardTraits`/`keywords` 的原始卡面字符串（`"Armour 2."` / `"Talent: Alpha Warrior"` 这类是**显示文本**，
   不是标识符；`DefinedTraitNumber` 是大小写敏感的 Ordinal 查表，直接喂卡面串会恒 0）。
   枚举是池内标识的**超集** ⇒ 覆盖面只多不少。
3. **不覆盖**「某个 trait 名在两个入口都不存在」这种情形（那时两边都 0，断言看不出来）——
   那是「表该不该有这一格」的问题，归判据 §6·6，不归一致性断言。

**静态交叉核（本会话现跑，非手抄）**：脚本从**源文件文本**里抽出两张表 + 枚举表，逐 id 比对 ⇒
`TraitAiScore` 43 个 id（37 静态 + 6 动态）、字符串表 43 条、**MISMATCH = 0**；
B4 里那 43 个 id 与「实际非默认值的 id 集合」**完全相等**（无多无少），且 43 个都能在枚举表里查到名字。
