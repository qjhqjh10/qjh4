## 二 🔴 裁定：**不能「提前真抽」**（本件最重要的一条，证据全在代码里）

直觉做法是「在面板那一刻把 `BuildChoiceOptions` 提前调一次」。**这条路会把对局打散**：

1. **面板只在本地那一侧跑**。远端对局是把动作经 `LocalAct:284 → _net.OnLocalAction` 送过去、
   由 `NetApply.Apply`（`BattleDriver:351`）**直接落引擎** —— **远端不跑面板、也没有 ask 这一批**。
2. 所以「在面板那一刻消耗 `ctx.GetRandomInt`」只在**行动方**发生 ⇒ 随机表游标（`RandomNumbersIndex`）
   两端错位；而 `NetProtocol.Fingerprint:557` 把 **`ctx.Events.Count`** 也吃进去
   （`ctx.Log` 会 `Events.Add`，`BattleContext.cs:1855`）⇒ 连**日志条数**都不能只有一侧多。
3. **本地录像重放**同样不跑面板（`ApplyLoggedAction:340` → `NetApply.Apply`）⇒ 同样错位。
4. 另一条死路：把推演塞进 `ChooseCardCandidates`（面板确实会调它）—— 但它是**纯读**口，
   `RuleEngineTest.cs:9265` 有一条断言钉着「**不掷骰、不记账**」，而且 **8 处**测试在调它
   ⇒ ⛔ 不能改成有副作用。

⇒ **抽取必须仍然发生在「两端都会跑」的那一处 = `TakePickCard`**。于是只剩一条路：
**面板「偷看」、引擎「复用」，而偷看一个数都不消耗。**

## 三 改法（`RuleEngine/Core/EffectResolver.cs`，`partial class RuleCore`）

### 3·1 偷看：`PeekChoiceOptions(ctx, owner, op, cands, source)` → `List<CardDef>`（:20176）

- 判据地基：`BattleContext.RandomNumbers[100]` 是**开局一次烧好、之后只读**的定长表，
  `GetRandomInt` 只是「按游标取一格 + 游标 ++」（`BattleContextRandom.cs:62-72`）
  ⇒ **把同一条算式照抄一遍**就能推出「结算时那 N 张会是什么」，而**不动 `ctx` 的游标**。
- 实现上**没有第二份算法**：`BuildChoiceOptions` 里那唯一一处取随机的那行改成 `NextChoiceRandom(...)`，
  偷看模式下它读表 + 推进一个**本地游标**（`_choicePeekCursor`），而**不调用** `ctx.GetRandomInt`。
- 偷看时**不写 `ctx`**：`SetChoiceOptions` 与两句 `ctx.Log` 都加了 `if (_choicePeekCursor < 0)` 闸
  （写了就会「只有跑了面板那一侧多一条事件」）。
- `maxTargets` **必须由调用方给**：开面板那一刻 `ctx.PlayingCard` / `ctx.ActingUnit` 还没指向这一问
  （`ctx.PlayingCard` 的写点在 `EffectResolver.cs:371`，结算里）⇒ `ChoiceLimitOf(ctx)` 此刻读到的是**上一张卡**。
  为此给 `BuildChoiceOptions` 加了可选形参 `int limitOverride = int.MinValue`（老调用点不受影响）。
- 幂等：同一个 ask 再问一次（面板重摆）直接返回缓存那份，**不重复推演**。

### 3·2 复用：`TakePeekedChoiceOptions(ctx, owner, op, cands)`（:20220，`TakePickCard` 里先试它）

四条**同时**成立才复用：

| # | 条件 | 为什么 |
|---|---|---|
| ① | 同一条 ask 的**内容键**（`Verb`+`Source`+`ChooseSrc`+`Payload`）+ 同 `owner` | 🔴 **⛔ 不能按 `EffectOp` 实例认** —— 面板那条来自 `PlayerChooseOps` 的一次 `EffectText.Parse`、结算那条来自**另一次** `Parse`，**永远是两个对象**（`EffectText.Parse` 不缓存）。内容键只用来**配对** |
| ② | `ctx.RandomNumbersIndex` 与推演时**相等** | 同一起点 |
| ③ | 结算时候选表与推演时**逐项同 id 同序**（含张数） | 同一池 |
| ④ | `ChoiceLimitOf(ctx)` == 推演时的 `maxTargets` | 同一 N |

四条同时成立 ⇒「真抽」的结果**必定**就是推演那 N 张 ⇒ 复用时：
**游标按推演的消耗格数前推**（`RandomNumbersIndex = StartIndex + Draws`）＋ `ctx.SetChoiceOptions(...)`
＋ **原样补上那条 `ctx.Log`** ⇒ `ctx.Events` / 随机流 / 残局指纹 **一个字节都不变**。
不成立 ⇒ **丢弃推演、照旧真抽**（= 今天的行为），并 `UnityEngine.Debug.LogWarning` 出声
（⛔ 不用 `ctx.Log`：那正是会让 A/B 两端事件数不等的那一跳）。

## 五 预期影响（简报要求的「单列」）

### 5·1 随机流 / 指纹：**零变化**（与简报的预期**不同**，这里要说清为什么）

简报预期「会改 `play check` 随机流」。**本件不会**，这是设计目标而不是意外：

- 无面板的路径（`ruleprobe play all dump` / `play check` / AI / 远端 / 重放）**根本不会产生推演**
  （推演只由 `PeekChoiceOptions` 产生，而它今天**还没有调用方**）⇒ `TakePeekedChoiceOptions` 恒 `null`
  ⇒ 走 `BuildChoiceOptions`，与改前**逐字相同**。
- 接线之后（§六）也不变：复用路径**逐位等价**于真抽（§3·2 的四条）。

⇒ **可验证的判据**：接线前后 `ruleprobe play check` / `play all dump` 应当**逐字节相同**。
**若变了，就是本件有 bug**（例如偷看漏了 `ctx` 写、或复用没有把游标推到位），别当成「预期变化」放过。

唯一会变的是**面板摆出来那 3 张**（这正是要修的），以及玩家因此**选了另一张**（真人局才有影响）。

### 5·2 覆盖到的 / 覆盖不到的

| 档 | 结论 |
