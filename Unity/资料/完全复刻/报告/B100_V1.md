## 〇 票（一句话）

**不建议整体改 A。建议 `253 → A`（采纳，但理由要换）· `254 → 维持 B`（不采纳，理由与 `B100_D4` 不同）。**

- `253 ChoiceOfCardEnemy`：敌方档**没有面板** ⇒ peek 从不参与 ⇒ 引擎真抽，池、游标、取 `options[0]` 与 `.c` 逐位相同；`SortByCostAndName` 那一格在**我们唯一可达的模式**（离线非 replay）原版**也不排**。**可判 A。**
- `254 ChoiceOfCardPlayer`：`GetChoiceOptions` 本体 1:1，但**原版把「算候选池」与「算 options」放在同一刻**（`GetChoiceOptions.c:36` 就调 `GetChoiceFullPool`），我们**拆成了两刻**（面板那一刻算池、结算那一刻算 options）。凡是「候选池里含正在打出的这张牌」的卡（`ChooseSrc == "hand"` 且筛选词是通称），**两边池必然差一张** ⇒ 面板摆的 ≠ 引擎抽的，而且面板**有可能把玩家正在打出的那张牌当成可选项摆出来**（原版不会）。**可达、可观测 ⇒ 维持 B。**

> `B100_D4` 的 §C·2 / §C·3 结论（`Author of the Codex` 零可观测）**我独立复核成立**；但它把「可达性」收窄成「池 > maxTargets ∧ choose 之前有消耗随机的 op」，**漏掉了「池的计算时刻错位」这一整类**（见 §四）。所以它的 A 建议只对 `253` 成立。

## 一、我自己回源得到的四个答案

### Q1 · 原版**什么时候**算 options？

**就在选择发生的那一刻现算 —— 池和 options 在同一句里一起算，没有任何「提前算好」的缓存。**

| 路径 | 判据 |
|---|---|
| 敌方 | `decomp_full/BattleManager__ChoiceOfCardEnemy.c:31` `lVar3 = GetChoiceOptions(...)` —— 在 `ActiveSkillDisplay.FadeOut`（`:19`）之后、写 `cardChosenInSelection`（`:47`）之前 |
| 玩家 | `decomp_full/BattleManager__ChoiceOfCardPlayer.c:27` `GetChoiceOptions(...)` —— 在 `UnpauseForAnim`（`:18`）/ `UIstate=0xe`（`:20`）之后、`ChooseCardMenu.Setup`（`:50-54`）之前 |
| 入口 | `BattleManager._ChooseCardMethod_d__449__MoveNext.c:16-19` 先 `GetChoiceFullPool` 查空池（空 ⇒ `callback(0)`、不开面板），`:28-35` 再按 `isPlayer(+0x2c)` 分流；玩家支 `:43-53` 等 `UIstate==0xe` 醒来后再 `GetChoiceIndexOfCard(BattleManager+0x2e8)` 取下标回调 |
| **池** | **`BattleManager__GetChoiceOptions.c:36` `GetChoiceFullPool(...)` 是 `GetChoiceOptions` 的**第一句** —— 池和 options **同一个时刻** |

⇒ 原版**没有**「面板先算一份、结算再算一份」这回事：`GetChoiceOptions` 进出一次就把池、options、排序全定了。
⇒ 我们的 `PeekChoiceOptions`（`RuleEngine/Core/EffectResolver.cs:20177`，只读预烧表推演）**不是原版的形状**，它是为了弥补「面板早于结算」这个**我们自己造成的时序**而加的补偿件。补偿在多数卡上是精确的，但不是全部（见 §四）。

### Q3 · 随机游标两边**消耗次数**是否相同？

**相同，且每一次消耗落在同一个 op 上。** 逐条：

| # | 谁在消耗 | 原版 | 我们 | 次数 |
|---|---|---|---|---|
| ① | `GetChoiceOptions` 的主循环，每一圈一次 | `GetChoiceOptions.c:53` `GetRandomInt(0, pool.Count)` | `EffectResolver.cs:19665` → `NextChoiceRandom` → `BattleContext.GetRandomInt` | **= 满足 `|left| ≥ 2` 的圈数** |
| ② | **池只剩 1 张时那一圈** | `MatchData__GetRandomInt.c:18-19` `if (b <= a+1) return a;` ⇒ **不消耗** | `BattleContextRandom.cs:65` 同式；`NextChoiceRandom` `:20077` `if (maxExcl <= 1) return 0;` | **0** |
| ③ | 补齐那一段（`:71-108`） | **没有任何随机调用** | `:19673-19687` 同样**一次都不抽** | **0** |
| ④ | 排序 | `:110-114` 纯比较，不抽 | 不做（同样不抽） | **0** |
| ⑤ | `GetChoiceFullPool` / `ChooseCardCandidates` | `GetChoiceFullPool.c` 全程无随机 | `EffectResolver.cs:4641-4790` 纯读 | **0** |
| ⑥ | 面板（`ShowAsk`） | 原版**没有**独立的第二次算 | `PeekChoiceOptions` 用**本地游标**读预烧表（`:20072-20081`）⇒ **不碰 `ctx.RandomNumbersIndex`** | **0** |

**实例（`Author of the Codex`，池 3 / N 3）**：i=0 时 `|left|`=3 ⇒ 消耗 1；i=1 时 `|left|`=2 ⇒ 消耗 1；i=2 时 `|left|`=1 ⇒ **不消耗** ⇒ **总消耗 = 2**。两边一样。
（注：`EffectResolver.cs:19691` / `:20238` 的日志写「引擎消耗了 `{opts.Count}` 次随机」——池 3/N 3 时它印 3，实际 2。**只是文案**，见 §六·1。）

⇒ **`MatchData.GetRandomInt` 是纯函数式取表**（`idx = cursor % len; cursor++`，`MatchData__GetRandomInt.c:21-25`），两边同起点同列表同算式 ⇒ **消耗次数相同 ⇒ 之后的随机流不再错位**。账里 ①②③ 三条历史残留（「少消耗 N-1」「走 `ShowRng`」「手抄表」）**确已作废**。

## 四、新发现：面板与引擎的**池**不是同一刻算的（`B100_D4` 没覆盖的那一类）

### 4·1 时序

```
原版：  出牌 →（卡离手）→ 结算 …→ ChoiceOfCardPlayer.c:27 GetChoiceOptions
                                        └─ 内部 :36 GetChoiceFullPool（池）+ 抽 N + 排序，一口气

我们：  BeginPlay（卡**还在手牌**，BattleDriver.cs:11126 `hand[idx]`）
          → ShowAsk：ChooseCardCandidates(:11215) 算池 → PeekChoiceOptions(:11233) 按这块池推演
          → DoPlay → PlayCard → ps.Hand.RemoveAt(handIdx)（RuleCore.cs:3956 / EffectResolver.cs:2588，**先离手**）
          → 结算 → DoChooseCard:4802 再算一次池（此时已无这张）→ TakePickCard:4523 真抽
```

判据：`BattleDriver.cs:8307-8309` 的注释 **「我们这张牌**根本没离开手牌**」** —— 面板那一刻，正在打出的那张**还在 `ps.Hand` 里**。

### 4·2 具体卡（现读，`cards_engine.json` v44）

**`Path of the Seer`（`09bcb1b3b8794c4429d82d4b2e68fa1f`，tactic / cardType 20）**

| 字段 | 值 |
|---|---|
| `desc` | `Ephemeral.` / `Choose a card in your hand and return it to your deck. Draw a card. Gain 1 Spirit Stone` |
| `choiceSet.targetsAffected` | **50**（手牌域）· `maxTargets` **3** · `filterSpecificCards` **[]** · `includeSpells 1` · `includeSelf 0` |
| 解析结果（`EffectText.cs:6540-6580` 现读） | `ReChooseWhat` 剥掉 `a ` ⇒ `what = "card"`；`head` = `choose a card in your hand` ⇒ **`ChooseSrc = "hand"`**；`FilterChoose`（`CreatePool.cs:341-380`）里 `w` 剥成空 ⇒ **`any = true`（不筛）** |

| 时刻 | 池 | 依据 |
|---|---|---|
| 面板那一刻 | `ps.Hand` **含正在打出的 `Path of the Seer`**（H 张） | `EffectResolver.cs:4736` `case "hand": source = ps.Hand.ConvertAll(...)`，**没有任何「排除 PendingCard」的闸** |
| 引擎结算那一刻 | `ps.Hand` **不含它**（H-1 张） | `RuleCore.cs:3956` / `EffectResolver.cs:2588` 在结算前已 `RemoveAt` |
| 原版 | **不含它**（H-1 张） | 原版 `GetChoiceFullPool` 也在卡离手之后 `GetChoiceOptions.c:36` |

**后果（两条，都可观测）：**
1. `TakePeekedChoiceOptions` 的复用条件 ③（`EffectResolver.cs:20229` `ChoiceSameCandIds`）**次次不成立** ⇒ 每次都打一条 `Debug.LogWarning`（`:20231`），并回落到真抽。随机流不受影响（真抽消耗与推演相同），**但面板摆的是从 H 张里抽的 3 张，引擎抽的是从 H-1 张里抽的 3 张 ⇒ 集合可能不同。**
2. 面板**有可能把玩家正在打出的那张牌当可选项摆出来**（H≤3 时必然摆出来）。玩家若点了它 ⇒ `EffectResolver.cs:4538` 「面板报回来的那张不在候选里 ⇒ 改由引擎等概率挑」，等于**白选一次**。**原版永远不会出现这个选项。**

### 4·3 这一类的判据（`B100_D4` §C·5 那条前提测试是**错的**）

`B100_D4` 写的前提是「**池 > maxTargets 且 choose 之前有消耗随机的 op**」。这条只覆盖「随机起点不同」，**漏了两个更宽的口子**：

- **A：池的计算时刻不同**（本节）—— 与随机**无关**。`Path of the Seer` 的 choose 是**首个 op**（游标根本没动），照样失配，因为**池差一张**。
- **B：候选池在结算前被本卡自己的前序 op 改动**（如先抽牌/先死人再选）—— 同样是条件 ③ 失配，也不要求任何随机 op。

正确的可达性判据应当是三条并列：
> ① choose 之前有消耗 `GetRandomInt` 的 op **且** 池 > `maxTargets`（随机起点差 ⇒ 集合差）；
> ② 池在「面板那一刻」与「结算那一刻」不是同一个集合（`hand` 域**含正在打出的那张**是最常见的一条）；
> ③ 结算时的池与开面板时不同（前序 op 动过手牌/牌堆/墓地）。

## 五、我不同意 `B100_D4` 的地方

1. **§C·2「可观测差异 = 0」只对 `Author of the Codex` 成立，不能推广到 253/254。** 那张卡 `池 == maxTargets == 3`，所以「失配」只换来一次顺序变换。换成池 > 上限的卡结论就反过来。
2. **§C·5 的重开条件是错的（写窄了）**：它只盯「池 > maxTargets ∧ choose 前有随机 op」，**漏了「池的计算时刻不同」这一整类**（§四）。按它写的那条断言（「满足该条件的卡数必须 = 0」）今天就会是 **0**，于是永远绿灯 —— 而 `Path of the Seer` 每一局都在失配。
3. **§C·4「其余 62 张 `choosecard` 卡的 choose 都是首个 op ⇒ `StartIndex` 不变 ⇒ peek 复用成功」**：这只证明了复用条件 **②**（游标没动），**没有证明条件 ③**（候选逐项同 id 同序）。`Path of the Seer` 正是条件 ② 成立、条件 ③ 不成立的活例子。
4. **§C·3「不改」这一条我同意**（⛔ 绝不能把「算 options」挪到面板那一刻去消耗随机 —— 那会让只跑面板的一侧多消耗）。我建议的修法**不动随机语义**：**让面板算候选时剔除 `PendingCard`**（或让面板与引擎共用同一份 `cands`），这样条件 ③ 在 `hand` 域上自然成立。

## 六、顺手发现（⛔ 未改，只报）

1. **日志把 `opts.Count` 当消耗次数印**：`EffectResolver.cs:19691` / `:20238`「引擎消耗了 `{opts.Count}` 次随机」。池 3 / N 3 时实际只消耗 **2** 次（第 3 圈 `maxExcl = 1` 不消耗）。纯文案，但会让下一个人**拿日志去对随机游标时对不上**。`TakePeekedChoiceOptions` 那边真正的次数是 `e.Draws`（`cur - start`），是准的。
2. **`includeSelf` 在 `ChooseCardCandidates` 的 `hand` 支里没被读**（`:4736` 只做 `ps.Hand.ConvertAll`）。原版 `AbilityLogic.GetTargets` 是读 `includeSelf`/`excludeNotSelf` 的（我们的等价物只在 `CountEval.cs` 那一路有：`CountEval.cs:19-20, :737-739`）。**`choicesDefinition.includeSelf` 的语义我们只在计数路口实现了，选牌口没实现** —— 这与 §四 的「池含正在打出的那张」很可能是**同一个根**（`Path of the Seer` 的 `includeSelf = 0`）。**还没查清**：`AbilityLogic.GetTargets` 的 `includeSelf` 分支对「候选是手牌里的牌、actor 是刚打出的这张」到底怎么判。建议单独立账（属 `GetChoiceFullPool` / `ChooseCardCandidates` 那一行，那一行现在记 **A**）。
3. **排序（`SortByCostAndName`）引擎侧不做**（`:19600-19604` 已如实标注）：玩家档无害；敌方 `bVar5 = false` 档（联网 / `matchType 0xa0` replay）原版会排、我们不排。**今日不可达**（我们既没有原版式的 replay，联机双方又都是人），但**它是一条真的结构差**，将来若做原版 replay 必须补。
