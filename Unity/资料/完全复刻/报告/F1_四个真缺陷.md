## β1 · `DeckFilter.IsEmpty` 漏算 `Costs`

- **根因**：2026-10-25 加「多选费用」时，`Costs` 只接进了 `CostOk` / `CostSelected`，
  **没接进「有没有筛选」这个谓词**。`IsEmpty` 只列了单值五项 + `Factions`/`Rarities`/`Types` 三个集合。
- **改了哪几行**：`Deck/DeckEditorState.cs:177` —— 末行尾部追加 `&& (Costs == null || Costs.Count == 0)`（**同一行，行数不变**）；
  另把 `:166-168` 那句「5 个筛选字段都没设」的 doc 改写成「单值五项 **＋** 四个集合全空」，并把「漏 `Costs` 的后果」写进去（3 行→3 行）。
- **为什么这么改（判据）**：
  - **同一段上一条已经立了这个口径**：只设 `Factions` 集合时 `IsEmpty` 必须为假（`Editor/DeckScene.cs:2077`，一直是绿的）
    ⇒「集合也算筛选条件」在生产里**本来就是既有语义**，`Costs` 是 2026-10-25 新加的第 4 个集合字段
    （`Deck/DeckEditorState.cs:70-77`，注释自己写着「原版 `CardCostFilter` 也是集合」）⇒ 它**必须**和另三个同档。
  - **没有第二份实现**：全仓 `grep "Rarities == null"` 只有 `:176` 一处 ⇒ `IsEmpty` 是唯一判据，改一处即全局生效。
  - **⚠️ 就地订正简报里的一句**：简报说 `Shell/CollectionWindow.cs:3726` 是「同一口径的**另一处**、留给 C1」——
    **它不是另一份实现**，它写的是 `!d.State.Filter.IsEmpty`（`RefreshClearFilter`，`Shell/CollectionWindow.cs:3726`），
    是本谓词的**消费者** ⇒ **我的改动已经把收藏窗那颗 `Clear filters` 一起修好了，C1 那边没有活要干**（见末节「越界发现」）。
- **生产影响（不是只影响自检）**：`hdr_clear`「Clear filters」的显隐 = `!State.Filter.IsEmpty`
  （`Deck/DeckRuntime.cs:4806` 的 `RefreshHeader`）＋ 它的**命中闸**（`Deck/DeckRuntime.cs:8468` 的 `KeyLive`）

- **怎么验（可观察量）**：

  2. 生产侧：`Deck` 页只勾一个费用档 ⇒ `_hdrClear` / `_hdrClearTx` 的 `activeSelf == true`、
     且 `_rt.UiTopKeyAt(钮心)` 返回 `"hdr_clear"`（不是 null）；
  3. 回归：`DeckFilter.None.IsEmpty == true`（六个字段全空）—— 上面 `Editor/DeckScene.cs:5570` 那条「（前提）一个筛选都没设」盯着。

## β2 · 收件箱选中行换底图没同步 `WindowButton._normalTex`

- **根因**：原版 `MessageContainer.ToggleSelection(bool)` 换的是**同一个 `Image` 的 `sprite`**
  （`background.sprite = selected ? selectedMessageSprite : normalMessageSprite`）—— 常态/选中**长在同一个字段**上。
  我们把它拆成两层：底图 quad 的贴图（`RefreshSelection` 换）＋ `WindowButton._normalTex`
  （`Bind()` 那一刻记下的常态图，`Exit()`/`Release()` 还原时用它）。
  **只换前者** ⇒ 悬停过一次的**选中行**被 `Exit()` 还原成「未选中」那张 ⇒ 选中态掉色。
- **改了哪几行**：

  - 类尾追加 `:1202` `const string RowHitName = "RowHit";` ＋ `:1219` `void SetRowNormalTex(int row, Texture t)`
    （反查 `_rowNodes[row].Find(RowHitName)` → `GetComponent<WindowButton>()` → `SetNormalTex(t)`）；
  - `Shell/InboxWindow.cs:1074`：`AddHit(e, "RowHit", …)` → `AddHit(e, RowHitName, …)`（**同一行，行数不变**，名字只留一处定义）。
- **为什么这么改（判据）**：
  - `WindowButton.TexOf(default/Selected)` 两支**都返回 `_normalTex`**（`Shell/WindowButton.cs:185-187`）
    ⇒ 「离开时恢复什么」完全由 `_normalTex` 决定；`SetNormalTex` 的 doc 写的就是这个用法
    （`Shell/WindowButton.cs:466-468`：「底色**由别人换掉之后**要调一次，否则悬停退出时会把这一层恢复成绑定时那一刻的旧图」）。

    而插在那儿会让 `:360/:572/:726/:745/:766/:785/:861/:899/:941/:997/:1044` 全线漂 ⇒ 账要重钉一片。

    反查名字**已经是既有契约**（`Editor/RewardsScene.cs:10952` 的 A273 那一段就是 `FindChild(rowHov, "RowHit")`）。
  - **找不到是合法的**：整条落在视口外时 `MenuDraw.Hit` 按 `ClipRect` 直接返回 null（`Shell/MenuDraw.cs:2235`）

## β3 · `Message Display/Title` 重排后没重新左对齐

- **根因**：左对齐只在 `Build()` 里调过一次（`Shell/InboxWindow.cs:442` 的 `TitleLeft(_mdTitleLb, MdTitle)`）。
  之后 `ShowDetail` 里 `SetText(m.Title)` 换了更长的串 ⇒ `SetTextTmp` 依次做
  `_tmp.ForceMeshUpdate()` + `RefreshBounds()`（`Battle/Label.cs:1604-1605`）——
  而 `RefreshBounds` 是把整块**居中**摆进锚点 ⇒ **宽度变了、中心没变** ⇒ 左缘跟着漂。
  原来那次左对齐的平移量是按**旧宽**算的（`Label.PlaceLeftNow`，`Battle/Label.cs:1774-1780`）。
- **改了哪几行**：`Shell/InboxWindow.cs:790` —— 同一行内改成
  `if (_mdTitleLb != null) { _mdTitleLb.SetText(m.Title ?? ""); TitleLeft(_mdTitleLb, MdTitle); }`（**行数不变**）。
- **为什么这么改（判据）**：
  - 原版那颗是 `m_HorizontalAlignment = **1 (Left)**`（`menu_dump.py` 亲跑，逐字抄在 `Shell/InboxWindow.cs:1116-1117`：
    `…/Content/Message Display/Title` = `'WELCOME TO WARPFORGE CLOSED ALPHA!' … 对齐=Left/Middle`）⇒ 左缘必须钉在框左沿 **791.02**。
  - **`TitleLeft` / `MenuDraw.AlignLeft` → `Label.AlignLeftOn` 是绝对定位、幂等**：
    它先 `RefreshBounds()` 再 `PlaceLeftNow(worldLeftX)`，位置 = `worldLeftX − ParentXInDesign + WorldW/2`
    ⇒ 用的是**当前**宽度，重复调用不会累积漂移（`Battle/Label.cs:1753-1781`）。
  - ⚠️ 顺带一条 **P7 兜底正好用得上**：`SetText` 之后若还没量到宽度，`AlignLeftOn` 会把请求记成 `_pendAlignX`，
    由下一次 `RefreshBounds` 尾句 `TryApplyPendingAlign` 兑现（`Battle/Label.cs:1759-1762`）—— 不会静默丢。
- **怎么验（可观察量）**：
  1. A470 那条：`Content/Message Display/Title` 的**渲染左缘** = **791.02**（修前 1162.89）；
  2. 换一条**更短**的标题（原版短标题那条）再量一次，左缘**仍是 791.02**（挡「按旧宽算，短标题又漂回去」）；
  3. 同窗另一颗 `Content/Title`（`'Inbox'`，不跑 `SetText`）**保持不变**（它本来就是绿的）。

## β4 · `BuildStatLayers` 无条件把 `_statFlash` 刷白

- **根因**：`Build` 的**第一句**是 `CaptureStatChanges(d)`（`Core/CardView.cs:4197`），它按原版
  `CardScript.UpdateHealthText` 的 `doColorChange = 1` 把**持续色**算进 `_statFlash`
  （`StatColorVsBase`，`:3443`）。而同一趟 `Build` **末尾**的 `BuildStatLayers()`（`:4601`）里，
  那个循环第一句是**无条件** `_statFlash[s] = Color.white;` ⇒ 刚算出来的落色被抹回白
  ⇒ `SyncStatLayers()`（`:4602` → 取 `_statFlash[s]`，`:13130`）把四个数值层画成纯白。
  **带伤进场的兵，数值第一次画出来是白的**（下一次 `SetData` 才变红）。
- **改了哪几行**：`Core/CardView.cs:13088` —— `_statFlash[s] = Color.white;` → `if (_statFlash[s].a <= 0f) _statFlash[s] = Color.white;`
  （`:13087` 的那句注释一起改写成「只在槽位仍是数组默认透明时才补白」＋为什么；**3 行进 3 行出，行数不变**）。
- **为什么这么改（判据）**：
  - **原始意图（不能丢）**：`Color[]` 的默认元素是 `(0,0,0,0)` 不是白，
    不补白的话 `ApplyStatFlashes` 会把数字乘成**全透明**（`:13086-13088` 原注释就是这句）⇒
    **⛔ 不能改成「永远不补白」**。
  - **为什么 `a <= 0f` 这个守卫够用、且不会误伤**：`CaptureStatChanges` 的首句就是 `ClearStatFlashes()`
    （`:3424` → `:13527-13531`），它**把六格全填成 `Color.white`** ⇒
    走到 `BuildStatLayers` 时每格的 alpha **必然 ≥ 1** ⇒ 守卫**恒为假**、`_statFlash` 原样保留；
    只有「有人绕开 `Build` 直接建层」那种未初始化态（alpha = 0）才补白。
  - **`BuildStatLayers` 的四个调用点全在 `CaptureStatChanges` / `SetData` 之后**
    （`:2405` SetFace · `:3372` SetData · `:4521` Build 内 · `:4601` Build 内）⇒ 正常路径守卫一次都不会误触。
  - **手牌那条（K4 ②）为什么一直绿**：它先建层、后 `SetData(dmg)`，第二次 `CaptureStatChanges` 之后没人再刷白
    ⇒ 与 `X3` 的静态推断一致（本件已按此实现，但仍**未跑起来**复核，见末节「没修的 / 没验的」）。
- **怎么验（可观察量）**：
  1. `CardView.Create(带伤数据, …, CardFace.Board)` 之后**立刻**读 `bv.StatFlash(CardView.StatHealth)`
     —— 期望 `(0.973, 0.306, 0.353)`（=`CardFeel.StatDownColor`），**实得不再是 `(1,1,1)`**；
  2. 同一张卡的**生命那一层**材质色（`_stats[StatHealth].sharedMaterial` 的颜色键）= 同一个落色
     （`SyncStatLayers` 取 `_statFlash[s]`，`:13130`）；
  3. **回归（⛔ 别让它变红）**：一张**满血**建出来的兵，四个数值仍是**白**（`StatColorVsBase` 在 `cur == bas` 时返回 `Color.white`）；
     以及「数字看得见」（alpha 没被乘成 0）。
