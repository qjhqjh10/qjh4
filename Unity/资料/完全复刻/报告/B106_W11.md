## ⑤ 顺手发现（另立账，未改）

- **F1 · 抽屉内容在画布上整体偏 31.5 / 41.2 px（8 个子件同病）**
  `ScaleAbout(r, 0, 0, 0.8f, entry)`（`DailyRewardPopup.cs:890`）把 `localScale=0.8` 近似成「绕 **Entry 左上角** 缩放」，
  而原版 `NormalReward` 的 `m_Pivot` 是 **(0.5,0.5)** ⇒ 真实是**绕抽屉中心**缩放。
  差值恒为 `0.2·drawerTopLeft + 0.1·drawerSize` = **(+31.5, +41.2) px**（抽屉在 Entry 里的左上角 = (−6.2,−5.51)、尺寸 327.42×423.13）。
  交叉验证：原版 BG 的 Entry 内视觉框 = `39.64..275.38`（`menu_rect.py` 绝对值 − Entry 原点），我们画在 `8.14..243.88` ⇒ 差 31.5 ✔。
  ⚠️ **内部相对关系是对的**（例如 Extra 标识相对 BG 右上角的位置与原版逐像素一致），错的是**整块**的绝对位置 ⇒ 属 R2、需裁定。
- **F2 · `TxtRewardWarning` 用的是 `\n`、官方词条是 `<br>`**
  `Loc.T` **不**把 I2 的 `<br>` 转成换行（`Core/Loc.cs` 全文 0 处 `<br>`）⇒ 直接绑上去会**把 `<br>` 印在屏幕上**。
  我这一颗（`InboxWindow.cs:534`）**就地做了 `.Replace("<br>","\n")`**，与出厂字面量逐字相同。
  🔴 **同族风险**：其它窗（`RewardWindow` / 战役窗…）若绑到含 `<br>` 的词条，会踩同一个坑 ⇒ 建议在 `Loc` 或 `Label` 层统一处理一次（另立账，不属本件）。
- **F3 · `RewardsScene.cs:10328` 的注释已过期**
  它写「期望值是**手写字面量**（不读 `DailyData.MoreRewardsInText()`）」—— 现在那个口返回 `Loc.T(...)`（en 仍是 `More Rewards In`），
  `:10335` 那条断言**照样绿**；但注释里的理由需要下一轮改成「手写字面量 = 防自证」。⚠️ 该文件不在我白名单，**没动**。
