## 二、OFF-47 第 1 步（NRE）—— 为什么**没有**直接改 `showInNavigationBar`

### 2·1 判据（现读反编译，全部可复核）

`NavigationPanelController.BuildEventButtons` 的过滤谓词
（`decomp_full/NavigationPanelController.__c___BuildEventButtons_b__13_0.c`）：

```
data = element + 0x18                     // ParentEvent.Data
if (data.location != null) {
    if (data.location.type != 0) return false;   // ← EventLocationType.Main = 0
    return data.showInNavigationBar;             // ← data + 0x60
}
```

- `ParentEventData.showInNavigationBar` 在 **+0x60**（`dump.cs:62661-62668`）——字段名/类型与任务书一致。
- `EventLocationType` = `Main 0 / None 1 / Parent 2`（`dump.cs:52733`）。
- 我们现有的 `ParentEvents.RawEvents[0]` 是 `{location:{type:1}, showInNavigationBar:false}`。

⇒ **只把 `showInNavigationBar` 改 true 不会有任何效果**：`location.type == 1 (None)` 在第一句就被 `return false` 掉了，
type-5 toggle 仍然不会被创建，NRE 照旧。必须**同时**把 `location.type` 改成 0（Main）。

### 2·2 真改了会怎样（量化，取自本地场景序列化）

`MainMenu Warpforge.unity` 的 `NavigationPanelController`（`MonoBehaviour_1955.json`）：
`navToggles` 5 条（type 0/2/1/3/4）、`buttonContainer` = RectTransform `1112`。

- `buttonContainer` 挂 **VerticalLayoutGroup**（`MonoBehaviour_1973.json`）：
  `m_Spacing = -16.35`、`m_ChildAlignment = 1 (UpperCenter)`、`m_Padding.top = -5`。
- 每个 nav 子件 RectTransform 都是 `sizeDelta = 164.31 × 169.68`（5 个子件 anchoredPosition 全是 0 ⇒ 靠 layout 排）。
- 容器高度 = 父(1080) − 148.34 = **931.66**：
  - 5 件：5×169.68 + 4×(−16.35) = **783.0**（居中 ⇒ 顶部留 74.3）
  - 6 件：6×169.68 + 5×(−16.35) = **936.3** ⇒ 溢出 4.7px，顶部偏移变 −2.3 ⇒ **整列图标上移 ≈76.6px**
- 新增的那颗按钮渲染什么（`Event Navigation Button.prefab`）：
  - `Selected highlight` 子件 `m_IsActive: 1`、`m_Color (0.67, 0.13, 0.09, 1)`、`sizeDelta 164.31×169.68`
    ⇒ **一整块红底**
  - `Image`（`buttonIcon`）的 sprite 由 `EventAssets[key=0]` 给；我们没给 ⇒ 透明
  - `Text Background` 在 `TryGetLabel(4)/(0)` 都失败时被 `SetActive(false)`（`OpenEventButton__SetButtonInfo.c`）
  ⇒ **一个没有图标、没有文字的纯红方块**，外加整列位移。
- 参考图（`桌面/warpforge参考图/主界面参考图.png`）主栏**只有 5 颗**（玩/收藏/商店/奖励/社交），没有第 6 颗。

⇒ 这条改动的**唯一收益**是让 `GetToggle(5)` 不再 null；代价是主菜单导航栏多一颗红色空按钮 + 整列上移。
按任务书「有风险就写进报告并给出替代方案」，**本波不落这条数据改动**。

### 2·3 替代方案（推荐，需调度台派给 mod 写手）

`BaseParentEventWindow.Open`（`decomp_full/BaseParentEventWindow__Open.c`）只有末尾这一段会抛：

```
lVar1 = NavigationPanelController.GetToggle(5);
if ((lVar1 != 0) && (*(long long *)(lVar1 + 0x20) != 0)) {
    if (*(char *)(*(long long *)(lVar1 + 0x20) + 0x120) != 0) return;  // 已经是选中态
    NavigationPanelController.SetToggle(5); return;
}
FUN_1803f47a0();   // ← 取不到 toggle 就抛
```

建议在 `WfOfflineProbe` 里对 `BaseParentEventWindow.Open` 加 **Prefix（返回 false 跳过原方法时先手工做等价动作）** 或
**Finalizer（吞掉异常）**：

```csharp
// 🔶 自己设计（非原版）：离线数据没有 showInNavigationBar 的 ParentEvent（原版由服务端下发），
//    type-5 navToggle 恒不存在 ⇒ 原版 Open 末尾必抛。这里只跳过「同步导航栏选中态」这一句。
static bool Prefix_BaseParentEventWindowOpen() {
    // 先照常执行等价于 GameWindowWithTabs.Open 的路径由原方法负责；
    // 这里仅当 GetToggle(Event) == null 时让原方法跑完并吞掉末尾异常。
    return true;
}
static Exception Finalizer_BaseParentEventWindowOpen(Exception __exception) {
    return __exception is NullReferenceException ? null : __exception;
}
```

（更稳的是 Prefix 里判断 `NavigationPanelController.Instance?.GetToggle(Event) == null` 后直接复制
`GameWindowWithTabs.Open(this)` 的行为，但那是重写，成本更高；Finalizer 是最小改动，且 Open 的
实质工作（`GameWindowWithTabs.Open` → `SetupTabs`/`ToFocus`）在抛之前**已经完成** —— 见
`BaseParentEventWindow__Open.c:11-13`：`GameWindowWithTabs__Open(param_1,0)` 是第一句。）

### 9·2 有没有「保留 OFF-49 Toggle 又不触发选军」的安全做法

| 候选改法 | 结论 |
|---|---|
| `showInMainMenu: false` | ❌ 无效 —— `GetActiveEvent` 不读这一格（它只影响主菜单模式卡）。本波已经是 false。 |

  「待有安全方案再做」。
