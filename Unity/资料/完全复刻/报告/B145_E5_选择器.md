## A-18 结论（`actingCard` 取谁 + 风险）

**原版判据**（`decomp_full/AbilityLogic__GetTargets.c`）：
- `:763-772`（`iVar6 = param_2 + 0x10`，`if (iVar6 == 0x50 || iVar6 == 0x28)`）——
  `0x28 = 40 attacker` 与 `0x50 = 80 actingCard` **同一支**：把 **`param_4`** `Add` 进池，然后
  `goto LAB_180818485`（= **直接 return 池**，**不过** `:1086-1095` 的 36 格循环）。
- 形参映射（由 `GetChoiceFullPool` 的调用点反证）：`param_3 = thisCard`（`:207` 读 `param_3 + 0x40` 当 `isPlayer`）、
  `param_4 = actingCard`、`param_5 = targetCard`；`BattleManager__GetChoiceFullPool.c:28-35` 传的是
  `GetTargets(this, choicesDefinition, actingCard, actingCard, targetCard, 0)` ⇒ **选牌那条路上 `thisCard == actingCard`**。

**所以 `actingCard` 在本引擎应该取谁**：
- 判据语义 = 「**触发/发起这一次结算的那张牌**」（原版 `AbilityLogic` 的 `actingCard` 形参）。
- 本引擎对应物 = **`UnitState actor` / `actingCandidate`**（`ActionPump.AbilityCriteriaAllowsAt` 的
  `actingCandidate`、`EffectResolver.ResolveTargets` 的 `subject`/`actor`、`CountEval.Matches` 的 `actor`）。
- `TargetCriteriaEval.Matches` 当前的 `thisCard` 形参 = **载体（carrier）**，**不是** `actingCard`；
  而 `Matches` 的签名里**根本没有 `actingCard`** ⇒ 现在无法表达这一档。

**现状与风险（⛔ 本轮不改）**：
- `ta=40`：现在拿 `candidate == thisCard` 比。**在选牌池那条路是对的**（`thisCard == actingCard`），
  在**普通触发**那条路是错的（载体 ≠ 触发者，例如「A 打出时，B 的响应能力」）。
- `ta=80`：现在**无条件 `return true`** ⇒ 引擎的候选池若来自通用池（`AddSide` 扫盘），
  **所有候选都过**；原版这里池只有**一张**（`actingCard`）。这是**方向偏宽**的真差异（多留候选）。
- **要真修，必须给 `Matches` 加第 9 个形参 `UnitState actingCard`** 并把它从 13 个调用点透传
  （`ActionPump.cs:805/916/1031/2295/2389/2402` · `CountEval.cs:836/1329` · `EffectResolver.cs:2431/3672/17919/21263/21559` ·
  `EnchantmentExecutor_B115.cs:1127` · `RuleCore.cs:11729/18050`）——**其中 6 个在我白名单外**
  ⇒ 只能由调度台另派。**补丁形状**：`case 40/80: if (acting == null) { gap="…没有 actingCard ⇒ 判不了"; return null; } return ReferenceEquals(candidate, acting);`
  （`null` 当「判不了」而不是 `true`，否则就是今天这个方向偏宽）。
