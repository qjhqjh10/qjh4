## 四 这套 schema 在真实域上暴露的问题（**试点的重点**）

按「会不会让 12 块并行跑出假绿」排序。

### 4.1 🔴🔴 最高：`判据出处` **只验前缀、不验文件存在** ⇒ 打错路径照样绿

机检 C5 的实做（`feature_index_check.py:243-246`）只做两件事：**整串里含不含** `cpp2il/` `decomp_full/` …
和**含不含** `CardPresentation/` `RuleEngine/Core` `MyGame/Assets`。**它从不打开那个文件。**

我这一块就**写错 5 条**（一条都没有被机检拦住，是我自己另写脚本逐个 `os.path.exists` 才发现的）：

| 我第一版写的 | 实际是 |
|---|---|
| `decomp_full/ContainerOfferEvent__OpenOfferContainer.c` | `decomp_full/Everguild.LiveOps.ContainerOfferEvent__OpenOfferContainer.c`（**命名空间前缀**） |
| `decomp_full/ShopConfig__GetDlcBundle.c` | `decomp_full/Everguild.LiveOps.Config.ShopConfig__GetDlcBundle.c` |
| `decomp_full/GeneralOfferPopupDrawerBase__DrawRewards.c` | **该文件不存在**（只有 `__Initialize.c` / `__ReleaseAssets.c`） |
| `cpp2il/…/Everguild.LiveOps/ShopOfferInventory.cs` | `cpp2il/…/ShopOfferInventory.cs`（**不在 LiveOps 子目录**） |
| `decomp_full/Everguild.LiveOps.ShopStore__TryPurchase.c` | **泛型类方法体没被导出**（只有闭包 `…__TryPurchase_b__0.c`）⇒ 改用 `cpp2il/…/ShopStore.cs` |

根因：**账里的 `判据出处` 列是不带路径的相对名**（`ContainerOfferEvent.cs:267`、`PriceDisplay.cs:9`），
每个块的代理必须自己推出「它在 `cpp2il/out_cpp2il_dev_ilspy/` 还是 `…/Everguild.LiveOps/` 还是 `decomp_full/Everguild.LiveOps.Xxx__`」——
**12 个块 = 12 次同样的猜**，而猜错**零成本通过**。

⇒ **建议（派 K1–K12 之前做）**：给 C5 加一句 `os.path.exists`，并把「账的相对名 → 完整路径」变成**一个公共映射函数**放进机检脚本，
代理直接调用（或让脚本 `--resolve-judge` 打印）。

### 4.2 🔴 高：**多认领只告警、退出码 0** ⇒ 分母污染的闸是软的

实测（把 `ShopTab.CheckTimer` 同时挂给 `FP-SHOP-001` 与 `FP-SHOP-005`，并把三列同步以免先被 C2 拦住）：

```
功能点 13 条 | … | 多认领 1
失败 0 | 告警 1
  ⚠ 一行被 2 个功能点同时认领：商店.tsv:298 ShopTab.CheckTimer(out DateTime timer)
rc = 0
```

设计 §1.3 把「一行一个 primary owner」写成**硬规矩**（分母要干净），但机检把它归到 C6「只告警」。
⇒ 任何「`rc==0` 就算过」的合并脚本会**接受一个脏分母**。
**建议**：加 `--strict`（把 `多认领 > 0` 判失败），合并脚本一律带 `--strict`。

### 4.3 🔴 高：机检**没有「按域」口径** ⇒ 每个 part 都打「未认领 9,269」

本块覆盖 351/351，但脚本打的是全局：

```
功能点 13 条 | 账行 9620 | 已被认领 351 | 未认领 9269 | 多认领 0
⚠ 还有 9269 条账行没被任何功能点认领（索引尚不完整，不是「全绿」）
```

设计 §3.4 说「合并后的**主表**必须让 `未认领 = 0`」—— 这是对的；但**每份 part 单独过闸时**
这个数**恒为 9,269 减去本块**，毫无信息量，而且**会训练人不看它**（狼来了）。
⇒ **建议**：加 `--domain 商店`（只统计该域的账行），part 阶段看域内未认领，
只有在**合并后**才看全局的 0。

### 4.4 中：`我们的落点` **没有「合法地没落点」这种值**

- 写 `—` ⇒ 机检判「没有 `文件:行` 形状」⇒ **红**；
- 写空串 ⇒ **绿**，但与「忘了填」**无法区分**。

本块 `FP-SHOP-008`（36 行全 C、全无落点）只能写空串，并在备注里解释。
⇒ **建议**：明确一个哨兵值（如 `无` / `N/A`），让机检放行 + 统计「有多少功能点没有落点」——
这个数本身是有用的指标（本域 1 个，占 7.7%）。

### 4.5 中：`等级` 混淆「复刻」与「`🔶 自己设计`」⇒ 与铁律 18 打架

本域至少两处：`ShopStore.GetBaseData`（A，差异列写「值是我们挑的」）、`ShopData.Offers` 的价格与拥有数。
**账判 A、索引跟着 A**，于是「A」既包含「照原版复刻」也包含「我们自己编的数值」。
⇒ 建议在功能点级加一列（或 `等级` 加后缀）`自查`，标出「本功能点含 `🔶 自己设计` 的构成行」，
否则第二层的 `真复刻率` 会**系统性偏高**（本项目「自己编的数值」不少）。

### 4.6 中：**B 与 C 的界线没有口径** ⇒ 定级不可复现

`FP-SHOP-003` 的 3 条 B、`FP-SHOP-001` 的 2 条 B、`FP-SHOP-002` 的 5 条 B，账面理由**全是**
「无实现行可指」/「等价物在但没有同名方法」—— 行为其实**都在**。
但同一本账里，`CurrencyExtensions` 那 4 行因为「整层没有」判 C。
两种都是「没有独立方法」，一个 B 一个 C ⇒ **换个代理可能判出不同等级**（而 `等级` 是最差档，一动就整条变）。
⇒ 建议在 schema 里把这两类**显式命名**：`B = 行为在、落点不可逐方法指认` · `C = 行为缺`，
并在设计文档里给 3 个正例 + 3 个反例。

### 4.7 小：`原版构成` 的 token 粒度会**被迫变长**，而且**跨 FP 牵连**

`FP-SHOP-005`（倒计时与到期）的 10 行**散在 6 个类**里。为了让「倒计时」成为一件完整的事，
我不得不：
1. 逐方法写 10 个 token（不能用 `类.*`）；
2. 把 `ShopTab` 的 2 个方法从 `FP-SHOP-001` 摘出来（`FP-SHOP-001` 因此也只能部分逐方法列）。

⇒ 改一个类的方法归属要**同时改两个 FP 的 token 列表**，而 `构成条数/状态分布/等级` 会跟着变
（我的生成器是脚本算的，所以**改完重跑即可**；若手写就必然对不上）。
**这条正好证明设计 §1.2(b)「三列必须由账重算」是对的** —— 但也说明**没有一个「token 编辑器」**时，
跨 FP 的重构很痛。⇒ 建议：`原版构成` 允许「补集写法」（`类.* 减去 x,y`），或提供按行号选行的工具。

### 4.8 小：P3 域**必然**产生「玩家做不到的一件事」的大桶，schema 没给它的写法

`FP-SHOP-013`（56 行）里混着编译器生成的匿名类型 3 行、构建工具 `AssetBundlesEditorObject` 2 行、
`Shops`/`ShopOfferEvent` 的服务端数据层、`BoostManager`。
`功能点名` 的约束是「**玩家能做的一件事**，不许是类名」—— 这类桶**既不是玩家动作，也不能写类名**。
本块只能写成「商店的服务端报价与存档数据层（… → 本地静态表）」，并靠 `边角` + 备注兜住。
⇒ 12 块里 K11（其他/基础设施 823 行，**预期大量 D**）与 K12（未分类 1183 行）会遇到**同样且更大**的问题。
**建议**：允许 `功能点名` 用「（载体）…」前缀，并规定这类 FP 一律 `边角` + 在 `优先级` 用 `P3`；
或者干脆给 P3 域开一张**并行的简化表**（只要「账行 → 原版判据 → 为什么不做」三列，不要落点/验收口）。

### 4.9 运营风险：**账在被我读的同时被别人改**（实测发生）

我这一块跑的过程中，`账/泛型与启动链_补读.tsv` 被**另一个写手改了 5 行**（`git diff --numstat` = `5/5`，
改动落在 `:47-51` 与 `:775-790`，**不是我引用的 `:34-42`**，且是原地替换、行号没有位移 ⇒ 本块结论不受影响）。

但这说明：**12 块并行时，账会一直动**，而 `构成条数 / 状态分布 / 等级` 是**按账现算**的 ——
账一动，已经交回来的 part 就可能**不再是重算值**（C2 会红）。
⇒ **合并前必须对每份 part 重跑一次机检**（设计 §3.4 已写「合并前每份 part 都要单独过 §3.4 的机检」，
这里补一条**实测依据**：这不是假想风险，它在我这一块就发生了）。

  （`FP-SHOP-011` IAP 50 行 · `FP-SHOP-013` 服务端数据层 56 行 = **106 行 / 30.2%**），
  它们是「原版有、本地不做」的正经构成（账已判 D 并写了理由），不是没地方放。
- 一个「**没有独立功能点**」的边角：`Shops.CheckNotification` + `ShopContainerInventory.CheckNotification`（红点，2 行）
  —— 为了把它们单独立成「商店红点」我得再拆 2 个类的 token（像 `FP-SHOP-005` 那样），
  **我判断不值**，就留在各自的类族里。⇒ 这是**粒度判断**，不是漏账；这也说明
  「2 行的小行为要不要独立成 FP」需要一条判据（建议：≥3 行或 ≥2 个类才独立成 FP）。

### ② schema 哪里不够用

见 §四，按影响排序：**判据路径不验存在（4.1）→ 多认领不红（4.2）→ 没有按域口径（4.3）
→ 落点无「空」哨兵（4.4）→ 自设计不标记（4.5）→ B/C 界线（4.6）→ token 粒度过长（4.7）→ P3 桶无写法（4.8）
→ 账并行被改（4.9，运营风险不是 schema 缺陷）**。

**列不够用的地方具体是两处**（其余列够）：
1. **缺一列「本 FP 是否含 `🔶 自己设计`」**（4.5）—— 现在只能塞进 `备注`，机器读不到。
2. **`验收口` 缺「类型」位**（4.3 的延伸）—— 一条断言、一条 `cmd:`、一条「今天没有验收」混在一格。
   本块的 `FP-SHOP-008` 只能把「第 4 键是关着的母版」当成验收口，**它挡不住活动页签被误加**。

**粒度不对的地方**：`等级` 取最差档**是对的**（本域实测 80.3%→30.8% 的差就是它挣出来的），
但它**不区分「C 是因为暂停」还是「C 是因为真缺」**。本域 7 条 C 里 **4 条带 `?`** 就是这个问题。
`?` 只表达「有存疑行」，而存疑行的定义是「账行本身可疑」，**不是**「这条 C 可以接受」。
⇒ 建议 `存疑行` 之外再加一个**关闭不了**的统计位，或允许 `等级` 后带 `~`（= C 来自暂停/裁定，等外部条件）。
