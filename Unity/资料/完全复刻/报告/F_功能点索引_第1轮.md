## ② 判据

### 2.1 归并方法（三层，规则全部写死在 `_tmp_view/wfres/gen_feature_index.py`）

1. **方法名正则**（只对巨型类）：`BattleManager` 578 / `CardScript` 361 / `PlayerDataManager` 217 个方法——
   按类归并会把「出牌/攻击/死亡/回合」揉成一坨。**规则顺序 = 优先级**（`ResolveTrigger` 归「触发链」不归「攻击」）。
2. **原版类名正则**：其余域按类归并。
3. **兜底**：每域一条 `.*`，**保证不丢行**；命中的类名×行数逐条列在索引 §3。

**三个技术处理**：① 泛型类名先归一化（`CollectionItem<T>` → `CollectionItem`，否则 `$` 锚点漏 75 行）；
② 编译器生成类型（`<>f__AnonymousType…`，267 行全 D）单独一档；③ 状态 = 分布 + 最高档，
并明写「**最高档 A 只代表至少一个方法已对齐**」。

每个的 `备注` 列现在是「🔴 用户已暂停 —— **恢复起点**：…」。举两条：

- **活动线 · 事件框架（LiveOps）** → 先建 `LiveOpsHandler` + `LiveOpsEvent<TSave>` 两个基类
  （原版签名里带 `blockedEvents` / `shared`），再接 `LiveOpsManager` 的注册表 —— **所有活动的底座**。

### 2.4 主链/边角：补了一版**由账推导**的分类（索引 §4）

- **我判版**：按方案 §4.2 的 P0/P1 定义人工判断。

🔴 **先报一个总账级事实**：**9,614 行里 `等级 = P0` 的行是 0 条**（C 行只有 P1×369 与 P2×1,202）

## ⑤ 没查清 / 边界

1. **不是功能点全集**：从账里长出来的，账没列的方法不会出现。
2. **粒度不均**：`战斗逻辑驱动` 1,535 行切成 22 个功能点，`本地化` 10 行也是 1 个 —— 账的规模差异。
3. **2,609 行（862 类）仍落兜底**：粗粒度不是丢行；`未分类/其他` 那 1,184 行是**有意不切**。
4. **「最高档 A」会骗人**：只表示至少一个方法已对齐。
5. **主链/边角两版都没定论**：我判版没有账内一手判据；账推版因为 **P0 = 0** 判不出主链。
6. **暂停线 10 个功能点的「恢复起点」**是按既有结论写的**方向**，不是详细施工图。

## ⑥ 顺手发现

1. 🔴 **`存档与玩家数据` 那 217 条 C：我上轮说「多半该判 D」—— 已按调度台裁定改回 C**。
   理由（调度台给的一手判据）：`PlayerDataManager` 的行为是「**中央存档 + 每活动一份 `TSave`**」，
   我们换成了 **7 份各自为政的本地存档** —— 那是**替代物但不是等价物**；
   证据就是我们自己的结论「**恢复活动线的正确起点 = 存档归并 → `LiveOpsHandler`**」。
   ⇒ **它是真缺口（C），不是「不适用」（D）**。⛔ 记一条通用口径：**「我们有别的做法」不等于 D**，
   D 只给「原版没有 / 离线不可用 / 死代码」。
2. **`战斗场景加载与开场` 的 10 条 C 全部来自 `TipPrebattle`**（同组 `EverguildSceneManager` /
   `LoginScreenManager` / `TestLoginManager` / `ShowStatusWhenConnecting` 一条 C 都没有，全是 D）。
3. **`UI 特效` 33 条 C**（`UIBorderGlow` 13 · `NestedFadeGroupBase` 11 · `UITransformTweenController` 9）——
   看起来是真缺，建议单独派一条。
4. **账里 `等级 = P0` 一条都没有** —— 这条比任何单个功能点都重要：它意味着「主链问题」这个维度
   **在账上还没有判据落地**。
5. **同一份账被多个域共用**（`泛型与启动链_补读.tsv` 里就有 8 个域）—— 归并**按行的 `域` 列分**，不是按文件名。
