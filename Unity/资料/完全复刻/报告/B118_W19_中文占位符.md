# B118_W19 · `descZh` 里的 `((Key,arg))` 占位符

> 结论先说：**这些记号不是缺陷、也不是我们漏展开的一环 —— 它们是原版数据本来的样子，
> 渲染层（`CardIcons.RewriteMarks`）会按原版四支展开。全池实测「渲染后残留 = 0 张」。**
> ⇒ **数据零改动**（改数据会偏离原版，并弄红三条已钉死的自检）；改交一只**只读闸**，让这件事以后可复跑。

## 1 · 根因（占位符是哪一步漏展开，带 文件:行号）

**没有漏展开的步骤。** 链路是「数据存模板 → 渲染时展开」，原版就是这样：

1. `工具/gen_cards_engine.py:6508-6535` —— `descZh` 三个写手（低→高）：
   ① `数据/卡牌翻译/zh_cards.json`（我们自译，兜底）→ ② **官方表 `Card_Description/*` 的 zh 列**（本层，`:6526-6535`
   `entry["descZh"] = _ozd`，**逐字节照抄**）→ ③ `cardface_fixes.json` 的人工值（PnP 逐张核过）。
2. 官方表 `Unity/数据/游戏数据/官方本地化_en+zh-CN.json` 的 `Card_Description/ASH46` zh 列**本身就是**
   `((Deal_x_damage_to_a_random_enemy,3))。每有一个友方载具，重复此效果` ⇒ 我们抄过来当然带记号。
3. 渲染层把它展开：`CardPresentation/Core/CardIcons.cs:326`（有记号就整串交给 `RewriteMarks`）→ `:647-655`（四支按序）→
   `:779-789 RewriteMarkModular`：`((Key,a,b))` → 词条 `Modular_Description/<Key>`，`{0}`/`{1}` 代参。
   **判据 = 原版** `d:/2/tools/decomp_full/SupportMethods__ModifyLocalization.c:75-186`。
4. 卡面正文其实**不读** `DescZh`：`BattleDriver.FaceTextFull`（`:28404`）先取
   `Loc.OfficialCurrent(Card_Description/<key>)`（`:28430-28438`），取不到才回 `DescZh`；
   最终在 `:28463` 过 `CardIcons.Rewrite`。⇒ 中英文两条路都必然经过记号展开。

**为什么英文 `desc` 没有记号**：`desc` 来自卡 SO / OCR 那条链（已是展开后的成品文本），不是官方 `Card_Description` 的 en 列（en 列同样带记号）⇒ 「中英不对称」是**两条数据源不同**，不是缺陷。

**数据指纹**：233 张里 **225 张**与官方 zh 列**逐字节相同**；另 8 张是人工 PnP 修正或新版官方
（`GOF61`/`GOF26` 只差一个全角冒号/尾空格，`SOR30`/`SOR4`/`SOR39`/`SOR31` 是人工改写）。

## 3 · 改了什么

**数据零改动。** 理由三条（都在 §1/§4 有实据）：
① 记号是**原版数据原样**，展开它就是偏离原版（铁律 11/18·0：默认复刻原版）；
② 渲染后残留 **0**，玩家看不到占位符 ⇒ 没有要修的现象；
③ 在生成期展开会弄红三条已钉死的自检并被下一次重生成**逐个修正回去**：
   - `Editor/BattleScene.cs:25730` `Check(h == 0xE59A576Eu)` —— `desc`/`descZh` 的 FNV-1a 指纹，**一动 233 张必红**；
   - `Editor/BattleScene.cs:25518` `Check(faceMarked > 100)` —— 前提断言「全池 `descZh` 带官方记号的卡 >100 张」；
   - `CardIcons.cs:326` 的世代分流：只有 `((…))`、无 `[[…]]`/`<sprite` 的卡（如 `ASH46`）**会被踢出自造图标层闸**、
     改走按卡 `card_icon_plan`，渲染结果随之改变（且我无权跑 Unity 验证）。

**新增（唯一落盘）= `工具/check_desc_zh_marks.py`**（只读闸，零写盘；不带参数只打印用法 rc=2）：
按 `RewriteMarks` 的 ①②③ 模拟一遍，报「渲染后还剩几处原始记号 + 解不开的键」。
词条源 = 运行时那两张表（`Resources/official_names.json` / `Fonts/Warpforge Trait TextSprites.asset`）。
复跑：`python -I -X utf8 d:/4/Unity/工具/check_desc_zh_marks.py --check`

## 5 · 仍展开不了的（逐条）

**0 条。** 三类记号逐类核过：
- `((Key,a,b))` 76 键 / 263 处 —— 官方表 + 运行时表全有，参数 0 处缺失；
- `$$ID$$` —— 233 张里 **47 处 / 37 个 id**（本批全池共 139 处），37 个 id 在 `Card_Name/*` **全命中、缺 0**；
- `[[枚举名]]` —— 全池 60 个 token 全部有 `Atlas_trait_icon_<名>` 图（73 张图表）⇒ 按原版走「图+词」；
  其中 8 个名字**没有 `Card_Trait/*` 中文词条**（原版兜底只印枚举名）—— 那是**另一笔已知账**（`RewriteMarkTraits` 的 doc 记着），本批不碰。

**如果调度台仍要求在生成期展开**（不建议，代价见 §3）：要同时改 `Editor/BattleScene.cs` 的指纹 `0xE59A576E`
与 `faceMarked > 100` 前提，并逐卡核 `card_icon_plan` 分流（要跑 Unity，超本批权限）。
产物可直接复用 `check_desc_zh_marks.py` 的 `expand()`（把 `official_names.json` 换成官方表即可，实测同样 0 残留）。

## 6 · 顺手发现

1. `gen_cards_engine.py:6526` 的 `_dkey` 直查用的是**卡 id**，而 `descZh` 的官方键空间里有一批
   **32 位 GUID 键**（如 `09bcb1b3b8794c4429d82d4b2e68fa1f`）—— 这些卡就是靠 id 直查命中的
   （官方 `Card_Description/<GUID>` 确实存在），不是漏写。⛔ 别按「卡 id 不是 GUID」判成坏键。
2. `cardface_fixes.json` 现有 **284** 条人工 `descZh`（生成器注释里写 279 = 2026-10-18 的读数）⇒ 该数字已过期，别引用 279。
3. 新脚本可当「`desc`/`descZh` 换源」的回归闸：新源若引入本地没有的 `Modular_Description` 键，`--check` 立刻 rc=1。
