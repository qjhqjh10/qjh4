## 三、走了哪条修法、为什么

| 候选 | 结论 |
|---|---|
| **(a) 扩 `BOOSTER_GROUPS[1]` 的根/材质后重跑 `--prefabs`** | ❌ **做不动**：`repack_tree` 的 `extra_materials` 只在本组源包里按名字找，那 16 个材质**不在**本组源包（§二·1）。加进 `roots` 也一样（`[P1] 这个包里没有 GameObject`）。 |
| **(a') 本件采用的**：把外部对象当**独立内层 CAB 并进同一个产物** + 改写引用 | ✅ **采纳**。对象**逐字搬原件**（`repack_tree` 打出的小包），不造任何材质/贴图；引用改成包内兄弟 CAB ⇒ 产物**自包含**，不依赖别的包在不在场。 |
| **(b) 运行时重绑**（`ArenaOriginalShaderRebind` 那套） | ⏭ 不需要了：材质与 shader 都进包之后引用自己就通。**而且 (b) 要改 `BoosterPackAssets.cs`（本批白名单外）**，能不做就不做。 |

**为什么 (a') 没退化成品红**：材质的**属性值**（`m_Floats` / `m_Colors` / `m_TexEnvs`）是原版对象**原样**搬过来的，
`repack_tree` 只改 `m_StreamData.path`/offset（搬流时）。贴图数据实测**逐字节相同**（§四）。

### 3.1 顶层结构的变化（**这是我们对「分包方式」的选择，不是原版结构**）

原版把它们分成 5 个 Addressables 包；我们把它们并进**同一个产物**的 7 份内层 CAB：

```
CAB-wfboostersextra      ← 17 棵 prefab + 24 个材质 + 16 个 shader（原有主 CAB，内容不变）
CAB-boostermatsdup       ← 11 个材质 + 9 张贴图          (from duplicateassetisolation)
CAB-boostermatsbs        ←  3 个材质 + 2 张贴图          (from battlesharedresources)
CAB-boostermatsmenu      ←  1 个材质 + 1 张贴图          (from menusharedresources)
CAB-boostermatsfont      ←  1 个材质 + 1 张贴图 + 1 shader(from fonts)
CAB-boosterfxshaders     ←  6 个 Shader                  (from shaders_assets_all)
CAB-boosterfxbuiltin     ←  1 个 Shader                  (from unitybuiltinassets)
+ 5 份 .resS
```

⚠️ 内层 CAB 名**必须换**（`CAB-boostermats*` / `CAB-boosterfx*`）：沿用源包名会与运行时已加载的
`wf_shaders.bundle`（内层 `CAB-805d8e…`）/ `wf_builtin.bundle`（内层 `CAB-5ffb81…`）/ `wf_tmp_shaders.bundle`
（内层 `CAB-daee69…`）/ `wf_arena_shaders.bundle`（内层 `CAB-68cc81…`）**撞名** ⇒
Unity 判「同一个包」**整包拒收**（`_write_bundle` 那段实测记着这个坑）。

## 七、还差什么 / 顺手发现（⛔ 不许静默）

### 7.1 本件还差

1. 🔴 **Unity 侧那一跳**：多 CAB 产物能不能 `LoadFromFile`、材质能不能渲（判据 = `B97W32Assert.Run`）。
   旁证很足（同工程的 `wf_arena_prefabs_battlearena3.bundle` 就是 2 份 CAB 的产物），但**没验过 7 份的**。
2. ⚠️ **`--prefabs` 现在会顺带产出这一份** —— 但它同时重写 `wf_prefabs_extra` / `wf_menus_extra` /
   `wf_battleshared_extra` / `wf_mainmenu_extra`。本批白名单只允许动卡包那一份，所以我**没跑 `--prefabs`**；
   哪天调度台要跑，先确认那 4 个产物重跑后**内容不变**（本件实测单项重跑是逐对象相同的）。
3. ⏭ `B97_W23` §4.4 那两条（3D 物件要不要真摆 / OBJ 与 prefab 二选一）原样有效，本件没动。

### 7.2 🔴 顺手发现：**同一个缺陷在另外 4 个 `repack_tree` 产物里都存在**（同样的量法，只读实测）

| 产物 | 材质槽悬空 | 材质→shader 悬空 |
|---|---|---|
| `wf_menus_extra.bundle` | **29**（7 个不同材质） | **6** |
| `wf_prefabs_extra.bundle` | **31**（9 个） | **7** |
| `wf_battleshared_extra.bundle` | **13**（5 个） | 0 |
| `wf_mainmenu_extra.bundle` | **58**（9 个） | **3** |
| （已修的）`wf_boosters_extra.bundle` | 0 | 0 |

- **根因是通用的**：`repack_tree()` 只跟 `m_FileID == 0`（同 CAB）的引用走，`m_FileID != 0` 的
  **一律记成「真外部引用」就放过** ⇒ 凡是 prefab 引用「别的 Addressables 包里的材质」的产物都会中这个病。
- **修法现成**：本件的 `merge_imports_into_bundle()` 就是通用口（给一个 `imports` 表即可），
  但每个产物要**各自的 imports 清单**（哪几个材质/在哪几个源包）+ **白名单**。
- ⚠️ 其中 `wf_menus_extra`（卡包打开那扇窗 + 4 个 `Boosterpack Open Card Rarity *` 粒子）**直接影响开包演出**，
  优先级最高；`wf_prefabs_extra`（阵亡爆散体等）次之。
- 建议：立账 → 下一波按「产物」切块，一个产物一个代理（文件互不相交）。

### 7.3 另一条（供以后判断，不是缺陷）

`BoosterPackAssets` 那条「经 prefab 传递取材质」的路**没有变**，但**现在包里多了 5 份 CAB**：
`LoadAsset<Material>(名字)` 仍然取不到这 16 个（它们不在容器里 —— 这是**有意**的，见 §四 第 7 条）。
将来若要做「按名字重绑」，要么把它们登记进容器（会动 W23 那条钉子），要么从 prefab 树上取（现在就能取到，且 shader 已非空）。
