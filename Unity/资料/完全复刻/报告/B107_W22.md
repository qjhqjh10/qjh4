### 4.1 那 2 行：裸重生成的变化，以及最终为什么是 0 行

**裸重生成**（只修 stride、不加 tie-break）会动 2 行的 **2 个列**：

| 名字 | PathID | 旧 A 件 / `A路字节相同` | 裸重生成的 A 件 | 裸重生成的 `A路字节相同` |
| --- | --- | --- | --- | --- |
| `Cone.003` | `-5582013513765483648` | `Cone.003__a76e0f14.asset` / `bytes_equal` | `Cone.002__a76e0f14.asset` | **`bytes_diff(107360/107360)`** |
| `Cone.004` | `-5181414759189312640` | `Cone.004__a9e8be1b.asset` / `bytes_equal` | `Cone.001__a9e8be1b.asset` | **`bytes_diff(107360/107360)`** |

- 原因：这两个 PID 的原版网格是**多 stream**。旧口径把原版坐标解错时，只有「整块字节与原件相同」那份
  `.asset` 的解错结果也完全一样（因为 blob 逐字节相同）⇒ 旧实现凑巧选对了。修好 stride 后**两份重复几何的
  位置都 exact / dev 0**，而 `best_project_match` 只比 `(bad, dev)` ⇒ 平手，靠目录枚举顺序选中了**非字节相同**那份。
- ⇒ **这 2 处裸重生成是「降级」**（几何仍对，但丢掉了更强的「逐字节相同」证据）。因此按 §八 加了
  **内容型 tie-break**（`orig_raw` 存在时，同分优先 `_typelessdata` 与原件逐字节相同者），
  **最终重生成 = 与旧表逐字节相同（0 行变化）**。

## 五、顺手发现（不在本单范围，调度台分流）

1. **🔴 同款 stride bug 曾在 `工具/gen_arena_vertexcolors.py`（已在 §八 追加轮次修掉）**
   - 原 `:209` 与 `:609` 两处都写 `max(c['offset'] + item_size(...) for c in ch if _dim(c))`（取所有 stream 的 max）。
   - 现读：该工具扫的 14 个 bundle 里 **165 个流式网格全是单 stream**；多 stream 的 4 个都在**非流式**网格上
     （`Spore_Large` / `Spore_Large1` / `Chain11` / `Firepits.002`，且**都没有顶点色** `ch3.dim=0`）
     ⇒ 今天对产物**零影响**（`--check` rc=0 已证），修它属于「堵将来的静默错」。
2. **`资源/R2_重建网格/` 的 X 约定是混的**（现读 26 份全扫）：
   - **22 份 = 原版原样**（即 `流式=0` 的那 22 行：`Cone.*` / `Cylinder` / `Background Sky` / `RockDebris_Low` /
     `IceShard02` / `CandleFlame_*` / `Sphere` / `Spirt Stone`(1 份) 等，`same` 偏差 ≤ 5e-7）；
   - **4 份 = X 取反**（`流式=1` 那 4 行：`Spirt Stone` + `Floor ×3`）。
   - 而 `cmp_mesh_vertices.py` 的 `analyze()` 对 `find_export()` 的结果**一律 `negate_x=True`** ——
     当前恰好只被那 4 份（negX）命中，所以输出是对的；但**这是一颗定时炸弹**：
     哪天 flow=0 的重建件进了 `find_export`，会被当成 negX 比、然后误报「不一致」。
   - 本单**没改**这条（改它会动既有 169 条的口径判定，超出本单范围）；建议调度台决定「统一重建件约定」或「按文件核约定」。
3. **`best_project_match` 的 tie-break 依赖候选枚举顺序**（glob 的目录序，Windows 上不是排序序）：
   同几何重复件（本条命中的就是 `__a76e0f14` / `__a9e8be1b` 这种同后缀双份）会「谁先扫到选谁」。
   **已收口（§八）**：不再用 `rel(path)` 排序（那会选到**非字节相同**那份 = 倒退），改成
   **同分优先「`_typelessdata` 与原件逐字节相同」的 `.asset`**（内容判据，与 R3 的 `Abytes` 证据一致）；
   没有 `orig_raw` 时行为与以前完全一致（169 条逐字节不变）。
4. **`_tmp_view/b107_r3/r2_coverage.json` 的 `export_v` 列对 8 条多 stream 件是旧口径**（用 buggy `orig` 算的）；
   它**不被** `build_r2_tsv.py` 使用（那边用自己的 `correct_positions`），所以没污染已出的表 —— 但别拿它当判据。

### 8.3 tie-break 的实现（以及为什么**不**按 `rel(path)`）

调度台建议「同几何重复件按 `rel(path)` 取最小」。实测**不能这么做**：那 2 个 PID 的字母序靠前那份
（`Cone.002__a76e0f14` / `Cone.001__a9e8be1b`）正是**非字节相同**的重复件 —— 按路径排会稳定地选到错的那份。

改用的判据是**内容**：

- `best_project_match(orig, idx, orig_raw=None)` 新增可选参数 `orig_raw`（原网格 `m_VertexData.m_DataSize` 的原始字节）；
- 排序键从 `(bad, dev)` 扩成 **`(bad, dev, byteeq)`**，其中 `byteeq = 0` 当且仅当该 `.asset` 的
  `_typelessdata` 与 `orig_raw` **逐字节相同**；同分时才起作用。
- **兼容性**：`orig_raw=None` 时 `byteeq` 恒 0 ⇒ 与旧行为**完全一致**。流式网格 `m_DataSize` 为空 ⇒ 169 条全部走旧行为（已逐字节验证）。
- 调用方更新：`analyze()` 传 `_d['m_VertexData']['m_DataSize']`；临时脚本 `r2_coverage.py` 传 `tt['m_VertexData']['m_DataSize']`。
