## 二、选的方案与理由

### 2.1 三个注入点（推荐做法照做）

`RuleEngine/Data/DeckLibrary.cs` **类尾**新增（本类**不认识** `SaveCenter` / `SaveKeys` / `StoreOn`）：

```csharp
public static Func<string, string> ReadLegacyText;      // 旧档完整路径 ⇒ 原文（null = 两边都没有）
public static DeckLegacySaver SaveLegacyText;           // (旧档路径, payloadJson, out error) ⇒ 是否真写成
public static Func<bool> CentralSaveExists;             // 中央档在不在（注册方负责先判 StoreOn）
public delegate bool DeckLegacySaver(string legacyFullPath, string payloadJson, out string error);
```

外加两个**类尾私有**的一跳函数（把分支收在类尾，让中段的两个调用点保持**单物理行**）：

```csharp
static List<PlayerDeck> ReadDecksThroughHooks(out DeckStore.LoadNote note, out string detail, out int current)
bool WriteDecksThroughHooks(out string error)   // 实例方法（要 `_decks`/`_current`）
```

注册点在 **Shell 侧** = `CardPresentation/Deck/DeckRuntime.cs` **文件尾**（新增 `partial` 段）：

```csharp
[UnityEngine.RuntimeInitializeOnLoadMethod(UnityEngine.RuntimeInitializeLoadType.BeforeSceneLoad)]
static void RegisterDeckLibrarySaveHooks()
{
    DeckLibrary.ReadLegacyText     = path => SaveCenter.ReadThroughLegacy(SaveKeys.PlayerDecks, path);
    DeckLibrary.SaveLegacyText     = (string path, string json, out string err) => SaveCenter.SaveThroughLegacy(SaveKeys.PlayerDecks, path, json, out err);
    DeckLibrary.CentralSaveExists  = () => SaveCenter.StoreOn && SaveCenter.Exists(SaveKeys.PlayerDecks);
}
```

**为什么用 `RuntimeInitializeOnLoadMethod` 而不是 `Awake()`**（简报写的是「`DeckRuntime` 的初始化处」）：

1. `Awake()` 只有**卡组编辑窗存在**时才跑，而 `DeckLibrary.Load()` 的调用方还有
   `BattleDriver.PickSavedDeck`（`Battle/BattleDriver.cs:4835`）/ `CollectionData` 等，**都在开窗之前**
   ⇒ 挂 `Awake` 会漏一大片（那些路径会退回纯文件路，双写就白做了）。
2. **批处理自检是 edit mode**（`-batchmode -executeMethod` 不进 play）⇒ 这个钩子**不会**触发 ⇒
   自检仍然走 `DeckStore` 那条纯文件路 = **W6 之前的行为，零变化**。
   这正好也是铁律要的「钩子为空时行为不变」在自检侧的落地。
3. 真跑起来（player / 编辑器 play）时才注册 ⇒ 双写与「先中央档、再旧档」按 W6 的设计**真的生效**
   （W6 那版虽然写了，但读侧只在编辑窗那条路上生效）。

### 2.2 `existed` 修正 —— **选「钩子自己按 `StoreOn` 收口」（简报里的第二种）**

- 注册方把 `CentralSaveExists` 注册成 **`() => SaveCenter.StoreOn && SaveCenter.Exists(key)`**；
  `DeckLibrary` 这一侧**只做 OR**，**不引入「落盘门」概念**。
- 另加一道保险：**`ReadLegacyText == null` 时根本不问 `CentralSaveExists`**
  （两个钩子必须同进同退，否则「问了一个、读的却是另一条路」又会造出同样的自相矛盾）。
- **为什么选它**：如果把 `StoreOn` 判在 `DeckLibrary` 里，就得让 `RuleEngine` 认识
  「这一趟允不允许写盘」——那是 `CardPresentation` 的门（`SaveCenter.StoreOn` / `DailyData.StoreOn`），
  搬进来等于**换一个方向的反向依赖**（概念上的）。让注册方收口 = 判据留在**它自己那个域**里。

**假阳性的根**（W6）：`existed` 无条件 `|| SaveCenter.Exists(key)` —— 而 `SaveCenter.Exists` 走
`PathOf/RootDir`（`SaveCenter.cs:80-101, 252-257`）**不看 `StoreOn`**；`ReadThroughLegacy` 却
**在 `StoreOn == false` 时根本不看中央档**（`SaveCenter.cs:1165-1175`）⇒ 玩家真有中央档时，
`DeckStore.OverridePath` 指临时文件的批处理里 `existed` 恒 true ⇒ `ClassifyLoad("no save file", true)`
= `Failed`（应为 `NoSaveFile`）。W7 之后**批处理里根本不会去问中央档**，这一路与 `Read` 侧天然一致。

## 四、「钩子为空 ⇒ 与 W6 之前逐字等价」的自证

拿 `git diff` 里**被 W6 改掉的那两行原文**（= W6 之前那一版）逐句对照：

**读（W6 之前 `DeckLibrary.cs:123-124`）**

```csharp
bool existed = System.IO.File.Exists(DeckStore.Path);
var list = DeckStore.LoadAll(out note, out detail, out current);
```

**W7 之后（钩子全为 null）**

- `:125` ⇒ `System.IO.File.Exists(DeckStore.Path) || (ReadLegacyText != null && …)`
  —— `ReadLegacyText == null` ⇒ `&&` **短路**，整个右侧不求值 ⇒ 结果**等于** `File.Exists(...)`，**连求值次数都一样**（`CentralSaveExists` 一次都不会被调）。
- `:126` ⇒ `ReadDecksThroughHooks(...)`；它体内 `if (ReadLegacyText != null)` 为假 ⇒
  `return DeckStore.LoadAll(out note, out detail, out current);` —— **与上面那行原句逐字同一调用**
  （同一个方法、同一组 `out` 实参、同一个求值顺序）。

**写（W6 之前 `DeckLibrary.cs:359`）**

```csharp
bool ok = DeckStore.SaveAll(_decks, _current, out err);
```

**W7 之后（钩子为 null）**：`WriteDecksThroughHooks(out err)` 体内 `if (SaveLegacyText != null)` 为假 ⇒
`return DeckStore.SaveAll(_decks, _current, out error);` —— **逐字同一调用**。
（⚠️ `DeckStore.Serialize` 只在**有钩子**时才调 ⇒ 空钩子这一支连「多序列化一遍」都没有。）
`LastError = ok ? null : err; return ok;` 两行**一个字没动**。

**结论**：空钩子的两条路 —— `File.Exists` / `DeckStore.LoadAll` / `DeckStore.SaveAll` ——
就是 W6 之前那三条语句本身，**不是「等价实现」，是同一个方法调用**。
⇒ 自检（`RuleEngineTest` / `DeckScene` / `CollectionScene` / `BattleScene`）、编辑器工具、
任何没有 Shell 的场景，行为**零变化**。

## 五、与「W6 现状」的差异（**如实列出**，⛔ 不是等价）

只有一处，而且只在**分支病态**（旧档存在但读它抛异常）时才看得见：

| 场景 | W6（`ReadThroughLegacy`，`StoreOn=false`） | W7（空钩子 ⇒ `DeckStore.LoadAll`） | 判定 |
|---|---|---|---|
| 旧档不存在 | `SafeRead` → `null` → `Parse(null)` = `NoSaveFile` | `File.Exists` 假 → `NoSaveFile` | **相同** |
| 旧档在、读成功 | `SafeRead` → 原文 → `Parse` | `File.ReadAllText` → `Parse` | **相同**（`Parse` 是同一个方法） |
| 旧档在、**读抛异常** | `SafeRead` 捕获 → `null` → `NoSaveFile`（`LastLoadCode` = `NoSaveFile`） | `LoadAll` 捕获 → `ReadFailed`（`detail = "read failed: …"`） | 🔴 **`LastLoadCode` 不同**：两者 `ClassifyLoad` 都是 `Failed`（`existed` 为真），**只有细一档的错误码不同**。W7 反而更准（真的读到一半炸了，就该是 `ReadFailed`） |

这条我**没有去对齐**（要「逐字等于 W6」就得在钩子为空时也复刻 `SafeRead` 那段吞异常逻辑，
那就等于把 W6 那版**绕过 `DeckStore` 的文件 IO** 再抄一遍）。判据：W6 那一支本来就不是判据，
`DeckStore.LoadAll` 才是（它是这条路的正本，`LastLoadCode` 的语义只在它身上成立）。

   本笔用 `git diff -U0` 的 hunk 头 + 现读 7 个落点代替，见 §三。

   要验的话：起 `-wfscene Shell` player，进卡组编辑改一次卡组，看

   静态字段再赋一次同样的 lambda，**幂等**；但如果将来有人在这三个 lambda 里塞副作用，要回来加闸。
4. **没建 `账/_parts/B99_W7.tsv`** —— 本笔没有新增「原版行为 ⇒ 我们的实现」条目，
   纯属`实现手法`整改（判据侧原版没有对应物），且既有落点行号一个没动 ⇒ 没有可补的账行。
   若调度台要求，可补一行说明「`RuleEngine` ⇄ `CardPresentation` 的存档边界 = 注入钩子」，
   但那属于**架构备注**、不是账（账的粒度是「原版方法 → 我们的落点」）。
