## 二 三条真缺陷 + 关键改法

### 🔴 B9 / B10 —— 触屏点手牌**永远不开卡面展示窗**（用户可见）
**病灶（精确到行）**：
- `Hand/CardInteraction.cs:836-858` `EndPressCandidate()`：`:848-849` 先 `OnTapped(card)`，`:854` 才 `SetHovered(-1)`。
- `BattleDriver.OnCardTapped()`（`:12673-12699`）第一道闸 `:12683` = `if (interaction.CardDisplaySuppressedFor(card)) return;`
- `CardDisplaySuppressedFor(card)`（`CardInteraction.cs:560-563`）= `card == HoveredCard && !DragOnlyBlocked()`。
- ⇒ **候选态（触摸那条正路）松手时 `_hovered` 必然还等于这张卡** ⇒ 每次轻点都被吞。
- **对照**：`Tap()` 那条走 `SimulatePress → PickUp`，而 `PickUp` 在 `:893` 就 `SetHovered(-1)` ⇒ 同一张卡同一位移**却能开窗**。这是两条路唯一的差别。

**最小复现**：`it.SimulateHover(p); it.SimulatePressPendingForTest(p); it.SimulatePendingReleaseForTest(p);` ⇒ `drv.CardDisplay.Visible` 不变。

**最小改法**：把 `EndPressCandidate` 里的 `SetHovered(-1)` **提到 `OnTapped` 之前**（`:848` 前调一次，`:854` 保留幂等）。语义上也更贴原版：`OnPointerClick` 到达时 `StopShowingCardInHand` 已经开始收牌。
⛔ **不要把 `CardDisplaySuppressedFor` 整条删掉** —— 它对应原版 `ToggleOpenCardDisplayOnTouch(false)`（`CardScript.ShowCardInHand:10597`），是真闸；问题是它在「按下→松手」这条路上**恒真**。

### 🔴 B13 —— 打过普通局再进教程局时，「跳过教程」钮**不出现**
**病灶**：`SettingsPanel._matchType` **只在 `Create(...)` 那一次**被赋（`BattleDriver.cs:28081`，在 `BuildHud()` 里），而 `BuildHud` 被 `if (_hudBuilt) return;`（`:27288-27300`）闩住 ⇒ 后续所有 Begin 复用第一次那局的 matchType。两个打开口（`ClickSettingsHud():5738-5753` / `SimulateOpenSettings():12014-12018`）都只 `Show()`，**不刷新**。原版 `BattleSettingsWindow.Open` **每次打开都读**。
**直证**：紧接着的 `SetMatchType(Tutorial)` / `SetMatchType(Replay)` 两条断言**都绿** ⇒ 面板没坏，只是打开时拿到的是陈旧值。
**改法**：两个打开口 `Show()` 之前加 `_settingsPanel.SetMatchType(Ctx.MatchType)`；或给 `SettingsPanel` 一个 `Func<MatchType?>` 供给口、在 `Show()` 里读一次（= 原版 `Open` 的读法）。⛔ 别在每个调用点各推一份。

## 四 判不准

### 4·1 残骸 4 条（B3–B6）的根因
**已证实**：那 4 条测的 `CardView` **没有 3D 卡身**（`Body3DWorldScale == 0` + 日志「找不到 body3D 节点」）；而 Oct-24 日志里同一格是 `0.31891 vs 0.31891`（有 3D 体）⇒ **Oct-24 之后才出现的状态变化**。
**静态读码能确定的**：`_body3D` 只在 `CardView.Build`（`:4361`，`board==true`）与 `SetFace(Board)`（`:2322`）里被建，**全文件没有一处把它置 null / 销毁** ⇒ 要么视图**不是按 `CardFace.Board` 建的**，要么 `BuildBody3D` 返回 null。后者必然打一条 `[CardView]` 警告（四条都有），而**整份日志一条都没有** ⇒ 只能是前者。
**最像的机制**：`BattleDriver.SyncBoard` 的「**认领旧视图**」退路（`:25335-25450`）：`hasView` 分支只 `v.SetData(...)`（`:25414`），**从不 `SetFace(CardFace.Board)`** ⇒ 若那一格挂着上一段留下的**非 Board 视图**，认领后一直是 `CardFace.Hand` ⇒ 四条症状逐条吻合。**但没有任何日志能证明这一点。**
**下一次跑 Unity 的最小探针（3 行）**：在 `ProbeRemnantView` 返回前打印 `v.Face` / `v.Body3DWorldScale` / `SyncBoard` 那次的 `created` 标志与 `views[slot]` 认领前的名字。
若 `Face != Board` ⇒ 定性翻成 **(β)**（产品症状：手牌视图被当场上单位摆进棋盘），修法 = `SyncBoard` 的 `hasView` 分支补一次 `v.SetFace(CardFace.Board)`。

### 4·2 `gen_cards_engine.py` 的 doc 数与实测增量对不上
`工具/gen_cards_engine.py:2569-2600` 的 doc 写「池内 **83 张 / 86 条**」；实测新增是 **69 张 / 93 条**。两者口径必然不同，没时间去读到能互相解释。**不影响本次定性**（新增行逐条都满足 `targetsAffected!=0 || playerTurn!=0`），但建议改 R1–R3 时顺手把 doc 那两个数改成实测值。
