### 2.2 关键匹配规则（今天踩过的坑都写在这）

1. **去泛型**：账里的类名**去掉了泛型参数**（`Inventory` / `CollectionItem` / `ConfigProvider` / `BiDirectionalDictionary`）。直接精确匹配会得到 **43 个「dump 里不存在」的假结论** —— 全部是 `<T>` 截断。本轮按 `<` 截断后匹配。
2. **模糊匹配先做**：复数 `s`、前后缀、大小写都试过；**除泛型外没有其他命中**（0 个）。
3. **同名 ≠ 已实现**：`def` 只说明我们**定义了同名类**；`ref` 多数是注释（本项目大量在注释里引用原版方法名）⇒ 所以单列 `alias` 与 `meth` 两个证据列，不把 `ref` 当实现。
4. **方法级证据**：取该类「全游戏定义它的类数 ≤ 3」的非平凡方法名，在我们的 `.cs` 里搜；`meth=命中/总数`。这是「读过并照做」的**弱证据**，只用来从「完全没碰过」里分离「读过」。
5. **record 识别**：方法里出现 `PrintMembers` 或 `<Clone>$` = C# `record`。它们的「9 个方法」里 **8 个是编译器样板**（`ToString/PrintMembers/op_Equality/op_Inequality/GetHashCode/Equals/Equals/<Clone>$/Deconstruct`）⇒ **不能按方法数衡量工作量**。
6. **引用计数只算 dump.cs**：看不到 prefab/scene 里的挂载 ⇒ **MonoBehaviour 的 `refs=0` 不等于死代码**（1,488 里有 522 个 MonoBehaviour）。真正的死代码判定还要求 **非 MonoBehaviour + 0 外部引用**，且本轮一律写「疑似」。
7. **不改账名**：账里 21 份 TSV 一字未改；所有归类只写进本目录。

### 2.3 档位判定顺序

`编译器生成` → `第三方/插件` → `无方法` → `接口/契约` → `数据模型(record)` → `编辑器/调试类` → `工具类` → `服务端/后端(P3)` → 业务：`账内 D`（再按备注分 死代码/P3/判不做）→ `账内 C` → `A/B 或 有实现件` = 已覆盖 → 剩下的 「0 引用且非 MonoBehaviour」= 疑似死代码 → 其余 = 真业务缺口。
