**⇒ 结论（新模型）五条：**

1. **holder 内容宽 = `PadL + Σ物品宽 + Spacing×(n−1) + PadR`** —— 那三颗件**一格都不占**。
   出厂（0 个物品）= **60** = prefab 实读（`m_SizeDelta.x = 0` + CSF `h:MinSize` ⇒ `30+30+0`）✔ 逐位吻合。

2. **`Unlock Button` = 列底部居中**：`anchorMin = anchorMax = (0.5,0)` · `pivot (0.5,0)` · `pos (0,15)`
   ⇒ 中心 x = holder 中心 x，**底边 = holder 底 − 15**。（`pos.y` 在 uGUI 向上为正 —— 本仓 y 向下。）
3. **`Warning` = 列底部居中、宽 = `0.8 × holder 宽 + 30`**（锚 `0.1..0.9` 横拉 80% + `sizeDelta.x = 30`）。
   ⚠️ **W-C1 与本件之前都把它当成「父宽循环 ⇒ 原版取不到」** —— **那个循环是假矛盾**：
   它不进布局表 ⇒ 父宽 = 纯内容宽 ⇒ **精确值**。
4. **`Badge` = 列左上角**（`anchor/pivot (0,1)` · `pos (0,0)`）—— **连 `PadL`(30) 都没加**。
5. **物品**：**holder 布局组里唯一的子件**，`MiddleCenter` + `ctrlH=1`（用子件自己的首选高）
   ⇒ 竖向居中在 `[holder.y1+25, holder.y2−85]`（**这一半我们原来就是对的**），槽号仍是**反序 `k = n−1−i`**。

## 四、E1 那套「逐子件宽度数组」还有没有用

**判断：留用，但它的角色从「修缺陷」变成「防线」；一个字都没删。**

理由（三条，逐条给依据）：

1. **它的原始理由被推翻，但 API 本身没有错** —— E1（2026-10-12）加
   `HorizontalChild(PxRect, float[] childWs, …)` + `HorizontalChildOwnHeight` 转发版，理由是
   「本窗那一列**混宽**（物品 200 / 按钮 245 / 徽标 100）」。A537 查实：那三颗件 `m_IgnoreLayout = 1`
   ⇒ **那一列今天【只有物品】、全同宽** ⇒ **「混宽列」这个前提不存在**。
   但那个重载本身（`left = 容器左 + padL + Σ_{j<index}(childWs[j]+spacing)`）是**正确的一般式**，删它没有收益。
2. **`BuildColumn` 仍在用它**（`ws = [ItemW]×n` 喂 `HorizontalChildOwnHeight`）——
   保留这个写法是为了守住 A239 的另一半：**「容器内容宽」与「子件落点」从同一张表派生**。
   今天它与等宽重载**逐位同值**（表是等宽的），所以这一步是**防线**：哪天真有混宽子件，不会静默走错路。
3. **`HorizontalContentW(float[])` 还有两个活调用点**（本窗 + `Shell/ForgeTab.cs:384`）⇒ 本来就删不掉。

**处理：只改注释、不动代码**（`Core/UguiRect.cs`，`git diff --numstat` = **33/0**）——
E1 那段 doc 里「**实害**（本仓实测，`Shell/CampaignRewardWindow.cs` 的列：物品 200 / 按钮 245 / 徽标 100）：
`Unlock Button` 实到 1325..1570…」**是一段与事实不符的记录**（它把错模型的产物当成「混宽列的证据」）
⇒ 按铁律 5 **就地更正**：写明「那个『混宽列』是错模型的产物，A537 已翻案」，并
「⛔ 别把这段当成『那一列是混宽的』的依据」。同时在等宽重载那条加一句指针。
