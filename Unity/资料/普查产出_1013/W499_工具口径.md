## 一、结论（哪个口径是对的、依据什么）

### 1·1 🔴 A499 悬着的那一问：`menu_rect.py` **【没有】自己的一份「兄弟过滤」**

**答：没有，而且不该有。** 它**根本不跑布局组**：

- 全文通读（566 → 812 行），`m_Padding` / `m_Spacing` / `m_ChildAlignment` / `m_CellSize`
  **只出现在 `kinds` 的字段指纹那两行**（HEAD 版 `:405-406`，现版 `:583-593`），
  **没有任何一处**把它们送进过计算；文件头自己就写着「⚠️ **不含 LayoutGroup**」。
- 它对孩子的唯一动作是 `Bundle.children()`（HEAD `:191`，裸读 `m_Children`）与 `walk` 的递归（HEAD `:416`），
  **两者都不过滤** —— 与 `menu_dump.walk`（`工具/menu_dump.py:2162`，同样是裸 `b.children(rtpid)`）**同口径**。

⇒ **A487 那一族缺陷（「哪些兄弟参与布局」）在 `menu_rect` 侧不存在**，
`menu_dump._rect_children`（`工具/menu_dump.py:1628` 起）仍然是那条规则的**唯一一份**，
本件**没有在 `menu_rect` 里造第二份**。H41 §七·4 那句「**不排除**它有自己的一份」可以**销掉**。

### 1·2 但同族的「布局判定」口径差 **3** 处：改齐 2 处、判「不改」1 处

| # | 差异 | 谁对 | 依据（**原版语义**，不是「哪个文件先写」） |
|---|---|---|---|
| **D1** | `menu_rect` 表尾把**所有**带布局组的节点一并说成「子节点位置由布局算」——**包括 `m_Enabled=0` 的** | **`menu_dump` 对** | uGUI 的布局件挂在 `m_Enabled=0` 的组件上时**原版根本不跑它**（`menu_dump.apply_layout_to_children` 里 2026-09-27 那条 + 实例 `Player Profile Window > Menu Area`：照跑会把 `Tab Buttons` 的 y 从 **180.24 顶到 187.24**）。⇒ 那类节点的子件**就停在模板位**，说「由布局算」是把人**引去重算一遍** |
| **D2** | `menu_rect` **没有**「自己 active、祖先 inactive」这一档（`menu_dump` 打 `ANC✗`） | **`menu_dump` 对** | uGUI 的 `activeInHierarchy` 看**整条父链**（本机 `LayoutGroup.cs:60` 的 `!rect.gameObject.activeInHierarchy`）⇒ 那些件**原版一个像素都不画**；`menu_dump.walk:2084-2088` 明写「**必须标出来**，否则读表的人会以为那件是可见的」——**不许静默** |
| **D3** | `menu_rect` 的组件判定**只用字段指纹**（`menu_dump` 是**类名优先、指纹兜底**） | **两边都对，但只能留一份** | A127「靠 MonoScript 的类名判，不靠字段猜」是 `menu_dump` 后来的口径；而 `menu_rect` **拿不到 monoscripts 索引**（`menu_dump` 反向 `import menu_rect` ⇒ 在这里调它会成环）⇒ 它走的**就是 `menu_dump.fingerprint` 那一条兜底路**（逐字相同）。**实测 `bundle_menus_assets_all`：`menu_dump` 认的 1470 个布局组，指纹一个不漏、无一处误报** ⇒ **不改**，把理由写进代码注释 |

### 1·3 顺带坐实的两条（同族，已改）

- **D4**：`walk` 里 `scl = rt.get('m_LocalScale', {'x':1,'y':1})` —— 键**存在但为 `null`** 时拿到 `None` 再 `.get` ⇒ **`AttributeError` 崩**；
  `menu_dump.walk:2118`（现读）用的是 `or` 那一支。⚠️ 实测本包 **16510 个 RT、0 个是 null** ⇒ today 无影响，但两处写法**必须一致**（已改）。
- **D5**：`--active-only` **同口径**（两边都按**自己那一格** `m_IsActive` 过滤：`menu_rect` / `menu_dump:3260` / `:3312` / `:3352`）⇒ **口径不改**，
  但 `menu_rect` 那一侧**原来连 `help=` 都没有**（其他开关全有）⇒ 补 help + 文档写明「这是 `activeSelf`、不是 `activeInHierarchy`」。

## 七、【调度台追加①】`_scan_go` 的「pid 撞车 ⇒ 静默挂错名字」

### 7·1 根因与修法

**根因（坐实）**：一个导出目录里**可以有两个内层 CAB 各有一个同号 GameObject**，
而 HEAD 版 `_scan_go` 写的是 `self.go[true_pid] = j` —— **后扫覆盖先扫**，且**一个字都不说** ⇒
`self.go[pid]` 是谁**取决于 `os.listdir` 的顺序**（不可复现）。

**案发现场**（`bundle_scenes_scenes_mainmenuwarpforge`）：

| 事实 | 证据 |
|---|---|
| `Icon_238.json`：`m_Name="Icon"`，`m_Component=['371', …]`，`RT_371.m_Father = 359` | 文件实读 |
| `Player Level.json`：`m_Name="Player Level"`，`m_Component=['1279', …]`，`RT_1279.m_Father = 1125` | 文件实读 |
| **两份都自称 `m_GameObject.m_PathID = 238`** | `RT_371` / `RT_1279` 各读一次 |
| `RT_359`（`Resource Counter Item`）的 `m_Children = [372, 371]` | 文件实读 |

⇒ 走 `Resource Counter Item` 那棵树时，`self.go['238']` 落到了 `Player Level` 上 ⇒ 那一行印成 `Player Level`。

**修法（三层，缺一层都不够）**：

1. **不再覆盖**：真 pid 的登记**先到先得**（确定），并把撞车记进 `go_coll` + **出声**（`go_coll_warning`，写 stderr）。
   ⚠️ **专账 `_go_pid`**：`self.go` 里还有**退化解键**（按文件名尾巴写的），拿它当依据会把
   「真 pid 撞退化解键」**误报成撞车** —— 实测**虚报成 64 组**（真值 **49**）。这一条是我自己第一版写错、**当轮查出并改掉**的。
2. **认得对**：新增 `go_by_rt`（**RT pid → GO dict**）+ `go_obj_of_rt` / `go_name_of_rt` ——
   **这一颗 RT 的 pid 是唯一的**，拿它去问「哪个 GO 文件的 `m_Component` 里列过它」认得准。
   `walk` 的**名字 / `m_IsActive` / 组件列**三样**一起**改成走它（原来三样**一起**取错）。
   ⚠️ 老路退回：查不到就 `self.go.get(go_of_rt(...))` ⇒ **无撞车时逐字节同旧值**（§4·2/§4·3 已证）。
3. **找得到**：新增 `find_rt()` —— 因为 `find_go` 只在**pid 去重后的 `self.go`** 里找，
   撞车时**另一份 GO 根本不在那张索引里** ⇒ `Resource Counter Item` 按名字 **整个找不到**
   （第一版只做「先到先得」时实测复现：`找不到 GameObject「Resource Counter Item」`）。
   两个工具的 `main()` 都改走它。

## 八、【调度台追加②】`menu_dump.py` 的 `m_Enabled` 列会误导读者

### 8·1 根因（**是工具的缺陷，不是读的人不小心**）

一个节点挂**多个组件**时，表里那四格（sprite / 贴图模式·颜色 / 文字 / 其它参数）是
**各组件的内容并排拼起来的**（`main()` 里四个 `join`）—— **没有一格说得清自己属于哪个组件**；
而 `m_Enabled=0` 原来是**裸标记**。⇒ 读者自然把「被禁」记到**另一个组件**头上。

**真代价**：`资料/普查产出_1013/A表现核_块1.md` §A389 把 `holder/Image` 写成
「`Image` 挂着 `m_Enabled = 0`（原版根本不画它）」。**现读两份 MB 原文**：

| 文件 | 内容 |
|---|---|
| `MonoBehaviour_-5355200480893724929.json`（= `image` 字段指的那一个） | **`m_Enabled: 1`** · `m_Sprite: {m_FileID: 10, m_PathID: -6034862274493247622}`（= `40k_missions_milestone_off`） ⇒ **这一颗 Image 是画出来的** |
| `MonoBehaviour_7171112632542172927.json`（同一节点） | **`m_Enabled: 0`** ⇒ **被禁的是 `Outline`** |

（`m_Sprite` 那个 `m_FileID: 10` 是**跨文件引用**，正是「同一目录里多个内层 CAB」的同一个成因 —— 与 §七 同源。）

### 8·2 影响面（本包实测）

| 项 | 数 |
|---|---|
| 挂 **≥2 个组件**的 GO | **9764** |
| 其中**有组件被禁**的 | **595** |
| 「**启用且有 sprite 的 `Image`** + 另一个被禁组件」这一档（= 最容易被误读的形状） | **23**（全是 `Image`+`Outline`，图都是 `40k_missions_milestone_off`） |

### 8·3 修法（三条）

1. **标记带类名**：`describe()` 两处（`Image` 支 `:582`、兜底支 `:698`）改成
   ` **m_Enabled=0**（`Outline` 组件被禁 ⇒ 它不画；**组件级禁用 ≠ GO inactive**）`
   ⇒ 单组件那一档也**更准**（「这一件」原来与「这个组件」混着说）。
2. **行内出声**：新增 `multi_comp_flag()`（判据只此一份），≥2 组件**且**有禁用 ⇒ 打
   `⛔MULTI-COMP(2组件·1禁用)`；**两种输出模式都打**（纯文本 `:3331`、`--md` `:3275`）；
   图例与共享 `read_note` 各补一条（`:3246-3250`）。
   ⚠️ **`n == 1` 且它就是禁用的 ⇒ 不出声**（四格同属一件、没有歧义）—— 这条**单独钉了断言**（见 8·4）。
3. **新自检 ⑳**（真数据，不是打桩）：`bundle_menus_assets_all` 里 GO `-2290505579751386358`（名 `Image`）
   = `Image`(**启用**) + `Outline`(**禁用**)：
   ① `Image` 那一格**不许**出现 `m_Enabled=0`；② `Outline` 那一格**必须有且带类名**；
   ③ 行内标记 = `⛔MULTI-COMP(2组件·1禁用)`；④ 单组件（且禁用）⇒ `''`；⑤ 两组件都启用 ⇒ `''`。
