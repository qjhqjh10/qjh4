## 〇、五条结论（先看这个）

1. **原版不是「只有少数几处 Bottom」—— 只有 64%/67% 是 `Middle`**。两个包合起来 **186/547 = 34%** 的非 Middle：
   主菜单 `Middle 64.0 · Capline 9.3 · Midline 23.4 · Bottom 2.8 · Top 0.5 (%)`；战斗 `67.3 · 3.0 · 25.8 · 2.4 · 1.5`（§二）。
   ⇒ A712 那句「`Card Counter` 子树里只有它是 Bottom」**是对的**（本笔现读复核：主菜单 6 个 Bottom 里 5 个是
   卡面效果列的 `EnchanterText`）—— **但「全工程按 Middle 画」这件事影响面是 1/3，不是 1 处。**

2. 🔴 **`工具/menu_dump.py` 早就把这一格印出来了**（简报里的「先现读确认它印不印」= **印**）：
   `对齐=Center/Bottom` 那一格就是 `m_HorizontalAlignment`/`m_VerticalAlignment`（`工具/menu_dump.py:101` 的
   `V_ALIGN` 表 + `:603` 的打印）。**不需要新写工具**，逐站核档位用现成命令即可。

3. **我们今天的做法 = 全工程一档「把行盒居中到节点位」**（`Battle/Label.cs:799-809`）——
   61 个 `Label.Create` 调用点全扫过：**纵向 anchor 全是 `0.5`**（52 处 `(0.5,0.5)` + 7 处 `(0,0.5)` + 1 处 `(0,0)`
   + 1 处变量）⇒ **0 处按档画过**。而生产代码里已有 **80 行注释**（**24 个文件**）写着「原版这颗是 Capline/Midline」
   ——**判据早就有了，只是没落到摆位那一行**（§三·1）。

4. **33% 那一部分的应改量 = 1.5 ~ 8 px（不是「四分之一行高」的普适值）**，**方向和大小逐档不同**：
   `Top/Bottom` 与**框高**绑（`(框高 − 行盒高)/2`，`Single Counter` ≈ 8.4 px）；`Capline`/`Midline` 与**原版字体的
   度量**绑（≈ 0.05 em，fs 33 → 1.7 px）。算式与数见 §4·5。

5. 🔴🔴 **本笔按 TMP 源码公式推出来的最大一条（⚠️ 推导，不是实测）：那 67% 的 `Middle` 其实也没对准** ——
   我们字体的**行盒比原版高 1.6 倍**（1.516·F vs 0.947·F）且不对称度不同（基线离行盒心 0.4325 em vs 0.2632 em）
   ⇒ 两边都「居中行盒」时**我们的字墨比原版低 ≈ 0.13 F**（fs 35 → 4.5 px）。**这条没有任何断言看得见**（§4·4）。
   ⇒ **先实测确认，再决定改法**（§5·0）—— 它决定「只加档位偏移」能不能算完工。

## 一、口径（本机 TMP 的垂直档枚举 · 现读）

**判据 = 本机 TMP 源码 `Library/PackageCache/com.unity.ugui@27635d171b1a/Runtime/TMP/TMP_Text.cs:24-85`**（本笔现读）：

| 低位（横向） | 值 | 高位（纵向） | 值 | 枚举名 |
| --- | --- | --- | --- | --- |
| `Left` | 0x1 | `Top` | **0x100 = 256** | `VerticalAlignmentOptions.Top` |
| `Center` | 0x2 | `Middle` | **0x200 = 512** | `Middle` |
| `Right` | 0x4 | `Bottom` | **0x400 = 1024** | `Bottom` |
| `Justified` | 0x8 | `Baseline` | **0x800 = 2048** | `Baseline` |
| `Flush` | 0x10 | `Geometry`（别名 **`Midline`**） | **0x1000 = 4096** | `Geometry` |
| `Geometry` | 0x20 | `Capline` | **0x2000 = 8192** | `Capline` |

- 🔴 **简报里那句「`Midline = 4096` · `Capline = 2048` · `Baseline = 4096`」要订正**：
  本机枚举是 `Baseline = 0x800 = 2048` · `Geometry/Midline = 0x1000 = 4096` · `Capline = 0x2000 = 8192`。
  `工具/menu_dump.py:101` 的 `V_ALIGN` 表与本笔现读**逐值相同** ⇒ 那份表可以照用。
- **`m_textAlignment = 65535`（0xFFFF）是「Converted」哨兵**（`TMP_Text.cs:68`）：运行期 TMP 会把
  `m_HorizontalAlignment | m_VerticalAlignment` 合成它（`:6025`）。**存档里那一格没有信息，看两个分量**。
- **运行时会不会被改写？** 本笔只查了唯一可疑的写入点：I2 本地化
  （`d:/2/tools/decomp_full/I2.Loc.LocalizeTarget_TextMeshPro_UGUI__DoLocalize.c:157` 那句 `set_alignment`）——
  它调的 `…_InitAlignment_TMPro.c` **每一条分支都只做横向成对翻转**（`0x101↔0x104` = `TopLeft↔TopRight` 这一族），
  **纵向那几个 bit 一个都没动**（两个出参都从原值出发）⇒ **序列化里的 `m_VerticalAlignment` 就是运行时的值**
  （⚠️ **写入点没穷尽**，见 §六·3）。

## 四、我们今天的做法（现读）

### 4·1 `Battle/Label.cs` 的算式（**唯一那条**）

```csharp
// Battle/Label.cs:799-809
public void RefreshBounds() {
    var b = _tmp.textBounds;                       // TMP 的【行盒】（见 4·4）
    _tmpW = Max(|b.size.x|, 1e-4); _tmpH = Max(|b.size.y|, 1e-4);
    _tmp.rectTransform.localPosition =             // ⇐ 摆的是 TMP 子节点（`TmpFont.NewText(transform,…)`）
        new Vector3(-anchor.x * _tmpW - b.min.x,   //    ⇒ anchor.y=0.5 时 = 【块心落在节点位上】
                    -anchor.y * _tmpH - b.min.y, 0f);
}
```
- `anchor` 是 `Label` 自己那个 `Vector2` 字段（`Battle/Label.cs:27-28`），**不是** uGUI 的锚点。
- `Shell` 侧一律走 `Shell/MenuDraw.cs:1553-1571` 的 `Text()`：节点摆在 **`PxRect` 的中心**
  （`MenuDraw.Local` = `LayoutSpace.RectCenter − 父位置`，`:30-31`），anchor 恒传 **`new Vector2(0.5f, 0.5f)`**（`:1557-1558`）。
- 所以全工程的实际行为 = **「把文字块（行盒）居中到原版那个矩形的心」**，**与 `m_VerticalAlignment` 无关**。
- 已有的两个「对齐口」只做横向：`AlignLeftOn`/`AlignRightOn`（`:862-880`）—— 它们只改 `localPosition.x`。
- `Battle/Label.cs:315-316` 把这个映射写得很清楚：**「`TextAlignmentOptions.Left` = H=Left + V=Middle，
  正好是原版 `m_HorizontalAlignment=1` + `m_VerticalAlignment=512` 那一对」** ⇒ **只用了枚举的横向那一半**。

### 4·4 🔴 摆位的算术：两边的**度量**不一样（本笔的推算 · **没实测**）

**判据（全部现读）**：

| | 我们的字体 `NotoSerifCJK-Regular SDF` | 原版主力 `Pragati-Regular SDF` | 原版次要 `Asar-Regular SDF` |
|---|---|---|---|
| 出处 | `Core/TmpFont.cs:27`（`Resources/Fonts/…`） | `…/assets_full/bundle_fonts_assets_all/MonoBehaviour/Pragati-Regular SDF.json` | 同目录 `Asar-Regular SDF.json` |
| `m_PointSize` | 50 | 95 | 94 |
| `m_AscentLine` | 57.55 | 70 | 80 |
| `m_CapLine` | 36 | 60 | 61 |
| `m_DescentLine` | −14.3 | −20 | −35 |
| 行盒高 ÷ em | **1.437** | **0.9473** | **1.2234** |
| 行盒心 → 基线 | 0.4325 em | 0.2632 em | 0.2394 em |
| 大写高 ÷ em | 0.72 | 0.6316 | 0.6489 |

- **我们的行盒 = 1.516 × fontPx px**（= 1.437 em × 1.0547，其中 em = 1.0547·fontPx，由
  `Core/TmpFont.cs:266-270` 实测的「行盒 0.1437 / 字形 0.0948」两个比值定出来）。
  🔵 **独立佐证（实跑数，不是本笔推的）**：`Editor/MainMenuScene.cs:6957-6958` ——
  「汉字行盒 ≈1.3em = 52px 正好顶到框高 52 ⇒ TMP 让了一档（**实测 34.292**）」
  ⇒ `52 / 34.292 = **1.516**` **逐位吻合**。同样地，原版那颗是拉丁 `Trophy Name`、
  行盒矮（0.947×40 = 37.9 < 52）⇒ **不收缩、停在 40** ⇒ 两边 0.947 / 1.516 **各自被这次实跑反证过一次**。
- ⇒ **我们的基线落在框心下方 0.456·F**（= 0.4325 em × 1.0547）；**原版 `Middle` 的基线只落在 0.2632·F**。
  ⇒ **即使原版是 `Middle`，我们的字墨也比原版低 ≈ 0.13·F**（fs 35 → **4.5 px**，fs 50 → 6.5 px）。
- ⚠️ **为什么至今没人看见**：纵向**渲染盒**断言存在但极少，而且**断的全是「行盒中线 = 原版框心」** ——
  那正是**把我们的 `Middle` 当成判据**（= 铁律那条「断言别盯我们自己的口径」）：`Editor/MainMenuScene.cs:4838`
  （行内 `Points`「**画出来那块字**竖直居中于 299.86/377.83 那个框」）· `:6863`（`Next Tier` 的纵向中线 = 550.92）·
  `Editor/RewardsScene.cs:3051/3054`（「渲染中心 y = 原版框的中心」，且注释自己写明量的是**框**高）。
  其余 12 处 `TmpRenderedRect` 调用**只用 x**（`Editor/MainMenuScene.cs:339` 的度量函数 + 15 个调用点）。
  ⇒ **一条「字墨落在哪」的断言都没有**（那是 `topLeft/bottomLeft` 那一层，见 §5·0）。
- ⛔ **这条是推导，不是实拍** ⇒ 归 §五 的**前置项**，**不许直接照它改实现**。

### 4·5 换算表（**每一条都要拿上面那两张表算，不能一个常数走天下**）

设 `F` = 那一颗原版的 `m_fontSize`（px，= 我们传的 `fontPx`）、`Hb` = 原版那一颗的**框高**（px）：

| 原版档 | 原版基线的位置（相对框心，向上为正） | 我们现在的基线 | **需要的位移**（Pragati / Asar） |
|---|---|---|---|
| `Middle` | −0.2632 F | −0.456 F | **+0.193 F / +0.217 F（上移）** |
| `Capline` | −0.3158 F | 同上 | **+0.140 F / +0.132 F（上移）** |
| `Midline`（全大写或数字） | −0.3158 F（= 墨水盒心 = 大写盒心） | 同上 | **+0.140 F** |
| `Midline`（带下伸部的小写串） | −(墨水顶+墨水底)/2 F | 同上 | ≈ **+0.02 F ~ +0.14 F**（逐串不同，要用那串的 `characterInfo` 算） |
| `Bottom` | −Hb/2 + 0.2105 F | 同上 | **−Hb/2 + 0.667 F** |
| `Top` | +Hb/2 − 0.7368 F | 同上 | **+Hb/2 − 0.281 F** |

- **TMP 的公式出处**（本笔现读）：`…/com.unity.ugui@27635d171b1a/Runtime/TMP/TextMeshPro.cs:4193-4232`
  的 `switch (m_VerticalAlignment)` —— `anchorOffset` 就是**基线**的位置（由 Top/Bottom 两支反推确定）：
  `Top = 上角 − ascent` · `Middle = 心中 − (ascent+descent)/2` · `Bottom = 下角 − descent` ·
  `Capline = 心中 − capLine/2` · `Geometry = 心中 − (墨水顶+墨水底)/2`。
- **两个例**（本笔推的，⚠️ 没实拍）：
  · `Card Counter/Single Counter/Counter`（Pragati · Hb **50** · F 名义 35，我们的自适应会先收到 50/1.516 = **33.0**）
    ⇒ 位移 = −25 + 0.667×33 = **−3.0 px（下移）**。（⚠️ 注意：这里「Bottom 该下移 (50−33.2)/2 ≈ 8.4」与
    「我们本来就低了 0.193F ≈ 6.4」**方向相反、互相抵掉大半** ⇒ **不能只照其中一个改**。）
  · 主菜单导航 `PLAY`（Pragati · fs **33** · Capline）⇒ 位移 = **+0.140×33 ≈ +4.6 px（上移）**。

## 五、改法选项（≥2 条 · 各自的影响面与自检）

### 5·0 🔴 **前置项（先做这个，再动摆位）**

`characterInfo.ascender/descender` 是**行盒**、`topLeft/bottomLeft` 才是**字形四边形** ⇒ 两个口都有，不必新写探针。

「只加档位偏移」**修完 33% 仍然全错**，而且 §4·5 的位移**每一格都要重算**（基准线变了）。
**代价**：跑一次已有的 `*.Run`（主对话的同步点即可），**不需要新的自检宿主**。

### 选项 A —— 在 `Label` 上加「垂直档」，`RefreshBounds` 内统一换算

  `TextBox`/`Txt`/`Label.Create` …）+ 现有断言里的 `RenderedRect`/`CheckAtWorld`/`TmpRenderedRect`
  **全都量的是行盒** ⇒ 预期会有一大批期望值要改（**改期望值本身是风险**：`A490` 那条教训就是「量法一变，旧断言全变成自证」）。

### 选项 B —— 照 `AlignLeftOn/AlignRightOn` 那一族加「垂直口」，**逐处显式调**

- **动的文件**：`Battle/Label.cs` 加 3 个方法（`AlignBottomOn(boxBottomY)` / `AlignTopOn(boxTopY)` / `NudgeYBy(dy)`，
  都只改 `localPosition.y`，与两个横向口对称）· `Shell/MenuDraw.cs` 加薄助手（`AlignBottom(lb, r)` / `AlignTop(lb, r)` /
  `NudgeV(lb, px)`，与 `:1598-1607` 的 `AlignLeft/AlignRight` 同形）。
- **影响面**：**小且可控** —— **只有原版非 Middle 的那些站位才调它** ⇒ 没调的件**逐位不变（零回归）**；
  要改的处数 ≈ §三·1 那 80 行注释能认出来的那些（生产代码 ~60 处量级）。
