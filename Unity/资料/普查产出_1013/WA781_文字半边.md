### 2. 三个关键问题的答案

**① 「加一个可选形参」够不够？—— 够，而且比「够」还多一点。**

`Rect` / `Nine` / `Tiled` / `Hit` 这四个**同族的静态件**今天的形状就是：

```csharp
public static ImageQuad Rect(Transform parent, Texture2D tex, PxRect r, string name, int q,
                             Color? tint = null, bool keepAspect = false, PxRect? clip = null,
                             Vector2 clipSoftness = default(Vector2))
{
    var _st = ViewportClip.Resolve(parent, clip, clipSoftness, default(Vector4));
    clip = _st.RenderClip;  …
```

⇒ **`Text` / `TextBox` 是全族里唯一两个漏掉这一对的**（`Shell/MenuDraw.cs:1553` / `:1579` 改前）。
把同样的两个可选形参加在**签名末尾** ⇒ **185 + 21 个调用点一个字都不用改**（源码兼容：
旧调用点最多只传到现在最后一个形参 `autoBasePx`）。

**② 「静态版本拿不到 `Transform` 怎么 `Resolve`」—— 简报这一问的前提不成立。**

`MenuDraw.Text` / `TextBox` 的**第一个形参就是 `Transform parent`**（它们不是「手上只有矩形」的那种函数），
而且标签就是建在它下面的（`Label.Create(parent, …)`）⇒ `ViewportClip.Resolve(parent, clip, clipSoftness, zero)`
**一句就够** —— 与 `Rect` / `Nine` / `Hit` 逐字同形。
（真正「手上只有矩形」的是 `ClipRect` / `Visible` / `PaddedClip` / `ApplySoftEdges` 那几个 ——
那才需要 `ClipRectAbove` / `VisibleAbove` 这种由调用方先解析的重载，见迁移表补充节「谁解析 / 谁不解析」。）

**③ 于是「必须逐个调用点传」那条路根本不用走 —— 而且那条路本来也走不通。**

点名那三处（`Army Name` / `Premium Text` / `Army Text`）住在
`Shell/PurchasePremiumWindow.cs` 与 `Shell/RankedRewardEventWindow.cs` —— **两个都在本件的 ⛔ 黑名单里**
（A435 庚 owns）。⇒ 「加形参 + 逐个调用点传」这条路**在本件的白名单下不可能完成**
（会把「字也裁了」拆成「两扇窗裁了、其余全没裁」= 又一个半拉子）。

### 3. 结论：**做**（加末尾两个可选形参 + 一句 `Resolve` + 最后一步 `ClipText`）

**为什么是「做」而不是「只报不改」**：

1. 判据齐了（原版 `RectMask2D` 一视同仁 + 同族四个静态件的现成写法 + `MenuWindowBase.Text` 这个成品范本）；
2. **零调用点改动** ⇒ 不越白名单（只动 `Shell/MenuDraw.cs` 一个生产文件）；
3. **`Resolve` 的三段优先级天然给出「零行为变化」那一档**：`clip == null` 且父链上没有节点
   ⇒ 落第 3 支 + `ClipText` 首句 `!clip.HasValue ⇒ return false` ⇒ **逐位不变**
   （今天全仓**只有已迁完的那批窗**有节点，其余窗一个都没有）；
4. 只报不改 = 把一条**判据明确、一行能修**的缺陷继续挂着，与铁律 11 冲突。

**⚠️ 但「零行为变化」要写准**：它是「**父链上没有节点的窗**零行为变化」。
在**已经挂上节点的那批窗**里，这一改**就是**行为变化 —— 那正是本件的**目的**（原版就裁）。
受影响面的清单见 §四（**这一条是本件最大的风险，必须让调度台看见**）。

### 4. 与「第 7 种载体」的关系（别混）

普查（`WA766_同形口普查.md`）把「第 7 种载体」定义为「**生产代码里把 `clip` 形参就地用掉、
不转调 `MenuDraw.*` 解析口**的行」。`MenuDraw.Text` / `TextBox` **不属于那一族** ——
它们原来是**连 `clip` 形参都没有**（另一种形状：**压根没有入口**）。
⇒ 本件**不碰** `NodeShadowedByParam` / `NodeResolutions` 那两个计数（一条都不读、也一条都不写断言）。

### 5. 顺带定掉的一个口径：**不做「整块在视口外 ⇒ 不建」那道闸**

`MenuWindowBase.Text` / `TextBox`（A435① 成品）有两道：① `Visible` 整块在外就不建；② 压边的字切一刀。
本件**只做 ②**（裁），**不做 ①**（闸）。四条理由：

1. **返回值契约**：`MenuDraw.Text` 今天**恒定返回一个标签**（`null` 只可能来自 `Label.Create`）。
   加 ① 会让它在 200 个调用点上**可能返回 `null`** —— 那是**比本账更大的改动面**，
   而「哪些调用点解引用返回值」本件**没有逐个核**（⛔ 不许靠猜）。
2. **画面上等价**：只裁不建 = 框外的字被夹成**零面积**的四边形 ⇒ **画不出像素**，与原版被掩码裁掉同形。
3. 走 `MenuWindowBase` 那一族的窗**本来就有 ①**（那一层没被本件碰），行为没有退化。
4. 铁律 13·7：判据清楚、改动面清楚的才做；① 的炸点范围**没查清** ⇒ 不进这一件。

🔴 **那一条差异仍然开着**（`MenuDraw.Text` 不像 `MenuWindowBase.Text` 那样 cull）——
已写进 `MenuDraw.Text` 的注释里（「另立账，⛔ 别在这儿顺手加」），**建议调度台按铁律 11 另开一条**。

**🔴 三个刻意做的选择（⛔ 别顺手改回去）**：

1. **交给 `ClipText` 的永远是「调用方原样那一份 `clip`」，不是 `_st.RenderClip` 那份快照。**
   判据 = `ClipText` 里 A484 那一段：`ClippedTextGuard` 要在**节点挪动之后重新解析**；
   存快照会让守卫**永远按旧框重裁**（静默），而且每重裁一次就给 `NodeShadowedByParam` **误报 +1**。
   ⚠️ 这一条在**本件**里还多一层意义：`MenuDraw.AlignLeft/Rignt` → `Label.AlignLeftOn/RightOn`
   → `RefreshBounds()` → 守卫 `Reclip()` ⇒ **「先 `Text` 后 `AlignLeft`」那些调用点靠守卫补刀才正确**
   —— 若存快照，那一刀会落在**旧位置**的框上。
2. **`TextBox` 的内层走 `TextCore`（不裁），⛔ 不是 `Text`。**
   若走 `Text`，会「先裁一刀 → `SetWrapWidth`/`SetAutoFitBox` 重排把它冲掉 → 再裁第二刀」：
   白做一次，而且会让 `TextClipUnavailable` / `TextClipUploadSkipped` 这两个**诊断计数虚高**
   （它们只在 `ClipText` 真跑起来之后才数）。
   ⚠️ 后果：**这一条没有断言盯**（幂等 ⇒ 不会红）—— 见 §六·4。
3. **新形参加在【末尾】**（不是插在 `q` 后面）—— 否则 185 个旧调用点的位置实参全部错位。
