## 二、为什么会发生（六条成因，每条都有实例）

### 成因 1 🔴 **尺子错了：拿 PnP 印刷品当数字版规格**

卡面那一轮（2026-09-12 ~ 09-15）手上**只有 PnP 成品卡图**，于是把「PnP 上印什么」当成了「数字版印什么」。
后果：阵营行、兵种行、版面，都是**照印刷品补的**。

**判据**：PnP 是**实体印刷品**，原版游戏是**数字版**，是**两个产品、两套版式**。
PnP 能当尺子的：**内容**（卡名 / 费用 / 攻血甲 / 效果文字 / 立绘是哪张 / 关键词图标）。
PnP **不能**当尺子的：**版式与显隐规则**（哪一层在哪印、什么时候印、印多大、要不要溢出）。

### 成因 2 🔴 **只看静态字段，不看运行时**

「原版没有文字底板」这条结论，来自场景里 `Textbackgrounds` 那个 GO 的 **`m_IsActive = false`** ——
而运行时 `CardTextsController` 的 state 表**每一条都把它列进激活列表**。
⇒ **静态字段 ≠ 运行时行为**，这条本是铁律 4 的精神，在卡面这条线上又踩了一次。

### 成因 3 🔴 **新增一层时，没问「既有机制会不会动它」**

`ApplyTint()` 从 2026-09-13 起就**遍历 `_layers` 给每一层刷整卡色**。
2026-09-15 加「文字底板」时，把它 `AddLayer` 进了 `_layers` ⇒ **底板的颜色被整卡着色覆盖成白色**。

**为什么难发现**：① 它是**静默**的（不报错、不打警告）② **只在「卡被着色」时才现形** ——
离屏探针（`CardFaceProbe`）不调 `SetTint`，所以**第一版渲出来是对的、游戏里才是坏的**。

**下次怎么挡**：**加一层之前，先 grep 谁会遍历 `_layers`**（整卡着色 / `SetAlpha` / 刷新 / 高亮），
问一句「这一层的颜色/纹理是它自己说了算，还是别人说了算」。
⚠️ 判据不一致的那一类（原版写死的常量 vs 会被统一刷新的量）**要显式标出来**。

### 成因 4 🔴 **出牌是「搬视图」不是「重建视图」，漏了状态迁移**

「场上按场景分层」只在 **建卡** 那条路上生效；而**从手牌打出去的兵**走的是
`SetData()` + `SetParent()`（为了让落位动画不丢）—— **视图没重建，场景也就没换**。
症状特别阴：**督军是对的（出生就在场上）、打出去的兵是错的**，两个入口只走对一个。

**下次怎么挡**：一个对象有**多个出生/迁移入口**时，把「按场景分层」这种**状态**做成
**每个入口都必须调一次**的显式方法，并且**每个入口各配一条断言**。

### 成因 5 🔴 **验收方式不够：没有「逐张对着成品卡并排比」这一步**

当时有的验收是：**断言**（只能验我想到的东西）+ **截图**（只能看宏观）。
⇒ 上面三条错**同时通过**了 588 条断言和四张截图。
而只要有**一次**把我们的卡和 PnP 并排渲出来看，**三条一次全露**。

**判据**：**断言管行为，并排比管"像不像"** —— 两条都要，缺一条就会漏掉整整一类错。

### 成因 6（元）🔴 **「全量反编译」没有成为默认第一步**

2026-09-18 全量反编译就做完了（26282 个方法体），文档也写着「要问『原版怎么做 X』先看它」。
但实际工作顺序是 **先动手 → 出问题 → 才去查**。

**同一个会话里的对照实验**：
- **先查后做**的：卡组串格式 → 直接读 `CardDeck__Serialize.c` → **一次改完，2948/2948 全过，零返工**。
- **先做后查**的：卡面三条 → 每条都要「改 → 跑 → 看图 → 发现还不对 → 再查」→ **返工三轮**。

⇒ 差距不在能力，**在开工前查没查**。

## 三、已经成文的规矩（照这个做）

1. **卡面 / UI 这类「多层叠加」的东西，先做一张「层 × 场景 × 出现条件」的表再动手。**
   判据是表，不是截图。表里每格都要有出处（资产路径 / `文件:行号`），没出处的格子写「？」。
2. **PnP 是印刷品，不是数字版规格。** 内容可以用它当尺子；**版式与显隐规则不行**。
3. **加一层之前，先 grep 谁会遍历 `_layers`**，问「这一层的颜色/纹理谁说了算」。
4. **一个对象有多个出生/迁移入口时，分层这种状态要在每个入口显式设置，并各配一条断言。**
5. **改完卡面，至少抽一张真卡，和 PnP 成品图并排渲一次**（`CardFaceProbe` 已加 `Howling Banshee Exarch`）。
6. **动手之前先问一句「这件事全量反编译里怎么说」** —— 这是本项目最便宜的一步。

## 四、还没核完的（开放项，别当已解决）

| 项 | 卡在哪 |
|---|---|
| ✅ **放大窗立绘溢出 ×1.27 —— 2026-09-19 定案：不改** | **机制有据**（`bigSizeMultiplier = 1.2699999809265137`、`scaleTime = 0.3`，`MonoBehaviour_5393623139443973056.json`）· 但 **原版的默认是「不溢出」**：`CardImageController.currentState` 是**非序列化的 private 字段** ⇒ 运行时初值 = `default(ImageInFrameSize)` = **`Small (0)`**，只有 `CardDisplayWindow` 在 `rawCard.useOverDraw == true` 时才调 `SetImageOverDraw(Big)`。而 `useOverDraw` 挂在**卡资产**上（服务端）⇒ **本地判不出哪几张该溢出**。**字段存在本身就说明这是"少数卡的特例"** ⇒ 拿不到时**照默认（不溢出）**比"一律溢出"更接近原版。⚠️ 我们之前说的「一律 ×1.27 更接近原版」**是错的，已收回**。 |
| **手牌立绘要不要破框** | 同上：原版只有放大窗且只在 `useOverDraw` 为真时溢出 ⇒ **手牌不溢出**是默认。我们手牌现在有一点（`_artFront` + `ArtCoverMargin = 1.04`）。**未改**，记着。 |
| ⚠️ `CARD_IMAGE_CLAMP_RANGE_WHEN_SMALL/BIG` 的**字面值拿不到** | 它们是 il2cpp 元数据里的 `static readonly Vector4`，反编译只剩类 token、预制体里也没有 ⇒ **「立绘裁到哪个矩形」精确复刻不了**，只能用 fit + 现有余量近似。 |
| ⚠️ `CardImageScalebyCardTypeSO`（逐卡类型的立绘缩放）**不在本地** | 全量解包里 `*-ScalebyCardType*` / `*CardImageScale*` **零命中**。它是那份 `cardScales` 字段指向的 SO ⇒ **逐类型的立绘缩放也复刻不了**。 |
| **卡面还有哪些层没核过** | **没做过系统性盘点**。现在有的是零散的（底板/卡框/费用/数值/徽标/立绘各查过一次），差一张「层 → 出处 → 值」的总表 |
| ✅ 阵营行那条**推翻了用户 2026-09-17 的口述** | 用户 2026-09-19 裁定：**「一切根据原版，如果解包资料文件支持，那么就是我的意见错误」** ⇒ 按**代码**走（哪都不印），**不改回去**。 |
