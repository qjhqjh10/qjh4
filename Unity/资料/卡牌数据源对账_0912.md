### ✅ 稀有度这个 bug 已修（2026-09-12）

**症状**：我们的 `legendary` 有 **341 张**，而宝石表实测只有 **194 张** —— 明显偏多。
逐张比：**151 张冲突，其中 140 张是「我们记成 legendary、宝石实测是 common/rare/epic/special」**。

| 卡 | 我们（改前） | 卡面宝石实测 |
|---|---|---|
| Autarch | legendary | common |
| Night Spinner | legendary | common |
| Shining Spear | legendary | common |
| Ursula Creed | legendary | epic |
| Hornet / Night Spinner | legendary | rare / common |

**根因**（`工具/gen_cards_engine.py`）：判据写的是

```python
if rarity not in RARITIES:      # ← 只在 OCR 值是**非法串**（空串 / `defence`）时才查宝石表
```

—— 把**权威来源当补丁用**。OCR 写错但「看起来合法」的值（`legendary`）原样放行。
而这个脚本自己的文档字符串里白纸黑字写着宝石表「**是唯一的权威来源**」：
**代码没实现它声明的意图**。

**怎么确认的**（不是靠推理，是看卡面）：
`D:/2/Warpforge部队卡片/Aeldari/3部队/Warpforge_08_Night-Spinner.png` 与
`…/Warpforge_03_Shining-Spear.png` —— 卡面**底部那颗菱形宝石都是浅蓝（= common）**。

**怎么修的**：改成**只要宝石表里有这张卡就用它**（`got, how = rarity_lookup(name)` 提到最前）。
重跑后 474 张定档，分布变成
`common=313 / rare=320 / epic=229 / legendary=197 / special=48 / 空=22`
（宝石表自己的分布是 rare=328 / common=312 / epic=235 / legendary=194 / special=48 —— 基本吻合）。

**影响面不止显示**：`DeckRules.CopyLimit` 按稀有度定**同名牌上限**（传说 1 张、其余 2 张），
所以这 140 张的**组卡规则**一直是错的。已加断言（`RuleEngineTest.cs` 的 `TestOriginalCardPool` ⑤，
四张对过卡面的卡 + 传说总数上限）钉住。

**还差的**：宝石表里也没有的 **22 张**（`Medic Scion` / `Commissar Elan` / `Lord Kakophonist`…），
以及 6 张靠**模糊匹配**补上的（`Helfire Pit` / `Land Rider` / `Sisters Repentia`…，脚本会列出来建议抽查）。

### ✅ 同一天修掉的第二个稀有度 bug：**重名卡互相覆盖**（3 张）

宝石表**按卡名查**，同名不同卡时**后写的赢**。1118 行里有 5 个卡名重复，
其中 **3 个两行稀有度不同** —— 也就是说这 3 张一直在取另一张卡的值：

| 卡名 | 宝石表两行 | 我们（改前） | 实为 |
|---|---|---|---|
| `Terminator Champion` | 批次 C = common / 批次 E = epic | BlackLegion 拿了 epic | BlackLegion = **common** |
| `Maulerfiend` | 批次 C = epic / 批次 E = common | BlackLegion 拿了 common | BlackLegion = **epic** |
| `Bladeguard Veteran` | 批次 D = rare / 批次 U = common | DarkAngels 拿了 common | DarkAngels = **rare** |

**怎么定的**（两条独立证据，互相印证）：
1. **批次 → 阵营**：把每批次的卡名拿回卡池查阵营投票 →
   `C=BlackLegion`(73/76) · `D=DarkAngels`(75/75) · `E=EmperorsChildren`(59/59) · `U=Ultramarines`(130/131)
2. **开图看卡面宝石**（三张逐一核过）：

| 卡面文件 | 图上宝石 | 结论 |
|---|---|---|
| `Chaos/3部队/Warpforge_44_Terminator-Champion.png`（图上是 Black Legion） | 浅蓝 | common |
| `Chaos/3部队/Warpforge_46_Maulerfiend.png`（Black Legion） | **紫** | epic |
| `Dark Angels/3部队/Warpforge_26_Bladeguard-Veteran.png` | **绿** | rare |

⚠️ 顺带一条**文档自己的错**：`卡牌完整信息库_0824.md` L288 把 Dark Angels 的 Bladeguard Veteran
记成「浅蓝[common]」，**卡面是绿的（rare）** —— 宝石表对、文档错。
（`card_stats.json` 里这张的 OCR 值本来就是 `rare`，是我们查表把它覆盖错了。）

修法：`gen_cards_engine.py` 加 `RARITY_BY_FACTION` 表，按「阵营 + 卡名」特判。
修后分布 `common=312 / rare=321 / epic=229 / legendary=197 / special=48`，
与宝石表自己的分布（rare=328 / common=312 / epic=235 / legendary=194 / special=48）几乎重合。
**根子还是「卡名当 id」**（`项目任务.md:727` 记过同一件事），真要治本得给卡发稳定 id。

## 四、🔴 更正：子代理说「文档有『甲』列、我们没有 armour」—— **这条是误读**

那份表的列头写的是「甲」，但**实测值是远程攻击**（`ranged`），不是护甲：

| 卡 | 文档 `费用\|攻\|甲\|血` | 我们 `cost/attack/ranged/health` |
|---|---|---|
| Dire Avenger | 4 \| 2 \| **4** \| 4 | 4 / 2 / **4** / 4 ✓ |
| Terminator Champion | 6 \| 6 \| **5** \| 6 | 6 / 6 / **5** / 6 ✓ |
| Tactical Marine | 2 \| 2 \| **2** \| 3 | 2 / 2 / **2** / 3 ✓ |
| Wave Serpent | 7 \| 3 \| **6** \| 8 | 7 / 3 / **6** / 8 ✓ |

四张逐值相等 —— **那一列是远程攻击**，我们早就有（`cards_engine.json` 的 `ranged`）。

**护甲另有来源、而且我们已经实现**：它是**关键词**（`Armour 1` / `Armour 3`），
值取整串第一个数字（`CardDef.cs:145`/`:264`，和 `rule_core` 同一套规则）→
`UnitState.Armor = KwValue("armour")`（`UnitState.cs:49`）→ 减伤 `max(1, dmg - Armor)`（`RuleCore.cs:386`）。

> ⚠️ 这条印证了工作准则第 3 条：**只看列头不看值会认错**。列头是别人写的，值是数据。
