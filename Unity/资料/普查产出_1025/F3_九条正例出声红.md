# F3 —— `RuleEngineTest.Run` 九条「正例出声」红（2026-10-25 · 第七十五会话）

**结论先行：九条**全部是 **α 类（夹具缺口）**，**不是**生产回归，**也不是**计数器口径问题。
一个字都没在断言上动（⛔ 没改松），改的是三个夹具构造函数里**缺的一格 `conditionsVersioned: true`**。

**根因（一句话）**：`E9` 今天把 `TargetCriteriaEval.Matches` 的**第 ⑧ 步**
（`conditionsFilter` / `excludeCondition`，`FilterMethods__CheckIfMeetsCriteria.c:298-303`）接上了，
而第 ⑧ 步的 `cond` 形参由 `ActionPump.AbilityLevelConditionRow` 拼：
**`Card.ConditionsVersioned == false`（`CardDef` 构造缺省）⇒ 送一个
`Condition = ConditionUnknown(-1)` 的哨兵** ⇒ `ConditionEval.MeetsUnit(…, -1, …)` 回 `null`
⇒ `Matches` 在第 ⑧ 步 `return null` ⇒ 闸走「**判不了 ⇒ 放行 + 出声**」那一支
⇒ `AbilityLevelCriteriaWarningsForTest` / `AbilityActingCriteriaWarningsForTest` **各 +1**。

E2 / E3 / E6 三个夹具造的都是**合成卡**，从来没给过 `conditionsVersioned`
（`CardDef` 那个形参缺省 `false`）⇒ **每一个 `ta = 10 allFiltered` 的正例**都撞上这一步。
**真卡池不会**：`CardDatabase.Parse` 写的是 `conditionsVersioned: dto.version >= 15`，
现读卡表 v27 ⇒ 全池 `true`，第 ⑧ 步 `cond == null` ⇒ `c = ConditionNone(0)` ⇒
`ConditionEval.Match` 的 `case 0: return true`（`ConditionEval.cs:192-193`）⇒ **静默放行**。

**为什么排除 β / γ**：

- **不是 β（生产多打）**：同一次调用里 `Matches` 在**前 7 步全过**（否则会走 `verdict == false`
  那支、正例断言本身会红），所以 `cond` 是它唯一回 `null` 的地方；而 `cond` 为 `null`（真卡路径）
  时第 ⑧ 步恒真（`case 0 → true`）。⇒ 生产代码对真卡**零行为变化**。
- **不是 γ（计数口径）**：`AbilityLevelCriteriaWarningsForTest` 与
  `AbilityActingCriteriaWarningsForTest` 两个计数是**分开**的，而 #4/#5 是**各 +1** ——
  并口不会有这种现象；且警告文案点名了 `cond=-1`。
- **也不是「断言没清零」那种 α**：九条**全部**用的是**相对增量**
  （`int warn0 = …; Check(…, warn0, …)` 或 `Check(… - l0, 0, …)`），已经在用例开头取过基线了
  ⇒ 所以**不需要**加 `Reset…ForTest()`。

## 四、顺手发现（⛔ 我没动，请主对话排）

1. 🔴 **同一缺口在 E4 / E8 也在，但那边现在是「弱绿」**（日志里另外 **6 条** `cond=-1` 就是它们）：
   - `E4PickA` / `E4PickB` / `E4PickC`（`RuleEngineTest_EngineE4.cs` 的 `E4AbilityCard`，`:109`）
   - `E8bFriendly` / `E8bEnemy` / `E8bAny` / `E8bAny2` / `E8bSelfAlly`（`E8bAbilityCard`，`:53`）
   - `E8bLOk`（`E8bListener`，`:95`）—— 🔴 **这一条最值得改**：`⑦b 放行 ⇒ 恰好 1 条 Trigger`
     现在是靠「**判不了 ⇒ 放行**」绿过去的，不是「**满足 ⇒ 放行**」；改了才是真判别式。
   - **同一处一行改法**（`conditionsVersioned: true`）。我已逐条核过：这三个夹具的
     **所有** warn 计数断言（`E4:338/353`、`E8:236/293`）走的都是 ⑧ 步**之前**的分支
     ⇒ 改了不会翻红。**但我没有 Unity 可验，且这三个文件不在我这份简报的 9 条范围内**，故留给你派单。
2. ⚠️ **`cond=-1` 这句警告对排查的人不友好**：它只说「`条件 cond=-1` 判不了」，
   没说是**为什么**（真实原因 100% 是「卡表 < v15、`ConditionOf` 回 `Unknown`」）。
   建议把这句的来源标出来（`AbilityLevelConditionRow` 送哨兵时**没有**任何 why 字段可带，
   `TargetCriteriaEval` 只能打 `cond={c}`）。要么给 `ConditionSpec` 加一格 `Why`，
   要么在 `Matches` 的第 ⑧ 步 `gap` 里加一句「（`-1` = 卡表 < v15 / 这一列没落）」。**只是可读性，不是缺陷。**
3. ℹ️ `RuleEngineTest_EngineE7.cs`（四道闸 ward / wardWb / summitRift / tainted）与
   `_EngineE1.cs` 的夹具**都没走 ability 级闸**，本轮零影响。
