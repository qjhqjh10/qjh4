## 七 · 顺手发现（按铁律 5 就地订正了两份普查报告）

1. 🔴 **`E2` 报告对 `Damaged(60)` 的 `targetCard` 读错了**（**已就地订正**，`E2_ability_criteria管线.md` §三·2 表格加了一行订正）：
   原文「`Damaged` 的 `targetCard` 是 `ResolveDamageDealt` 的 `param_2`（**伤害来源**）」——
   `CardScript__ResolveDamageDealt(param_1 = 观察者, param_2 = **被打的那张**, param_3 = DamageInfo)`
   （`BattleManagerSupport__BroadcastUnitDamaged.c:19` 对被打者自己调 `(param_2, param_2, param_3)`、
   `:59/:70/:82` 对每张在场卡调 `(lVar3, param_2, param_3)`），而 `:161-163` 是
   `OnTrigger(0x3c, …, thisCard=param_1, actingCard=DamageInfo.actingCard, targetCard=**param_2 = 被打者**)`。
   ⇒ `targetCard` = **被打者**（= 我们的 `subject`），**那一格可以接**；真正缺的是 `actingCard`（伤源）。
   ⛔ 别再把这条当「拿 `subject` 顶就是筛错人」。（这也让 `BL8` 的 `friendlyUnits=1/includeHero=1/
   includeMinions=0` = 「友方督军」与卡面「When your Warlord receives damage」对上了。）
2. 🔴 **`E4` 报告有两处被证伪**（**已就地订正**，`E4_trigger目标与activeAbility目标池.md` §二·4·1 / §五·3 / 「仍开」#1）：
   `AM69` 的 criteria 例子（→ 见 §三）· 「`SW9` 那行是 logic 级、不是同一格」（→ 见 §一）。
3. **`TargetCriteriaEval.Matches` 的 `cond == null` 只有一个含义**（「明确没有条件」）—— 想在
   「列没落 = 未知」时说「判不了」，只能**造一个 `Condition = -1` 的哨兵**走下去（本批就是这么做的）。
   建议把这条口径写进 `Matches` 的 doc（本批没改它的注释，怕与别的写手撞文件）。
4. **`ResolveTarget` 的 `EnemyUnit` 支原来会把「显式选中的督军」静默换掉**（§二·3）—— 这是**先于本批**
   的缺陷，只是没有卡走到（`Ability:` 0 张）。同类风险：`FireTriggerDeferred` 那条 `ResolveEffect(...,
   chosen)`（`RuleCore.cs:11412`）的 `chosen` 来自 `FireTriggerAt`，今天不是督军；若将来有触发把督军当
   `chosen` 传，旧代码同样会换掉（本批同一句修复已覆盖）。
5. **`gen_cards_engine.py` 的 `chosenAbility` 只落在 `activeAbility` 那一支**（v24 的 `ca`）——
   `cardAbilities[].abilityLogic[].chosenAbility` **全池没有列**。这是 E5-4 第 1 件的硬前置，
   也是 `E2` §三·3「op ↔ ability 下标」之外**另一条**能用来配 op 的线索（380 这类「系统动作」比正文文字更确定）。
6. `AbilityActingGateCard` / `AbilityLevelGateTarget` 现在都是「只认两个事件」的 switch
   （`EffectResolver.cs:6920/6963`），§五 那张表把它们**逐族**列了出来 —— 下一批照着加分支即可。
