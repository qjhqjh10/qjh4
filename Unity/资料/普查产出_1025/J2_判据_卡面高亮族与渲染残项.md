### A2 两个常量：`DAT_1834b3178` = **0.15f**；`originalSize` 是**惰性捕获**，不在 `Start`

- **判据结论**
  - **`DAT_1834b3178 = 0.15f`** —— 两条独立证据：① `read_literal.py` 读 `D:/2/unity_run_ref/GameAssembly.dll` 4 字节 = `0.15`
    （8 字节读 = 1.955e-08，明显是错宽度）；② `dump.cs:38853` 的 `private const float scaleTime = 0.15;`。两者逐位一致。
  - **`originalSize`（+0x48）赋值时机 = 惰性，`HighlightIfNeeded` 与 `get_TargetScale` 各自开头**，条件 = 它当前仍
    ≈ `Vector3.zero`（距离² < `DAT_1834b2ba8`）。**没有 `Start` / `Awake`** —— `dump.cs:38871-38877` 的方法表只有
    `get_TargetScale` / `HighlightIfNeeded` / `.ctor` 三个。
    - `get_TargetScale` 那一支更狠：命中「≈0」时**同时**刷新 `originalSize`(+0x48) 与 `targetScale`(+0x3C)（`HighlightAttackType__get_TargetScale.c:27-39`）。
    - ⇒ 语义 = 「第一次被调用时，把**当刻**的 `textCounter.localScale` 记成基准」，之后只在基准仍是 0 时才重记。
      ⚠️ 推论：如果某颗数值 TMP 的初始 scale 真的是 0（被隐藏的档），它每次调用都会重记 —— 原版没管这个边界。
  - **`DAT_1834b2ba8 = 1e-10f`**（`read_literal.py` 4 字节；= (1e-5)²，全项目「向量是否近似相等」的同一个常量）——
    旁证：`NetworkingPeer__AlmostEquals.c` · `CardScript__AlreadyInPosition.c:44` · `CombatCameraZoom__ClampShiftLimits.c:52` 都是
    `< DAT_1834b2ba8` 的平方距离判据（工具会把它标成「不像字面量」，那是启发式误报）。
  - **比较对象 = `Vector3.zero`**：那段代码读的是 `UnityEngine.Vector3` 类的静态字段区首项（`DAT_1842da2a8 + 0xb8` 的 `+0x00`）。
    证据链（不是猜）：同一个静态区在 `MoveByKeys__FixedUpdate.c:44-46` 被读 `+0x3c/+0x44` = **`Vector3.right`**（静态字段 index 5 × 12 B），
    首项 index 0 即 `zeroVector`。⇒ 「基准还等于零」就是「还没捕获过」。
  - 顺带核准（同批读的）：**`DAT_1834b2dc8 = 0.3f`**（选择器用，W3 已记，本轮复读一致）。

### B5 「矩形外 α 更不透明」—— **判据结论：不需要改；`ArtOpaque` 与原版逐像素等价（不是近似）**

- **判据结论**
  1. **原版那条公式是加法、不是裁切**（`X1 §一` 已用 DXBC 坐实）：
     `alpha = saturate(texAlpha + inside01)`，`inside01 = (0.18 < u ≤ 0.82 && v > 0) ? 1 : 0`（u/v = **sprite 的 UV**）。
     ⇒ 矩形内**强制不透明**，矩形外**保留贴图 alpha**。它从来不会切掉插图。
  2. **为什么这条对我们等价于 `ArtOpaque`（α≡1）** —— 两条独立的理由，各自都成立：
     - **立绘层的贴图 alpha 是「角色抠图」，不是页面 alpha**：`Shaders/ArtOpaque.shader` 头部与 `CardPresentation` 注释实测
       「单位卡 91–97% 是透明的」。把这一层改成「保留贴图 alpha」会把整幅立绘透出卡框底色 ——
       这正是 2026-10-21 真机缺陷「聊天头像被底板挡住」的成因（`Battle/UnitChatPanel.cs:614-630` 已按这个理由选了 `ArtOpaque`）。
     - **对整页 sprite（tactic/defence/1 张督军）实测：矩形外 alpha 就是 255**。本轮全量扫 `Resources/Art/cards/art_*.png`
       的 496 张方图：**窗口外一个非不透明像素都没有的 422 张**；剩下的 74 张窗口外只有 ≤ **3441 px**（占页面 0.9%，
       即一两像素的边缘编码毛刺）。⇒ `saturate(255 + x) = 1` ≡ `ArtOpaque`。
     - 单位卡的裁块（670×1024）在**原版**里是「图集里的子矩形」（`m_RD.textureRect = {x:176.5, w:670.5}` ⇒ 页内 u 0.172–0.827），
       而 uGUI `Image` 的 UV 取的是 `sprite.uv`（**图集坐标**，不是 sprite 局部 0..1）⇒ 它采到的 u 永远落在窗口内 ⇒ `inside01 ≡ 1`。
       （⚠️ 这一条是**推断**：前半「textureRect = 0.172–0.827」是实据，后半「uGUI 用图集坐标」是 uGUI 的既有语义、本轮没再反编译核对一遍。）
       ⇒ 原版那一档**也**是 α≡1。⇒ 两种 sprite 形制都等价。
  3. **该改成什么**：**什么都不用改**。若将来为了「形式对齐」仍想加，唯一做法 = 在 `Shaders/ArtOpaque.shader` 增一个 `_ClampRange`
     属性 + `c.a = saturate(c.a + inside01)`（**默认 `_ClampRange` 让 inside 恒 1 ⇒ 现有调用点行为逐位不变**）；
     ⛔ **不要**在 `CardView` 那一侧改（材质/shader 是唯一能表达「逐像素 α」的地方）。
  4. **会不会影响其它卡型**：会，**而且方向是坏的** —— `ArtOpaque` 现在还被 `Battle/UnitChatPanel.cs:627`（聊天头像）与
     卡面立绘底层共用；一旦改成「保留贴图 alpha」，聊天头像立刻退回「透底板」那条已修缺陷。所以这条**不建议动**。

- **状态 → 参数**

  | 卡型 / sprite 形制 | 原版矩形内 | 原版矩形外 | 我们（`ArtOpaque`） | 差 |
  |---|---|---|---|---|
  | 单位卡（裁块 sprite，UV 本身在窗内） | α=1 | 采不到（UV 不落在窗外） | α=1 | **0** |
  | 战术/防御（整页 1024²/512² sprite） | α=1 | = 贴图 α（实测 255） | α=1 | **0**（74/496 张 ≤0.9% 边缘像素） |
  | 聊天头像（同 `Card Image Overflow`） | α=1（窗内） | 贴图 α | α=1 | 未逐张量（见「还差什么」） |

- **还差什么**：① 建议主对话把 `X1 §一·5` 那句「我们比原版更不透明」**订正**成「在可见范围上等价（单位卡 UV 不落窗外；整页 sprite 窗外 α 实测 255）」；
  ② 聊天头像那一格（`Challenge`/`Daimyo` 头像 sprite）**没逐张量** —— 若哪天有人发现头像四周多出一块实色，回到本条查（贴图 α vs `ArtOpaque`）。
