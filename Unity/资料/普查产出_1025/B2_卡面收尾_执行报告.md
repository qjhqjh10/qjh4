## 二、B2-2 `Editor/CardFactionProbe.cs:452` 的静默兜底 —— **已改**

### 2·1 问题（B 的报告 §1·5·1 已认定，本轮复核成立）

`OurFrameRect` 原来只遍历 `FaceLayerRoot`（`2DCard`）的**直接子件**找 `"frame"`。`M2` 之后
`frame` 挂在 `2DCard/Front` 下（孙件）⇒ 永远找不到 ⇒ `return false` ⇒ 调用方静默走
`FrameQuadCrop()`（结果错）。

### 2·2 改法

- **下钻规则与 `CardView.ApplyBoardSortingOrders` 同一条**：`FaceRoot` 的直接子件里碰到
  `FaceContentRoot`（= `Front`）要再往下走一层。实现 = 用 `view.FaceContentRoot` 当「层所在的那一级」。
- **两圈都临时关掉再还原**：① `2DCard` 下**除 `Front` 以外**的直接子件（数值层 `stat0..3` / 徽标 /
  状态环 —— 它们按原版语义**不搬进 `Front`**）；② `Front` 下**除 `frame` 以外**的层。
  ⚠️ 只改 `face` → `content` 而不管第 ① 圈的话，数值/徽标会混进这张「只有卡框」的渲图 ⇒ 卡体矩形量歪。
  两圈都在 `finally` 里**按原值还原**（含原本就关着的）。
- **不许静默**：`FaceLayerRoot == null`、`FaceContentRoot == null`、以及**找不到 `frame`** 三种情况
  各打一条 `Debug.LogWarning`，最后那条会**把 `Front` 下所有层名列出来**（下一个人一眼看出层名变了）。
  调用方原本就有一条 warning（「量不到 ⇒ 退回 `FrameQuadSize` 矩形」），现在会**两条一起出现**，
  不会再「悄悄换个算法继续跑」。
- 顺手（同一文件、白名单内）：`FrameQuadCrop()` 的兜底矩形补了 `+ CardView.FrontAposY` ——
  `FrameQuadSize.z`（= `FrameUnitY` = −0.03）是**原版 `Front` 局部值**，不补的话这条兜底会整体低
  0.08 卡单位（≈2.4% 卡高）。判据同 `CardView.FrontAposY` 那段。

## 三、B2-3 异画（1024²）的 UV 映射核对 —— **核清了：不是「异画」，是「整页方图」；确实偏，已落代码**

### 3·1 先纠正 B 的顺手发现（铁律 5）

B 写的是「**496/1168 张是 1024²（哈希名 = 异画）**」。**一半对一半错**：

| B 的说法 | 实测（本轮现读） |
|---|---|
| 496 张是 1024² | 尺寸对：`1024²×495 · 512²×1 · 671×1024×671 · 670×1024×1`（合计 1168） |
| 「哈希名 = 异画」 | **不成立**：495 张里只有 **124** 张是 32 位哈希名，另外 371 张是正常卡 id（`art_am39`…） |
| 它们「异画」 | **不是**。真正的督军异画是另一条通道 `Resources/Art/altarts/alt_<id>.png`，**7 张，全是 671×1024** ⇒ **走同一套常量、没有偏差** |

**那 496 张到底是什么**：它们的**原版 sprite `m_RD.textureRect` 就是整页**（不是裁块）。
现读判据（不是推算）：

- `bundle_astramilitarumcardassets_assets_all/Sprite/AstraMilitarum_strat_Born Soldier.json`
  → `m_RD.textureRect = {x:0, y:0, w:1024, h:1024}`（同目录 `Texture2D/…png` 也是 1024²）；
- `bundle_orksgoffcardassets_assets_all/Sprite/Ork_Goff_strat_Uge Choppa.json`
  → `{0,0,512,512}`（纹理 512²）；
- 对照组：`…/AstraMilitarum_warlord_Lord Solar Leontus.json` → `{x:176.5, y:0, w:670.5, h:1024}`。
- **全量普查**（13 个 `bundle_*cardassets*/Sprite`）：`670.5×1024` **657 个** · `1024×1024` **548 个**
  ⇒ 这是**原版数据里真实存在的两种 sprite 形制**，不是导出 bug。
- **和卡类型完全对应**（我们的 1168 张按 `cards_engine.json` 的 `type` 分）：
  `tactic` **445 张全方图** · `defence` **39 张全方图** · `unit` **586 张全是裁块** ·
  `hero` 55 张裁块 + **1 张方图**（`SW2 Njal Stormcaller`）。

### 3·2 偏差是怎么来的（结论：确实偏，而且偏得很大）

- 原版只做一句 `material.SetTexture(_CardImage, rawCard.cardSprite.texture)`
  （`d:/2/tools/decomp_full/BattleCardUI__SetCardImageTo3DBase.c`，逐行读过）⇒ 喂的是**整页**；
  采样坐标 = mesh 第二套 UV（UV1，**写死在网格上**，正面 0.1818–0.8203 × 0.0017–0.9978）。
  ⇒ **原版对任何卡都只采页上那一窗。**
- 我们的 PNG 有两种：裁块（670.5/1024 宽的那块）、整页（1024² / 512²）。
  原来那组写死的常量是按**裁块**推的 ⇒ 对整页那 496 张，等于把**整页都铺上去**：
  左右各多采 18%（窗从 0.6385 页宽变成 0.9752 页宽）⇒ **立绘被横向压扁约 36%**。
- **旁证（很硬）**：场上卡溶解用的是**原版 shader** `Everguild/Cards/3D Card Dissolve`
  （`CardView.cs:5737` 那段），它照旧直采 UV1 ⇒ 它本来就"对"。也就是说：**只有我们自写的
  `Card3D` 那一份是偏的** —— 这不是我新加的假设，是既有代码里就有的一处自相矛盾。

### 3·3 落地的做法（按「每张图的来源算 UV」，不是打两张常量表的补丁）

- **`Core/CardArt.cs` 新增唯一实现**：`ArtUvRect(Texture2D)` → `Vector4`（xy=min / zw=max），两支：
  - `|w−h| ≤ 1`（**方图 = 整页**）→ 原版窗原样 `(0.1818, 0.0017, 0.8203, 0.9978)`；
  - 否则（**sprite 裁块**）→ 原版窗 + 四边 3~5 px 余量 = §1·2 那组。
  判别式为什么成立：当前 1168 张只有四种尺寸，方图 ⇔ 纹理被整页导出；而裁块的纹理是 671/670 宽
  ⇒ 不可能被误判成方图（NPOT 缩放也只到 512，仍非方）。**判据/算式/两种来源的 JSON 证据全写在该函数
  头顶那段注释里（唯一出处）**，并配了 `CardBaseDemo` ①·d 的尺寸普查断言兜住「出现第三种形状」。
- **`Core/CardView.cs`**：新增 `ArtUvRectProp = "_ArtUvRect"` + `ApplyArtUvRect(m, tex)`；
  写入点两处，正好覆盖全部出生/换图入口：
  `BuildBody3D`（建体时）· `SetCardImageTo3DBase`（`SetData` / `SetCardMaterial` /
  `RestoreOriginalMaterial` / `SetAmbush` 四条路最后都走到它，判据注释原本就写着「判据只此一处」）。
  ⚠️ 伏击图（`GenestealerCults_special_Ambush.png`，1024²）也走同一个口 ⇒ 同样按方图那支算，
  这与原版一致（原版那道闸换的也是同一个 `_CardImage` 槽、同一套 UV1）。
- **`Shaders/Card3D.shader`**：`lerp(_ArtUvRect.xy, _ArtUvRect.zw, artT)`（见 §1·4）。
- **`Editor/CardBaseDemo.cs`**：①·a / ①·c / ①·d / ①·e 四条断言（见 §1·4）。

### 3·4 没做的事 / 为什么
