### 1·3 那 546 条为什么升不了（这是 R28 的核心结论）

- **`inferred-keyword` 528 条**：它们的真判据是 **`CardTrait` SO 的 `TraitEffects[].effectAnim`**，
  而这份 SO **两个 build 的本地资源里都没有**：
  · `guid_map_bundles.tsv`（枚举 84 个本地束的 `m_Container`）里 `className == CardTrait` **0 行**；
  · `d:/2/新解包资源/assets_full/**` 全库 grep `_traitEffects` / `TraitEffects` **0 命中**；
  · 安卓 1.35.0 `UnityDataAssetPack.apk` 的 84 个 bundle 里**没有 `cardtraits` 束**；
  · `card_raw.json` 的 `CardTraits` 是**内联结构**（`name` + 枚举 id），**不是指向 SO 的 PPtr**
    ⇒ 也无法从卡 SO 反查。
  ⇒ **判据空**（⛔ 不是「没查」、也⛔ 不是「按名字能配」）。
- **`inferred-name` 18 条**：卡 SO 的 116 个字段（含全部 `m_AssetGUID`）**逐条扫过**，没有任何一条指向该 prefab
  —— 纯属「卡名是动画名前缀」的巧合（例 `AM30 Artillery Manticore down 1x`）。
  ⚠️ 其中 42 条 `_unclassified` 本来就不是事件（`VfxMap` 的 `events` 里没有这个键），**运行时不可达**。

## ③ 没查清 / 只能记「判据缺」的部分

1. **`conflict_event` 那 34 条到底该不该播** —— SO 证明了「同一动画属于事件 X」，但**不能证明原版不在事件 Y 也播它**
   （那条支路在缺失的 `CardTrait` SO 里）。⇒ **保留未删**，逐条列在附录；要裁得先有 `CardTrait` SO。
2. **`inferred-keyword` 的 528 条** —— 判据 SO 两个 build 都没有（见 1·3）。**这是 R28 真正的「判据空」**，不是本批能解的。
3. **`alternativeAbility` 只有 1 条非空引用**（`SW21 Wulfen Pack Leader`，GUID `945014349c7e3cd4b93922bafe782387`）——
   **它和该卡的 `activeAbility` 是同一个 GUID**（`Cut Wulfen`）。把它加进 `so_refs` 会在 `ability` 造**第二条 authoritative**，
   而 `VfxMap` 对同档多条的规则是**全播** ⇒ **会播两遍**。⇒ **故意不加**；SW21 的那条动画已由 `activeAbility` 覆盖。
4. **`hit` / `attack_melee` 两族的推断条目** —— `VfxMap` 2026-10-23（`W63`）已把 **authoritative** 的这两族搬到
   `UnitAttack` 桶（`Core/VfxMap.cs` 那段注释），但**推断档留在旧桶**（注释原话「它们不是 `UnitAttack(50)` 触发的」）。
   推断档该不该跟着搬 = **消费侧口径**，`VfxMap.cs` 不在本代理白名单 ⇒ 未动、如实登记。
5. **卡 SO 里另外几族「逐卡资产」没进 `_assetRefs`**（**不在 R28 口径内**，只记不猜）：
   `defaultChatSound` 等 10 个聊天语音字段（各 64–66 条非空）· `customIntroChatData[].customSound`（55）·
   `customIntroByArmyChatData[].customSound`（15）· `fullHeroSpriteReference`（65，立绘）。要不要收 = 另立账。

## ⑤ 顺手发现（只报不改）

1. **生成器产物里两处过期话术**（已在本次一并订正，属铁律 5）：
   `_headline` 与 `hop2.limits[0]` 仍写「真值快照是 **2022 时代**（1,195 张）、我们 168 张查不到」——
   `T14`（2026-10-18）换源后现读是 **1,351 张 / 池内 1,127 张缺 0**。产物是给工具/下个会话读的，留着会误导。
2. **`EC57` 的 `summonAudio` 指向一条 UM 语音**：GUID `6a6fb8c37ab200c469bcc799c5dbd57b` → `VO_UM_Primaris Intercessor - For the Imperium`
   （UM 卡束）。**guid_map 与 catalog 两条判据一致** ⇒ **原版 SO 自己就这么写**（大概是占位），不是我们的映射错；
   照原版保留（我们按卡 SO 播，这是「照原版」）。
3. **`guid_map_bundles.tsv` 的结构性缺口**：它只枚举各束的 `m_Container`，而**短键束**（EC 卡束键是 `71`/`49`/`0a`…）
   的「GUID ↔ 短键」这一跳**只有 catalog 有**。本次没改那张表（不在白名单），而是在生成器里加了第二判据；
   若将来要根治，可让 `gen_guid_map_from_bundles.py` 吃 catalog 的 `internalId` 列（**建议，未做**）。
4. **运行时精确语音有 1 条文件缺失**（既有、非本轮引入）：`VO_UM_Firestrike Servoturret - Battlefields are filled with the remains of the obstinate`
   —— 生成器每次跑都会出声（`:1210` 附近那一段）。源包里也缺 ⇒ `import_original_audio.py` 也补不出来。
5. **`stats.authoritative.guidMapGuids` 保持 6,140（不含兜底补进来的 2 个）** —— 有意为之：它报的是「表本身的体量」，
   兜底解出的另计 `resolvedByCatalogGuids`，两个数各说一件事，⛔ 别合并。
