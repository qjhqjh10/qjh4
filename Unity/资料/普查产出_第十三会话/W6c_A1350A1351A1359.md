### 一、`A1350` 第①步 —— `MainMenuScene.QuadPxRect` 转调共用件

- **改了什么**：`Editor/MainMenuScene.cs:12231`（函数体，原 `:12215`）——
  `static bool QuadPxRect(ImageQuad q, out float x1, out float y1, out float x2, out float y2)`
  的函数体由**甲式**
  （`q.WorldW * 108f` ＋ `LayoutSpace.PxX(q.transform.position.x)` / `PxY(...)`）
  换成**一行转调** `MenuDraw.QuadRectPx(q, out x1, out y1, out x2, out y2)`（乙式）。
  文件头加了 `:12216-12230` 的 doc（改动理由 + 两式差在哪 + 同文件 `RenderedRect` 本次不动的声明）。
  **函数名 / 形参 / 返回契约一个字没改** ⇒ 同文件那 **7 个调用点**（`:11222` `:11557` `:11581/82` `:12235`
  `:12296` `:12303`）**一个都不用动**（`MenuDraw.QuadRectPx` 的 `out` 重载契约逐字相同：
  `q == null` ⇒ 四个 out 归 0、返回 `false`）。
- **为什么**：铁律「两处写同一条规则 = 迟早不一致」；`R6` 的 `A1350` 表第 1 行判「要收，成本最低」。
- **等价性论证（静态）**：
  - **y 中心项**：乙式 `PixelOfDesign(PosInDesignSpace(t))` → `LayoutSpace.ToDesignPixel`，其 **y 那一半直接转调
    `LayoutSpace.PxY`**（`Shell/MenuDraw.cs:615` 自述）＝ 甲式的 `LayoutSpace.PxY(t.position.y)`；而
    `PosInDesignSpace` 的除法在**父链单位缩放**下是恒等 ⇒ **逐位相同**。
  - **尺寸项**：甲式 `WorldW × 108f`；乙式 `WorldW × K`，`K = LayoutSpace.DesignPxH / DesignHeight = 1080/10 = 108`
    ⇒ **同一个数**。
  - **x 中心项**：甲式写死 108；乙式走**实测** `PxPerWorldX`（`DesignPxW / VisibleWidth`，16:9 实得 107.99999）
    ⇒ **差 ≤ 2.5e-4 px**（`R6` 实算）。⚠️ **不是「逐位不变」**，措辞照 `R6`。
  - **非 16:9 / 父链带缩放**：两式**才**分家（乙式除回设计帧、x 用实测斜率）—— 那是本条要收掉的**潜伏差**。
    本宿主自检把 `cam.aspect` 钉成 `DesignAspect`、父链单位缩放 ⇒ **今天零可观测差异**。
- **该补什么断言**：
  - **夹具**：沿用宿主已有的探针节点（同文件 `A781` 那处已经在临时节点上 `AddComponent<ViewportClip>()`，`:11230`）。
  - **输入 / 期望**：① 既有那几条（`:11222` A781 图、`:11557/11581` 导航图标，期望值是**字面量 + 0.5px 容差**）
    照旧绿 —— 它们现在跑的就是转调后的口；② 新增：在**父链 `localScale = 2` 的探针节点**上建一颗 quad，
    断 `QuadPxRect` 报的仍是**设计矩形**（容差 0.01px）。
  - 🔴 **灭自证那一半**：② 就是那一半 —— **旧实现（甲式）在这条上必红**（它的中心项用的是**已缩放**的

    `q.transform.position`（世界量）与**设计矩形字面量**，两者不是同一处代码。

- **为什么**：铁律 11（与原版不符 ⇒ 要收）；`R6` 顺手发现 3 的判据。
- **等价性 / 行为论证（静态，逐条）**：
  1. **本仓九宫格的三块 = 三个「一块 quad + 一段固定 uv 被拉伸」（`ImageQuad.CreateNineSlice` 建完即
     `SetUvRect`；上下 `border = 0` ⇒ 行 0/2 宽高为 0、创建时被跳过，只剩 `_01/_11/_21`）。**
  2. **「把这颗 quad 横向缩到 s 倍」≡「把它按 `s × WorldW` 重建」** —— 网格顶点在**局部空间** ±`WorldW/2`，
     渲染时由 `localToWorld` 乘上去；uv 是**逐顶点**的、缩放不改它 ⇒ **世界空间的三角形与 uv 插值逐点相同**
     ⇒ **像素一致**（不是「近似」）。⇒ 用 `localScale.x` 就不必每次拖动销毁/重建 9 个节点（那是旧注里
     「太吵」的那个顾虑），而语义与「按目标宽重建」等价。
  3. **摆位**：`总宽 total = t × 轨道宽`；左端帽 `[left, left+cap]`、中段 `[left+cap, left+total−cap]`、
     右端帽 `[left+total−cap, left+total]`（`left = −轨道宽/2` 恒不动）⇒ **无缝无叠**，与 uGUI
     `GenerateSlicedSprite` 在 `anchorMax = (value,1)` 下的格位逐一对应。
  4. **退化**：`总宽 < 两端端帽之和` ⇒ 两端各缩成 `总宽/2`、中段宽 0 —— 逐句照
     `Image.GetAdjustedBorders`（**逐轴**、`rect.size < border.x + border.z` 时才缩），中段宽 0 时
     `localScale.x = 0`（零面积 ⇒ 画不出来），**⛔ 不用 `SetAspect(0)`**（那个会造**镜像 quad**）。
  5. **既有断言读数逐位不变**（静态核过）：两个宿主量 `Fill` 层的都是 `ImageQuad.WorldH` 的并集
     （`BattleScene.cs:9665-9674` / `SettingsScene.cs:3351-3360`），`WorldH` 我一个字没动；
     `SettingsScene.cs:3446-3450` 的端帽宽读的是 `WorldW`（**也不含缩放**）⇒ 值=1 那一帧实得仍是 **13.5**；
     队列那几条（`SettingsScene:3416-3432`）不动。`HasArt`（`_fillRoot.childCount > 0`）仍是 3。
  6. **公开行为面未变**：`Create` 签名 / `Contains` / `SetFromPointer` / `SetValue` / `LeftWorld` / `RightWorld` /
     `HandleHitPx` / `TrackWorldH` 全部原样；新增的三个只有**新**的只读 getter。
  7. ⚠️ **本件不裁切**（`MenuDraw.Nine` 的 `clip` 形参没传）：生产侧挂 `ViewportClip` 的只有 7 处滚动视口
     （`AvatarTab/CampaignTab/ShopWindow/PracticeModePopup/TutorialModePopup/LiveOpsEventWindow/TitleTab`），
     滑块两条父链都不在其中 ⇒ `Resolve` 解析不出裁切、不会与 `ClipNineChildren` 打架。
     （即便将来有，旧的整体缩放**同样**会打坏它 ⇒ 不是本次引入的新风险。）

  - **夹具**：`WfSlider.Create(...)` 探针（同 `Editor/BattleScene.cs:13423` 的 `A218Probe` 形状），
    战斗档 `trackW = 561.08 / trackH = 12 / capScale = 1 / handlePx = 34.406`，`SetValue(1f/0.5f/0.2f, fire:false)`。
  - **输入 / 期望（一律写字面量，⛔ 不引用 `WfSlider.*` 常量）**：

  - 🔴 **灭自证那一半**：① 断 **`FillCapWorldW` 在两个不同的值上【相等】** ——
