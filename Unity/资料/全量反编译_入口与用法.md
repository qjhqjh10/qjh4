## 二、怎么查（四条路，按常用度排）

```bash
# ① 「这个类/方法干什么」—— 按类名找文件，直接读
ls D:/2/tools/decomp_full | grep -i "<类名>"

# ② 「谁调用了它」（找触发点）—— 全目录 grep 方法名
grep -rl "<方法名>" D:/2/tools/decomp_full | head

# ③ 「这个字段是什么 / 在第几字节」—— 查 dump.cs（带偏移）
grep -n "<字段名>" D:/2/tools/il2cpp_out/dump.cs

# ④ 「这句字符串哪来的」
grep -a "<字符串>" D:/2/tools/all_strings.txt      # ⚠️ 必须 -a，文件被判成 binary
```

**命名规律**（从产物反推，用得上）：

| script.json 里的名字 | 产物文件名 |
|---|---|
| `类$$方法` | `类__方法.c` |
| `类.<状态机>d__25$$MoveNext` | `类._状态机_d__25__MoveNext.c` |
| `类.<方法>b__23_0`（闭包） | `类___方法_b__23_0.c` |

⚠️ **`<` / `>` 被换成 `_`**；`$$` 换成 `__`。**按 `script.json` 的名字直接拼文件名会拼错** —— 用 `ls | grep` 找。

## 四、两条判读前提（**不知道就会误判**）

1. 🔴 **`decomp_full` 是 Ghidra 的 C 风格伪码，不是可编译的 C#。** 它是**控制流 + 原版符号名 + 字段偏移**，
   用来**查证语义**，不能用来编译。
2. 🔴 **「grep 出 0 命中」≠「原版没有」** —— 一定要先确认**搜对了地方**：
   - `all_strings.txt` **必须 `grep -a`**（文件被判成 binary，不带 `-a` 会静默 0 命中）
   - 字符串表**只有字符串字面量、没有字段名** ⇒ 拿字段名搜它是**无效否定**
   - 嵌套类型的产物名与 `script.json` 的名字**拼法不同**（见 §二 的表）

照 `资料/反编译工具链_重建记录.md` 跑。要点：

- **别删 `D:/2/tools/ghidra_proj/`（2.6 GB）** —— 删了下次要**再花几小时**重新分析
- 复用工程：`-process GameAssembly.dll -noanalysis`（几分钟）

- 名单文件是「**十进制地址 ⇥ 名字**」，由 `工具/gen_ghidra_lists.py` 从 `script.json` 生成
- 🔴 **生成名单时别只提顶层类名** —— 2026-09-18 第一次全量就这么漏掉了**全部嵌套类型（7,536 个方法，占 29%）**，
  症状是 `grep -c MoveNext` = **0**。要连嵌套一起提（按「外层类名 + `.`」前缀匹配）。
- ⚠️ 产物文件数会**少于 `ok=` 的数**（重载/协程壳会撞名），**别拿文件数当成功率** —— 看 Ghidra 的 `DECOMP DONE ok=… fail=…`
