## 二、怎么查（四条路，按常用度排）

```bash
# ① 「这个类/方法干什么」—— 按类名找文件，直接读
ls D:/2/tools/decomp_full | grep -i "<类名>"

# ② 「谁调用了它」（找触发点）—— 全目录 grep 方法名
grep -rl "<方法名>" D:/2/tools/decomp_full | head

# ③ 「这个字段是什么 / 在第几字节」—— 查 dump.cs（带偏移）
grep -n "<字段名>" D:/2/tools/il2cpp_out/dump.cs

# ④ 「这句字符串哪来的」
grep -a "<字符串>" D:/2/tools/all_strings.txt      # ⚠️ 必须 -a，文件被判成 binary

# ⑤ 🆕 2026-09-29 「反编译里的 `DAT_184XXXXXX` 到底是哪个字符串」
#    反编译器把字面量**内联**进了 `.c`，方法体里只剩一个 `DAT_0x184XXXXXXXX` 地址 ⇒
#    `grep "Battle/Mulligan" decomp_full` 会**全空**（这正是过去几次「查不到」的真因）。
#    解在 `d:/2/tools/il2cpp_out/stringliteral.json`（地址 ⇥ 字符串字面量表，2.3 MB）。
PYTHONIOENCODING=utf-8 python -c "
import json,sys
t=json.load(open(r'd:/2/tools/il2cpp_out/stringliteral.json'))
d={int(e['address'],16): e['value'] for e in t}
for name in sys.argv[1:]:
    off=int(name.split('_')[1],16)-0x180000000
    print(name,'->',d.get(off,'（表里没有）'))
" DAT_184288d20 DAT_1842890f0
```
🔴 **换算规则：`DAT_0x184XXXXXX` = `0x180000000` + 表内 `address`**（`0x180000000` = 那个模块的 ImageBase；表里的
`address` 直接就是 RVA）。⚠️ **必须带 `PYTHONIOENCODING=utf-8`** —— 否则非 ASCII 词条会 `UnicodeEncodeError` 中断。
**实测（2026-09-29 本机复跑过，四条全中）**：`DAT_184288d20`=`Battle/Mulligan/Instructions` ·
`DAT_1842890f0`=`Battle/Mulligan/secondTurn` · `DAT_18428a128`=`Battle/Tips/GoFirst` · `DAT_184289000`=`Battle/Mulligan/WaitEnemy`
—— 这正是「换牌阶段那行『你先手/你后手』由 `MulliganManager.ActivateMulligan` 按先手二选一」的直证。
⚠️ 表里**只有字符串**：地址对不上 / 表里没有 ⇒ 那个 `DAT_` 不是字符串（可能是 float 常量，见
`资料/战斗规则与数值_出处.md` §三 从 `GameAssembly.dll` 读四字节那条路）。

✅ **2026-10-17 复核（`A1509③` 收口）：这两件工具已在仓里、现跑通过，⛔ 不用再「落地」一次。**

`PYTHONIOENCODING`。`script.json` 是 **127 MB**，`rva_of_method.py` 每次整读一遍（几秒）—— 查同一个类里的多个方法时，
**一次把关键词放宽**（加上类名前缀、多给几条 `limit`）比反复跑省时间。

**命名规律**（从产物反推，用得上）：

| script.json 里的名字 | 产物文件名 |
|---|---|
| `类$$方法` | `类__方法.c` |
| `类.<状态机>d__25$$MoveNext` | `类._状态机_d__25__MoveNext.c` |
| `类.<方法>b__23_0`（闭包） | `类___方法_b__23_0.c` |

⚠️ **`<` / `>` 被换成 `_`**；`$$` 换成 `__`。**按 `script.json` 的名字直接拼文件名会拼错** —— 用 `ls | grep` 找。

## 四、三条判读前提（**不知道就会误判**）

1. 🔴 **`decomp_full` 是 Ghidra 的 C 风格伪码，不是可编译的 C#。** 它是**控制流 + 原版符号名 + 字段偏移**，
   用来**查证语义**，不能用来编译。
2. 🔴 **「grep 出 0 命中」≠「原版没有」** —— 一定要先确认**搜对了地方**：
   - `all_strings.txt` **必须 `grep -a`**（文件被判成 binary，不带 `-a` 会静默 0 命中）
   - 字符串表**只有字符串字面量、没有字段名** ⇒ 拿字段名搜它是**无效否定**
   - 嵌套类型的产物名与 `script.json` 的名字**拼法不同**（见 §二 的表）
   - 🆕 🔴 **而且「grep 出 0 命中」≠「没有代码在做这件事」** —— 2026-10-05 实测：`"debug_buttons"` 在
     `decomp_full` 里**确实 0 命中**，据此写了「没有任何脚本在关它」；**实际有**（`MissionDebugButtons.Setup()`
     = `gameObject.SetActive(false)`，而且**真会被调到**）。
     ⇒ **按名字 grep 只能证明「没人按名字找它」**；要判「有没有人关它」，得**认类**（`dump.cs` 的 `class` 行 + `Slot:` + `all_methods.txt` 的地址）。
3. 🆕 🔴 **多个 `.c` 内容与首行函数名完全相同 ≠ 导出事故，那是 IL2CPP 的【同体折叠（ICF）】**。
   **实测**：`MissionDebugButtons__Setup.c` 与另外 **15 个**文件**字节完全相同**、且首行函数名**都是
   `BattleAlliancePanel__CloseButtonClick`**（`HUDFPS__Awake` / `DebugAutoDisabler__OnEnable` / `BuildNumber__Awake` /
   `UICardInfoItem__Reset` / `BoundTooltipItem__HideTooltip` …）—— 全是「`gameObject.SetActive(false)`」这种**一行体**。
   ✅ **判法**：去 **`all_methods.txt`** 查那几个方法**是不是同一个地址**（那一族**共享 `5536896` = `0x547C80`**）。
   ⚠️ **为什么这条重要**：**它差点被当成噪声过滤掉** —— 少了这条，看的人会把「名字对不上的 `.c`」直接跳过，
   于是**又漏一次**（而它正好是一个悬案的答案）。

4. 🔴 **有些 `.c` 的【内容】与首行函数名对不上（符号错配）—— 不是 ICF、也查不到同一地址**。
   **2026-10-17 实测两处**：`WelcomePopup__OnClose.c` 的内容是 `TutorialTipScript__StopTipPermanent`；
   `PlayerDataManager__CheckShowRateGame.c` 的内容是 `NetworkingPeer__OnMessage`。
   ⇒ **受影响的结论只能写成「在这份语料里搜不到」**，⛔ **不能写成「原版没有调用点」**
   （反例：`Tutorial Message Window PopUp` 的旧记录「反编译里没有调用点」就是被这一条坑掉的 —— 实际调用点在
   `TutorialManager__ShowTutorialMessageWindow.c`）。
   出处 = `资料/普查产出_1017/UI/R2_暂缓批复核.md` §六·5。

照 `资料/反编译工具链_重建记录.md` 跑。要点：

- **别删 `D:/2/tools/ghidra_proj/`（2.6 GB）** —— 删了下次要**再花几小时**重新分析
- 复用工程：`-process GameAssembly.dll -noanalysis`（几分钟）
- 跑之前先 `export JAVA_HOME="D:\\2\\tools\\jdk-21.0.12.1+1"`（不设会报 `The 'java' command could not be found`）
- 名单文件是「**十进制地址 ⇥ 名字**」，由 `工具/gen_ghidra_lists.py` 从 `script.json` 生成
- 🔴 **生成名单时别只提顶层类名** —— 2026-09-18 第一次全量就这么漏掉了**全部嵌套类型（7,536 个方法，占 29%）**，
  症状是 `grep -c MoveNext` = **0**。要连嵌套一起提（按「外层类名 + `.`」前缀匹配）。

**三条使用纪律**：
1. **一个文件可能有多个顶层类型**（`MissionEvent.cs` 同时有 `MissionEvent` 和 `MissionEvent<TS,TD>`）⇒ 按名找方法前，**同文件内所有顶层类型一起扫**。
2. **名字被 IL2CPP 转义**：`_003C_`=`<` · `_003E_`=`>` · `_007C_`=`|` ⇒ 先反转义再比对。
3. 🔴 **Cpp2IL 会「静默丢体」**（给 `{ }` 且零 note，但机器码里真有逻辑）⇒ 凡「Cpp2IL 说空」，**一律用 RVA 复核**：
   **`RVA 0x4B33B0` = 全局共享空方法桩**（机器码 `c2 00 00` = `ret 0`，`dump.cs` 里被 **1,815 处** `// RVA:` 引用）⇒ 「原版这方法是空的」**可以直接问二进制，不用推理**。

## 🔑 VA 反汇编的两把通用钥匙（2026-10-25 R7 实证，9 个印证点全自洽）

> 遇到 `FUN_1800021F0(idx, iface, obj)` / `FUN_1803F17A0(obj, iface, idx)` 这类**接口分派**、或 `[klass+0xNNN]` 这类**虚方法槽**，不用猜 —— 查下面两张表就定名。

### 钥匙 1 · 接口分派的 `idx` = `dump.cs` 里的 `Slot:` 列

拿到 `idx` 直接去 `D:/2/tools/il2cpp_out/dump.cs` 找该接口成员的 `Slot:` 值。
本轮印证：`1=Initialize` · `3=Dispose` · `7=ResetEventProgress` · `10=TryScheduleHandlerRefresh` · `13=ToggleEventActivation` · `15=GetBaseData` · `16=GetBaseSave` · `18=GetEndDate` · `21=get_Priority` · `27=GetEvents`。

### 钥匙 2 · `klass` 的 vtable 基址 `0x138`、槽宽 `0x10`

`[klass + 0xNNN]` ⇒ 虚方法号 = `(0xNNN − 0x138) / 0x10` ⇒ 再去 `dump.cs` 按 `Slot:` 定名。
本轮印证：`0x278`=20=`HandlerKey` · `0x2B8`=24=`BeforeRefresh` · `0x2C8`=25 · `0x298`=22 · `0x3F8`=44=`LoadEventData` · `0x2E8/0x2F0`=**vtable[27] 的 `{methodPtr, methodInfo}`**。

### 四条配套纪律（踩过）

1. ⛔ **别用 cpp2il 的成员排序推接口槽序** —— 它是重排过的；**只认 `dump.cs` 的 `Slot:`**。
