## 〇、先纠正一个坑：`CardsHorizontalLayout` 有**两份**实例，别拿错

同一个场景 `07_场景/battlearena1/MonoBehaviour/` 下有两份，字段名一样、值完全不同：

| | **MB 5271（权威）** | MB 4053（本文件原先引的） |
|---|---|---|
| 挂在 | GO 1192 | GO 58 |
| `m_scale` | **0.73** → 卡正好 165×263 px | 0.54 |
| `m_betweenElementsSpacing` | **1.45**（世界单位）→ 0.95 卡宽，牌几乎挨着 | 0.6 |
| `m_verticalOffsetLookTo` | **−330**（负的，和 Tooltip "Should be negative" 对得上） | 74.5（正的，自相矛盾） |
| `m_maxHeight` | **0.70**（正） | −0.78 |
| `m_numberOfCardsForMaxHeight` | **12** | 10 |
| `m_maxLayoutSize` / 小屏 | 0.59 / 0.51 | 0.51 / 0.51 |

**怎么判定 5271 才是权威的**（三条互相独立、都对得上）：

1. `0.73 × 2DCard 宽 2.0927 × 108 px/单位 = 165 px` —— 和 `d:/warpforge/scripts/battle.gd`
   里独立量出来的「原版手牌卡 165×263」**完全一致**；4053 的 0.54 算不出这个数。
2. `m_verticalOffsetLookTo` 的 Tooltip 写着 **"Should be negative"**，只有 5271 是负的。
3. 把 4053 的 `spacing=0.6` 和 `maxLayoutSize=0.51` 放一起会**自相矛盾**（单张间距 > 整把牌上限）；
   5271 的 1.45 / 0.59 在「都是可见宽比例」的读法下自洽，且 `n=8` 起压缩、`n=12` 弧高拉满，
   两个阈值都落在合理区间。

> 4053 不是垃圾数据，它是**另一套预设**（可能是小屏档或旧版本）。要引就引 5271。

### `m_yAxisCurve` 的 5 个关键帧（照抄进 `AnimationCurve`）

```
time      value     归一化(值域 -3.392..+0.011 → 0..1)
-0.010   -3.392     0.000
 0.133   -2.261     0.333
 0.485   +0.011     1.000
 0.884   -2.370     0.301
 1.000   -3.385     0.002
```

**形状不是抛物线** —— 头 13% 就升到 1/3 高度，中段是**平台**，两端陡降（`HandLayout` 照这条实现）。

> 可以用 Unity 原生 `AnimationCurve` 字段直接存这 5 个关键帧（含 inSlope/outSlope，原始 JSON 里都有）。

```
isWeaponSetup               0                武器位布局（未启用）
```

### 三条可直接照搬的结论

1. **槽位是等距的**：玩家侧 x = ±3 / ±6 / ±9 /（±12），间距 3.0。
2. **敌方镜像**（敌方 `leftSlotPosNormal` 是 +x）—— 我们开 `BoardLayout.mirror`。
3. **缩放不一样**（0.36 vs 0.69）：那是 3D 战场的**透视补偿**（敌方棋盘更远），
   在正交 2D 布局里**不适用**，两边应该同尺寸。

> ⚠️ 原版是 **3D 战场**（单位站在地板上，相机有透视），我的是**正交 2D**。
> 所以 `y` 坐标（-0.6 / 5.0）和缩放差不能照搬，**能照搬的是「等距 3.0」「镜像」这两条结构**。

### 施工时新踩到的三个坑（原方案没预见到）

1. ~~**手牌卡比原版矮、比原版宽**~~ ✅ **2026-09-12 解决了**。原版卡本体是
   **2.0927×3.3313**（比例 0.628），当时我们自己挑了 1.45×2.03（0.714）。按宽度对齐（165 px）
   之后卡就矮了 12%，于是**满手 12 张时中间那条弧会盖住前排督军卡底部的数值**。
   当时的解法是「两行棋盘整体上移 0.05（54 px）」——**那是个补丁，现在撤了**：
   `CardView.Width/Height` 改成 2.0927×3.3313（出处 `子代理读报_2dcard_0827.md` 的
   `2DCard (GO 1075, RT 2876, size 2.0927×3.3313)`），贴图缓冲 256×371 → **256×407**，
   两行回到原版的 0.3444 / 0.5685、手牌行回到 0.1204。
   现在场卡 **137.2×218.4**、手牌 **165.0×262.7**，都是精确值（`BattleScene.Run` 里逐条断言）。
   ⚠️ 按原版数值摆，**手牌卡底会出屏 1 px（1081.3）**、中列卡会探进前排下方 ~30 px —— **原版就是这样**，
   所以那两条断言改成「和原版几何对账」而不是「绝对不许碰」。
2. **相机的宽高比必须在建东西之前定死**：`HUD 文字` / `格位底片` / `槽带` 都是**建的时候算一次**
   世界坐标，而 `LayoutSpace.VisibleWidth` 跟着 `cam.aspect` 走。批处理下相机默认是 **4:3** ——
   建完再拍 16:9，HUD 会整片偏左（本次真踩到，ENERGY 那行跑到手牌底下去）。
   解法：`BuildScene` 里 `LayoutSpace.Apply` 之后立刻 `cam.aspect = DesignAspect`；
   另外 `BattleDriver` 每帧查一次可见宽，变了就 `ReanchorHud()` + 重摆底片。
3. **牌挨得近之后，命中测试会命中「压在上面」的邻牌**：原版间距是 0.95 卡宽（牌几乎挨着、
   左右各压一点），所以点在 X 的牌上可能选到 X−1 —— 这本身是对的（原版 `useZOrder` 就是
   「左卡压右卡」）。但 `CardBaseDemo` 里「悬停第 6 张」的用例是按**不重叠**写的，
   现在必须拿「露出来的那半边」去点。

## 八、还没搞清楚的

- ~~`m_verticalOffsetLookTo = 74.5` 怎么用~~ → **已解决**：权威实例 5271 上是 **−330（世界单位）**，
  负号和 Tooltip 对得上。含义是「卡看向手牌**下方** 330 单位处的一点」→ 顶边朝外撇。
  换算：`330 × 14.835 px/单位 ÷ 108 px/单位 = 45.33`（我这套的世界单位）。
- ~~压缩阈值~~ → **已解决**：`n × 1.45 > maxLayoutSize(0.59 + 宽高比修正)` 就压缩，`n=8` 起触发，
  和 `m_numberOfCardsForMaxHeight = 12` 是同一档。注意原版**除 n 不除 n−1**。
- ~~`Z_OFFSET_BY_POSITION_INDEX` 的具体值~~ → 序列化数据里没有，自定 `0.004`（量级很小）。
- **剩下的真未知**：`m_elemetsParent` 指向的父节点带什么变换（原版手牌是 3D 的，父节点有旋转），
  以及 `allowSelectCardLayoutOverFlow`（让位时要不要考虑上限）没做 —— 现在让位是「先让出去，
  再按同一套公式重排」，没有溢出分支。
