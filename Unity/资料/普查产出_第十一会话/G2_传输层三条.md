### 二·二 `A1268` —— `Setup` 不停旧读线程 ✅ 做完

| 项 | 内容 |
|---|---|
| **我方现状（改前）** | `Setup`（改前 `:263-285`）只 `old.Close()`，**不打断旧 `ReadLoop`**；旧读线程拿的还是**旧** `_stream`，旧 socket 一关它就 `Fail` ⇒ `Publish(connected:false)` + `_peerLost = true` 打在**共享**状态字上 |
| **判据** | `F5` §三 C · 候选 (iii)：那一句若落在 `Setup` 的 `Publish(true)` **之后**，**活着的新连接**就被标成「掉了」；`F5` 明说它**解释不了丢帧** ⇒ 独立一笔 |
| **实现形状** | 给连接编【代】：`int _gen`（`:82`），`Setup` **第一句**就 `Interlocked.Increment`（`:312`，⚠️ **在 `old.Close()` 之前** —— 那一下正是唤醒旧线程的动作）；`ReadLoop(gen, st)` 按值拿到「哪一代 / 哪条流」（`:352`），循环条件 `gen == _gen` 为假就退出（`:358`）；`Fail(int gen, string why)`（`:394`）里 `gen != _gen` ⇒ **一个字都不改共享状态**、只如实记一笔「旧读线程退出了」。 |
| **两道闸都要有** | `ReadLoop` 那道管「别再读旧流」；`Fail` 那道管「别改共享状态」。删任一道，另一道都堵不住（自检 R⑤~R⑨ 钉的是第二道）。 |
| **会不会影响既有行为** | ① **正常路径零变化**：单连接时 `gen` 从不变化，`Fail` 走的分支与改前逐字相同。② **重连路径变好了**：`Setup` 之后旧线程的迟到 `Fail` 不再把新连接标成掉线（这正是本账要的）。③ **一处「少了」的**：旧线程退出**不再**冒充「真掉线」—— 它改走 `Debug.Log`（信息级）+ 明确文案。这不影响任何会判状态的消费方（`PeerLost` / `IsConnected` 该怎样还怎样）。 |
| **⚠️ 断言为什么是「结构性」的** | 「旧读线程迟到的 `Fail` 打在新连接上」那个交错是**微秒级、而且不可控**（唤醒旧线程的是 `old.Close()`，醒来时机归 OS 调度）⇒ 拿真 socket 跑一万次也撞不稳，写成行为断言只会是「**永远绿（或永远红）的假断言**」（同 `NetSelfTest` §O 的 `_state`、§P 的 `ScriptedTransport` 那两条的理由）。所以加了两个 `ForTest` 口（`:137` `GenerationForTest` · `:148` `FailForTest(generation, why)`），把「哪一代」**当参数摆出来** ⇒ 那个交错**每次都必现**。⚠️ 两个口**生产路径一处都不调**（与 `NetSession.SetClockForTest` / `SinceLastRecvMsForTest` 同族）。 |

### 抓日志的手法

沿用本仓**现成**的那一套 —— `Application.logMessageReceived` + `(cond, stack, LogType)` 过滤
（先例：`Editor/BattleScene.cs:3614` 那族的 `hWarn` / `hTy` 写法，都是批处理下跑绿的宿主）。
⚠️ 它能用是因为 `Fail` 那条话是**主线程**打的（`Pump` 里）⇒ 回调**同步**到达；
若哪天把打印挪回后台线程，这套抓法就作废（所以 §二·一 那条「不在 `Fail` 里直接 `Debug.Log`」是**硬约束**）。

### 没写出来的断言（差什么）

**没有**「用真 socket 让旧读线程自然迟到」的那条 —— ⛔ **写不出来**，不是没写：
那个交错的量级是微秒、且唤醒时机归 OS 调度，**没有可注入的挂点**就不可能稳定复现
（这正好是本工程已经立过的规矩：「写成行为断言只会是永远绿的假断言，比没有更糟」）。
⇒ 用 `FailForTest(generation, …)` 把「哪一代」摆出来是**唯一**有鉴别力的写法，理由已写进代码注释。

## 五、🔑 `A1267` 的日志有没有让 X2 变得可查？—— **有，而且给出了一个「一眼判别」的签名**

**先看签名**：新那行日志与 `NetSession` 那行状态字落在**同一个 `Pump()`** 里，而且**紧挨着**

```

[Net] WaitingReconnect：对手掉线了，正在等他回来…   ← 原来就有（F5 E3 那一行）
```

⇒ **下次怎么看**（`netbattle.log` 里 grep `传输层掉线：原因 =`）：

| 日志里那句「原因」 | = `Fail` 的哪一个调用点 | 对 X2 的含义 |
|---|---|---|
| `对面关掉了连接`（`St/PeerClosed`） | `ReadLoop` `ReadFull(...) <= 0`（`NetTransport.cs:363`/`:371`） | **优雅 FIN** ⇒ `bye` 是在 **FIN 之前**就丢的 ⇒ **不是**候选 (i)（abortive close 丢接收队列），而是「**写成功但没上线**」那一档 |
| `读取中断：…`（`St/ReadAbort`） | `ReadLoop` 的 `catch`（`:362`/`:370`） | **abortive** —— 消息里会带 `ECONNRESET` / 「连接被重置」/「forcibly closed」之类字样 ⇒ **候选 (i) 成立**（收到 RST 时把还没被应用读走的 `bye` 一起丢了） |
| `发送失败：…`（`St/SendFailed`） | `Send` 的 `catch`（`:393`） | 🔴 **读线程当时还活着**，是**写**先失败的 ⇒ 客机那一侧根本没把 `bye` 写上线（去查客机日志里 `在**传输层报失败了**` / `**没发出去**` 那两条告警） |
| `帧长度不合理` / `收到的帧解不出信封` | `ReadLoop`（`:366`/`:374`） | 对面发的东西不是本协议的帧 ⇒ 另一档（协议/版本） |

**另外两条现在也各自有了唯一的签名**：
- `[Net] 旧连接的读线程退出了（原因：…）—— 它属于第 N 代连接、当前是第 M 代`（**`Debug.Log`**）

- 那行「传输层掉线」**只会在真掉线时出现一次**（本机主动收工那一档**不出声**，`R⑭` 钉着）
