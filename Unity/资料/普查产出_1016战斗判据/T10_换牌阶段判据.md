### `A1668` —— 换牌期「点到哪张卡」两条命中规则合一

**原版行为**
- 换牌期每张手卡的碰撞体是**开着且原始尺寸**的：`CardCollider2D__SetColliderNotInHand.c:11-24`（`SetColliderNotInHand`）—— 那张牌就是**给点着看的**（R2 §交互，`资料/普查产出_第二十五会话/R2_原版换牌规格.md`）。
- 「点到哪一张」这件事原版**不自己排序**：它交给命中的**那一个**。`BattleManager__GetTargetInPos.c:104` 一句 `Physics2D.GetRayIntersectionNonAlloc(...)`，随后 `:105-130` **只取数组第 [0] 项**（`*(longlong *)(param_1 + 0x340)` 那个预分配 `RaycastHit2D[]`，读 `+0x20/+0x28/+0x30` = 元素 0），**没有任何排序/比较**。即：**"谁最先被物理层返回就用谁"**。
- 🔴 **换牌那一行本身不重叠**：布局实例 `MB_4881` 的 `m_useRotation = 0`、`m_yAxisCurve` 平线 0（`手牌布局_原版算法与参数.md` §五）⇒ 一条**完全平直的横排**；间距（414 或 502.2）**大于**卡宽（292 或 383.8）⇒ **相邻卡不相交**。⇒ 「索引序」与「最前序」**在换牌期结果必然相同**。
- 真正会分叉的只有**我方手牌那个扇形**（重叠区），而那一档原版走的也是同一条"物理最先返回"的路。

**我们现状**
- `Battle/MulliganPanel.cs:758-763` `CardAt` —— 按 `_cards` **下标递增**取第一个 `Contains` 命中（注释自陈"重叠处取【下标最小】的那张"）。
- `Hand/CardInteraction.cs:633-645` `HitTest` —— 取 **z 最小（最前）**（`if (z < bestZ)`）。

**差异**
- 两处**不是同一条规则**（一处下标序、一处 z 序）。换牌行上等价（不重叠）；扇形手牌上才分叉 —— 但那一档不在换牌期。
- 原版在"重叠"这一档上其实是**委托给物理层**（无显式规则），我们要挑一个：z 最小（离相机最近）是原版"最近优先"的对应物，也是本仓已有读法。

**怎么改**
- 把 `MulliganPanel.CardAt` 收成与 `CardInteraction.HitTest` **同一条**（取 z 最小），或抽一个共用静态口（例如 `CardHitTesting.Frontmost(cards, world)`），两处都调它。**风险极低**（换牌行不重叠 ⇒ 行为零变化，只满足"一条规则只写一处"）。
- 落点：`Battle/MulliganPanel.cs:758-763`；顺带在 `Hand/CardInteraction.cs:633-645` 改调同一口。
- ⚠️ 不必照原版那条"物理层说了算"实现（那正是本仓已知偏离：我们没有 collider/射线层，见 `C3` 结构差异 #5）—— 只需**两处一致**。

### `A1749` —— 选牌面板 `scale` 到底怎么读（**裁定：选牌不偏大，两扇面板运行期输出本来就不同**）

**原版行为（分三层讲）**

1. `m_scale`（`dump.cs:112196` `CardsHorizontalLayout` 的 `+0x78`）**是卡片的 localScale 乘子，不是 px** —— 判据 = `CardScript__GetCardInHandScale.c`：`fVar1 = layout.m_scale`，返回 `Vector3.one × fVar1`（那个基向量取 `DAT_1842da2a8 + 0xb8` 指向的 `+0xc/+0x10/+0x14`，即 Unity `Vector3` 静态块里的 **`one`**，紧邻的 `+0x18` 就是 `up`，见 `CardScript__TryDraggingFromHand.c:49-50`）。⇒ 用户 2026-10-13 那句「**这里可能是比例**」**成立**。
2. 四份实例**同字段同单位、值不同**：我方 `MB_5271 = 0.73` · 敌方 `MB_4053 = 0.54` · 选牌 `MB_4052 = 183.41` · 换牌 `MB_4881 = 183.41`（`资料/手牌布局_原版算法与参数.md` §五，逐字段实读）。差 250 倍**不是单位不同** —— 是**卡的父链空间不同**：手牌卡的父 `HandArea` lossyScale ≈ 108（× pxPerWorld 14.835），选牌/换牌卡的父链在 Canvas 那侧（≈ 0.0674）；同一个乘子乘出来差 ≈148×。**选牌那一档恰好父链缩放 ×14.835 ≈ 1** ⇒ 于是 **`卡宽(px) = 卡本地宽 2.0927 × m_scale`** 在这个画布上**数值上成立**（2.0927 × 183.41 = **383.8 px**）。
3. 🔴🔴 **关键新判据（本轮找出，A1749 原文没引）**：原版**运行期探针**在**选牌**面板上**直接调** `CardsHorizontalLayout.GetPosition(i,n)`，量到 **n=2/3 的中心距 = 502.2 px**（把返回的世界坐标 ÷ `lossyScale 0.0674`）—— 出处 `d:/4/Unity/资料/原版参照图/Unity参照管线_0825/data/panel_0914b/报告.md:61-75`。⇒ **选牌那一行的间距 = 502.2（运行期实测）**，与序列化字段吻合。

**我们现状**
- 选牌：`Battle/CardChoicePanel.cs:128` `CardScale = 183.41f/108f` ⇒ 卡宽 `2.0927 × 183.41 = 383.8 px`（`Core/CardView.cs:223` `Width = 2.0927f`）；间距 `SpacingPx(n)`（`:114-121`，n≤3 = 502.2）。
- 换牌：`Battle/MulliganPanel.cs:351` `CardWidthPx = 292f` · `:356` `RowSpacingPx = 414f`（来源 = 用户实拍）。

**差异 / 裁定**
- **选牌 = 383.8 / 502.2 与原版 layout 字段 + 运行期探针**一致 ⇒ **不偏大**。原文那句「三张一行要 **2156 px 装不进 1920**」**不成立**：3 张 span = `2×502.2 + 383.8 = 1388 px < 1920`（即使 4 张 2008.8 也还在屏内、只是进压缩分支）。
- **换牌 = 292 / 414**（用户实拍）也**站得住**：本轮把那张实拍按 0.821 归一后复核，**眼钮 x（设计 184.45 → 帧 151.5，实测 153.5）与卡行中心 y（设计 511 → 帧 420，实测卡行中心 ≈424）都吻合**。
- 🔴 **两扇面板运行期的输出本来就不同**：选牌 = 502.2 px（运行期探针）· 换牌 ≈ 414 px（实拍）。**尽管 `MB_4052` 与 `MB_4881` 序列化字段逐字相同** —— 因为 `GetPosition` 的输出还依赖运行态的 `m_elemetsParent.lossyScale` / `m_calculatedMaxLayoutSize(+0x80)` / 压缩分支 / `BattleManager.MaxCardsInHand`（`CardsHorizontalLayout__GetPosition.c` 逐句）。⇒ **A1749 的隐含前提「同一个组件 ⇒ 同一个值」在运行期不成立**（这正是铁律 5·c 那一类）。

**怎么改**
- **选牌保持不动**（383.8 / 502.2 正确）· **换牌保持不动**（292 / 414 正确）—— **A1749 可结案**（"选牌偏大"的怀疑不成立）。
- 建议在 `Battle/CardChoicePanel.cs:123-128` 与 `Battle/MulliganPanel.cs:342-356` 各补一句："**两扇面板运行期输出不同（选牌 502.2 / 换牌 ≈414），不是同一个值**"，把来源与"运行期实测"分开标清。
- ⚠️ 唯一保留的疑问：换牌那个 414/292 **只来自视频实拍**（见 §三），未在真机复测 —— 若将来真机复测出别的值，**以真机为准**。
