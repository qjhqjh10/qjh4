## 一、实测：这 448 张的文本长什么样

数据源 `Unity/MyGame/Assets/RuleEngine/Resources/cards_engine.json`（`type == "tactic"`）。

| 量 | 数 | 说明 |
|---|---|---|
| 战术卡 | **448** | 另有单位 586 / 督军 56 / 防御 39，共 1129 |
| 分句（按 `.` 切） | **659** | 平均 1.47 句/张 |
| 单句卡 | 255 | |
| 多句卡 | **193（43%）** | 2 句 176 / 3 句 16 / 4 句 1 |
| **整条 desc 的唯一骨架** | **430 / 448** | 吃数字后仍几乎不重复 |

### 🔴 结论一：**模板匹配行不通**

430 条唯一骨架 / 448 张卡 —— 整条文本几乎没有重复。**别指望「覆盖 TOP-N 句型就拿下 80%」**。
覆盖只能靠**可组合的文法**：`动词 + 数值 + 载荷 + 目标 + 时长`，逐分句组合。
这正是 `_resolve_text` 的做法，也是我们要走的路。

### 分句级（659 条）首词分布

| 首词 | 数 | 占比 | 首词 | 数 | 占比 |
|---|---|---|---|---|---|
| `give` | 168 | 25.5% | `create` | 15 | 2.3% |
| `deal` | 82 | 12.4% | `destroy` | 12 | 1.8% |
| `if`（条件句） | 53 | 8.0% | `heal` | 11 | 1.7% |
| `choose` | 39 | 5.9% | `lower` | 11 | 1.7% |
| `draw` | 38 | 5.8% | `oath` | 10 | 1.5% |
| `ephemeral`（前导关键词） | 37 | 5.6% | `repeat` | 9 | 1.4% |
| `deploy` | 31 | 4.7% | `return` | 6 | 0.9% |
| `your`（`Your units/warlord…`） | 26 | 3.9% | `gain` | 6 | 0.9% |
| `for`（`for each/every`） | 24 | 3.6% | `it` | 5 | 0.8% |
| | | | `codex` | 5 | 0.8% |

前 2 个动词（`give` + `deal`）就占 **38%**；前 8 个覆盖 **约 78%**。
剩下的 22% 是长尾：`oath` / `codex` / `reanimate` / `talent:` / `pray:` 等**阵营专属机制**。

那些是**单位**的能力段落（走同一个解析器，但不是本轮战术卡的事）。

## 二、🔴 结论二：`give` 的载荷名字空间 = 关键词表

`give X to Y` 的分句有 **164 条**，`X` **去重后 78 个**：

| X | 出现 | X | 出现 |
|---|---|---|---|
| `+N`（攻击力） | 12 | `vulnerable N` | 4 |
| `N health` | 12 | `stealth` | 4 |
| `armour N` | 8 | `invulnerable` | 4 |
| `flank` | 6 | `N attack and N health` | 4 |
| `N [attack]` | 6 | `markerlight N` | 4 |
| `blast N` | 5 | …其余 66 个各 1–3 次 | |
| `shield` | 5 | | |

**这 78 个 X 几乎全是规则书里的关键词**（`Armour` / `Flank` / `Blast` / `Shield` / `Stealth` /
`Vulnerable` / `Invulnerable` / `Markerlight`…）。

> ⚠️ **战术卡这一轮和「关键词还差 48 个」是同一件事**，不是两件。
> `RuleCore.UnimplementedKeywords` 现在有 48 个没结算（全池 61 个，已实现 13 个）。
> 做 `give`/`lose`/`gain` 必然会碰到它们 —— **两边要一起推进，别各做各的**。

### 🔑 但真正高杠杆的不是那 78 个，是**一个函数**

原版把「给某单位加东西」收敛在**一处**：`rule_core.gd:_apply_gain`（`:3266`，70 行）+ 一张
**`GIVE_KW` 前缀表**（`:2408`，**54 条**）。`give` / `gain` / `lose` 全部走它，**不是 78 个独立实现**。

`_apply_gain` 做三件事：

1. **多属性拆分** —— 先按 `, ` 再按 ` and ` 递归拆
   （Autarch `"+1 melee, +1 ranged and +1 Health"` → 三段；`"Give -1 Attack and -1 Armor"` 同理）。
2. **关键词授予** —— 拿 `GIVE_KW` 做**前缀匹配**，命中就把 `kws[关键词] += 数值`（数值 = 文本里第一个数字，
   没有就 1）；`armour` / `shield` / `stun` 三个还要**同步状态字段**（`armor` / `shield=true` / `stun_turn`）。
3. **属性增减益** —— 一条正则吃下所有数值型载荷：
   `([+-]?\d+)\s+(ranged attack|attack|ranged|health|armor|melee|might|fist|strength)\b`
   → 加 `attack` / `health`（连带 `max_health`）/ `armor`（负值 clamp 0）/ `ranged_attack`。
   ⚠️ `might` / `fist` / `strength` 是**原版图标语义**，都归到 `attack`（注释里标了出处）。
4. **限时增益**登记进 `temp_buffs`（`{kind, name, val, end, src}`），回合结束按 `end` 移除。
   —— 这就是「`this turn` / `until your next turn`」那个时长修饰的落点。

### 🔴 结论三：覆盖率要报**两个数**，不是两个混在一起

原版自己是**两层分开**的，照抄这个结构：

| 层 | 原版叫什么 | 我们 | 含义 |
|---|---|---|---|
| **施加上** | `GIVE_KW`（54 条）+ 属性正则 | 要做 | 能不能把效果**记到单位身上** |
| **机制上** | `KW_IMPLEMENTED`（`:52`，**59 个**） | 现在只有 **13 个**（`CardDef.cs:175`） | 记上去之后**真的会不会生效** |

> **一个 `give Flank to a friendly troop`，如果 `Flank` 没有机制，这张卡「能打」但「没用」。**
> 那就是静默失败。所以自检必须分开报：
> **「文本能解析 N/448」** 和 **「载荷有机制 M/448」**，两个数都往上推才算数。
> 卡面打 `*` 的判据也必须同时看这两层。

## 三、规格书：`_resolve_text` 的 handler 顺序

来自 `rule_core.gd:2513` 的函数头注释 + 逐段注释实测（行号为该函数内偏移，`2513 + n`）：

```
顶层（整条 desc 扫，可提前 return）
  ① for each / for every / repeat   → _resolve_for_each       (:2524)
  ② "N Choose" 裸数字付费激活        (能量不够就不激活不结算)   (:2529)
  ③ repeat this effect              → _resolve_repeat         (:2542)
  ④ Choose a <X> from deck/hand/…   → _resolve_choose         (:2547)
  ⑤ "For the rest of this battle"   持久化注册                (:2552)
  ⑥ "Your next troop this turn costs N less"                  (:2559)
  ⑦ create（分句扫描，含条件 create）→ _create_card            (:2570)
  ⑧ Genomic Enhancement / Dark Pact 阵营专属池                 (:2618/:2632)

逐分句（顺序固定，见函数头）
  0)  条件伤害 "If it has X, deal N instead"                   (:2635)
  0b) "already had/has X → … instead"                          (:2652)
  1)  Deal N damage [+ and 连接句] [+ 条件/死亡回能]            (:2671)
  2)  Stun（含 "and Stun it" / "Stun N random enemies"）        (:2754)
  2b) Blind 失明（远程=0）                                      (:2786)
  3)  Destroy（Invulnerable 挡）                                (:2818)
  4)  Heal N（无目标=己方督军）                                  (:2839)
  5)  Draw N [+ 5a 定向翻找 / 5b 特定卡名]                       (:2863)
  7)  Return X to hand [+ 7a Reload Duty / 7b Lower cost / 7c cost less] (:2897)
  8)  Refill energy [+ 8a Faith / 8b N Energy]                  (:2952)
  9)  Deploy X（免费部署：指定卡名 / 牌库随机 N 单位）             (:2970)
  6)  Give X to Y（三种语序变体 + 时长修饰）                      (:3010)
  6b) Lose X（移除目标关键词）                                   (:3082)
  6c) Gain X（给己方全体/自身 + 主语捕获 + 裸数字=1 能量）          (:3101)
  Spirit Stones / Spend all your Spirit Stones                  (:3118/:3126)
```

⚠️ **注意 6 排在 9 后面**（不是数字序）—— 顺序是「先具体后一般」的试探顺序，**照抄别自作主张重排**。

### 语序变体（`give` 有三套，`L:3010` 起）

1. 常规：`Give <内容> to <目标>`
2. `Give to <目标> <内容>`（Enhanced Aggression 卡面原文）
3. `Give it <内容>` / `Give this unit <内容>`（无 `to`，when 总线文本）

时长修饰：`this turn` → 回合结束移除；`until your next turn` → 下回合开始移除。

## 四、移植策略

### 原则

1. **照 handler 顺序移植，不重排、不合并** —— 顺序本身是语义的一部分（先具体后一般）。
2. **解析与应用分开**：`_resolve_text` 是「边解析边改 ctx」，我们要 **`TryParse` → 一组 `EffectOp`**，
   再统一应用。理由：① 算覆盖率必须能「只解析、不动状态」；② 自检能只验解析结果。
3. **不许静默失败**：解析不出来 → `ErrUnimplemented` + 卡面打 `*`，自检里报「能解析 N/448」。
4. **原版那份卡专属 hack 要不要抄？** —— 抄，但**标注出处**。
   （`_resolve_text` 里有相当一部分是单卡特判：Amalia 的 "damage equal to your Faith"、
   Grim Resolve 的死亡回能、Lord of the Storm 的 and 连接句……）
   ⚠️ **先不抄**：等覆盖率量出来、确认哪几条 hack 对应多少张卡再决定 —— 别把沼泽整个搬过来。

### 度量：覆盖率就是进度条

自检里报 **「战术卡文本解析：能解析 N/448」**，分两档：
- **完全解析**（每个分句都被认领）—— 这个数是**验收标准**。
- **部分解析**（有分句落空）—— 单独报，因为「半懂的卡比不懂更危险」（会打一半效果）。

### 顺序（每步都要让 N 上升 + 加断言）

| 步 | 做什么 | 预期覆盖 |
|---|---|---|
| 1 | 骨架：分句器 + `EffectOp` + **覆盖率双计数器**（解析 / 机制）+ `deal` 一个 handler 打通全链路 | ~16% |
| 2 | **`_apply_gain` + `GIVE_KW` 那一层**（一次做完 `give`/`gain`/`lose` 的底座）+ 属性增减益 + 限时 `temp_buffs` | ~38%（give 全量） |
| 3 | `draw` / `heal` / `destroy` / `stun` / `deploy` | ~55% |
| 4 | `if` 条件句 / `for each` / `repeat` / `choose` | ~70% |
| 5 | `create` / `return` / `refill` / `lower` + 长尾阵营机制 | 尽量高 |
| 6 | **机制层**：按「哪些载荷出现得多」排序补 `KW_IMPLEMENTED`（59 个的名单在 `rule_core.gd:52`） | M/448 往上推 |

### 引擎侧要一起改的（`项目任务.md` 第九节列的另两条）

- `RuleEngine/Core/RuleCore.cs:204` —— 非单位卡直接 `ErrUnimplemented`，要给战术卡开两条路：
  「要不要选目标」（`EffectTargets.NeedsPick` 已有判据）。
- `RuleEngine/Data/DeckBuilder.cs:153` —— `type != "unit"` 就丢，改成「能解析才收」。
- `PlayCard`（`RuleCore.cs:217`）加战术卡分支：扣费 → 结算 → **进弃牌堆**。
  ⚠️ 保住 `CanPlayCard` 注释里那条「**先费用、后格位**」的顺序断言（`RuleCore.cs:206`）。
- 防御卡（39 张）：引擎里除了 `DeckRules` 的合法性校验**没有任何地方认识 `defence`**，本轮仍不做。
