## 四、期望值 vs 实测值

### 4.1 期望（**由原版字段 + 原版贴图算出来**）

原版混合式（`Sprites/Default`：`SrcAlpha OneMinusSrcAlpha`，`src.rgb = tex.rgb × _Color.rgb = 0`）：

```
out = dst × (1 − _Color.a × tex.a) = dst × (1 − 0.647 × tex.a)
```

整块矩形上的 alpha 均值：

| 映射 | `mean(tex.a)` | **线性压暗 = 0.647 × meanα** | 线性透过率 |
|---|---|---|---|
| **我们的（整张拉伸）** | **0.8778** | **56.8 %** | **0.4321** |
| 原版的（Sliced，border 7/0/7/9、PPUmult 14.7、spritePPU 100、refPPU 100） | 0.8302 | 53.7 % | 0.4629 |

（Sliced 的算法：border 换算成卡单位 = `7/14.7 = 0.4762`、`9/14.7 = 0.6122`、下 0 ⇒ 左右各 26.8 % 宽度、上 39.5 % 高度；
九宫格按面积加权 = `0.8302`。**这张贴图的上缘羽化带在原版里占了底板高度的 39.5 %，我们只占 ~22 %**。）

### 4.2 实测

**(a) 「只留这一层」那一帧**（`_tmp_view/cardbase/cardbase_probe_textbg_only.png`，1920×1080；我重新读图核对）

- 矩形内均值 **59.10**（= 日志里的 59.10，坐标对得上 ⇒ **主对话修好的 `LayerPxRect` 是对的**）。
- 同行（numpy row 440）边缘两侧相邻像素：外 **118** → 内 **76.5**（左缘）；内 **76.5** → 外 **128**（右缘）。
  换到**线性**空间求透过率：`lin(76.5)/lin(118) = 0.405`；`lin(76.5)/lin(128) = 0.340`。
  ⇒ 反推 `tex.a ≈ 0.92 ~ 1.02`，**期望值是 1.0**（即 `0.647 × 1`）。
  ⇒ **这一层的 alpha 确实原样生效了，而且（若有偏差）是「更暗一点」，不是「压得不够」**。
- 视觉佐证（我把那块裁出来看过）：羽化带在矩形**上缘**、宽度 ≈ 矩形的 **22 %** 高度（= 7/32） ⇒ **UV 方向与拉伸映射都对**。

**(b) 全卡开/关对比**（同一次 run，同一张卡、同一块矩形）

| 来源 | 底板**关** | 底板**开** | 净掉 |
|---|---|---|---|
| 探针 `[像素]` | **46.13** | **35.62** | **22.8 %** |
| 断言 ④（同一 run 里更早一次） | **59.6** | **51.9** | **12.8 %** |

**差在哪一步（把 12.8 % / 22.8 % 与 56.8 % 拆开）：**

1. **Linear 色彩空间压缩**：`ProjectSettings/ProjectSettings.asset:50 → m_ActiveColorSpace: 1`。α=0.647 的纯黑层，**sRGB 上看得见的掉幅只有 35~43 %**（基数越暗掉幅越大），**不是 65 %**。
2. **画在底板上方的层不被压暗**（原版同序：`CardFrame` / `Card Info` 都在它上面）。拿探针那次做线性分解：
   `Δ_linear = lin(46.13) − lin(35.62) = 0.02743 − 0.01729 = 0.01014`；
   而 `Δ = 0.647 × meanα × (底板上方那几层【透过】的光)` ⇒ **透过 = 0.01014 / 0.568 = 0.01784**（sRGB ≈ 36），
   则**上方那几层自己的光 = 0.02743 − 0.01784 = 0.00958**（sRGB ≈ 25）。
   ⇒ **像素的 65 % 来自底板之下（被压暗）、35 % 来自底板之上（不压暗）** ⇒ 净掉幅必然是 `0.65 × 56.8 % ≈ 37 %`（线性）≈ **22.8 %（sRGB）**。**算式闭合，与实测 22.8 % 逐位吻合。**
3. **断言那次为什么只有 12.8 %** ⇒ 见 §七②：同一块矩形在同一次 run 里测了两次，**读数不一样**（关：46.13 vs 59.6）⇒ 这个量**依赖测量时刻的场景状态**，不是一个稳定常量。

**结论**：`④` 量到的 12.8 % **不是「没画」也不是「压得不够」**，而是「**能被压暗的那 65 % 光 × 线性空间下 sRGB 的压缩**」。

## 五、④ / ④·b 两条断言该怎么判

### 5.1 `④` —— 错在**期望值的来路**，不在阈值本身

现文案：`掉 ≥ 25%　—— 原版 m_Color 的 α 0.647 按混合反推该掉 ≈ 65%`

- `≈65%` **只在线性空间里成立**，而本工程是 Linear ⇒ 印出来给人看的是 35~43 %。
- 更关键：**底板之上那几层不被压暗 ⇒ 全卡开/关的差值永远小于这一层自己的压暗量**，小多少**取决于这张卡被压暗的是多亮的东西**（本轮实测：关=46 / 开=36 时差 22.8 %；同一 run 里另一次 59.6/51.9 就差 12.8 %）。
  ⇒ **拿「全卡开/关的净掉幅」做固定阈值，从原理上就不会稳。**

**该怎么判（照原版判据）：**

> **把这一层【单独】渲两帧（其余卡层全关）——开 / 关，把两块读数换到【线性】空间比：
> `mean(lin(开)) / mean(lin(关))` 应当 = `1 − 0.647 × meanα`。
> 其中 `0.647` = 原版 Image 的 `m_Color.a`（资产字段），`meanα` = **原版那张 32×32 贴图**在这块 quad 上的 alpha 均值
> （拉伸映射 = **0.878** ⇒ 期望透过率 **0.432**；容差 ±0.06）。**

- 这条是**灭自证**的：期望值来自**原版字段 + 原版贴图资产**，不来自我们的代码——把 `TextBgAlpha` 连实现一起改回去，这条照样红。
- 方法上**不需要知道背景是什么**（开/关两帧的背景逐像素相同，比值天然把背景约掉）——这正是 `RenderPixels` 那条「同一个画面渲两次、只翻这一层」的本意，只是把**比值**从「sRGB 净掉幅」换成「**线性透过率**」即可。
- 现有探针已经产出过这一帧（`cardbase_probe_textbg_only.png`），把「只留这一层」那一步加上「再关一次、再渲一次」就是这条断言。

### 5.2 `④·b` —— **判据前提不成立**，建议删掉或改判

现文案：`底板矩形内 / 紧邻上方那一条（同宽、半高）的行均亮度比 < 0.8`。

- 实测 `pxUp` 在**左下半屏**：`pxIn` 的 y 是 559..726（1920×1080，原点左下），`pxUp = y 726..809.5`。
  按「卡在 (0,1.6,0)、卡高 3.3313 卡单位 = 360 px、底板上缘 y01 = 0.462」折算：
  **`pxUp` = 卡的 y01 `0.231 ~ 0.463` = 【立绘窗】**，而 `pxIn` = 卡的 y01 `0.462 ~ 0.928` = **文字板**。
- ⇒ 这条是拿**文字板**去和**它上面的插画**比亮度。实测 `内 51.9 / 上 32.1 = 1.617` —— **插画本来就比文字板暗**，与「底板有没有画」无关。
- **原版判据里没有「板 vs 板外一圈」这一条**；原版只描述「**一块黑底、α=0.647、盖在文字区**」。
  ⇒ **要么删掉**（§5.1 那条已经覆盖了），**要么改成**「同一像素、开/关两帧之比」（那就等于 `④`）。

### 5.3 一句提醒

⛔ **不要把阈值从 25 % 降到 10 %** —— 那只是把红抹平；`④` 该换的是**量法与期望值的来路**（§5.1），不是数字。

## 七、顺手发现（**只报，我没有改任何东西**）

① **真的偏离：原版 `m_Type = 1`(Sliced)，我们是整张拉伸。**
   - 判据：`MonoBehaviour_-2228335281872200768.json` 的 `m_Type = 1` + `Sprite/…` 的 `m_Border = {7,0,7,9}` + `m_PixelsPerUnitMultiplier = 14.7` + `m_PixelsToUnits = 100`。
   - 差别：**上缘那条羽化带在原版占底板高度的 39.5 %、我们只占 22 %**；整块 alpha 均值 0.8302 vs 0.8778（我们的平均值**更暗 3.7 个百分点**、但形状不对）。
   - 影响面：**所有 2D 卡面（手牌 / 放大窗 / 卡组编辑 / 收藏）**；不影响 `Big`/`Small` 两档的尺寸与位置。
   - 按铁律 11：**要复刻**，判据 = 上面四个字段；实现侧要动 `SpriteQuad`（现在 4 顶点、UV 拉满）或另给一个九宫格 mesh —— 属于改动，**本轮未做**。

② **`④` / `④·b` 量的那个「净掉幅」在同一次 run 里不可复现**（46.13 vs 59.6，同一矩形同一张卡）。
   ⇒ 这两条断言的**红/绿本身就不稳**；先按 §5.1 换成线性透过率再谈修。

③ **卡内所有层共用一个 `renderQueue`（探针实测 `3000`）**：`CardView.cs:722-727` 的 `StampQueue` 把**这张卡的 `_queue`** 刷给**每一层**，所以卡内层序**完全依赖「到相机的距离」排序**（本仓已记过的坑）。
   今天排出来是对的（底板的 bounds.center 在 y=−0.65，比 `art` 的中心低 ⇒ 距离更远 ⇒ 先画），
   **但这是「碰巧对」**：一旦相机相对卡的高度变了（比如卡在屏幕上方/下方时），`art`(不透明) 与 `textBg` 的相对顺序可能翻过来，那时底板会**整块被立绘吃掉**。
   ⚠️ 我只报现象，**没有量「多斜会翻」**（判据不好取，要跑真机）。
