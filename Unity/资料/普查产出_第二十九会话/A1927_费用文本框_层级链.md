## 四、`61.70` 与 `48.82` 的关系（是「父级的函数」还是「各写各的」？）

**两个数用两套不同的机制，锚点决定了哪一套** —— 逐位算式（全部可用 `menu_rect.rect_of` 的式子复现）：

```
Cost 的宽：aMax.x − aMin.x = 0.5 − 0.5 = 0      ⇒ 锚跨项 = 0 × 父宽
          ⇒ 宽 = m_SizeDelta.x × lossyScale = 48.8191 × 1 = 48.8191   ← 【绝对常量，与父无关】
Cost 的高：aMax.y − aMin.y = 0.888 − 0.112 = 0.776
          ⇒ 高 = 0.776 × 父高 + 0 = 0.776 × 61.70 = 47.8792          ← 【父级的函数】
居中：    ref_n.y = 0.112 + 0.776 × 0.5 = 0.5 恰好 = 父的竖向中心，ap = (0,0)
          ⇒ 框心 = 图心（与 DeckRuntime 注释里那句「四边等距内缩」一致）
```

`Cost Image` 的 `61.70` 自己**也是算出来的**（不是写死的）：
`(0.03,0)→(0.03,1)` + `sd.y = 6` ⇒ 高 = `1 × 55.70 + 6 = 61.70`；宽由 **`AspectRatioFitter`** 定：
同 GO 上 `m_AspectMode = 2`（**HeightControlsWidth**）、`m_AspectRatio = 1.0` ⇒ 宽 = 高 × 1.0 = 61.70。
（组件出处：`MonoBehaviour/MonoBehaviour_-1560527530319417564.json`；`Image` 是 `m_Type = 0(Simple)` ·
`m_PreserveAspect = 0` · sprite pid `-3526939114648998153`。）

⇒ **「48.82 与 61.70 的关系」= 宽方向「写死 48.82，比图窄 12.88」· 高方向「父高的 77.6%（= 图高的 77.6%）」。**
两种写法**都对**，各自都对得上读数（`(61.7−48.82)/2 = 6.44` 与 `(61.7−47.88)/2 = 6.91` = 四边等距内缩），
⛔ **不能只抄其中一个数就把另一个当「父级的函数」推**（高会随父变、宽不会）。

## 五、第 ④ 问：我们 `50 → 4.88` / `32 → 3.05` 的成因（算式 + 每一步出处）

### 5·1 `4.88` 与 `3.1255` 是怎么来的（纯折算）

调用点：`Deck/DeckRuntime.cs:1895` → `rowCntLb.SetAutoFitBox(U(48.82), U(47.88), 18f, 50f, 32f)`
（`U(px) = px/108`，`DeckRuntime.PxPerUnit = 108`）。

`Battle/Label.cs` 的 `SetAutoFitBox`（`:826`）里那三行的算式：

```
nomPx   = NominalPx()            = FontSizeToPx(cur) = cur × WorldGlyphPerFontSize × PxPerWorld   （Label.cs:940-943 / :667-669 / :1363）
        = cur × 0.0948 × 108     = cur × 10.2384
fontSizeMax = cur × (maxPx / nomPx) = cur × 50 / (cur × 10.2384) = 50 / 10.2384 = 4.88357          （Label.cs:907）
fontSizeMin = 18 / 10.2384 = 1.7581                                                                （Label.cs:908）
baseCur     = cur × (basePx / nomPx) = 32 / 10.2384 = 3.12549                                      （Label.cs:902 / :905）
```

🔑 **三个数都与 `cur`（调用方创建 label 时的标称字号）无关** —— 因为 `nomPx` 与 `maxPx/minPx/basePx`
**同一个量纲**、`cur` 在比式里约掉了。⇒ **`4.88` 与「框多大」也无关**，它只由「原版那两个数 + 本工程那条 px 口径」决定。

**反向自证**：交接文档记的「上限 **4.88**」与 `50 ÷ 4.88357` 逐位吻合（`50/4.88 = 10.2459`，与 `10.2384` 差 0.07%，
是断言里 `F2` 打印的取整）⇒ 说明 `WorldGlyphPerFontSize ≈ 0.0948` 这个常数在那次自检里就是真的。

### 5·2 `3.05` 是怎么来的（TMP 自己的自适应，**不是**我们写的）

TMP 本体源码（**本地就有**：`MyGame/Library/PackageCache/com.unity.ugui@27635d171b1a/Runtime/TMP/TextMeshPro.cs`；
我们用的是 **3D `TextMeshPro`**，见 `Core/TmpFont.cs:184 NewText` 的 `AddComponent<TextMeshPro>()`）：

| 步 | 出处 | 内容 |
|---|---|---|
| 起点 | `TextMeshPro.cs:2149-2150` | `m_fontSize = Clamp(m_fontSizeBase, m_fontSizeMin, m_fontSizeMax)` = `Clamp(3.1255, 1.758, 4.8836)` = **3.1255** |
| 可用高 | `:2022-2023` | `m_marginWidth/Height = rect.size − margin`；原版 `m_margin=(0,0,1.83,0)` ⇒ **原版可用高 = 47.88**（我们没写 margin ⇒ 同样 47.88） |
| 溢出判据 | `:3038 / :3044` | `textHeight = m_maxTextAscender − m_maxLineDescender`，**`textHeight > marginHeight + 0.0001` 就缩** |
| 缩小梯 | `:3075-3082` | `m_maxFontSize = m_fontSize`；`Δ = max((m_fontSize − m_minFontSize)/2, 0.05)`；`m_fontSize -= Δ`；**量化到 1/20** |
| 放大梯 | `:4138-4149` | `Δ = max((m_maxFontSize − m_fontSize)/2, 0.05)`；`m_fontSize += Δ`；**量化到 1/20**；`m_fontSize = min(…, m_fontSizeMax)` |
| 退出条件 | `:4138-4139` | `fontSizeDelta = m_maxFontSize − m_minFontSize` **不 > 0.051** 就停 |

**我们那颗 TMP 的度量**（`NotoSerifCJK-Regular SDF`，`faceInfo`：`pointSize 50` · `scale 0.9` ·
`ascentLine 57.55` · `descentLine −14.3` ⇒ **行盒 = 71.85/50 = 1.437 em**；出处
`assets_full/bundle_fonts_assets_all/MonoBehaviour/NotoSerifCJK-Regular SDF.json`）：

```
本地单位每 fontSize 的「1 em」= 0.1            ← TmpFont 实测（Core/TmpFont.cs:103-113：字形 0.0948 = 0.948 em、行盒 0.1437 = 1.437 em，两条互证）
textHeight(F) = 1.437 × 0.1 F = 0.1437 F  （本地单位）
框高（本地单位）= U(47.88) = 47.88 / 108 = 0.44333          ← Label.SetAutoFitBox 写进 sizeDelta.y（Label.cs:836-839）
⇒ 装得下的最大 F = 0.44333 / 0.1437 = 3.0853
```

**把上面那张梯子按 3.0853 手跑一遍**（这就是「为什么恰好是 3.05 而不是 3.10 或 3.00」）：

| 迭代 | 动作 | `m_fontSize` | `textHeight` | 结果 |
|---|---|---|---|---|
| 1 | 起点 | 3.1255 | 0.44915 > 0.44333 | **溢出** ⇒ 缩：Δ = max((3.1255−1.7581)/2, .05) = 0.6837 |
| 2 | 缩 | 2.4418 → 量化 **2.45** | 0.35206 | 装得下 ⇒ 涨：Δ = (3.1255−2.45)/2 = 0.33775 |
| 3 | 涨 | 2.7878 → **2.80** | 0.40236 | 装得下 ⇒ 涨：Δ = (3.1255−2.80)/2 = 0.16275 |
| 4 | 涨 | 2.9628 → **2.95** | 0.42392 | 装得下 ⇒ 涨：Δ = (3.1255−2.95)/2 = 0.08775 |
| 5 | 涨 | 3.0378 → **3.05** | 0.43829 | 装得下 ⇒ 涨：Δ = max((3.1255−3.05)/2, 0.05) = **0.05** |
| 6 | 涨 | 3.10 | 0.44547 > 0.44333 | **溢出** ⇒ 缩：Δ = max((3.10−3.05)/2, 0.05) = 0.05 |
| 7 | 缩 | **3.05** | 0.43829 | 装得下 ⇒ 退出：`m_maxFontSize − m_minFontSize = 3.10 − 3.05 = 0.05`，**不 > 0.051 ⇒ 停** |

⇒ **终值 `m_fontSize = 3.05`** —— 与实测的 `3.05` **逐位相同**（含 1/20 量化网格与 `0.051` 退出门槛）。
🔑 这条不只是「能解释」，而是**预测到了那个具体值**：`3.05` 落在 `[3.05, 3.10)` 这一格、
而 `3.0853` 的精确边界恰好在这个格内 ⇒ 说明「行盒 = 1.437 em、1 em = 0.1 F」这套度量是对的。

### 5·3 那**原版**为什么能停在 `50`？（本条的真正答案）

**原版那颗 TMP 的字体不是 Noto，是 `Pragati-Regular SDF`**（§二）。它的 `faceInfo`
（`assets_full/bundle_fonts_assets_all/MonoBehaviour/Pragati-Regular SDF.json`）：

```
pointSize 95 · scale 1.0 · ascentLine 70 · descentLine −20 ⇒ 行盒 = 90/95 = 0.9474 em
```

在原版那个「1 单位 = 1 画布 px」的空间里（即 `1 em ≈ fontSize px`，理由见下）：

```
F = 50  ⇒  textHeight = 0.9474 × 50 = 47.368 px  ≤  47.88 px（框高）  ⇒ 【装得下，不缩】
反过来算这框能装的最大值 = 47.88 / 0.9474 = 50.54 px  ⇒ 原版把 m_fontSizeMax 定在 50
                                                     = 「刚好卡在这个框的极限上」
```

🔑 **这就是「原版停在 50」的机制**：不是它「不想缩」，是**它的字体行盒矮**，`50` 这一步本来就没溢出。
⭐ 顺带**反证**了「原版 `1 em ≈ fontSize px`」这个前提（我没法直接观测原版渲染，只能这样推）：
**作者把框定成 `47.88`、同时把上限定成 `50`，两者恰好卡死在同一个极限上（差 0.51px）** ——
这是「上限 = 这个框能装的最大字号」的典型写法，而不是巧合。

### 5·4 两边并排（把两条链折到同一个尺度上比，**与缩放无关**）

「字的墨迹高 ÷ 框高」这个比值是**纯字体账**、与 px/世界单位都无关（TMP 的适配是**比大小**，全程用本地单位）：

```
我们（Noto 被行盒夹住 ⇒ 撑满行盒）:  墨迹/框 = (墨跡/em) ÷ (行盒/em)
                                     = 0.8217 ÷ 1.437 = 0.5718     ← 0.8217 = TmpFont 实测的拉丁大写比（0.0779/0.0948）
原版（Pragati，框没夹住 ⇒ 停在 50）: 墨迹/框 = (60/95) ÷ (90/95) = 0.6667
⇒ 我们 / 原版 = 0.858  ⇒  我们的数字【比原版小 ≈14%】
   （若改用 faceInfo 的 capLine 口径算我们那一侧：0.72/1.437 = 0.501 ⇒ 小 ≈25%；区间 14%~25%，
     差别来自「Noto-CJK 的拉丁数字墨迹」用实测 0.0779 还是 faceInfo 的 0.72 em —— 见 §七·③）
```

**绝对数（按本工程的 px 口径）**：我们收敛后标称 = `3.05 × 10.2384 = 31.23 px`，其中数字的**墨迹** ≈ `25.7 px`；
原版 `50` 那一档的数字墨迹 = `(60/95) × 50 = 31.58 px`。

### 🔴 **5·5 一条必须写下来的警告（铁律 5·c：一个值 ≠ 全部情况）**

> 「**原版在同一框里停在 `m_fontSizeMax`**」这句判据，用的是 **prefab 序列化字段 `m_fontSize = 50`**。
> **那个字段在自适应开着时不是运行期读数** —— TMP 每次重排都会先把它**重置**成
> `Clamp(m_fontSizeBase, min, max) = Clamp(32, 18, 50) = 32`（`TextMeshPro.cs:2149-2150`），
> 再跑那张梯子收敛。⇒ 序列化的 `50` = **作者当时烘进去的残值**，不等于运行期收敛值。
> ✅ 本报告给出的是**推导**（`Pragati` 下这框放到 `50` 不溢出 ⇒ 会停在 50），**不是观测**；
> 要坐实得在**原版运行期**读一次那颗 TMP 的 `m_fontSize`（§七·②）。

## 六、结论：`48.82 × 47.88` 能不能当「正确的具体大小」用？

**有条件能 —— 条件是「连同它的四个搭档一起用」，且不拿它当『字有多大』的尺子。** 逐条：

| 用法 | 能不能用 | 条件 / 判据 |
|---|---|---|
| 当**布局框**（喂 `SetAutoFitBox` 的前两个参数） | ✅ **能用** | 是 prefab 原始字段逐位重算出来的真值（§二、§三），且这一链**没有缩放帧**。 |
| 当**「宽」的常量** | ✅ **能用** | 宽是**绝对常量** `48.8191`（锚点在 x 上重合）⇒ 与父宽无关，照抄是对的。 |
| 当**「高」的常量** | ⚠️ **只能当「父高 61.7 时的结果」** | 高 = `0.776 × 父高`。原版**别的行高**下它不是 47.88 ⇒ 照抄常量之前先确认父高是 61.70。 |
| 当**「字该多大」的尺子** | ⛔ **不能用** | 框高 47.88 与渲染出来的墨迹（我们 ≈25.7px / 原版 ≈31.6px）**差一大截**；框只管「装得下装不下」。 |
| 当**「画面像不像」的判据** | ⛔ **不够** | 光有框，缺**字体（`Pragati`）+ `auto[18,50] base 32` + `margin.z 1.83` + `Center/Capline`** 这四样，画面就定不下来 —— 我们这次差的就是**字体**那一样。 |

### 🔴 对 `A1927` 那个「二选一」的裁定意见（**只给判据，不给「抹红」的建议**）

那条账写「两条硬判据只能满足一条：① 改字号上限折算 ② 承认框错、退回 61.7」。**本报告的证据否掉这个二选一**：

1. **框没错** —— `48.82 × 47.88` 是原版原文（§二），退回 `61.7` 是**把对的改回错的**。
2. **上限折算没错** —— `50 → 4.88` 是本工程唯一的 px 口径（§5·1），改它要连 41 个调用点一起改，而它本身自洽。
3. **真正缺的是「字体」** —— 原版这颗 TMP 的 `m_fontAsset = Pragati-Regular SDF`；
   我们**全仓只有 `NotoSerifCJK`**（`Core/TmpFont.cs:31 ResourcePath` 是唯一入口，`Label` 全走它）。
   ⇒ TMP 被 `Noto` 的 **1.437 em** 行盒夹住才落到 `3.05`；换成 `Pragati`（0.947 em）后，
   **同一个框、同一组 `[18,50]/32`** 就会停在 `50`（§5·3）⇒ **两条判据能同时满足，不需要动框，也不需要动上限。**

⇒ 建议的下一步判据链（**执行由主对话定**）：
- `A1024`（按用途选字体）是这条账的**上游**；在它落地前，`DeckScene` 的 `A1735⑥`
  （`tmp.fontSize >= tmp.fontSizeMax − 0.01`）**判的是一个「字体对了才成立」的性质** ⇒
  它今天红/绿都说明不了「符不符合原版」，**该断的是「渲染墨迹 ÷ 框高」这个与缩放无关的比值**（§5·4）。
- ⛔ 不采纳的两条：把 `maxPx` 改大（`>50` 就是发明原版没有的值）· 把框退回 `61.7`（§三已证 61.7 是**费用图**的框）。
